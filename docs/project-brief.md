# 项目简报: He-API

> **China LLMs for the World** —— 中国大模型出海的合规桥梁

---

## 执行摘要

He-API 是一个**面向海外开发者的中国大模型 API 聚合网关 + Web 控制台**，通过 OpenAI 兼容协议与统一计费、合规及智能路由能力，让全球开发者在 5 分钟内零障碍调用通义、DeepSeek、Kimi、GLM、豆包、文心等中国一线大模型。

我们要解决的核心问题是：**中国大模型能力已具备国际竞争力，但海外开发者因注册门槛（手机号/银行卡/实名）、纯中文界面、RMB-only 计费及陌生的中国合规边界而被挡在门外**。目标市场是全球独立开发者、AI SaaS 中小团队、研究/采购决策者，以及出海中国企业的海外子公司。

核心价值主张：**邮箱注册即用、多币种多通道计费（USD/Stripe/PayPal + 支付宝/微信支付 + 加密货币）、多语言体验（i18n）、OpenAI 协议兼容、智能路由+合规即服务**——把"中国一线大模型"打包成海外开发者熟悉的 SaaS 形态。

---

## 问题陈述

### 当前状态与痛点

中国大模型（DeepSeek-V3、Qwen2.5、Kimi K1.5、GLM-4、豆包、文心 4.0 等）在多项 benchmark 上已逼近或超越 GPT-4 / Claude，且推理成本低 5-10 倍。然而对于一个想用上这些模型的海外开发者，路径上有 5 道墙：

1. **注册墙**: 国内厂商控制台普遍要求中国大陆手机号、身份证或企业营业执照；外籍个人几乎无法完成注册。
2. **语言墙**: 控制台、API 文档、错误信息、客服支持基本仅有中文；少数厂商提供的英文文档严重滞后或不完整。
3. **计费墙**: 仅支持人民币、支付宝/微信/对公转账；不接受 Stripe / PayPal / 信用卡 / 加密货币——海外开发者无可用通道。
4. **合规认知墙**: 海外开发者不熟悉 ICP 备案、算法备案、生成式 AI 备案、数据出境管理、敏感词治理等规则，自行接入易踩雷。
5. **生态墙**: OpenRouter、LiteLLM、Helicone、Together.ai 等海外 LLM 网关聚焦 OpenAI/Anthropic/Meta/Mistral，对中国模型支持薄弱、价格高、无中国厂商关系沉淀。

### 影响量化（基于公开数据假设，**置信度: 中**）

- 海外有 **2,800 万+** 注册开发者（GitHub 2024 年度数据），其中调用 LLM API 构建产品的开发者保守估计 ≥ 500 万。
- 中美 LLM 推理价格差: 同等质量层级 Qwen-Max / DeepSeek-V3 比 GPT-4o 便宜 60-80%；意味着海外开发者每月支付的 OpenAI 账单中，30-50% 是可被替代的"质量过剩"消费。
- 现有海外聚合平台对中国模型的覆盖率 < 10%，且接入即过期、限流严重。

### 现有方案为何不够

| 替代方案 | 缺陷 |
|---|---|
| 海外开发者直接接入中国厂商 | 注册/支付/语言/合规 4 道墙，几乎走不通 |
| OpenRouter / LiteLLM / Helicone | 专注欧美模型，中国模型支持薄弱、不稳定、无合规层 |
| One-API / NewAPI 等开源项目 | 是开源工具不是 SaaS，无产品化海外服务、无 SLA、无支付通道 |
| 中国 LLM 厂商各自出海 | 各家分散，开发者要分别注册/计费/集成，无统一协议、无横向对比 |

### 紧迫性

中国大模型能力的国际化窗口期已经打开（DeepSeek 在 2025 年初引爆全球关注），但海外尚无产品化的"一站式中国 LLM SaaS"。**先发者将占据"中国模型海外网关"的事实标准位置**——类比 Stripe 之于支付、Cloudflare 之于 CDN。

---

## 解决方案

### 核心理念

构建一个**位于中国境内、面向海外的合规网关层**：海外开发者通过统一的 OpenAI 兼容端点 (`/v1/chat/completions`) 调用，请求由 He-API 路由到背后已完成所有中国合规接入工作的多家国产大模型。

### 7 大差异化卖点

1. **海外友好注册**: 邮箱 + OAuth (Google/GitHub) 即可，免国内手机号、免银行卡、免实名认证
2. **多币种多通道计费**: Stripe / PayPal / 信用卡 / 加密货币 (USDT/USDC) + **支付宝 (Alipay+ 国际版) / 微信支付 (WeChat Pay HK / Cross-border)**——既覆盖标准国际支付，也对中国主体支付通道做兜底，降低国际支付通道被风控冻结的风险
3. **全球多语言支持（i18n）**: MVP 阶段至少覆盖 10+ 主流语言（英、中、日、韩、西班牙、法、德、葡萄牙、俄、阿拉伯），用户在控制台或 SDK 中可切换；文档、UI、错误消息、邮件通知均支持本地化；后续可按需扩展语言包
4. **OpenAI 协议兼容**: 客户只需把 `base_url` 从 `api.openai.com` 改成 `api.he-api.com`，零代码修改即可迁移
5. **智能路由**: 按"质量 / 成本 / 延迟"三维度自动选最优模型，支持自动 failover 与负载均衡
6. **跑分透明**: 公开 He-API 内嵌 benchmark，对比中国模型 vs GPT-4 / Claude / Gemini 的真实质量与延迟数据
7. **合规即服务**: 内置敏感词过滤、生成式 AI 备案、数据境内存储——海外客户开箱合规

### 为什么这次能成

- **能力侧成熟**: DeepSeek/Qwen/Kimi 已是 GPT-4 量级，不再需要"为了中国而中国"——本身就是有竞争力的模型选择
- **协议侧标准化**: OpenAI API 已成为 LLM 调用事实标准，兼容协议让迁移成本降到接近零
- **生态侧空白**: 当前没有任何一家公司把"中国合规 + 海外计费 + 多语言本地化体验"三件套同时做到位
- **杠杆点对**: 我们不做模型，只做网关——轻资产、快迭代、可与任何模型厂商建立非排他合作

### 高层愿景

成为"中国 LLM 出海的默认入口"——任何海外开发者想用中国模型，第一反应是 He-API；任何中国 LLM 厂商想触达海外，最高效的路径是 He-API。

## 目标用户

### 主要用户群体: 全球独立开发者与 AI SaaS 中小团队

- **画像**: 18-45 岁，居住在北美/欧洲/东南亚/拉美/印度，技术栈以 Python / Node.js / Go 为主，已在使用 OpenAI / Anthropic API 构建产品
- **当前行为**: 在 OpenAI 平台月消费 $50-$5,000；关注 HackerNews / Twitter / Reddit r/LocalLLaMA 上的模型对比；对成本敏感且愿意为可靠性付费
- **痛点**:
  - 想试用 DeepSeek/Qwen 节省 60% 推理费用，但官方注册不通
  - 担心单一供应商风险（OpenAI 宕机 / 涨价 / 政策变动），需要 Plan B
  - 没时间研究中国合规细节
- **目标**: 用最低迁移成本接入第二供应商；对部分场景（代码、长文本、中文）切换到性价比更高的中国模型

### 次要用户群体: AI 研究者 / 模型采购决策者 / 出海中国企业的海外子公司

- **画像**:
  - 大学/研究机构需要做跨国模型评测的研究员
  - 中大型企业 CTO / AI Lead，正在做"中美 LLM 选型"的横向对比
  - TikTok / Shein / Temu 等出海中国公司的海外团队，业务在海外、合规要求中国模型
- **当前行为**: 多账户/多供应商手动管理、自建 benchmark
- **痛点**: 缺统一基准；中国厂商英文资料不足；横向对比成本高
- **目标**: 一次接入即可运行多家模型 A/B 测试，拿到决策依据

## MVP 范围

### 核心功能（必须有）

1. **统一 API Key 管理 + 配额限流**: 多 Key、按 Key 限速、按 Key 维度的成本上限熔断
2. **计费与账单**: 按 token / 按调用次数计费、月度账单；多币种 (USD 默认 + RMB)；多通道支付（Stripe + PayPal + USDC + 支付宝 Alipay+ + 微信支付 WeChat Pay HK / Cross-border）；自动充值与余额预警
3. **监控与日志**: 请求级追踪、错误率、延迟、Token 消耗，按用户 / 模型 / 时间多维聚合，开发者可下载日志
4. **智能路由**: OpenAI 兼容入口下，按 `质量 / 成本 / 延迟` 策略自动选模型；模型故障自动 failover；多模型负载均衡
5. **OpenAI 协议兼容入口**: 统一 `/v1/chat/completions`、`/v1/embeddings`、`/v1/models` 端点；流式响应（SSE）；function calling 基础参数透传
6. **内容安全 / 敏感词过滤**: 入参/出参双向过滤；可配置严格度；命中后返回标准错误码
7. **多模态支持**: 图像理解（Qwen-VL、GLM-4V）、语音转文字（Doubao TTS/ASR）、视频理解（基础接入）
8. **海外友好注册**: 邮箱 + Google/GitHub OAuth；免国内手机号；免实名认证；GDPR-compliant 隐私协议
9. **多语言 Web 控制台 + 多语言文档**: 采用 i18n 框架，MVP 默认 10+ 语言（英、中、日、韩、西、法、德、葡、俄、阿），支持运行时切换；文档、UI、错误消息、邮件通知均本地化；含 Quickstart、API Reference、Cookbook
10. **接入 6-8 家中国主流模型**: Qwen (通义千问)、DeepSeek、Kimi (Moonshot)、GLM (智谱)、Doubao (字节豆包)、文心 (百度)、混元 (腾讯)；初期 6 家、Beta 期补齐 8 家

### MVP 范围外

- 模型微调（fine-tuning）/ 训练服务
- He-API 自有模型托管
- 私有化部署版本（On-prem）
- 离线 SDK / 移动端原生 SDK（暂仅提供 HTTP + 主流语言客户端）
- 高级 Agent 框架编排（多步推理、工具循环、记忆管理）
- 高级 Function Calling 编排（仅做参数透传，不做编排层）
- 自有 RAG / 向量数据库托管服务
- 企业级 SSO / SAML / RBAC（仅做基础 Team 协作）
- 中国大陆境内客户支持（仅服务海外客户，避开与中国厂商直营竞争）

### MVP 成功标准

MVP 视为成功当且仅当**同时满足**以下条件：

- 上线后 60 天内累计注册 ≥ 1,000 个海外开发者（非中国 IP 验证）
- 累计成功 API 调用 ≥ 1,000 万次、累计 USD 结算 ≥ $10,000
- 至少 1 篇来自海外（HackerNews / Twitter / Reddit / Dev.to）的非付费第三方推荐
- 网关可用性月度 ≥ 99.9%、P95 网关层叠加延迟 ≤ 150ms
- 完成 ICP 备案 + 算法备案 + 至少 1 项生成式 AI 备案，无任何合规警告事件

## 技术考量

### 平台要求

- **目标平台**: Web 控制台（响应式，桌面优先）、HTTPS REST API、Server-Sent Events（流式）、WebSocket（V2 实时场景）
- **浏览器/系统支持**: Chrome / Edge / Safari / Firefox 最近 2 个大版本；移动端浏览器可用但非优先
- **性能要求**:
  - 网关层 P95 叠加延迟 ≤ 100ms（不含模型推理时间）
  - 单实例并发 ≥ 5,000 RPS
  - 横向无状态扩展，理论上限取决于后端模型容量
  - 流式响应首字符时间（TTFB）≤ 300ms 网关层叠加

### 技术偏好

> **由 Architect 最终决定**；以下为业务侧建议方向：

- **前端**: React / Next.js + TypeScript；i18n 框架（建议 next-intl / react-intl），MVP 默认 10+ 语言、运行时切换；Tailwind / shadcn-ui 类现代组件库
- **后端**: Go（高并发网关层首选）或 Rust（极致性能）；管理面可考虑 Node.js / Python（生态丰富）
- **数据库**: PostgreSQL（主数据：用户、订单、Key、配额）+ Redis（限流、缓存、Session）+ ClickHouse / TimescaleDB（请求日志、监控聚合）
- **消息队列**: Kafka / Pulsar（异步日志、计费事件、审计流）
- **托管/基础设施**: 阿里云 / 腾讯云 / 华为云境内 VPC（满足备案要求）；K8s 容器化；境外边缘 TLS 终端（CloudFront / Cloudflare 仅做 TLS、不缓存内容）

### 架构考量

- **仓库结构**: Monorepo（gateway / console / sdk / docs / infra），便于跨服务一致性；推荐 Turborepo / Nx
- **服务架构**: 网关层无状态横向扩展；账户/计费/监控为独立服务；模型适配器以 plugin 模式独立部署，新增模型仅需新增 adapter
- **集成需求**:
  - 上游: Qwen / DeepSeek / Kimi / GLM / Doubao / 文心 / 混元 各官方 API
  - 下游: Stripe / PayPal / Crypto Payment Processor (Coinbase Commerce 或 BitPay) / **支付宝开放平台 (Alipay+ 国际版接入) / 微信支付商户平台 (WeChat Pay HK / Cross-border)**
  - 第三方: GitHub OAuth / Google OAuth / 邮件（SendGrid / 阿里云邮推）/ 国际短信（Twilio，仅可选 2FA）
- **安全/合规**:
  - **境内主体 + 全套备案**: ICP、算法、生成式 AI 备案三件套
  - **数据 100% 境内存储**: 包括请求日志、用户数据、模型回包；不向海外服务器复制/缓存任何持久化数据
  - **流量合规边界**: 海外用户 → 境外边缘 TLS → 境内网关 → 境内模型 → 响应原路返回；响应仅做 TLS 终止与转发，**不在境外节点持久化**
  - **加密**: 全链路 TLS 1.3；敏感字段（API Key、支付凭据）KMS 加密存储
  - **API Key 安全**: 哈希存储、可吊销、IP 白名单、调用范围限定
  - **GDPR / CCPA**: 海外用户数据处理需提供导出/删除接口

### 非功能要求

- **高扩展性**: 网关层无状态、横向扩展；账户/计费/监控可独立扩缩容
- **云原生**: 全栈容器化（Docker），K8s 友好部署；CI/CD 流水线
- **i18n 国际化**: 前后端均需采用 i18n 框架（如 react-intl / next-intl 前端；ICU MessageFormat 后端），文案外置便于翻译；货币与时间格式按用户 locale 显示
- **可观测性**: 全链路追踪（OpenTelemetry）、结构化日志、指标采集；告警与值班响应机制
- **成本敏感**: 早期低成本基础设施起步，按量付费优先于预购；关注单位调用成本随量级下降的曲线

## 约束与假设

### 约束条件

- **预算**: 早期低成本基础设施起步（建议种子轮预算 ≤ ¥3M / $400K）；优先按量付费，避免过度预购
- **时间线**: MVP 4-8 周内可发布（**激进**）；建议 8-12 周（合规备案至少占 4-6 周）。**置信度: 低**——4 周对完整合规交付存在重大风险
- **资源**: 团队规模未知；建议最小阵容 1 PM + 1 前端 + 2 后端 + 1 SRE/合规 + 1 设计 = 6 人核心团队
- **技术**: 必须使用境内云（阿里/腾讯/华为）；必须支持 OpenAI 协议兼容；模型接入受上游厂商 API 稳定性与限流约束
- **合规**: 必须以中国境内法人公司主体运营；ICP / 算法 / 生成式 AI 备案为硬性前置（非快速申领）

### 关键假设

- **市场假设**: 海外开发者对中国模型的需求真实存在，且对成本敏感程度足以驱动迁移行为
- **能力假设**: 中国主流大模型在 6-12 个月内继续保持与 GPT-4 / Claude 同档次的竞争力
- **合规假设**: "海外用户调用中国模型，响应原路返回不构成数据出境"这一边界在监管层面持续被认可（**置信度: 中**——需法律意见书背书）
- **支付假设**: Stripe / PayPal 愿意为中国境内主体的"AI API 转售"业务开通商户账户（**置信度: 中-低**——可能需要香港或新加坡子公司作为收单主体）
- **协议假设**: OpenAI 兼容协议在 12-24 个月内仍是事实标准，不会出现破坏性变更
- **厂商关系假设**: 中国 LLM 厂商对"统一海外网关"持开放或合作态度，不会主动封禁第三方聚合
- **延迟假设**: 通过香港/新加坡边缘节点 + 境内网关，海外用户感知 P95 延迟可控制在 800ms 以内（含模型推理）

## 风险与待解问题

### 关键风险

- **🔴 合规边界风险（HIGH）**: "海外用户调用 + 境内模型 + 响应原路返回不构成数据出境"的法律解释存在不确定性。一旦监管认定为出境，需 CAC 安全评估或标准合同备案，时间线延长 6-12 个月。**缓解**: 上线前取得专业法律意见书；与监管部门预沟通；预留香港子公司方案 B
- **🔴 国际支付通道风险（HIGH）**: 中国境内主体直接使用 Stripe / PayPal 开通"AI 转售"账户成功率低；可能被风控冻结。**缓解**: 启用香港/新加坡公司作为收单主体；与中国 LLM 厂商境内对公结算；多通道并行 + 加密货币兜底；**支付宝/微信支付作为中国主体可控通道是关键兜底**，可降低 Stripe/PayPal 被冻结时的业务中断风险；目标是任一通道故障时其他通道可承接 80%+ 流量
- **🔴 上游模型政策变动（HIGH）**: 中国 LLM 厂商可能因竞争原因封禁聚合层 API、或国家政策禁止国产模型对外服务。**缓解**: 与 2-3 家头部厂商签战略协议（流量分成换稳定供给）；MVP 即支持 ≥ 6 家分散依赖
- **🟡 海外开发者认知与信任（MEDIUM）**: 西方开发者对中国 SaaS / 数据隐私存在疑虑，可能影响转化。**缓解**: 透明合规白皮书、开源 SDK、第三方审计、社区运营（Twitter/HN/Discord）
- **🟡 延迟体验（MEDIUM）**: 全球用户访问境内服务的物理延迟不可避免。**缓解**: 多地域边缘 TLS 终端；合理 SLA 公示；针对延迟敏感场景提供香港/新加坡可用区中转选项
- **🟡 竞争对手快速跟进（MEDIUM）**: OpenRouter / LiteLLM 可能加大中国模型支持力度。**缓解**: 抢占品牌定位；深耕厂商关系；构建合规壁垒（海外玩家短期难复制）
- **🟢 模型质量波动（LOW-MED）**: 中国厂商 API 不稳定可能影响整体可用性。**缓解**: 智能路由 + failover；公开各模型可用性数据
- **🟢 协议演变（LOW）**: OpenAI 协议被新标准取代。**缓解**: 适配器层抽象；兼容多协议时机成熟时跟进

### 待解问题

- 收单主体最终方案：境内主体 + 境外子公司（香港 / 新加坡）的最优结构是什么？税务、合规、用户信任如何权衡？
- 与中国 LLM 厂商的商务关系：是流量分成、独家代理、还是普通 API 客户？需谈判节奏是怎样的？
- 定价策略：是直接 markup（透明加价 5-15%）还是订阅制（Pro/Team/Enterprise 分档）？或两者结合？
- 内容安全合规层：在中国厂商已自带敏感词过滤的情况下，He-API 是否还需独立过滤层？双层过滤误杀率如何控制？
- 退款政策与 SLA：海外客户对 SLA 与 refund 的期待与中国厂商现实可承诺范围之间的差距如何处理？
- 开源策略：网关代码是否开源（参考 LiteLLM 模式扩大社区）？开源边界与商业化护城河如何切分？
- 海外营销首发渠道：Product Hunt / HackerNews / Twitter influencer / 技术博客投放，预算与节奏分配？

### 需要进一步研究的领域

- **法律**: 中国《生成式 AI 服务管理暂行办法》《数据出境安全评估办法》对"境内 LLM 服务海外用户"的明确边界（需正式法律意见书）
