**Architect Open Questions** (gathered for Architect Round 1):

- **Q1 — Endpoint URL surface**: `/v1/me/keys` (user-bound, mirrors Story-2.5 `/v1/me/profile` precedent + Story-2.6 `/v1/me/data-export`; the JWT `sub` claim IS the implicit user_id) vs `/v1/keys` (collection-style, user_id derived from JWT but URL is shorter)? SM defaults to **`/v1/me/keys`** because (a) the JWT path on the gateway is currently `/v1/me/*` per Story-2.2/2.5/2.6 precedent, (b) per-route middleware wiring is simpler when paths share a prefix, (c) "my keys" matches the user mental model. The 3 routes:
  - `POST /v1/me/keys` — create (returns plaintext ONCE)
  - `GET /v1/me/keys` — list (no plaintext)
  - `DELETE /v1/me/keys/{api_key_id}` — revoke

- **Q2 — Immediate revocation mechanism**: security.md §8.2.1 names three alternatives. SM defaults to **option (c) per-key-id sentinel** (`auth:apikey:revoked:{api_key_id}` SET with TTL 300s; gateway's Story-3.2 positive-cache-hit path additionally checks the sentinel before returning OK). Rationale: zero new infrastructure (Redis already in place), TTL bounded by the cache TTL it must outlive, single-write on revoke (auth-svc only — no subscriber maintenance), zero gateway-pod state (statelessness preserved). Architect may prefer (a) Redis pub/sub (lower-latency for already-subscribed gateway pods but adds per-pod subscriber state) OR (b) Kafka audit-consumer reuse (zero new infrastructure since `audit.event` is already emitted, but adds gateway-side consumer-group complexity).

- **Q3 — `teams` table creation + `api_keys.team_id` FK ALTER**: Pre-flagged at `data-models.md §4.5` Change Log row 2 (2026-05-18 Story 3.2) as "Epic 5 owner". Epic 5 YAML does NOT spawn a dedicated `teams` table story (5.1-5.5 are all key-management). SM defaults to **defer** because (a) Story 5.1 issues user-scoped keys only (`team_id=NULL` for every row), (b) the FK ALTER + table creation is non-trivial and orthogonal to Story 5.1's headline AC, (c) team-scoped keys are not on the Epic-5 deliverable list. Architect may rule (i) Story 5.1 lands the `teams` skeleton + FK ALTER as a follow-on, or (ii) split into a sibling Story 5.1a, or (iii) defer to a future Epic when team-collaboration becomes a deliverable.

- **Q4 — NEW envelope codes**: The post-Story-3.6 5-field envelope contract requires every NEW code to register in `apps/api-gateway/internal/openaierr.CodeMetadata` (architecture `rest-api-spec.md §5.1.2`). Story 5.1 needs:
  - `403_api_key_owner_mismatch` ({403, "invalid_request_error"}) — revoke/get of an `api_key_id` belonging to a different user (IDOR defence; client-visible message anti-enumerable per BR-2.4 — same envelope regardless of "exists, not yours" vs "doesn't exist", which collapses Q4 into the next bullet)
  - `404_api_key_not_found` ({404, "invalid_request_error"}) — id does not exist (per anti-enumeration, this MAY collapse to `403_api_key_owner_mismatch` — SM default: collapse into a single `404` envelope returned for BOTH "not yours" AND "doesn't exist" so attackers cannot enumerate id space)
  - `429_rate_limit_key_create` ({429, "invalid_request_error"}) — anti-abuse rate-limit on create endpoint (BR-1.10 — 10 creates / hour / user default)
  - `409_api_key_already_revoked` ({409, "invalid_request_error"}) — alternatively per BR-3.4 the revoke endpoint is idempotent (200 on revoke-already-revoked); SM default: idempotent 200 (return current `revoked_at`) — no new envelope code.
  Architect ratifies: which codes land + collapse strategy for anti-enumeration.

- **Q5 — Anti-abuse rate-limit ceiling for `POST /v1/me/keys`**: SM defaults to **10 creates / hour / user** (parity with Story-2.5 BR-2.8 profile update; the surface attack vector is similar — burst create to flood the table or DoS bcrypt cost=12 at 250ms per op). Architect may rule different ceiling. Per-IP secondary cap (anti-credential-stuffing-via-stolen-JWT) — SM default: none in this Story (JWT is user-scoped already); Architect may add.

- **Q6 — Optimistic concurrency on revoke**: SM defaults to **NOT REQUIRED** because revoke is a terminal-state idempotent operation (revoke-already-revoked is a no-op return-current — BR-3.4); the etag/version-column protection from Story 2.5 prevents "lost update" on mutating edits, which does not apply to a write-once-then-immutable column like `revoked_at`. Architect may rule otherwise.

- **Q7 — AAL claim requirement for revoke**: SM defaults to **`aal>=1`** (same as Story 2.5 PUT /v1/me/profile per Architect Q4 ruling — low-blast-radius mutation on the user's own resource; the user reasonably expects single-click revoke when they suspect a key is compromised). Architect may rule `aal>=2` mandatory if the threat model includes "attacker with leaked session cookie revokes legitimate user's keys to lock them out" — counter-argument: that attacker can already access the dashboard and exfiltrate everything, so revoke-friction is closing-the-stable-door.

- **Q8 — Key generation format precision**: security.md §8.2 step 2 says `"he-" + base62(32 bytes) → ~46 chars total`. 32 bytes encoded in base62 ≈ 43 chars (32 / log₂(62) = 32 / 0.7 ≈ 43). So total ≈ 46. SM defaults to **exactly `"he-" + base62(32 bytes)` with the canonical 0-9A-Za-z alphabet** (`stdlib/big.Int` with base62 conversion OR a vendored constant-time base62 encoder — SM defers tool choice to Dev). `key_prefix` stores first 12 chars (`he-` + 9 base62 chars). Architect may rule on canonical alphabet ordering OR mandate a specific library.

- **Q9 — `users.status` gating on create**: Story 2.5 BR-1.9 + Story 2.7 (not yet drafted) define `users.status = 'pending_deletion'` semantics. SM defaults to **reject create with 403 `403_account_pending_deletion`** if the user is in pending_deletion state (parity with Story-2.5 BR-1.9); revoke is permitted from pending_deletion state (a user winding down their account SHOULD be able to revoke keys defensively). Architect may rule otherwise.

- **Q10 — Key name input validation**: SM defaults to **parity with Story-2.5 BR-2.3 display_name** (1-100 runes after NFC, Letter/Mark/Number/Punctuation/Symbol-Currency code points + ASCII space; reject control/format/private-use/other-symbol; uniqueness NOT enforced per-user so users may have multiple keys named "Production"). Architect may rule different policy (e.g., reject `<` `>` to harden against future innerHTML render, or impose tighter length).

### AC1: Create API Key — `POST /v1/me/keys` returns plaintext exactly ONCE, persists bcrypt hash, audits, rate-limits

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access JWT cookie valid per Story 2.2 BR-3.7; `aal>=1` per Q7 SM default)
  - `users.status = 'active'` (NOT pending_deletion per Q9 SM default)
  - User has issued fewer than 10 keys in the trailing 1 hour window (per BR-1.10 rate-limit ceiling)
WHEN
  - User calls `POST /v1/me/keys` with JSON body `{"name": "<UTF-8 1-100 runes>"}` (only `name` is in scope for Story 5.1; `scope` + `monthly_cost_cap_usd` are Story 5.2)
  - Console BFF Server Action `createMyKey({name})` → api-gateway `POST /v1/me/keys` (carries he_access cookie + CSRF guard from Story 2.2) → auth-svc gRPC `AuthService.CreateApiKey(CreateApiKeyRequest{user_id, name})`
THEN
  - api-gateway:
    - Extracts `user_id` from the verified JWT `sub` claim (Story 2.2 middleware); the request body MUST NOT carry a `user_id` — IDOR defence (BR-1.3).
    - Increments rate-limit counter `ratelimit:apikey:create:{user_id}` (Redis INCR + EXPIRE 3600). If at ceiling BEFORE the RPC, returns 429 `429_rate_limit_key_create` + `Retry-After` (seconds-until-counter-expires) header. No RPC issued; no row created.
    - Validates the body shape: strict-field-validation per BR-1.2 (only `name` permitted; any other key → 400 `400_unknown_field` with `field=<offending_key>`).
    - Validates `name`: NFC-normalized, trimmed, 1-100 runes, allowed code-point classes per BR-1.7 (Q10 SM default — parity with Story-2.5 display_name).
  - auth-svc CreateApiKey:
    - Loads `SELECT status FROM he_api.users WHERE id=$1 LIMIT 1`. If `status='pending_deletion'` → returns gRPC `FailedPrecondition` `account_pending_deletion` (gateway translates to 403 per Q9).
    - Calls the plaintext-generation helper at `apps/auth-svc/internal/apikey/generate.go`:
      - Reads 32 bytes from `crypto/rand.Reader` (NEVER `math/rand`); aborts (gRPC `Internal`) on read error.
      - base62-encodes the 32 bytes using the canonical alphabet `0-9A-Za-z` (Q8 SM default) → ~43 chars.
      - Composes `plaintext = "he-" + <43 base62 chars>` (~46 chars total).
      - Computes `key_prefix = plaintext[:12]` (per security.md §8.2 step 4) — first 12 chars; this is the indexed-lookup column on the Validate path (Story 3.2).
      - Computes `key_hash = bcrypt.GenerateFromPassword([]byte(plaintext), 12)` (cost=12 per §8.2 step 3); aborts (gRPC `Internal`) on bcrypt error.
    - In a single PG transaction:
      - `INSERT INTO he_api.api_keys (id, user_id, team_id, name, key_prefix, key_hash, scope, monthly_cost_cap_usd, current_month_cost_usd, last_used_at, revoked_at, created_at) VALUES (gen_random_uuid(), $user_id, NULL, $name, $key_prefix, $key_hash, '{}'::jsonb, NULL, 0, NULL, NULL, NOW()) RETURNING id, created_at`
      - Emits Kafka `audit.event` (audit_event_type=`api_key.created`) with PII-safe payload per BR-3.5 (NEVER plaintext, NEVER hash).
    - Returns `CreateApiKeyResponse{api_key_id, key_prefix, name, created_at, plaintext}` — `plaintext` is set ONCE in this response and NEVER persisted.
  - api-gateway:
    - Translates → HTTP 201 Created; response body:
      ```json
      {
        "api_key_id": "<uuid>",
        "key_prefix": "he-XXXXXXXXX",
        "name": "<as-stored>",
        "plaintext": "he-XXXXXXXXX...",
        "created_at": "2026-05-20T12:00:00Z",
        "warning": "This plaintext is shown ONCE. Store it now — it cannot be retrieved later."
      }
      ```
    - Sets `Cache-Control: no-store, no-cache, must-revalidate` + `Pragma: no-cache` (PII page — plaintext must not be cached by intermediate proxies even though TLS already excludes off-path actors; defence-in-depth).
    - slog records: `event="apikey_created"`, attrs `api_key_id`, `user_id` (hashed per BR-3.7), `key_prefix`, `client_ip_hash`, `user_agent_hash` — **NEVER** the plaintext, **NEVER** the hash.
  - Console Server Action:
    - On 201: navigates to a one-shot "Save your key" modal/page (Story 5.5 owns the UI rendering — Story 5.1 only commits the API contract). The page renders `<ApiKeyDisplay>` per front-end-spec §5.2 line 602 (one-time mask + copy-to-clipboard + "I've saved it" confirmation). The plaintext is NOT placed in session storage or any persistent client-side cache.
    - On 400/429/403/503: surfaces the canonical envelope code to a toast + the form retains the typed `name` for retry.
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | `POST /v1/me/keys` is **JWT-authenticated** (he_access cookie), NOT bearer-API-key-authenticated. Issuing new keys via a bearer API key would create a key-can-create-keys cycle (lateral movement risk) — explicitly rejected. The API-key path is the Story-3.2 bearer-auth flow on `/v1/chat/completions` etc.; the key-management path is the JWT flow on `/v1/me/*`. The two are non-overlapping by middleware composition: `bearerAuth.RequireAPIKey` is wrapped only on `/v1/chat/completions` + cohorts (Story 3.2 BR-1.4); `/v1/me/keys` wraps `verifier.RequireJWT` only. |
| BR-1.2 | Strict-field-validation: the POST body MUST contain ONLY keys in `{name}`. Any other key → 400 `400_unknown_field` with `field=<offending_key>` (parity with Story 2.5 BR-2.2 + Story 2.2 BR-2.4). The Story-5.2 scope fields (`scope`, `monthly_cost_cap_usd`) WILL be added there — Story 5.1 strict-rejects them so Dev cannot accidentally accept-and-discard. |
| BR-1.3 | `user_id` is **EXTRACTED from the verified JWT `sub` claim** by the gateway middleware (Story 2.2 BR-3.7) and passed to auth-svc via the gRPC field; the request body / path / query string MUST NOT carry a `user_id` even though the gRPC contract requires it — gateway translates from JWT and ignores any client-supplied value. Defence-in-depth against IDOR. |
| BR-1.4 | Plaintext generation uses `crypto/rand.Reader` ONLY. `math/rand` is REJECTED (predictable across process restarts on Go 1.21- and even on Go 1.22+ the seed is observable via timing). 32-byte entropy gives 2^256 ≈ 1.16×10^77 keyspace — practical collision is impossible. |
| BR-1.5 | The plaintext is returned in the response body and NEVER again. It is NEVER written to PG (only the bcrypt hash), NEVER to slog, NEVER to OTel span attributes, NEVER to Kafka audit payloads, NEVER to error messages. A test (5.1-SECURITY-001 per QA test design) MUST grep captured logs for the literal plaintext and assert zero matches. |
| BR-1.6 | The `GET /v1/me/keys` list response (AC2) MUST NOT carry plaintext — only `key_prefix` is surfaced. Once the user closes the create-time "Save your key" modal without saving the plaintext, they MUST rotate to a new key (issue new + revoke old via Story 5.1 itself; rotation-as-one-call is a future Story). |
| BR-1.7 | `name` accepts UTF-8 1-100 runes after NFC normalization. Allowed code-point classes: Letter (L), Mark (M), Number (N), Punctuation (P), Symbol-Currency (Sc), ASCII space (single between words). REJECT: control chars (Cc), format chars (Cf), surrogates (Cs), private-use (Co), unassigned (Cn), other Symbol classes (S-{Sc}). NULL / empty / whitespace-only is REJECTED with 400 `400_invalid_key_name` — `name` is REQUIRED (unlike Story-2.5 display_name which permits clearing). |
| BR-1.8 | `name` is NOT enforced to be globally unique nor per-user unique — users may have multiple keys named "Production" (e.g., one per CI/CD pipeline). UX-wise, the console SHOULD warn on duplicates (Story 5.5 owns this) but the API does not reject. |
| BR-1.9 | bcrypt cost=12 generation is **synchronous** in the request handler (≈ 200-350ms typical on Story-1.3 cluster sizing). Story 5.1 accepts this tail-latency in the headline path because (a) create is a low-frequency operation per user (a key lasts months/years; users don't create keys per request), (b) the rate-limit ceiling (BR-1.10) bounds aggregate cost. If Architect prefers async-and-poll, request escalation to a new Story; SM defaults to sync. |
| BR-1.10 | Rate-limit on `POST /v1/me/keys`: 10 successful-or-failed creates / hour / user (`ratelimit:apikey:create:{user_id}` Redis INCR+EXPIRE 3600). At ceiling → 429 `429_rate_limit_key_create` + `Retry-After: <seconds-until-counter-expires>` header. Parity with Story-2.5 BR-2.8 profile-update rate-limit. Per-IP secondary cap deferred (Q5). |
| BR-1.11 | If the user's session-bound CSRF guard rejects the POST (parity with Story 2.2 BR-3.7 cookie-mode mutation requires `X-CSRF-Token` matching), the gateway returns 403 `403_csrf_check_failed` BEFORE this handler runs. Story 5.1 does NOT replicate CSRF handling — it inherits from Story 2.2. |
| BR-1.12 | If gateway → auth-svc gRPC fails with `UNAVAILABLE` or `DEADLINE_EXCEEDED`, gateway returns 503 `503_auth_unavailable` (existing envelope code from Story 2.2 / 3.2). The rate-limit counter is NOT incremented on RPC failure (refund pattern) so a transient auth-svc outage does not consume the user's per-hour budget. |
| BR-1.13 | Response field order is locked (per BR-1.4 Story-3.6 precedent): `api_key_id` → `key_prefix` → `name` → `plaintext` → `created_at` → `warning`. This order is enforced by Go struct field declaration order on the api-gateway side (`handlers.CreateKeyResponse`). |
| BR-1.14 | The `warning` field is a fixed English string in this Story (i18n-key `account.keys.errors.plaintext_one_time` is the i18n surface but the gateway returns the literal English; Story 5.5 owns localization at the rendering layer). Rationale: clients consuming the API directly (curl, programmatic SDKs) get a clear warning regardless of `Accept-Language`; localized UI happens in the console. |

### AC2: List API Keys — `GET /v1/me/keys` returns user-bound metadata only (NEVER plaintext, NEVER hash)

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access JWT cookie valid per Story 2.2 BR-3.7)
  - User has 0..N API keys in `he_api.api_keys` matching `user_id=$1` (both active and revoked rows are surfaced)
WHEN
  - User navigates to `/{locale}/(console)/keys` (Story-5.5-owned page); Server Component invokes Console BFF Server Action `listMyKeys()` → api-gateway `GET /v1/me/keys` → auth-svc gRPC `AuthService.ListApiKeys(ListApiKeysRequest{user_id})`
THEN
  - api-gateway:
    - Extracts `user_id` from JWT `sub` claim (BR-1.3 parity).
    - Calls `AuthService.ListApiKeys`.
  - auth-svc ListApiKeys:
    - `SELECT id, name, key_prefix, scope, monthly_cost_cap_usd, current_month_cost_usd, last_used_at, revoked_at, created_at FROM he_api.api_keys WHERE user_id=$1 ORDER BY created_at DESC LIMIT 100` (LIMIT 100 is the MVP cap per BR-2.2 — pagination is open Q4).

    - Returns `ListApiKeysResponse{keys: [{api_key_id, name, key_prefix, scope, monthly_cost_cap_usd, current_month_cost_usd, last_used_at, revoked_at, created_at}, ...]}`. The `scope` + `monthly_cost_cap_usd` + `current_month_cost_usd` fields are surfaced as-stored (default `{}` / NULL / 0 from Story 5.1 inserts) — Story 5.2 will populate them.
  - api-gateway:
    - Translates → HTTP 200; body:
      ```json
      {
        "object": "list",
        "data": [
          {"api_key_id":"<uuid>","name":"My First Key","key_prefix":"he-Aa1Bb2Cc3","scope":{},"monthly_cost_cap_usd":null,"current_month_cost_usd":"0","last_used_at":null,"revoked_at":null,"created_at":"2026-05-20T12:00:00Z"},

        ]

    - Sets `Cache-Control: no-store` (the response carries `key_prefix` which though non-secret is PII-adjacent — never cache).
    - slog records: `event="apikey_list"`, attrs `user_id` (hashed per BR-3.7), `key_count` (the LEN of data array), `client_ip_hash`, `user_agent_hash`. NEVER per-key `key_prefix`.

    - Table with columns `Name | Scope | Created | Last used | Actions` per front-end-spec §P-5

```

| ID | Rule |
|----|------|
| BR-2.1 | List is **user-bound** — see BR-1.3. The SQL WHERE clause is `WHERE user_id=$1` with `$1` sourced from JWT `sub`; the request body MUST NOT carry a `user_id`. IDOR defence (the list endpoint MUST NOT accept a `?user_id=` query parameter). |

| BR-2.3 | Sort order: `ORDER BY created_at DESC` (newest first — matches front-end-spec §P-5 implicit ordering). Tie-breaking by `id` UUID (stable when two keys are created in the same microsecond, which is unrealistic but the test asserts deterministic ordering). |
| BR-2.4 | Revoked keys are INCLUDED in the response (the user needs to see historical revocations for audit purposes — "did I revoke this on 2026-05-15? yes I did"). They are NOT filtered out by the gateway / auth-svc — the UI is free to hide them (Story 5.5 UX decision); the API is honest. |
| BR-2.5 | The list response MUST NEVER carry `key_hash` and MUST NEVER carry plaintext (plaintext is unrecoverable post-create; even if SOMEHOW reconstructable, the contract prohibits it). 5.1-SECURITY-002 (per QA test design) MUST grep the response body for any plaintext-shaped string (`he-[A-Za-z0-9]{40,253}`) and assert zero matches. |

| BR-2.9 | No rate-limit on `GET /v1/me/keys` — read endpoints are cheap and not abuse-vectors. The Story 2.2 global per-IP cap (if any) applies generically. |
| BR-2.10 | `monthly_cost_cap_usd` and `current_month_cost_usd` are returned as **string-formatted decimals** (e.g., `"50.00"`) NOT JSON numbers. Rationale: `NUMERIC(10,2)` and `NUMERIC(12,4)` are exact-decimal types in PG; JSON number is IEEE 754 binary float, which can lose precision on round-trip (e.g., `0.1 + 0.2 != 0.3`). Stripe API uses the same string-decimal convention for money fields. Architect may overrule. |

### AC3: Revoke API Key — `DELETE /v1/me/keys/{api_key_id}` is owner-scoped, immediate-effect via cache invalidation, idempotent, audited

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access JWT cookie valid per Story 2.2 BR-3.7; `aal>=1` per Q7)
  - An `api_keys` row exists with `id=$api_key_id`, `user_id=$jwt_sub`, `revoked_at=NULL` (or non-NULL — see idempotent path)
  - Some api-gateway pods may have cached a positive Validate result at `auth:apikey:{sha256(plaintext_for_this_id)}` from a prior Story-3.2 Validate hit (TTL ≤ 300s remaining)
WHEN
  - User clicks `[⊗ Revoke]` on Console P-5 page → confirmation modal → Server Action `revokeMyKey({api_key_id})` → api-gateway `DELETE /v1/me/keys/{api_key_id}` → auth-svc gRPC `AuthService.RevokeApiKey(RevokeApiKeyRequest{user_id, api_key_id})`
THEN
  - api-gateway:
    - Extracts `user_id` from JWT `sub` claim.
    - Validates path parameter: `api_key_id` MUST be a valid RFC 4122 UUID-v4-shaped string; reject with 400 `400_invalid_request` if not.
    - Calls `AuthService.RevokeApiKey`.
  - auth-svc RevokeApiKey:
    - In a single PG transaction:
      - `SELECT id, user_id, key_prefix, revoked_at FROM he_api.api_keys WHERE id=$api_key_id LIMIT 1 FOR UPDATE`. If 0 rows: returns gRPC `NotFound` (gateway translates to 404 per Q4 SM default — collapsed with owner-mismatch for anti-enumeration).
      - If `user_id != $jwt_sub` (request user_id from JWT): returns gRPC `NotFound` (anti-enumeration — same envelope as actual not-found per Q4 SM default; alternative is `403_api_key_owner_mismatch` if Architect overrules).
      - If `revoked_at IS NOT NULL` (already revoked): returns success with `RevokeApiKeyResponse{api_key_id, revoked_at: <existing-value>, was_already_revoked: true}` (BR-3.4 idempotent — terminal state).
      - Else: `UPDATE he_api.api_keys SET revoked_at=NOW() WHERE id=$api_key_id RETURNING revoked_at`; emits Kafka `audit.event` (audit_event_type=`api_key.revoked`) with PII-safe payload (BR-3.6).
    - **Invalidates the gateway-side Story-3.2 cache** per the mechanism Architect Q2 ratifies. SM default mechanism (option c — per-key-id sentinel):
      - `SET auth:apikey:revoked:{api_key_id} 1 EX 300` (TTL matches Story-3.2 cache TTL — sentinel outlives any in-flight positive cache entry; auto-cleanup means PG `revoked_at` is the durable source of truth after 300s — by then any subsequent cache fill ALREADY reads the revoked row from PG and never caches a positive).
      - The gateway-side Story-3.2 positive-cache-hit path (`apps/api-gateway/internal/middleware/bearer_auth.go`) MUST ADDITIONALLY check `EXISTS auth:apikey:revoked:{cached.api_key_id}` before returning OK on a cache hit. (Story 5.1 modifies the Story-3.2 file to add this check — see Tasks T4.x.)
      - Note: this is a Story-5.1 modification to a Story-3.2-owned file. Test impact: Story-3.2 cache-hit unit tests need extension for the new sentinel branch (covered in 5.1-UNIT-021..025).
    - Returns `RevokeApiKeyResponse{api_key_id, revoked_at, was_already_revoked}`.
  - api-gateway:
    - Translates → HTTP 200 OK (idempotent success — 204 No Content was considered + rejected because the response carries `revoked_at` for the UI to display); body:
      ```json
      {"api_key_id":"<uuid>","revoked_at":"2026-05-20T12:05:00Z","was_already_revoked":false}
      ```
    - Sets `Cache-Control: no-store`.
    - slog records: `event="apikey_revoked"`, attrs `api_key_id`, `user_id` (hashed), `was_already_revoked`, `client_ip_hash`, `user_agent_hash`. NEVER plaintext, NEVER hash.
  - Console Server Action:
    - On 200: invokes `revalidatePath('/{locale}/(console)/keys')` → the table re-renders with the revoked row greyed out + `revoked_at` badge populated; success toast `account.keys.revoke.success`.
    - On 404: toast `account.keys.revoke.not_found` (anti-enumerable message — "Key not found or already removed"); the row may still be visible if the table state is stale → trigger `router.refresh()`.
    - On 401/403/503: standard envelopes per the gateway-cross-cutting handler.
  - **Immediate-effect verification (E2E test 5.1-E2E-005)**:
    - Issue key K (AC1) → record plaintext.
    - Validate K via `POST /v1/chat/completions` with `Authorization: Bearer K` → 200 (Story-3.3 mock or Epic-4 adapter response) — positive cache filled at `auth:apikey:{sha256(K)}`.
    - Revoke K via `DELETE /v1/me/keys/{id}` → 200.
    - **Within ≤ 5 seconds of the revoke 200 response** (Architect Q2 ratification SLA), validate K again via `POST /v1/chat/completions` → 401 `401_invalid_api_key`. The sentinel (or pub/sub or Kafka consumer per Q2) takes effect — the positive cache hit is invalidated.
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | Revoke is **owner-scoped** — see BR-1.3 / BR-2.1. The SQL WHERE clauses are `WHERE id=$api_key_id` followed by an in-handler `if row.user_id != $jwt_sub` guard; combining into `WHERE id=$1 AND user_id=$2` is a valid alternative (gives the same effect — 0 rows = NotFound) but separating the guard makes audit logging cleaner (the slog records the IDOR attempt with `api_key_id` for forensics). |
| BR-3.2 | Anti-enumeration parity (Story-3.2 BR-2.4 pattern): "key not found" + "key not yours" return the SAME 404 envelope from the gateway. Differentiated envelopes leak whether the id-space slot is taken. SM default per Q4 SM default ratifies the collapse. Architect may overrule to use `403_api_key_owner_mismatch` for the owner-mismatch case; SM recommends AGAINST. |
| BR-3.3 | Revoke is **idempotent** terminal state. Re-revoking an already-revoked key returns 200 with `was_already_revoked: true` + the EXISTING `revoked_at` timestamp (NOT a new NOW() — the historical revoke moment is preserved for audit). |
| BR-3.4 | Idempotency means NO new Kafka audit event on the second-and-subsequent revoke calls — only the first transition NULL → NOW() emits `api_key.revoked`. Subsequent calls are no-ops audit-wise. |
| BR-3.5 | The Kafka audit event `api_key.created` payload (BR shared with AC1) is `{audit_event_type:"api_key.created", api_key_id, user_id, key_prefix, name, client_ip_hash, user_agent_hash, ts}`. PII surface: zero (key_prefix is the first 12 chars of plaintext — by design displayable; name is user-supplied label, NOT credential material; client_ip + user_agent are hashed per Story-2.3 m-4 helpers). |
| BR-3.6 | The Kafka audit event `api_key.revoked` payload is `{audit_event_type:"api_key.revoked", api_key_id, user_id, key_prefix, name, revoked_at, client_ip_hash, user_agent_hash, ts}`. The `key_prefix` + `name` are denormalized into the audit event (not requiring audit-svc to join `api_keys`) since the row may be later hard-deleted (future GDPR Story); audit retention is 30d per Story-2.2 audit-svc topic config. |
| BR-3.7 | `user_id` in slog records is `sha256(user_id_uuid)` hex (Story-2.3 m-4 helper) — never the raw UUID. The audit Kafka event carries the RAW UUID (audit-svc is the authorized consumer of PII per security.md §8.1 layer 8 "审计"). |
| BR-3.8 | Immediate-effect cache invalidation: per Architect Q2 ratification. SM default = sentinel `auth:apikey:revoked:{api_key_id}` with TTL 300s (matches Story-3.2 cache TTL). The gateway's Story-3.2 positive-cache-hit path is modified to additionally check the sentinel via `EXISTS` before returning OK. Worst-case lag from `UPDATE revoked_at=NOW()` to gateway-side 401 = round-trip latency to Redis on the NEXT cache hit (single-digit milliseconds typical). This UPGRADES the security.md §8.2.1 documented "5-min worst-case lag" for revoked keys (the §8.2.1 note SHOULD be amended to reflect the Story-5.1 sentinel — Architect ratifies amendment text on Round 1). |
| BR-3.9 | Revoke is permitted from `users.status='pending_deletion'` (Q9 ratification) — a user winding down their account SHOULD be able to defensively revoke keys. Create is NOT permitted from pending_deletion (BR-1 cross-ref AC1). |
| BR-3.10 | No rate-limit on `DELETE /v1/me/keys/{id}` — revoke is a security-positive action; rate-limiting it would create a counter-productive friction (user notices a key compromise and tries to revoke five keys in 10 seconds — they MUST succeed). The natural cap is the LIMIT 100 of the list endpoint (BR-2.2) — a user has no more than 100 keys to revoke. |
| BR-3.11 | The `was_already_revoked` field is **a Story-5.1 He-API extension** to the response — not part of any OpenAI-compatible API. Story 5.1's `/v1/me/keys` namespace is He-API-native (not OpenAI-compatible), so this is in-scope. Field-order per BR-1.13 precedent: `api_key_id` → `revoked_at` → `was_already_revoked`. |
| BR-3.12 | The Story-3.2 file `apps/api-gateway/internal/middleware/bearer_auth.go` is MODIFIED by Story 5.1 to add the sentinel-check branch. The modification is additive — no Story-3.2 behaviour is removed. Story-3.2 tests SHALL continue to pass; Story 5.1 adds new test cells for the sentinel branch (5.1-UNIT-021..025). |
| BR-3.13 | If the sentinel write fails (Redis unavailable in the auth-svc), the auth-svc `RevokeApiKey` still returns success to the user (the PG `revoked_at=NOW()` is the durable source of truth; the cache will simply natural-expire at TTL 300s — worst-case 5 minutes, which is the security.md §8.2.1 pre-Story-5.1 contract). slog records `event=apikey_revoke_sentinel_failed` at WARN. Architect Round 1 may upgrade this to "fail-closed: return 503 if sentinel write fails" — SM default is fail-open (graceful degradation to the §8.2.1 baseline). |

### Technical Constraints

- **Go runtime**: 1.22+ (per `docs/architecture/tech-stack.md §2.1` "网关语言"). MUST use `net/http` stdlib ServeMux + Go 1.22+ path parameter syntax `mux.Handle("DELETE /v1/me/keys/{api_key_id}", ...)` — NO `mux` libraries (gorilla/mux, chi). `r.PathValue("api_key_id")` is the standard accessor. [→ docs/architecture/tech-stack.md#21-完整技术清单, ADR-2]
- **bcrypt cost=12**: per `docs/architecture/security.md §8.2` step 3 — `bcrypt.GenerateFromPassword([]byte(plaintext), 12)`. The constant `bcrypt.DefaultCost` is 10 in `golang.org/x/crypto/bcrypt` — **do NOT use it**; explicitly pass `12`. [→ docs/architecture/security.md#82-api-key-生命周期]
- **crypto/rand only**: per `docs/architecture/security.md §8.2` step 1 — "Generate 32 bytes cryptographic random". MUST use `crypto/rand.Reader` (NOT `math/rand`). Read 32 bytes via `io.ReadFull(rand.Reader, buf[:])`; abort with error on short read. [→ docs/architecture/security.md#82-api-key-生命周期]
- **base62 encoding**: SM Q8 default (Architect ratifies) — canonical alphabet `0-9A-Za-z` (62 symbols). Implement as a small self-contained helper (no external dependency) using `math/big.Int` constant-time conversion OR a vendored 30-line table-based encoder. [→ docs/architecture/security.md#82-api-key-生命周期, Story 5.1 Architect Q8]
- **key_prefix length**: 12 chars (`"he-" + 9 base62 chars`) per `docs/architecture/security.md §8.2` step 4 ("first 8-12 chars" — SM ratifies the upper bound 12 per Story-3.2 BR-1.1 cascade which already assumes 12-char prefix). Schema column is `VARCHAR(16)` — fits with slack. [→ docs/architecture/data-models.md#41-postgresql-schema-核心表, security.md#82]
- **PostgreSQL access**: pgx (per `docs/architecture/tech-stack.md §2.1` "后端 OLTP DB" — Story 1.6 wired pgx; Story 3.2 extended with `apps/auth-svc/internal/repository/api_keys.go`). All queries MUST be parameterized via `pgx.Conn.Exec(ctx, sql, args...)` — NEVER string-concatenated SQL (coding-standards.md §12.1 + security.md §8.1 layer 6). [→ docs/architecture/coding-standards.md#121-go-后端, security.md#81]
- **Redis access**: `github.com/redis/go-redis/v9` (per Story 3.2 wiring in `apps/api-gateway/internal/cache/redis.go`). The auth-svc may need to add a Redis client wired in `cmd/server/main.go` if Story 2.2 did not (T3.2 verifies). - **Kafka producer**: `github.com/segmentio/kafka-go` (per Story 2.2 wiring in `apps/auth-svc/internal/audit/producer.go`). Topic `audit.event` with 30-day retention (`docs/architecture/data-models.md §4.4`). Audit emission is AFTER PG commit (best-effort; on Kafka failure: log WARN, do NOT roll back PG — the auth-svc owns the row, audit-svc is downstream). [→ docs/architecture/data-models.md#44-kafka-topics, Story 2.2 + 2.5 audit-emit pattern]
- **Proto generation**: Buf (per `docs/architecture/tech-stack.md §2.1` "内部 RPC"). Update `packages/proto/he/auth/v1/auth.proto`; run `buf generate`; commit `packages/proto/gen/go/he/auth/v1/auth*.pb.go` regenerated outputs (vendored — CI checks drift via `git diff --exit-code packages/proto/gen/`). ### Database Design

> **No DDL change in Story 5.1** (per `cumulative_context_impact.db_schema=false`). This section documents the READ + WRITE semantics on the existing `he_api.api_keys` table.

- **INSERT (AC1)**: All 12 columns populated except `team_id` (NULL per Q3), `monthly_cost_cap_usd` (NULL — Story 5.2 mutates), `current_month_cost_usd` (DEFAULT 0), `last_used_at` (NULL until first Validate hit), `revoked_at` (NULL). `id` is server-side `gen_random_uuid()`. `created_at` is server-side `NOW()` (DEFAULT). The handler RETURNING-clauses both `id` and `created_at` to populate the response without a re-SELECT.

- **UPDATE (AC3)**: `UPDATE he_api.api_keys SET revoked_at=NOW() WHERE id=$1 RETURNING revoked_at`. The `FOR UPDATE` lock is acquired earlier via the `SELECT ... FOR UPDATE` to serialize concurrent revoke attempts on the same id (the idempotent path short-circuits before the UPDATE). No other columns mutate — `revoked_at` is the only state field this Story writes on the revoke path.

- **SELECT (AC2)**: `SELECT id, user_id, team_id, name, key_prefix, scope, monthly_cost_cap_usd, current_month_cost_usd, last_used_at, revoked_at, created_at FROM he_api.api_keys WHERE user_id=$1 ORDER BY created_at DESC, id LIMIT 100`. **EXPLICITLY OMITS `key_hash`** at the SQL layer (BR-2.5 defence-in-depth — the column is never even fetched into auth-svc memory, eliminating any accidental leak via repository struct field access). T2.2 has a test (5.1-UNIT-019) asserting `key_hash` does not appear in the generated SQL or the returned column set.

- **Index usage**: `idx_api_keys_user_id` is hit by AC2's WHERE clause + AC3's authorisation check. `idx_api_keys_hash` (Story-3.2 introduced) is NOT used by Story 5.1 (that index is for the Validate hot path's bcrypt-compare candidate fetch by `key_prefix`). No new indices needed.

- **Concurrency**: `WHERE id=$1 FOR UPDATE` (revoke path) is fine-grained — does not contend with other users' rows. Concurrent revokes of the SAME id by the same user serialise via the row lock; the LAST one wins (idempotency makes "wins" semantically equivalent — same `revoked_at` value preserved per BR-3.3).

- **Schema reference** [→ docs/architecture/data-models.md#41-postgresql-schema-核心表]:
  ```sql
  CREATE TABLE api_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    team_id UUID,                                     -- nullable, NO FK in Story 3.2 (Q3 deferral confirmed)
    name VARCHAR(100) NOT NULL,
    key_prefix VARCHAR(16) NOT NULL,                  -- 'he-' + 9 base62 chars = 12 chars used; column holds 16 for slack
    key_hash TEXT NOT NULL,                           -- bcrypt cost=12; ~60 chars
    scope JSONB NOT NULL DEFAULT '{}',                -- Story 5.1 inserts '{}'; Story 5.2 populates
    monthly_cost_cap_usd NUMERIC(10,2),               -- nullable; Story 5.1 inserts NULL
    current_month_cost_usd NUMERIC(10,2) DEFAULT 0,   -- Story 5.1 inserts DEFAULT 0
    last_used_at TIMESTAMPTZ,                         -- nullable; updated by Story-3.2 Validate path
    revoked_at TIMESTAMPTZ,                           -- nullable; Story 5.1 sets to NOW() on revoke
    created_at TIMESTAMPTZ DEFAULT NOW()
  );
  CREATE INDEX idx_api_keys_user_id ON api_keys(user_id);
  CREATE INDEX idx_api_keys_hash ON api_keys(key_hash);  -- Note: index name is misleading — it's really on (key_prefix); see Story 3.2 T1.3 for rationale
  ```

**Story-specific test focus areas** (informs QA test design — non-exhaustive):

- **Security-critical** (5.1-SECURITY-*):
  - **5.1-SECURITY-001** Plaintext leakage audit: capture slog output from a 100-request batch (create + list + revoke); plaintext substring count MUST be 0
  - **5.1-SECURITY-002** Response-body plaintext absence: GET /v1/me/keys response body grep for `^he-[A-Za-z0-9]{40,253}$` shape → count MUST be 0
  - **5.1-SECURITY-003** bcrypt cost: `bcrypt.Cost(hash) == 12` on 100 generated keys
  - **5.1-SECURITY-004** crypto/rand attestation: verify via test-injectable rand reader OR runtime pprof that `Generate()` uses `crypto/rand` not `math/rand`

  - **5.1-SECURITY-006** Kafka audit-event payload absence: capture Kafka emit payloads from 50 create + revoke events; plaintext + hash substring count MUST be 0
  - **5.1-SECURITY-007** bcrypt-DoS resistance: 50 concurrent create requests at rate-limit ceiling 10 — verify the 11th onward rejects in < 5ms (BEFORE bcrypt would run)

- **Functional** (5.1-UNIT-*, 5.1-INT-*, 5.1-E2E-*):
  - Happy paths for create, list, revoke (covered in AC Coverage Matrix)
  - Idempotent re-revoke (BR-3.3)

  - Empty list (BR-2.8)
  - Concurrent revoke same id (BR-3.x serialization)

This matches GMP `mpz_get_str` base 62 AND most vendored implementations. However Go's stdlib `math/big.Int.Text(62)` uses the SAME alphabet — so the SM default is enforceable via stdlib without a third-party dep. Document this anchor in T1.1 + Dev Notes.
  - **Fix**: Dev's T1.1 helper either uses `(&big.Int{}).SetBytes(buf).Text(62)` (concise, stdlib-only) OR a 30-line table-based encoder. - **L-3 — Anti-enumeration response delay parity** (BR-3.2): The Story collapses "not found" and "owned by other user" to the same 404 envelope. To fully defeat timing-based enumeration the response time should also be uniform (a fast 404 for nonexistent vs a slower 404 after row-fetch-then-user_id-mismatch leaks the existence bit). SM did not address this. Risk: low — `WHERE id=$1 FOR UPDATE` is a B-tree lookup ≈ same latency for hit-but-wrong-user vs miss.
  - **Fix**: Add 5.1-SECURITY-005 timing-side-channel assertion: 1000 trials each of (nonexistent UUID) vs (existing UUID, wrong user); the P50 latency delta MUST be ≤ 5ms (well below network jitter). NO change to the implementation; this is a regression-prevention assertion only.
