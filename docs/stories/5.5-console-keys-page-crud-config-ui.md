**Epic Goal**: 完整的 API Key 生命周期 + 多维限流 + 月度消费上限熔断
**Epic DoD relevant to this Story**: "用户可创建/吊销/配置 API Key" — Story 5.1 closes the API contract for create / list / revoke; Story 5.2 closes the configure (scope + IP whitelist + monthly cap) API contract; Story 5.4 closes the cap-circuit-breaker + email notification path. **Story 5.5 closes the headline UX**: the keys page IS the user's surface for the Epic-5 deliverable. Without Story 5.5, every Epic-5 capability is only reachable via curl — which fails the Epic DoD verb "用户可" (users can).

**Architect Open Questions** (gathered for Architect Round 1):

- **Q-E5 — cap_tripped surfacing**: Should `ApiKeyEntry` on GET /v1/me/keys gain a `cap_tripped:bool` field reflecting the Story-5.4 `keystate:apikey:cap_tripped:{api_key_id}` sentinel? SM default: **YES, EXTEND**. Rationale: (a) Story 5.4's sticky-trip semantics mean `current >= cap` is NECESSARY but NOT SUFFICIENT for the badge (current may have been cron-reset to 0 while sentinel persists until manual purge per Story 5.4 BR-3.5); (b) computing it client-side requires the UI to know about the Redis sentinel which violates the API surface as the contract boundary; (c) the auth-svc ListApiKeys RPC can pipeline the EXISTS check across keys in a single MULTI/EXEC. Architect alternatives: (i) the UI heuristic-only (`current >= cap`) — accepts the cron-reset edge case; (ii) NEW endpoint `GET /v1/me/keys/{id}/status` — adds a second round-trip; (iii) the field lands but is computed server-side from PG `current_month_cost_usd >= monthly_cost_cap_usd` only (cron-reset edge case still missed). SM defaults to option (a) (server-side EXISTS check pipelined).

- **Q-V1 — visual baseline count**: SM defaults to **20 baselines** (5 layouts × 4 locales — en/zh-CN/de/ar). Layouts: (i) list page populated, (ii) list page empty state, (iii) create modal, (iv) configure drawer, (v) revoke dialog. Architect may reduce: e.g., 12 baselines = 3 layouts × 4 locales (drop list-empty + revoke-dialog as low-risk-of-layout-drift). The Story 4.7 precedent (`apps/console/e2e/marketing-models-a11y.spec.ts`) has `test.skip` for axe-core pending a follow-up Story — SM does NOT propose to skip a11y here since the page is authenticated-user CRUD with form interactions (higher a11y risk).

- **Q-A2 — clipboard auto-expiry**: Should Playwright assert clipboard auto-expiry (the copied plaintext disappears from the clipboard after N seconds, e.g., GitHub-style 60s)? SM default: **NO, out-of-scope** — browser controls clipboard lifetime; assertion would be brittle (Firefox vs Chromium differ; Safari has stricter sandboxing). The clipboard hygiene contract is that the UI MUST NOT proactively re-set the clipboard after the initial copy (no clipboard polling, no auto-clear). Architect may rule for inclusion.

- **Q-T1 — TanStack Query vs Server Action + revalidatePath**: SM defaults to **Server Action + `revalidatePath('/[locale]/(console)/keys')`** (zero client cache state). Rationale: keys list is read-mostly with low write frequency (users don't reload the list more than every ~30s — Story 5.1 BR-1.10 caps creates at 10/hour); a client-side cache adds invalidation complexity for negligible UX benefit. Architect may rule TanStack Query is mandated (existing tech-stack §2.1 row lists it) — SM counter: tech-stack inclusion is a CAPABILITY-AVAILABLE flag, not a USE-FOR-EVERY-PAGE mandate; the marketing models page (Story 4.7) uses Server Components + `revalidate: 300` with NO TanStack Query, setting precedent for this Story.

- **Q-U1 — Plaintext URL-param vs server-state**: SM defaults to **URL `searchParams` carrying the plaintext for the duration of the one-time-display sub-page**. The plaintext is in the URL bar (visible to the user) but the URL is `router.replace(...)`-scrubbed on "I've saved it" so it does NOT enter browser history. Alternatives: (a) Server-side ephemeral state (NEW Redis key `keysession:plaintext:{user_id}:{api_key_id}` TTL 60s — adds infrastructure complexity for marginal benefit since the user's own browser already has the URL); (b) POST-redirect-GET with server-rendered single-use token (the token references the plaintext server-side; one-page-view consumes the token — defends against URL-bar-screenshot leaks but adds complexity). Architect may rule alternative (a) or (b); SM defaults to URL searchParams per **KISS**.

- **Q-IPV6 — IPv6 zone-id rejection**: SM defaults to **REJECT IPv6 addresses with zone-ids** (e.g., `fe80::1%eth0`) in the client-side validator. Rationale: zone-ids are link-local and have no meaning at the API gateway boundary; rejecting them at the form is a defence-in-depth (server also rejects per Story 5.2 BR-1.5 — `net/netip.ParseAddr` accepts zone-ids but our validator can match Go's `Addr.IsLinkLocalUnicast()` behaviour). Architect may rule otherwise.

- **Q-COPY1 — Copy button confirmation timing**: SM defaults to **toast appears immediately on copy; auto-dismisses after 4s** (front-end-spec §5.1 toast default). The toast text is "API key copied to clipboard." Architect may rule for a persistent indicator next to the field (e.g., the [📋 Copy] button briefly turns into [✅ Copied!] for 2s before reverting) — both patterns are accessible; SM defaults to toast for code reuse.

- **Q-RTL1 — IP whitelist input direction in RTL**: SM defaults to **IP/CIDR inputs render LTR even when document direction is RTL** (parity with code blocks in front-end-spec §5.2 `<CodeSnippet>` which similarly preserves LTR). IP literals like `192.168.1.0/24` are LTR-only tokens; RTL rendering would visually invert the octet order. The `dir="ltr"` attribute on the `<input>` element handles this. Architect may rule for component-level vs site-wide setting.

- **Q-MOBILE1 — Configure drawer on mobile**: SM defaults to **full-page modal on `<md` breakpoint, right-side drawer on `>=md`** (parity with front-end-spec §8.2 mobile-strategy section). The drawer width is `min(420px, 100vw)`; full-page modal slides up from the bottom. Architect may rule for a different breakpoint (e.g., the configure form has 3 sections — could keep drawer on `>=sm`).

- **Q-RL1 — Rate-limit countdown timer source-of-truth**: SM defaults to **Server-supplied `Retry-After` header** (Story 5.1 BR-1.10 — integer seconds, 1..3600). The client renders a JS-driven countdown using `setInterval(1s)` decrementing from the header value. Architect may rule for a different display (e.g., humanized "in 5 minutes" via `Intl.RelativeTimeFormat`). SM defaults to integer seconds for precision.

- **Q-FOCUS1 — Focus restoration after modal close**: SM defaults to **focus returns to the [+ New Key] button after CreateKeyModal closes** (parity with shadcn-ui Dialog default behavior). Per WCAG 2.4.3 (Focus Order) + 3.2.3 (Consistent Navigation). Architect ratifies — no alternative requested.

### AC3: Configure API Key — `<ConfigureKeyDrawer>` renders the row's current scope + cap, accepts partial-updates per Story 5.2 BR-1.x, calls `updateMyKey({api_key_id, patch})` Server Action → `PATCH /v1/me/keys/{api_key_id}`

**Scenario**
```gherkin
GIVEN
  - User is on `/[locale]/keys` with at least one ACTIVE (non-revoked) key
  - The user owns the target key (Server-side IDOR check per Story 5.2 BR-1.1; UI does not enforce — relies on server)
WHEN
  - User clicks the [⚙] icon button on a row
  - `<ConfigureKeyDrawer>` opens — right-side drawer on `>=md` breakpoint per Q-MOBILE1; full-page modal on `<md`

    - Section "Models scope" — multi-select of allowed models; if `scope.models` is empty, the "All models" toggle is ON (visually a switch) and the multi-select is disabled; toggling OFF enables the multi-select with current value `[]`; the model options are loaded from the existing models registry via the `/public/models` endpoint (Story 4.7) — client-side fetch on drawer mount (cache: 'force-cache' since the catalogue is stable for ~5min per Story 4.7 ratification)

    - Section "Monthly cost cap" — currency input pre-filled with the locale-formatted version of `monthly_cost_cap_usd` (e.g., `"50.00"` → en: "50.00", de: "50,00", ar: "٥٠٫٠٠"); a "No cap" toggle that clears the field; the canonical-string wire value is `null` when toggled "No cap" or `parseDecimal(input, locale)` otherwise

  - The form uses React Hook Form + Zod; ONLY changed fields are included in the PATCH payload (`dirtyFields` from RHF drives the diff). Empty PATCH (no fields dirty) → Save button stays disabled per Story 5.2 BR-1.3
THEN
  - Server Action: `fetch(${apiGatewayURL}/v1/me/keys/${api_key_id}, { method: 'PATCH', headers: {...}, body: JSON.stringify(diffPatch), cache: 'no-store' })`
  - api-gateway → auth-svc UpdateApiKey gRPC → PG UPDATE + Kafka emit + Redis sentinel write
  - On 200:
    - Server Action returns `Result.ok(updatedRow)`
    - Client `revalidatePath('/[locale]/keys')` (so the list table picks up the new state on next render)
    - Toast "Key updated" (4s auto-dismiss)
    - Drawer closes; focus returns to the [⚙] button on the row
  - On 400 `400_unknown_field` (server-side strict-field rejection — should NOT happen if the Zod schema is in sync): inline error + generic toast + console.error for telemetry
  - On 400 with structured field errors (per Story 5.2 — `param: 'scope.models[0]'`, `param: 'scope.ip_whitelist[2]'`, etc.): React Hook Form `setError(<field path>, {message})`
  - On 404 `404_api_key_not_found` (race — another tab revoked the key OR cross-user IDOR attempt): toast "This key is no longer available." + close drawer + revalidate list
  - On 403 `403_account_pending_deletion`: toast + close drawer + redirect to /[locale]/settings (Story 2.7 placeholder)
  - On 5xx: generic toast; Save button re-enables
```

| ID | Rule |

| BR-U-2 | The form computes the diff via React Hook Form `dirtyFields` — ONLY changed top-level fields are sent in the PATCH. ### AC4: Revoke API Key — `<RevokeKeyDialog>` confirms via type-name-to-confirm guard, calls `revokeMyKey({api_key_id})` Server Action → `DELETE /v1/me/keys/{api_key_id}`; idempotent re-revoke shows the `was_already_revoked` field gracefully

**Scenario**
```gherkin
GIVEN
  - User is on `/[locale]/keys` with at least one ACTIVE (non-revoked) key
WHEN
  - User clicks the [⊗] icon button on an active row
  - `<RevokeKeyDialog>` opens — modal dialog with:
    - Heading: "Revoke API key?"
    - Warning body: "This action is permanent. Once revoked, this key cannot be reactivated. Apps using this key will receive 401 errors immediately." (`role="alert"` + `aria-live="assertive"`)
    - Display of the key's identifying info: Name + Prefix (e.g., "My First Key (he-Aa1Bb2Cc3…)") — for visual confirmation
    - Type-name-to-confirm guard: text input below the warning, label "Type the key name to confirm: {name}" — the user MUST type the EXACT name (case-sensitive) into the input; the [Revoke] button is disabled UNTIL the typed value matches exactly
    - [Cancel] button (left, default focus) + [Revoke] button (right, destructive variant red, initially disabled)
  - User types the exact name → [Revoke] button enables
  - User clicks [Revoke]
THEN
  - Server Action: `fetch(${apiGatewayURL}/v1/me/keys/${api_key_id}, { method: 'DELETE', headers: {...}, cache: 'no-store' })`
  - api-gateway → auth-svc RevokeApiKey gRPC → PG UPDATE revoked_at + Kafka emit + Redis revoke-sentinel write
  - On 200 with `was_already_revoked=false` (first revoke):
    - Server Action returns `Result.ok({revoked_at, was_already_revoked: false})`

    - Toast "Key revoked successfully" (4s; per BR-R-2 the toast carries an Undo-action SLOT but the action is NOT wired — revoke is irreversible per security.md §8.2; the slot exists in case future Story adds reactivation)

    - Same revalidate + close
  - On 404 `404_api_key_not_found` (cross-user IDOR — should NOT happen via normal UI flow since the user reached this dialog from the row's [⊗] button which already passed the AC1 list user-binding):
    - Toast "This key is no longer available" (defence-in-depth — preserves the anti-enumeration collapse from server)
    - Close + revalidate
  - On 401: redirect to signin (BR-L-3)
  - On 403 `403_csrf_check_failed`: CSRF refresh + retry once
  - On 5xx: generic toast; Revoke button re-enables for retry
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-R-1 | Type-name-to-confirm guard is MANDATORY per SM design choice (parity with GitHub repository deletion + Stripe API key deletion; anti-misclick). The comparison is EXACT case-sensitive Unicode equality (`typed === name`). NFC normalization is applied to BOTH sides before comparison (so a user typing the name via a different IME composition path matches). |
| BR-R-2 | The Revoke action is IRREVERSIBLE per security.md §8.2 contract. The toast on success does NOT offer an Undo action (would be misleading). Future Story may add reactivation (Story 5.1 boundary lock REJECTED reactivation; if architecture changes, Story 5.5 would gain Undo). |
| BR-R-3 | The dialog is a Dialog (NOT a Drawer) — modal-blocking per shadcn-ui DialogContent. Focus trap is enforced. ESC closes (Cancel). |
| BR-R-4 | The [Revoke] button has `<Button variant="destructive">` (front-end-spec §5.1 — red colour) AND the loading-state spinner (in-flight). Visual hierarchy: [Cancel] = ghost (low emphasis) + [Revoke] = destructive (red, high emphasis, deliberately disabled until confirm-text matches per WCAG 3.3.4 error prevention for legal/financial/data changes). |
| BR-R-5 | Idempotent re-revoke (Story 5.1 `was_already_revoked=true`) surfaces a DIFFERENT toast variant — info-level "Key was already revoked" with the historical `revoked_at` timestamp. This is UX-distinct from the success path so the user understands the action was a no-op. |
| BR-R-6 | The row visual transition (active → revoked-with-opacity-0.5) happens via Next.js `revalidatePath` triggering a Server Component re-render — there is NO optimistic UI in Story 5.5. SM defaults to server-state-driven UI for correctness (an optimistic revoke would need to roll back on server failure, adding complexity for marginal speed benefit). |
| BR-R-7 | If the user closes the dialog (Cancel / ESC / outside-click / [×]) AFTER typing the confirm name, the typed value is discarded (uncontrolled input — no React state preservation). Re-opening the dialog presents a blank input. |
| BR-R-8 | The dialog displays the key Prefix alongside the Name — defence-in-depth against a user revoking the wrong key when they have multiple keys with the same name (BR-1.8 cascade — Story 5.1 does NOT enforce unique names). The Prefix is the first 12 chars (`he-XXXXXXXXX`) per Story 5.1 BR-2.5 — sufficient for visual disambiguation. |
| BR-R-9 | The dialog's "key name to confirm" label uses the key's literal name (i18n with interpolation `account.keys.revoke.confirm_label({name})`) — the name renders via JSX text node (React auto-escapes; defends against `<script>` in name). |
| BR-A11Y-10 | The Dialog has `role="alertdialog"` (NOT just `role="dialog"`) — signals destructive-action semantics to screen readers. WCAG 3.3.4 + WAI-ARIA Authoring Practices `alertdialog` pattern. |
| BR-A11Y-11 | The type-name-to-confirm input has `aria-label="Type the key name {name} to confirm revoke"` (visible label may be visually compact; sr-only label expansion ensures screen-reader users get the full instruction). Default focus is the [Cancel] button (Q-FOCUS1 + WCAG 3.3.4); the type-name input is the SECOND tab stop. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| Confirm-name input | string | yes | Must equal the key's `name` exactly after NFC | (no error message — silent disable of Revoke button) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Typed name does not match | n/a | (no error — button stays disabled) | Revoke button disabled until match |
| Server 200 + was_already_revoked=true | 200 | "Key was already revoked." | Info toast; close + revalidate |
| Server 200 + was_already_revoked=false | 200 | "Key revoked successfully." | Success toast; close + revalidate |
| Server 404 | 404 | "This key is no longer available." | Toast; close + revalidate |
| Server 401 | 401 | (no toast — redirect) | router.replace to signin |
| Server 403 csrf | 403 | (no toast initially) | CSRF refresh + retry once |
| Server 5xx | 5xx | "Service temporarily unavailable." | Generic toast; Revoke re-enables |

**UI Interaction**
| Trigger | Behavior |
|---------|----------|
| User clicks [⊗] | Dialog opens; focus → [Cancel] (default-focus on safe choice per Q-FOCUS1) |
| User tabs into the confirm input | Input gets focus; aria-label announced |
| User types matching name | Revoke button enables; visual feedback (button color changes from grey to red) |
| User types non-matching name | Revoke button stays disabled |
| User clicks Cancel / ESC / outside / [×] | Dialog closes; typed text discarded; focus returns to the [⊗] button on the row |
| User clicks Revoke | Spinner; on success toast + close + revalidate |
| Screen-reader user enters dialog | `role="alertdialog"` announces "Revoke API key" + body text + label; user navigates via Tab |

**Examples**
- **Input**: User clicks [⊗] on key named "My First Key". Types "My First Key" exactly. Clicks Revoke → 200 `was_already_revoked=false`; success toast + row revoked.
- **Input**: User clicks [⊗], types "my first key" (lowercase) → Revoke button stays disabled (case-sensitive per BR-R-1).
- **Input**: User clicks [⊗], types correctly, clicks Revoke; another tab had just revoked → 200 `was_already_revoked=true`; info toast.
- **Input**: User clicks [⊗], types correctly, clicks Cancel mid-confirmation → dialog closes; no API call; row unchanged.
- **Input**: User clicks [⊗] on a key that another tab just deleted (impossible currently — delete is not in scope, but if Story 5.7 adds it) → 404 toast.

## Dev Notes

### Technical Constraints

- **Frontend stack** [→ tech-stack.md#2.1]: Next.js 14.2+ App Router; TypeScript 5.4+ strict mode; shadcn-ui + Tailwind 3.4+; next-intl 3.x; React Hook Form 7.x + Zod 3.x. **No new top-level dependencies** — every component is built from existing shadcn-ui primitives.
- **Server Components** [→ tech-stack.md#2.1; coding-standards.md#12.2]: The page + sub-page are RSC; `'use client'` directive ONLY on components that need browser-side interactivity (modals, drawers, form components). RSC default keeps client bundle minimal.
- **Server Actions** [→ coding-standards.md#12.2]: All mutations go through `'use server'` Server Actions. Cookie passthrough via `cookies()` from `next/headers`. CSRF tokens flow through automatically with the cookie since they live in `he_csrf` cookie (Story 2.2 BR-3.7 pattern). NO direct `fetch` from client components to the api-gateway.
- **No TanStack Query** [→ Q-T1 SM default]: Per Q-T1, Story 5.5 uses Server Components + `revalidatePath` for state coherence. Tech-stack lists TanStack Query as available; Story 5.5 declines per KISS. If Architect rules MUST-USE, swap in a `useApiKeys()` hook on the client side wrapping `listMyKeys()`.
- **No new HTTP routes** [→ rest-api-spec.md#5.1.3]: Story 5.5 consumes existing endpoints. The console BFF Server Actions are SERVER-SIDE functions reachable only via the `<form action={...}>` RSC pattern; they are NOT exposed as routes.
- **i18n** [→ front-end-spec.md#6.1, #6.2]: 10 MVP locales; en + zh-CN FULL; 8 stub-translated per Story 2.1 m-1 cascade. Use next-intl `getTranslations` server-side; `useTranslations` client-side. Namespace `account-keys`.
- **RTL** [→ front-end-spec.md#6.2]: `dir="rtl"` on `<html>` flows through next-intl `getLocale`. IP / CIDR / money inputs override with `dir="ltr"` per Q-RTL1. Test in Arabic (`ar`).
- **A11y** [→ front-end-spec.md#7.1]: WCAG 2.1 AA; axe-core scan on all surfaces; keyboard-only navigation; screen-reader announcements; focus management on modal open/close.
- **Plaintext discipline** [→ security.md#8.2, BR-1.5 cascade from Story 5.1]: NEVER persist plaintext client-side; NEVER log server-side; URL search-string scrubbed on confirm. Test surface: 5.5-SECURITY-001..003.
- **HTML escape** [→ coding-standards.md#12.2]: React JSX auto-escapes text node content; `dangerouslySetInnerHTML` is FORBIDDEN throughout this Story. Test surface: 5.5-UNIT-021 (HTML escape).
- **Performance** [→ front-end-spec.md#9.2]: LCP target ≤ 2.5s on 4G; page chunk ≤ 50KB gzipped (size-limit budget); the 7 new business components are tree-shakeable.

// apps/console/app/[locale]/(console)/keys/_actions/create.ts (excerpt — see T0.7 + T2.4)

'use server';
import { cookies, headers } from 'next/headers';
import { CreateApiKeyResponseSchema } from '@/lib/api/me-keys';
import type { Result, ApiError } from '@/lib/api/errors';

export async function createMyKey({ name }: { name: string }): Promise<Result<{ api_key_id: string; plaintext: string }, ApiError>> {
  const cookieHeader = cookies().toString();
  const csrf = headers().get('X-CSRF-Token') ?? '';
  const res = await fetch(`${process.env.INTERNAL_API_GATEWAY_URL}/v1/me/keys`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Cookie: cookieHeader, 'X-CSRF-Token': csrf },
    body: JSON.stringify({ name }),
    cache: 'no-store',
  });
  if (res.status === 201) {
    const parsed = CreateApiKeyResponseSchema.parse(await res.json());
    // BR-PD-3: NEVER log plaintext server-side
    const { plaintext, ...telemetry } = parsed;
    console.log('apikey_created', telemetry);
    return { ok: true, value: { api_key_id: parsed.api_key_id, plaintext } };
  }
  // ... handle 400 / 401 / 403 / 429 / 5xx per AC2 error table
  return { ok: false, error: await translateError(res) };
}
