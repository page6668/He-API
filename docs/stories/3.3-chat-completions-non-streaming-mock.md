### AC1: Handler Request / Response Contract — Non-Streaming Happy Path

**Scenario**
```gherkin
GIVEN the api-gateway binary built from apps/api-gateway/cmd/server, started on :8080, with HE_API_AUTH_SVC_URL pointing at a reachable auth-svc and HE_API_REDIS_URL pointing at a reachable Redis 7.2+ instance
AND a valid api_keys row exists (issued via the Story-3.2 IssueKeyForTest helper) so the bearer-auth middleware admits the request
WHEN a client issues `POST /v1/chat/completions` with header `Authorization: Bearer he-abc123XYZ...` and body:
  ```json
  {
    "model": "qwen-max",
    "messages": [
      {"role": "system", "content": "You are helpful."},
      {"role": "user", "content": "Say hi."}
    ],
    "stream": false,
    "temperature": 0.7
  }
  ```
THEN
  - the bearer-auth middleware (Story 3.2) admits the request and populates `r.Context()` with `APIKeyID` / `BearerUserID` / `Scope` (unchanged from Story 3.2 BR-1.4 — the handler MUST read these via `middleware.APIKeyIDFromContext` / `middleware.BearerUserIDFromContext` to confirm wiring; missing context values short-circuit to HTTP 500 with `500_gateway_misconfigured` per the project precedent at `apps/api-gateway/internal/handlers/2fa_disable.go:38`)
  - the handler decodes the JSON body (bounded by `http.MaxBytesReader(w, r.Body, 1<<20)` = 1 MiB, BR-1.2)
  - the handler returns HTTP 200 with `Content-Type: application/json; charset=utf-8` and a body matching this exact shape (whitespace-insensitive; field ordering matches OpenAI SDK expectations — `id` → `object` → `created` → `model` → `choices` → `usage`):
    ```json
    {
      "id": "chatcmpl-mock-<12-hex-chars>",
      "object": "chat.completion",
      "created": 1715000000,
      "model": "qwen-max",
      "choices": [
        {
          "index": 0,
          "message": {"role": "assistant", "content": "Hello from He-API mock. Real upstream lands in Story 4.x."},
          "finish_reason": "stop"
        }
      ],
      "usage": {"prompt_tokens": 10, "completion_tokens": 20, "total_tokens": 30}
    }
    ```
  - the response carries the standard SecurityHeaders bundle from the existing Story-2.2 middleware (CSP / HSTS / X-Frame-Options), and NO `Set-Cookie`, NO `X-He-Request-Id` header (request-id taxonomy lands in Story 3.6), NO `X-He-Selected-Model` (selected-model header lands when Smart Routing in Story 6.x materializes)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | The handler MUST be wired into the existing per-route bearer-auth wrap at `apps/api-gateway/cmd/server/main.go:223` — i.e. `mux.Handle("POST /v1/chat/completions", bearerAuth.RequireAPIKey(http.HandlerFunc(chat.ServeHTTP)))` — NOT global mux wrap. The `chatPlaceholder` inline function (Story 3.2 `main.go:306-314`) is DELETED in this Story per the Architect OQ6 ruling intent ("Story 3.3 supersedes within ~1 sprint"). |
| BR-1.2 | Request body MUST be read through `http.MaxBytesReader(w, r.Body, 1<<20)` (1 MiB). The OpenAI protocol does not formally bound request size, but a 1 MiB limit accommodates ~250k tokens of system+user prompt while preventing a single oversized payload from monopolising gateway memory. Exceeding the limit returns HTTP 413 with `{"error":{"code":"413_payload_too_large","message":"Request body exceeds 1 MiB.","type":"invalid_request_error","param":null,"he_request_id":null}}`. |
| BR-1.3 | The handler MUST use the existing `writeJSON` / `writeError` helpers from `apps/api-gateway/internal/handlers/auth.go:375-381` (DO NOT define a parallel error envelope — the OpenAI 5.1.2 error shape is the contract for Stories 3.2-3.6 already, BR-1.5 of Story 3.2). |
| BR-1.4 | The response `id` field MUST be `chatcmpl-mock-` + 12 lowercase hex chars derived from `crypto/rand` (NOT `math/rand`). The handler MUST construct it via a helper `newMockCompletionID()` so the test suite can stub the random source. Injection is via the `WithIDFactory(f func() string) ChatHandlerOption` constructor option per Architect Round 1 OQ4 ruling (parallel-test-safe; precedented by `NewAPIKeyAuthenticator` at `apps/api-gateway/internal/middleware/bearer_auth.go:204`). The package-mutable exported-var pattern (`var handlers.NewID`) is explicitly rejected because two concurrent `t.Run` cases that both stub a global race for shared state. |
| BR-1.5 | The response `created` field MUST be a Unix timestamp (seconds) — `time.Now().UTC().Unix()` — populated at response-write time. Tests MUST tolerate a ±5 second skew from `time.Now()` at assertion time. |
| BR-1.6 | The response `model` field MUST echo back the `model` field from the request body verbatim (after AC2 validation passes). The mock does NOT remap or alias models — that responsibility lands in Smart Routing (Epic 6). |
| BR-1.7 | The response `object` field MUST be the literal string `chat.completion` (NOT `chat.completion.chunk` — that is the streaming object, reserved for Story 3.4 SSE chunks). |
| BR-1.8 | The handler MUST log at INFO with `slog.String("event", "chat_completions_mock")` + `slog.String("model", req.Model)` + `slog.String("api_key_id", apiKeyID)` + `slog.Int("messages_count", len(req.Messages))` exactly once per accepted request (no per-message logging — avoids log spam on long conversations). PII redaction: NEVER log `messages[].content` (rest-api-spec.md §5.1 keeps prompts opaque; PII MUST be redacted before log output per `coding-standards.md §12.3`). |
| BR-1.9 | The handler context MUST be derived from `r.Context()` so the obs.WrapHTTPHandler-injected OTel span (`apps/api-gateway/cmd/server/main.go:258`) propagates trace-IDs into the eventual real-upstream call site (no-op for the mock in this Story, but the indirection MUST be in place — no `context.Background()` substitutions). |

### AC2: Request Validation + `stream=true` Deferral

**Scenario**
```gherkin
GIVEN the api-gateway started with the Story-3.3 chat handler wired
AND a client holds a valid bearer key admitting it past Story-3.2 auth
WHEN the client sends `POST /v1/chat/completions` with body `{"model": "qwen-max", "messages": [{"role":"user","content":"hi"}], "stream": true}`
THEN
  - the handler validates the JSON body successfully (model + messages present, well-formed)
  - the handler short-circuits on `stream=true` BEFORE the mock-response generation, emitting HTTP 501 with exact body:
    ```json
    {"error":{"code":"501_streaming_not_implemented","message":"Streaming chat completions are not yet implemented. Track Story 3.4 for delivery.","type":"server_error","param":"stream","he_request_id":null}}
    ```
  - the structured log line carries `slog.String("event", "chat_completions_stream_rejected")` + `slog.String("api_key_id", apiKeyID)` so the SRE dashboard can count premature stream-client usage (informs Story 3.4 priority + sequencing)
WHEN the client sends `POST /v1/chat/completions` with body `{"messages": [{"role":"user","content":"hi"}]}`  (model missing)
THEN
  - the handler emits HTTP 400 with code `400_invalid_request` and message `"Field 'model' is required and must be a non-empty string."`
WHEN the client sends `POST /v1/chat/completions` with body `{"model": "qwen-max", "messages": []}` (empty messages)
THEN
  - the handler emits HTTP 400 with code `400_invalid_request` and message `"Field 'messages' must be a non-empty array (max 256 entries) with each entry having role + string content."`
WHEN the client sends `POST /v1/chat/completions` with body `{"model": "qwen-max", "messages": [{"role": "wizard", "content": "hi"}]}` (invalid role)
THEN
  - the handler emits HTTP 400 with code `400_invalid_request` and the same `messages` error message (role-set rejection collapses into the messages-validity error)
WHEN the client sends a body that is not valid JSON (e.g., trailing comma, missing brace)
THEN
  - the handler emits HTTP 400 with code `400_invalid_request` and message `"Request body is not valid JSON."`
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | Validation order is FIXED: (1) `MaxBytesReader` truncation → 413 ; (2) JSON parse → 400 `Request body is not valid JSON.` ; (3) `model` presence + non-empty + length ≤ 100 → 400 invalid_request ; (4) `messages` non-empty + ≤ 256 entries + each entry has valid role + non-empty string content → 400 invalid_request ; (5) `stream=true` → 501 streaming_not_implemented ; (6) accept → emit mock response. This order MUST be preserved so test fixtures can stack one-condition-at-a-time without ambiguity. |
| BR-2.2 | The valid `role` set is exactly `{"system","user","assistant","tool"}`. The OpenAI protocol introduced `developer` in late-2024 GPT-4o family; this Story DEFERS `developer` until Epic 4 confirms which upstreams accept it (Architect rule: do NOT enrich beyond what the mock can faithfully demo). `function` is the legacy alias for `tool` per OpenAI deprecation notice and is NOT accepted. |
| BR-2.3 | The `stream=true` 501 path uses `type: "server_error"` (matching `rest-api-spec.md §5.1.2` mapping for 5xx codes) and sets `param: "stream"` so OpenAI-SDK error parsing surfaces the offending field cleanly. AC1 and other-400 cases use `type: "invalid_request_error"` per the same §5.1.2 mapping. |
| BR-2.4 | The handler MUST NOT echo back any of the request body in the error message (defence-in-depth — avoids log/error reflection of attacker-supplied data even though OpenAI's own server is forgiving here; aligns with `coding-standards.md §12.3` "All PII in logs..."). |
| BR-2.5 | The validation MUST happen in a pure function `validateChatRequest(req *ChatRequest) (validationError, ok)` so the test pyramid (unit > integration > e2e per `testing-strategy.md §13.1`) gets a fast feedback loop on every validation branch — TDD-friendly. |

**Business Rules**
| ID | Rule |
|----|------|

## Dev Notes

### Technical Constraints

- **OpenAI protocol fidelity (BR-1.7 / BR-1.4 / BR-1.6)** — The response shape MUST match `[Source: docs/architecture/rest-api-spec.md#5-api-规范api-specification]` §5.1.1 Chat Completions response stub. Field naming is `snake_case` per the OpenAI wire contract (verified at `[Source: docs/architecture/coding-standards.md#12-编码规范coding-standards]` §12.3 "API 字段命名遵循 OpenAI 协议（snake_case）"); internal gRPC keeps `camelCase` from proto defaults but that does NOT apply to this Story's REST surface.
- **Streaming deferral (AC2 + BR-2.3)** — `stream=true` MUST return HTTP 501 with `code=501_streaming_not_implemented` in this Story. The OpenAI 5.1.2 standard-error-code table at `[Source: docs/architecture/rest-api-spec.md#5-api-规范api-specification]` §5.1.2 does NOT list a 501 code (501 is reserved for OUR internal "feature not yet implemented" signalling — Story 3.1 ratified this taxonomy via `chatPlaceholder` 501 stub which we now formalize for the streaming sub-feature). Story 3.4 removes the 501 path entirely.
- **Bearer-auth wiring (BR-1.1)** — Per `[Source: docs/stories/3.2-bearer-token-api-key-auth.md]` AC1 BR-1.4, the per-route `mux.Handle("POST /v1/chat/completions", bearerAuth.RequireAPIKey(...))` registration is the contract — global mux wrapping would break the JWT-protected `/v1/auth/*`, `/v1/me*`, `/v1/account/data-export*` paths. This Story preserves the per-route wrap and only swaps the inner handler.
- **Request body size cap (BR-1.2)** — 1 MiB via `http.MaxBytesReader`. The existing auth-flow handlers cap at 8 KiB (`apps/api-gateway/internal/handlers/auth.go:72` / `:157` / `:196`) because those bodies are credentials-only; chat-completions bodies legitimately reach hundreds of kilobytes (system prompts, tool definitions, long conversation history). 1 MiB is the consensus OpenAI-clone bound (mirrors LiteLLM's default; Cloudflare Workers' free-tier body cap; etc.). Larger limits (~8 MiB for vision payloads) are deferred to Epic 9 when multimodal content lands.
- **PII redaction (BR-1.8)** — `messages[].content` MUST NEVER appear in any log line, OTel attribute, or error response. Per `[Source: docs/architecture/coding-standards.md#12-编码规范coding-standards]` §12.3 "所有 PII 在日志输出前脱敏". Test T1.7 enforces this on the structured log path; AC2 BR-2.4 enforces it on the error-response path.
- **Cold-start preservation (T5.3)** — Story 3.1 AC2 set a hard 1000-ms P95 cold-start SLO. The new handler is constructed in `main()` via `handlers.NewChatCompletionsHandler(logger)` — a single struct allocation + logger pointer copy, sub-millisecond cost. The structured-log writer + `crypto/rand` reader are lazy (first use is on first request). No measurable cold-start impact, but the developer MUST run the benchmark once and record it in Dev Log to confirm no regression vs the Story-3.2 baseline.
- **OpenTelemetry trace propagation (BR-1.9)** — `obs.WrapHTTPHandler` at `[Source: docs/architecture/source-tree.md#6-源代码组织source-tree]` `packages/go-observability/` injects the incoming request span into `r.Context()`. The handler MUST pass `r.Context()` through to all sub-calls (mocked here, but the call-site indirection is the Epic 4 hand-off point — `modelAdapter.Chat(r.Context(), req)` will be the swap-in).
- **Testing pyramid (per `[Source: docs/architecture/testing-strategy.md#13-测试策略test-strategy]` §13.1)** — Unit tests carry the bulk of the validation-branch coverage (~50% of total testing budget for this Story). Integration tests cover the bearer-auth chain wiring (~25%). The Python SDK contract test is a single E2E-style test (~5% of testing budget but disproportionately high-value because it's the only Story-3.3 test that catches "JSON tag typo silently breaks Pydantic parse" — a class of bug no Go-side test can ever surface).
- **Story 3.2 BR-2.8 enforcement-mechanism change (Architect Round 1 OQ1 ruling)** — Story 3.2 BR-2.8 originally enforced "no production binary may issue API keys" via the Go `_test.go` file-extension rule (`apps/auth-svc/internal/apikey/seed_test.go` is unimportable from any `cmd/...` binary). Story 3.3 needs the helper at CI/dev-bootstrap time (T3.5 + the `gateway / openai-sdk-contract` CI job), so the mechanism is being relaxed: the helper body moves to a non-test file `apps/auth-svc/internal/apikey/seed.go` exporting `apikey.SeedAPIKey(...)`, and BR-2.8's invariant is re-enforced via a CI import-graph audit (T3.6) that fails the build if `apps/api-gateway/cmd/server` or `apps/auth-svc/cmd/server` acquire a dependency on the `apikey` internal package. Only the test-utility binary `apps/auth-svc/cmd/issue-test-key` and `_test.go` files may import `apikey.SeedAPIKey`. The architectural intent of BR-2.8 (production binaries cannot mint keys) is preserved exactly; only the enforcement mechanism (file-extension → import-graph audit) changes.

```go
// File: apps/api-gateway/internal/handlers/chat_completions.go

// ChatRequest is the OpenAI-compatible inbound JSON body. Unknown fields
// are tolerated (passthrough via json.RawMessage for forward-compat with
// Stories 3.4-3.6 and Epic 4 parameter validation).
type ChatRequest struct {
    Model          string          `json:"model"`
    Messages       []ChatMessage   `json:"messages"`
    Stream         bool            `json:"stream"`
    Temperature    json.RawMessage `json:"temperature,omitempty"`
    MaxTokens      json.RawMessage `json:"max_tokens,omitempty"`
    Tools          json.RawMessage `json:"tools,omitempty"`
    ToolChoice     json.RawMessage `json:"tool_choice,omitempty"`
    ResponseFormat json.RawMessage `json:"response_format,omitempty"`
}

// ChatMessage matches the OpenAI message shape — string content only
// in this Story; multipart content arrays land in Epic 9 (multimodal).
type ChatMessage struct {
    Role    string `json:"role"`
    Content string `json:"content"`
}

// ChatResponse mirrors rest-api-spec.md §5.1.1 success body.
type ChatResponse struct {
    ID      string       `json:"id"`
    Object  string       `json:"object"`
    Created int64        `json:"created"`
    Model   string       `json:"model"`
    Choices []ChatChoice `json:"choices"`
    Usage   ChatUsage    `json:"usage"`

### Testing Requirements

**Story-specific test focus areas** (in addition to the project-default coverage thresholds):

1. **SDK parser compatibility (AC3 — highest unique value)** — The Python SDK's Pydantic-based response parser is the single source of truth for "does our shape work for real customers?" Field-name typos, missing required fields, and incorrect types all surface here in a way no Go-side test catches. The contract test MUST run in CI on every PR touching `apps/api-gateway/internal/handlers/chat_completions.go`.

2. **Validation branch coverage (AC2)** — Per `[Source: docs/architecture/testing-strategy.md#13-测试策略test-strategy]` §13.1 unit tests carry 50% of the testing budget. Every rule in the BR-2.1 ordered validation pipeline gets its own table-driven test case (one row per rule failure path + one happy path). Estimated 8 cases × 1 testfunc = ~50 lines.

3. **Determinism floor (AC4 — `TestChatCompletions_Determinism_1000Calls`)** — 1000 in-process invocations × ~50µs per call = ~50 ms test runtime. Cheap, guards against future "we accidentally added a random emoji to make the demo cuter" regressions that would silently break BR-4.4 ASCII-safety.

4. **Bearer-auth chain regression (T5.1 / T5.2)** — Story 3.2 owns the auth surface; Story 3.3's main risk is "I changed `main.go` and accidentally broke the wrap". T5.1 + T5.2 are paired guards: one positive (auth ok → 200), one negative (no header → 401, handler NEVER invoked via the panic-on-call sentinel approach Story 3.2 BR-1.1 documented).

5. **Cold-start regression (T5.3)** — Story 3.1's 1000-ms P95 cold-start SLO is a hard contract. The Dev MUST run the benchmark once and record numeric results in Dev Log. Acceptance criteria for "no regression" is the 95th percentile staying within +50 ms of the Story-3.2 baseline (recorded at `[Source: docs/stories/3.1-gateway-http-framework-health-coldstart.md]` Dev Agent Record section).

6. **PII non-leakage (T1.7)** — Crucial defence against the "I added a debug log line during dev and forgot to remove it" regression. Test pattern: capture all log output during a known-bad request (content includes the literal token `SHOULD_NEVER_APPEAR_IN_LOG`); assert the captured buffer does NOT contain that string. Lightweight, high-leverage.

7. **Test integrity (per testing-strategy.md alignment)** — All tests MUST use real assertions (e.g., `assert.Equal` with concrete expected values). NO conditional `if got != want { /* ignore */ }` blocks; NO `_ = err`-style discards in test bodies. Stories 3.1 and 3.2 set the precedent; this Story carries the convention forward.

**OQ4 — handler factory pattern: package-mutable `handlers.NewID` exported var vs constructor-injected idFactory.**

**Ruling**: PREFER constructor-injection. The package-mutable var pattern (`var NewID = newMockCompletionID` + tests reassign) works for serial tests but is **parallel-test brittle**: two concurrent `t.Run` cases that both stub `handlers.NewID` race for the global state. The bearer_auth.go module at `apps/api-gateway/internal/middleware/bearer_auth.go:204` already establishes the constructor-injection precedent (`NewAPIKeyAuthenticator(upstream, redisFactory, logger)`). Apply the same pattern here:

```go
type ChatCompletionsHandler struct {
    logger *slog.Logger
    newID  func() string  // injected; production default is newMockCompletionID
}

func NewChatCompletionsHandler(logger *slog.Logger, opts ...ChatHandlerOption) *ChatCompletionsHandler {
    h := &ChatCompletionsHandler{logger: logger, newID: newMockCompletionID}
    for _, opt := range opts { opt(h) }
    return h
}

type ChatHandlerOption func(*ChatCompletionsHandler)

func WithIDFactory(f func() string) ChatHandlerOption {
    return func(h *ChatCompletionsHandler) { h.newID = f }
}
```

Test usage: `NewChatCompletionsHandler(testLogger, WithIDFactory(func() string { return "chatcmpl-mock-deadbeef1234" }))` — no global state, parallel-test safe.
