## Epic Context
**Epic**: 9 - 监控、日志与多模态
用户级用量大盘 + 历史日志 + Vision/ASR/TTS 多模态接入。Epic DoD: 控制台用量大盘可用 · 90 天历史日志可下载 · 图像/语音多模态 API 可调通。9.4 is the operational-observability spine under the whole epic — it does not close a DoD bullet, it makes every other story's request path debuggable as one connected trace.

**Story Deliverables**:
- `packages/go-observability`: install a GLOBAL W3C `tracecontext` + `baggage` propagator (`obs.SetupPropagation()`), and an outbound-client helper (`obs.NewHTTPClient()` / `obs.WrapTransport()`) that wraps `otelhttp.NewTransport` so EVERY connect-RPC / HTTP client injects `traceparent`. (Today: NO global propagator is set anywhere and NO outbound client is instrumented → every service starts a fresh ROOT trace and the chain is broken.)
- Wire `obs.SetupPropagation()` into every service `cmd/server/main.go` (right after `otel.SetTracerProvider`), and replace every bare `&http.Client{}` that builds a downstream connect client with the instrumented client (routingclient, notifyclient, adapterclient, auth/notification/usagelog/billing/payment upstreams).
- Kafka trace propagation: inject W3C `traceparent` into `kafka.Message.Headers` on every produce (billingemit, analyticslog, auth audit, usage-log-export) and extract+continue on every consume so async hops (billing-svc / analytics-svc / export worker) join the originating trace.
- A bounded head-sampling policy (`ParentBased(TraceIDRatioBased)`) driven by `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG`, with the gateway as the sampling root.
- Grafana visibility: the existing Jaeger datasource surfaces a full request waterfall; Loki↔Jaeger derived-field correlation on `trace_id` + `he.request_id` (log→trace and trace→logs pivot); an operator runbook ("trace one request by `he.request_id`").
- A PII-in-spans guard (non-negotiable security rule): span attributes are an allow-list of registered `he.*` keys + OTel `http.*` semconv only — NEVER prompt/response bodies, API keys, `Authorization`, email, or client IP. New `he.*` attributes registered in arch §11.5.
- otel-collector config: error-trace retention + a PII-scrub processor (defense-in-depth), per Architect ruling.
- Doc/registry updates: arch §11.5 (`he.*` span attrs), §11.1 (Jaeger→Grafana note), `infrastructure-deployment` (sampling + collector config), an operator trace runbook.

### AC1: 同步全链路贯通 — 跨服务 W3C trace context 传播（global propagator + 出站 client 注入）

**Scenario**
```gherkin
GIVEN
  - Story 1.4 shipped `packages/go-observability` (NewTracerProvider → OTLP/gRPC exporter, WrapHTTPHandler → otelhttp server span) and every service main calls otel.SetTracerProvider (e.g. api-gateway/cmd/server/main.go:102)
  - Story 3.6 derives he_request_id = "req_"+hex(traceID[0:6]) and stamps it as the `he.request_id` span attribute on the server span
  - TODAY there is NO global TextMapPropagator and every downstream connect client is built with a bare &http.Client{} (routingclient/client.go:46, adapterclient/registry.go:261, main.go:131/263/279/490/844/856), so otelhttp neither extracts an incoming `traceparent` (server side) nor injects one (client side)
WHEN
  - A single request enters the gateway (e.g. POST /v1/chat/completions) and fans out across connect-RPC to routing-svc → auth-svc (key validation) → adapter (upstream model) → notification/billing as needed
THEN
  - The shared `obs` package installs a GLOBAL composite propagator `tracecontext` + `baggage` (`obs.SetupPropagation()`), called in EVERY service main immediately after otel.SetTracerProvider — so otelhttp server handlers EXTRACT the incoming `traceparent` and the server span becomes a CHILD of the caller's span (no longer a root)
  - EVERY outbound connect/HTTP client is built via the instrumented helper (`obs.NewHTTPClient()` whose `Transport = otelhttp.NewTransport(base)`) so the client span INJECTS `traceparent` into the outgoing HTTP/2 headers
  - The result: one user request = ONE connected trace with ONE trace_id spanning gateway→routing-svc→auth-svc→adapter(+upstream)→…; `he.request_id` (3.6) is now identical on every span of that trace (it always was derived from the trace_id, but the trace_id is finally continuous)
  - Span attributes carry ONLY the registered `he.*` allow-list + OTel `http.*`/`rpc.*` semconv — NEVER request/response bodies, API keys, `Authorization` headers, email, or client IP (BR-TR-7)
  - Degraded mode is preserved: when OTEL_EXPORTER_OTLP_ENDPOINT is empty the propagator is STILL installed (so context flows for slog trace_id correlation) but spans are not exported (1.4 1.4-UNIT-210 parity) — propagation is independent of export
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-TR-1 | **Global propagator (shared, once)**: `obs.SetupPropagation()` sets `otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(propagation.TraceContext{}, propagation.Baggage{}))`. It is idempotent and lives in `packages/go-observability` so all 8 services get identical wire format (W3C `traceparent`/`tracestate` + `baggage`). Called in each `cmd/server/main.go` right after `otel.SetTracerProvider` (the SAME placement-before-use discipline as the meter provider, main.go:111-120). Exact propagator set = Q-PROP. |
| BR-TR-2 | **Outbound client instrumentation**: a shared `obs.NewHTTPClient(opts...)` (and/or `obs.WrapTransport(rt http.RoundTripper)`) returns an `*http.Client` whose `Transport` is `otelhttp.NewTransport(...)`. EVERY downstream connect client constructor MUST use it instead of a bare `&http.Client{}` (preserving each call site's existing `Timeout`). Sites: `routingclient`, `notifyclient`, `adapterclient`, and the `authv1connect`/`notificationv1connect`/`usagelogv1connect`/`billingv1connect`/`paymentv1connect` clients in `main.go`. A grep-auditable invariant: zero bare `&http.Client{}` remains on a downstream-RPC path (BR-TR-1/2 are the AC1 anti-orphan binding). |
| BR-TR-3 | **Server side already correct, do not regress**: `WrapHTTPHandler` (otelhttp.NewHandler) already opens the server span; once BR-TR-1 sets the global propagator it will automatically extract the parent. No per-service server change is needed beyond the propagator install. The connect HANDLERS (server) inherit the otelhttp-wrapped mux. |
| BR-TR-4 | **Baggage is minimal + PII-free**: if `he.request_id` is carried in baggage (Q-PROP) it is the ONLY business value permitted; user_id / email / api_key / model-input are NEVER put in baggage (baggage crosses the wire in cleartext headers and would re-introduce the very PII leak BR-TR-7 forbids). Default: rely on trace_id continuity, baggage carries at most `he.request_id`. |
| BR-TR-5 | **Sampling is head-based + parent-respecting (Q-SAMPLE)**: the SDK uses `ParentBased(TraceIDRatioBased(ratio))` so a child service ALWAYS honors the gateway root's sampling decision (a sampled request stays sampled across the whole chain; an unsampled one is dropped consistently — no half-traces). Ratio is read from `OTEL_TRACES_SAMPLER_ARG` (default 1.0 in non-prod, a bounded ratio in prod per Architect). The gateway is the sampling root. |
| BR-TR-6 | **The upstream-model call is the key business span** (Epic-4 path): the adapter→vendor HTTP call MUST appear in the trace as a client span so the trace shows where wall-clock time actually goes (TTFB to the model). **[Architect escalation correction 2026-06-11]** This span lives INSIDE the adapter microservice's own upstream client (`apps/adapters/*/internal/upstream/client.go`), NOT in the gateway's `adapterclient` — `adapterclient` is a connect-RPC client to the SEPARATE adapter service (`registry.go:266`), so BR-TR-2's wrap on it only produces the gateway→adapter hop span. Delivering BR-TR-6 therefore requires instrumenting the 6 adapter services (T6): the adapter must (a) install the global propagator + a wrapped server handler so the gateway→adapter `traceparent` is EXTRACTED and the adapter server span joins the trace, and (b) wrap its vendor upstream transport with `otelhttp.NewTransport(<existing custom transport>)` (preserving the per-vendor `ForceAttemptHTTP2`/ALPN policy, OQ-4.2-5) to emit the model-TTFB client span. Span name/attrs reuse `he.selected_model` where present; no prompt/response content (BR-TR-7). Depth of additional manual spans (DB/Redis/ClickHouse) = Q-SPANCOV (deferred). |
| BR-TR-7 | **PII / secret exclusion in spans (NON-NEGOTIABLE, security)**: span attributes are an ALLOW-LIST — the registered `he.*` keys (§11.5) + OTel `http.*`/`rpc.*`/`db.system` semconv ONLY. NEVER recorded as span data: chat prompt/response/messages, `Authorization`/`X-He-Api-Key` header values, API-key plaintext or full hash, user email, `client_ip`, full URLs with query secrets. ### AC2: 异步全链路贯通 — Kafka 消息透传 trace context（produce 注入 + consume 续接）

**Scenario**
```gherkin
GIVEN
  - The platform publishes async events over Kafka (segmentio/kafka-go): billing events (api-gateway/internal/billingemit/emitter.go), analytics request_logs (api-gateway/internal/analyticslog/emitter.go), audit (auth-svc/internal/audit/kafka.go), and the usage-log-export request (Story 9.3)
  - These messages today carry at most a manual `RequestId` proto field (Story 3.6) but NO W3C trace context, so the consuming worker (billing-svc credit / analytics-svc ingest / export worker) starts a brand-new root trace disconnected from the request that produced the event
WHEN
  - A produced message leaves a request that is inside an active trace, and later a consumer fetches it
THEN
  - On PRODUCE, the producer injects the current span context into `kafka.Message.Headers` as W3C `traceparent` (+ `tracestate`) via the global propagator over a `propagation.HeaderCarrier`-style adapter for kafka headers (a small shared `obs` kafka-carrier helper)
  - On CONSUME, the worker EXTRACTS that context from the message headers and starts its processing span as a CHILD of the producing span (sync-style parent) OR as a NEW trace with a SPAN LINK back to the producer — the choice (child vs link) is Q-KAFKA, because Kafka is at-least-once + fan-out and a strict parent can distort latency/retry semantics
  - The result: the async leg (e.g. gateway billing emit → billing-svc credit apply, or gateway analytics emit → analytics-svc request_logs ingest) is visible in the SAME trace (or one link-hop away) as the originating /v1/* request
  - Headers carry ONLY `traceparent`/`tracestate`/`baggage` (+ the existing `RequestId`) — never PII (BR-TR-7 applies to message headers too)
  - At-least-once redelivery is safe: a redelivered message re-extracts the same upstream context and creates a fresh (idempotent-by-design) consumer span — no trace corruption, no duplicate side effect beyond the consumer's own existing idempotency guard
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-TR-8 | **Produce-side injection (shared helper)**: a single `obs` helper (e.g. `obs.InjectKafkaHeaders(ctx, &msg)`) writes the global propagator's fields into `kafka.Message.Headers`. EVERY producer uses it: `billingemit`, `analyticslog`, auth `audit/kafka.go`, and the 9.3 usage-log-export publisher. Additive — existing headers/`RequestId` are preserved. |
| BR-TR-9 | **Consume-side extraction + span start**: a matching `obs.ExtractKafkaHeaders(ctx, msg) (context.Context)` reconstitutes the upstream context; the consumer then `tracer.Start(ctx, "<topic> consume", trace.WithSpanKind(SpanKindConsumer)[, trace.WithLinks(...)])`. Child-vs-link semantics = Q-KAFKA (default SM proposal: **span link** for fan-out/at-least-once topics, child for strictly 1:1 request→worker handoffs). |
| BR-TR-10 | **At-least-once safety**: a redelivered message produces a NEW consumer span sharing the same upstream link/parent — trace stays well-formed; the side-effect idempotency remains the consumer's existing guard (e.g. 9.3 claim guard, billing dedup). Tracing adds NO new exactly-once requirement. |
| BR-TR-11 | **Producer span timing**: the produce call itself is wrapped in a short producer span (`SpanKindProducer`) so the trace shows the enqueue point; injection happens AFTER the span context exists. Producing OUTSIDE a trace (e.g. a cron/cold path) → no `traceparent` injected (consumer correctly roots a new trace) — no error. |
| BR-TR-12 | **Header PII rule**: kafka headers carry ONLY `traceparent`/`tracestate`/(optional) `baggage` + the pre-existing `RequestId`. NEVER user_id/email/key/model-input in headers (BR-TR-7 / BR-TR-4 extended to Kafka). |

**Data Validation**
| Field / input | Rule | Behavior on invalid |
|---------------|------|---------------------|
| `traceparent` kafka header | W3C format | malformed/missing → consumer starts a new root trace (no crash); logged at debug |
| message with no trace headers (legacy/in-flight) | tolerated | consumer roots a new trace — back-compat for messages produced before 9.4 ships |
| baggage header size | bounded (W3C ≤ 8KB) | oversized → propagator drops baggage; trace_id still propagates |

**Error Handling**
| Scenario | Behavior | Action |
|----------|----------|--------|
| produce fails | existing producer error path unchanged; the span records the error status (no PII) | inherited from each emitter |
| consumer can't extract context | new root trace + debug log | message still processed (tracing never blocks business logic — TS-CONS-005 parity) |
| redelivery (at-least-once) | new consumer span, same link/parent | idempotency = existing consumer guard, not tracing |

**Examples**
- **Input**: a billed `/v1/chat/completions` request emits a billing event → **Expected**: the Kafka message has a `traceparent` header; billing-svc's credit-apply span links back to (or parents under) the gateway request trace — an operator opening the request trace in Grafana sees the downstream credit application.
- **Input**: a message produced by the pre-9.4 build (no headers) is consumed after 9.4 deploys → **Expected**: consumer roots a fresh trace, no error (back-compat).

### AC3: Grafana 可见 + trace↔log 关联 + 采样/PII 策略（operator visibility，epic AC 落地）

**Scenario**
```gherkin

  - Story 1.4 deployed Jaeger (in-memory) behind the otel-collector and Grafana with a Jaeger datasource + Loki datasource (infra/helm/observability)

  - The sampling policy (BR-TR-5) keeps prod trace volume bounded while ALWAYS keeping a trace whole (parent-based); error traces retention is handled by the collector (Q-COLLECTOR — e.g. tail-sample errors at 100%)

```

**Business Rules**
| ID | Rule |
|----|------|
| BR-TR-13 | **Grafana is the viewing surface (epic AC)**: traces are viewed in Grafana via the EXISTING Jaeger datasource (1.4). | BR-TR-14 | **Bidirectional trace↔log correlation**: provision (a) a Loki datasource `derivedFields` entry matching `trace_id` (regex over the JSON slog field) → Jaeger trace link, and (b) the Jaeger datasource `tracesToLogsV2` config → Loki, keyed on `trace_id`. `he.request_id` is the human handle; `trace_id` is the machine join key. Lives in the observability helm values (`grafana-datasources`), not in app code. |
| BR-TR-15 | **Sampling & retention policy (documented)**: `infrastructure-deployment` records the head-sampling ratio per env (BR-TR-5) + the collector tail-sampling/error-retention policy (Q-COLLECTOR). **Data Validation**
| Field / config | Rule | Behavior on invalid |
|----------------|------|---------------------|
| Loki `derivedFields` regex | matches the slog `trace_id` JSON field | misconfig → link absent (no data loss); caught by a values-lint / manual smoke |
| Jaeger `tracesToLogsV2` datasource | valid Grafana datasource yaml | invalid yaml → Grafana datasource fails to load (caught at deploy) |

**Error Handling**
| Scenario | Behavior | Action |
|----------|----------|--------|
| Jaeger in-memory evicts an old trace | trace not found in Grafana | expected (staging retention ~2h, 1.4 Q4) — runbook notes it |

### Telemetry / Span Design (WHY, not full code)
- **Propagator (BR-TR-1, Q-PROP).** Composite `tracecontext`+`baggage`. WHY both: `tracecontext` carries trace_id/span_id (the continuity); `baggage` is OPTIONAL and, if used, carries at most `he.request_id` — never PII (it crosses the wire as a cleartext header, BR-TR-4). Set ONCE in `obs`, called per service main. The alternative (per-service propagator) risks wire-format drift across 8 services — rejected.
- **Outbound client (BR-TR-2).** `obs.NewHTTPClient` returns `&http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport), Timeout: opt}`. WHY a shared helper: there are ≥9 client-construction sites; a helper makes "instrumented by default" the path of least resistance and lets the T-AUDIT grep enforce zero bare clients. Trade-off: callers must pass their `Timeout` through the helper (mechanical).
- **Sampler (BR-TR-5, Q-SAMPLE).** `ParentBased(TraceIDRatioBased(r))`. WHY parent-based: a downstream service must NOT independently decide to drop a span the gateway already sampled (that yields a trace with holes). Root = gateway. Ratio via env so prod can throttle without a redeploy. Errors-always-sampled is a tail decision → collector (Q-COLLECTOR).
- **Kafka carrier (BR-TR-8/9, Q-KAFKA).** A `propagation.TextMapCarrier` over `[]kafka.Header`. Inject on produce, extract on consume. Child vs span-link: a span LINK is the safer default for at-least-once + fan-out (a redelivered or fanned-out message doesn't distort the producer's latency tree), a CHILD reads cleaner for strict 1:1 request→worker handoffs. Architect rules per topic (Q-KAFKA).
- **Store + Grafana (BR-TR-13, Q-STORE).** SM-preferred minimal: KEEP Jaeger (1.4-deployed), surface in Grafana via the existing Jaeger datasource — the epic AC ("Grafana 可看到完整请求链路") is satisfied without a Tempo migration. Tempo (TraceQL, metrics-to-traces, object-store retention) is a heavier, separately-justified change → Architect Q-STORE. §11.1 today names Jaeger.
- **Correlation (BR-TR-14).** Loki `derivedFields` regex on the slog `trace_id` → Jaeger; Jaeger `tracesToLogsV2` → Loki, both keyed on `trace_id`. Lives in helm values, not app code. `he.request_id` is what the operator types; `trace_id` is what the tools join on.

### Security / Privacy (this story is security_sensitive)
- **Span/header PII allow-list (BR-TR-7/12).** The single most important rule: traces and Kafka headers are a NEW data path to a NEW store (Jaeger) — they must obey the SAME PII rules as logs (1.4 slog redaction) and exports (9.2/9.3). Prompts, completions, API keys, `Authorization`, email, IP NEVER become span attributes or header values. Enforced at code (allow-list, grep-auditable) + collector scrub (defense-in-depth).
- **No data-export-to-overseas regression.** Tracing adds no cross-border egress (Jaeger/collector are in-cluster); the §11.3 `DataExportSuspect` alert (must stay 0) is unaffected — but Dev must NOT point the OTLP exporter at any external SaaS tracing backend. In-cluster collector only.
- **Sampling ≠ security.** Sampling drops VOLUME, never masks PII — PII must be absent regardless of sample rate.
