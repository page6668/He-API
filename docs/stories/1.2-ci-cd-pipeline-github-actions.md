## 验收标准

> ⚠️ **遗留格式说明**: Epic-1 YAML 使用旧版 `acceptance_criteria` 字符串数组格式。Enhanced AC 结构（GIVEN/WHEN/THEN + 业务规则 + 错误处理）尚未填充；本 Story 按字面 AC 渲染，并提供 SM 展开说明以闭合需求歧义。

### AC1: PR 自动跑 lint / unit / integration

**字面要求**: PR 自动跑 lint / unit / integration

**展开（SM 解释）**:

- 任意对 `main` 分支的 PR 打开（`pull_request: opened`）、再推（`synchronize`）、重新打开（`reopened`）均触发：
  - `lint.yml`：执行 `pnpm lint`（TS 端，通过 Turborepo 编排 `eslint`）+ `golangci-lint run ./apps/... ./packages/...`（Go 端，含 govet / gosimple / staticcheck / ineffassign / errcheck）+ `gofumpt -l -d .` 不应有 diff。`[Source: docs/architecture/coding-standards.md#12.1]`
  - `test.yml`：
    - **unit**：`pnpm test`（Turborepo 编排 Vitest，本 Story 阶段 shared-types 无业务测试，命令必须成功且 exit 0；占位单元测试可由 Dev 在 `packages/shared-types/__tests__/empty.test.ts` 添加）；`go test ./apps/api-gateway/... -count=1`（apps/api-gateway 在 Story 1.1 已有占位 `main.go`，本 Story 内 Dev 至少添加一条占位 `_test.go` 让 test 链路实际跑过）。
    - **integration**：声明独立 job（matrix: `integration`），本 Story 阶段以 `echo "no integration tests yet — gated by Story 1.5/1.6"` + `exit 0` 占位，但 job 必须在 PR 检查列表中出现且通过，确保 1.5/1.6 接入时无需重新配置 PR 检查项。`[Source: docs/architecture/testing-strategy.md#13.2]`
  - 三个 workflow 全部成功，PR 上的 "Checks" 显示 6 个状态项（lint-ts / lint-go / unit-ts / unit-go / integration / build-image-pr）全绿。
- PR 触发时 `build-images.yml` 仅执行 `docker build` 不 push（验证 Dockerfile 可构建），从而尽早暴露镜像层面的构建错误。
- 任一 job 失败 → PR 的 "Required" 状态变红 → branch protection 阻止合并（branch protection rule 由仓库 Admin 配置，本 Story 在 README 给出操作说明，不在代码内配置）。

### AC2: merge 自动部署 staging

**字面要求**: merge 自动部署 staging

**展开（SM 解释，Architect Round 1 已仲裁 → 采纳 Gated graceful skip 策略 + GITHUB_TOKEN 闭环）**:

- PR 合并到 `main` 后，工作流链路按以下顺序自动触发：
  1. **build-images.yml** 的 `build-image-main` job（`on: push: branches: [main]`）：`docker build` + `docker push` 到阿里云 ACR (`${{ secrets.ACR_REGISTRY }}/he-api/api-gateway:${git_sha}`，仅 immutable tag)，并通过 `actions/upload-artifact@v4` 输出 `image-sha.txt`（内容为 `${{ github.sha }}`）作为 workflow artifact。需消费 `secrets.ACR_REGISTRY / ACR_USERNAME / ACR_PASSWORD`。`[Source: docs/architecture/infrastructure-deployment.md#7.3]`
  2. **deploy-staging.yml**（`on: workflow_run: workflows: ["build-images"], types: [completed], branches: [main]`；job 级 `if: ${{ github.event.workflow_run.conclusion == 'success' }}`）：
     a. **update-helm-values**：通过 `actions/download-artifact@v4` 拉取上游 `image-sha.txt` → 以 `git_sha` 用 `yq` 改写 `infra/helm/api-gateway/values-staging.yaml` 的 `image.tag` 字段，使用内置 `${{ secrets.GITHUB_TOKEN }}`（job-level `permissions: { contents: write }`）执行 commit + push 回 `main`（commit 信息：`chore(deploy): bump api-gateway staging to <sha>`）。**关键**：GitHub 官方约定 `GITHUB_TOKEN` 推送的 commit/push 事件**不会**再次触发同仓库的 workflow run，从机制层面切断 push → deploy-staging → bot-commit → push 的无限循环。
     b. **trigger-argocd-sync**：可选地通过 `argocd app sync` CLI（Story 1.3 接入后启用），当前阶段以 stub 步骤打印 "ArgoCD endpoint not configured (Story 1.3 dependency)" + `exit 0`，并保留 `if: vars.ARGOCD_ENDPOINT != ''` 真实分支以便 Story 1.3 接入时无需改 workflow。
- **Gating（Architect Round 1 已批准）**：阿里云 ACR 与 ArgoCD 在 Story 1.3/1.4 才落地，本 Story 必须支持 secrets/资源缺失下的 graceful skip。**统一采用 job-env 映射模式**（替代不可靠的 step 级 `if: secrets.X != ''`）：
  - `build-image-main` job 在 env 段映射 `HAS_ACR: ${{ secrets.ACR_USERNAME != '' && 'true' || 'false' }}`；push 步骤 `if: env.HAS_ACR == 'true'`，否则走 fallback 步骤打印 "ACR_USERNAME not configured (Story 1.3 dependency)" 到 `$GITHUB_STEP_SUMMARY` 并 exit 0；workflow artifact 仍照常上传 `image-sha.txt`，保证下游 workflow_run 触发条件不被破坏。
  - `update-helm-values` job 在 **checkout 之后**用 step-level output 探测文件存在性（`id: probe_helm` step 运行 `[ -f infra/helm/api-gateway/values-staging.yaml ] && echo exists=true || echo exists=false` → `$GITHUB_OUTPUT`）；yq 改写步骤 `if: steps.probe_helm.outputs.exists == 'true'`，否则 fallback 打印 "values-staging.yaml not yet created (Story 1.3 dependency)" 并 exit 0。**重要时序约束**：不能将该 gating 放在 job env 段——job env 的求值时刻早于 `actions/checkout`，此时 `GITHUB_WORKSPACE` 为空，`hashFiles(...)` 永远返回 `''`，gating 永远走 fallback（M-new-1 修复）。
  - `trigger-argocd-sync` job 在 env 段映射 `HAS_ARGOCD: ${{ vars.ARGOCD_ENDPOINT != '' && 'true' || 'false' }}`；真实 sync 步骤 `if: env.HAS_ARGOCD == 'true'`。
  - 上游 `build-images` 即便走 gated skip 路径仍 exit 0 → workflow_run.conclusion = success → 下游 `deploy-staging` 仍触发并跑通各 gated 分支；workflow 整体以 exit 0 完成，即 "workflow 自动触发并端到端跑通"，符合"自动部署 staging" 的工作流契约；真实生效在 1.3/1.4 完成后无需修改 workflow 文件。
- **可验证标志**：合并 PR 后 30 秒内 Actions 标签页出现 `build-images` workflow run（main 触发分支）、其 success 后 1 分钟内出现 `deploy-staging` workflow run（workflow_run 触发分支），两者最终状态均为 success，job 摘要中包含 image SHA 与各 gating 跳过原因。

      ```yaml
            name: image-sha
            run-id: ${{ github.event.workflow_run.id }}
            github-token: ${{ secrets.GITHUB_TOKEN }}
        - name: Resolve image SHA from artifact
          run: echo "SHA=$(cat image-sha.txt)" >> "$GITHUB_ENV"
        - name: Probe helm values existence
          id: probe_helm
          run: |
            if [ -f infra/helm/api-gateway/values-staging.yaml ]; then
              echo "exists=true" >> "$GITHUB_OUTPUT"
            else
              echo "exists=false" >> "$GITHUB_OUTPUT"
            fi
        - name: Update helm values (real)
          if: steps.probe_helm.outputs.exists == 'true'
          env:
            SHA: ${{ env.SHA }}
          run: |
            yq eval -i '.image.tag = strenv(SHA)' infra/helm/api-gateway/values-staging.yaml
            git config --local user.email "github-actions[bot]@users.noreply.github.com"
            git config --local user.name  "github-actions[bot]"
            git add infra/helm/api-gateway/values-staging.yaml
            git commit -m "chore(deploy): bump api-gateway staging to ${SHA}"
            git push
        - name: Skip helm update (fallback)
          if: steps.probe_helm.outputs.exists != 'true'
          run: echo "values-staging.yaml not yet created (Story 1.3 dependency) — skipping update" >> "$GITHUB_STEP_SUMMARY"
      ```
    - **Push 使用默认 `GITHUB_TOKEN`**（C1 修复约定保持不变）：GitHub 官方约定 `GITHUB_TOKEN` 推送的 commit 不会触发同仓库 workflow，机制层面切断无限循环；job-level `permissions: contents: write` 提供该 token 的推送权限。
  - [x] Job `trigger-argocd-sync`（`needs: update-helm-values`）：
    - env 段映射 `HAS_ARGOCD: ${{ vars.ARGOCD_ENDPOINT != '' && 'true' || 'false' }}`。

    - Fallback step `if: env.HAS_ARGOCD != 'true'`：`echo "ArgoCD endpoint not configured (Story 1.4 dependency) — skipping sync" >> $GITHUB_STEP_SUMMARY` && exit 0。
  - [x] 工作流 summary 输出（`$GITHUB_STEP_SUMMARY`）：image SHA / helm values 是否被更新 / argocd sync 是否被触发 / 各 gating 跳过原因。

### 技术约束

- **CI 运行器**: GitHub-hosted runner `ubuntu-22.04`（本 Story 不引入自托管 runner）`[Source: docs/architecture/tech-stack.md#2.1]`
- **Node 版本**: 20 LTS（从根 `.nvmrc` 读取，由 `actions/setup-node@v4` 通过 `node-version-file: '.nvmrc'` 解析） `[Source: docs/architecture/tech-stack.md#2.1; Story 1.1 已固化]`
- **pnpm 版本**: 9.15.9（由根 `package.json` `packageManager` 字段锁定；`pnpm/action-setup@v4` 读取该字段） `[Source: Story 1.1 已固化]`
- **Go 版本**: 1.22+（`actions/setup-go@v5` 显式 `go-version: '1.22'`） `[Source: docs/architecture/tech-stack.md#2.1]`
- **Linter**: golangci-lint（含 govet, gosimple, staticcheck, ineffassign, errcheck）+ gofumpt `[Source: docs/architecture/coding-standards.md#12.1]`
- **TS Linter**: ESLint + Prettier（已在 Story 1.1 `pnpm lint` 链路就位） `[Source: docs/architecture/coding-standards.md#12.2]`
- **测试覆盖率门槛**: Go 后端 ≥ 70%（本 Story 阶段 api-gateway 仅占位 main，无业务逻辑，覆盖率指标不强制 fail；门槛在 Story 1.5 业务代码进入后才启用 fail-fast）`[Source: docs/architecture/coding-standards.md#12.1]`
- **GitOps 模型**: build-images.yml (build + push ACR + upload image-sha artifact) → **workflow_run completed/success** → deploy-staging.yml (download artifact → update Helm values via `GITHUB_TOKEN` → ArgoCD sync) `[Source: docs/architecture/infrastructure-deployment.md#7.3]`
- **缓存策略**: 必须启用 pnpm store cache、Go module cache、Docker buildx gha cache，目标二次 PR 的 lint+test+build 全链路 ≤ 60s
- **secrets 处理**:
  - 所有 secrets/vars 引用必须使用 `${{ secrets.* }}` 或 `${{ vars.* }}`，禁止 echo 完整 secret 值
  - **统一 gating 模式**（替代不可靠的 step 级 `if: secrets.X != ''`）：
    - **secrets/vars 类条件（与 workspace 无关）**：在 job env 段映射布尔字符串（`HAS_X: ${{ secrets.X != '' && 'true' || 'false' }}` 或 `${{ vars.X != '' && 'true' || 'false' }}`），步骤通过 `if: env.HAS_X == 'true'` 切换。适用于 `HAS_ACR`（消费 `secrets.ACR_USERNAME`）、`HAS_ARGOCD`（消费 `vars.ARGOCD_ENDPOINT`）。GitHub Actions 对 `secrets` context 在 step `if:` 中的直读支持不可靠，env-mapping 是官方推荐稳健方式。
    - **workspace-dependent 条件（必须在 checkout 之后求值）**：诸如 `hashFiles(...)`、文件存在性等依赖工作区内容的探测，**不可**放在 job env 段——job 级 `env:` 表达式在 step 启动之前求值，此时 `GITHUB_WORKSPACE` 为空目录，`hashFiles(...)` 永远返回 `''`，gating 失效。改用 **step-level output**：在 `actions/checkout` 之后插入 `id: probe_X` step 写 `echo "exists=true|false" >> "$GITHUB_OUTPUT"`，后续真实/fallback 步骤通过 `if: steps.probe_X.outputs.exists == 'true'` 切换。适用于 `HAS_HELM_VALUES`（M-new-1 修复）。
- **GitOps token 策略**（C1 修复）：deploy-staging.yml 使用内置 `${{ secrets.GITHUB_TOKEN }}` + job-level `permissions: contents: write`，**不引入** `GITOPS_BOT_TOKEN` 自定义 PAT；GitHub 官方约定 `GITHUB_TOKEN` 推送的 commit/push 事件不会再次触发同仓库 workflow，机制层面切断 push → deploy-staging → bot-commit → push 的无限循环
- **镜像 tag 策略**: 仅 push immutable tag `:${git_sha}`，**不**使用 `:staging-latest` mutable tag；ArgoCD 通过 Helm values 中的 `image.tag = ${git_sha}` 拉取唯一镜像，保证 GitOps 镜像不可变原则（避免同名 tag 内容变化导致 K8s pull policy 行为分歧与回滚追溯困难）
- **CGO 策略**: CI 测试路径 `CGO_ENABLED=1`（用于 `go test -race`）；Dockerfile 生产构建 `CGO_ENABLED=0`（静态二进制 + distroless）。两路径明确分离，便于 1.5/1.6 业务代码进入时定位 race detector 与纯 Go 路径的行为差异
- **本 Story 不引入**: 任何业务代码、数据库迁移、API endpoint、真实部署到 K8s 集群（K8s 由 Story 1.3 提供）

#### High Issues (1)

- **M-new-1: `HAS_HELM_VALUES` 在 job env 中使用 `hashFiles()` 时序错位，导致 gating 永远走 fallback** (T4 `update-helm-values` job, lines 226-228 / AC2 line 140)
  - 描述：T4 第 2 子任务在 job env 段声明 `HAS_HELM_VALUES: ${{ hashFiles('infra/helm/api-gateway/values-staging.yaml') != '' && 'true' || 'false' }}`。GitHub Actions 对 job 级 `env:` 表达式的求值发生在**所有 step 启动之前**，此时 `actions/checkout` 尚未执行，`GITHUB_WORKSPACE` 为空目录 → `hashFiles(...)` 返回空字符串 → `HAS_HELM_VALUES` 永远 `'false'`。
  - 影响：**Story 1.3 配置真实 `values-staging.yaml` 后，update-helm-values job 仍会全量走 Step 4 fallback 路径，永远不会真实改写 Helm values + git push**。这使整条 GitOps 流水线（build → push ACR → update Helm → ArgoCD sync）的"update Helm"环节静默失效——没有任何 error log，只有 step summary 一直打印 "values-staging.yaml not yet created"。是工作流契约的根本性误判，对 Story 1.3/1.4 端到端验证伤害大。
  - 根因：`hashFiles()` 求值时机 vs 工作区可见性的常见 GH Actions footgun。对照设计：HAS_ACR（消费 `secrets.*`）与 HAS_ARGOCD（消费 `vars.*`）都不依赖 workspace，env 段求值时机无问题；只有 HAS_HELM_VALUES 依赖 workspace 文件。
  - Fix（推荐方案）：将 HAS_HELM_VALUES 改为 **step 级 output**，在 checkout 之后求值：
    ```yaml
    steps:
      - uses: actions/checkout@v4
        with:
          ref: main
          token: ${{ secrets.GITHUB_TOKEN }}
      - uses: actions/download-artifact@v4
        with:
          name: image-sha
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
      - name: Resolve image SHA from artifact
        run: echo "SHA=$(cat image-sha.txt)" >> $GITHUB_ENV
      - name: Probe helm values existence
        id: probe_helm
        run: |
          if [ -f infra/helm/api-gateway/values-staging.yaml ]; then
            echo "exists=true" >> "$GITHUB_OUTPUT"
          else
            echo "exists=false" >> "$GITHUB_OUTPUT"
          fi
      - name: Update helm values (real)
        if: steps.probe_helm.outputs.exists == 'true'
        env:
          SHA: ${{ env.SHA }}
        run: |
          yq eval -i '.image.tag = strenv(SHA)' infra/helm/api-gateway/values-staging.yaml
          git config --local user.email "github-actions[bot]@users.noreply.github.com"
          git config --local user.name  "github-actions[bot]"
          git add infra/helm/api-gateway/values-staging.yaml
          git commit -m "chore(deploy): bump api-gateway staging to ${SHA}"
          git push
      - name: Skip helm update (fallback)
        if: steps.probe_helm.outputs.exists != 'true'
        run: echo "values-staging.yaml not yet created (Story 1.3 dependency) — skipping update" >> "$GITHUB_STEP_SUMMARY"
    ```
    同步更新 AC2 line 140 的 gating 描述（去掉 `HAS_HELM_VALUES` 在 env 段映射的说法，改为 "在 checkout 之后用 step output 探测文件存在性"）。同步技术约束 line 321 的统一 gating 模式表述：增加一条"workspace-dependent 条件（如 `hashFiles`、文件存在性）必须放在 checkout 之后的 step 级 `if:`，不可放在 job env"。
  - 不会受同类问题影响的其余 gating：HAS_ACR / HAS_ARGOCD 保持 job env 模式即可。

  - 影响：一旦 Story 1.3 配置真实 `GITOPS_BOT_TOKEN`（PAT），workflow 将无休止运行，消耗 GitHub Actions 配额 + 污染镜像 registry + 触发 ArgoCD 反复 sync。本 Story 因 secrets 未配置不会暴露此问题，但架构缺陷已"焊死"在 workflow 文件中。
  - Fix（任选其一，建议方案 1）：
    1. **方案 1（推荐）**：将 token 显式约定为 `${{ secrets.GITHUB_TOKEN }}`（在 job permissions 加 `contents: write`），并在 README/T5 中明示"GITOPS_BOT_TOKEN 即 GITHUB_TOKEN，由 GitHub 自动注入"。GitHub 官方文档：使用 `GITHUB_TOKEN` 创建的 commit/push 事件**不会**触发同仓库的下游 workflow run（这正是设计用途）。删除 README 中"需 admin 配置 GITOPS_BOT_TOKEN"条目。
    2. **方案 2**：保留自定义 PAT，但 commit message 加 `[skip ci]` 后缀 + 在 `deploy-staging.yml` 顶部加 job 级 `if: !contains(github.event.head_commit.message, '[skip ci]')`。同时在 README 标注此约束。
    3. **方案 3**：split 出独立 infra repo（架构文档 §7.3 提到的"separate repo or same"分支）——超出本 Story 范围，建议放入 Story 1.4 ArgoCD 设计。

#### High Issues (3)

- **M1: `wait-for-build` 轮询机制应改为 `workflow_run` 原生触发器** (T4 第 2 子任务)
  - 描述：T4 通过 `actions/github-script@v7` 轮询 `build-images.yml` 同 SHA 的 run 状态（超时 15min）。这是"两个独立 workflow 共享 push 触发 + 后者轮询前者"的反模式：
    - 浪费 Actions 分钟数（轮询本身占用 runner）
    - 状态机不可靠（network blip / API rate limit / build run 还没 enqueue 时轮询）
    - 调试困难（GitHub UI 看不到串联关系）
  - Fix：将 `deploy-staging.yml` 改用 `on: workflow_run`：
    ```yaml
    on:
      workflow_run:
        workflows: ["build-images"]
        types: [completed]
        branches: [main]
    jobs:
      gate:
        if: ${{ github.event.workflow_run.conclusion == 'success' }}
        # ... update-helm + trigger-argocd
    ```
    然后从 `build-images.yml` 的 main push 分支 job 输出 image SHA 作为 artifact，供 `deploy-staging.yml` 下载消费。删除 T4 的 `wait-for-build` job。

- **M2: `if: secrets.X != ''` 模式在 step-level 不可靠**（T3 build-image-main job / T4 update-helm-values job）
  - 描述：T3 设计 `if: secrets.ACR_USERNAME != ''` 保护 push 步骤。GitHub Actions 对 `secrets` context 在 `if:` 中的支持有以下限制：
    - secrets 在 step 级 `if:` 中可访问但不可靠（取决于工作流可见性）；
    - 更稳健的模式是先在 job env 中映射布尔值再用于 `if:`。
  - Fix：标准化模板：
    ```yaml
    jobs:
      build-image-main:
        env:
          HAS_ACR: ${{ secrets.ACR_USERNAME != '' && 'true' || 'false' }}
        steps:
          - name: Push to ACR
            if: env.HAS_ACR == 'true'
            run: docker push ...
          - name: Skip push (no ACR secrets)
            if: env.HAS_ACR != 'true'
            run: echo "ACR_USERNAME not configured (Story 1.3 dependency)" >> $GITHUB_STEP_SUMMARY
    ```
    在 T3 / T4 所有 `if: secrets.X != ''` 处统一改造。

- **M3: `golangci-lint run ./apps/... ./packages/...` 中 `./packages/...` 未在 go.work 注册**（T1 lint-go job）
  - 描述：当前 `go.work` 仅声明 `use ./apps/api-gateway`（Story 1.1 现状），`packages/proto/`、`packages/sdk-go/` 尚未创建。`golangci-lint run ./packages/...` 在没有 Go module 注册时会 error: "no Go files in /path/to/packages"。
  - Fix：本 Story 阶段 golangci-lint 作用域改为 `./apps/...`，将 `./packages/...` 延迟到 Story 4.x（sdk-go 引入时）。同步更新 README 中"本地 reproduce 命令"段。

#### Medium Issues (3)

- **m1: `staging-latest` 可变 tag 与 GitOps 镜像不可变原则冲突**（T3 build-image-main job）
  - 描述：Story 同时 push `:${git_sha}` 和 `:staging-latest`。后者是 mutable tag，对 GitOps（ArgoCD pull image tag → sync）不友好——同名 tag 内容会随 push 变化，可能引发 K8s pod 不重启（image pull policy=IfNotPresent 时）或难以追溯回滚。
  - Recommendation：仅 push immutable tag `:${git_sha}` + `:staging-<short-sha>`（人类可读但仍唯一）；`update-helm-values` job 写入 `image.tag: ${git_sha}` 即可。删除 `:staging-latest`。

- **m2: `go test -race` 依赖 CGO_ENABLED=1，与 distroless 镜像 CGO_ENABLED=0 行为不一致**（T2 unit-go / T3 Dockerfile）
  - 描述：`-race` 标志要求 CGO 启用；GitHub-hosted runner 默认 CGO_ENABLED=1，所以 `go test -race` 跑得过。但生产构建用 `gcr.io/distroless/static-debian12` + `go build` 默认 CGO_ENABLED=0（静态二进制），两个二进制行为分支可能不一致（cgo 路径 vs 纯 Go 路径）。
  - Recommendation：在 CI test 中显式 `CGO_ENABLED=1 go test -race`；在 Dockerfile 中显式 `CGO_ENABLED=0 go build`；在 dev log 注释清楚 CI 与生产构建的 CGO 差异，便于 1.5/1.6 业务代码进入时不踩 race detector 报告了 cgo 路径竞态的坑。

- **m3: `expectTypeOf<Empty>` 占位测试引用了未定义的 `Empty` 类型**（T2 vitest 占位）
  - 描述：`packages/shared-types/src/index.ts` 当前未导出 `Empty` 类型（Story 1.1 已交付内容验证）。Story 1.2 dev 说明使用 `expectTypeOf<Empty>().toEqualTypeOf<Record<string, never>>()` 会立即 type error。
  - Recommendation：改为最简运行时占位：
    ```ts
    import { describe, it, expect } from 'vitest'
    import * as types from '../src/index.js'
    describe('shared-types module', () => {
      it('loads without error', () => { expect(types).toBeDefined() })
    })
    ```
