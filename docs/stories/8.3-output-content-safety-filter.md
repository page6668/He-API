## Story

**As a** the He-API gateway operating under 生成式 AI 服务备案 compliance (and the operators who must demonstrate **出参** 敏感词过滤 for the 备案 audit, completing the bidirectional filter that 8.2 began on the 入参 side),
**I want** the §9.3 出参 Filter wired into the **response path** of `POST /v1/chat/completions` so the model-generated completion is scanned against the Story-8.1 `safety-lexicon` SoT — for **non-streaming** responses the assembled completion is scanned and, on a hit, the content is **replaced with redacted text + `finish_reason:"content_filter"`** before the 200 body is written; for **streaming** responses a bounded sliding-window buffer scans the accumulating output and, on a hit, the stream is **immediately terminated with a redacted `content_filter` terminal** (已发出的 chunk 无法收回，但日志记录) — reusing 8.2's `contentsafety.Scanner` core and `Recorder` seam (`direction:"output"`),
**so that** prohibited model output never completes to the caller, the user gets a deterministic OpenAI-native `content_filter` signal (not an error — the request succeeded; the output was filtered), and Story 8.5 (治理日志) can persist the output-interception record for 备案 — closing the Epic-8 DoD "入参/出参敏感词过滤上线" without forking the lexicon, the scanner, or the event taxonomy.

## Epic Context
**Epic**: 8 - 内容安全与合规准备
双向敏感词过滤 + 治理日志 + 备案材料归档。

**Epic DoD**: 入参/出参敏感词过滤上线 · 严格度可按 Key 配置 · 备案材料 PDF 模板生成。

**Story 8.3 Deliverables** (the SECOND half of "入参/出参过滤上线" — the OUTPUT direction, completing what 8.2 began):
- A **non-streaming output guard** in the response path: after a completion is assembled (mock + adapter non-stream + A/B merge), every `choices[].message.content` is scanned against `safetylexicon.DefaultLexicon` (REUSING `contentsafety.Scanner.ScanText` — the §9.3 Bloom→词典 core 8.2 built); a confirmed hit **replaces** the choice content with a fixed non-leaking 脱敏 string and sets `finish_reason:"content_filter"` BEFORE the 200 body is written.
- A **streaming output guard** (`contentsafety.StreamGuard`, stateful, per-request): a bounded rune sliding-window buffer (§9.3 "最近 200 tokens 滑窗") that observes each content delta as the chunker emits it; on a confirmed hit it **immediately terminates** the stream and emits a redacted `content_filter` terminal chunk + `data: [DONE]`. Already-flushed chunks are unrecoverable (§9.3 "无法收回") but the interception is logged.
- A **chunker-level interception seam** so the §9.3 detection lives where content deltas are extracted (the chunker, NOT the minimal SSE `Writer` — AR1-R4 Writer-minimalism), wired as a nil-default optional guard into both `MockChunker` and `AdapterChunker` (zero overhead / byte-identical when unwired).
- An **additive `DirectionOutput` const** on the 8.2 `contentsafety` recorder + reuse of the existing `SafetyEvent`/`Recorder`/`NopRecorder` seam (`direction:"output"`, `action:"blocked"`) so Story 8.5 binds the same `content_safety_logs` writer for both directions with no contract change.

> **Scope boundary (explicit)**: Story 8.3 is the **OUTPUT direction only** (the 入参 reject is Story 8.2, DONE). OUT of scope and owned elsewhere: §9.3 layer (3) the BERT 模型分类器 (later epic); **per-Key 严格度** loose/default/strict (Story 8.4 — 8.3 blocks on ANY confirmed match = the future "strict" posture, mirroring 8.2 BR-1.4); the actual **`content_safety_logs` DB write + excerpt redaction + 6-month retention + 备案 PDF** (Story 8.5 — 8.3 makes ZERO DB changes and supplies only the output event shape). Tool-call/function-arg output and multimodal output remain DEFERRED (8.3 scans string `content`/`delta.content` only — the same surface 8.2 scans; multimodal = Epic 9). The `400_content_filter` **error** code is INPUT-only (8.2) — 8.3 does NOT emit it; output uses the OpenAI-native `finish_reason:"content_filter"` success-body signal.

## Acceptance Criteria

### AC1: 非流式出参过滤 — 命中替换 + finish_reason:"content_filter" (Non-streaming output: redact + content_filter signal)

**Scenario**
```gherkin
GIVEN an authenticated non-streaming POST /v1/chat/completions whose upstream completion has been assembled into a ChatResponse (mock path, adapter non-stream path, OR A/B merged path) — BEFORE writeChatJSON writes the 200 body
WHEN the gateway scans every choices[].message.content string (each Normalize-d via the shared safetylexicon.Normalize) against safetylexicon.DefaultLexicon using the REUSED contentsafety.Scanner.ScanText (§9.3 Bloom 快速排除 → 词典匹配)
THEN
  - on the FIRST confirmed Lookup hit in a choice, that choice's message.content is REPLACED with a fixed non-leaking 脱敏 string (OQ-8.3-5) and its finish_reason is set to "content_filter" — the 200 status and the overall chat.completion envelope shape are PRESERVED (the request succeeded; the OUTPUT was filtered — this is NOT a §5.1.2 error and the 400_content_filter code is NOT emitted)
  - a clean completion (no confirmed match in any choice) passes through BYTE-IDENTICALLY to the pre-8.3 behaviour (no regression on the mock, adapter non-stream, or A/B path)
  - the redacted content carries NO sensitive substring (the matched term goes ONLY to the 8.5 output event seam, never echoed to the caller — avoid leaking the lexicon, mirroring 8.2 AC1)
  - the scan covers EVERY choice independently (A/B returns ≥2 choices; each is scanned + redacted independently, preserving the per-choice x_he_model attribution)
```

### AC2: 流式出参过滤 — 滑窗缓冲检测 + 立即终止 + 脱敏终止帧 (Streaming output: sliding-window buffer + immediate termination + redacted content_filter terminal)

**Scenario**
```gherkin
GIVEN an authenticated streaming POST /v1/chat/completions (req.Stream=true) dispatched through serveStream → a chunker (MockChunker OR AdapterChunker) emitting content deltas as data: <json>\n\n events
WHEN each content delta is observed by a per-request contentsafety.StreamGuard that maintains a bounded rune sliding-window buffer (§9.3 "最近 200 tokens 滑窗") over the accumulating output text and resolves it via the REUSED scanner pipeline (Normalize → window → MightContain → Lookup)
THEN
  - on the FIRST confirmed hit the stream is TERMINATED IMMEDIATELY: the chunker stops forwarding upstream content deltas, the gateway emits a terminal chunk with delta carrying the 脱敏 string (or empty) and finish_reason:"content_filter", then data: [DONE]\n\n
  - already-flushed chunks are NOT recalled (HTTP commits bytes irrevocably — §9.3 "已发出的 chunk 无法收回") but the interception IS logged + recorded to the 8.5 output event seam (§9.3 "但日志记录")
  - a term spanning a chunk boundary (e.g. arriving split across two deltas) IS detected — the buffer accumulates across deltas so the scan sees the joined text, NOT per-delta fragments (no false-negative at chunk seams — the gravest defect class)
  - a clean stream (no confirmed match) is BYTE-IDENTICAL to the pre-8.3 stream (same bootstrap/content/terminal/[DONE] sequence, same TTFB anchor) — the guard adds no events and no observable reordering when unwired-or-clean
  - the guard is per-request stateful (constructed fresh per stream) and never shared across goroutines; the scanner core it calls remains pure/concurrent-safe
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | The §9.3 detection lives at the CHUNKER level (where `chunk.Delta.Content` / mock `piece` is extracted), NOT in the SSE `Writer` — the `Writer` is deliberately minimal and observability/content-aware logic belongs in the chunker (AR1-R4). Both `MockChunker` (chat_chunks.go:84-145) and `AdapterChunker` (adapter_chunker.go:85-135) gain an OPTIONAL guard field (nil default); when nil the Stream loop is byte-identical to today (OQ-8.3-1). [Source: apps/api-gateway/internal/streaming/chat_chunks.go:84-145], [Source: apps/api-gateway/internal/streaming/adapter_chunker.go:85-135], [Source: apps/api-gateway/internal/streaming/sse.go:29-63] |
| BR-2.2 | The sliding-window buffer bound is RUNE-based, NOT token-based: the gateway has NO tokenizer on the stream path (token counts arrive only from the upstream `usage` tail, adapter_chunker.go:110-112), so §9.3's "200 tokens" is approximated by a documented rune budget calibrated to cover the corpus's longest term plus a generous window (OQ-8.3-3). The window MUST be ≥ the corpus max term-length (`safetylexicon.Lexicon.TermLengths()` truth, REUSED via the scanner) so a stored term is never split out of the window — the no-false-negative invariant (BR-2.5). |
| BR-2.3 | Detection is ACCUMULATE-then-scan across deltas: the guard appends each delta's content to a rolling buffer (capped at the window budget, oldest runes dropped) and re-scans the buffer after each append, so a term split across chunk boundaries is caught at the seam (BR-2.1 of 8.2's no-false-negative posture extended to the stream). The scan is the REUSED `Scanner.ScanText` over the buffer window. |
| BR-2.4 | The leak-vs-latency policy (OQ-8.3-2): 8.3 emits chunks as the chunker produces them (preserving TTFB / low latency) and terminates on the first in-buffer hit — accepting that the part of the term that already aged out of the window + flushed is unrecoverable (§9.3 "无法收回"). The window therefore minimizes — but does not eliminate — leaked output. The SM proposal is emit-then-scan-tail with a window ≥ longest-term so the offending term is caught at latest when its final rune lands; the Architect may instead rule a HOLD-BACK window (buffer the most-recent window before flushing → near-zero leak, higher TTFB latency). This is the central 8.3 design decision — see OQ-8.3-2. |
| BR-2.5 | NO-FALSE-NEGATIVE is a HARD invariant (a missed output term = a missed 出参 filter = compliance failure, inherited from 8.2). The window bound MUST come from corpus truth (`TermLengths()` via the scanner), the shared `Normalize` MUST be applied identically (no drift), and the cross-chunk-seam case MUST be tested. The perf/latency budget (BR-2.6) is a SOFT gate; the no-false-negative assertion is HARD. |
| BR-2.6 | Streaming termination reuses the existing terminal mechanics: the gateway writes the `content_filter` terminal via the same `streaming.Writer.WriteEvent` + `WriteDone()` path content chunks use (consistent flush semantics + middleware-wrap survival, AR1-R3), then returns. It does NOT reuse `writeSSEErrorFrame` (that is for upstream ERRORS, BR-2.6 of 4.1 — a `502/504` SSE error envelope); a `content_filter` termination is a SUCCESSFUL-but-filtered completion, NOT an error frame. [Source: apps/api-gateway/internal/handlers/chat_completions_stream.go:313-343], [Source: apps/api-gateway/internal/streaming/sse.go:98-124] |
| BR-2.7 | Billing on a stream block: the existing `maybeStreamTPMDeduct` partial/total logic (chat_completions_stream.go:359-393) is PRESERVED — a content_filter termination meters the tokens actually consumed up to the cut (treated like a completed-with-tail-usage or partial case, NOT a no-charge). 8.3 MUST NOT introduce a new metering path; it reuses the committed-stream deduction. (OQ-8.3-6.) |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| stream window budget | int (runes) | yes | ≥ max(`TermLengths()`); documented constant calibrated to ~§9.3 200-token window (OQ-8.3-3) | n/a (build-time contract) |
| terminal delta.content (on block) | string | optional | the 脱敏 string or empty; carries NO sensitive substring | n/a |
| terminal finish_reason (on block) | string | yes | literal `"content_filter"` | n/a |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Sensitive term detected mid-stream | (none — 200 already committed) | content_filter terminal + [DONE] | Stop forwarding upstream deltas; emit content_filter terminal; emit 8.5 output event; partial TPM deduct via existing path |
| Term split across two content deltas | (none) | (per above) | Buffer accumulates across deltas → detected at the seam (no false-negative) |
| Clean stream (no match) | (none) | normal stop terminal + [DONE] | Byte-identical to pre-8.3 stream; full TPM deduct + usage emit unchanged |
| Hit detected but headers NOT yet flushed (term in the very first delta) | (none) | content_filter terminal | Headers flush on the terminal write; still a 200 SSE response (content_filter), NOT a JSON error envelope |

**Examples**
- **Input**: upstream streams `"…"`, `"敏感"`, `"词…"` (term split across the 2nd+3rd deltas)
  **Expected**: buffer joins `敏感词` → detected; stream terminates with a `content_filter` terminal + `[DONE]`; the `敏感` chunk may already be on the wire (logged, unrecoverable); 8.5 output event recorded
- **Input**: a fully clean stream
  **Expected**: bootstrap → content chunks → `finish_reason:"stop"` terminal → `[DONE]`, byte-identical to the pre-8.3 path; usage/TPM unchanged

### AC4: 无漏报、确定性、性能与回归守卫 (No-false-negative + determinism + latency budget + regression guards)

  - the verdict is DETERMINISTIC: identical completion / identical delta sequence → identical redact/terminate outcome and identical matched_rule (pure scan over the immutable lexicon; the StreamGuard's buffering is order-deterministic)

## Dev Notes

### Technical Constraints

- **Canonical design source**: the §9.3 出参 Filter — `流式 chunk 缓冲：最近 200 tokens 滑窗检测 → 命中后立即终止流，返回脱敏内容 → 已发出的 chunk 客户端处理（无法收回，但日志记录）`. **Story 8.3 implements the 出参 (output) direction**: the sliding-window stream guard + immediate termination + redacted terminal, PLUS the non-streaming output equivalent (scan-the-assembled-completion + redact) that completes "出参过滤上线". [Source: docs/architecture/9-合规架构compliance-architecture.md:35-38]
- **Consumer of 8.1 + 8.2, not a fork**: 8.3 resolves against `safetylexicon.DefaultLexicon` (SoT) via the EXACT 8.2 `contentsafety.Scanner` — it adds a stateful `StreamGuard` wrapper for the stream case but the scan core (Normalize → window → MightContain → Lookup, longest-match-first) is REUSED unchanged. The 8.2 Architect explicitly anticipated this: OQ-8.2-7 ruling — "If 8.3 出参 filter ends up sharing the scanner core, extraction can be revisited then — note for 8.3." Sharing the in-gateway `contentsafety` package (no extraction) is the KISS choice. [Source: apps/api-gateway/internal/contentsafety/scanner.go:36-114], [Source: docs/stories/8.2-input-content-safety-filter.md (OQ-8.2-7 ruling)]
- **OUTPUT signal is `finish_reason:"content_filter"`, NOT an error**: a filtered OUTPUT is a request that SUCCEEDED — the gateway accepted it, dispatched it, the upstream produced tokens — and only the generated content was filtered. The OpenAI-native expression is the success-body `finish_reason:"content_filter"` (on `ChatChoice.FinishReason string`, chat_completions.go:122), NOT the `400_content_filter` ERROR envelope (§5.1.2:124, which is INPUT-only and is 8.2's first/only caller). The codebase already sets custom finish_reasons (`he_upstream_error` on A/B partial-fail markers, rest-api-spec:29) so `content_filter` fits the established shape. Status stays 200. [Source: apps/api-gateway/internal/handlers/chat_completions.go:119-122], [Source: docs/architecture/rest-api-spec.md:124,29]
- **Two response paths, two mechanics**: (1) **Non-stream** — the full completion is assembled into a `ChatResponse` before any byte is written (`writeChatJSON(w, 200, resp)` at chat_completions.go:570-571; `serveAdapterNonStream` :665-695; A/B merge), so 8.3 scans + redacts the in-memory body in place — the simple, leak-free case. (2) **Stream** — content is flushed incrementally via the chunker → `Writer.WriteEvent`, so 8.3 buffers a sliding window and terminates on a hit, accepting that already-flushed bytes are unrecoverable (§9.3). [Source: apps/api-gateway/internal/handlers/chat_completions.go:570-571,665-695], [Source: apps/api-gateway/internal/handlers/chat_completions_stream.go:45-103,202-294]
- **Chunker-level seam, NOT Writer-level**: the SSE `Writer` is deliberately minimal (BR-4.4 / AR1-R4 — "observability extensions belong in the chunker, not here"), and it only ever sees ALREADY-marshaled JSON bytes (re-parsing them to recover `delta.content` would be fragile + double-work). The content delta is extracted inside the chunker (`marshalAdapterChunk` reads `c.Delta.Content`, adapter_chunker.go:181-183; `MockChunker` splits `c.content` into `piece`s, chat_chunks.go:113-126). So the guard hook lives at the chunker, as an OPTIONAL nil-default field → byte-identical loop when unwired. [Source: apps/api-gateway/internal/streaming/sse.go:29-63], [Source: apps/api-gateway/internal/streaming/adapter_chunker.go:170-202], [Source: apps/api-gateway/internal/streaming/chat_chunks.go:84-145]
- **The "200 tokens" window with no tokenizer**: the gateway has NO tokenizer on the stream path — token counts arrive only from the upstream `usage` tail (`AdapterChunker.tailUsage`, adapter_chunker.go:69-71,110-112). So §9.3's "最近 200 tokens" is approximated by a RUNE budget (OQ-8.3-3), bounded BELOW by the corpus max term-length (`safetylexicon.Lexicon.TermLengths()` truth, REUSED via the scanner) so a stored term is never split out of the window — the no-false-negative invariant. Introducing a real tokenizer just for the window bound is rejected (heavy, vendor-specific, and unnecessary — a generous rune window strictly covers the detection need). [Source: apps/api-gateway/internal/streaming/adapter_chunker.go:69-71,110-112], [Source: apps/api-gateway/internal/contentsafety/scanner.go:42-49]
- **Billing is post-dispatch (inverse of 8.2)**: 8.2 rejected BEFORE dispatch → no charge. 8.3 acts AFTER dispatch → the upstream tokens are already consumed, so the existing metering (`tokenDeducter.TPMDeduct` + `emitUsage` non-stream at chat_completions.go:573-577,684-695; `maybeStreamTPMDeduct` for the stream at chat_completions_stream.go:359-393) is PRESERVED — redaction mutates only the body, never `resp.Usage`. 8.3 introduces NO new metering path (OQ-8.3-6). [Source: apps/api-gateway/internal/handlers/chat_completions.go:573-577,684-695], [Source: apps/api-gateway/internal/handlers/chat_completions_stream.go:359-393]
- **No runtime failure mode**: like 8.2, the lexicon is in-process + immutable (panics at init if bad), so `Lookup` never errors at request time; the scan is a pure deterministic in-memory function. The StreamGuard adds bounded mutable buffer state but no I/O — no fail-open/closed branch to design.
- **Toolchain limits**: pure-Go + httptest; no `buf`/`atlas`/`docker` needed (zero proto/DB/migration). Do NOT re-run workspace `go mod tidy` (otel pin gotcha). [Source: memory project_otel_version_pin_gotcha], [Source: memory project_toolchain_env_limits]
