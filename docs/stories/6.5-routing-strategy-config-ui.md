### Architect Open Questions (gathered for Architect Round 1)

> SM defaults are stated; the Architect rules IN/DEFER/OVERRULE. **Q-A is the headline fork.**

- **Q-A — Hot-path resolution of the per-user default (mechanism)** ⚠️ HEADLINE. `Decider.Decide(ctx, model, header, userID, heRequestID)` [Source: apps/api-gateway/internal/routingclient/decider.go:91] already carries `userID` on the hot path, and `ParseStrategy(model, header)` [Source: apps/api-gateway/internal/routingclient/strategy.go:37] resolves the 6.2 cascade. 6.5 must resolve `userID → default_routing_strategy` and inject it as a NEW tier (between header and STRATEGY_DEFAULT) WITHOUT a per-request PG/auth-svc round-trip on every chat call. **SM default = Option A (JWT claim)**: mint a `drs` (default-routing-strategy) claim into the access token at login/refresh (auth-svc already issues the RS256 access token, 15-min TTL [Source: apps/console/lib/auth/cookies.ts]); the gateway reads it from the validated claims it already has and passes it into an extended `ParseStrategy(model, header, userDefault)`. **Pro**: zero hot-path I/O; fits the stateless-JWT model. **Con**: a freshly-saved default takes effect only on the next token refresh (≤15min staleness) — the UI must tell the user "applies on your next session refresh" OR the save flow force-refreshes the access token. **Architect alternatives**: (B) a gateway-side cache (Redis or in-proc LRU keyed by `user_id`, populated lazily via auth-svc GetMe, invalidated on PUT /v1/me/profile) → immediate effect, at the cost of a cache layer + invalidation correctness; (C) accept a per-request auth-svc lookup behind the existing 100ms routing budget (simplest, but adds a hot-path RPC to every chat call — SM rejects as a hot-path regression).

- **Q-B — Persistence home**: SM default = **ALTER the existing `he_api.users` table** (`migrations/postgres/0019_add_default_routing_strategy_to_users.sql`, ADD COLUMN `default_routing_strategy VARCHAR(20) NULL`), exactly as `locale`/`timezone` live on `users` [Source: migrations/postgres/0002_create_users.sql:12-28]. Additive, nullable, reversible (down drops the column), non-destructive. Architect alternative: a separate `user_preferences`/`user_settings` table (over-engineered for one enum column — SM rejects; no other preference needs it yet).

- **Q-C — Contract shape (REST + gRPC)**: SM default = **additive only**. `PUT /v1/me/profile` body gains an OPTIONAL `default_routing_strategy` string field (enum `quality|cost|latency`, or explicit `null`/omitted-to-clear — Architect to rule clear-semantics, see Q-D) [Source: apps/api-gateway/internal/handlers/update_profile.go]; `GET /v1/me` response gains `default_routing_strategy` (always present, nullable) [Source: apps/api-gateway/internal/handlers/me.go:57-91]; auth-svc `UpdateProfileRequest` + `GetMeResponse` gain the matching additive proto field (same buf-additive pattern proven in 6.1/6.2 — does NOT cross `buf breaking: FILE`). NO new endpoint. Architect confirm: reuse PUT /v1/me/profile (vs a dedicated PUT /v1/me/routing-preference) — SM default = reuse (it is a profile preference; the strict-unknown-field validator just gains one allowed key).

- **Q-D — "Clear the default" semantics + enum surface**: the valid persisted values are `{quality, cost, latency}` plus the "no default" state (→ STRATEGY_DEFAULT passthrough = today's behaviour). SM default = the UI offers **4 choices: 默认/Passthrough (clears → NULL), Quality, Cost, Latency**; the API treats an explicit JSON `null` as "clear", and OMITTING the field as "leave unchanged" (consistent with the Story-2.5 partial-update semantics). The persisted `STRATEGY_DEFAULT`/`UNSPECIFIED`/`he-router-*` are NOT user-selectable as a default (they are per-request directives, not account preferences). Architect may rule whether a sentinel string `"default"` is stored vs NULL.

- **Q-E — Key-scope (Story 5.2) interaction** (6.2-Q-F precedent): if a user's persisted default routes to a model outside the API key's `scope.models`, the existing Story-5.2 keypolicy gate would 403 a request the user did not per-request ask to route. SM default = **status-quo enforcement**: the routing decision is computed (now possibly driven by the user default), then post-validated by the existing keypolicy gate; on conflict the gateway returns the same `403` the user would get today for an out-of-scope model. No new candidate-scope field (Q-F was ruled SIMPLE in 6.2). Architect confirm: the user-default does NOT bypass key scope, and a 403 here is acceptable (the user set an account default broader than a scoped key — documented).

- **Q-F — Default can't be resolved (fail-open vs fail-closed)** (6.2-Q-G precedent): if the resolution mechanism (Q-A) fails (claim absent on an old token / cache miss + lookup error), does the gateway fall back to `STRATEGY_DEFAULT` (open — today's passthrough, chat never blocks) or error? SM default = **fail-OPEN to STRATEGY_DEFAULT** (the user-default is a convenience, never a correctness gate; an unresolvable default degrades to exactly 6.2's behaviour; slog `user_default=unresolved`). Architect confirm (SM sees no reason to fail-closed here — there is always a safe passthrough fallback, unlike 6.2's meta-model case).

- **Q-G — Precedence label + observability**: the EXTENDED cascade is meta-model > header > **user-default** > STRATEGY_DEFAULT. SM default = when the user-default drives the decision, slog carries `strategy_source=user_default` and the existing `he_routing_decisions_total` metric is unchanged (it already labels by `strategy`; the resolved strategy is what matters). The `X-He-Selected-Model` header (6.2) is unchanged. Architect may request an additive `strategy_source` slog field (SM default = yes, slog only, non-PII, no metric cardinality change).

- **Q-H — Console surface placement**: SM default = a **new "routing" sub-section on the existing Settings area** (mirroring `settings/profile/` [Source: apps/console/app/[locale]/(console)/settings/profile/page.tsx]) — either a new `settings/routing/` page or a card within the profile page; the control is a radio/select with the 4 Q-D choices + explanatory copy. i18n strings land in the existing `account` namespace [Source: apps/console/i18n/namespaces.ts:1-14]; if `gen-i18n-keys` codegen crashes (known 2fa-namespace issue), the `packages/i18n-keys/src/account.ts` union is hand-authored. Architect/UX may rule a dedicated page vs an inline profile card.

## Story

As an **authenticated He-API console user managing my account**,
I want **to choose a default routing strategy (quality / cost / latency, or none) in the console settings, have it persist to my account, and have the gateway apply it automatically to my chat requests that don't already carry a per-request strategy directive**,
so that **I can set my routing preference once instead of attaching an `X-He-Routing-Strategy` header or a `he-router-*` meta-model to every single request — while keeping full per-request override power and zero behaviour change when I haven't set a default.**

### AC2: Persistence + contract — `PUT /v1/me/profile` + `GET /v1/me` + auth-svc + `0019` migration (additive)

**Scenario**
```gherkin
GIVEN the users table gains an additive nullable column default_routing_strategy (migration 0019)
WHEN PUT /v1/me/profile is called with { default_routing_strategy: <value|null> } and a valid he_access JWT
THEN
- the gateway forwards the additive field to auth-svc UpdateProfile (gRPC, additive proto field), user_id from the JWT (never the body)
- auth-svc validates the value against the enum {quality, cost, latency} (or null to clear); an unknown value → 400 (reusing the strict field-validation + 400 envelope discipline of Story-2.5 update_profile)
- auth-svc persists it via the existing SELECT FOR UPDATE + etag-compare + UPDATE transaction (optimistic concurrency; If-Match preserved)
- GET /v1/me returns default_routing_strategy (always present, nullable) reflecting the persisted value
- an OMITTED default_routing_strategy on PUT leaves the existing value unchanged (partial-update semantics); an explicit null clears it
- the 0019 migration is reversible (down drops the column) + non-destructive (no existing column/table altered destructively); atlas.sum updated
```

### AC3: Gateway applies the persisted default on the hot path — NEW precedence tier, zero regression when unset

**Scenario**
```gherkin
GIVEN the Story-6.2 strategy cascade (meta-model > X-He-Routing-Strategy header > STRATEGY_DEFAULT) at routingclient.ParseStrategy
WHEN a POST /v1/chat/completions request is processed and the gateway resolves the user's default (mechanism per Q-A)
THEN
- ParseStrategy is EXTENDED to accept the resolved user default and insert it as a NEW tier: meta-model > header > user-default > STRATEGY_DEFAULT
- a request with a he-router-* meta-model → meta wins (user-default ignored)
- a request with an X-He-Routing-Strategy header → header wins (user-default ignored)
- a concrete model with NO meta-model and NO header AND a persisted user default → routes by the user default (e.g. default=cost → STRATEGY_COST over the candidate set)
- a concrete model with NO meta-model, NO header, and NO persisted default → STRATEGY_DEFAULT passthrough, selected_model == req.Model (BYTE-FOR-BYTE Story-6.2 behaviour — zero regression for the 6-vendor adapter matrix)
- if the user default cannot be resolved (Q-A mechanism failure) → fail-OPEN to STRATEGY_DEFAULT (never blocks chat); slog user_default=unresolved (Q-F)
- when the user-default drives the decision, slog carries strategy_source=user_default (non-PII, NEVER user_id) (Q-G)
- a user-default that routes to a model outside the API key scope is post-validated by the existing Story-5.2 keypolicy gate (same 403 as today — Q-E)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR3-1 | `ParseStrategy(model, header)` [Source: apps/api-gateway/internal/routingclient/strategy.go:37-54] is EXTENDED to `ParseStrategy(model, header, userDefault)`; the user-default tier sits BETWEEN the header branch and the terminal `return STRATEGY_DEFAULT`. The meta-model and header branches are UNCHANGED (cascade-lock from 6.2 BR1-1 preserved). |
| BR3-2 | `Decider.Decide(ctx, model, header, userID, heRequestID)` [Source: apps/api-gateway/internal/routingclient/decider.go:91] resolves `userID → userDefault` (mechanism per Q-A) BEFORE calling ParseStrategy. `DecideAB` (6.4) is likewise updated for consistency IF A/B requests honour the default (Architect to confirm — SM default: A/B is an explicit per-request directive, so the user-default does NOT apply to DecideAB; the X-He-AB-Models header is itself the directive). |
| BR3-3 | ZERO hot-path regression when no default is set: the user-default tier is a pure addition; with `userDefault == UNSPECIFIED/none` the function returns exactly what 6.2 returns. The 6-vendor adapter matrix, 6.2/6.3/6.4 routing tests, SSE shape, keypolicy (5.2) / rate-limit (5.3) / cap (5.4) gates all remain green. |
| BR3-4 | Fail-OPEN: an unresolvable user-default degrades to STRATEGY_DEFAULT (Q-F) — there is ALWAYS a safe passthrough fallback (unlike 6.2's meta-model fail-closed case). slog `user_default=unresolved`. |
