### AC1: QPS — per-second request rate limit per API key (excess returns 429 `429_rate_limit_qps` + `Retry-After: 1`)

**Scenario**
```gherkin
GIVEN
  - Authenticated request to `/v1/chat/completions` (Story 3.3/3.4/4.x) or `/v1/embeddings` (Story 3.5)
  - The bearer-auth middleware (Story 3.2) has resolved `api_key_id` + `user_id` into the request context via cached claims
  - The api-key's effective QPS ceiling is `qps_max` (constant free-tier default `10`, sourced from Helm `values.yaml` → env var `RATELIMIT_FREE_TIER_QPS_MAX` per BR-1.3 + M-3 source-of-truth; per-key configurable ceilings deferred to a future 5.x Story per Architect C-1 ratification)
  - Redis is reachable (otherwise fail-open path per AC-X cross-cutting; see BR-2.6)
WHEN
  - The ratelimit middleware (`apps/api-gateway/internal/middleware/ratelimit/`) runs INSIDE the bearer-auth boundary, BEFORE the chat-completions handler (Story 3.3) or embeddings handler (Story 3.5)
  - It invokes the atomic Redis Lua script `check_and_incr.lua` with axis=`qps`, key=`ratelimit:key:{api_key_id}:qps`, ceiling=`qps_max`, ttl=1
  - The Lua script atomically: (1) reads the current counter, (2) if `current >= ceiling` returns `{0, retry_after=ttl_remaining_seconds, exhausted_axis="qps"}` WITHOUT incrementing, (3) else `INCR` the counter, sets `EXPIRE key 1 NX` (NX = do not reset TTL on subsequent increments within the same second), and returns `{1, ...}`
THEN
  - **Allowed path** (counter was < ceiling): middleware passes the request to the next handler unchanged. slog records `event=ratelimit_decision attrs={axis=qps, outcome=allowed, api_key_id=<uuid>, current=<n>, ceiling=<qps_max>, he_request_id=<id>}`. Prometheus counter `he_ratelimit_decisions_total{axis="qps",outcome="allowed"}` incremented.
  - **Denied path** (counter was ≥ ceiling): middleware short-circuits with HTTP 429; response body is the canonical 5-field envelope per `openaierr.Write`:
    ```json
    {"error":{"code":"429_rate_limit_qps","message":"Rate limit exceeded: per-second request budget","type":"invalid_request_error","param":null,"he_request_id":"req_xxxxxxxxxxxx"}}
    ```
  - Response headers MUST include `Retry-After: <seconds>` (RFC 7231 §7.1.3 delta-seconds form, integer only; for QPS the value is `1` since the QPS key TTL is 1 second; never an HTTP-date).
  - slog records `event=ratelimit_decision attrs={axis=qps, outcome=denied, api_key_id=<uuid>, current=<n>, ceiling=<qps_max>, retry_after_seconds=1, he_request_id=<id>}`. Prometheus counter `he_ratelimit_decisions_total{axis="qps",outcome="denied"}` incremented.
  - Cross-axis interaction: when QPS is denied, RPM + TPM counters MUST NOT be incremented (the Lua script returns BEFORE any INCR if ANY axis is exhausted; BR-2.4 atomicity).
  - Cross-pod statelessness: N gateway pods serving the SAME `api_key_id` MUST see a SHARED counter (Redis is the single source of truth; no per-pod LRU cache for rate-limit state).
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | Counter key format `ratelimit:key:{api_key_id}:qps` MUST exactly match the architecture `data-models.md §4.3` Redis Key 规范 (REUSE pre-declared row). The `api_key_id` is the UUID-v4 from `he_api.api_keys.id` (Story 3.2 + 5.1 columnar source). |
| BR-1.2 | Counter TTL is exactly 1 second (`EXPIRE key 1 NX`). The `NX` flag is non-negotiable — it prevents counter TTL extension on subsequent increments within the same second window (a `EXPIRE` without NX would slide the window indefinitely and break the fixed-window contract per Architect Q2 SM default). |
| BR-1.3 | `qps_max` is the constant `RATELIMIT_FREE_TIER_QPS_MAX` env var (default `10`), loaded once at boot from Helm `values.yaml` `ratelimit.freeTierDefaults.qpsMax` (M-3 + C-1 remediation). NO per-request resolution; NO read of `api_keys.scope` (Story 5.2's frozen contract does not carry `rate_limits`). Per-key configurable ceilings DEFERRED to a future 5.x Story. NEVER infer from `monthly_cost_cap_usd` (independent concern). |
| BR-1.4 | Atomic check-and-incr semantics: the Lua script MUST be atomic from Redis's perspective (Redis processes a Lua block in a single thread). | BR-1.5 | The envelope code `429_rate_limit_qps` is PRE-EXISTING in `rest-api-spec.md §5.1.2` (added pre-Story-3.6 promotion). NO Architect ratification needed for THIS code — the row already exists. The new code (`429_rate_limit_rpm`) is AC2's concern. |
| BR-1.6 | `Retry-After` header value: for QPS, MUST be exactly `1` (integer; the QPS window is 1 second; `Retry-After: 1` means "the client may retry in 1 second" — RFC 7231 §7.1.3 delta-seconds form). NEVER an HTTP-date; NEVER 0; NEVER a fractional second. |
| BR-1.7 | The middleware MUST NOT log plaintext API keys (BR-1.9 parity with Story-4.5 + Story-3.2 TC-9 — slog discipline). ### AC2: RPM — per-minute request rate limit per API key (excess returns 429 `429_rate_limit_rpm` + `Retry-After: <60-window-elapsed>`)

**Scenario**
```gherkin

  - Authenticated request to `/v1/chat/completions` (Story 3.3/3.4/4.x) or `/v1/embeddings` (Story 3.5)

WHEN
  - The ratelimit middleware invokes the same atomic Lua script `check_and_incr.lua` with axis=`rpm`, key=`ratelimit:key:{api_key_id}:rpm`, ceiling=`rpm_max`, ttl=60
  - The Lua script atomically: (1) reads the counter, (2) if `current >= ceiling` returns `{0, retry_after=ttl_remaining_seconds, exhausted_axis="rpm"}` WITHOUT incrementing, (3) else `INCR` + `EXPIRE key 60 NX` and returns `{1, ...}`
  - The QPS + RPM + TPM checks are pipelined in a SINGLE Lua script call (BR-2.4 — atomic across all 3 axes for cross-axis consistency)
THEN
  - **Allowed path**: middleware passes the request to the next handler. slog records `event=ratelimit_decision attrs={axis=rpm, outcome=allowed, api_key_id=<uuid>, current=<n>, ceiling=<rpm_max>, he_request_id=<id>}`. Prometheus `he_ratelimit_decisions_total{axis="rpm",outcome="allowed"}` inc.

  - Response headers: `Retry-After: <ttl_remaining_seconds>` (integer; the value is the time UNTIL the RPM counter TTL expires, which is between 1 and 60 inclusive depending on how far into the window the request is). NEVER 0; NEVER fractional; NEVER HTTP-date.
  - slog records `event=ratelimit_decision attrs={axis=rpm, outcome=denied, retry_after_seconds=<n>, ...}`. Prometheus inc.
  - Cross-axis: if QPS already failed in this Lua call, RPM + TPM counters are NOT touched (BR-2.4).
```

| ID | Rule |
|----|------|
| BR-2.1 | Counter key format `ratelimit:key:{api_key_id}:rpm` MUST follow the architecture `data-models.md §4.3` Redis Key 规范 EXTEND of the per-key `:qps` row (the `data-models.md §4.3` row currently lists `ratelimit:key:{api_key_id}:qps  同上`; this Story realises the implied `:rpm` + `:tpm` siblings). |
| BR-2.2 | Counter TTL is exactly 60 seconds (`EXPIRE key 60 NX`). Same NX semantics as BR-1.2. |
| BR-2.3 | `rpm_max` is the constant `RATELIMIT_FREE_TIER_RPM_MAX` env var (default `300`), loaded once at boot from Helm `values.yaml` `ratelimit.freeTierDefaults.rpmMax` (M-3 + C-1 remediation). Same resolution semantics as BR-1.3. |
| BR-2.4 | Atomicity across 3 axes: the Lua script MUST evaluate QPS → RPM → TPM in a single atomic block. If any axis is exhausted, the script returns IMMEDIATELY without incrementing ANY counter. Rationale: a denied request shouldn't consume budget on the OTHER axes (otherwise a single 429 would burn 3 axes' worth of budget on retries). The Lua return envelope is `{decision, retry_after_seconds, exhausted_axis}` where `exhausted_axis ∈ {"qps", "rpm", "tpm", null}`. The Go-side middleware maps `exhausted_axis` to the envelope code `429_rate_limit_<axis>`. |

Joins the pre-existing `429_rate_limit_qps` + `429_rate_limit_tpm` (already in `rest-api-spec.md §5.1.2`). The Lua script returns this value as part of its envelope so the Go middleware does not need to re-call Redis. Rationale: a stale `Retry-After: 60` when the actual remaining is 5s would frustrate clients with overly-conservative back-off; a stale `Retry-After: 1` when the actual remaining is 55s would have the client hammer prematurely. |
| BR-2.7 | The RPM counter SHARES Redis with the QPS + TPM counters but operates on a DIFFERENT key with a DIFFERENT TTL. The 3 counters are INDEPENDENT — exhausting one does NOT affect the others' counters (only the request's outcome). |
| BR-2.8 | The 429 response flows through `openaierr.Write(w, ctx, 429, "429_rate_limit_rpm", "Rate limit exceeded: per-minute request budget", nil)` (Story 3.6 canonical writer). |

### AC3: TPM — per-minute upstream-token rate limit per API key (post-deduction model; excess returns 429 `429_rate_limit_tpm` + `Retry-After: <60-window-elapsed>`)

**Scenario**
```gherkin
GIVEN
  - Authenticated request to `/v1/chat/completions` (Story 3.3/3.4/4.x)
  - The bearer-auth middleware (Story 3.2) has resolved `api_key_id` + `user_id` into the request context
  - The api-key's effective TPM ceiling is `tpm_max` (constant free-tier default `60000`, sourced from env var `RATELIMIT_FREE_TIER_TPM_MAX` per BR-3.3 + M-3 source-of-truth)
  - The QPS + RPM axes pre-check have ALREADY passed (otherwise the request was rejected earlier in the Lua script per BR-2.4)
  - Redis is reachable
WHEN
  - **Pre-check phase (in the same Lua script that ran for QPS + RPM)**: The Lua script reads `ratelimit:key:{api_key_id}:tpm` and compares to `tpm_max`. If `current >= tpm_max`, returns `{0, retry_after=ttl_remaining_seconds, exhausted_axis="tpm"}` and the middleware short-circuits with 429 (similar to AC2's denied path). If `current < tpm_max`, the Lua script DOES NOT increment the TPM counter at this stage (post-deduction model per Architect Q3 SM default — the token count is not yet known).
  - The pre-check passes; the request proceeds to the chat-completions handler → upstream adapter → Story 4.1 Connect-RPC adapter → vendor LLM.
  - **Post-deduction phase**: After the upstream returns the canonical `usage.total_tokens` value (per Story 4.1 BR-3.3 Normaliser interface + BR-2.4 streaming-tail-usage chunk), the ratelimit middleware's TPM post-deduction hook (`tpm_deduct.go`) invokes `INCRBY ratelimit:key:{api_key_id}:tpm <usage.total_tokens>; EXPIRE ratelimit:key:{api_key_id}:tpm 60 NX`. This is fire-and-forget from the request's perspective (the response has already been written; the deduction races against the NEXT request's pre-check).
THEN
  - **Allowed path (pre-check passes)**: request proceeds. After the response is fully written, post-deduction happens. slog records `event=ratelimit_tpm_deducted attrs={api_key_id=<uuid>, tokens=<usage.total_tokens>, new_counter=<n>, he_request_id=<id>}`.
  - **Denied path (pre-check fails)**: HTTP 429 + canonical envelope `{"error":{"code":"429_rate_limit_tpm","message":"Rate limit exceeded: per-minute token budget","type":"invalid_request_error","param":null,"he_request_id":"<id>"}}`. `Retry-After: <ttl_remaining>` (integer 1-60).
  - Streaming-path edge cases (per Architect Q10 ratification, SM defaults documented in BR-3.4 / BR-3.5 / BR-3.6 / BR-3.7 below).
  - The TPM counter sees a delayed update relative to the request that consumed it. Race window: ⌊upstream_latency_seconds × rps⌋ requests may be in flight against an "outdated" counter view. SM default: accept (BR-3.8 quantifies the bound).
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | Counter key format `ratelimit:key:{api_key_id}:tpm` — EXTEND of the architecture `data-models.md §4.3` Redis Key 规范 (sibling to per-key `:qps` + `:rpm`). |
| BR-3.2 | Counter TTL is 60 seconds (`EXPIRE key 60 NX`). The `INCRBY <usage.total_tokens>; EXPIRE 60 NX` pair MUST be issued together (Redis pipeline OR Lua) so the TTL is set on the first INCR of a new window. |
| BR-3.3 | `tpm_max` is the constant `RATELIMIT_FREE_TIER_TPM_MAX` env var (default `60000`), loaded once at boot from Helm `values.yaml` `ratelimit.freeTierDefaults.tpmMax` (M-3 + C-1 remediation). Same resolution semantics as BR-1.3. |
| BR-3.4 | **Post-deduction model** (Architect Q3 SM default): the TPM counter is INCRemented AFTER the upstream returns `usage.total_tokens`. The pre-check at request-time reads the counter WITHOUT incrementing. Race window: a request in-flight (e.g., 10000 tokens) + a concurrent request whose pre-check sees the pre-deduction counter — both pass. No `usage` chunk arrived. SM default: deduct `prompt_tokens` only (deterministic from request body, NOT including the completion-side; the assumption is the user already "paid" for the prompt processing even though the response was incomplete). slog WARN `event=ratelimit_tpm_partial_deduction attrs={api_key_id=<uuid>, prompt_tokens=<n>, reason=<stream_error|client_disconnect>}`. |
| BR-3.7 | **Upstream `missing-tail-usage` 502 fail-fast** (Architect Q10 case iv; Story 4.1 BR-3.4): the upstream returned a chunk stream BUT never emitted the `usage` chunk → Story 4.1 raises a 502. SM default: do NOT deduct at all (the upstream call is treated as failed; charging the user's TPM budget for a failed call would be unfair). slog WARN `event=ratelimit_tpm_failed_no_deduction attrs={api_key_id=<uuid>, reason=missing_tail_usage}`. |
| BR-3.8 | Race-window bound (analytical): with `qps_max=10` and `tpm_max=60000`, the per-request token-count is bounded by the request's `max_tokens` field (which is upstream-capped by model context window — e.g., 8K-128K depending on model). The worst-case over-shoot is `qps_max × per_request_tokens = 10 × 128000 = 1.28M tokens` in 1 second — well above any plausible 1-second budget. In practice this is mitigated by the QPS axis catching the burst first. The race-window over-shoot is bounded but unbounded in the sense that a single request can carry up to `max_tokens` worth of post-deduction. The architecture accepts this for MVP per Architect Q3 SM default. |
| BR-3.9 | The 429 response flows through `openaierr.Write(w, ctx, 429, "429_rate_limit_tpm", "Rate limit exceeded: per-minute token budget", nil)` (Story 3.6 canonical writer). The envelope code `429_rate_limit_tpm` is PRE-EXISTING in `rest-api-spec.md §5.1.2`. |
| BR-3.10 | **NEVER log token content** (parity with Story-4.5 BR-1.9 + Story-3.2 TC-9 + Story-5.1 PII discipline). The `tokens=<n>` slog attribute carries the INTEGER count; it MUST NOT carry the message contents. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `tpm_max` (from `RATELIMIT_FREE_TIER_TPM_MAX` env var) | int | required (boot-time) | ≥ 1 AND ≤ 100000000 (defensive — 100M tokens/min is well above any plausible commercial tier). Default `60000` if env var unset. Same boot-time validation as `qps_max`. | (boot-time config; HALT) |
| `usage.total_tokens` (from upstream Normaliser) | int | required (on success path) | Must equal `usage.prompt_tokens + usage.completion_tokens` per Story 4.1 BR-3.3 `ValidateInvariants`. If invariant fails: Story 4.1 already raises `ErrUsageConstraintViolation` → 502; the ratelimit hook is never invoked on the failure path. | (handled upstream; Story 5.3 trusts the Normaliser) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Pre-check counter ≥ ceiling | 429 | `429_rate_limit_tpm` | `openaierr.Write` + `Retry-After: <ttl_remaining>` (1-60) + slog + Prometheus inc. |
| Post-deduction Redis error | n/a | n/a (best-effort) | slog WARN `event=ratelimit_tpm_deduct_failed attrs={api_key_id=<uuid>, tokens=<n>, error=<err>}`; Prometheus `he_ratelimit_tpm_deduct_failed_total` inc. The user-facing response is NOT affected (the response has already been written by the time post-deduction runs). |
| Stream error mid-flight | n/a | n/a | Deduct `prompt_tokens` only per BR-3.6; slog WARN. |
| Stream missing tail-usage (Story 4.1 BR-3.4 502) | (handled upstream) | (handled upstream) | Do NOT deduct per BR-3.7; slog WARN. |

**Examples**
- Input: `api_key_id=abc-...`, `tpm_max=60000`, current counter at 45000 (pre-deduction view). Pre-check passes. Request consumes 8000 upstream tokens. After response: `INCRBY 8000`; counter is now 53000.
- Input: same key, counter at 59500. Pre-check passes (59500 < 60000). Request consumes 8000 tokens. After response: counter is now 67500 — exceeded by 7500. The NEXT request's pre-check will see 67500 ≥ 60000 and return 429. SM default: this is the accepted race-window per BR-3.4 / BR-3.8.
- Input: streaming request, mid-flight client disconnect after 1000 tokens of completion have streamed. Deduct `prompt_tokens` only (e.g., 200) per BR-3.6; slog WARN `partial_deduction`. The 1000 tokens streamed are NOT deducted (the user did not receive a complete response).
- Input: streaming request, upstream `missing-tail-usage` 502 (Story 4.1 BR-3.4). NO deduction per BR-3.7; slog WARN `failed_no_deduction`. The user's TPM budget is not charged for the failed call.

### Cross-Cutting Business Rules (apply to AC1 + AC2 + AC3)

**BR-X.1 (Atomicity)**: All 3 axes are evaluated in a SINGLE atomic Lua script call (`check_and_incr.lua`). The script's return envelope is `{decision: 0|1, retry_after_seconds: int, exhausted_axis: "qps"|"rpm"|"tpm"|nil}`. The Go middleware maps `exhausted_axis` to the envelope code `429_rate_limit_<axis>`. (BR-1.4, BR-2.4 detail.)

**BR-X.2 (Fail-mode)**: If the Redis Lua call errors / times out (5ms timeout per Architect Q6 SM default), the middleware fails OPEN — passes the request through unchanged, with slog WARN `event=ratelimit_fail_open attrs={error=<err>, api_key_id=<uuid>}` and Prometheus `he_ratelimit_fail_open_total{axis="<n/a>"}` increment. Architect Q6 ratifies. (See Q6 in SM Decision Record for the divergence-from-Story-2.3-OQ3 rationale.)

**BR-X.3 (Cross-pod statelessness)**: N gateway pods serving the SAME `api_key_id` MUST share counters via Redis (no per-pod cache). The Story-3.1 stateless-gateway invariant is preserved.

**BR-X.4 (Middleware chain position)**: The ratelimit middleware MUST run AFTER bearer-auth (Story 3.2 — needs `api_key_id`) AND AFTER request-id (Story 3.6 — slog needs `he_request_id`). MUST run BEFORE the chat-completions / embeddings handler. Per Architect Q9 SM default: chain order (outside-in) `requestid → cors (public-only) → bearer-auth → ratelimit → handler`. For `/v1/me/*` (JWT) routes, the rate-limit middleware is N/A (this Story applies only to bearer-auth paths).

**BR-X.5 (Telemetry cardinality bound)**: Prometheus metrics MUST keep cardinality bounded. `he_ratelimit_decisions_total{axis,outcome}` = 3 axes × 2 outcomes = 6 series. NO per-`api_key_id` label (would unbound cardinality). `he_ratelimit_check_duration_seconds` = 1 histogram with default buckets. `he_ratelimit_fail_open_total{axis}` = 3 series. Total Prometheus series budget: ≤10 NEW series across the whole middleware.

**BR-X.6 (Slog discipline)**: NO plaintext API keys, NO message content, NO token content in slog records. Only the integer `api_key_id` (UUID), counter values, ceiling values, axis names, and `he_request_id` are slog-safe. (Parity with Story 4.5 BR-1.9 + Story 3.2 TC-9.)

**BR-X.7 (Hot-path performance budget)**: The middleware's added latency MUST be ≤ 2ms P95 for the success path (Lua round-trip; documented in §10.1 of architecture as part of the gateway 100ms P95 budget). Benchmark assertion: `BenchmarkCheck` ≤ 500ns/op for the 3-axis Lua call path (Redis miniredis stub for the benchmark; Architect Q6 timeout is 5ms for the live Redis call).

**BR-X.8 (`/v1/embeddings` TPM semantics)**: For `/v1/embeddings` (Story 3.5), `usage.total_tokens` is the `prompt_tokens` (embeddings have no completion dimension; Story 3.5 BR-2.5 deterministic mock). The TPM post-deduction uses `usage.total_tokens` unchanged. AC3 applies verbatim to this route.

**BR-X.9 (Future-route extensibility)**: The middleware is mounted via a route-list (`apps/api-gateway/cmd/server/main.go` wiring). Adding a future route (e.g., `/v1/audio/transcriptions` in Epic 9) is a 1-line wiring change. The middleware is NOT path-aware (it consumes `api_key_id` only).

### Technical Constraints

- **Performance budget** [Source: `docs/architecture/10-性能与可扩展性performance-scalability.md §10.1`]: Gateway P95 budget is 100ms; the ratelimit middleware must add ≤2ms P95 (1 Redis Lua round-trip with 3 keys pipelined; BR-X.7). The Story-3.1 cold-start budget of 1s is unaffected (middleware adds ~0ms to cold-path since Redis client is lazy-init via `sync.Once` per Story-3.2 cold-start pattern).
- **Stateless gateway invariant** [Source: `docs/architecture/high-level-architecture.md §1.2`]: "Stateless Gateway: 网关层零状态，K8s HPA 横向扩展". The middleware MUST NOT cache rate-limit counters in process memory. Redis is the single source of truth. (BR-X.3)
- **Atomicity non-negotiable**: The Lua script's atomicity is what makes the rate-limit accurate under concurrency. A non-atomic check-then-incr would have race windows that allow over-spending. Redis processes a Lua block in a single thread per `EVAL`/`EVALSHA` contract (this is foundational and documented in Redis docs).
- **Connect-RPC streaming contract from Story 4.1** [Source: `docs/stories/4.1-deepseek-adapter-streaming-non-streaming.md` BR-2.4]: streaming adapters emit `usage` BEFORE `data: [DONE]`. Story 5.3's TPM post-deduction hook depends on this contract being respected (BR-3.5).
- **Story 4.1 missing-tail-usage 502** [Source: `docs/stories/4.1-deepseek-adapter-streaming-non-streaming.md` BR-3.4]: when the upstream stream closes without a `usage` chunk, Story 4.1 raises 502; Story 5.3 trusts this and does NOT deduct (BR-3.7).
- **Story-3.6 5-field envelope contract** [Source: `docs/architecture/rest-api-spec.md §5.1.2` post-Story-3.6 ratification line 145-151]: the 429 responses MUST be written via `openaierr.Write(w, ctx, status, code, message, *param) error` (BR-1.8, BR-2.8, BR-3.9). NO per-middleware error writer.

**Lua script return envelope** (T0.2 — `check_and_incr.lua`):
- Returns a 3-element Redis Lua array: `{decision, retry_after_seconds, exhausted_axis_index}`
- `decision`: `1` = allowed, `0` = denied
- `retry_after_seconds`: integer 1-60 (0 on allowed path)
- `exhausted_axis_index`: `0` = none, `1` = qps, `2` = rpm, `3` = tpm (Lua does not have string sum types ergonomically; integer-encoded for performance)
- Go side maps the integer back to the axis name for envelope-code construction.

**Lua script pseudocode**:
```lua
-- KEYS[1] = ratelimit:key:{id}:qps; KEYS[2] = ...:rpm; KEYS[3] = ...:tpm
-- ARGV[1] = qps_max; ARGV[2] = rpm_max; ARGV[3] = tpm_max
-- ARGV[4] = qps_ttl=1; ARGV[5] = rpm_ttl=60; ARGV[6] = tpm_ttl=60
-- ARGV[7] = pre_check_only_for_tpm = 1  (TPM is post-deduction; pre-check reads but does NOT INCR)

local qps_cur = tonumber(redis.call('GET', KEYS[1]) or 0)
if qps_cur >= tonumber(ARGV[1]) then
  local ttl = redis.call('TTL', KEYS[1])
  if ttl < 0 then ttl = 1 end
  return {0, ttl, 1}
end

local rpm_cur = tonumber(redis.call('GET', KEYS[2]) or 0)
if rpm_cur >= tonumber(ARGV[2]) then
  local ttl = redis.call('TTL', KEYS[2])
  if ttl < 0 then ttl = 1 end
  return {0, ttl, 2}
end

local tpm_cur = tonumber(redis.call('GET', KEYS[3]) or 0)
if tpm_cur >= tonumber(ARGV[3]) then
  local ttl = redis.call('TTL', KEYS[3])
  if ttl < 0 then ttl = 1 end
  return {0, ttl, 3}
end

-- All 3 axes passed; INCR QPS + RPM (TPM is post-deduction, NOT incremented here).
-- EXPIRE ... NX (Redis 7.0+; testcontainers Redis 7.2 pin per tech-stack.md §2.1) is the canonical form:
-- set TTL ONLY if no TTL is currently set. Matches BR-1.2 / BR-2.2 NX intent verbatim (M-1 remediation).
redis.call('INCR', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[4], 'NX')
redis.call('INCR', KEYS[2])
redis.call('EXPIRE', KEYS[2], ARGV[5], 'NX')

return {1, 0, 0}
```

**Post-deduction Lua** (T0.3 — `TPMDeduct`):

Canonical form per Architect H-2 remediation: custom Lua with strict `EXPIRE NX` semantics. Matches BR-3.2 NX intent verbatim; symmetric with the main `check_and_incr.lua` per M-1. The go-redis `Pipeline(IncrBy, Expire)` form is REJECTED because go-redis `Expire(ctx, key, ttl)` does NOT issue `EXPIRE NX` — it slides the TTL on every call, which would silently extend the 60-second window indefinitely on hot keys and contradict the fixed-window contract Architect Q2 ratified.

`apps/api-gateway/internal/middleware/ratelimit/scripts/tpm_deduct.lua` — 2-line script:
```lua
-- KEYS[1] = ratelimit:key:{api_key_id}:tpm
-- ARGV[1] = tokens (int); ARGV[2] = ttl_seconds (60)
redis.call('INCRBY', KEYS[1], ARGV[1])
redis.call('EXPIRE', KEYS[1], ARGV[2], 'NX')
```

Go invocation:
```go
func (m *Middleware) TPMDeduct(ctx context.Context, apiKeyID uuid.UUID, tokens int) error {
  key := fmt.Sprintf("ratelimit:key:%s:tpm", apiKeyID)
  return m.tpmDeductScript.Run(ctx, m.redis, []string{key}, tokens, 60).Err()
}
```

The script is loaded once at boot via `redis.NewScript(tpmDeductLua)` (precedent: `check_and_incr.lua` loader in T0.2 — `EVALSHA` cache + `EVAL` fallback on `NOSCRIPT`). Atomicity guaranteed by Redis single-threaded Lua execution.

#### High Issues (2)

- **H-1 — Missed reuse of Story-3.2 bearer-auth cached claims; T0.8 introduces a per-request PG `SELECT` on the hot path** (Dev Notes "Database Design" → `ResolveCeilings` Go snippet, T0.8 task): The current design calls `SELECT scope FROM he_api.api_keys WHERE id=$1` on EVERY rate-limit check (i.e., every authenticated request).
