## Story

**As a** developer building on the He-API OpenAI-compatible platform,
**I want** to send an image-understanding (Vision) request through the standard `POST /v1/chat/completions` endpoint — using the OpenAI multipart `content` array with `image_url` parts — and have it routed to a vision-capable model (Qwen-VL / GLM-4V),
**so that** my existing OpenAI-SDK image-understanding code works unchanged against He-API, closing the epic's "图像/语音多模态 API 可调通" promise for the image modality.

### AC1: OpenAI 兼容多模态入参 — `messages[].content` 接受 string | 多模态数组（gateway 解析 + vision-only 路由）

**Scenario**
```gherkin
GIVEN
  - The gateway's OpenAI-compatible `ChatMessage` is string-only TODAY (`apps/api-gateway/internal/handlers/chat_completions.go:98-100`, `Content string`), with `validateChatRequest` rejecting an empty/absent string content (line 1190-1199) and the body cap at 1 MiB (`maxChatBodyBytes`, line 62-64) — multipart was explicitly deferred to Epic 9
  - The OpenAI Vision wire shape is `messages[].content` = an ARRAY of parts: `{"type":"text","text":"..."}` and `{"type":"image_url","image_url":{"url":"https://… | data:image/png;base64,…","detail":"auto|low|high"}}`
  - Story 4.7 already models `ModelCapabilities.Vision bool` (`models.go:43`); the catalogue (`packages/models-catalogue`) gains `qwen-vl-max` + `glm-4v` with `vision: true` (AC2)
WHEN
  - A client POSTs `/v1/chat/completions` with a `model` that is vision-capable and at least one `messages[].content` entry that is a multipart array containing ≥1 `image_url` part
THEN
  - The gateway parses `content` as EITHER a plain string (back-compat — every Epic-1→8 flow is byte-identical; `Content` still populated) OR a typed array of parts (`text` | `image_url`), via a custom `UnmarshalJSON` on `ChatMessage` that branches on the JSON token (string vs array) — NO existing text request changes shape or behaviour
  - The gateway validates the multipart structure (AC3 limits) and the part schema (each part has a known `type`; `text` parts have `text`; `image_url` parts have a non-empty `image_url.url`; unknown part `type` → 400)
  - The gateway resolves the model's `vision` capability: an `image_url` part addressed to a NON-vision model (e.g. `deepseek-v3`, `glm-4`) → `400_invalid_request` ("model '<id>' does not support image input") BEFORE any upstream dispatch
  - A vision request is routed via the EXISTING `adapterclient.Registry.Resolve(model)` path to the qwen / glm adapter that hosts the VL model id (AC2); the multipart content is carried on the wire per AC2
  - Text-only requests to a vision model still work (a VL model may receive a pure-text turn); a vision model is a SUPERSET of text capability
  - The content-safety input scanner (Story 8.2, `chat_completions.go:515`) scans the TEXT parts of every message (concatenated/iterated text segments) at the resolved per-Key strictness (8.4); `image_url` parts are NOT text-scanned (outside the 8.1 lexicon scope) — NO 8.2/8.4/8.5 regression, and a blocked text part still returns the canonical `400_content_filter` with zero upstream call
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | **Dual-shape `content` (back-compat-preserving)**: `ChatMessage.Content` is parsed by a custom `UnmarshalJSON` that accepts a JSON string (→ `Content string`, `Parts == nil` — the byte-identical legacy path) OR a JSON array (→ `Parts []ContentPart`, `Content == ""`). A bare object or any other JSON type → 400. Every existing text-only request (Epics 1-8) MUST remain byte-identical end-to-end; `3.3-UNIT-033` (which today asserts array → 400) is REPLACED by an array → 200/route test, and a new test pins the string path unchanged. |
| BR-1.2 | **ContentPart schema**: a part is `{type: "text", text: string}` OR `{type: "image_url", image_url: {url: string, detail?: "auto"\|"low"\|"high"}}`. `type` is required and MUST be one of the two; `text` parts require a non-empty `text`; `image_url` parts require a non-empty `url`. `detail` defaults to `"auto"` when absent. Unknown `type`, missing required sub-field → `400_invalid_request` (param points at the offending part path, e.g. `messages[2].content[1].image_url.url`). |
| BR-1.3 | **Vision-capability gate (fail-closed, pre-dispatch)**: if ANY message carries an `image_url` part, the resolved model MUST have `Vision == true` (Story-4.7 `capabilitiesByModelID`). A non-vision model + image part → `400_invalid_request` BEFORE routing/dispatch (no upstream call, no usage/billing — mirrors the 8.2 reject-before-dispatch ordering). A pure-text request to ANY model (vision or not) is unaffected. |
| BR-1.4 | **Vision is a superset of text**: a vision model id (`qwen-vl-max`, `glm-4v`) accepts BOTH a string `content` and a multipart array — a text-only turn to a VL model routes normally (the adapter emits the vendor's text shape). 9.5 adds image INPUT; it does not remove text input from VL models. |
| BR-1.5 | **Content-safety scans text parts only (do-not-regress)**: the Story-8.2 scanner is fed the TEXT segments of each message (for a multipart message, every `text` part's `text`; for a string message, the string — unchanged). `image_url` parts are not passed to the lexicon scanner (binary/URL data is out of the 8.1 text-lexicon scope). The reject-before-dispatch ordering, per-Key strictness (8.4), and `400_content_filter` envelope (8.5) are all preserved; a clean request still falls through byte-identically. |
| BR-1.6 | **No new endpoint, no shape divergence**: 9.5 adds NO new REST route — it extends the EXISTING `POST /v1/chat/completions` request body. The response shape is unchanged (a normal `chat.completion` / streaming `chat.completion.chunk`); the model "sees" the image and answers in text. `GET /v1/models` (4.7) surfaces `vision: true` for the 2 new ids — no other API-registry change. |
| BR-1.7 | **`validateChatRequest` guard MUST accept multipart (M-3 fix — Architect M-2)**: the existing per-message guard at `chat_completions.go:1189-1197` rejects `!ok || m.Content == ""` → 400. Under BR-1.1/BR-2.2 a multipart message has `Content == ""` and `Parts != nil`, so the UNAMENDED guard would 400 EVERY image request. The guard MUST be amended to: reject only when role is invalid OR (the message has neither a non-empty `Content` NOR `len(Parts) > 0`) — i.e. a message is valid if it carries a non-empty string content OR ≥1 content part. A positive test pins a multipart message past validation; the legacy empty-string-content rejection is preserved for pure-string messages. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `messages[].content` | string \| array | yes | string (legacy) OR non-empty array of parts; object/number/bool → 400 | "Field 'messages[].content' must be a string or an array of content parts." |
| `…content[].type` | string | yes (per part) | one of `text`, `image_url` | "Unsupported content part type '<v>'. Supported: text, image_url." |
| `…content[].image_url.url` | string | yes (image part) | non-empty; scheme ∈ {`https`, `data:image/*;base64`} (AC3 BR-3.2) | "Field 'image_url.url' is required and must be an https URL or a data:image/…;base64 URI." |
| `…content[].image_url.detail` | string | no | one of `auto`,`low`,`high`; default `auto` | "Field 'image_url.detail' must be one of: auto, low, high." |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| `content` is a JSON object / number / bool | 400 | "Field 'messages[].content' must be a string or an array of content parts." | reject pre-dispatch (param = `messages[i].content`) |
| `image_url` part to a non-vision model | 400 | "Model '<id>' does not support image input." | reject pre-dispatch (BR-1.3), zero upstream call |
| unknown content-part `type` | 400 | "Unsupported content part type '<v>'." | reject pre-dispatch (param = part path) |
| text part trips the 8.2 lexicon | 400 | "Request was blocked by the content safety filter." | canonical `400_content_filter`, param=nil (8.2/8.5 reuse) |

**Examples**
- **Input**: `{"model":"qwen-vl-max","messages":[{"role":"user","content":[{"type":"text","text":"What is in this image?"},{"type":"image_url","image_url":{"url":"https://example.com/cat.jpg"}}]}]}` → **Expected**: 200; routed to the qwen adapter hosting `qwen-vl-max`; response is a normal `chat.completion` whose assistant text describes the image; no image bytes/URL in any log line or span.

- **Input**: `{"model":"qwen-max","messages":[{"role":"user","content":"hello"}]}` (legacy text) → **Expected**: byte-identical to the pre-9.5 path (back-compat, BR-1.1).

### AC3: 图像输入安全与限额 — SSRF 防护 + 体积/数量上限 + PII 不外泄（非协商安全契约）

**Scenario**
```gherkin
GIVEN
  - `image_url.url` accepts EITHER a remote URL (`https://…`) or an inline `data:image/<fmt>;base64,<payload>` URI (OpenAI Vision shape)
  - A remote URL is an SSRF vector (an attacker-supplied URL could target internal services / cloud metadata `169.254.169.254` / `file:`/`gopher:` schemes); a large base64 payload is a memory/DoS vector; image bytes are user PII
  - Today the body cap is 1 MiB (`maxChatBodyBytes`, line 62-64) — the code comment already anticipates "~8 MiB for vision payloads … when multimodal content lands"
WHEN
  - A vision request carries `image_url` part(s) — remote URL and/or base64
THEN
  - **SSRF (RATIFIED Q-IMG-SSRF = pure pass-through)**: the gateway and the adapters NEVER fetch the remote URL themselves — the URL is forwarded to the vendor, which fetches it server-side. He-API thus has ZERO server-side image-fetch SSRF surface. As defense-in-depth, the gateway still REJECTS obviously-abusive URLs pre-dispatch: scheme MUST be `https` (remote) or a `data:image/…;base64` URI; `http:`/`file:`/`ftp:`/`gopher:`/`data:` non-image and URLs whose host is a private/loopback/link-local IP literal (`10.*`,`127.*`,`169.254.*`,`192.168.*`,`172.16-31.*`,`::1`,`fc00::/7`) → `400_invalid_request`. The fetch+revalidate alternative is REJECTED (it *creates* the egress SSRF surface, then needs TOCTOU/IP-re-resolution guards — net-negative).
  - **Size / count limits (RATIFIED Q-IMG-LIMITS)**: a two-stage body cap (M-3, see BR-3.8) — the HTTP read cap is `maxVisionBodyBytes = 8 MiB` (`1<<23`) for this endpoint; max images per request `maxImagesPerRequest = 8`; max DECODED base64 size per image `maxImageBytes = 4 MiB`; allowed mime types `image/png`,`image/jpeg`,`image/webp`,`image/gif`. Exceeding any → `400_invalid_request` (`413`-style payload-too-large mapped to the canonical 400 family per the §5.1.2 one-code-per-scenario rule). These are RATIFIED constants, not placeholders.
  - **PII / secret discipline (NON-NEGOTIABLE)**: image bytes, base64 payloads, and image URLs are NEVER written to logs, slog fields, span attributes, or error messages (cascade: 9.4 BR-TR-7 spans, 9.2 BR-RD-9 logs, 9.3 BR-EX-12 exports; `chat_completions.go:590` already withholds `messages[].content` from logs — extended to parts). Error envelopes reference the part PATH (`messages[2].content[1]`), never the URL/bytes
  - A request with NO image part is on the existing 1 MiB text path, completely unaffected (the vision cap applies only when a multipart/image part is present)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | **No server-side image fetch (RATIFIED Q-IMG-SSRF, SSRF-eliminating)**: neither the gateway nor any adapter performs an HTTP GET on `image_url.url`. The URL (or data URI) is forwarded to the vendor, which fetches it. This eliminates the SSRF surface at our tier entirely. The fetch+validate model is REJECTED (it would require an egress allow-list + IP re-resolution/TOCTOU guard — net-negative). |
| BR-3.2 | **URL scheme/host allow-list (defense-in-depth, even with pass-through)**: a remote `image_url.url` MUST be `https://` with a host that is NOT a private/loopback/link-local IP literal; OR a `data:image/(png\|jpeg\|webp\|gif);base64,<payload>` URI. `http:`, `file:`, `ftp:`, `gopher:`, non-image `data:`, and private-IP hosts → `400_invalid_request` pre-dispatch. (This protects the vendor + our reputation even though WE don't fetch.) |
| BR-3.3 | **Vision limits (RATIFIED Q-IMG-LIMITS constants)**: `maxVisionBodyBytes = 8 MiB` (`1<<23`); `maxImagesPerRequest = 8`; `maxImageBytes = 4 MiB` (decoded base64, per image). The 1 MiB text cap (`maxChatBodyBytes`) is UNCHANGED for non-vision requests — enforced post-parse per the two-stage cap (BR-3.8). These are RATIFIED constants (not placeholders); name them as `const`s in `chat_completions.go`. |
| BR-3.4 | **Allowed mime types**: base64 `data:` URIs MUST declare `image/png`, `image/jpeg`, `image/webp`, or `image/gif`; an unsupported/declared-non-image mime → 400. (Remote `https` URLs are not mime-checked by us — the vendor validates; we only scheme/host-check per BR-3.2.) |
| BR-3.5 | **PII discipline (NON-NEGOTIABLE, cascade)**: image bytes / base64 / image URLs are NEVER logged, slog'd, span-attributed, or echoed in error messages. Extends `chat_completions.go:590` ("PII (messages[].content) is intentionally NOT logged") to the multipart parts; aligns with 9.4 BR-TR-7 (spans), 9.2 BR-RD-9 (logs), 9.3 BR-EX-12 (exports). Error params reference part PATHS only. |
| BR-3.6 | **Reject ordering (fail-closed, pre-dispatch)**: all AC3 validations (scheme/host, count, size, mime) run AFTER JSON parse + structural validation (AC1) and BEFORE content-safety scan / routing / any upstream call — a rejected vision request makes ZERO upstream calls and incurs ZERO usage/billing (same ordering discipline as 8.2 reject-before-dispatch). |
| BR-3.7 | **`detail` is forwarded, not interpreted**: `image_url.detail` (`auto`/`low`/`high`) is validated (enum) and passed through to the vendor; the gateway does NOT downscale/resize images (no image processing on our tier — keeps the SSRF/processing surface zero). |
| BR-3.8 | **Two-stage body cap (Architect M-3 — vision-ness is unknown before the body is read)**: `http.MaxBytesReader` caps the read BEFORE JSON parse, but whether a request is vision can only be known AFTER parse. Therefore: **stage 1** — set the endpoint's HTTP read cap to `maxVisionBodyBytes` (8 MiB / `1<<23`) UNCONDITIONALLY (replacing the bare 1 MiB `maxChatBodyBytes` reader on `/v1/chat/completions`); **stage 2** — after JSON parse, if the request is NON-vision (no `image_url` part) AND the raw body length exceeded `maxChatBodyBytes` (1 MiB), reject with the EXISTING 1 MiB `413`/400 error — this preserves the byte-identical text-path size contract (a >1 MiB text request still fails exactly as pre-9.5). A naive "raise the cap only for vision" is unimplementable because the cap precedes the parse. Tests: non-vision 2 MiB body → 400 (stage 2); vision 2 MiB body → accepted; any body > 8 MiB → 400 at the reader (stage 1). |
