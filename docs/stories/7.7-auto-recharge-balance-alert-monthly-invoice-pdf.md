```yaml
Q-PAYMENT-METHODS:   # MOST CONSEQUENTIAL — where the off-session-chargeable token lives
  question: "Where does the reusable, off-session-chargeable payment token live? `balances.auto_recharge_payment_method_id UUID` (data-models §4.1 L81) exists nullable since 7.1's 0008 but references NOTHING — there is no `payment_methods` table today."
  sm_default: "NEW `he_api.payment_methods` table: (id UUID PK, user_id UUID NOT NULL REFERENCES users(id), payment_provider VARCHAR(50) — stripe (card off-session is Stripe-only in 7.7), provider_pm_token VARCHAR(200) — the opaque Stripe PaymentMethod id (PCI §8.4: token ONLY, NEVER a PAN), brand VARCHAR(20) + last4 CHAR(4) — display-safe only, is_default BOOLEAN, created_at). Add the FK `balances.auto_recharge_payment_method_id → payment_methods(id)` (additive ALTER — the column already exists). A NEW POST /v1/billing/payment-methods begins a Stripe SetupIntent (client confirms card → off_session PaymentMethod); the token is saved server-side bound to the authenticated user."
  why: "Auto-recharge is meaningless without a stored, reusable, off-session-chargeable instrument. The §4.1 column was pre-declared for exactly this. A dedicated table isolates the stored-token security surface + supports multiple saved methods + a display-safe (brand/last4) list view (front-end-spec §3.3 / P-9 Auto Recharge config). Alternative: defer saved-payment-methods to its own story and ship 7.7 alert+invoice only — SM rejects (auto-recharge is the headline AC1 of this story)."
Q-OFFSESSION:        # off-session charge capability — the 7.3 seam is on-session only
  question: "The 7.3 `PaymentProvider` seam is ON-SESSION (CreateCheckout → redirect URL + VerifyWebhook). Auto-recharge needs an OFF-SESSION / merchant-initiated charge (no user present). Extend the seam, and for which providers?"
  sm_default: "EXTEND `PaymentProvider` additively with `ChargeOffSession(ctx, pmToken, amountUSD) (extOrderID, err)` + `CreateSetupIntent(ctx, userID) (clientSecret, err)`. Wire ONLY the `stripe` impl in 7.7 (Stripe off_session PaymentIntent confirm — the canonical merchant-initiated-transaction path). PayPal reference-transactions / USDC / Alipay+ / WeChat off-session are OUT (USDC has no off-session concept; the others need separate MIT agreements). Non-card providers return a typed `ErrOffSessionUnsupported`; the auto-recharge config UI only offers Stripe-card methods. The off-session charge STILL settles via a provider webhook → the 7.3 exactly-once credit path is UNCHANGED (no new credit code)."
  why: "Off-session is a fundamentally different provider call than checkout-redirect; isolating it on the seam keeps 7.4-7.6 impls untouched. Stripe-card-only is the pragmatic MVP — it covers the auto-recharge use case without re-opening every provider integration. Architect ratifies the seam signature + the card-only scope."
Q-TRIGGER:           # storm-prevention fence — the dominant correctness risk
  question: "Where does the threshold check fire, and how is an auto-recharge storm (concurrent debits → N top-ups) prevented?"
  sm_default: "billing-svc evaluates the threshold AFTER each 7.1 post-deduction commit (off the chat hot path — the deduction is already async). If new balance < auto_recharge_threshold_usd AND auto_recharge_enabled: acquire a Redis SETNX lock `autorecharge:lock:user:{id}` (TTL ≈ provider-charge + webhook-settle window, e.g. 5 min) AND verify no pending auto recharge_order exists; only then start ONE off-session charge. The lock releases on terminal order state (paid/failed) or TTL. Net: AT MOST ONE in-flight auto-recharge per user. The CREDIT flows through the 7.3 webhook fence (exactly-once)."
  why: "The trigger sits on the already-async deduction path so it never touches the chat response. The Redis-lock + pending-order double-fence is the money-IN analogue of the 7.1 exactly-once debit fence. Architect ratifies the fence (lock TTL, the release-on-terminal mechanism, and whether the pending-order guard alone suffices without the lock)."
Q-INVOICE-TABLE:     # invoice persistence + per-user-month idempotency
  question: "Persist monthly invoices in a NEW `invoices` table, or compute-on-read?"
  sm_default: "NEW `he_api.invoices` table: (id UUID PK, user_id UUID NOT NULL REFERENCES users(id), period CHAR(7) — 'YYYY-MM' UTC, total_debit_usd NUMERIC(12,4), total_credit_usd NUMERIC(12,4), currency CHAR(3) DEFAULT 'USD', status VARCHAR(20) — generated/emailed, pdf_object_key VARCHAR(300), created_at). UNIQUE(user_id, period) = the idempotent per-user-month fence (cron INSERT ... ON CONFLICT DO NOTHING). The invoice freezes the period's figures at generation time (a later refund doesn't retro-mutate a sent statement)."
  why: "A monthly statement is a point-in-time financial record that must be reproducible byte-for-byte after the fact (audit) — compute-on-read would drift as the ledger evolves. The UNIQUE fence makes the cron exactly-once-per-user-month. Architect ratifies the table + whether refunds issue a credit-note vs mutate."

  question: "Which service generates the PDF, with what lib, and where is it stored?"
  sm_default: "billing-svc (or the scheduler that owns the cron) aggregates the period + renders the PDF via a pure-Go PDF lib (e.g. `jung-kurt/gofpdf` or `go-pdf/fpdf` — tech-stack §2.1 addition, Q-PDF-LIB) → stores it in the existing object store (private bucket, non-enumerable key) → writes invoices.pdf_object_key → emits a NotificationEvent so notification-svc emails the link/attachment (notification-svc owns templating+email per the 5.4 precedent; it does NOT generate the PDF). GET /v1/billing/invoices/{id}/pdf proxy-streams the object owner-only."
  why: "Splitting generation (billing-svc, which has the ledger data) from delivery (notification-svc, which owns SendGrid + localized templates) respects the existing service boundaries. A pure-Go PDF lib avoids a headless-browser dependency. Architect ratifies the lib, the owning service, and the storage (object store vs regenerate-on-download — SM prefers store-once for audit reproducibility)."
Q-SCHEDULER:         # the monthly cron home
  question: "Where does the monthly invoice cron live?"
  sm_default: "An in-process scheduler in billing-svc (REUSE the Story 5.4 monthly-cap-reset cron + 7.2 daily-fx-refresh cron mechanism — same lib/pattern), firing at 00:00 UTC on the 1st for the PRIOR calendar month. Multi-pod safety via the invoices UNIQUE(user_id, period) fence (every pod can run; only one wins each row). No new scheduler service."
  why: "billing-svc holds usage_ledger + recharge_orders (the invoice inputs) and already is the money-authority service. Reusing the 5.4/7.2 cron mechanism avoids a new dependency. Architect confirms the cron home + the leader-election-vs-idempotent-fence approach (SM defaults idempotent-fence, no leader election)."
Q-ALERT-CHANNEL:     # low-balance alert delivery path
  question: "Does the low-balance alert fire via a direct notification-svc gRPC (5.4 cap_threshold precedent) or via the `notification.queued` NotificationEvent topic?"
  sm_default: "REUSE the 5.4 model: billing-svc fires the alert (gRPC to notification-svc's Notify surface, mirroring `cap_threshold.go`) with the once-per-episode SETNX dedupe sentinel. A NEW localized template `low_balance` (mirrors `cap_warning`/`cap_tripped` — html+txt per locale). Architect may prefer the async `notification.queued` topic for decoupling — SM defaults to the direct-gRPC parity with 5.4 for consistency."
  why: "5.4 already established the threshold→localized-email pattern with dedupe; reusing it minimizes new surface. Architect rules direct-gRPC vs topic."
Q-FAILMODE:          # repeated auto-recharge failure handling
  question: "What happens when an off-session auto-recharge charge repeatedly fails (declined card, expired token)?"
  sm_default: "On a failed off-session charge: mark recharge_order=failed, release the fence, send the low-balance alert (AC2) WITH a 'auto-recharge failed — update your payment method' variant, and do NOT immediately retry. After N consecutive failures (e.g. 3) within a window, auto-DISABLE auto_recharge_enabled (set FALSE) + notify, so a dead card doesn't generate endless failed charges + alerts. The user re-enables after fixing the method."
  why: "A retry loop against a dead card spams the provider + the user. Disable-on-repeated-failure is the standard SaaS posture. Architect ratifies N + the auto-disable behaviour."
Q-MIGNUM:            # migration ordinal
  question: "Migration file number?"
  sm_default: "`0014_create_payment_methods_and_invoices.sql` — SM ASSUMES 0014 as the next free ordinal after 7.3's 0010; 7.4/7.5/7.6 may have consumed 0011-0013. Dev MUST verify the actual highest applied migration at implementation time and renumber to the true next free ordinal (the number is mechanical, not a design decision)."
  why: "Migration numbers are sequential + environment-determined; the exact ordinal is confirmed against the live migrations dir at Dev time, not guessed at draft."
Q-ZEROINVOICE:       # zero-activity months
  question: "Does a user with zero usage AND zero recharges in a month get an invoice?"
  sm_default: "NO invoice for a fully-inactive user-month (skip — no email noise). A user with ANY activity (≥1 ledger row OR ≥1 paid recharge) gets an invoice. Architect may prefer always-issue (zero-statement) for completeness — SM defaults skip-empty."
  why: "Emailing a $0.00 invoice to dormant accounts is noise. Architect ratifies skip-empty vs always-issue."
```

### AC1: 自动充值 — off-session auto-recharge on low balance (余额低于阈值自动充值)

**Scenario**
```gherkin
GIVEN
  - User U has configured auto-recharge via PUT /v1/billing/auto-recharge: {enabled:true, threshold_usd:"5.00", amount_usd:"20.00", payment_method_id:PM} where PM is a Stripe off-session PaymentMethod saved by U (payment_methods.user_id = U)
  - he_api.balances has U with current_usd above the threshold; no pending auto-recharge order exists for U
  - The 7.1 deduction path is live (a usage.recorded event debits balances.current_usd)
WHEN
  - A 7.1 debit commits and drives balances.current_usd for U BELOW auto_recharge_threshold_usd ("5.00")
  - billing-svc evaluates the auto-recharge trigger AFTER the deduction commits (off the chat hot path)
THEN
  - billing-svc attempts to acquire the storm fence: SETNX `autorecharge:lock:user:U` (TTL ≈ provider-charge + webhook-settle window) AND confirms NO pending auto recharge_order exists for U
  - if the fence is acquired: billing-svc → payment-svc ChargeOffSession(PM.token, "20.00" USD) → Stripe confirms an off_session PaymentIntent → a pending recharge_orders row is created (payment_provider=stripe, the auto-recharge intent)
  - the off-session charge SETTLES via the provider webhook → the **7.3 exactly-once credit path is invoked UNCHANGED** (recharge_orders pending→paid + balances.current_usd += settled_amount in ONE PG tx); balance:user:U:realtime mirrored
  - the fence is RELEASED on terminal order state (paid or failed) or on lock TTL expiry (fail-safe)
  - **storm invariant**: if many concurrent debits each observe balance < threshold, AT MOST ONE in-flight auto-recharge is started for U (the SETNX lock + pending-order guard serialize them); the other observers find the fence held → no-op
  - a successful auto-recharge sends a RECEIPT email (the 7.3 payment.completed → notification-svc path), NOT a low-balance alert (AC2)
  - on a DECLINED off-session charge: recharge_orders=failed, fence released, a low-balance alert fires (AC2, "auto-recharge failed" variant); after N consecutive failures the auto_recharge_enabled flag is auto-set FALSE (Q-FAILMODE) — no endless retry against a dead card
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-R-1 | The trigger fires AFTER the 7.1 PG deduction commits — NEVER inside the deduction transaction (a payment-provider network call must never hold a balances-row lock). It sits on the already-async usage.recorded consumer path (off the chat response). |
| BR-R-2 | **At-most-one-in-flight** is the load-bearing invariant: `SETNX autorecharge:lock:user:{id}` + a `recharge_orders` pending-auto guard. Concurrent debits / parallel consumers crossing the threshold start EXACTLY ONE top-up. The lock TTL bounds a stuck charge; the release-on-terminal-state is the primary release. |
| BR-R-3 | The auto-recharge AMOUNT is the configured `auto_recharge_amount_usd` (the INTENT); the CREDITED amount is the PROVIDER-CONFIRMED settled amount (7.3 Q-AMOUNT cascade — never a client value). USD only (single SoT). |
| BR-R-4 | The off-session charge is supported ONLY for Stripe-card PaymentMethods in 7.7 (Q-OFFSESSION). A non-card provider method → `ErrOffSessionUnsupported`; the config UI only offers Stripe-card methods. |
| BR-R-5 | The CREDIT reuses the 7.3 exactly-once webhook fence verbatim — 7.7 introduces NO new credit path. A redelivered settle webhook is idempotent (7.3 pending→paid state-machine). |
| BR-R-6 | **Auto-disable on repeated failure** (Q-FAILMODE): after N (SM default 3) consecutive failed auto-recharge charges within a window, set `auto_recharge_enabled=false` + notify; the user re-enables after fixing the payment method. |
| BR-R-7 | PUT /v1/billing/auto-recharge MUST validate `payment_method_id` belongs to the authenticated user (payment_methods.user_id = session user) — a foreign method id is rejected (cross-user-binding guard, never accepted). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| enabled | bool | yes | — | n/a |
| threshold_usd | string-decimal | when enabled | > 0; ≤ amount_usd recommended | `422_invalid_auto_recharge` — "Threshold must be a positive amount." |
| amount_usd | string-decimal | when enabled | > 0; provider/account minimum honored | `422_invalid_auto_recharge` — "Recharge amount must be a positive amount." |
| payment_method_id | uuid | when enabled | MUST exist AND belong to the user AND be a Stripe-card method | `422_invalid_payment_method` / `403` — "Selected payment method is invalid." |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Foreign / non-existent payment_method_id | 422 | `422_invalid_payment_method` — "Selected payment method is invalid." | reject PUT; do not enable (BR-R-7) |
| Off-session charge declined | (internal) | — | recharge_order=failed; fence released; low-balance alert "auto-recharge failed" (AC2); count toward auto-disable (BR-R-6) |
| Fence already held (concurrent) | (internal) | — | no-op; the in-flight top-up covers this episode (BR-R-2) |
| Non-card method on ChargeOffSession | (internal) | `ErrOffSessionUnsupported` | do not charge; surface at config time (BR-R-4) |
| Lock TTL expiry with no terminal state | (internal) | — | fail-safe release; next debit re-evaluates (BR-R-2) |

**Examples**
- **Input**: U balance "5.20", threshold "5.00", amount "20.00", enabled. A debit of "0.34" → balance "4.86" < "5.00" → fence acquired → charge $20 off-session → webhook settle → balance credited +20 → "24.86". A burst of 5 more debits during the charge each see balance < threshold but the fence is held → no second charge. ✅ at-most-one.
- **Input**: U's saved card is expired → ChargeOffSession declines 3× across 3 low-balance episodes → after the 3rd, `auto_recharge_enabled=false` + "update your payment method" alert; no 4th charge attempt. ✅ auto-disable.

### AC2: 余额预警 — proactive low-balance alert email (余额预警)

**Scenario**
```gherkin
GIVEN
  - User U's balance is being debited by the 7.1 path
  - A low-balance alert threshold applies (SM default: the SAME auto_recharge_threshold_usd when set; otherwise a system default low-balance threshold — Q-ALERT-THRESHOLD)
  - notification-svc is live with localized SendGrid templates (5.4 cap_threshold precedent)
WHEN
  - A 7.1 debit drives balances.current_usd for U below the low-balance threshold, AND
  - EITHER auto-recharge is OFF, OR auto-recharge is ON but the off-session charge FAILED (AC1 decline)
THEN
  - billing-svc fires a low-balance alert to notification-svc (gRPC parity with 5.4 cap_threshold — Q-ALERT-CHANNEL) using a once-per-episode dedupe sentinel `balancestate:user:U:low_balance_notified` (SETNX, no TTL — cleared on the next successful recharge / period roll)
  - notification-svc renders the NEW localized `low_balance` template (html+txt per locale, mirrors cap_warning) and dispatches ONE email to U's account email
  - **dedupe invariant**: a balance hovering near the threshold across MANY debits sends AT MOST ONE alert per low-balance EPISODE — NOT one per debit; the sentinel clears only when balance returns above the threshold (next recharge), so a later re-dip re-alerts once
  - if auto-recharge is ON and the top-up SUCCEEDS → NO low-balance alert (the receipt email covers it, AC1); the alert is the fallback for the no-auto-recharge / failed-auto-recharge case
  - the alert carries the current balance + a CTA (top up / configure auto-recharge) — money rendered as a string-decimal
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-A-1 | **Once-per-episode dedupe** via `balancestate:user:{id}:low_balance_notified` SETNX (no TTL), cleared when the balance crosses back ABOVE the threshold (a successful recharge). Mirrors the 5.4 cap_threshold SETNX-dedupe — at most one alert per low-balance episode. |
| BR-A-2 | The alert is SUPPRESSED when auto-recharge is ON and succeeds (the receipt email is the user signal). It FIRES when auto-recharge is OFF, or ON-but-failed (the "auto-recharge failed, update your method" variant). |
| BR-A-3 | The email is LOCALIZED per the user's locale (front-end-spec §1: "所有 UI 文案、错误消息、邮件、PDF 都按 locale 渲染") — REUSE the notification-svc multi-locale template mechanism (cap_tripped/cap_warning precedent: html + txt per locale). |
| BR-A-4 | The alert fire is fire-and-forget from billing-svc's perspective — a notification-svc failure logs + counters but never blocks/rolls back the debit (the debit already committed). |
| BR-A-5 | Money in the alert (current balance, threshold) is a string-decimal (Q-Spec-4 cascade). |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| Already-notified this episode (sentinel set) | skip — no duplicate email (BR-A-1) |
| notification-svc unavailable | log `low_balance_alert_failed` + counter; debit stands; retry/next-debit re-attempts (BR-A-4) |
| User has no email on file | log + skip (no crash); surfaced as an ops metric |
| Auto-recharge succeeded | suppress alert; receipt email instead (BR-A-2) |

**Examples**
- **Input**: balance "5.00"→"4.80" (threshold "5.00"), auto-recharge OFF → ONE `low_balance` email; next 10 debits down to "2.10" → NO further emails (sentinel set). User tops up to "30.00" → sentinel cleared. Later dips below "5.00" again → ONE new email. ✅ once-per-episode.
- **Input**: balance dips below threshold, auto-recharge ON + charge succeeds → balance back to "24.86" → NO low-balance email (receipt instead). ✅ suppression.

### AC3: 月度账单 PDF — monthly invoice generation + PDF + email + retrieval (月底邮件发送 PDF 账单)

**Scenario**
```gherkin
GIVEN
  - he_api.usage_ledger holds the prior month's debits (7.1) and he_api.recharge_orders holds the prior month's paid credits (7.3) for user U
  - The monthly invoice cron is scheduled at 00:00 UTC on the 1st (REUSE 5.4 monthly-reset / 7.2 daily-fx cron, Q-SCHEDULER)
  - he_api.invoices has UNIQUE(user_id, period)
WHEN
  - The cron fires for period P = the just-ended UTC calendar month (e.g. on 2026-07-01 00:00 UTC, P = "2026-06")
  - For each user U with ANY activity in P (≥1 usage_ledger row OR ≥1 paid recharge_order — Q-ZEROINVOICE skip-empty)
THEN
  - billing-svc aggregates: total_debit_usd = SUM(usage_ledger.cost_usd WHERE user_id=U AND ts in P); total_credit_usd = SUM(recharge_orders.amount WHERE user_id=U AND status='paid' AND paid_at in P) — string-decimal money, NUMERIC(12,4)
  - INSERT INTO invoices (user_id=U, period=P, total_debit_usd, total_credit_usd, status='generated', ...) ON CONFLICT (user_id, period) DO NOTHING — **exactly one invoice per (user, period)** despite cron re-run / multi-pod
  - if the row was newly inserted: render a PDF (Q-PDF lib) summarizing the period (header, account, period, total debit/credit, per-model usage breakdown, closing balance) → store in the private object store → write invoices.pdf_object_key → advance status to 'emailed' AFTER notification-svc dispatches the invoice email (with the PDF link/attachment, localized)
  - **accuracy invariant**: invoice totals reconcile against the 7.1 ledger and 7.3 orders for the SAME window (total_debit == GET /v1/usage total_cost for P); no double-count, no missing charge
  - a client calls **GET /v1/billing/invoices** → 200 list of the user's invoices (period, totals string-decimal, status, has_pdf)
  - a client calls **GET /v1/billing/invoices/{id}/pdf** → owner-only (invoices.user_id = session user; foreign id → 403/404 IDOR guard) → proxy-streams the stored PDF
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-I-1 | **Exactly-one-per-user-month** via `invoices` UNIQUE(user_id, period) + INSERT ON CONFLICT DO NOTHING. A cron re-run / multi-pod race inserts zero rows for an already-generated user-month → skip. The email-sent transition (generated→emailed) is advanced ONCE (guarded) — no duplicate invoice, no duplicate email. |
| BR-I-2 | An invoice FREEZES the period figures at generation time — a later refund/adjustment does NOT retro-mutate a sent statement (refunds are a future credit-note story). The PDF is reproducible from the frozen `invoices` row. |
| BR-I-3 | period = the just-ended UTC calendar month (`date_trunc('month', now() AT TIME ZONE 'UTC') - interval '1 day'`-based boundary), aligned with the 7.1 GET /v1/usage current-month boundary + the 5.4 00:00-UTC-1st reset. |
| BR-I-4 | Skip-empty (Q-ZEROINVOICE): a user with zero ledger rows AND zero paid recharges in P gets NO invoice (no email noise). Any activity → an invoice. |
| BR-I-5 | All money fields on invoice responses + the PDF are string-decimals (Q-Spec-4 cascade). |
| BR-I-6 | GET /v1/billing/invoices/{id}/pdf is OWNER-ONLY (IDOR guard) — invoices.user_id must equal the session user; the object key is non-enumerable; no public/un-authed PDF route. |
| BR-I-7 | The PDF is LOCALIZED to the user's locale (front-end-spec §1 — emails AND PDFs render per locale). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| period | char(7) | yes (system) | 'YYYY-MM' UTC | n/a (system-generated) |
| total_debit_usd | NUMERIC(12,4) | yes | ≥ 0; string-decimal on API | n/a |
| total_credit_usd | NUMERIC(12,4) | yes | ≥ 0; string-decimal on API | n/a |
| id (download) | uuid | yes | MUST belong to session user | `404`/`403` (IDOR — BR-I-6) |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Cron re-run, invoice exists | (internal) | — | ON CONFLICT DO NOTHING → skip (BR-I-1) |
| GET /v1/billing/invoices/{id}/pdf, foreign id | 404 | `404_not_found` — "Invoice not found." | reject (IDOR guard, BR-I-6) — 404 not 403 to avoid existence disclosure |
| PDF object missing/unreadable | 500 | `500_internal_error` | log + alert; row can be re-rendered from frozen figures (BR-I-2) |
| notification-svc unavailable at email step | (internal) | — | invoice stays status='generated'; re-attempt on next cron tick / retry (no duplicate insert, BR-I-1) |
| User inactive in period | (none) | — | no invoice generated (skip-empty, BR-I-4) |

**Examples**
- **Input**: U has 132 debits totaling "4.5600" + 1 paid recharge "20.0000" in 2026-06. On 2026-07-01 00:00 UTC → invoices row (period "2026-06", total_debit "4.5600", total_credit "20.0000") → PDF rendered + stored + emailed. GET /v1/billing/invoices shows it; GET .../{id}/pdf streams it. Cron retried same day → ON CONFLICT → no second invoice/email. ✅ exactly-once.
- **Input**: user V downloads invoice id belonging to U → 404 (IDOR guard). ✅
- **Input**: dormant user W (no activity in 2026-06) → no invoice, no email. ✅ skip-empty.

### Technical Constraints

- **No new money SoT, no new credit path** — auto-recharge TRIGGERS a 7.3 recharge off-session; the actual balance CREDIT flows through the existing 7.3 exactly-once webhook fence (`recharge_orders` pending→paid + `balances.current_usd` credit in ONE PG tx). Do NOT write a second credit path. [→ docs/stories/7.3-stripe-paypal-integration.md#data_sync_analysis]
- **The trigger sits OFF the chat hot path** — it runs after the 7.1 `usage.recorded` consumer commits the deduction (already async). A payment-provider network call must NEVER hold a `balances` row lock or block a chat response. [→ docs/stories/7.1-billing-engine-per-token-per-call-markup.md AC2 BR-D-3]
- **Storm fence is load-bearing** (the dominant risk) — `SETNX autorecharge:lock:user:{id}` (TTL ≈ charge+settle window) + a `recharge_orders` pending-auto guard → at-most-one in-flight top-up. This is the money-IN analogue of the 7.1 exactly-once debit fence; treat it with the same rigour. [→ SM data_sync_analysis above]
- **PCI §8.4 boundary EXTENDED** — store ONLY the opaque Stripe PaymentMethod token in `payment_methods.provider_pm_token`; NEVER a card PAN (SAQ-A held). The token is secret-grade: slog-redacted, never logged in full, env-discipline per 7.3. [→ docs/architecture/security.md §8.4; docs/stories/7.3-stripe-paypal-integration.md security_analysis]
- **String-decimal money everywhere** (Q-Spec-4 cascade) — all money fields (auto-recharge amounts, invoice totals, alert balance) serialize as string-decimals (`"20.00"`), NEVER JSON numbers; Decimal arithmetic (shopspring/decimal — the 7.1 lib), never float64. [→ docs/architecture/data-models.md §4.5 Change Log 2026-05-25 Q-Spec-4]
- **USD only** — single SoT (7.2 Q-SOT cascade); 7.7 does not introduce CNY auto-recharge or CNY invoices (CNY is 7.2's compute-on-read display). [→ docs/architecture/data-models.md §4.1 balances NOTE L84-87]
