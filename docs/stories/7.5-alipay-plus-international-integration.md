### AC2: 支付确认入账 — payment-success notification → exactly-once balance credit (USD pass-through / CNY→USD at fx) (充值到账)

**Scenario**
```gherkin
GIVEN
  - a PENDING recharge_orders row for user U {payment_provider:'alipay', external_order_id:<Antom paymentId>, amount:50.0000 (USD) or 350.0000 (CNY), currency:'USD'|'CNY', status:'pending'} (from AC1)
  - the user has paid in their Alipay+ wallet on Antom's hosted cashier; Antom will POST a signed payment notification to POST /v1/billing/webhooks/alipay
  - the inherited exactly-once credit machinery (recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id) + the provider-agnostic billing-svc credit applier incl. its toUSD CNY→USD branch) is REUSED unchanged
WHEN
  - Antom POSTs a signed notification (resultStatus S | U | F) to POST /v1/billing/webhooks/alipay
THEN
  - **resultStatus=S (SUCCESS → CREDIT)**: alipay.VerifyWebhook (AC3) verifies the RSA signature → returns a VerifiedEvent {Kind:EventRechargePaid, OrderID:<our id from paymentRequestId>, ExternalOrderID:<Antom paymentId>, SettledAmount:"50.00" (or "350.00" — minor-unit→decimal, the Antom-settled TRUTH), Currency:'USD'|'CNY', Status:'paid'}; the webhook handler emits the SAME he.payment.v1 payment.completed PaymentEvent (UNCHANGED producer); billing-svc's provider-agnostic credit applier consumes it and, in ONE PG transaction: (1) `UPDATE recharge_orders SET status='paid', paid_at=NOW() WHERE id=$order AND status='pending'` → zero rows (redelivery) ⇒ skip; (2) else verify settled==intent in the PAID currency (BR-C-3 / Q-FX-INTENT), convert settled toUSD (USD pass-through, or CNY/rate HALF-UP — credit.go:290-311), then `UPDATE balances SET current_usd = current_usd + creditUSD, updated_at=NOW() WHERE user_id=U` (UPSERT zero row if absent); (3) COMMIT
  - **post-commit (best-effort, INHERITED)**: INCRBYFLOAT balance:user:U:realtime by creditUSD; a Redis failure logs + alerts but the durable PG credit stands
  - **resultStatus=U (in-progress / unknown → NO CREDIT)**: VerifyWebhook returns Kind:EventUnhandled; the handler 200-ACKs; NO balance change; recharge_orders stays 'pending'
  - **resultStatus=F (fail / closed / cancelled → NO CREDIT)**: Kind:EventRechargeFailed → recharge_orders.status='failed'; NO credit; 200 ACK
  - **settled<intent (partial / mismatch → PARK)**: the inherited amount-integrity guard (settled≠intent in the paid currency → stay pending + alert + NO credit, BR-R-1) parks it; 200 ACK
  - **observable**: GET /v1/balance reflects the credit after resultStatus=S (reads PG authoritative); for a CNY recharge the credited current_usd is the fx-converted value; Prometheus he_payment_credit_amount_usd{provider="alipay"} histogram; slog payment_credit{order_id, user_id, provider:"alipay", settled_amount, settled_currency, settled_usd}
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-C-1 | **Credit fires ONLY on resultStatus=S** (Antom finality). resultStatus=U (in-progress/unknown) NEVER credits — crediting a non-terminal result risks crediting a payment that never completes (Q-CONFIRM). resultStatus=F → status='failed', no credit. |
| BR-C-2 | **Exactly-once credit is INHERITED** (the 7.3 recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id)). A redelivered payment-success finds status='paid' → zero-row UPDATE → no second credit. The UNIQUE key is per-provider so an Antom paymentId never collides with a stripe/paypal/coinbase id. |
| BR-C-3 | **The credited amount is the provider-confirmed Antom-settled value** (BR-R-1 cascade), minor-unit→string-decimal (Q-AMOUNT-UNITS), NEVER the create-order intent. The amount-integrity guard compares settled-vs-intent in the **PAID currency** (Q-FX-INTENT) BEFORE the toUSD conversion — so fx-rate drift between create and settle does NOT falsely trip the park. A genuine settled≠intent → park + alert + NO credit. |
| BR-C-4 | **CNY→USD fx-at-credit (FIRST real exercise, INHERITED code)**: a CNY settlement credits balances.current_usd at the latest 7.2 fx_rate at settlement via the EXISTING credit.go toUSD() branch (USD = settled / CNY-per-USD rate, DivRound HALF-UP moneyScale=4 — credit.go:290-311 + fxRateSQL:103-104). A USD settlement is the toUSD() pass-through. current_rmb stays reserved/0 (7.2 Q-SOT). The credit applier is UNCHANGED — 7.5 is the first channel to drive its non-USD branch. |
| BR-C-5 | **The credit applier + producer + consumer are REUSED VERBATIM** — alipay emits the SAME PaymentEvent; no alipay-specific code exists downstream of VerifyWebhook. Any alipay special-casing leaking into credit.go is a design regression (BR-A-1 cascade). |
| BR-C-6 | **USD single SoT** (7.2 Q-SOT, INHERITED): the credit ALWAYS lands in balances.current_usd; there is no second accounting wallet. The 7.1 reconciliation invariant (debits + credits ↔ balance) is extended additively. |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| resultStatus=S, signature valid, pending order, settled==intent | pending→paid + credit (toUSD, one tx); 200 ACK |
| resultStatus=S redelivered (already paid) | zero-row UPDATE → no second credit; 200 ACK (BR-C-2) |
| resultStatus=U | 200 ACK; NO credit; order stays pending (BR-C-1) |
| resultStatus=F | recharge_orders.status='failed'; NO credit; 200 ACK |
| resultStatus=S but settled<intent (paid currency) | park + alert; NO credit; 200 ACK (BR-C-3) |
| verified but PG down on apply | 5xx; do NOT ACK; Antom redelivers (inherited at-least-once + idempotent) |
| minor-unit parse / scale failure | fail-closed: park + alert, NO credit (never a mis-scaled credit, Q-AMOUNT-UNITS) |

**Examples**
- **Input**: pending USD order $50 → resultStatus=S (settled 50.00 USD) → settled==intent → pending→paid + current_usd +50.0000; GET /v1/balance → `{"current_usd":"50.0000",...}`. ✅ auto-credited.
- **Input**: pending CNY order ¥350 → resultStatus=S (settled 350.00 CNY), latest rate 7.00 CNY/USD → creditUSD = 350/7.00 = 50.0000 → current_usd +50.0000; current_rmb untouched. ✅ CNY→USD fx-at-credit.
- **Input**: the SAME payment-success redelivered → already 'paid' → zero-row UPDATE → no second credit. ✅ exactly-once.
- **Input**: resultStatus=U (in-progress) → 200 ACK, balance unchanged, order still 'pending'. ✅ no premature credit.
- **Input**: resultStatus=S but settled 49.50 CNY-paid for a ¥350 intent (short) → park + alert + NO credit; order stays 'pending'. ✅ amount-integrity holds (compared in CNY).

### AC3: Alipay+ webhook 安全 — RSA2 asymmetric signature verification + inherited exactly-once backbone (安全)

**Scenario**
```gherkin
GIVEN
  - POST /v1/billing/webhooks/alipay is mounted OUTSIDE the bearer/CSRF chain (4.7 /public/* precedent, REUSED) — the Alipay+ signature is the sole credential
  - ALIPAY_PLUS_ALIPAY_PUBLIC_KEY (verify) + ALIPAY_PLUS_MERCHANT_PRIVATE_KEY (sign outbound) are configured (Q-SIG); raw-body + ALL headers are preserved end-to-end (the gateway forwards the EXACT bytes + Client-Id/Request-Time/Signature, REUSED billing_webhook.go:70-76 pass-through)
  - the provider impl is configured with the PUBLIC notify path (WithNotifyPath, default "/v1/billing/webhooks/alipay") for signed-string reconstruction (Q-NOTIFY-PATH)
  - the recharge_orders state-machine + UNIQUE fence carry the inherited idempotency (AC2 BR-C-2)
WHEN
  - a notification POST arrives (genuine, forged, replayed, stale, or amount-tampered)
THEN
  - **genuine (valid signature)**: alipay.VerifyWebhook reconstructs `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>`, base64-decodes the `Signature` header value, and verifies it with `rsa.VerifyPKCS1v15(alipayPublicKey, crypto.SHA256, sha256(signedString), sig)` → match AND Request-Time within the freshness window → parse the payment notification → map resultStatus → VerifiedEvent Kind (AC2) → process; return 2xx promptly
  - **forged (invalid/absent/tampered signature, or wrong key)**: VerifyWebhook returns provider.ErrSignatureInvalid → the handler maps it to `400_webhook_signature_invalid` BEFORE parsing the body into any money action; NO credit; slog payment_webhook_rejected{provider:"alipay", reason:"signature"} + metric; the body is NEVER trusted
  - **constructed-string tampering (altered URI / Client-Id / Request-Time / body)**: ANY altered component changes the signed string → RSA verify fails → `400_webhook_signature_invalid` (fail-closed); the impl reconstructs the URI from its CONFIGURED public notify path (NOT r.URL.Path, which is the internal proxied path)
  - **replayed (a captured VALID payment-success re-POSTed)**: ⚠️ POSTURE BETTER THAN 7.4 — (a) a STALE Request-Time (outside the bounded skew) → reject (the signature-timestamp freshness layer Coinbase lacked, RESTORED); (b) a within-window replay is neutralised by the inherited recharge_orders pending→paid state-machine (zero-row UPDATE → no second credit) — defence-in-depth, TWO layers
  - **exactly-once credit (INHERITED)**: credit applies ONLY on a pending→paid transition; already-paid ⇒ zero rows ⇒ 200 ACK + skip; status-flip + credit are ONE PG tx (atomic); UNIQUE(payment_provider, external_order_id) prevents two orders binding one Antom paymentId
  - **amount integrity (INHERITED)**: the credited amount is the provider-verified Antom-settled value (minor-unit→decimal); settled≠intent (paid currency) → park + alert + NO credit
  - **PCI / no-card**: the Alipay+ notification carries wallet payment ids + amounts — NEVER a card PAN (wallet channel, provider-hosted cashier; SAQ-A boundary holds); we persist the Antom paymentId + our order id only
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-W-1 | **Signature verification is MANDATORY and happens BEFORE any body processing** (INHERITED, BR-W-1 from 7.3/7.4). An unverified Alipay+ notification body is NEVER parsed into a credit. The signature is the credential (the route is otherwise unauthenticated). |
| BR-W-2 | **Alipay+ signature scheme** (NEW — FIRST ASYMMETRIC): the `Signature` header is `algorithm=RSA256,keyVersion=<v>,signature=<urlencoded-base64>`; verify with RSA-SHA256 (`rsa.VerifyPKCS1v15`, `crypto.SHA256`) against ALIPAY+'s PUBLIC key over the reconstructed `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>` string. ⚠️ ASYMMETRIC: we hold only Alipay+'s PUBLIC key to verify (not a shared secret) — the channel cannot be forged from our config alone. ⚠️ CONSTRUCTED string: the signed content is method+URI+Client-Id+Request-Time+body, NOT the raw body alone. |
| BR-W-3 | **Raw-body + header integrity** (INHERITED + EXTENDED): RSA verify needs the EXACT raw bytes Antom signed AND the exact Client-Id + Request-Time header values; no middleware (gateway proxy included) may re-serialize/normalize the body OR drop those headers. The gateway billing_webhook.go forwards ALL headers verbatim + the raw body byte-faithfully (billing_webhook.go:70-76, REUSED — verified sufficient, no proxy change). |
| BR-W-4 | **Replay defence = Request-Time freshness + state-machine** (⚠️ BETTER than 7.4 coinbase): the Alipay+ signed string INCLUDES Request-Time → a bounded-skew freshness check rejects stale notifications (the signature-timestamp layer Coinbase lacked, RESTORED, on par with Stripe); the inherited recharge_orders pending→paid idempotency neutralises any within-window replay. Two layers. P0 test lanes: stale-Request-Time reject + replay-of-valid-success idempotency. |
| BR-W-5 | **Provider 2xx discipline** (INHERITED, BR-W-5 from 7.3): verified + already-processed → 200 (so Antom stops retrying); verification FAILURE → 400; transient processing error (PG down) → 5xx so Antom redelivers (at-least-once + idempotent). |
| BR-W-6 | **Secrets** (Q-SIG, ⚠️ higher blast radius): `ALIPAY_PLUS_MERCHANT_PRIVATE_KEY` (signs ALL our outbound Antom calls — broader blast radius than an HMAC webhook secret) is DISTINCT from `ALIPAY_PLUS_ALIPAY_PUBLIC_KEY` (verifies inbound; a public key) and `ALIPAY_PLUS_CLIENT_ID`; all env-injected; the PRIVATE key NEVER logged (the 7.3/7.4 secret discipline cascade). keyVersion in the Signature header supports rotation. |
| BR-W-7 | **Minor-unit fail-closed** (Q-AMOUNT-UNITS): a minor-unit→decimal parse/scale failure on a verified notification → park + alert + NO credit; NEVER a silently mis-scaled (100×) credit. |
| BR-W-8 | **No card data / wallet no-PAN** (§8.4): the payload carries Antom payment ids + wallet amounts only — never a PAN; we persist the paymentId + order id. The SAQ-A provider-hosted boundary holds (the user authenticates in their wallet on Antom's cashier). |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Invalid / absent / tampered `Signature`, or wrong public key | 400 | `400_webhook_signature_invalid` — "Webhook signature verification failed." | reject before body processing (BR-W-1); slog + metric (REUSED code) |
| Altered URI / Client-Id / Request-Time / body (constructed-string component) | 400 | `400_webhook_signature_invalid` | RSA verify fails (fail-closed, BR-W-2/W-3) |
| Stale Request-Time (outside skew window) | 400 | `400_webhook_signature_invalid` | reject (freshness layer, BR-W-4) |
| Verified but already-processed (redelivery / within-window replay) | 200 | — | ACK + skip; no second credit (BR-W-4/W-5) |
| Verified but PG down on apply | 5xx | — | do NOT ACK; Antom redelivers (BR-W-5) |
| Verified resultStatus=U (in-progress) | 200 | — | ACK; no-op, no credit (AC2 BR-C-1) |
| Verified but settled ≠ order intent (paid currency) | 200 | — | ACK (verified) but park + alert + NO credit (BR-C-3) |
| Verified but minor-unit scale failure | 200 | — | ACK (verified) but park + alert + NO credit (BR-W-7) |

**Examples**
- **Input**: forged POST with a bogus `Signature` (or signed by a non-Alipay key) → `400_webhook_signature_invalid`; no recharge_orders touched; no credit. ✅ forgery blocked (asymmetric — cannot forge without Alipay+'s private key).
- **Input**: a genuine notification but with a tampered Request-Time header → reconstructed string differs → RSA verify fails → 400. ✅ constructed-string integrity.
- **Input**: a captured valid payment-success replayed 1h later → Request-Time now stale → rejected by the freshness window (layer 1). Even if within window → order already 'paid' → zero-row UPDATE → no credit (layer 2). ✅ replay neutralised (two layers, BR-W-4).
- **Input**: genuine resultStatus=S for a pending order → verified → pending→paid + credit (one tx). ✅ exactly-once.

## Dev Notes

> **Key Principle**: enough context here that the Dev Agent need not re-read architecture docs. All references are `[→ file#section]` or `file:line`. **The defining constraint of this story is REUSE**: 7.3 built a provider-agnostic spine; 7.4 proved the additive-channel pattern; 7.5 adds ONE provider impl. Do NOT rebuild or modify the spine. The TWO genuinely-new things are both INSIDE the provider impl: (1) the RSA2 asymmetric signature over a constructed string; (2) the minor-unit amount parse. The CNY→USD fx is INHERITED credit.go code, first-exercised here.

### Technical Constraints
- **Additive-only on a proven seam** — implement `alipay.Provider` against the EXISTING `PaymentProvider` interface (`apps/payment-svc/internal/provider/provider.go:86-96`); wire it in `buildRegistry` (`cmd/server/main.go` ~181-186, coinbase precedent); add `"alipay"` to `supportedProviders` (`apps/api-gateway/internal/handlers/billing_write.go:47`); mount the webhook route. Do NOT touch the producer, the credit applier (incl. its toUSD fx branch), recharge_orders, the proto, or the Kafka topic. [→ provider.go:2-6 names 7.5]
- **Alipay+ / Antom asymmetric signature scheme** (the genuinely-new security primitive, Q-SIG) — the `Signature` header is `algorithm=RSA256,keyVersion=<v>,signature=<urlencoded-base64>`; verify with `rsa.VerifyPKCS1v15(alipayPublicKey, crypto.SHA256, sha256(signedString), sig)` over the reconstructed `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>` string BEFORE parsing (BR-W-1/W-2). ⚠️ FIRST asymmetric scheme (we hold Alipay+'s PUBLIC key, not a shared secret); ⚠️ FIRST constructed-string signing (method+URI+Client-Id+Request-Time+body — NOT raw body alone). The URI is the CONFIGURED public notify path (Q-NOTIFY-PATH — `WithNotifyPath`, default "/v1/billing/webhooks/alipay"), NOT `r.URL.Path` (which is the internal proxied path at the handler). Request-Time gives a freshness window → reject stale (BR-W-4 — the replay-timestamp layer Coinbase lacked, RESTORED). [→ AC3]
- **Outbound signing** — sign OUR Antom calls (CreateCheckout) with `ALIPAY_PLUS_MERCHANT_PRIVATE_KEY` (RSA-SHA256) over the same constructed-string shape. ⚠️ This private key has a BROADER blast radius than an HMAC webhook secret (it authenticates ALL our outbound calls) — never log it. [→ AC1 BR-A-7]
- **Credit on resultStatus=S ONLY** (Q-CONFIRM) — `S` → EventRechargePaid (credit); `U` (in-progress/unknown) → EventUnhandled (200 ACK, no credit); `F` → EventRechargeFailed; settled≠intent → park via the inherited amount-integrity guard. [→ AC2 BR-C-1]
- **Provider-confirmed amount, never intent** (BR-R-1 cascade, INHERITED) — SettledAmount in the VerifiedEvent is the Antom-confirmed value (minor-unit→decimal); the billing-svc applier already parks settled≠intent. Do NOT credit the create-order intent. [→ AC2 BR-C-3]
- **Minor-unit amounts** (Q-AMOUNT-UNITS) — Antom paymentAmount.value is an INTEGER in the currency's minor units (USD/CNY = 2 digits → "5000" = "50.00"). Use a per-currency minor-unit table (NOT a hardcoded /100) + fail-closed on scale loss → string-decimal end-to-end (shopspring/decimal). A mis-scale = a 100× credit defect (BR-W-7). [→ AC1/AC2]
- **Multi-currency USD/CNY + fx-at-credit** (Q-CURRENCY, ⚠️ FIRST real exercise) — alipay enables {USD, CNY}. A CNY settlement credits `balances.current_usd` at the latest 7.2 fx_rate at settlement via the EXISTING `credit.go` toUSD() branch (USD = settled / CNY-per-USD rate, DivRound HALF-UP moneyScale=4 — credit.go:290-311 + fxRateSQL:103-104). USD settlement = pass-through. current_rmb stays reserved/0 (7.2 Q-SOT). ⚠️ The amount-integrity guard must compare settled-vs-intent in the PAID currency (Q-FX-INTENT) so fx drift doesn't falsely park. The credit applier is UNCHANGED — 7.5 only drives its non-USD branch. [→ AC2 BR-C-3/C-4]
- **No card / wallet channel** — Alipay+ is a wallet/account channel (user authenticates in their wallet on Antom's hosted cashier); no PAN transits He-API (SAQ-A boundary holds, §8.4). [→ AC3 BR-W-8]
- **Money + amount fields are string-decimals** — never JSON numbers (Q-Spec-4 / 7.1 BR-A-3). [→ docs/architecture/data-models.md §4.5]
- **Decimal, never float** — `shopspring/decimal`, HALF-UP; already in payment-svc/billing-svc go.mod (REUSED). [→ 7.1 Architect M-1]
- **New deps respect workspace otel pins** — `go get pkg@ver`, do NOT re-tidy the workspace. [[project_otel_version_pin_gotcha]]
- **Toolchain limits** — buf/atlas/docker cannot run locally; tests via httptest/pgxmock/miniredis; testcontainers/compose E2E = CI. No proto change in 7.5 (no hand-edited pb.go needed). RSA test keys: generate an ephemeral RSA keypair in-test (crypto/rsa) to sign fixtures + verify — no real Alipay key needed. [[project_toolchain_env_limits]]
