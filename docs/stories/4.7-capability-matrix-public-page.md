**Goal**: 实现 6 家中国主流 LLM 的 plugin 适配器，规范化为 OpenAI 协议；并验证流式/非流式/token 用量准确透传

- **Backend AC1** — `GET /v1/models` response shape EXTENDED to include a non-null `capabilities` sub-struct on every `ModelEntry` (additive JSON field; backward-compatible with the OpenAI Python SDK Pydantic `extra="allow"` policy verified in Story 3.5 contract tests).
- **Backend AC1 (companion)** — NEW unauthenticated `GET /public/models` endpoint mirroring the same capability matrix shape, so the anonymous public marketing page can fetch it without a bearer key (single Go-side source of truth; the bearer-protected `/v1/models` + public `/public/models` emit byte-identical capability payloads for the 11-entry catalogue).

- **OpenAI SDK contract tests** — Existing `openai_sdk_models_contract_test.py` extended to assert the new `capabilities` field exists and is well-shaped per AC1 BR-1.2; NEW `public_models_contract_test.py` exercises the unauthenticated endpoint via plain `httpx` (the OpenAI SDK has no native concept of a key-less ModelList client).

### AC1: GET /v1/models 返回完整能力标签 + 公开镜像端点 GET /public/models

**Scenario**
```gherkin
GIVEN the api-gateway is running with Story 3.5's `handlers.ModelsHandler` extended per this Story
  AND the 11-entry static catalogue `modelsCatalogue` carries a per-entry `Capabilities` sub-struct populated per BR-1.2/BR-1.3
WHEN a client calls EITHER (a) `GET /v1/models` with a valid bearer API key OR (b) `GET /public/models` with NO Authorization header
THEN both responses MUST return HTTP 200 with `Content-Type: application/json`
  AND the response body MUST be the OpenAI `ModelList` envelope `{"object":"list","data":[ModelEntry, ...]}`
  AND every `data[i]` entry MUST contain a non-null `capabilities` field whose shape conforms to BR-1.2
  AND every entry's `capabilities` value MUST be populated per the 11-row table in BR-1.3 verbatim (no missing fields, no spurious extras)
  AND the bearer-protected and unauthenticated responses MUST be byte-identical for the catalogue payload (single Go-side source of truth — verified via 4.7-INT-001)
  AND the existing Story-3.5 fields (`id` / `object` / `created` / `owned_by`) MUST retain their canonical declaration order; `capabilities` appears LAST as a He-API extension (BR-1.4)
  AND the OpenAI Python SDK's `client.models.list()` MUST continue to round-trip the response without raising (Pydantic `extra="allow"` policy — verified via 4.7-CONTRACT-001)
```

- **No DB writes on the request path** — Capability data is in-memory (Go static map per T0.3). - **No new auth surface** — `GET /v1/models` bearer-auth chain is UNCHANGED (Story 3.2 BR-1.4 inheritance). `GET /public/models` is the FIRST unauthenticated endpoint on the gateway pre-Story-5.x rate-limit Stories — no IP allow-listing, no rate-limiting in Story 4.7 (deferred). [→ docs/architecture/security.md] if/when a security section exists for unauthenticated read endpoints; otherwise rely on the architecture's general "least privilege" posture.
- **Backward compatibility with OpenAI SDK** — The `capabilities` field is additive on the OpenAI `Model` shape. The official Python SDK (`openai==1.40.*` per Story 3.3 pin) uses Pydantic with `extra="allow"` so the field surfaces via `model.model_extra["capabilities"]`. TypeScript SDK (`openai-node`) similarly allows unknown fields. Story-4.7 contract tests (T2.7) verify this explicitly. [→ Story 3.5 BR-2.9 + AR1-R5 — same backward-compat principle established for the embeddings response shape.]
- **i18n key-set completeness** — Story-2.1 cascade requires the key SET (NOT the translated values) to be complete in every locale file for CI `console / i18n-keys-completeness` to pass. T0.5 + T0.7 enforce this; non-English locales receive `[en-pending]` prefixed values per the Story-2.1 m-1 precedent. [→ docs/architecture/source-tree.md] "注: Story 2.1 — `apps/console/messages/` 采用 namespace-split".
- **No streaming, no SSE** — Both backend endpoints are pure non-streaming JSON. They do NOT touch the Story-3.4 streaming.Writer / AdapterChunker plumbing.
- **Performance regression marker** — < 5ms P95 on warm path for BOTH backend endpoints (BR-1.10). Not an AC-level SLO; documented for cold-start preservation. Frontend Lighthouse Performance ≥ 90 (BR-2.10) is also a regression marker, not an AC gate.

### Database Design

**Decision (pending Architect OQ-4.7-2 ratification)**: Story 4.7 KEEPS capability data in-memory (Go package-private `capabilitiesByModelID` map). The `he_api.models` table schema in [→ docs/architecture/data-models.md#§4.1] already declares `capabilities JSONB NOT NULL`, but the table has NO physical migration in `migrations/postgres/` yet (database-registry.md shows only `0006_create_api_keys.sql` as of Story 3.2).

**SM lean** (deferral): Land the data in-memory + leave the migration for a later Story (likely Epic 5 or Epic 6 routing) where DB-driven model lookup becomes load-bearing. Rationale:
1. **Single source of truth principle** is preserved EITHER WAY — the Go map IS the source of truth in option B; the DB seed would BECOME the source of truth in option A.
2. **Operational risk** — adding a migration introduces (a) seed-data drift risk between dev/staging/prod, (b) runtime DB dependency for the public endpoint (latency + availability hit on the marketing page's TTI), (c) the need to introduce a Story-5.x cache invalidation strategy.
3. **YAGNI** — neither AC requires DB-backed lookup; both work with in-memory data; the architecture's pre-flagged DB schema is aspirational, not load-bearing.

**Option A scope (if Architect rules in favour)**: ADD `migrations/postgres/0007_seed_models_catalogue.sql` (Atlas versioned migration per Story 1.6 Q1 cascade) inserting the 11 catalogue rows with full capability JSONB. Backend handlers SHIFT to read the catalogue from DB at startup via a new `internal/models/repository.go` (precedent: `internal/adapterclient.Registry` in Story 4.1). Risk: per-deploy ConfigMap-style drift if seed file diverges from Go-side adapter capabilities (Story 4.8 contract tests would catch).

import { z } from "zod";

export const ModelCapabilitiesSchema = z.object({
  chat: z.boolean(),
  streaming: z.boolean(),
  function_calling: z.boolean(),
  vision: z.boolean(),
  json_mode: z.boolean(),
  context_window_tokens: z.number().int().nonnegative(),
  max_output_tokens: z.number().int().nonnegative(),
});
export type ModelCapabilities = z.infer<typeof ModelCapabilitiesSchema>;

export const ModelEntrySchema = z.object({
  id: z.string(),
  object: z.literal("model"),
  created: z.number().int(),
  owned_by: z.string(),
  capabilities: ModelCapabilitiesSchema,
});
export type ModelEntry = z.infer<typeof ModelEntrySchema>;

export const PublicModelsResponseSchema = z.object({
  object: z.literal("list"),
  data: z.array(ModelEntrySchema),
});
export type PublicModelsResponse = z.infer<typeof PublicModelsResponseSchema>;

export async function fetchPublicModels(): Promise<PublicModelsResponse> {
  const base = process.env.HE_API_PUBLIC_BASE_URL ?? "http://localhost:8080";
  const res = await fetch(`${base}/public/models`, { next: { revalidate: 300 } });
  if (!res.ok) {
    // BR-error-handling row 1 — return empty matrix; caller renders fallback banner
    return { object: "list", data: [] };
  }
  const json = await res.json();
  const parsed = PublicModelsResponseSchema.safeParse(json);
  if (!parsed.success) {
    // Filter malformed entries silently per AC2 error-handling row 2
    return { object: "list", data: [] };
  }
  return parsed.data;
}

Versioning the URL would imply SDK reach it does not have. `/v1/models?public=true` couples auth-bypass to a query parameter (anti-pattern: CORS preflight + middleware path matching + observability filtering all become more complex). `/public/*` is the version-independent public-information convention which Epic-9 observability + Epic-10 marketing endpoints (`/public/benchmark`, `/public/compliance`) inherit. **Reject** `/v1/public/models` and `/v1/models?public=true`.

#### OQ-4.7-5: ModelsHandler ↔ PublicModelsHandler sharing — **Constructor injection ratified** (SM lean)
`NewPublicModelsHandler(logger, startedAt, snapshot)` provides explicit dependency surface — testable via `httptest`, no hidden init-order coupling, no shared mutable state. Package-level shared state complicates parallel-test isolation. Handler embedding via Go struct promotion would mix bearer-aware and bearer-bypass methods on a single type — semantically wrong. Both handlers share a common `data []ModelEntry` snapshot built ONCE at `main.go` bootstrap from `modelsCatalogue` + `capabilitiesByModelID`; both endpoints emit byte-identical bodies (verified by 4.7-INT-001).

#### OQ-4.7-6: 405 envelope code — **NEW `405_method_not_allowed` ratified** (SM lean)
Story-3.6 ratification established the §5.1.2 precedent "one envelope code per HTTP scenario". The current superset has dedicated codes for 401, 402, 403, 410, 412, 413, 423, 428, 429, 500, 501, 502, 503, 504 — adding 405 fills the only major method-mismatch hole. Reusing `400_invalid_request` would conflate "request body invalid" with "wrong HTTP method", breaking observability dashboard filtering (oncall query "how often does someone POST to /public/models?" cannot be answered without a dedicated code). T5.5 §5.1.2 row addition is correct; T2.3 MUST set `Allow: GET` header per RFC 7231 §6.5.5 (already specified in AC1 error-handling row 4). New codeMetadata entry: `405_method_not_allowed → invalid_request_error` (consistent with §5.1.2 mapping table for 4xx codes).

#### OQ-4.7-7: CORS policy for `/public/*` — **Allow `*` scoped to `/public/*` with anti-credential guard ratified**
Capability data is read-only public information — zero user data, zero credentials, zero session cookies. Third-party model-comparison websites + benchmark aggregators benefit ecosystem reach (precedent: HuggingFace model-card API allows `*` CORS). **HARD CONSTRAINTS**:
1. `Access-Control-Allow-Origin: *` MUST scope ONLY to `/public/*` path prefix in the existing `apps/api-gateway/internal/middleware/cors` chain.
2. The `/public/*` handler MUST NOT emit `Access-Control-Allow-Credentials: true` AT ALL (combining `*` with credentials is a standard CORS attack vector).
3. `/v1/*` and `(console)`-targeted endpoints retain their existing tight allow-list (`he-api.com` + `console.he-api.com`) — bearer-protected routes MUST NOT widen.
4. Add 4.7-INT-007 (NEW test ID per m-1) asserting `Access-Control-Allow-Credentials` is NEVER sent on `/public/models` OPTIONS or GET responses.

#### OQ-4.7-8: Frontend cache policy — **`revalidate: 300` (5-min ISR) ratified** (SM lean)
Capability data changes rarely (vendor capability shifts on weeks/months, not minutes). 5-min staleness is acceptable for marketing-page TTI optimisation. `build-time static` is **rejected** — couples deploys (cache invalidation requires console redeploy). `cache: 'no-store'` is **rejected** — defeats Next.js Server Component caching for a marketing page expected to draw search traffic. Optional dev-mode refinement (m-3): `revalidate: 60` when `NODE_ENV !== 'production'`.

#### OQ-4.7-9: `(marketing)` group placement — **Inside `apps/console/app/[locale]/` ratified** (SM lean)
`docs/architecture/source-tree.md §6 line 40` already pre-flags `(marketing)/` inside `apps/console/app/[locale]/`. Story 4.7 implements the pre-flagged design — this is NOT a new architectural decision. Splitting into `apps/marketing/` adds operational overhead (separate `package.json` + Turbo task wiring + ArgoCD Application + dedicated deploy domain) WITHOUT benefit at this stage — both surfaces share the same i18n namespace registry + design system. Epic-10 marketing-launch MAY split if bundle size or deploy cadence demands; that is a future Story's decision under its own ADR.
