### AC1: `/health` Endpoint — Response Contract + Probe Compatibility

**Scenario**
```gherkin
GIVEN the api-gateway binary built from apps/api-gateway/cmd/server (current main.go scaffold from Story 2.6) and started on the default port :8080 with all required env vars (HE_API_JWT_PUBLIC_KEY_PATH, HE_API_AUTH_SVC_URL, HE_API_NOTIFICATION_SVC_URL) wired to valid endpoints
WHEN any client (kubelet probe, ALB health check, curl, or test harness) sends GET /health (or GET /healthz, the alias kept for the existing infra/helm/api-gateway/values.yaml probe paths)
THEN
  - the server responds 200 OK
  - the response Content-Type is application/json; charset=utf-8
  - the response body is exactly the deterministic JSON document {"status":"ok","service":"api-gateway","version":"0.0.1"} (compact, no trailing newline), with `version` sourced from the `serviceVersion` const already defined in main.go
  - the response carries a `Cache-Control: no-store` header so kubelet / ALB never reuse a stale probe response
  - the response does NOT carry the SecurityHeaders middleware's full CSP / HSTS bundle (probes are intra-cluster; CSP on a non-HTML JSON probe is meaningless and wastes bytes) — the `/health` route is registered on a sibling mux mounted BEFORE the SecurityHeaders + CSRF chain
  - the response Set-Cookie header is absent (probes must be stateless)
  - the route accepts GET only; HEAD returns 200 with empty body (per RFC 9110 §9.3.2); any other method returns 405 Method Not Allowed with body {"error":"method_not_allowed"} (no he_request_id needed — probe path is outside the request-id middleware per BR-1.4 below; full he_request_id taxonomy lands in Story 3.6)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | The handler MUST be a pure function with NO dependencies on `auth-svc` / `notification-svc` upstream availability, NO Redis reachability check, NO DB reachability check — health probes verify the **gateway process itself is alive**, not the full topology. Deep-health (with upstream readiness) is a future Story (placeholder: 9.x in Epic 9 - 可观测). |
| BR-1.2 | The handler MUST be registered on `mux.HandleFunc("GET /health", health.Serve)` (Go 1.22 method-aware ServeMux) plus a literal sibling `mux.HandleFunc("GET /healthz", health.Serve)` — both paths invoke the same handler so the existing `infra/helm/api-gateway/values.yaml` (which references `/healthz` on lines 44 & 50) is not broken; new probes / docs prefer `/health`. |
| BR-1.3 | The handler MUST be mounted on a **separate** `http.ServeMux` (call it `probeMux`) wrapped by `obs.WrapHTTPHandler` ONLY (for OTel span emission), NOT by `SecurityHeaders` / `CSRF`. The main `mux` (with the full middleware chain) is mounted at all other paths. The two muxes are dispatched by a top-level `http.HandlerFunc` that routes `/health` and `/healthz` to `probeMux` and everything else to the wrapped main mux. |
| BR-1.4 | The handler MUST emit an OTel span named `http.health` with attributes `{http.method, http.route, http.status_code}` (so the probe traffic is visible in Grafana Tempo + Prom rate metrics), but MUST NOT enter the (future) request-id middleware (Story 3.6) — `he_request_id` is for billable requests, not probes. |
| BR-1.5 | The response body MUST be **byte-identical** across invocations (no timestamp, no PID, no hostname) so a downstream CI golden-file diff is feasible. The `version` field is read from the `serviceVersion` const at compile time, not at request time. |
| BR-1.6 | The handler MUST execute in ≤ 1 ms of wall-clock time on the CI baseline (2 vCPU / 2 GiB), measured at the inner handler level (excluding TCP accept + TLS handshake). Validated by `BenchmarkHealthHandler` (see Dev Notes). |
| BR-1.7 | The handler file MUST live at `apps/api-gateway/internal/handlers/health.go` (consistent with the existing `internal/handlers/` layout from Stories 2.2-2.6 — `me.go`, `jwks.go`, etc.) and export a `HealthHandler` struct + `NewHealthHandler() *HealthHandler` constructor (DI-friendly for future deep-health). |
| BR-1.8 | The `serviceVersion` const in main.go (currently `"0.0.1"`) is the authoritative source — the handler MUST NOT hardcode a separate version literal. If a future Story bumps the version, the probe response reflects it automatically. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `Method` (request) | string | yes | ∈ {GET, HEAD} | 405 → {"error":"method_not_allowed"} |
| `Path` (request) | string | yes | ∈ {/health, /healthz} | 404 (handled by mux, default behaviour) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Non-GET/HEAD method | 405 | `{"error":"method_not_allowed"}` | Set `Allow: GET, HEAD` header per RFC 9110 §10.2.1 |
| Path not /health or /healthz | 404 | (mux default) | Not handled by HealthHandler |

**Examples**
- Input: `GET /health HTTP/1.1` → 200 OK, `{"status":"ok","service":"api-gateway","version":"0.0.1"}`
- Input: `GET /healthz HTTP/1.1` (legacy Helm probe path) → 200 OK, **identical** body
- Input: `HEAD /health HTTP/1.1` → 200 OK, empty body, Content-Length: 0
- Input: `POST /health HTTP/1.1` → 405 Method Not Allowed, `{"error":"method_not_allowed"}`, `Allow: GET, HEAD`

### AC2: Cold-Start ≤ 1000 ms (P95 over 5 runs, CI baseline)

**Scenario**
```gherkin
GIVEN a freshly-built api-gateway binary (output of `CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o gateway ./cmd/server`) and the CI baseline runner (GitHub Actions ubuntu-22.04, 2 vCPU / 2 GiB — see Story 1.2 ci.yml)
WHEN the cold-start benchmark `apps/api-gateway/cmd/server/coldstart_bench_test.go` is invoked via `go test -run=^TestColdStart$ -count=5 ./apps/api-gateway/cmd/server` (5 runs to compute P95)
THEN
  - the benchmark spawns the binary as a child process via `exec.Command` with a temporary RSA public-key file (test fixture, 2048-bit, generated in TestMain) wired through HE_API_JWT_PUBLIC_KEY_PATH
  - HE_API_AUTH_SVC_URL and HE_API_NOTIFICATION_SVC_URL are pointed at a stubbed http.Server (test harness) that accepts the TCP connection but returns 503 — the gateway's connectrpc clients only dial lazily on first /v1/* request, so 503 is fine for /health
  - the benchmark polls GET http://127.0.0.1:8080/health with 5 ms intervals starting at t=0 (immediately after exec.Start returns)
  - the FIRST 200 OK response is recorded at t=t_first_ok
  - the metric `cold_start_ms = (t_first_ok - exec_start_time).Milliseconds()` is asserted ≤ 1000
  - across 5 independent runs (process restarted each run), the P95 of `cold_start_ms` MUST be ≤ 1000 (fail the test otherwise)
  - the test outputs all 5 measurements + min / P50 / P95 / max to t.Log so regression PRs are visually obvious
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | "Cold start" is measured **gateway-process-only** — does NOT include `go build` time, does NOT include K8s pod scheduling, does NOT include image pull. The number isolates the binary's own boot path (config parse + RSA key parse + OTel TracerProvider init + connectrpc client construction + mux registration + ListenAndServe). |
| BR-2.2 | Threshold = **1000 ms P95** over 5 runs (per Epic 3 AC). If a future Story adds expensive boot-time work (e.g., warming a 100 MB embedding cache), it MUST land alongside a budget renegotiation or be deferred to async post-listen. |
| BR-2.3 | The benchmark MUST run on every PR via the existing `go-test` CI job (Story 1.2) — no new CI workflow needed; existing matrix entry `apps/api-gateway` picks it up automatically. Add a job step `go test -run=^TestColdStart$ -count=5 ./apps/api-gateway/cmd/server -timeout=30s` ONLY if the default `go test ./...` doesn't include it (it does, since the file is in the same package). |
| BR-2.4 | The benchmark MUST NOT depend on a real Redis / PostgreSQL / Kafka instance — those are out of /health's scope per AC1 BR-1.1. The stubbed auth-svc / notification-svc upstreams cover the connectrpc client construction path. |
| BR-2.5 | The TracerProvider init in main.go currently dials the OTLP collector (`go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc`); if that dial is synchronous and adds > 100 ms to cold-start, refactor to a no-op exporter when `HE_API_OTEL_DISABLED=1` is set (test harness sets this env). Decision rationale + impact MUST be documented in the Architect review if changed. |
| BR-2.6 | Compile flags MUST match production: `CGO_ENABLED=0`, `-trimpath`, `-ldflags="-s -w"` — same as `apps/api-gateway/Dockerfile`. Building with default flags (CGO=1, dev mode) skews cold-start by 30-50 ms and would invalidate the gate. |
| BR-2.7 | If the benchmark fails on a particular runner due to noisy neighbours, the failure threshold is **P95**, not max — so 1 of 5 runs being > 1000 ms still passes if the 95th-percentile is below the bound. (5 runs is the minimum statistically meaningful sample; expanding to 10 / 20 is a future-story optimisation.) |
| BR-2.8 | A `BenchmarkColdStart` (Go benchstat-friendly) variant MUST also exist in the same file — Dev can run `go test -bench=. -benchmem -count=10 ./apps/api-gateway/cmd/server` locally for tuning. The CI gate uses the `TestColdStart` (P95 assertion) path; the `BenchmarkColdStart` is informational. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `runs` (test internal const) | int | yes | ≥ 5 (BR-2.7) | n/a (compile-time) |
| `threshold_ms` (test internal const) | int | yes | = 1000 (BR-2.2) | `t.Fatalf("cold-start P95 = %dms, exceeds budget = %dms", p95, threshold)` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Child process exits non-zero before first 200 | n/a | `t.Fatalf("api-gateway exited %d before /health was ready; stderr=%q", code, stderr)` | benchmark fails |
| /health never returns 200 within 5 s (process running but stuck) | n/a | `t.Fatalf("/health did not respond 200 within 5s; final status=%d", lastStatus)` | benchmark fails |
| P95 > 1000 ms across 5 runs | n/a | `t.Fatalf("cold-start P95 = %dms, exceeds budget = %dms; runs=%v", p95, threshold, runs)` | benchmark fails |

**Examples**
- Input: 5 runs measuring [420, 480, 510, 520, 580] ms → P95 ≈ 568 ms (linear interpolation) → PASS
- Input: 5 runs measuring [420, 480, 510, 520, 1200] ms → P95 ≈ 1064 ms → FAIL (regression PR blocked)
