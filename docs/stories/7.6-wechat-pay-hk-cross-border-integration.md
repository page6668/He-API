### AC2: 支付确认入账 — TRANSACTION.SUCCESS callback (verify + decrypt) → exactly-once balance credit (USD pass-through / HKD,CNY→USD at fx) (充值到账)

**Scenario**
```gherkin
GIVEN
  - a PENDING recharge_orders row for user U {payment_provider:'wechat', out_trade_no=<our order id>, amount:50.0000 (USD) or 390.0000 (HKD), currency:'USD'|'HKD'|'CNY', status:'pending'} (from AC1)
  - the user has paid in their WeChat app (scanned the code_url QR); WeChat will POST a signed+encrypted callback to POST /v1/billing/webhooks/wechat
  - the inherited exactly-once credit machinery (recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id) + the provider-agnostic billing-svc credit applier incl. its paid-currency guard:194-204 + toUSD branch) is REUSED unchanged
WHEN
  - WeChat POSTs a signed+encrypted callback (event_type TRANSACTION.SUCCESS / REFUND.* ; decrypted trade_state SUCCESS | NOTPAY/USERPAYING | CLOSED/PAYERROR) to POST /v1/billing/webhooks/wechat
THEN
  - **TRANSACTION.SUCCESS + trade_state=SUCCESS (→ CREDIT)**: wechat.VerifyWebhook (AC3) verifies the RSA signature AND AES-256-GCM-decrypts the `resource` → returns a VerifiedEvent {Kind:EventRechargePaid, OrderID:<our id from out_trade_no>, ExternalOrderID:<WeChat transaction_id>, SettledAmount:"50.00" (or "390.00"/"350.00" — minor-unit→decimal, the WeChat-settled TRUTH), Currency:'USD'|'HKD'|'CNY', Status:'paid'}; the webhook handler emits the SAME he.payment.v1 payment.completed PaymentEvent (UNCHANGED producer); billing-svc's provider-agnostic credit applier consumes it and, in ONE PG transaction: (1) `UPDATE recharge_orders SET status='paid', paid_at=NOW() WHERE id=$order AND status='pending'` → zero rows (redelivery) ⇒ skip; (2) else verify settled==intent in the PAID currency (BR-C-3, credit.go:194-204), convert settled toUSD (USD pass-through, or HKD/CNY÷rate HALF-UP), then `UPDATE balances SET current_usd = current_usd + creditUSD, updated_at=NOW() WHERE user_id=U` (UPSERT zero row if absent); (3) COMMIT
  - **post-commit (best-effort, INHERITED)**: INCRBYFLOAT balance:user:U:realtime by creditUSD; a Redis failure logs + alerts but the durable PG credit stands
  - **trade_state=NOTPAY/USERPAYING (in-progress → NO CREDIT)**: VerifyWebhook returns Kind:EventUnhandled; the handler 200-ACKs (`{code:SUCCESS}`); NO balance change; recharge_orders stays 'pending'
  - **trade_state=CLOSED/PAYERROR/REVOKED (fail → NO CREDIT)**: Kind:EventRechargeFailed → recharge_orders.status='failed'; NO credit; 200 ACK
  - **REFUND.\* event (→ NO-OP)**: Kind:EventUnhandled; 200 ACK; no money action (Q-REFUND deferred)
  - **settled<intent (partial / mismatch → PARK)**: the inherited amount-integrity guard (settled≠intent in the paid currency → stay pending + alert + NO credit, BR-R-1) parks it; 200 ACK
  - **observable**: GET /v1/balance reflects the credit after SUCCESS (reads PG authoritative); for an HKD/CNY recharge the credited current_usd is the fx-converted value; Prometheus he_payment_credit_amount_usd{provider="wechat"} histogram; slog payment_credit{order_id, user_id, provider:"wechat", settled_amount, settled_currency, settled_usd}
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-C-1 | **Credit fires ONLY on event_type=TRANSACTION.SUCCESS AND resource.trade_state=SUCCESS** (WeChat finality). NOTPAY/USERPAYING (in-progress) NEVER credits — crediting a non-terminal result risks crediting a payment that never completes (Q-CONFIRM). CLOSED/PAYERROR/REVOKED → status='failed', no credit. REFUND.* → 200 no-op (Q-REFUND). |
| BR-C-2 | **Exactly-once credit is INHERITED** (the 7.3 recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id)). A redelivered SUCCESS finds status='paid' → zero-row UPDATE → no second credit. The UNIQUE key is per-provider so a WeChat transaction_id never collides with a stripe/paypal/coinbase/alipay id. Binding is by out_trade_no=<our order id> from the DECRYPTED resource. |
| BR-C-3 | **The credited amount is the provider-confirmed WeChat-settled value** (BR-R-1 cascade), minor-unit→string-decimal (Q-AMOUNT-UNITS), NEVER the create-order intent. The amount-integrity guard compares settled-vs-intent in the **PAID currency** (credit.go:194-204, the 7.5 fix) BEFORE the toUSD conversion — so fx-rate drift between create and settle does NOT falsely trip the park. A genuine settled≠intent → park + alert + NO credit. |
| BR-C-4 | **HKD/CNY→USD fx-at-credit (HKD-first exercise, INHERITED-AND-PROVEN code)**: an HKD settlement credits balances.current_usd at the latest 7.2 fx_rate at settlement via the EXISTING credit.go toUSD() branch (USD = settled / HKD-per-USD rate, DivRound HALF-UP moneyScale=4 — fxRateSQL:103-104). CNY reuses the 7.5-driven branch. A USD settlement is the toUSD() pass-through. current_rmb stays reserved/0 (7.2 Q-SOT). The credit applier is UNCHANGED — 7.6 only drives the HKD pair (a missing HKD rate → park, Q-HKD-FX). |
| BR-C-5 | **The credit applier + producer + consumer are REUSED VERBATIM** — wechat emits the SAME PaymentEvent; no wechat-specific code exists downstream of VerifyWebhook. ⚠️ Unlike 7.5 (which justifiably fixed the guard), 7.6 needs ZERO credit.go change — the paid-currency guard is already correct. Any wechat special-casing leaking into credit.go is a design regression (BR-A-1 cascade). |
| BR-C-6 | **USD single SoT** (7.2 Q-SOT, INHERITED): the credit ALWAYS lands in balances.current_usd; there is no second accounting wallet (no current_hkd). The 7.1 reconciliation invariant (debits + credits ↔ balance) is extended additively. |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| TRANSACTION.SUCCESS, signature valid, decrypt ok, pending order, settled==intent | pending→paid + credit (toUSD, one tx); 200 `{code:SUCCESS}` |
| SUCCESS redelivered (already paid) | zero-row UPDATE → no second credit; 200 ACK (BR-C-2) |
| trade_state=NOTPAY/USERPAYING | 200 ACK; NO credit; order stays pending (BR-C-1) |
| trade_state=CLOSED/PAYERROR/REVOKED | recharge_orders.status='failed'; NO credit; 200 ACK |
| REFUND.* event | 200 ACK; no-op (Q-REFUND deferred) |
| SUCCESS but settled<intent (paid currency) | park + alert; NO credit; 200 ACK (BR-C-3) |
| verified+decrypted but PG down on apply | 5xx / `{code:FAIL}`; do NOT ACK-success; WeChat redelivers (inherited at-least-once + idempotent) |
| minor-unit parse / scale failure | fail-closed: park + alert, NO credit (never a mis-scaled credit, Q-AMOUNT-UNITS) |
| HKD settle but no HKD fx_rate row | park (fail-closed; no credit at unknown rate, Q-HKD-FX); alert |

### AC3: WeChat Pay webhook 安全 — APIv3 asymmetric signature verify + AES-256-GCM resource decrypt + inherited exactly-once backbone (安全)

**Scenario**
```gherkin
GIVEN
  - POST /v1/billing/webhooks/wechat is mounted OUTSIDE the bearer/CSRF chain (4.7 /public/* precedent, REUSED) — the WeChat signature is the sole credential
  - WECHAT_PAY_PLATFORM_PUBLIC_KEY (+ _PLATFORM_CERT_SERIAL, verify) + WECHAT_PAY_MERCHANT_PRIVATE_KEY (sign outbound) + WECHAT_PAY_APIV3_KEY (decrypt resource) are configured (Q-SIG/Q-ENCRYPT); raw-body + ALL headers are preserved end-to-end (the gateway forwards the EXACT bytes + Wechatpay-Signature/Timestamp/Nonce/Serial, REUSED billing_webhook.go:70-76 pass-through)
  - the recharge_orders state-machine + UNIQUE fence carry the inherited idempotency (AC2 BR-C-2)
WHEN
  - a callback POST arrives (genuine, forged, replayed, stale, tampered-ciphertext, or wrong-key)
THEN
  - **genuine (valid signature + intact ciphertext)**: wechat.VerifyWebhook (1) selects the platform public key by `Wechatpay-Serial`, reconstructs `<Wechatpay-Timestamp>\n<Wechatpay-Nonce>\n<rawBody>\n`, base64-decodes `Wechatpay-Signature`, and verifies with `rsa.VerifyPKCS1v15(platformPublicKey, crypto.SHA256, sha256(signedString), sig)` → match AND Wechatpay-Timestamp within the freshness window → (2) AES-256-GCM-decrypts the `resource` with the APIv3Key (nonce + associated_data + ciphertext incl. tag) → (3) parse the plaintext transaction → map trade_state → VerifiedEvent Kind (AC2) → process; return 200 `{code:SUCCESS}` promptly
  - **forged (invalid/absent/tampered signature, wrong key, or UNKNOWN Wechatpay-Serial)**: VerifyWebhook returns provider.ErrSignatureInvalid → the handler maps it to `400_webhook_signature_invalid` BEFORE any decrypt/parse; NO credit; slog payment_webhook_rejected{provider:"wechat", reason:"signature"} + metric; the body is NEVER decrypted or trusted
  - **tampered ciphertext / wrong APIv3Key (⚠️ NEW — encryption layer)**: even with a valid OUTER signature, an attacker-tampered `resource.ciphertext`/`nonce`/`associated_data` OR a wrong APIv3Key → AES-256-GCM auth-tag mismatch → decrypt error → fail-closed (reject, NO credit, NEVER parse a partial plaintext); the GCM tag is a SECOND integrity guard under the signature
  - **replayed (a captured VALID SUCCESS re-POSTed)**: (a) a STALE Wechatpay-Timestamp (outside the bounded skew) → reject (the freshness layer, on par with Stripe/7.5); (b) a within-window replay is neutralised by the inherited recharge_orders pending→paid state-machine (zero-row UPDATE → no second credit) — defence-in-depth, TWO layers
  - **exactly-once credit (INHERITED)**: credit applies ONLY on a pending→paid transition; already-paid ⇒ zero rows ⇒ 200 ACK + skip; status-flip + credit are ONE PG tx (atomic); UNIQUE(payment_provider, external_order_id) prevents two orders binding one WeChat transaction_id
  - **amount integrity (INHERITED)**: the credited amount is the provider-verified WeChat-settled value (minor-unit→decimal from the DECRYPTED resource); settled≠intent (paid currency) → park + alert + NO credit
  - **PCI / no-card**: the WeChat callback carries wallet payment ids + amounts — NEVER a card PAN (wallet channel, in-app authentication; SAQ-A boundary holds); we persist the WeChat transaction_id + our order id only
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-W-1 | **Signature verification is MANDATORY and happens BEFORE any decrypt/body processing** (INHERITED, BR-W-1 from 7.3/7.4/7.5). An unverified WeChat callback body is NEVER decrypted or parsed into a credit. The signature is the credential (the route is otherwise unauthenticated). Verify-THEN-decrypt-THEN-parse — a forged request never reaches the decrypt path (no decrypt oracle). |
| BR-W-2 | **WeChat APIv3 signature scheme** (ASYMMETRIC, RSA family de-risked by 7.5): verify `Wechatpay-Signature` (base64) with RSA-SHA256 (`rsa.VerifyPKCS1v15`, `crypto.SHA256`) against the WeChat PLATFORM public key SELECTED BY `Wechatpay-Serial`, over the reconstructed `<Wechatpay-Timestamp>\n<Wechatpay-Nonce>\n<rawBody>\n` string. ⚠️ ASYMMETRIC: we hold only WeChat's PUBLIC verify key. ⚠️ Signed string is timestamp+nonce+body ONLY (NO method/URI → NO `r.URL.Path` trap, SIMPLER than Alipay+). ⚠️ Unknown/mismatched Wechatpay-Serial → reject (do NOT skip verification). |
| BR-W-3 | **AES-256-GCM `resource` decrypt** (⭐ NEW PRIMITIVE, Q-ENCRYPT): after signature verify, decrypt `resource.ciphertext` (base64) with AES-256-GCM — key=WECHAT_PAY_APIV3_KEY (32B), nonce=resource.nonce (12B), additionalData=resource.associated_data; Go `gcm.Open` consumes the trailing 16B auth tag. The GCM auth tag is a SECOND integrity guard — any ciphertext/nonce/AAD tampering OR a wrong APIv3Key → tag mismatch → decrypt error → fail-closed (NO credit, NEVER parse a partial plaintext). A decrypt failure is treated like a verify failure (no money action). |
| BR-W-4 | **Raw-body + header integrity** (INHERITED + EXTENDED): both RSA verify AND the signed-string reconstruction need the EXACT raw bytes WeChat signed AND the exact Wechatpay-Timestamp/Nonce/Serial header values; no middleware (gateway proxy included) may re-serialize/normalize the body OR drop those headers. The gateway billing_webhook.go forwards ALL headers verbatim + the raw body byte-faithfully (billing_webhook.go:70-76, REUSED — verified sufficient, no proxy change). |
| BR-W-5 | **Replay defence = Wechatpay-Timestamp freshness + state-machine** (on par with 7.5/Stripe): a bounded-skew freshness check rejects stale callbacks; the inherited recharge_orders pending→paid idempotency neutralises any within-window replay. Two layers. P0 test lanes: stale-timestamp reject + replay-of-valid-success idempotency. |
| BR-W-6 | **Provider ACK discipline** (INHERITED, BR-W-5 from 7.3): verified + already-processed → 200 `{code:SUCCESS}` (so WeChat stops retrying); verification/decrypt FAILURE → 400 (`400_webhook_signature_invalid`); transient processing error (PG down) → 5xx / `{code:FAIL}` so WeChat redelivers (at-least-once + idempotent). |
| BR-W-7 | **Secrets** (Q-SIG/Q-ENCRYPT, ⚠️ TWO high-value): `WECHAT_PAY_MERCHANT_PRIVATE_KEY` (signs ALL our outbound calls — broad blast radius) + `WECHAT_PAY_APIV3_KEY` (the NEW symmetric AES-256 key — decrypts EVERY callback resource) are DISTINCT from `WECHAT_PAY_PLATFORM_PUBLIC_KEY`/`_PLATFORM_CERT_SERIAL` (verifies inbound; a public key) and `WECHAT_PAY_MCH_ID`/`_MERCHANT_CERT_SERIAL`; all env-injected; the PRIVATE key + the APIv3Key NEVER logged (the 7.3/7.4/7.5 secret discipline cascade). Wechatpay-Serial selects the verify cert (rotation). |
| BR-W-8 | **Minor-unit fail-closed** (Q-AMOUNT-UNITS): a minor-unit→decimal parse/scale failure on a verified+decrypted callback → park + alert + NO credit; NEVER a silently mis-scaled (100×) credit. HKD joins the per-currency minor-unit table (2 digits). |
| BR-W-9 | **No card data / wallet no-PAN** (§8.4): the payload carries WeChat transaction ids + wallet amounts only — never a PAN; we persist the transaction_id + order id. The SAQ-A in-app-authentication boundary holds (the user authenticates in their WeChat app via the QR). |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Invalid / absent / tampered `Wechatpay-Signature`, wrong or UNKNOWN serial key | 400 | `400_webhook_signature_invalid` — "Webhook signature verification failed." | reject before decrypt/parse (BR-W-1); slog + metric (REUSED code) |
| Altered Wechatpay-Timestamp / Nonce / body (signed-string component) | 400 | `400_webhook_signature_invalid` | RSA verify fails (fail-closed, BR-W-2/W-4) |
| Stale Wechatpay-Timestamp (outside skew window) | 400 | `400_webhook_signature_invalid` | reject (freshness layer, BR-W-5) |
| Valid signature but tampered ciphertext / wrong APIv3Key (GCM tag mismatch) | 400 | `400_webhook_signature_invalid` | decrypt fails → fail-closed; NEVER parse partial plaintext (BR-W-3) |
| Verified+decrypted but already-processed (redelivery / within-window replay) | 200 | `{code:SUCCESS}` | ACK + skip; no second credit (BR-W-5/W-6) |
| Verified+decrypted but PG down on apply | 5xx | `{code:FAIL}` | do NOT ACK-success; WeChat redelivers (BR-W-6) |
| Verified trade_state=NOTPAY/USERPAYING (in-progress) | 200 | `{code:SUCCESS}` | ACK; no-op, no credit (AC2 BR-C-1) |
| Verified but settled ≠ order intent (paid currency) | 200 | `{code:SUCCESS}` | ACK (verified) but park + alert + NO credit (BR-C-3) |
| Verified but minor-unit scale failure | 200 | `{code:SUCCESS}` | ACK (verified) but park + alert + NO credit (BR-W-8) |

**Examples**
- **Input**: forged POST with a bogus `Wechatpay-Signature` (or signed by a non-WeChat key, or an unknown serial) → `400_webhook_signature_invalid`; no decrypt attempted; no recharge_orders touched; no credit. ✅ forgery blocked (asymmetric — cannot forge without WeChat's platform private key).
- **Input**: a genuine signature but a tampered `resource.ciphertext` → outer verify passes, AES-GCM tag mismatch → decrypt fails → 400; NEVER parsed. ✅ encryption-layer integrity (BR-W-3).
- **Input**: a genuine callback but with a tampered Wechatpay-Timestamp header → reconstructed string differs → RSA verify fails → 400. ✅ signed-string integrity.
- **Input**: a captured valid SUCCESS replayed 1h later → Wechatpay-Timestamp now stale → rejected by the freshness window (layer 1). Even if within window → order already 'paid' → zero-row UPDATE → no credit (layer 2). ✅ replay neutralised (two layers, BR-W-5).
- **Input**: genuine TRANSACTION.SUCCESS for a pending order → verified + decrypted → pending→paid + credit (one tx). ✅ exactly-once.

### Technical Constraints
- **Additive-only on a proven seam** — implement `wechat.Provider` against the EXISTING `PaymentProvider` interface (`apps/payment-svc/internal/provider/provider.go:86-97`); wire it in `buildRegistry` (`cmd/server/main.go` ~207, alipay precedent); add `"wechat"` to `supportedProviders` + `providerCurrencies` (`apps/api-gateway/internal/handlers/billing_write.go:47,53`); mount the webhook route. Do NOT touch the producer, the credit applier (incl. its toUSD fx branch + the paid-currency guard:194-204), recharge_orders, the proto, or the Kafka topic. [→ provider.go:2-6 names 7.6; 0010_*.sql:42 reserves "wechat"]
- **AES-256-GCM `resource` decrypt** (⭐ the genuinely-new security primitive, Q-ENCRYPT) — WeChat APIv3 callbacks deliver the payment result ENCRYPTED: `resource:{algorithm:"AEAD_AES_256_GCM", ciphertext:<base64>, nonce:<12B>, associated_data:"transaction", original_type:"transaction"}`. Decrypt AFTER the signature verifies: `block,_ := aes.NewCipher(apiV3Key /*32B*/); gcm,_ := cipher.NewGCM(block); plain,err := gcm.Open(nil, []byte(nonce), base64decode(ciphertext), []byte(associated_data))`. The trailing 16B GCM auth tag is consumed by `gcm.Open` — any tampering OR a wrong key → `err != nil` → fail-closed (NO credit, NEVER parse partial plaintext). This is the FIRST encrypted webhook body on the platform (Stripe/Coinbase HMAC + Alipay+ RSA all signed PLAINTEXT). [→ AC3 BR-W-3]
- **WeChat APIv3 asymmetric signature scheme** (Q-SIG — SAME RSA family as 7.5, different shape) — verify `Wechatpay-Signature` (base64) with `rsa.VerifyPKCS1v15(platformPublicKey, crypto.SHA256, sha256(signedString), sig)` over `<Wechatpay-Timestamp>\n<Wechatpay-Nonce>\n<rawBody>\n` BEFORE decrypt (BR-W-1/W-2). ⚠️ Signed string is timestamp+nonce+body ONLY — NO method/URI → **NO `r.URL.Path` canonicalisation trap** (simpler than Alipay+'s constructed string; this is the one place 7.6 is EASIER than 7.5). Select the platform public key by `Wechatpay-Serial` (unknown serial → reject; Q-CERT-ROTATION). Wechatpay-Timestamp gives a freshness window → reject stale (BR-W-5). [→ AC3]
- **Outbound signing** — sign OUR WeChat calls (CreateCheckout) with `WECHAT_PAY_MERCHANT_PRIVATE_KEY` (RSA-SHA256) over `<METHOD>\n<URL>\n<timestamp>\n<nonce>\n<body>\n`, in an `Authorization: WECHATPAY2-SHA256-RSA2048 mchid="...",nonce_str="...",timestamp="...",serial_no="<merchant cert serial>",signature="<b64>"` header. ⚠️ This private key has a BROAD blast radius (it authenticates ALL our outbound calls) — never log it. [→ AC1 BR-A-7]
- **Credit on trade_state=SUCCESS ONLY** (Q-CONFIRM) — event_type=TRANSACTION.SUCCESS + resource.trade_state=SUCCESS → EventRechargePaid (credit); NOTPAY/USERPAYING → EventUnhandled (200 ACK, no credit); CLOSED/PAYERROR/REVOKED → EventRechargeFailed; REFUND.* → EventUnhandled (no-op); settled≠intent → park via the inherited guard. [→ AC2 BR-C-1]
- **Provider-confirmed amount, never intent** (BR-R-1 cascade, INHERITED) — SettledAmount in the VerifiedEvent is the WeChat-confirmed value (decrypted `amount.total` minor-unit→decimal); the billing-svc applier already parks settled≠intent. Do NOT credit the create-order intent. [→ AC2 BR-C-3]
- **Minor-unit amounts** (Q-AMOUNT-UNITS) — WeChat `amount.total` is an INTEGER in the currency's minor units (USD/HKD/CNY = 2 digits → "5000" = "50.00"). EXTEND the 7.5 per-currency minor-unit table with HKD (NOT a hardcoded /100) + fail-closed on scale loss → string-decimal end-to-end (shopspring/decimal). A mis-scale = a 100× credit defect (BR-W-8). [→ AC1/AC2]
- **Multi-currency USD/HKD/CNY + fx-at-credit** (Q-CURRENCY, HKD-first exercise) — wechat enables {USD, HKD, CNY}. An HKD/CNY settlement credits `balances.current_usd` at the latest 7.2 fx_rate at settlement via the EXISTING `credit.go` toUSD() branch (USD = settled / quote-per-USD rate, DivRound HALF-UP moneyScale=4 — fxRateSQL:103-104). USD settlement = pass-through. current_rmb stays reserved/0 (7.2 Q-SOT). ⚠️ The amount-integrity guard compares settled-vs-intent in the PAID currency BEFORE conversion (credit.go:194-204 — the 7.5 fix, INHERITED). The credit applier is UNCHANGED — 7.6 only drives the HKD pair. ⚠️ Needs an HKD fx_rate row (Q-HKD-FX, T0.3). [→ AC2 BR-C-3/C-4]

- **Money + amount fields are string-decimals** — never JSON numbers (Q-Spec-4 / 7.1 BR-A-3). [→ docs/architecture/data-models.md §4.5]
