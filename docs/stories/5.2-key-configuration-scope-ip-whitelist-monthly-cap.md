The trusted-proxy CIDR list MUST be sourced from a **NEW Kubernetes ConfigMap** `api-gateway-trusted-proxies` mounted on the api-gateway pod (precedent: Story-4.5 `doubao-endpoint-ids` ConfigMap), declaring two env vars: `CLOUDFLARE_CIDRS` and `INGRESS_CIDRS` (each a comma-separated CIDR list). The implementation uses `net/netip` stdlib to parse XFF as a list, walks from the rightmost (direct caller — k8s ingress) backwards, skipping any hop matching a CIDR from the union of `CLOUDFLARE_CIDRS` + `INGRESS_CIDRS`, and returns the first non-trusted public IP encountered. Empty XFF or all-trusted XFF → use `r.RemoteAddr`. If both env vars are unset (or empty), the walker degrades safely to `[]netip.Prefix{}` — XFF is effectively ignored and `r.RemoteAddr` always wins (failsafe-against-misconfig posture). - **Q-I — `users.status` gating on PATCH**: SM defaults to **reject PATCH with 403 `403_account_pending_deletion`** for `users.status='pending_deletion'` (parity with Story-5.1 Q9 ruling — a user winding down their account should NOT be widening attack surface). Architect may rule to ALLOW (a user defensively narrowing their whitelist while pending-deletion is reasonable) — SM counter-argument: revoking is the better defensive primitive (Story 5.1) and is permitted from pending_deletion.

- **Q-J — `monthly_cost_cap_usd` value validation**: SM defaults to **[0.01, 999999.99] USD inclusive, OR NULL** (preserves Story-5.1 NULL semantics for "no cap"). The lower bound 0.01 avoids accidental 0-cap that would deny all calls; the upper bound respects the `NUMERIC(10,2)` PG column. Money is sent as a JSON string per BR-2.10 / Architect Q-Spec-4 ratified in Story 5.1; reject JSON-number on first-principles (precision-loss). - **Q-K — `api_keys.updated_at` column add?**: The Story-3.2 `0006_create_api_keys.sql` schema does NOT include an `updated_at` column (only `created_at`). ### AC1: Configure API Key — `PATCH /v1/me/keys/{api_key_id}` mutates scope.models / scope.ip_whitelist / monthly_cost_cap_usd; partial-update semantics; cache-invalidation on commit

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access JWT cookie valid per Story 2.2 BR-3.7; `aal>=1` per Q-I-related Story-5.1 Q7 cascade)
  - `users.status = 'active'` (NOT pending_deletion per Q-I SM default)

    - Checks revoke sentinel (Story 5.1 path) — ABSENT → cache entry valid.
    - Checks config-updated sentinel (Story 5.2 new path per BR-1.9) — ABSENT → cache value is current.
    - Passes resolved key + identity to the request context.
  - NEW `keypolicy.go` middleware (runs AFTER bearer_auth, BEFORE chat-completions handler):
    - Computes `client_ip` via the trusted-proxy walker (Q-E ratified).
    - Calls `keypolicy.CheckIPWhitelist(clientIP netip.Addr, whitelist []string) bool`:
      - If `whitelist` is empty → return `true` (allow).
      - Otherwise: for each entry, parse as CIDR (`net/netip.ParsePrefix`) OR addr (`net/netip.ParseAddr`); test `prefix.Contains(clientIP)` OR `addr == clientIP`.

```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | Empty `scope.ip_whitelist` means "any IP allowed" — preserves Story-5.1 INSERT default of `scope='{}'::jsonb` (no `ip_whitelist` key → effectively empty). |
| BR-2.2 | `client_ip` discovery uses the Q-E trusted-proxy walker — XFF parsed only across trusted hops sourced at server-startup from the NEW `api-gateway-trusted-proxies` ConfigMap env vars `CLOUDFLARE_CIDRS` + `INGRESS_CIDRS` per T0.7 (Architect Round 1 Q-E PARTIAL-APPROVE 2026-05-25). | BR-2.3 | CIDR matching uses `netip.Prefix.Contains` — IPv4 prefixes match IPv4 addrs only; IPv6 prefixes match IPv6 addrs only. Mixed-family no-match (no v4-in-v6 mapping ambiguity). |
| BR-2.4 | Loopback (`127.0.0.0/8`, `::1/128`) in the whitelist matches loopback client_ip — supports local-dev. |
| BR-2.5 | The check runs AFTER bearer_auth resolves successfully — a request with invalid bearer NEVER reaches this check (returns 401 first via Story-3.2 path). |
| BR-2.6 | The check runs BEFORE the chat-completions handler — short-circuit on deny means upstream models are NEVER called (zero cost on denied requests). |
| BR-2.7 | slog audit event on every denial; Prometheus counter on every denial — for SLO dashboards + security alerting. |
| BR-2.8 | Anti-enumeration parity: the response envelope is byte-identical regardless of whitelist size (1 entry vs 100 entries) — attackers cannot infer whitelist contents from response timing or body. |
| BR-2.9 | Failed XFF parsing (malformed header, untrusted proxy chain) → fall back to `r.RemoteAddr`. NEVER throw 500 — XFF is best-effort. |

| Field | Type | Required | Rules | Error Message |

| Scenario | Code | Message | Action |

| Whitelist empty | (200) | (no error) | Pass through. |

**UI Interaction** — N/A for AC2 (server-side enforcement; Story 5.5 owns the UI surfacing of "this IP was blocked").

### AC4: Enforce Monthly cap — gateway returns 402 `402_quota_exhausted` when `current_month_cost_usd >= monthly_cost_cap_usd` (and cap is non-NULL)

**Scenario**
```gherkin
GIVEN
  - Valid bearer token (Story-3.2 bearer auth resolves)
  - The key's `monthly_cost_cap_usd` is non-NULL (e.g., `"50.00"`)
  - The bearer cache entry has the extended shape per Q-A (includes `monthly_cost_cap_usd`)
  - The realtime monthly cost counter `usage:apikey:{api_key_id}:month_cost_usd` exists in Redis (Q-D Redis SoT)
WHEN
  - A request arrives at the gateway and the realtime counter reads `"50.01"` (just-exceeded the cap)
THEN
  - `keypolicy.go` middleware (runs after AC2 + AC3 in the same chain position):
    - `GET usage:apikey:{api_key_id}:month_cost_usd` → `"50.01"` (string-decimal — Redis stores via `INCRBYFLOAT` which uses scientific notation; gateway parses via `decimal.NewFromString` or `pgtype.Numeric` shim).
    - Calls `keypolicy.CheckMonthlyCap(current_usd, cap_usd decimal.Decimal) bool`:
      - If `cap` is NULL/zero-Decimal → return `true` (allow — no cap).
      - Otherwise: return `current.LessThan(cap)`.
    - Returns `false`:
      - Increments `apikey_policy_denial_total{check="monthly_cap", code="402_quota_exhausted"}`.
      - Emits slog `event=apikey_monthly_cap_denied` with attrs `api_key_id`, `user_id`, `current_cost_usd`, `cap_usd`.
      - Writes envelope `openaierr.Write(w, ctx, 402, "402_quota_exhausted", "API key monthly cost cap exhausted", nil)`.
      - SHORT-CIRCUITS — chat-completions handler NEVER runs.
  - On `GET` Redis error (5xx, timeout, connection refused) → fail-OPEN per Q-F SM default: log slog WARN `apikey_cap_check_redis_failed`, increment `apikey_cap_check_failures_total`, allow the request through.
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | NULL cap means "no cap" — preserves Story-5.1 INSERT default. |
| BR-4.2 | The realtime counter is Redis SoT (Q-D ratified) — `GET usage:apikey:{api_key_id}:month_cost_usd`. The PG column `current_month_cost_usd` is a periodic-sync destination only (Story 5.4 cron-reset target). |
| BR-4.3 | The cap is checked BEFORE the upstream model dispatch — no cost is incurred on denied requests. |
| BR-4.4 | The counter MAY not exist (key missing — first request of month OR billing-svc not yet deployed); MISSING → treat as `decimal.Zero` → always less-than-cap → allow. |
| BR-4.5 | Comparison precision: NUMERIC(10,2) for the cap is hard-bounded to 2 decimal places; the counter (`INCRBYFLOAT` writes float64) may have more precision — use `decimal.Decimal.LessThan` which compares exact values. |
| BR-4.6 | Redis-counter read failure: fail-OPEN per Q-F SM default (log WARN; allow through). Architect may ratify fail-closed in Round 1. |
| BR-4.7 | Story 5.4 will introduce the cron-reset + email predicate when the counter approaches the cap (e.g., 80% / 95% / 100% thresholds). Story 5.2 ONLY implements the 100% deny gate. |
| BR-4.8 | slog audit + Prometheus counter on every denial (parity with AC2/AC3). |
| BR-4.9 | Anti-enumeration parity (parity with AC2/AC3) — envelope is byte-identical regardless of how close-to-cap the counter is. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `current_month_cost_usd` (Redis) | string \| missing | no | decimal-parseable; missing → 0 | (fail-open on parse error per BR-4.6) |
| `monthly_cost_cap_usd` (cache) | string \| null | no | decimal-parseable | (fail-open on parse error) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| current >= cap | 402 | `"402_quota_exhausted"` | Short-circuit; deny. |
| cap NULL | (200) | (no error) | Pass through. |
| counter missing | (200) | (no error) | Treat as 0 (BR-4.4). |
| Redis GET fails | (200) | (log WARN) | Fail-open per BR-4.6 + Q-F. |

**Examples**
- Cap `"50.00"`, counter `"25.00"` → 200 (pass)
- Cap `"50.00"`, counter `"50.00"` → 402 (equal-to-cap → deny per BR-4.2)
- Cap `"50.00"`, counter `"50.01"` → 402
- Cap `null`, counter ANY → 200 (BR-4.1)
- Cap `"50.00"`, counter missing → 200 (BR-4.4)
- Cap `"50.00"`, GET fails → 200 + WARN (BR-4.6)

### Database Design

> **No DDL change in Story 5.2 default scope** (per `cumulative_context_impact.db_schema=false`). This section documents the UPDATE semantics on the existing `he_api.api_keys` table.

- **UPDATE (AC1)**: `UPDATE he_api.api_keys SET scope=$X, monthly_cost_cap_usd=$Y WHERE id=$1 AND user_id=$2 AND revoked_at IS NULL RETURNING (full row)`.
  - Trailing WHERE clause re-asserts revoke-state to defeat TOCTOU between the SELECT-FOR-UPDATE and the UPDATE.
  - Returns the full row so the response shape matches Story-5.1 ApiKeyEntry without a re-SELECT.

- **SELECT (AC1 - within transaction)**: `SELECT id, user_id, name, key_prefix, scope, monthly_cost_cap_usd, current_month_cost_usd, last_used_at, revoked_at, created_at FROM he_api.api_keys WHERE id=$1 AND user_id=$2 AND revoked_at IS NULL FOR UPDATE`.
  - Explicit row lock; serialises concurrent UPDATEs on the same id (last-writer-wins per Q-G ratification).

- **READ (AC2/AC3/AC4 - enforcement gates)**: The gateway does NOT issue a PG read for the policy checks — it reads from the Story-3.2 Redis cache (extended shape per Q-A). PG round-trip on every bearer request would VIOLATE the latency budget.

- **Concurrency**: `WHERE id=$1 FOR UPDATE` is fine-grained — does not contend with other users' rows. Concurrent UPDATEs of the same key serialise via the row lock; last-writer-wins per Q-G.

- **Schema reference** [→ docs/architecture/data-models.md#41-postgresql-schema-核心表]: unchanged from Story 5.1 — see the full schema there. Story 5.2 mutates `scope` (JSONB) and `monthly_cost_cap_usd` (NUMERIC(10,2)) only.

- **`updated_at` column — RATIFIED: NOT ADDED** [Architect Q-K Round 1 ruling 2026-05-25]: The `api_keys` schema carries `created_at` only — no `updated_at` column exists or is added in this Story. The Story does NOT write `updated_at` in any UPDATE statement. The canonical "last-modified" SoT is the Kafka `audit.event` (`api_key.config_updated`) event `ts` field — audit-svc consumes this topic and downstream compliance tooling can derive the per-key modification history with full PII safety. If a future Story makes a queryable `updated_at` a hard UI requirement (e.g., the P-5 Edit Modal needs to render "Last modified" without an audit-svc round-trip), it can land an ALTER TABLE migration `0007_api_keys_updated_at.sql` (`ADD COLUMN updated_at TIMESTAMPTZ DEFAULT NOW() NOT NULL` + backfill from `created_at`) — but Story 5.2 explicitly defers this. Architect Round 1 Q-K APPROVE'd this position; Architect Critical C1 mandated removal of every `updated_at=NOW()` reference that had crept into the SM draft.

  repeated string models = 1;        // optional; absent vs empty slice distinguishable via field presence
  repeated string ip_whitelist = 2;  // ditto
  bool models_present = 3;           // EXPLICIT field-presence flag (proto3 native quirk — repeated fields can't distinguish absent from empty)
  bool ip_whitelist_present = 4;     // ditto
