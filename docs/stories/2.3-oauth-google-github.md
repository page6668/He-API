architect_round_1_pending_questions:
  Q1:
    title: "PKCE + state 存储位置：Redis vs Signed Cookie (HMAC) vs Hybrid"
    options:
      - "(a) Redis: `auth:oauth:state:{state_id}` → JSON{provider, pkce_verifier, return_to, ip_hash, ua_hash, created_at, expires_at}，TTL=600s (10min)；callback 时 GET + DEL (one-shot)；与 Story 2.2 Q2 ruling email_verify token 同模式；适合无状态 api-gateway / 多 pod 部署"
      - "(b) Signed cookie (HMAC-SHA256, 用 Story 2.2 落地的 JWT private key 或独立 oauth-state-hmac-key)：state 直接编码 {pkce_verifier, return_to, nonce, exp} 入 cookie；callback 时验签 + nonce check；无 Redis 依赖；缺点：cookie 大小 (~500 bytes) + 撤销靠 nonce blocklist"
      - "(c) Hybrid: state_id 走 cookie + 实际 verifier+return_to 走 Redis；防止 cookie 体积膨胀但保留 Redis one-shot DEL 语义"
    sm_proposal: "(a) — 与 Story 2.2 Q2 Architect ruling 'Redis auth:email_verify:{sha256(token)}' 同模式；data-models.md §4.3 已注册 Redis key 命名空间习惯；one-shot DEL 实现天然 single-use 防 replay；signed cookie (b) 引入新 HMAC 密钥管理面（增加 Vault migration 路径压力）；hybrid (c) 复杂度高无明显收益。`pkce_verifier` 入 Redis 而非 cookie，避免任何 client 端泄露面（即便 cookie HttpOnly+Secure）；`state_id` cookie 仅承载 random ID + signature，cookie size 控制在 < 256 bytes。Redis key 命名提案：`auth:oauth:state:{sha256(state_id)}` (与 §4.3 既有 `auth:apikey:{key_hash}` 同 hashed-key 模式)"
    impact: "决定 auth-svc 是否引入独立 HMAC 密钥管理；决定 data-models.md §4.3 Redis key 注册新增 `auth:oauth:state:*` 条目（Architect M-3 doc-drift follow-up）；决定 callback 路径的 RTT 成本 (Redis GET+DEL ≤ 1ms 远低于 cookie HMAC verify 但 cookie 无 RTT)；决定 state-exhaustion 防护策略（Redis 可走 SETNX with TTL；cookie 路径需独立 IP-rate-limit）"

## Acceptance Criteria

### AC1: Google OAuth 登录 — Authorization Code + PKCE + ID token 验证 + 自动创建/关联/直登

**Scenario**
```gherkin
GIVEN 用户访问 `/{locale}/(auth)/signin` 或 `/{locale}/(auth)/signup` 页（Story 2.1 落地，Story 2.2 扩展）
  AND 用户已勾选 cookie 同意（Story 2.1 落地的 cookie banner — 若 locale=ar 则 RTL 布局）
  AND `users` 表 schema 已就位（Story 2.2 落地：oauth_provider / oauth_subject / email_verified_at / password_hash NULLABLE / status / locked_until / totp_enabled）
  AND `idx_users_oauth` partial index 已就位（Story 2.2 落地：`WHERE oauth_provider IS NOT NULL`）
  AND `he-api-auth-jwt-keys` K8s Secret + JWKS 端点 `/.well-known/jwks.json` 已就位（Story 2.2 落地）
  AND `he-api-oauth-credentials` K8s Secret 已注入（本 Story T0.5 落地，per Q5 sm_proposal=a）
  AND auth-svc 启动时已加载 Google OIDC discovery 配置（`https://accounts.google.com/.well-known/openid-configuration`）并 cached JWKS

WHEN 用户点击 `<OAuthButtonGroup>` 中的 "Continue with Google" 按钮
  → console Server Action `initiateOAuth('google', returnTo)`
  → console BFF (per Story 2.2 Q1 ruling) → api-gateway `GET /v1/auth/oauth/google/initiate?return_to={returnTo}&locale={locale}`
  → auth-svc gRPC `BeginOAuth(provider='google', return_to, locale, client_ip, user_agent)`

THEN
  - auth-svc 生成 state_id (crypto/rand 32 bytes → base64url, ≥256-bit entropy) + pkce_verifier (43 random bytes → base64url, 符合 RFC 7636 §4.1 [43,128] 范围)
  - 计算 pkce_challenge = base64url(SHA-256(pkce_verifier))
  - validate return_to against allow-list (BR-1.5)；若 invalid 直接返回 400 不进入 Redis 写入
  - Redis SETEX `auth:oauth:state:{sha256(state_id)}` (per Q1 sm_proposal=a, with TTL=600s, JSON value {provider, pkce_verifier, return_to, ip_hash=sha256(client_ip), ua_hash=sha256(user_agent), locale, created_at})
  - 构造 Google Authorization URL: `https://accounts.google.com/o/oauth2/v2/auth?client_id={GOOGLE_CLIENT_ID}&redirect_uri={REDIRECT_URI_BASE}/v1/auth/oauth/google/callback&response_type=code&scope=openid+email+profile&state={state_id}&code_challenge={pkce_challenge}&code_challenge_method=S256&prompt=select_account&hl={locale_to_google_hl_mapping(locale)}`
  - api-gateway 在响应中设置 short-lived signed cookie `he_oauth_state` (Path=/v1/auth/oauth, Secure, HttpOnly, SameSite=Lax, Max-Age=600, value=state_id)（BR-1.3 — state cookie binding，防止跨标签替换）
  - 302 Location: {google_authorize_url}
  - audit 写入 Kafka `audit.event`：`{event: 'auth.oauth.initiate', provider: 'google', client_ip_hash, ua_hash, state_id_hash}` (BR-4.5)

  ---

  用户在 Google 同意页授权后，Google 302 重定向到 `{REDIRECT_URI_BASE}/v1/auth/oauth/google/callback?code={code}&state={state_id}`

  → api-gateway `GET /v1/auth/oauth/google/callback?code={code}&state={state_id}`
    a. 读取 `he_oauth_state` cookie；若 cookie 缺失或值 ≠ query state → 拒绝 (BR-1.3 CSRF state binding)
    b. validate cookie + query state 字符集 (base64url) 防注入；DELETE cookie (one-shot)
  → auth-svc gRPC `CompleteOAuth(provider='google', code, state_id, client_ip, user_agent)`

THEN
  - Redis GETDEL `auth:oauth:state:{sha256(state_id)}` (one-shot — 防 state replay per BR-1.4)
    a. 若 Redis 返回 nil → state 不存在或过期 → 返回 400 `400_oauth_state_invalid`
    b. 若 stored.provider != 'google' → 拒绝 (防 cross-provider state 混淆)
    c. 若 stored.ip_hash != sha256(client_ip) OR stored.ua_hash != sha256(user_agent) → 拒绝 + audit `auth.oauth.callback.error_binding` (BR-1.6 client binding)
  - 调用 Google Token endpoint POST `https://oauth2.googleapis.com/token` 体: `grant_type=authorization_code&code={code}&redirect_uri={REDIRECT_URI_BASE}/v1/auth/oauth/google/callback&client_id={GOOGLE_CLIENT_ID}&client_secret={GOOGLE_CLIENT_SECRET}&code_verifier={stored.pkce_verifier}`
    a. 若 Google 返回 4xx/5xx → 返回 502 `502_oauth_provider_error` + audit `auth.oauth.callback.error_provider`
  - 从 token response 提取 `id_token`，通过 coreos/go-oidc/v3 验证：(1) signature against cached JWKS (2) iss == `https://accounts.google.com` (3) aud == GOOGLE_CLIENT_ID (4) exp > now() (5) nonce 检查可选（本 Story 不引入 nonce，仅依赖 state + PKCE）
    a. 验签失败 → 返回 401 `401_oauth_id_token_invalid` + audit `auth.oauth.callback.error_provider`
  - 提取 id_token claims：`sub` (Google subject id, 持久唯一) + `email` + `email_verified` (Google 自有 verification 状态)
    a. 若 email_verified != true → 返回 400 `400_oauth_email_not_verified` (BR-1.7 — 信任 provider 验证语义)
  - 进入 account-linking 决策（per Q2 sm_proposal=a verify-only auto-link）：
    1. SELECT id, status, totp_enabled, email_verified_at FROM users WHERE oauth_provider='google' AND oauth_subject=$sub LIMIT 1
       a. 若 hit → 现有 OAuth user 直登路径（branch A）
    2. 若 (1) miss → SELECT id, password_hash, oauth_provider, oauth_subject, email_verified_at, status FROM users WHERE email=$email LIMIT 1
       a. 若 hit AND status='pending_deletion' → 返回通用 401 `401_authentication_failed` (anti-enumeration per Story 2.2 BR-1.5/m-5 模式 — 不泄露账户状态)
       b. 若 hit AND email_verified_at IS NOT NULL AND oauth_provider IS NULL → existing-verified-user 自动 link 路径（branch B）
       c. 若 hit AND email_verified_at IS NULL → 返回 403 `403_oauth_link_unverified` + i18n 文案 `auth.oauth.errors.linkUnverified` (BR-2.1 verify-only auto-link)
       d. 若 hit AND oauth_provider='google' AND oauth_subject != $sub → 返回 409 `409_oauth_subject_mismatch` (provider account 改变；不允许自动 re-link，需用户先 unlink — Story 2.5 落地)
       e. 若 hit AND oauth_provider != 'google' → 返回 409 `409_oauth_conflict_other_provider` + i18n 文案 `auth.oauth.errors.linkOtherProvider` (already linked to another provider)
    3. 若 (2) miss → 全新用户路径（branch C）
  - **Branch A** (existing OAuth user re-login)：UPDATE users SET updated_at=NOW() WHERE id=$user_id；颁发 JWT (per Story 2.2 jwt 包)；audit `auth.oauth.callback.success` + `is_new_user: false`
  - **Branch B** (existing verified user auto-link)：UPDATE users SET oauth_provider='google', oauth_subject=$sub, updated_at=NOW() WHERE id=$user_id；颁发 JWT；audit `auth.oauth.link.success` + `auth.oauth.callback.success`
  - **Branch C** (new user via OAuth)：INSERT INTO users (id=gen_random_uuid(), email=$email, password_hash=NULL, oauth_provider='google', oauth_subject=$sub, email_verified_at=NOW(), locale=stored.locale, status='active', created_at=NOW(), updated_at=NOW())；颁发 JWT；audit `auth.oauth.callback.success` + `is_new_user: true`
  - All 三 branch：若 users.totp_enabled=true → 颁发 short-lived `requires_2fa` JWT (90s exp, scope='2fa-pending')，response action='requires_2fa' (Story 2.2 BR-3.5 hook 复用)；否则颁发 full session JWT (access 15min + refresh 7day per Story 2.2 BR-3.7)
  - api-gateway 翻译 gRPC response → HTTP Set-Cookie (he_access / he_refresh，per Story 2.2 cookie 矩阵) → 302 Location: stored.return_to (已通过 BR-1.5 allow-list 校验)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | state_id 必须 ≥ 256-bit entropy (crypto/rand 32 bytes)；TTL=600s (10min)；one-shot consumption (GETDEL); 若 callback 时 state 不存在或过期一律拒绝 (per RFC 6749 §10.12) |
| BR-1.2 | PKCE 必须使用 S256 challenge_method（禁用 plain）；verifier 长度 ∈ [43, 128] base64url chars per RFC 7636；verifier 入 Redis 而非 cookie（Q1 sm_proposal=a） |
| BR-1.3 | state cookie binding：`he_oauth_state` cookie (Path=/v1/auth/oauth, Secure, HttpOnly, SameSite=Lax, Max-Age=600)；callback 时 cookie 值必须 == query.state，否则 reject (防跨标签 state 替换) |
| BR-1.4 | state replay 防护：Redis GETDEL 实现 one-shot；若 callback 重放则 GETDEL 第二次返回 nil → 拒绝 |
| BR-1.5 | return_to allow-list (严格)：仅允许以下 prefix：`https://console.he-api.com/` / `https://staging.console.he-api.com/` / 相对路径 `/{locale}/` (re-prefix by api-gateway 加 origin)；其他一律 reject 400 `400_oauth_invalid_return_to`；validation 在 initiate 路径完成（不进入 Redis） |
| BR-1.6 | Client binding：state 内 ip_hash (sha256(client_ip)) + ua_hash (sha256(user_agent.full))；callback 时严格匹配；不匹配 reject 400 + audit (防 state token 跨设备劫持) |
| BR-1.7 | Google ID token email_verified=false 时一律拒绝（per Q2 sm_proposal=a）— Google 仅在 email 已验证后才设 email_verified=true，未验证 email 注册 / 临时邮箱不可信 |
| BR-1.8 | Google client_id + client_secret 通过 K8s Secret `he-api-oauth-credentials` 注入（Q5 sm_proposal=a）；启动时加载到内存；不入日志（structured logger 必须 redact） |
| BR-1.9 | OIDC discovery URL 启动时一次性加载 + cache；JWKS 定期刷新 (per coreos/go-oidc/v3 内置 5min cache TTL)；运行时 discovery 失败 → 服务启动失败 (fail-fast) |
| BR-1.10 | i18n：所有用户面文案走 `messages/{locale}/auth.json` 的 `oauth.*` key 集；Google 按钮文案 `oauth.continueWithGoogle`（含 Google logo SVG，brand color #4285F4 — 仅图标 + 文案分离，符合 Google Brand Guidelines for OAuth UI）；错误文案 `oauth.errors.*`；本 Story 落地 10 locale 完整版（en 主写，9 locale 占位）|

### AC2: GitHub OAuth 登录 — Authorization Code + PKCE + access token + /user + /user/emails

**Scenario**
```gherkin
GIVEN 与 AC1 GIVEN 相同（users schema / JWT 链路 / OAuth credentials Secret / api-gateway 已就位）
  AND auth-svc 启动时已加载 GitHub OAuth 配置（GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET, GITHUB_AUTHORIZE_URL=`https://github.com/login/oauth/authorize`, GITHUB_TOKEN_URL=`https://github.com/login/oauth/access_token`, GITHUB_API_BASE=`https://api.github.com`）— GitHub 非 OIDC，无 discovery 文档

WHEN 用户点击 `<OAuthButtonGroup>` 中的 "Continue with GitHub" 按钮
  → console Server Action `initiateOAuth('github', returnTo)`
  → api-gateway `GET /v1/auth/oauth/github/initiate?return_to={returnTo}&locale={locale}`
  → auth-svc gRPC `BeginOAuth(provider='github', return_to, locale, client_ip, user_agent)`

THEN
  - state_id + pkce_verifier 生成同 AC1
  - Redis SETEX `auth:oauth:state:{sha256(state_id)}` (same schema as AC1, stored.provider='github')
  - 构造 GitHub Authorization URL: `https://github.com/login/oauth/authorize?client_id={GITHUB_CLIENT_ID}&redirect_uri={REDIRECT_URI_BASE}/v1/auth/oauth/github/callback&scope=read:user+user:email&state={state_id}&code_challenge={pkce_challenge}&code_challenge_method=S256&allow_signup=true`
  - api-gateway 设置 `he_oauth_state` cookie (同 AC1 BR-1.3 同 cookie 复用，scope 由 cookie path /v1/auth/oauth 控制；不需要 provider-specific cookie)
  - 302 Location: {github_authorize_url}
  - audit `auth.oauth.initiate` + provider='github'

  ---

  GitHub 重定向 callback `{REDIRECT_URI_BASE}/v1/auth/oauth/github/callback?code={code}&state={state_id}`
  → api-gateway `GET /v1/auth/oauth/github/callback` (state + cookie validation 同 AC1)
  → auth-svc gRPC `CompleteOAuth(provider='github', code, state_id, client_ip, user_agent)`

THEN
  - Redis GETDEL state (同 AC1, validate provider='github')
  - 调用 GitHub Token endpoint POST `https://github.com/login/oauth/access_token` headers: `Accept: application/json`, body: `client_id&client_secret&code&redirect_uri&code_verifier={stored.pkce_verifier}` (per GitHub OAuth 2022 PKCE 支持)
    a. GitHub 4xx/5xx → 502 `502_oauth_provider_error`
  - 提取 access_token；调用 GitHub `GET /user` headers: `Authorization: Bearer {access_token}, Accept: application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28`
    a. 失败 → 502 `502_oauth_provider_error`
    b. 响应提取 `id` (GitHub user numeric id, 持久唯一) + `login` (username) + `email` (可能 null — 用户隐藏 primary email)
  - 调用 GitHub `GET /user/emails` (相同 headers) 解析 primary email：
    ```
    [ {email, primary, verified, visibility} ]
    ```
    a. 选择 `primary=true AND verified=true` 的 email
    b. 若无 verified primary email → 返回 400 `400_oauth_email_not_verified` (BR-2.7 — 与 AC1 Google 同标准；GitHub 用户必须至少有 1 个 verified primary email 才能注册/关联)
    c. 若 /user 端点已返回 email != null（用户公开 primary）则可跳过 /user/emails 调用 (优化路径)；但 verified 状态必须确认 → 仍调用 /user/emails 验证 verified=true (安全优先 > 性能)
  - account-linking 决策与 AC1 完全相同（branch A / B / C），仅 provider 字段值为 'github'，subject 为 GitHub id (字符串化的 numeric id)
  - JWT 颁发 + 2FA hook + cookie + 302 与 AC1 同
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | GitHub PKCE 支持自 2022-12 起；本 Story 强制使用 S256 (GitHub 现已支持)，与 AC1 同标准 |
| BR-2.2 | scope 限制为 `read:user user:email`（最小权限，per OAuth 2.0 §3.3）；禁止申请 `repo` / `admin:org` / `gist` 等 scope |
| BR-2.3 | GitHub `/user/emails` 必须调用以确认 verified 状态，即便 /user 已返回 email；安全优先 (BR-2.7) |
| BR-2.4 | GitHub user numeric id（不是 username）作为 oauth_subject；username 可改变，id 不可改变（per GitHub docs） |
| BR-2.5 | account-linking 决策与 Google 共用同一 `pkg/linking` 实现（per Q2 sm_proposal=a verify-only auto-link）；provider 字段唯一不同 |
| BR-2.6 | GitHub access token 不持久化（不入 Redis，不入 DB）；仅在 callback 路径内存中使用（提取 email 后立即丢弃） |
| BR-2.7 | GitHub primary email verified=false 时一律拒绝（与 BR-1.7 Google email_verified 同语义 — 信任 provider 验证，不接受未验证 email） |
| BR-2.8 | GitHub User-Agent header 必须设为 `He-API-Auth-Svc/0.1` (GitHub API 要求 per docs) |
| BR-2.9 | GitHub API 速率限制：unauthenticated 60req/h/IP，authenticated (with token) 5000req/h；本 Story 仅在 callback 路径 (1 user 1 flow) 调用，远低于限制；但实施防御性 backoff (1 retry on 5xx after 250ms) |
| BR-2.10 | i18n：`oauth.continueWithGitHub`（含 GitHub Octocat SVG，monochrome black/white）；其他文案 keys 与 Google 共用 `oauth.errors.*` namespace |

### AC3: 账号关联与自动创建 — verify-only auto-link + anti-takeover + 三分支决策

**Scenario**
```gherkin
GIVEN auth-svc `pkg/linking` 实现 account-linking 决策（per Q2 sm_proposal=a verify-only auto-link，AC1 + AC2 共用此包）
  AND users 表已就位（Story 2.2 落地 + 本 Story 不变更 schema per Q3 sm_proposal=a）
  AND `idx_users_oauth` (Story 2.2 落地, partial WHERE oauth_provider IS NOT NULL) 用于 branch A 查询性能
  AND `idx_users_email` (Story 2.2 落地, UNIQUE) 用于 branch B/C 查询性能

WHEN CompleteOAuth(provider, code, state_id, ...) 流程中 provider token 验证完成
  AND 已提取 (provider_subject, provider_email, provider_email_verified=true)

THEN 执行 linking 决策（按以下顺序，命中即停）：

  **Branch A: existing OAuth user re-login**
  ```sql
  SELECT id, email, status, totp_enabled, email_verified_at FROM users
  WHERE oauth_provider = $provider AND oauth_subject = $provider_subject LIMIT 1
  ```
  - 命中且 status='active' / 'locked' / 'suspended' / 'pending_deletion'：
    - status='active' → UPDATE users SET updated_at=NOW() WHERE id=$user_id；颁发 JWT (检查 totp_enabled hook)；audit `auth.oauth.callback.success` + is_new_user=false
    - status='locked' → OAuth login 路径**不受 password-brute-force 软锁影响**（OAuth 通过 provider 验证，与 password 失败无关）；正常颁发 JWT；audit 标 `bypass_lock=true`（合规审计可见）
    - status='suspended' → 拒绝 403 `403_account_suspended` + audit `auth.oauth.callback.rejected_suspended`
    - status='pending_deletion' → 拒绝通用 401 `401_authentication_failed` (anti-enumeration per Story 2.2 m-5)
  - 不命中 → 进入 Branch B 判定

  **Branch B: existing email user — verify-only auto-link decision**
  ```sql
  SELECT id, email, password_hash, oauth_provider, oauth_subject, email_verified_at, status
  FROM users WHERE email = $provider_email LIMIT 1
  ```
  - 命中且 status='pending_deletion' → 拒绝 401 `401_authentication_failed` (anti-enumeration, 与 Branch A 同)
  - 命中且 status='suspended' → 拒绝 403 `403_account_suspended`
  - 命中且 status='active' / 'locked':
    - **B.1** oauth_provider IS NULL AND email_verified_at IS NOT NULL → **auto-link 成功路径**: UPDATE users SET oauth_provider=$provider, oauth_subject=$provider_subject, updated_at=NOW() WHERE id=$user_id；颁发 JWT；audit `auth.oauth.link.success` + `auth.oauth.callback.success`
    - **B.2** oauth_provider IS NULL AND email_verified_at IS NULL → **拒绝 unverified link**: 不更新 users 表；返回 403 `403_oauth_link_unverified`；i18n 文案引导 'Please verify your email via password login first then retry OAuth'；audit `auth.oauth.link.rejected_unverified`
    - **B.3** oauth_provider = $provider AND oauth_subject = $provider_subject → 等价于 Branch A (理论上 Branch A 已命中，此路径不应触发；若触发记 audit `auth.oauth.link.inconsistency`)
    - **B.4** oauth_provider = $provider AND oauth_subject != $provider_subject → **拒绝 subject mismatch**: 不更新；返回 409 `409_oauth_subject_mismatch`；i18n 引导 'This email is linked to a different Google account. Contact support if this is unexpected.'；audit `auth.oauth.link.rejected_subject_mismatch`
    - **B.5** oauth_provider != $provider (e.g., user 已绑 google, 现在尝试 github 链接) → **拒绝 cross-provider conflict**: 不更新；返回 409 `409_oauth_conflict_other_provider`；i18n 引导 'This account is already linked to {other_provider}. Account unlinking will be available in Story 2.5.'；audit `auth.oauth.link.rejected_other_provider`
  - 不命中 → 进入 Branch C

  **Branch C: new user via OAuth (signup)**
  ```sql
  -- 必须使用 SERIALIZABLE 或 INSERT ... ON CONFLICT DO NOTHING 防 race condition
  -- (同一 email 在并发场景下两次 OAuth callback 同时进入 Branch C)
  INSERT INTO users (id, email, password_hash, oauth_provider, oauth_subject, email_verified_at, locale, status, created_at, updated_at)
  VALUES (gen_random_uuid(), $provider_email, NULL, $provider, $provider_subject, NOW(), $stored.locale, 'active', NOW(), NOW())
  ON CONFLICT (email) DO NOTHING
  RETURNING id
  ```
  - INSERT RETURNING id 命中 → 颁发 JWT；is_new_user=true；audit `auth.oauth.callback.success` + is_new_user=true
  - INSERT 0 行（ON CONFLICT — race condition：另一 OAuth flow 已在我们查询后但 INSERT 前完成同 email 注册）→ 重新执行 Branch B（防 lost-update）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | Branch A/B/C 决策必须**按顺序**执行；命中即停；不允许跳跃（防 race condition 引入的逻辑错误） |
| BR-3.2 | Branch B 的 verify-only auto-link 是**安全核心**：未验证 email 一律拒绝自动 link；行业标准（OWASP ASVS L2 V2.7 / GitLab CVE-2022-1162）；不可接受 trade-off |
| BR-3.3 | Branch C INSERT 必须使用 `ON CONFLICT (email) DO NOTHING` 防并发 race；失败时 fallback 到重新执行 Branch B（lost-update detection） |
| BR-3.4 | OAuth login 路径**不触发 password-failure 软锁**（users.locked_until 不变）；OAuth 自身限流通过 BR-4.2 ratelimit 实现 |
| BR-3.5 | OAuth login 成功后必须检查 users.totp_enabled；若 true → 颁发 short-lived `requires_2fa` JWT（90s exp, scope='2fa-pending'），不进入 full session；与 Story 2.2 BR-3.5 同 hook 模式 |
| BR-3.6 | Branch B/C 写入的 oauth_subject 必须是 provider 持久 ID（Google sub claim / GitHub numeric id），不是 email 或 username（防 provider account 重命名导致 link 失效） |
| BR-3.7 | Branch B.1 auto-link 不修改 users.email_verified_at / password_hash / status / locale / locked_until 等已有字段（仅 oauth_provider + oauth_subject + updated_at）；保留 password 登录能力（OAuth 是额外身份，不取代 password） |
| BR-3.8 | Branch C INSERT 时 locale 取自 stored.locale (initiate 时用户 cookie 推断)；不取 provider profile locale（Google profile locale 可能与用户当前浏览偏好不一致） |
| BR-3.9 | audit 事件必须包含 (provider, subject_hash=sha256(provider_subject), email_hash=sha256(email), branch_taken='A'/'B.1'/'B.2'.../etc, is_new_user, outcome='success'/'rejected_*')；email 与 subject 仅 hash，不入 audit 明文（PII 脱敏） |
| BR-3.10 | Branch A 中 status='locked' 仍可 OAuth 登录，但必须在 JWT claims 中标记 `was_locked=true`（debugging）；audit 记 `bypass_lock=true`（合规可见）；不静默修复 users.status（不调用 self-heal — self-heal 仅在 password login 路径执行） |

### AC4: 横切关注点 — state CSRF + open-redirect + ratelimit + audit + i18n + 安全 headers

**Scenario**
```gherkin
GIVEN AC1 / AC2 / AC3 已落地核心流程
  AND api-gateway 已落地 SecurityHeaders 中间件（Story 2.2 P1）
  AND Kafka `audit.event` topic 已就位（Story 2.2 P5 落地，partition-by-EmailHash）
  AND Redis `ratelimit:*` namespace 已就位（Story 2.2 落地）
  AND console i18n `messages/{locale}/auth.json` 已就位 10 locale (Story 2.2 落地)

WHEN OAuth flow 处于 initiate 或 callback 任一路径

THEN
  - **CSRF state 防护** (BR-4.1)：
    - state_id 强度 ≥ 256-bit (crypto/rand.Read 32 bytes → base64url)
    - state 必须同时存在于：(a) Redis (TTL=600s, one-shot) (b) signed cookie `he_oauth_state` (HMAC-signed if Q1 hybrid; 简单值 if Q1=a)
    - callback 时：query.state == cookie.state AND Redis GETDEL 成功；任一缺失 → reject
  - **Open-redirect 防护** (BR-4.5)：
    - return_to 参数严格 allow-list：
      ```
      production: ^https://console\.he-api\.com/
      staging: ^https://staging\.console\.he-api\.com/
      dev: ^https://localhost(:\d+)?/  OR  ^http://localhost(:\d+)?/
      relative: ^/[a-z]{2}(-[A-Z]{2})?/   (i.e., /en/ / /zh-CN/ / etc. — must include valid locale prefix)
      ```
    - validation 通过 `pkg/redirect.IsAllowed(returnTo) bool`；任一 mismatch → return 400 + audit `auth.oauth.invalid_return_to`
    - validation 在 BeginOAuth 入口完成，不进入 Redis 状态写入（防 polluted state TTL=600s 占位）
  - **Ratelimit** (BR-4.2)：
    - initiate 路径: Redis INCR `ratelimit:oauth:initiate:ip:{client_ip}` (EXPIRE 60s)；> 30 次/min → 429
    - callback 路径: Redis INCR `ratelimit:oauth:callback:ip:{client_ip}` (EXPIRE 60s)；> 30 次/min → 429
    - state-level (callback): 同 state_id 在 GETDEL 后已 DEL；replay 自然 reject (BR-1.4)
    - 速率限制对所有 OAuth 路径生效；与 Story 2.2 `ratelimit:signin:ip:*` / `ratelimit:signup:ip:*` 等同 namespace 模式
  - **Audit logging** (BR-4.3)：
    - 所有 OAuth 事件写入 Kafka `audit.event` topic (partition-by-EmailHash per Story 2.2 同模式)
    - 事件类型枚举：
      - `auth.oauth.initiate` (provider, ip_hash, ua_hash, state_id_hash, return_to_host)
      - `auth.oauth.callback.success` (provider, subject_hash, email_hash, is_new_user, branch_taken, was_locked, requires_2fa)
      - `auth.oauth.callback.error_state` (provider, ip_hash, reason='cookie_missing'/'redis_miss'/'replay'/'binding_mismatch')
      - `auth.oauth.callback.error_provider` (provider, ip_hash, reason='token_endpoint_failure'/'id_token_invalid'/'user_endpoint_failure'/'email_not_verified')

    - api-gateway SecurityHeaders 中间件已对所有 /v1/* 路径生效（Story 2.2 P1 落地）
    - OAuth callback 路径额外校验 `Referer` header（不强制要求，但若存在则必须以 google.com / github.com 为来源）；不通过 → audit 但不 reject（避免过严导致正常用户 referrer-policy=no-referrer 失败）

**Story 2.3 写入路径**（仅写已就位字段）：

```sql
-- Branch A re-login: 更新 updated_at
UPDATE users SET updated_at = NOW() WHERE id = $user_id;

-- Branch B.1 auto-link (verified email + null oauth_provider):
UPDATE users
SET oauth_provider = $provider,
    oauth_subject = $subject,
    updated_at = NOW()
WHERE id = $user_id AND oauth_provider IS NULL;
-- WHERE 子句 防 lost-update; 影响行 0 → fallback Branch A 重判（极罕见）

-- Branch C new user via OAuth (with race protection):
INSERT INTO users (id, email, password_hash, oauth_provider, oauth_subject,
                   email_verified_at, locale, timezone, status,
                   created_at, updated_at)
VALUES (gen_random_uuid(), $email, NULL, $provider, $subject,
        NOW(), $locale, 'UTC', 'active',
        NOW(), NOW())
ON CONFLICT (email) DO NOTHING
RETURNING id;
-- 若 0 行 → race detected → fallback to Branch B
```

- Branch A: `idx_users_oauth` (partial, WHERE oauth_provider IS NOT NULL) — Story 2.2 落地，本 Story **首次实际使用**（Story 2.2 创建该 index 但当时无 OAuth user）；EXPLAIN ANALYZE 应显示 `Index Scan using idx_users_oauth on users`

**事务边界**：
- 单条 UPDATE / INSERT 不需要 explicit transaction（默认 implicit autocommit per pgx）
- Branch A → B → C 决策路径不在单个事务中（每个 SELECT 独立）— ON CONFLICT DO NOTHING 提供 race protection 而非 SERIALIZABLE 隔离

### Testing Requirements

**Story-specific test focus areas** (与 Story 2.2 Comprehensive level + risk profile MANDATORY 同模式)：

1. **State CSRF token 安全测试 (P0)**：
   - state_id entropy 验证 (NIST SP 800-90A 推荐 ≥ 256-bit / crypto/rand)
   - Redis one-shot (GETDEL) 语义：consume 后 second consume 必须返回 nil
   - Cookie binding：cookie 缺失 / 不匹配 query state 一律 reject
   - IP/UA hash binding：mismatch 一律 reject + audit
   - TTL expired (>10min)：reject 400

2. **PKCE 验证测试 (P0)**：
   - verifier 长度边界 (43, 44, 127, 128, 42-reject, 129-reject per RFC 7636)
   - challenge_method=plain 必须被 reject（仅 S256）
   - verifier-challenge 配对：SHA-256(verifier) == base64url decode(challenge)
   - challenge 与 verifier mismatch：provider token exchange 失败 → reject

3. **Account-linking 决策矩阵全覆盖 (P0)**：
   - Branch A (existing OAuth): 4 个 status case (active/locked/suspended/pending_deletion)
   - Branch B (existing email): 5 个 sub-case (B.1/B.2/B.3/B.4/B.5)
   - Branch C (new user): 1 个 happy + 1 个 race condition (ON CONFLICT DO NOTHING)
   - 总共 10 个分支必须每条都有 unit test

4. **Provider integration tests (P0)**：
   - Google OIDC: mock JWKS server + 伪造但签名正确的 ID token → 验签通过；伪造但签名错误 → 验签失败
   - Google ID token claims: iss / aud / exp 验证
   - GitHub: mock /user + /user/emails 端点；primary verified 解析；primary unverified 拒绝；多 email 排序选择

5. **Open-redirect 防护 (P0)**：
   - return_to allow-list 测试 50+ 边界 case：
     - `https://attacker.com` → reject
     - `https://console.he-api.com.attacker.com` → reject (subdomain trick)
     - `https://console.he-api.com@attacker.com` → reject (@-trick)
     - `https://console.he-api.com//attacker.com` → reject (path-confusion)
     - `javascript:alert(1)` → reject (scheme)
     - `//attacker.com` → reject (scheme-relative)
     - `/en/dashboard` → allow (relative locale)
     - `/dashboard` → reject (无 locale prefix per regex)
     - `https://staging.console.he-api.com/foo` → allow (staging-only env)

6. **Ratelimit 测试 (P1)**：
   - initiate IP-based: 31 次/min → 第 31 次 429 + Retry-After
   - callback IP-based: 同上
   - Redis 不可用 fail-closed: ratelimit middleware 返回 503

7. **Anti-enumeration 测试 (P0)**：
   - pending_deletion 用户尝试 OAuth：与不存在 email 用户行为完全一致（响应内容、HTTP code、timing within ±50ms）
   - suspended vs not-exists：相同 generic 错误
   - Branch B.4/B.5 不允许信息泄露 provider 内部状态

8. **2FA hook 测试 (P1)**：
   - users.totp_enabled=true → CompleteOAuth 返回 requires_2fa=true + short-lived JWT (90s exp, scope='2fa-pending')
   - users.totp_enabled=false → 正常 access+refresh JWT 颁发

9. **Audit completeness (P1)**：
   - 每个 branch 都有对应 audit 事件类型
   - 所有 PII 字段 hash (sha256) 不入明文
   - non-blocking: Kafka producer 失败不阻塞 OAuth flow

10. **E2E happy paths (P0)**：
    - Google new user signup → onboarding
    - Google existing-verified-user auto-link → dashboard
    - Google existing-unverified-user reject → signin with toast
    - GitHub same 3 paths
    - Browser cookie 持久化跨页面（dashboard 受保护页可访问）

11. **E2E error paths (P1)**：
    - User clicks Google authorize 'Cancel' → 回 signin + access_denied toast
    - Mock provider 5xx → 502 toast + audit
    - State CSRF attack（构造 fake state） → 400 toast

12. **Security attack scenarios (P0)** — 与 Story 2.2 SEC-A0x 同模式：
    - SEC-A01: state CSRF replay (GETDEL 后 second consume reject)
    - SEC-A02: state cookie forge (没有 cookie 也能 callback 吗 → 不能)
    - SEC-A03: PKCE verifier mismatch (provider token exchange 失败)
    - SEC-A04: open-redirect via return_to
    - SEC-A05: account takeover via unverified email (Branch B.2 必须 reject)
    - SEC-A06: Google JWKS rotation race (cached old keys → 拒绝 new ID token)
    - SEC-A07: GitHub /user 401 token-revoked race
    - SEC-A08: provider response with email_verified=false → reject
