## Story

**As a** developer building on the He-API OpenAI-compatible platform,
**I want** to transcribe an audio file by POSTing it (multipart/form-data) to the standard `POST /v1/audio/transcriptions` endpoint with the OpenAI Whisper request shape, and receive the transcribed text in the Whisper response shape, routed under the hood to Doubao (Volcano Engine) ASR,
**so that** my existing OpenAI-SDK speech-to-text code (`client.audio.transcriptions.create(...)`) works unchanged against He-API, closing the "语音" (speech) half of the epic's "图像/语音多模态 API 可调通" promise.

## Acceptance Criteria

> Epic-9 legacy AC: **"语音转文字可用"** (speech-to-text works) + PRD **FR-8.2** ("接入 Doubao ASR；兼容 OpenAI Whisper API 协议"). ### AC1: Whisper 兼容入参 — `POST /v1/audio/transcriptions`（multipart/form-data 解析 + transcription-only 路由）

**Scenario**
```gherkin
GIVEN
  - Every He-API public endpoint to date ingests JSON (`/v1/chat/completions` @`chat_completions.go`, `/v1/embeddings` @`embeddings.go`); NO multipart/form-data parsing exists in the gateway yet
  - The OpenAI Whisper wire shape for `POST /v1/audio/transcriptions` is **multipart/form-data**: `file` (required, binary audio), `model` (required, string), `language` (optional, ISO-639-1), `prompt` (optional, string context), `response_format` (optional, `json`|`text`|`verbose_json`|`srt`|`vtt`, default `json`), `temperature` (optional, float ∈ [0,1])
  - Story 3.5 established the 2nd-endpoint precedent (`embeddings.go` — its OWN body-cap const `MaxEmbeddingBodyBytes`, its OWN validator, its OWN analytics/TPM hooks) and the `MaxEmbeddingBodyBytes` comment explicitly anticipates "Story 9.x (multimodal) … without renaming the chat-specific constant"
  - Story 4.7 / `packages/models-catalogue` models capabilities per model id; 9.6 adds a NEW `Transcription` capability (AC3)
WHEN
  - A client POSTs `/v1/audio/transcriptions` as multipart/form-data with a `file` part + a `model` that is a transcription-capable model
THEN
  - A NEW handler `audio_transcriptions.go` parses the multipart body via `r.ParseMultipartForm(maxAudioBodyBytes)` (after an `http.MaxBytesReader` read cap), extracts the SINGLE `file` part + the text fields, and validates them (AC4 limits + the field schema) — the request is rejected pre-dispatch on any violation (zero upstream call)
  - The handler resolves the model's `Transcription` capability (AC3): a model that is NOT transcription-capable (e.g. `qwen-max`, `doubao-pro`) → `400_invalid_request` ("model '<id>' does not support audio transcription") BEFORE any upstream dispatch
  - The DO-NOT-REGRESS fence (BR-1.6): conversely, the EXISTING `/v1/chat/completions` handler now REJECTS a non-`Chat` model (a `Transcription`-only id sent to the chat endpoint → 400 "does not support chat completions") — closing the gap that the chat handler never gated on `Chat:true`
  - A valid request is routed via the adapter wire (AC2) to the Doubao service that hosts the ASR translation; the transcribed text is returned in the Whisper response shape resolved from `response_format` (AC2 BR-2.6): `json` → `{"text":"…"}`; `text` → the raw transcript string (Content-Type `text/plain`); `verbose_json` → `{text, language, duration, segments}` when the upstream supplies segments (Q-ASR-RESPFORMAT)
  - The handler is wrapped by the SAME middleware chain as `/v1/chat/completions` (bearer-auth → analytics → key-policy → rate-limit → billing-gate) at registration in `cmd/server/main.go`; the rate-limit TPM axis + the pre-flight billing gate adapt to the no-tokens-until-after-transcription reality per AC3 BR-3.7
  - The content-safety scanner (Story 8.2) scans the TEXT fields (`prompt`, and per Q-ASR-LIMITS optionally the output transcript) at the resolved per-Key strictness (8.4); the audio bytes are opaque binary, NOT lexicon-scannable — NO 8.2/8.4/8.5 regression
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | **Multipart/form-data ingestion (NEW shape)**: the handler reads the body under an `http.MaxBytesReader(w, r.Body, maxAudioBodyBytes)` cap, then `r.ParseMultipartForm(maxAudioBodyBytes)`. Exactly ONE `file` part is required; zero `file` parts → 400 `"Field 'file' is required."`; >1 `file` part → 400. Non-multipart content-type (e.g. `application/json`) → `415_unsupported_media_type` (or the canonical 400 family per §5.1.2). This is the first multipart endpoint — it does NOT touch the JSON `/v1/chat/completions` or `/v1/embeddings` paths. |
| BR-1.2 | **Whisper field schema**: `model` required, non-empty, ≤ `modelMaxLen` (100, matching `he_api.models.id VARCHAR(100)`). `language` optional, ISO-639-1 2-letter (validated; unknown → 400). `prompt` optional, ≤ a length cap (Q-ASR-LIMITS). `response_format` optional ∈ {`json`,`text`,`verbose_json`,`srt`,`vtt`}, default `json`; an unsupported-in-9.6 value (e.g. `srt`/`vtt` if deferred) → 400 (Q-ASR-RESPFORMAT). `temperature` optional float ∈ [0,1]; out-of-range → 400. ### AC4: 音频输入安全与限额 — 上传体积/格式上限 + multipart DoS 防护 + PII 不外泄（非协商安全契约）

**Scenario**
```gherkin
GIVEN
  - `/v1/audio/transcriptions` accepts a binary `file` upload via multipart/form-data — a NEW surface vs every JSON endpoint: an oversized upload is a memory/DoS vector; a malformed multipart stream is a parser-DoS vector; audio bytes AND the transcript are user PII

WHEN
  - A client uploads an audio `file` (and optional text fields)
THEN
  - **Body cap**: `http.MaxBytesReader(w, r.Body, maxAudioBodyBytes)` caps the read BEFORE `ParseMultipartForm`; `maxAudioBodyBytes = 25 MiB` (`25<<20`, OpenAI parity — Q-ASR-LIMITS ratifies).   - **Format / mime allow-list**: the `file` part's content-type + extension (and a magic-byte sniff) MUST be in the allow-list `audio/{mpeg,mp4,wav,webm,m4a,flac,ogg}` ∩ {what Volcano accepts} (Q-ASR-LIMITS); an unsupported/declared-non-audio type → `400_invalid_request`.   - **PII / secret discipline (NON-NEGOTIABLE)**: audio bytes, the multipart raw stream, AND the transcribed text are NEVER written to logs, slog fields, span attributes, error messages, or analytics records (cascade: 9.4 BR-TR-7 spans, 9.2 BR-RD-9 logs, 9.3 BR-EX-12 exports; the 3.5 embeddings precedent already logs only SIZE signals, never `input` content). Structured logs carry only non-PII signals (model, api_key_id, audio_bytes_size, duration_seconds, mime). Error envelopes reference the field name (`file`), never the bytes
  - **Reject ordering (fail-closed, pre-dispatch)**: all AC4 validations (size, mime, part-count) run AFTER multipart parse + AC1 structural validation and BEFORE the transcription-capability gate / content-safety / any upstream call — a rejected request makes ZERO upstream calls and incurs ZERO usage/billing (same discipline as 9.5 BR-3.6 / 8.2)
  - **Temp-file hygiene**: any multipart temp file the runtime spills is removed (`r.MultipartForm.RemoveAll()` deferred) on every path (success + error) — no audio bytes left on disk
```

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| request body | bytes | — | ≤ `maxAudioBodyBytes` (25 MiB) | "Request body exceeds the maximum size (25 MiB)." |
| `file` mime/format | string | yes | in the audio allow-list (BR-4.3) | "Unsupported audio format '<mime>'." |
| `file` part count | int | — | exactly 1 | "Field 'file' must be a single audio file." |
| any log/span/export/analytics path | — | — | audio bytes / transcript NEVER emitted | (PII discipline BR-4.4; audited by a no-PII test) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| upload > 25 MiB | 413 | "Request body exceeds the maximum size (25 MiB)." | reject at reader (BR-4.1) |
| unsupported audio format | 400 | "Unsupported audio format '<mime>'." | reject pre-dispatch (BR-4.3) |
| malformed multipart stream | 400 | "Malformed multipart/form-data body." | `ParseMultipartForm` error → 400 |
| any log/span/export path | — | audio bytes / transcript NEVER emitted | PII discipline (BR-4.4), no-PII test |

**Examples**
- **Input**: a 40 MiB `.wav` upload → **Expected**: `413_payload_too_large` "exceeds the maximum size (25 MiB)." — rejected at the reader, ZERO upstream call, no audio bytes logged.
- **Input**: a `file` whose content is actually `text/html` (mislabelled `audio/mpeg`) → **Expected**: `400_invalid_request` "Unsupported audio format …" after the magic-byte sniff (BR-4.3).
- **Input**: a valid `hello.mp3` → **Expected**: 200; the log line carries `audio_bytes_size`/`mime`/`duration_seconds` but NEVER the audio bytes or the transcript; the temp file is removed on exit.

**Context.** QA Round 2 escalated exactly one open item: M-2, an `architecture_concern`. The Round-1 contract (Q-ASR-UPSTREAM ruling + AC2(g) + T3.3) said "fail-fast at boot on any unset ASR env." Dev correctly left behaviour unchanged and escalated rather than no-op-loop. The two options put to me:
- **(a)** Accept request-time as the contract; amend AC2(g)/T3.3; QA PASSes — no Dev work.
- **(b)** Require boot fail-fast gated on `doubao-asr` ∈ bound set — back to Dev.

**Ruling: (b), with the gate specified precisely. The Round-1 "boot fail-fast on unset" wording is hereby AMENDED — it did not account for the shared-service topology it itself ratified.**

> **BINDING:** At Doubao-service boot, **IF `doubao-asr` is present in the operator's *explicit* `DOUBAO_BOUND_MODEL_IDS` set AND `asrCfg.Configured() == false` → fail-fast (`log.Fatal`/panic), naming the missing `DOUBAO_ASR_UPSTREAM_*` envs. OTHERWISE boot normally** and retain the already-implemented request-time `connect.CodeUnavailable` as defence-in-depth.

**Why (b), not (a).** Dev's shared-service concern is legitimate — pure boot-fail-fast regresses chat-only deployments, which is unacceptable. But pure request-time (a) throws away the *entire value* of the 4.5 BR-1.12 precedent the contract cited: an operator who **declares intent** to serve ASR (lists `doubao-asr` in the bound set) yet fat-fingers an ASR env gets a service that boots "healthy," advertises `doubao-asr`, and fails only at a paying customer's first `Transcribe` — a runtime 503 on a **money-handling, security-sensitive** endpoint, when it should have been a deploy-time crash. The conditional gate keeps deploy-time misconfiguration detection exactly where it matters (declared ASR intent) while leaving chat-only deployments untouched. This is the minimal change that satisfies both forces — not over-engineering, a single conditional aligning the requirement with operator intent. **Confidence: High.**

**Implementation is small and the seam already exists.** `cmd/server/main.go:87-99` parses the explicit `DOUBAO_BOUND_MODEL_IDS` set *before* the `asrCfg.Configured()` auto-append at `:131-133` — so the explicit set is the correct, available signal of intent.
