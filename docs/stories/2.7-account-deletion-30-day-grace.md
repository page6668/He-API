### AC2: api-gateway `POST /v1/account/deletion` + auth-svc gRPC `RequestAccountDeletion` (re-auth, grace-window set, idempotent)

**Scenario**
```gherkin
GIVEN a verified user with a valid JWT cookie (Story 2.2) and users.status='active'
WHEN they POST to api-gateway POST /v1/account/deletion with body {reauth: {password?|confirm_email?, totp_code?}} (user_id NEVER in body — derived from JWT sub)
THEN api-gateway
  - MUST validate the JWT via the jwt-verify middleware (Story 2.2 BR-3.1), extracting user_id from the `sub` claim
  - MUST translate to gRPC auth.AuthService.RequestAccountDeletion(RequestAccountDeletionRequest{user_id, reauth}) (connect-go, mirroring account_data.go proxy [Source: apps/api-gateway/cmd/server/main.go:273-277])
  - auth-svc MUST first re-verify the credential server-side (BR-2.4): bcrypt-compare password OR exact-match confirm_email for OAuth-only; AND verify TOTP if users.totp_enabled — on mismatch return 403 `403_bad_reauth` WITHOUT state change
  - auth-svc MUST be idempotent: if users.status='pending_deletion' already → return the existing {pending_deletion_at, status='pending_deletion'} (HTTP 200; NO new audit/email) — see BR-2.6
  - on success (status='active' → 'pending_deletion'), auth-svc MUST atomically (single PG transaction):
      1. INCR Redis ratelimit:account:delete:{user_id} (EXPIRE 86400); if > 5 → rollback + 429 (BR-2.5)
      2. UPDATE users SET status='pending_deletion', pending_deletion_at = NOW() + INTERVAL '30 days', updated_at=NOW() WHERE id=$1 AND status='active'
      3. Revoke all active sessions/refresh tokens for the user (force re-auth into recovery flow) — Story 2.2 session store
      4. Produce audit.event (event_type='account.deletion.requested', payload per AC7 BR-7.1)
      5. Invoke notification-svc.SendEmail(template=EMAIL_TEMPLATE_ACCOUNT_DELETION_REQUESTED=9) — deletion-scheduled confirmation with the pending_deletion_at date + "cancel any time before then" CTA
  - api-gateway MUST return HTTP 200 {status:'pending_deletion', pending_deletion_at:ISO-8601, can_cancel_until:ISO-8601}
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | REST endpoint MUST be `POST /v1/account/deletion` (api-gateway, `apps/api-gateway/internal/handlers/account_deletion.go` — NEW, mirrors `account_data.go`). |
| BR-2.2 | gRPC RPC `RequestAccountDeletion` MUST be added to the EXISTING `auth` service contract (`packages/proto/he/auth/v1/auth.proto`), not a new service. Companion RPCs `CancelAccountDeletion` (AC3) + `GetAccountDeletionState` (AC1/AC3/AC4) land in the same proto edit. |
| BR-2.3 | Grace window is EXACTLY `NOW() + INTERVAL '30 days'` (wall-clock, server-side, UTC) — never client-supplied [Source: docs/architecture/security.md#8.3]. |
| BR-2.4 | auth-svc MUST NOT trust client-supplied `user_id` (derive from JWT only) AND MUST re-verify a fresh credential before the destructive transition (defense against session-hijack one-click deletion; OWASP ASVS L2). Credential rules per AC1 BR-1.4. The reauth payload is verified inside auth-svc — api-gateway only forwards it over the wire (TLS). |
| BR-2.5 | Anti-accident rate limit: Redis `ratelimit:account:delete:{user_id}`, counter, TTL 86400s, ceiling 5/24h. INCR happens inside the PG transaction (Lua/MULTI) per Story 2.6 BR-2.5 idiom; > 5 → rollback + 429. |
| BR-2.6 | Idempotency: a second request while already `pending_deletion` returns 200 with the SAME `pending_deletion_at` (no new email, no new audit, no window extension). A request while `status IN ('suspended','locked','deleted')` returns `409_account_not_deletable`. |
| BR-2.7 | The `UPDATE ... WHERE id=$1 AND status='active'` guard makes the active→pending transition a single-winner CAS; 0 rows affected ⇒ re-read state and apply BR-2.6 branch. |
| BR-2.8 | Session revocation (step 3) is REQUIRED so existing tabs cannot keep operating as a healthy account; subsequent requests hit the AC4 guard. |
| BR-2.9 | HTTP status semantics: 200 (new or idempotent existing), 401 (JWT), 403 (`403_bad_reauth`), 409 (`409_account_not_deletable`), 429 (rate-limit), 500 (PG/Redis/Kafka). Latency SLO p95 < 300ms (adds bcrypt + optional TOTP verify over Story 2.6's 200ms baseline). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `Authorization` (cookie) | string | yes | Valid HS256 JWT (Story 2.2); user resolvable | `401_unauthorized` [Source: rest-api-spec.md:161 region] |
| `reauth.password` | string | conditional | Required iff `password_hash IS NOT NULL`; bcrypt-verified | `403_bad_reauth` |
| `reauth.confirm_email` | string | conditional | Required iff OAuth-only; exact match `users.email` | `403_bad_reauth` |
| `reauth.totp_code` | string | conditional | Required iff `totp_enabled`; 6 digits; TOTP-valid (Story 2.4) | `403_bad_reauth` |
| `user_id` in body | — | forbidden | MUST be absent (BR-2.4) | `400_invalid_body` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| JWT invalid/expired | 401 | `401_unauthorized` | client refresh + retry |
| Re-auth credential mismatch | 403 | `403_bad_reauth` (NEW code; register in rest-api-spec §5.1.2 this Story) | no state change; console clears field |

- Input: wrong TOTP → 403 `403_bad_reauth`; users.status stays `active`.
- Input: body `{"user_id":"...","reauth":{...}}` → 400 `400_invalid_body`.

### AC6: `account-deletion-sweeper` CronJob — Physical Erasure after 30 Days ("30 天后物理删除")

**Scenario**
```gherkin
GIVEN one or more users rows WHERE status='pending_deletion' AND pending_deletion_at <= NOW()
WHEN the account-deletion-sweeper CronJob runs (schedule 0 2 * * * UTC, following the monthly-cost-reset pattern [Source: apps/auth-svc/cmd/monthly-cost-reset/main.go])
THEN for EACH due user, in a single PG transaction per user (idempotent, fail-isolated):
  1. PII anonymization of users row: email → 'deleted+'||id||'@anonymized.invalid' (preserves UNIQUE), display_name → NULL, password_hash → NULL, oauth_subject → NULL, totp_secret_encrypted → NULL; SET status='deleted', deleted_at=NOW(), anonymized_at=NOW() [Source: docs/architecture/security.md#8.3]
  2. Hard-delete (or rely on FK CASCADE) of PII-bearing children: api_keys, mfa_recovery_codes, data_export_requests are ON DELETE CASCADE [Source: migrations 0006:27, 0003:18, 0005:19] — removing the users row would cascade, BUT because we SOFT-delete (anonymize, not DROP) the users row, the sweeper MUST EXPLICITLY DELETE these children (CASCADE does not fire on UPDATE). balances is also explicitly deleted.
  3. Financial-retention tables (recharge_orders, subscriptions, payment_methods, invoices — NO ON DELETE CASCADE [Source: migrations 0010, 0011]) are RETAINED for legal/financial audit but have their user_id anonymization handled per OQ-3 (kept linked to the now-anonymized users row; figures frozen per Story 7.7 BR-I-2).
  4. content_safety_logs is NOT touched — it has NO FK to users and a separate 6-month retention cron (GDPR-erasure exemption §9.3) [Source: docs/architecture/security.md#9.3].
  5. ClickHouse request_logs: anonymize user_id (UPDATE/ALTER ... user_id → NULL or hash) for the user's rows; the 90-day TTL still applies [Source: docs/architecture/security.md#8.3].
  6. OSS: delete personal objects under gdpr-exports/{user_id}/* (Story 2.6 export ZIPs) via the OSS SDK.
  7. Produce audit.event (event_type='account.deletion.executed', AC7 BR-7.1) and invoke notification-svc.SendEmail(template=EMAIL_TEMPLATE_ACCOUNT_DELETION_COMPLETED=11) BEFORE email anonymization is committed... (see BR-6.4 ordering)
AND
  GIVEN any per-user step fails
  WHEN the error is captured
  THEN that user's transaction is rolled back, the failure is logged + audit (account.deletion.executed with a failure marker is NOT emitted; instead a WARN log + Sentry), and the sweeper CONTINUES with the next user (one bad row never blocks the batch); the CronJob exits 1 if any user failed (ops-visible) but commits all successful users.
```

### Database / Deletion-Model Design (WHY)
- **Soft-delete, not hard-delete.** §8.3 mandates retaining the anonymized `users` row for legal/financial linkage. Consequence: FK `ON DELETE CASCADE` (api_keys/mfa_recovery_codes/data_export_requests) does **not** fire on an UPDATE — the sweeper MUST explicitly `DELETE` PII-bearing children. This is the single most error-prone point of the Story (a dev who assumes CASCADE will leave orphaned PII). Called out in AC6 BR-6.3 + T8.2 asserts it.
- **`'deleted'` is a NEW app-layer terminal status** — no DDL/CHECK change (status set is app-validated since 0002). 
- **Cross-store erasure is not atomic.** PG is the source of truth; CH `request_logs` + OSS objects are reconciled post-commit via the `anonymized_at IS NULL` re-sweep gate (AC6 BR-6.6). A crash after PG commit but before CH/OSS leaves a recoverable, retried state — never a silent PII leak.

### Data Models — Interface Contracts (not implementations)

### Open Questions (require Architect ratification — security-sensitive, P0)
- **OQ-1 (login during grace)**: `rest-api-spec.md:161` glosses `403_account_pending_deletion` as "拒绝登录" (reject login), but `security.md §8.3` says the user CAN log in during the 30 days to cancel. This Story reconciles them by letting signin *authenticate* but yield a **recovery-only session** (console blocked, recovery page allowed). Architect to ratify this interpretation + whether the recovery session is a distinct token scope.
- **OQ-2 (cancel re-auth asymmetry)**: AC2 requires fresh credential re-auth to DELETE; AC3 requires only a valid JWT to CANCEL. Is restorative cancellation acceptable without re-auth, or must cancel also re-verify? (Default chosen: no re-auth for cancel, to avoid recovery deadlock.)
- **OQ-3 (financial-data disposition)**: recharge_orders / subscriptions / invoices / payment_methods have no FK CASCADE and carry legal/financial retention obligations (Story 7.7 BR-I-2). Default chosen: RETAIN, kept linked to the anonymized `users` row (no extra PII beyond user_id). Architect to confirm vs. a stricter user_id-nulling + standalone retention model, and to confirm `payment_methods` (Stripe token) disposition.

### Open Question Rulings (security-sensitive P0 — binding)

- **OQ-1 (login during grace) — RATIFIED.** Accept the recovery-only-session interpretation. The `security.md §8.3` "user can login during 30d to cancel" is the controlling intent (GDPR requires the cancellation path to be reachable). `403_account_pending_deletion` MUST be emitted for **console/business** API access only — NOT for the signin, recovery-page, or cancel endpoints. A distinct recovery token-scope/claim is **OPTIONAL for MVP**: AC2 step 3 revokes all prior sessions, so the only live session post-request is the one minted at signin, and the AC4 guard is status-driven + fail-closed (BR-4.5). Recommendation (non-blocking): have the signin success-path carry the `pending_deletion` status in the minted token/claim so the guard does not depend solely on a `GET /v1/account/deletion` round-trip. The literal `rest-api-spec.md:161` gloss ("拒绝登录") must be reconciled — see Major #1.

- **OQ-2 (cancel re-auth asymmetry) — RATIFIED.** The asymmetry is correct and intentional. Re-auth-before-destructive (OWASP ASVS L2 V8.3) applies to **deletion** (irreversible); **cancellation** is restorative, grants no new privilege, and is already gated by a successful signin (AC4) to reach the recovery page. Requiring a fresh credential to cancel would risk a recovery deadlock (a user who forgot their password mid-grace could otherwise never rescue the account) — the data-preservation default is the safer posture. Keep BR-3.4 as written.

- **OQ-3 (financial-data disposition) — RATIFIED WITH OVERRIDE.**
  - **RETAIN-linked** for `recharge_orders` / `subscriptions` / `invoices` — legal/tax/audit retention obligation; figures frozen (Story 7.7 BR-I-2); they carry no PII beyond `user_id`, which now points at the anonymized row. The story's default is correct.
  - **OVERRIDE for `payment_methods`.** This table holds `provider_pm_token` — an opaque but **off-session-chargeable** Stripe PaymentMethod id (Story 7.7 / 0011). Retaining a live chargeable instrument for a deleted account is a financial-security risk. The sweeper (AC6) MUST, for each due user: (1) call the Stripe **PaymentMethod detach** API for every `payment_methods` row, then (2) DELETE the rows (or null the token + retain only `brand`/`last4` if a display-history requirement is later established — but the live token MUST go). Billing history is preserved independently by `invoices`. **This is an AC6 scope addition** (a new sweeper step + a cross-store side-effect outside the per-user PG txn, reconciled like the CH/OSS steps via BR-6.6) — fold into AC6/T6 (see Major #2).
