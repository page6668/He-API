- Regression-update existing tests asserting `error.he_request_id == nil` (`apps/api-gateway/internal/handlers/chat_completions_test.go:273-274,446-447,856` + `apps/api-gateway/internal/middleware/bearer_auth_test.go:136-137`) — flip assertions to "matches the `X-He-Request-Id` response header value AND matches the regex `^req_[a-f0-9]{12}$`".

### AC1: Standardized OpenAI-Compatible Error Envelope on Every Error Response

**Scenario**
```gherkin
GIVEN the api-gateway is built with Story 3.6 wired
AND the new shared package `apps/api-gateway/internal/openaierr/` is in place with its single exported writer `openaierr.Write(w, ctx, status, code, message, param)`

  - `POST /v1/auth/signup` (Story 2.2)
  - `GET /v1/auth/verify-email` (Story 2.2)
  - `POST /v1/auth/resend-verification` (Story 2.2)

  - `POST /v1/auth/refresh` (Story 2.2)
  - `GET /v1/auth/oauth/{google,github}/{initiate,callback}` (Story 2.3)
  - `POST /v1/auth/2fa/enroll/{init,verify}` / `POST /v1/auth/2fa/challenge` / `POST /v1/auth/2fa/recovery-codes/{use,regenerate}` / `POST /v1/auth/2fa/disable` (Story 2.4)
  - `GET /v1/me` / `PUT /v1/me/profile` (Story 2.5)
  - `POST /v1/account/data-export` / `GET /v1/account/data-export/current` (Story 2.6)
  - `POST /v1/chat/completions` (Stories 3.3 / 3.4 — non-stream AND SSE)

THEN
  - the response status matches the canonical mapping in `rest-api-spec.md §5.1.2` (e.g., `401_invalid_api_key` → 401, `413_payload_too_large` → 413, `500_gateway_misconfigured` → 500)
```

### AC2: he_request_id Propagation — Header + Body + Trace Correlation

**Scenario**
```gherkin
GIVEN the api-gateway is built with Story 3.6 wired
AND the new middleware `apps/api-gateway/internal/middleware/requestid.go` is in the user-traffic chain as the OUTERMOST wrap (before SecurityHeaders + CSRF + per-route bearerAuth/JWT)
AND the probeMux (`/health`, `/healthz`) BYPASSES this middleware (Story 3.1 BR-1.3 precedent — `rootMux.Handle("/health", probeMux)` dispatches BEFORE the `handler` chain)
WHEN ANY request lands on a /v1/* or /v1/auth/* or /v1/me* or /v1/account/* route
THEN
  - the response carries `X-He-Request-Id: req_<12 hex>` header on EVERY response — success (200/201/204) AND error (4xx/5xx)
  - the header value matches `^req_[a-f0-9]{12}$` (12 lowercase hex chars after `req_` prefix)
  - the same value is accessible in the request context via `requestid.FromContext(ctx) (string, bool)` — `ok=true` for any /v1/* request, `ok=false` for probe routes (defensive — handlers SHOULD NOT call `FromContext` from probe handlers)
  - the same value appears in the `error.he_request_id` field of EVERY 4xx/5xx error body emitted via `openaierr.Write` (AC1 enforces the field; AC2 enforces the equality)
  - the same value appears as an OTel span attribute `he.request_id` (via `span.SetAttributes(attribute.String("he.request_id", reqID))` inside the RequestID middleware) — this lets customer-support staff resolve a user-reported `he_request_id` to the underlying Jaeger trace WITHOUT round-tripping through a separate ID map
  - the same value appears in EVERY slog log record emitted under this request (already handled by `obs.TraceContextHandler` — slog's `trace_id` / `span_id` fields are already populated; Story 3.6 ADDS the `he_request_id` field via `slog.SetDefault` wrapping, OR via the per-call-site `slog.String("he_request_id", reqID)` discipline — OQ5 below; SM lean: wrap once at middleware, NOT every call-site)
WHEN the SAME request reaches a downstream gRPC call (e.g., `bearerAuth.RequireAPIKey` calling `authSvcClient.ValidateApiKey(...)`)
THEN
  - the `he_request_id` value flows through to the downstream service via the OTel-propagated trace context (the OTel span attribute travels via W3C `traceparent` header — auth-svc / notification-svc CAN extract `he.request_id` from the current span attributes if/when they need to log it; this is NOT a synchronous gateway responsibility — Story 3.6 only guarantees the gateway-side stamping)
WHEN a client supplies an inbound `X-Request-Id` or `X-He-Request-Id` header on the REQUEST
THEN
  - the gateway IGNORES the inbound value (BR-2.5 — anti-spoofing) and generates a fresh `he_request_id` server-side
  - the inbound header is NOT logged or echoed
WHEN the OTel SpanContext is INVALID (e.g., the request bypassed `obs.WrapHTTPHandler` in a unit test, or the tracer is not yet initialized — defensive only; production always has a valid span)
THEN
  - the middleware falls back to `crypto/rand` to generate 6 random bytes → hex-encoded → `req_<12 hex>` (BR-2.4)
  - the fallback path is exercised by a dedicated unit test (3.6-UNIT-007)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | Public API surface of `middleware/requestid.go`: (i) exported func `RequestID(next http.Handler) http.Handler` — the middleware constructor (parameterless to match `SecurityHeaders` + `CSRF`'s functional shape); (ii) exported func `FromContext(ctx context.Context) (string, bool)` — context accessor (returns `("", false)` if no value stamped); (iii) UNEXPORTED context key (`type requestIDKey struct{}` — Go idiom: empty struct types avoid string-key collisions, mirrors `context.WithValue` discipline). NO `WithRequestID(ctx, id)` exported — the middleware is the only writer; tests use `context.WithValue(ctx, requestIDKey{}, id)` via a package-internal `setForTest(ctx, id)` helper exposed only in `requestid_test.go`. |
| BR-2.2 | The request-ID format is `req_<12 lowercase hex>` — 16 chars total, 6 bytes of entropy (48 bits → collision probability ~10⁻⁷ at 10K requests/sec for 10 minutes, acceptable for human-facing correlation; full trace_id is preserved in OTel for forensic uniqueness). The prefix `req_` is a fixed literal — matches the `rest-api-spec.md §5.1.1` line 45 documented format `req_xxxxxxxxxxxx`. NO alternative formats (e.g., `req-` with hyphen, UUID v4) are permitted — the format is locked by §5.1.1 ratification. |
| BR-2.3 | The derivation rule: ✅ **RATIFIED (Architect Round 1 — OQ1 APPROVED)** — the request-ID is derived from the OTel SpanContext's TraceID. Rationale: (a) deterministic with the trace — no separate ID generation, no risk of header-vs-log mismatch; (b) zero allocation on the hot path (TraceID is already in context); (c) the truncation to 6 bytes is one-way → an attacker observing a `he_request_id` cannot reconstruct the full TraceID (defence-in-depth against trace-context leakage via support-channel screenshots). | Handler calls `FromContext(ctx)` on a probe route (no request-id stamped) | (no error envelope — defensive) | (n/a) | Return `("", false)` — handler SHOULD NOT call FromContext on probes; if it does, it gets a clear zero-value signal to fall back |
| Inbound `X-Request-Id` header present (anti-spoofing) | (no error — silent ignore per BR-2.5) | (n/a) | Discard the inbound value; do NOT log (logging would create a side-channel where an attacker confirms IDs were ignored) |

- Successful `/v1/chat/completions` request (non-stream):

- Probe route bypass:

  ```go
  type requestIDKey struct{}

  func RequestID(next http.Handler) http.Handler {
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          ctx := r.Context()
          reqID := deriveRequestID(ctx)
          w.Header().Set("X-He-Request-Id", reqID)
          ctx = context.WithValue(ctx, requestIDKey{}, reqID)
          if span := trace.SpanFromContext(ctx); span.SpanContext().IsValid() {
              span.SetAttributes(attribute.String("he.request_id", reqID))
          }
          next.ServeHTTP(w, r.WithContext(ctx))
      })
  }

  func FromContext(ctx context.Context) (string, bool) {
      v, ok := ctx.Value(requestIDKey{}).(string)
      return v, ok
  }

  func deriveRequestID(ctx context.Context) string {
      if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
          tid := sc.TraceID()
          return "req_" + hex.EncodeToString(tid[0:6])
      }
      var buf [6]byte
      if _, err := rand.Read(buf[:]); err != nil {
          return "req_000000000000"
      }
      return "req_" + hex.EncodeToString(buf[:])
  }
  ```

### Open Questions for Architect (Round 1)

> Story 3.6 had 6 open questions; ALL SIX were ratified by Architect Round 1 (2026-05-19). The OQ entries below are retained as design-record context — each is closed.

- **OQ1 — `he_request_id` derivation rule** (BR-2.3): ✅ **RATIFIED (Architect Round 1 — APPROVED)** — `req_ + hex(TraceID[0:6])` — 6 bytes from the W3C TraceID, hex-encoded. Architect rationale: preserves §5.1.1 documented 12-char format; zero alloc; deterministic with trace; 1-way truncation defends against support-screenshot leakage. Alternatives considered: (a) full 16-byte TraceID hex (32-char tail) — breaks documented format; (b) UUID v4 independent of TraceID — loses 1:1 trace correlation; (c) `req_<timestamp>_<rand>` like Sentry's Event ID — readable but loses determinism.
- **OQ2 — Field order in marshalled JSON envelope** (BR-1.7): ✅ **RATIFIED (Architect Round 1 — APPROVED)** — the §5.1.2-documented canonical order `code` → `message` → `type` → `param` → `he_request_id` via struct-based marshalling (NOT `map[string]any` which alphabetically sorts to `code` → `he_request_id` → `message` → `param` → `type`). Architect rationale: map alphabetical-sort would break byte-exact golden-file tests (Story 3.5 precedent); struct-based marshalling is the right answer.
- **OQ3 — `openaierr.Write` return type**: ✅ **RATIFIED (Architect Round 1 — APPROVED)** — `func Write(...) error` — returns marshal/write errors so callers can log on failure (defensive; the marshal-fail path is unreachable for the canonical taxonomy but exists for telemetry hooks). Alternative considered: `func Write(...)` (no return; matches `http.Error` + `chat_completions.writeChatError` precedent — they discard write errors). Architect Round 1 confirmed: with-return is the defensive ergonomic choice — Story 9.x observability has a clean attachment slot on the return value.
- **OQ4 — Debug `details` field**: ✅ **RATIFIED (Architect Round 1 — CONFIRMED: do NOT add `details`)** — `openaierr.Write` does NOT expose a `details *string` 6th parameter (env-gated or otherwise). Architect Round 1 rationale: (i) OpenAI's error envelope is a 5-field contract; env-gated 6th fields drift from the SDK's `extra="allow"` discipline + risk leaking into production via misconfigured env vars; (ii) internal debugging belongs in slog + Jaeger (the trace already carries the full error context); (iii) callers MUST NOT leak attacker-controlled fields into `error.message` (BR-1.10 inheritance) — adding `details` increases the attack surface for accidental PII leakage. Closed; no further action.
- **OQ5 — slog `he_request_id` injection**: ✅ **RATIFIED (Architect Round 1 — APPROVED)** — `WithRequestIDExtractor` option on `obs.NewLogger` (BR-2.10) — auto-inject via the handler chain, no per-call-site discipline. Architect rationale: avoids the per-call-site discipline burden; `packages/go-observability/logger.go` `TraceContextHandler` is the correct seam (verified existing per-record `r.AddAttrs(...)` pattern). Alternative considered: document the per-call-site `slog.String("he_request_id", reqID)` discipline (lower coupling, but Story 3.5 BR-1.8 already documents the call-site burden as fragile).
- **OQ6 — `requestid` package home** (T2.1): ✅ **RATIFIED (Architect Round 1 — APPROVED)** — `apps/api-gateway/internal/middleware/requestid/` (subpackage form). Architect rationale: cleaner dependency graph — `openaierr → middleware/requestid` (leaf package) without pulling in `bearer_auth.go` / `jwt_verify.go` / `csrf.go`. Alternative considered: flat `apps/api-gateway/internal/middleware/requestid.go` (Go's import-cycle detector would accept it, but pulls more deps).
