  question: "Which Coinbase charge lifecycle events trigger the balance credit?"
  sm_default: "Credit ONLY on charge:confirmed (blockchain-confirmed — final). charge:pending (payment detected on-chain, awaiting confirmations) → 200 ACK, NO credit (EventUnhandled). charge:created → 200 ACK no-op. charge:failed (expired without sufficient payment / cancelled) → recharge_orders.status='failed', NO credit. charge:delayed (paid late / underpaid) → park (NO auto-credit). charge:resolved (merchant-resolved delayed charge) → DEFER (manual reconciliation, Q-UNDERPAY)."

### AC1: 充值地址生成 — create a Coinbase Commerce USDC charge → hosted_url + deposit address (用户可生成充值地址)

**Scenario**
```gherkin
GIVEN
  - a logged-in user U (JWT-cookie or bearer) with a he_api.balances row (or lazily-absent → treated as 0, 7.1 BR-A-2)
  - payment-svc is wired with the coinbase PaymentProvider impl (COINBASE_COMMERCE_API_KEY set → registry has "coinbase")
  - "coinbase" is in the gateway supportedProviders map (billing_write.go:46)
  - he_api.recharge_orders exists (migration 0010, REUSED); USD is the single accounting SoT (7.1/7.2 Q-SOT); USDC ≈ USD 1:1
WHEN
  - U calls POST /v1/billing/recharge {amount:"50.00", currency:"USD", provider:"coinbase"}
THEN
  - **create-order**: a PENDING recharge_orders row is written (via the existing billing-svc CreateRechargeOrder gRPC — UNCHANGED) {id, user_id:U, amount:50.0000, currency:'USD', payment_provider:'coinbase', external_order_id:<coinbase charge id/code>, status:'pending', paid_at:NULL}
  - **create-charge**: coinbase.CreateCheckout calls Coinbase Commerce `POST /charges` {name, pricing_type:"fixed_price", local_price:{amount:"50.00", currency:"USD"}, metadata:{order_id:<our id>, user_id:U}} with X-CC-Api-Key + X-CC-Version; the charge id is stored as external_order_id (Idempotency: our order id in metadata binds the charge to our row — BR-R-4 cascade)
  - **response**: 200 {order_id, checkout_url:"https://commerce.coinbase.com/charges/<code>", provider:"coinbase", usdc_address:<charge.addresses.usdc, Q-ADDRESS>} — money fields string-decimal (Q-Spec-4); the hosted_url is the primary path, the USDC address is informational (feeds the eventual Console QR flow, front-end-spec §3.3)
  - **observable**: Prometheus he_payment_recharge_total{provider="coinbase",result="created"}; non-PII slog payment_order_created{order_id, user_id, provider:"coinbase"} (NO secret, NO address PII beyond the charge id)
  - **seam parity**: this flows through the SAME POST /v1/billing/recharge handler + the SAME CreateCheckout seam as stripe/paypal — only coinbase.CreateCheckout's body differs (BR-A-1)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-A-1 | The recharge handler is PROVIDER-AGNOSTIC (REUSED from 7.3). Adding coinbase = a new `PaymentProvider` impl + a `supportedProviders` map entry; the handler, the gRPC order create, and the response shape are UNCHANGED. No coinbase special-casing in the handler. |
| BR-A-2 | The CREATE-ORDER amount is the user INTENT (display); the CREDITED amount is the provider-confirmed on-chain settled value (AC2, BR-R-1 cascade). recharge_orders.amount records the intent. |
| BR-A-3 | The Coinbase charge carries OUR order id + user id as `metadata` (server-side, from the authenticated session — NOT client-supplied). The webhook (AC2/AC3) resolves the user via OUR order id, never a client-asserted user_id (anti cross-user binding, 7.3 BR-R-4 cascade). |
| BR-A-4 | All money fields on the response are string-decimals (`"50.00"`) — Q-Spec-4 / 7.1 BR-A-3 cascade. The USDC address (Q-ADDRESS) is an opaque string, not a money field. |
| BR-A-5 | USDC ≈ USD: a `currency:"USD"` charge credits balances.current_usd 1:1 (toUSD() pass-through, REUSED). The channel is USDC-only (Q-COINS); the Commerce account enables USDC. |
| BR-A-6 | provider string = `"coinbase"` (the INTEGRATION, mirroring `stripe`/`paypal`); the recharge_orders.payment_provider VARCHAR(50) accepts it with NO schema change (0010_*.sql:42). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| amount | string-decimal | yes | parses to NUMERIC(12,4); `> 0`; ≤ sane ceiling | `400_invalid_payment_request` (REUSED) |
| currency | string | yes | ∈ enabled set (MVP {USD}; USDC settles in USD-equiv) | `400_unsupported_currency` (REUSED, 7.2) |

|----------|-------------|

### AC2: 链上确认入账 — charge:confirmed → exactly-once balance credit (链上确认后自动到账)

**Scenario**
```gherkin
GIVEN
  - a PENDING recharge_orders row for user U {payment_provider:'coinbase', external_order_id:<charge id>, amount:50.0000, status:'pending'} (from AC1)
  - the user has paid the Coinbase Commerce charge in USDC; Coinbase will POST signed lifecycle webhooks to POST /v1/billing/webhooks/coinbase
  - the inherited exactly-once credit machinery (recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id) + the provider-agnostic billing-svc credit applier) is REUSED unchanged
WHEN
  - Coinbase POSTs a signed webhook (charge:created | charge:pending | charge:confirmed | charge:failed | charge:delayed) to POST /v1/billing/webhooks/coinbase
THEN
  - **charge:confirmed (blockchain-confirmed → CREDIT)**: coinbase.VerifyWebhook (AC3) verifies the signature → returns a VerifiedEvent {Kind:EventRechargePaid, OrderID:<our id from metadata>, ExternalOrderID:<charge id>, SettledAmount:"50.00" (provider on-chain TRUTH), Currency:'USD', Status:'paid'}; the webhook handler emits the SAME he.payment.v1 payment.completed PaymentEvent (UNCHANGED producer); billing-svc's provider-agnostic credit applier consumes it and, in ONE PG transaction: (1) `UPDATE recharge_orders SET status='paid', paid_at=NOW() WHERE id=$order AND status='pending'` → zero rows (redelivery) ⇒ skip; (2) else verify settled==intent (BR-R-1 guard) then `UPDATE balances SET current_usd = current_usd + settled, updated_at=NOW() WHERE user_id=U` (UPSERT zero row if absent); (3) COMMIT
  - **post-commit (best-effort, INHERITED)**: INCRBYFLOAT balance:user:U:realtime by settled; a Redis failure logs + alerts but the durable PG credit stands
  - **charge:pending (on-chain seen, UNCONFIRMED → NO CREDIT)**: VerifyWebhook returns Kind:EventUnhandled (or a pending marker); the handler 200-ACKs; NO balance change; recharge_orders stays 'pending'
  - **charge:created → 200 ACK, no-op**
  - **charge:failed (expired / cancelled → NO CREDIT)**: Kind:EventRechargeFailed → recharge_orders.status='failed'; NO credit; 200 ACK
  - **charge:delayed / underpaid (settled<intent → PARK)**: the inherited amount-integrity guard (settled≠intent → stay pending + alert + NO credit, BR-R-1) parks it; 200 ACK (don't make Coinbase retry a verified event)
  - **observable**: GET /v1/balance reflects the +50.00 credit after charge:confirmed (reads PG authoritative); Prometheus he_payment_credit_amount_usd{provider="coinbase"} histogram; slog payment_credit{order_id, user_id, provider:"coinbase", settled_amount}
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-C-1 | **Credit fires ONLY on charge:confirmed** (blockchain-confirmed = Coinbase finality; reorg risk is Coinbase's). charge:pending (unconfirmed) NEVER credits — crediting unconfirmed funds risks crediting a payment that never lands (Q-CONFIRM). |
| BR-C-2 | **Exactly-once credit is INHERITED** (the 7.3 recharge_orders pending→paid state-machine + UNIQUE(payment_provider, external_order_id)). A redelivered charge:confirmed finds status='paid' → zero-row UPDATE → no second credit. The UNIQUE key is per-provider so a Coinbase charge id never collides with a stripe/paypal id. |
| BR-C-3 | **The credited amount is the provider-confirmed on-chain settled value** (BR-R-1 cascade), NEVER the create-order intent. A settled≠intent (underpayment) → park + alert + NO credit. USDC≈USD + Coinbase's price-lock window means a within-window full payment settles ≈ exactly = intent. |
| BR-C-4 | **USD single SoT** (7.2 Q-SOT, INHERITED): USDC credits balances.current_usd via toUSD() pass-through (currency='USD'); current_rmb stays reserved/0. The credit applier is UNCHANGED. |
| BR-C-5 | **The credit applier + producer + consumer are REUSED VERBATIM** — coinbase emits the SAME PaymentEvent; no coinbase-specific code exists downstream of VerifyWebhook. Any coinbase special-casing leaking into credit.go is a design regression (BR-A-1 cascade). |
| BR-C-6 | **Crypto is irreversible** — there is no refund/chargeback path for USDC (contrast Stripe). A confirmed credit is final; charge:resolved manual handling for delayed/underpaid is DEFERRED (Q-UNDERPAY). |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| charge:confirmed, signature valid, pending order | verify settled==intent → pending→paid + credit (one tx); 200 ACK |
| charge:confirmed redelivered (already paid) | zero-row UPDATE → no second credit; 200 ACK (BR-C-2) |
| charge:pending | 200 ACK; NO credit; order stays pending (BR-C-1) |
| charge:failed | recharge_orders.status='failed'; NO credit; 200 ACK |
| charge:delayed / settled<intent | park + alert; NO credit; 200 ACK (BR-C-3) |
| verified but PG down on apply | 5xx; do NOT ACK; Coinbase redelivers (inherited at-least-once + idempotent) |

**Examples**
- **Input**: pending order $50 → charge:confirmed (settled 50.00 USDC) → settled==intent → pending→paid + balance +50.0000; GET /v1/balance → `{"current_usd":"50.0000",...}`. ✅ auto-credited on confirmation.
- **Input**: the SAME charge:confirmed redelivered → already 'paid' → zero-row UPDATE → no second credit; balance stays 50.0000. ✅ exactly-once.
- **Input**: charge:pending (payment seen, 0 confirmations) → 200 ACK, balance unchanged, order still 'pending'. ✅ no premature credit.
- **Input**: charge:confirmed but settled 49.50 (underpaid) → park + alert + NO credit; order stays 'pending'. ✅ amount-integrity holds.

### AC3: Coinbase webhook 安全 — X-CC-Webhook-Signature verification + inherited exactly-once backbone (安全)

**Scenario**
```gherkin
GIVEN
  - POST /v1/billing/webhooks/coinbase is mounted OUTSIDE the bearer/JWT chain (4.7 /public/* precedent, REUSED) — the Coinbase signature is the sole credential
  - COINBASE_COMMERCE_WEBHOOK_SECRET is configured (Q-SDK); raw-body integrity is preserved end-to-end (the gateway forwards the EXACT bytes, REUSED billing_webhook.go pass-through)
  - the recharge_orders state-machine + UNIQUE fence carry the inherited idempotency (AC2 BR-C-2)
WHEN
  - a webhook POST arrives (genuine, forged, replayed, or amount-tampered)
THEN
  - **genuine (valid signature)**: coinbase.VerifyWebhook computes hex(HMAC-SHA256(rawBody, COINBASE_COMMERCE_WEBHOOK_SECRET)) and constant-time-compares it to the `X-CC-Webhook-Signature` header → match → parse the charge event → map the lifecycle to a VerifiedEvent Kind (AC2) → process; return 2xx promptly
  - **forged (invalid/absent/tampered signature)**: VerifyWebhook returns provider.ErrSignatureInvalid → the handler maps it to `400_webhook_signature_invalid` BEFORE parsing the body into any money action; NO credit; slog payment_webhook_rejected{provider:"coinbase", reason:"signature"} + metric; the body is NEVER trusted
  - **replayed (a captured VALID charge:confirmed re-POSTed)**: ⚠️ the Coinbase signature has NO timestamp segment → NO freshness window → the signature alone CANNOT detect replay; the inherited recharge_orders pending→paid state-machine makes a replayed confirmed event a no-op credit (zero-row UPDATE) — the state-machine is the SOLE replay fence for Coinbase (defence-in-depth degrades to one layer, AC2 BR-C-2)
  - **exactly-once credit (INHERITED)**: credit applies ONLY on a pending→paid transition; already-paid ⇒ zero rows ⇒ 200 ACK + skip; status-flip + credit are ONE PG tx (atomic); UNIQUE(payment_provider, external_order_id) prevents two orders binding one charge
  - **amount integrity (INHERITED)**: the credited amount is the provider-verified on-chain settled value; settled≠intent → park + alert + NO credit
  - **PCI / no-card**: the Coinbase webhook payload carries crypto amounts + charge ids — NEVER a card PAN (crypto has no card; stronger than the SAQ-A boundary); we persist the charge id + our order id only
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-W-1 | **Signature verification is MANDATORY and happens BEFORE any body processing** (INHERITED, BR-W-1 from 7.3). An unverified Coinbase webhook body is NEVER parsed into a credit. The signature is the credential (the route is otherwise unauthenticated). |
| BR-W-2 | **Coinbase signature scheme** (NEW): `X-CC-Webhook-Signature` = lowercase-hex `HMAC-SHA256(rawBody, COINBASE_COMMERCE_WEBHOOK_SECRET)`; verify with a CONSTANT-TIME compare (`hmac.Equal`) over the EXACT raw bytes. ⚠️ NO timestamp segment (unlike Stripe's `t=...,v1=...`) → no freshness/tolerance check is possible. |
| BR-W-3 | **Raw-body integrity** (INHERITED, BR-W-2 from 7.3): HMAC needs the EXACT raw bytes Coinbase signed; no middleware (gateway proxy included) may re-serialize/normalize the body before verification. The gateway billing_webhook.go pass-through is REUSED. |
| BR-W-4 | **Replay defence = state-machine ONLY** (⚠️ DIFFERS from 7.3): because the Coinbase signature has no timestamp, there is NO signature-freshness layer; a replayed VALID confirmed event is made harmless SOLELY by the recharge_orders pending→paid idempotency. This MUST be a P0 test lane. |
| BR-W-5 | **Provider 2xx discipline** (INHERITED, BR-W-5 from 7.3): verified + already-processed → 200 (so Coinbase stops retrying); verification FAILURE → 400; transient processing error (PG down) → 5xx so Coinbase redelivers (at-least-once + idempotent). |
| BR-W-6 | **Secrets** (Q-SDK): COINBASE_COMMERCE_WEBHOOK_SECRET (signature) is DISTINCT from COINBASE_COMMERCE_API_KEY (charge-create auth); both env-injected; NEVER logged (the 7.3/7.2 secret discipline cascade). |
| BR-W-7 | **No card data / crypto no-PAN** (§8.4): the payload carries charge ids + crypto amounts only — never a PAN; we persist the charge id + order id. Stronger than the card SAQ-A boundary (no card exists). |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Invalid / absent / tampered X-CC-Webhook-Signature | 400 | `400_webhook_signature_invalid` — "Webhook signature verification failed." | reject before body processing (BR-W-1); slog + metric (REUSED code) |
| Verified but already-processed (redelivery / replay) | 200 | — | ACK + skip; no second credit (BR-W-4/W-5) |
| Verified but PG down on apply | 5xx | — | do NOT ACK; Coinbase redelivers (BR-W-5) |
| Verified charge:pending / charge:created | 200 | — | ACK; no-op, no credit (AC2 BR-C-1) |
| Verified but settled ≠ order intent | 200 | — | ACK (verified event) but park + alert + NO credit (BR-W / Q-AMOUNT cascade) |

**Examples**
- **Input**: forged POST with a bogus X-CC-Webhook-Signature → `400_webhook_signature_invalid`; no recharge_orders touched; no credit. ✅ forgery blocked.
- **Input**: genuine charge:confirmed for a pending order → verified → pending→paid + credit (one tx). Redelivered (or replayed) → already-paid → 200 ACK, no second credit. ✅ exactly-once (state-machine is the sole replay fence — BR-W-4).
- **Input**: a captured valid charge:confirmed replayed 1h later → signature STILL valid (no timestamp) → BUT order already 'paid' → zero-row UPDATE → no credit. ✅ replay neutralised by the state-machine.

### Technical Constraints
- **Additive-only on a proven seam** — implement `coinbase.Provider` against the EXISTING `PaymentProvider` interface (`apps/payment-svc/internal/provider/provider.go:86-97`); wire it in `buildRegistry` (`cmd/server/main.go` ~149-175); add `"coinbase"` to `supportedProviders` (`apps/api-gateway/internal/handlers/billing_write.go:46`); mount the webhook route. Do NOT touch the producer, the credit applier, recharge_orders, the proto, or the Kafka topic. [→ provider.go:2-6]
- **Coinbase signature scheme** (the one genuinely-new security primitive) — `X-CC-Webhook-Signature` = lowercase-hex `HMAC-SHA256(rawBody, COINBASE_COMMERCE_WEBHOOK_SECRET)`; verify with `hmac.Equal` (constant-time) over the EXACT raw bytes BEFORE parsing (BR-W-1/W-2). ⚠️ NO timestamp segment → no replay-freshness window → replay defence is the inherited recharge_orders state-machine ALONE (BR-W-4). [→ AC3]
- **Credit on charge:confirmed ONLY** (Q-CONFIRM) — `charge:confirmed` → EventRechargePaid (credit); `charge:pending`/`charge:created` → EventUnhandled (200 ACK, no credit — unconfirmed on-chain funds are not money yet); `charge:failed` → EventRechargeFailed; `charge:delayed`/underpaid → park via the inherited amount-integrity guard. [→ AC2 BR-C-1]
- **Provider-confirmed amount, never intent** (BR-R-1 cascade, INHERITED) — SettledAmount in the VerifiedEvent is the on-chain confirmed value; the billing-svc applier already parks settled≠intent. Do NOT credit the create-order intent. [→ AC2 BR-C-3]
- **USDC ≈ USD** — charge created with `local_price.currency:"USD"`; settled currency='USD' → toUSD() pass-through 1:1 (REUSED, no fx). The credit lands in `balances.current_usd`; current_rmb stays reserved/0 (7.2 Q-SOT). [→ AC2 BR-C-4]
- **No card / crypto irreversible** — crypto has no PAN (no-PAN trivially holds, §8.4) and no refund/chargeback (a confirmed credit is final). [→ AC3 BR-W-7, AC2 BR-C-6]
- **Money + amount fields are string-decimals** — never JSON numbers (Q-Spec-4 / 7.1 BR-A-3). [→ docs/architecture/data-models.md §4.5]
- **Decimal, never float** — `shopspring/decimal`, HALF-UP; already in payment-svc/billing-svc go.mod (REUSED). [→ 7.1 Architect M-1]
- **New deps respect workspace otel pins** — `go get pkg@ver`, do NOT re-tidy the workspace. [[project_otel_version_pin_gotcha]]
