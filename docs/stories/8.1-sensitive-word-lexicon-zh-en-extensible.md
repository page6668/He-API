## Story

**As a** the He-API content-safety subsystem (and the platform operators preparing the 生成式 AI 服务备案),
**I want** a version-controlled, extensible Chinese + English sensitive-word lexicon (≥1000 中文 + ≥500 英文) exposed as a pure, fast-lookup Go library with per-term category + severity metadata,
**so that** Story 8.2 (入参过滤) and Story 8.3 (出参过滤) can match against a single source of truth, Story 8.4 (严格度配置) can map severity onto per-Key strictness, and Story 8.5 (治理日志) can record `matched_rule` for 备案 audit logs — all without re-implementing or forking the wordlist.

## Epic Context
**Epic**: 8 - 内容安全与合规准备
双向敏感词过滤 + 治理日志 + 备案材料归档。

**Epic DoD**: 入参/出参敏感词过滤上线 · 严格度可按 Key 配置 · 备案材料 PDF 模板生成。

**Story 8.1 Deliverables** (the FOUNDATION layer of the Epic — data + library only, NO request/response wiring):
- A new `packages/safety-lexicon/` Go SoT package holding the built-in ≥1000 中文 + ≥500 英文 term corpus.
- A pure, concurrent-safe matching API (Bloom prefilter + authoritative exact-match lookup) with per-term `{category, severity, canonical}` metadata.
- Construction-time invariant enforcement (count floors, closed enums, no duplicates) — panic-at-construction, mirroring `packages/models-catalogue` + `packages/plan-catalogue`.
- An extensibility mechanism: add/remove terms by editing embedded data files, no code change.
- A CI integrity guard (parse + floor + dedupe + determinism).

> **Scope boundary (explicit)**: Story 8.1 ships the lexicon **library and data only**. Tokenizing/scanning request or response text, returning the `400 content_filter` envelope, streaming-window detection, per-Key strictness config, and `content_safety_logs` writes are **Stories 8.2 / 8.3 / 8.4 / 8.5** and are NOT in this story. The consumers of this library are those future stories; 8.1 binds via package-init self-construction + its own test suite (the established catalogue precedent).

## Acceptance Criteria

### AC1: 内置词库覆盖与分类 (Built-in coverage & taxonomy)

**Scenario**
```gherkin
GIVEN the safety-lexicon package built at process init from its embedded category data files
WHEN DefaultLexicon is constructed
THEN
  - it contains ≥ 1000 distinct 中文 (Chinese) terms AND ≥ 500 distinct 英文 (English) terms (post-normalization, deduplicated)
  - every term carries EXACTLY ONE category from the closed set {political, pornographic, violence_terror, contraband, abuse, other}
  - every term carries EXACTLY ONE severity from the closed set {high, medium, low}
  - the term→metadata mapping is 1:1 (no term without metadata, no metadata orphan) and is enforced at construction
  - Lexicon.Len() returns the total term count and Lexicon.CountByLang() reports zh/en counts so the floor is a testable surface
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | Count floors are HARD: zh ≥ 1000, en ≥ 500. A build below either floor is a build-time programming error → panic at construction (NOT a runtime condition), mirroring the `plancatalogue.NewFromRegistry` / `modelscatalogue.NewFromRegistry` panic-at-construction precedent. |
| BR-1.2 | `category` is a closed Go enum; an unknown category token in the data → panic at construction. The 6-value set is the §9.3 governance taxonomy proposal (Architect-confirmable, OQ-8.1-5). |
| BR-1.3 | `severity` is a closed Go enum {high, medium, low}; an unknown severity token → panic at construction. Severity is the field Story 8.4 maps onto per-Key strictness (loose / default / strict). |
| BR-1.4 | The severity→strictness PRE-STAGE mapping is RESERVED for Story 8.4 and is NOT enforced or applied in 8.1. 8.1 only guarantees every term is severity-tagged. The intended (8.4-confirmable) mapping: `loose`=block high only; `default`=block high+medium; `strict`=block all three. |
| BR-1.5 | Language (`zh`/`en`) is derived deterministically from the source data file's language directory, NOT auto-detected from term content — this keeps the floor count auditable and avoids misclassifying loanwords. |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| zh count < 1000 OR en count < 500 at build | panic | `safetylexicon: zh term floor not met (got N, need 1000)` | Fail process start; CI integrity guard (AC4) catches it before merge |
| Unknown category/severity token in data | panic | `safetylexicon: unknown category "<tok>" at <file>:<line>` | Fail process start; reject the data edit |

**Examples**
- **Input**: `DefaultLexicon.CountByLang()`
  **Expected**: `{zh: ≥1000, en: ≥500}`; `DefaultLexicon.Lookup(<a known political term>)` → `{category: political, severity: high, canonical: <normalized term>}, true`

### AC2: 可扩展性 + 规范化 + 构造期校验 (Extensibility + normalization + construction validation)

**Scenario**
```gherkin
GIVEN an operator adds, edits, or removes a term line in an embedded category data file
WHEN the package is rebuilt
THEN
  - the change takes effect with NO code change beyond the data file edit (file is //go:embed-ed)
  - each raw term is normalized on load: Unicode NFKC fold + ASCII case-fold + strip surrounding whitespace + strip zero-width characters (U+200B/C/D, U+FEFF)
  - empty lines and `#`-prefixed comment lines are ignored (not counted, not stored)
  - a duplicate term (after normalization, detected ACROSS all categories AND languages) is rejected at construction (panic) — silent dedupe is forbidden so the corpus stays auditable
  - the resolved corpus is stored in a stable, sorted canonical order (determinism prerequisite for AC4)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | Extensibility mechanism = edit `packages/safety-lexicon/data/{zh,en}/<category>.txt` (one term per line). No registry-code edit, no recompile-of-logic required — only the embedded bytes change. This is the "可扩展" AC of the epic. |
| BR-2.2 | Normalization pipeline is fixed and ordered: NFKC → case-fold (ASCII; Chinese unaffected) → trim ASCII+Unicode whitespace → strip zero-width. The SAME normalization MUST be applied by consumers (8.2/8.3) to query inputs before `Lookup`; 8.1 exposes `Normalize(s string) string` as the canonical, shared entrypoint so the rule cannot drift between producer and consumer. |
| BR-2.3 | Cross-category duplicate detection is global: the same normalized term may NOT appear in two category files (a term has exactly one category, BR-1.2). Panic identifies both offending files+lines. |
| BR-2.4 | Comment (`#…`) and blank lines are first-class in data files (allow operators to annotate provenance/source per term-group for 备案 defensibility) and are excluded from counts. |
| BR-2.5 | Evasion handling scope: simplified⇄traditional Chinese folding is an OPEN decision (OQ-8.1-4). Leetspeak / pinyin substitution / homoglyph / symbol-insertion evasion is **explicitly OUT of 8.1** — that is the §9.3 model-classifier layer (pipeline layer 3), a later epic. 8.1 is the deterministic dictionary layer only. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| term (data line) | string | yes | non-empty after normalization; no embedded newline; ≤ 128 runes | `safetylexicon: invalid term at <file>:<line>` |
| category file name | enum | yes | stem ∈ closed category set | `safetylexicon: unknown category file <name>` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Same normalized term in two files | panic | `safetylexicon: duplicate term "<t>" (<fileA>:<lnA> & <fileB>:<lnB>)` | Reject build; operator removes one |
| Term normalizes to empty | panic | `safetylexicon: term at <file>:<line> normalizes to empty` | Reject build |

**Examples**
- **Input**: data line `  Ｂａｄ​Word  ` (full-width + trailing zero-width + surrounding spaces)
  **Expected**: normalized + stored as `badword`; `Lookup("BADWORD")` and `Lookup("ｂａｄword")` both resolve to the same canonical entry

### AC3: 匹配 API surface (Bloom prefilter + exact set + metadata)

**Scenario**
```gherkin
GIVEN the constructed DefaultLexicon
WHEN a consumer (Story 8.2 入参 / 8.3 出参) queries a candidate term
THEN the package exposes these pure, read-only methods:
  - MightContain(term string) bool — Bloom-filter fast-path (§9.3 pipeline layer 1: 98%+ non-hit exclusion); MAY false-positive, MUST NOT false-negative
  - Lookup(term string) (Match, bool) — authoritative exact membership; returns Match{Category, Severity, Canonical} for the matched_rule that Story 8.5 logs
  - Normalize(s string) string — the shared normalization entrypoint (BR-2.2)
  - Len() int / CountByLang() / Categories() []Category — introspection for tests + a future ops/stats surface
AND all methods are safe for concurrent reads (the structure is immutable after construction — no locks needed)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | `MightContain` is a probabilistic prefilter only. The contract is: `Lookup(t).ok == true ⇒ MightContain(t) == true` (no false-negative). A `MightContain==true / Lookup==false` outcome is an allowed Bloom false-positive — the consumer MUST confirm with `Lookup`. |
| BR-3.2 | `Lookup` internally normalizes its argument via `Normalize` (defence-in-depth) so a caller that forgets to pre-normalize still gets correct results; the doc directs hot-path callers to normalize once and reuse. |
| BR-3.3 | `Match.Canonical` is the normalized stored form (NOT the raw query) — this is the stable `matched_rule` value Story 8.5 persists to `content_safety_logs.matched_rule`, so audit logs are query-independent. |
| BR-3.4 | The package performs MEMBERSHIP only on whole normalized terms. Substring scanning / tokenization / sliding-window over free text is the consumer's job (8.2/8.3) — 8.1 deliberately does not own text segmentation (Chinese has no word boundaries; the segmentation strategy is an 8.2/8.3 design concern). |
| BR-3.5 | No I/O, no globals mutated after init, no `time`/`rand` in the hot path — pure functions over immutable state (mirrors the `models-catalogue` / `plan-catalogue` PURE-DOMAIN posture). |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Empty / whitespace-only query to Lookup | (none) | n/a | Returns `(Match{}, false)` — not an error; never panics on query input |
| Concurrent reads from N goroutines | (none) | n/a | Race-clean (verified under `-race`); no data race, no lock contention |

**Examples**
- **Input**: `MightContain("hello")` → likely `false` (fast exclusion); `MightContain(<known term>)` → `true`, then `Lookup(<known term>)` → `{category, severity, canonical}, true`
- **Input**: `Lookup("   ")` → `(Match{}, false)`

### AC4: 确定性、性能与 CI 完整性守卫 (Determinism, performance & CI integrity guard)

**Scenario**
```gherkin
GIVEN the embedded wordlist data files and the Bloom filter derived from them
WHEN CI runs the safety-lexicon test lane
THEN
  - construction is DETERMINISTIC: same data files → byte-identical resolved corpus order and an identical Bloom bit-set across runs/platforms (terms sorted before the Bloom is populated)
  - a CI integrity guard test asserts: data parses, count floors hold (AC1), zero duplicates (AC2), every category/severity token is in-enum
  - the Bloom false-positive rate is verified ≤ the configured bound (proposal: ≤ 1% at the realized term count) via a statistical test over a large miss-set
  - performance budgets hold on the benchmark: Lookup P99 and MightContain P99 are asserted under the documented ceilings (proposal: Lookup P99 < 2µs, MightContain P99 < 500ns — Architect/Dev-confirmable on the bench host)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | Determinism: terms are sorted (canonical byte order) before storage AND before Bloom population, so the Bloom bit-set is reproducible. No map-iteration order may leak into construction output. |
| BR-4.2 | The CI integrity guard runs in the standard Go test lane (`go test ./packages/safety-lexicon/...`) — no new CI infra. It is the safety-lexicon analogue of the existing `i18n-keys-completeness` / `buf generate` drift guards (precedent: source-tree.md Story 2.1 / 1.5). |
| BR-4.3 | Bloom sizing (m bits, k hashes) is chosen for the ≤1% FP bound at the realized corpus size and is documented in code; the FP bound is a TESTED invariant, not a comment. |
| BR-4.4 | Performance ceilings are soft-gated via benchmark assertions (`testing.B` + a threshold check, `t.Log` on the bench host variance) so they signal regression without being flaky on shared CI runners — mirrors the Story 4.7 `models_bench_test.go` < 5ms P95 soft-gate precedent. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| bloom_fp_rate | float | yes (test) | ≤ 0.01 over ≥ 100k random misses | `safetylexicon: bloom FP rate 0.0XX exceeds 0.01 bound` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Non-deterministic build detected | test FAIL | `corpus order / bloom bitset not reproducible` | Fix sort-before-populate; block merge |
| FP rate over bound | test FAIL | `bloom FP rate exceeds bound` | Resize Bloom (BR-4.3); block merge |

**Examples**
- **Input**: run `go test ./packages/safety-lexicon/...` twice
  **Expected**: identical pass; integrity guard green; bench thresholds met; FP-rate test green

## Dev Notes

### Technical Constraints

- **Canonical design source**: the content-safety pipeline is specified in `[Source: docs/architecture/9-合规架构compliance-architecture.md#9.3]`. The three input-filter layers are: (1) Bloom filter quick-exclude (98%+ traffic), (2) 词典匹配 / dictionary keyword match, (3) lightweight BERT classifier. **Story 8.1 builds the data + library underpinning layers (1) and (2) only.** Layer (3) (model classifier) and the actual filter wiring are later work.
- **SoT-as-code precedent (load-bearing)**: this package mirrors `[Source: packages/plan-catalogue/catalogue.go]` and `[Source: packages/models-catalogue/registry.go]` — a version-controlled CODE catalogue with **panic-at-construction** invariant enforcement, PURE-DOMAIN types (no JSON/proto/HTTP concerns), and a package-init `DefaultLexicon = NewFromRegistry(...)` self-binding. Rationale carries over verbatim: review + no per-pod drift + 境内-safe (the corpus is embedded in the binary, never fetched). [Source: packages/plan-catalogue/catalogue.go:1-23]
- **New-top-level-module precedent**: `packages/adapter-usage` established that a new sibling Go module under `packages/` is the accepted shape; replicate its `go.mod`/`go.work` wiring. [Source: docs/architecture/source-tree.md (Story 4.2 note, packages/adapter-usage)]
- **Compliance / data-residency**: the corpus and all matching are in-process and 境内 — no SaaS, no network. [Source: docs/architecture/9-合规架构compliance-architecture.md#9.1]
- **Toolchain limits (this environment)**: local cannot run `buf`/`atlas`/`docker`; this story needs none of them (pure Go package, tests via `go test`). DO NOT re-run workspace-level `go mod tidy` — it auto-bumps the pinned otel deps. [Source: memory project_otel_version_pin_gotcha], [Source: memory project_toolchain_env_limits]
- **Go / stack**: Go 1.22+, stdlib-first; the repo posture is zero-third-party-dep where stdlib suffices (cf. payment-svc Q-SDK). Prefer stdlib for the Bloom filter and hashing; only `golang.org/x/text/unicode/norm` (NFKC) may warrant a dependency — gate it on OQ-8.1-4. [Source: docs/architecture/tech-stack.md#2.1]

- **Security note**: the gravest defect class is a **false-negative** (a term that should match but doesn't). Tests must assert positive membership for a sampled set across every category + both languages, and assert normalization brings common evasions-in-scope (width/case/zero-width) to the canonical form.
