> **Architect Open Questions** (gathered for Architect Round 1):
> - **Q1**: Profile read endpoint surface — `GET /v1/me` (whole-user snapshot including email + totp_enabled, mirrors Story 2.2 token introspection) vs `GET /v1/me/profile` (profile sub-resource only, leaves email/totp_enabled to a separate `/v1/me/account` endpoint)? SM defaults to the **whole-user `GET /v1/me`** because (a) Settings → Profile page DOES need totp_enabled to render the "2FA enabled" badge in the same view, (b) email is currently the only stable user identifier visible to the user (read-only, not editable in this Story), (c) avoids the chatty-API anti-pattern of two round-trips for a single page. Architect may overrule for clean REST resource modeling.
> - **Q2**: Optimistic concurrency mechanism — etag (`If-Match: "{updated_at_unix_nanos}"` header per BR-2.7) vs version column (`users.version INT` + WHERE clause) vs last-writer-wins (no protection)? SM defaults to **etag from `users.updated_at`** because (a) the column already exists and is updated on every UPDATE via the migration default, (b) no new column means no new migration concerns, (c) the precision (nanos) is sufficient for human-edit races. Architect may rule version column if updated_at is reserved for non-locking semantics.
> - **Q3**: Locale-switch UX contract — `redirect()` to `/{newLocale}/settings/profile` (Server Action re-renders entire route segment with new locale; `he_locale` cookie also rewritten so middleware honors the new locale on subsequent navigations) vs `router.refresh()` (Next.js soft-refresh; relies purely on cookie-driven middleware re-evaluation; pathname stays at `/{oldLocale}/...` until next navigation, which would be jarring) vs full `window.location.assign('/{newLocale}/...')` (hard reload — defeats Epic-2 DoD "运行时切换" / runtime switch)? SM defaults to **`redirect()` + cookie rewrite** — see AC3 §Scenario. Architect may have a strict next-intl recipe preference.
> - **Q4**: AAL claim requirement for `PUT /v1/me/profile` — does an `aal>=1` access_token suffice (default), or does Architect want `aal>=2` enforced (forces 2FA-enabled users through a re-challenge on profile edit, parity with future Story 2.7 delete-account)? SM defaults to **`aal>=1`** because (a) profile edit is low-blast-radius (no auth/billing/key surface mutation), (b) re-challenge friction degrades the headline AC ("立即渲染" implies one click, not "click → 2FA challenge → click again"), (c) Story 2.4 BR-2.8 only commits to "issue aal=2 claim"; downstream enforcement is per-Story. Architect may rule otherwise — if AAL2 mandatory, AC3 §Scenario branches to interstitial mfa_token flow (≈ +1 day Dev work).

### AC1: View Profile — Settings → Profile renders current values from the authenticated session

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access cookie valid per Story 2.2 BR-3.7)
  - User navigates to `/{locale}/(console)/settings/profile` (P-11 Profile sub-page per front-end-spec §P-11 line 542 — sibling of /settings/security delivered by Story 2.4)
WHEN
  - The Next.js Server Component for the page renders
  - Console BFF Server Action `getMyProfile()` → api-gateway GET `/v1/me` (carries he_access cookie) → auth-svc gRPC `GetMe(user_id)` (user_id extracted by api-gateway middleware from JWT `sub` claim, NEVER trusted from request body)
THEN
  - auth-svc GetMe:
    - Loads `SELECT id, email, display_name, locale, timezone, totp_enabled, oauth_provider, created_at, updated_at FROM he_api.users WHERE id=$1 AND status NOT IN ('pending_deletion') LIMIT 1`
    - Returns `GetMeResponse{user_id, email, display_name, locale, timezone, totp_enabled, oauth_provider, created_at, updated_at, etag}` where `etag` = `fmt.Sprintf("\"%d\"", updated_at.UnixNano())` (BR-2.7)
    - On `pending_deletion`: returns gRPC `FailedPrecondition` with `reason='account_pending_deletion'` (api-gateway translates to 403 — already-deleted accounts should not surface profile editor; Story 2.7 owns the recovery flow)
  - api-gateway:
    - Translates gRPC → HTTP 200; body `{user_id, email, display_name, locale, timezone, totp_enabled, oauth_provider, created_at, updated_at}` (snake_case per coding-standards §12.3); response header `ETag: "{nanos}"` (BR-2.7)
    - Sets `Cache-Control: no-store` (PII page — never cache by intermediate proxies)
  - Console Server Component renders the Profile form pre-populated with the response:
    - `<Input name="display_name">` defaulted to `display_name || ''` — placeholder is the `account.profile.display_name.placeholder` i18n key ("Set your display name" in en); the input shows the placeholder when value is empty (cleared display_name treats NULL and empty string as the same UX state, see BR-1.6)
    - `<Input name="email">` shows email read-only with a `<Badge>account.profile.email.read_only_hint</Badge>` ("Email is set during signup and cannot be changed here")
    - `<Select name="locale">` lists the 10 MVP locales (Story 2.1 set) with native-language labels (see `<LocaleSwitch>` impl, packages/i18n-keys); currently-stored locale is pre-selected
    - `<Select name="timezone">` lists IANA Time Zone Database identifiers grouped by region (Africa/, America/, Asia/, …); currently-stored timezone is pre-selected; uses native `Intl.supportedValuesOf('timeZone')` for the source list (browser-native, no extra dependency)
    - `<Badge>` row showing 2FA status: if `totp_enabled=TRUE`, render the `account.profile.security.totp_enabled` key with a link to `/settings/security` (Story 2.4 page); if FALSE, render `account.profile.security.totp_disabled` with a CTA "Enable" link (also to /settings/security)
    - `<Badge>` row showing auth method: if `oauth_provider IS NOT NULL`, render `account.profile.auth_method.oauth_{provider}` ("Signed in with Google" / "Signed in with GitHub"); else render `account.profile.auth_method.email_password`
    - `<Submit>` button labeled `account.profile.actions.save` ("Save changes"); disabled until at least one field differs from the loaded values (form `dirty` state)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | `GET /v1/me` is **user-bound** — api-gateway middleware (Story 2.2 BR-3.7) extracts `user_id` from the verified JWT `sub` claim and passes it to auth-svc; the request body / query string MUST NOT carry a user_id (defense-in-depth against IDOR — even though gRPC contract requires it, gateway translates from JWT and ignores any client-supplied value). |
| BR-1.2 | `email` is **read-only** in this Story. The response surfaces it so the Settings → Profile page can display the read-only field, but `PUT /v1/me/profile` (AC2) does NOT accept email and rejects with `400_unknown_field` if present (parity with Story 2.2 BR-2.4 strict-field-validation). Email change requires a separate Story (mirrors Story 2.2 verify-email flow). |
| BR-1.3 | `totp_enabled` is surfaced read-only as Story 2.4 owns its lifecycle. Profile page links to `/settings/security` to enable/disable (Story 2.4 AC1/AC4) — Story 2.5 does NOT replicate the toggle. |
| BR-1.4 | `oauth_provider` is surfaced read-only. Users who signed up via OAuth (Story 2.3) have `password_hash IS NULL` — Story 2.5 does NOT introduce a "set a password" flow (separate Story; for MVP, OAuth-only users are locked into OAuth as their auth method). |
| BR-1.5 | `created_at` is rendered as a localized date using `Intl.DateTimeFormat(locale, {dateStyle:'long'})` — for screen readers, the ISO 8601 form is exposed via `<time dateTime={iso}>` (WCAG 2.1 SC 1.3.1 Info and Relationships). |
| BR-1.6 | `display_name` semantics: NULL in DB and empty string in UI form are functionally equivalent ("user has not set a display name"). The PUT endpoint (AC2) accepts empty string and converts to NULL before storage (BR-2.4). The Profile page never distinguishes "never set" from "explicitly cleared" — both render the placeholder. |
| BR-1.7 | `Cache-Control: no-store` is mandatory on `GET /v1/me` because the response carries `email` (PII) — no intermediate proxy may cache (per security.md §8.1 layer 7 "PII 脱敏" — applied here as no-cache rather than redaction since the user is authenticated to see their own email). |
| BR-1.8 | If `he_access` cookie is missing or invalid, the api-gateway middleware (Story 2.2 BR-3.7) returns 401 BEFORE this handler runs — Story 2.5 does NOT replicate auth handling. The Next.js Server Component, when receiving a 401 from the BFF Server Action, redirects to `/{locale}/(auth)/signin?return_to=/{locale}/settings/profile` (existing Story 2.2 return_to handling). |
| BR-1.9 | `pending_deletion` account state (Story 2.7) returns 403 BEFORE the profile body — page redirects to a Story 2.7 "Account is being deleted" interstitial (Story 2.7 owns the page; Story 2.5 only links). Until Story 2.7 lands, this Story's contribution is the 403 contract — client behavior on 403 is "show generic error toast" per BR-1.10 fallback. |
| BR-1.10 | If gRPC returns any error other than `FailedPrecondition`, api-gateway returns 500 generic — Console Server Component renders an `<EmptyState>` with `account.profile.errors.load_failed` + retry button (no PII in error message). |

### AC2: Update Profile — display_name + locale + timezone with strict validation, audit, optimistic concurrency

**Scenario**
```gherkin
GIVEN
  - User on `/{locale}/(console)/settings/profile` with the form rendered per AC1
  - User edits one or more of {display_name, locale, timezone}
  - User clicks "Save changes"
WHEN
  - Console BFF Server Action `updateMyProfile({display_name, locale, timezone, if_match_etag})` is invoked with the form values + the etag from the AC1 GET response (server-side state on the Server Action call site)
  - Server Action → api-gateway PUT `/v1/me/profile` (carries he_access cookie + `If-Match: "{etag}"` header) → auth-svc gRPC `UpdateProfile(user_id, display_name, locale, timezone, if_match)`
THEN
  - auth-svc UpdateProfile:
    - Validates field-level inputs (per "Data Validation" table) — on failure: returns gRPC `InvalidArgument` with structured `field_errors[]` (gateway translates to 400 + JSON body `{errors:{field:msg}}`)
    - Loads current `SELECT updated_at FROM he_api.users WHERE id=$1` (FOR UPDATE — row-level lock for the transaction)
    - Compares `fmt.Sprintf("\"%d\"", updated_at.UnixNano())` against `if_match` from request; mismatch → returns gRPC `FailedPrecondition` reason `etag_mismatch` (gateway translates to 412; see BR-2.7)
    - In the same PG transaction:
      - `UPDATE he_api.users SET display_name=$1, locale=$2, timezone=$3, updated_at=NOW() WHERE id=$user_id RETURNING updated_at`
      - Computes redacted diff for audit (see BR-2.10): `{display_name: {from: '<set>'|'<unset>', to: '<set>'|'<cleared>'}, locale: {from: 'en', to: 'zh-CN'}, timezone: {from: 'UTC', to: 'Asia/Shanghai'}}` — display_name is redacted; locale and timezone are non-PII enumerables so logged literally
      - Emits Kafka `audit.event` with `audit_event_type='profile.updated'`, payload includes `user_id, client_ip_hash, user_agent_hash, fields_changed:[…], diff:{…redacted…}, ts`
    - Increments rate-limit counter `ratelimit:profile:update:{user_id}` (10/hour per BR-2.8) — if at ceiling BEFORE the update, returns 429 with `Retry-After`
    - Returns `UpdateProfileResponse{user_id, display_name, locale, timezone, etag:{new_nanos}, totp_enabled, oauth_provider, email, created_at, updated_at}` (mirrors GetMeResponse — Console reuses the same renderer)
  - api-gateway:
    - Translates → HTTP 200; body mirrors GetMeResponse; response header `ETag: "{new_nanos}"`
    - If `locale` was changed: **overwrites the `he_locale` cookie** with the new value (`Path=/`, `HttpOnly=false` — Story 2.1 BR contract — so the next-intl middleware can read it from the document.cookie when the user navigates client-side; matches Story 2.1 cookie name + attributes); cookie `Max-Age` mirrors Story 2.1 setting (365 days)
  - Console Server Action:
    - On 200: invokes `revalidatePath('/{locale}/(console)/settings/profile')` then — if `locale` changed — invokes `redirect('/{newLocale}/(console)/settings/profile')` (Server Action returns a redirect signal; AC3 owns this code-path verification); if locale did NOT change, returns success state to the form which shows a success toast
    - On 412 (etag mismatch): returns a form error result `{kind:'concurrent_update', message:account.profile.errors.concurrent_update}` ("Profile was updated in another tab. Please reload."); Console renders a `<Banner>` with "Reload" CTA that triggers `router.refresh()`
    - On 400 field errors: surfaces `field_errors` to React Hook Form via `setError(field, {message})` — input borders turn red, error text appears below each invalid field (per front-end-spec §5.3)
    - On 429: surfaces a toast with `account.profile.errors.rate_limited` ("Too many updates. Please wait a moment before trying again.")
    - On 500/503: generic error toast `account.profile.errors.generic` ("Couldn't save changes. Please try again.")
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | All three fields (display_name, locale, timezone) are **independently optional** in the PUT payload — the endpoint accepts a partial body. Omitting a field means "do not change". Sending an empty string for display_name (`""`) means "clear" (writes NULL — BR-1.6 / BR-2.4 normalization). Sending null for locale or timezone is INVALID (these are NOT NULL with DB defaults; clearing them is meaningless). |
| BR-2.2 | Strict-field-validation: the PUT body MUST contain ONLY keys in `{display_name, locale, timezone}`. Any other key → 400 `400_unknown_field` with `field=<offending_key>` (parity with Story 2.2 BR-2.4). |
| BR-2.3 | `display_name` accepts Unicode but is stored after Unicode NFC normalization (`golang.org/x/text/unicode/norm`) — prevents homoglyph attacks across visually-identical-but-bytewise-different inputs (security.md §8.1 input-validation layer). Length is measured in **runes** after NFC, not bytes (so a 100-rune Chinese name = 300 bytes UTF-8 fits the column). |
| BR-2.4 | `display_name` empty string normalization: trim leading/trailing whitespace → if result is empty, store NULL. The endpoint NEVER stores the empty string (avoids the "NULL vs empty" semantic ambiguity per BR-1.6). |
| BR-2.5 | `display_name` is **not enforced to be globally unique** — multiple users may have the same display name. This is a UX label, not an identifier. Uniqueness lives on `users.email`. |
| BR-2.6 | `locale` MUST be a member of the Story 2.1 MVP set (en/zh-CN/ja/ko/es/fr/de/pt/ru/ar). V1.1 locales (zh-TW/hi/id from front-end-spec §6.1) are rejected — adding them happens when a future Story extends the i18n MVP set. |
| BR-2.7 | Optimistic concurrency via `If-Match` header against the etag returned by AC1's GET. Mismatch → 412 with a "Profile was updated in another tab" error. This prevents lost-update on the simultaneous-tab scenario (e.g., user has two browser tabs open on the profile page; edits each; saves both — without etag the second save silently overwrites the first). Architect Q2 may overrule mechanism choice. |
| BR-2.8 | Rate limit: `ratelimit:profile:update:{user_id}` Redis counter, 10 successful-or-failed updates / hour. At ceiling → 429 with `Retry-After` (seconds until counter expires). This is anti-abuse, not anti-error — a legitimate user does not edit their profile 11+ times per hour. Story 2.4 BR-5.1 framework is the reuse target. |
| BR-2.9 | Audit event `profile.updated` is emitted on **success only** (not on validation failure — those are not interesting for compliance / forensics in this Story's threat model; failed validation does not change state). On rate-limit-block, no event is emitted (no state change). |
| BR-2.10 | Audit diff redaction: `display_name` values are NEVER logged literally — only `<set>` / `<cleared>` / `<unchanged>` enums. `locale` and `timezone` are enumerable non-PII identifiers and are logged literally. `client_ip_hash` is `HashClientIP` /24 + /64 prefix (Story 2.3 m-4 helper). `user_agent_hash` is sha256 (Story 2.3 m-4 helper). PII surface: zero. |
| BR-2.11 | `users.updated_at` MUST advance to NOW() on every successful UPDATE (the migration sets a column default of NOW() but does NOT install a trigger — the application is responsible for setting it in the UPDATE statement; current Story 2.2 password-change path does the same). This is BR-load-bearing for etag (BR-2.7) — without an advancing timestamp, etag is stale and concurrency protection breaks. |
| BR-2.12 | Concurrent edits to the **same** user (BR-2.7 covers human-edit races); concurrent edits to **different** users (the normal case) are not contended — `WHERE id=$user_id` row-level lock is fine-grained and does not contend with other users' updates. |
| BR-2.13 | `notification-svc SendEmail` is **NOT invoked on profile update** by default. Rationale: low-risk mutation; spamming the user with confirmation emails on every display_name tweak is friction. *Exception (Architect Q4 pending)*: if Architect rules locale-change is a security-relevant transition (e.g., social-engineering pretext for credential phishing), this Story would add a `template='profile_locale_changed'` notification — currently OFF per SM default. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `display_name` | string \| null | no | After NFC + trim: empty → NULL allowed; non-empty 1–100 runes; allowed code-point classes: Letter (L), Mark (M), Number (N), Punctuation (P), Symbol-Currency (Sc), space (single ASCII space allowed between words). REJECT: control chars (Cc), format chars (Cf), surrogates (Cs), private-use (Co), unassigned (Cn), other Symbol classes (S-{Sc}) | `400_invalid_display_name` — `account.profile.errors.display_name.{invalid_chars\|too_long}` |

### AC3: Immediate UI re-render on locale change — the headline AC from Epic-2 YAML

**Scenario**
```gherkin
GIVEN
  - User on `/{currentLocale}/(console)/settings/profile`
  - User is authenticated, has just edited the `locale` field in the Profile form, and clicks "Save changes"
  - PUT `/v1/me/profile` completes successfully (AC2 happy path) with `newLocale != currentLocale`
WHEN
  - Server Action `updateMyProfile` receives the 200 OK response from api-gateway
  - api-gateway has already set the `he_locale` cookie to `newLocale` (AC2 §Scenario response-side)
  - Server Action invokes `redirect('/{newLocale}/(console)/settings/profile')` (Next.js Server Action redirect)
THEN
  - Next.js routes the user to `/{newLocale}/(console)/settings/profile`:
    - The URL in the browser address bar reflects `newLocale` (e.g., `/en/...` → `/zh-CN/...`)
    - The next-intl middleware (Story 2.1 落地物) reads the `[locale]` URL segment as the source of truth — `he_locale` cookie agreement is a backup signal, not the primary
    - The Server Component for `(console)/layout.tsx` and `settings/profile/page.tsx` re-render with `next-intl`'s `useTranslations` resolving against `messages/{newLocale}/account.json` + `messages/{newLocale}/common.json`
    - All visible strings (page title, section headers, field labels, button text, toast messages still in DOM, badges) appear in `newLocale`
    - For RTL locales (`ar`): `<RTLProvider>` (Story 2.1 component) detects `isRtlLocale('ar')` and renders the document with `dir="rtl"`; the layout flex-direction reverses; chevrons / back-arrows mirror per front-end-spec §6.2 last bullet
    - The form is re-mounted with the fresh response data (display_name + locale + timezone all newly applied) and a fresh etag (the new updated_at)
  - The success toast is rendered AFTER the re-render — it appears in `newLocale` (the `account.profile.toast.locale_changed` key, e.g., "Language changed to 简体中文")
  - There is NO "flash of untranslated content" (FOUC-i18n): because Next.js Server Components render the new locale on the server before sending HTML to the client, the user never sees a frame with old-locale text + new-locale URL
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | The locale switch contract is **server-driven**: the PUT response's locale wins. The previously-set `he_locale` cookie (Story 2.1 client-side via `<LocaleSwitch>`) is overwritten by the api-gateway response Set-Cookie header. This makes the DB the source of truth for "user's locale" and the cookie a write-through cache. |
| BR-3.2 | The redirect to `/{newLocale}/...` is mandatory — not optional. Rationale: Next.js App Router's `[locale]` segment is the source of truth for `useTranslations`; staying on `/{oldLocale}/...` with only a cookie update would leave the URL out-of-sync with the visible language — a known next-intl anti-pattern. |
| BR-3.3 | The redirect target preserves the pathname suffix (`/(console)/settings/profile` here) — so the user remains on the same page, just under the new locale. This is the contract `redirect('/{newLocale}/(console)/settings/profile')` honors. |
| BR-3.4 | Query parameters and hash fragments — if any are present on the URL when the user clicks Save — are preserved across the redirect. (For the profile page specifically, the URL is typically clean — no query params — so this rule is defensive for future code that may add `?tab=foo`.) |
| BR-3.5 | The `he_locale` cookie attributes (Path, Max-Age, SameSite, Domain) MUST match what Story 2.1's `<LocaleSwitch>` writes. Authoritative spec lives in `apps/console/lib/i18n.ts` (`buildLocaleCookieOptions` — Story 2.1). Server-side rewrite via api-gateway MUST use identical attributes (Architect Q3 may verify the helper is shared/imported). |
| BR-3.6 | "Immediate" in the headline AC means: from the user's perspective, the entire page content (including the toast confirming the change) is in `newLocale` on the next paint after Save resolves. This is achievable via Server Component re-render after redirect — no client-side `useEffect` polling, no React Suspense waterfall. |
| BR-3.7 | If the user changed `locale` AND `display_name` (and/or `timezone`) in the same Save, the redirect still fires — all three updates are applied atomically by the PUT (single SQL UPDATE per BR-2.11), and the user lands on the new-locale page with all three fields persisted. |
| BR-3.8 | RTL transition (e.g., from `en` to `ar`, or `ar` to `en`): handled entirely by `<RTLProvider>` (Story 2.1) reading the `[locale]` segment. No additional code in Story 2.5 — this Story validates that the existing RTL infrastructure correctly applies on the new layout boundary `(console)/layout.tsx`. |
| BR-3.9 | If the user's locale change involves a "long-text locale" (German "de" is canonical — see front-end-spec §6.2 "测试" bullet), the layout must not break. This is a regression risk Story 2.5 owns through its visual tests (T5.2 in §Tasks). |
| BR-3.10 | The cookie write happens at api-gateway level (HTTP response header), NOT at auth-svc gRPC level. auth-svc returns the locale in the response body only; api-gateway translates body → header. This boundary keeps the gRPC contract HTTP-cookie-agnostic (parity with Story 2.2 he_access / Story 2.4 he_mfa pattern). |
| BR-3.11 | If api-gateway fails to set the cookie for any reason (header-write failure — vanishingly rare), the DB has been updated and the redirect still fires. The next page render reads the locale from the URL segment (which IS correct), and the next-intl middleware reconciles the cookie on the subsequent navigation via the URL-takes-precedence rule. **Eventual consistency contract** for the cookie. |

| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| (no new fields beyond AC2 — AC3 is a UX-contract assertion on the response path of AC2) | — | — | — | — |

| Trigger | Behavior |
|---------|----------|
| Successful save with `newLocale != currentLocale` | URL changes from `/{oldLocale}/(console)/settings/profile` → `/{newLocale}/(console)/settings/profile`; HTML re-renders server-side with `newLocale` translations; success toast appears in `newLocale`; address bar reflects the new URL |

  **Expected**: PUT 200 → cookie `he_locale=zh-CN` set → redirect to `/zh-CN/(console)/settings/profile` → page renders with Chinese strings → success toast in Chinese ("已更新个人资料") → address bar shows `/zh-CN/(console)/settings/profile`; all in a single render cycle, no flash

  **Expected**: PUT 200 → no Set-Cookie for locale → no redirect → `revalidatePath` invalidates the cached page → re-render fetches new etag → success toast in English ("Profile updated"); URL stays at `/en/...`

  **Expected**: Page re-renders in German; all button text fits the existing layout (visual regression test T5.2); no overflow; toast in German ("Profil aktualisiert")

### Database Design

**Decision: ALTER TABLE ADD COLUMN (not a new table)**

`display_name` is a 1:1 user-bound attribute, joined every time the Profile page (or any future user-display-needing context) loads. Splitting into `user_profile` would impose a JOIN on every read with no compensating benefit (no soft-multi-tenancy, no cross-user shared rows, no migration to a different storage class). The column is nullable to express "not yet set" without a sentinel value.

**Migration content (T0.1)**:
```sql
ALTER TABLE he_api.users
    ADD COLUMN display_name VARCHAR(100);
```

**Why VARCHAR(100), not TEXT**:
- Bound at the DB layer aligns with BR-2.3 rune limit; even though VARCHAR(100) is bytes per PG, 100 runes worst-case in UTF-8 is 400 bytes which fits VARCHAR(2000) territory — but PG VARCHAR(N) bound is the **character count post-encoding**, NOT byte count, per PG manual (`utf8` encoding) — so VARCHAR(100) caps at 100 chars regardless of byte width. Application-layer BR-2.3 rune limit is the load-bearing check; the column bound is defense-in-depth.
- VARCHAR vs TEXT: identical performance in PG; VARCHAR encodes intent.

**Why no index on display_name**:
- BR-2.5 disclaims global uniqueness; there is no current query path that filters by display_name (the Profile page only reads by user_id). Adding an index would be premature optimization with no caller.

**Why no migration for `locale` / `timezone`**:
- Both columns already exist (Story 2.2 baseline `0002_create_users.sql` lines 19-20). Story 2.5 reads + writes them via the existing schema.

**3. Related Field Synchronization Analysis (LLM Reasoning)**

**Key Question**: Based on business logic reasoning, when this Story updates a field, are there other tables' fields that need to be synchronized?

**Reasoning**:
- `display_name` is a UX-only field. No FK relationships, no cached copies elsewhere. Safe to mutate in isolation.

```go
// apps/auth-svc/internal/handlers/update_profile.go (excerpt)
import "golang.org/x/text/unicode/norm"

func validateDisplayName(input string) (string, error) {
    if input == "" { return "", nil } // empty → NULL (BR-2.4)
    normalized := norm.NFC.String(strings.TrimSpace(input))
    if normalized == "" { return "", errInvalidDisplayName("too_short") } // whitespace-only
    if utf8.RuneCountInString(normalized) > 100 { return "", errInvalidDisplayName("too_long") }
    for _, r := range normalized {
        if !unicode.In(r, unicode.L, unicode.M, unicode.N, unicode.P, unicode.Sc) && r != ' ' {
            return "", errInvalidDisplayName("invalid_chars")
        }
    }
    return normalized, nil
}

func validateLocale(input string) error {
    for _, mvp := range []string{"en","zh-CN","ja","ko","es","fr","de","pt","ru","ar"} {
        if input == mvp { return nil }
    }
    return errInvalidLocale
}

func validateTimezone(input string) error {
    _, err := time.LoadLocation(input)
    if err != nil { return errInvalidTimezone }
    return nil
}
```

### Architect Rulings on Open Questions Q1-Q4

**Q1 — Profile read endpoint surface**: ✅ **APPROVE SM default**: `GET /v1/me` (whole-user snapshot) + `PUT /v1/me/profile` (profile-only). Asymmetry is justified by single-page-render pragmatism — Settings → Profile needs `email + totp_enabled + oauth_provider` inline to render the read-only badges (AC1 §Scenario), and a sub-resource split would force a 2-RTT page (anti-pattern). No `/v1/me/account` sub-resource introduced in this Story.

**Q2 — Optimistic concurrency mechanism (CRITICAL CLARIFICATION)**: ✅ **RULE: `users.updated_at.UnixMicro()` end-to-end + Go-side comparison in same FOR UPDATE transaction**.
- **Why**: PG `TIMESTAMPTZ` stores **microsecond** precision (per PG manual). Using `UnixNano()` introduces gratuitous trailing-zero nanos that are an unnecessary round-trip risk if anyone refactors to compare in SQL. Using `UnixMicro()` matches PG's native precision exactly — 1:1 lossless round-trip.
- **Comparison pattern**: Use **Go-side compare** (T2.1 §Scenario approach), NOT SQL `extract(epoch from updated_at)*1e9 = $5` (T0.3 alternate proposal). The float64 cast in `extract(epoch from)` is fragile; explicit `time.Time.UnixMicro()` int64 compare in Go is canonical.
- **Implementation contract**:
  1. GET response: `ETag: "{updated_at.UnixMicro()}"` — 16-digit int64
  2. PUT request: `If-Match: "{etag}"` header — same format
  3. In `UpdateProfile` repo method: `SELECT updated_at FROM he_api.users WHERE id=$1 FOR UPDATE` → compare `currentMicros := updated_at.UnixMicro()` against the parsed `ifMatchMicros` in Go → if equal, proceed to `UPDATE ... SET updated_at=NOW()`; else return `ErrEtagMismatch`. Both queries in the same transaction.
- **Action**: Update T0.3 to remove the SQL `extract(epoch ...) = $5` clause; update T0.3.note: "RESOLVED — use `UnixMicro()` end-to-end + Go-side compare." Update etag format in AC1 §Scenario + AC2 §Scenario + BR-2.7 + T0.3 + T1.1 + T2.1 from `UnixNano` to `UnixMicro`.

**Q3 — Cookie helper sharing**: ✅ **RULE: Extend `apps/api-gateway/internal/handlers/cookies.go` with `SetLocaleCookie`** that reuses the existing `cookieDomain()` + `secureFlag()` helpers (Story 2.2). The Go side is the canonical authority for the gateway response; the TS side (`apps/console/lib/i18n.ts` → `buildLocaleCookieOptions`) remains the authority for client-driven writes via `<LocaleSwitch>`. Both MUST stay in sync with identical attributes.
