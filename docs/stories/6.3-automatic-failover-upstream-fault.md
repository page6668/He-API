### Architect Open Questions (gathered for Architect Round 1)

> SM defaults are stated; the Architect rules IN/DEFER/OVERRULE. **Q-A + Q-B are the headline forks.**

- **Q-A — Failover candidate-source design (where does "the next model" come from?)** ⚠️ HEADLINE. The 6.2 `SelectModelResponse` returns a SINGLE `selected_model`; failover needs the *ordered next candidates*. **SM default = Option A**: add an additive `repeated string failover_chain = 7;` to `SelectModelResponse` — the ranked fallback model ids AFTER `selected_model` (so `selected_model` = chain head, `failover_chain` = the ordered tail). routing-svc populates it via a NEW **optional `RankedStrategy`** capability (`SelectRanked(ctx, candidates, hints) ([]ModelEntry, error)`) layered on the cascade-locked `Strategy` exactly as 6.2's `SourcedStrategy` was — the engine ALREADY computes a total order in `cheapest`/`bestByScore` ([Source: apps/routing-svc/internal/strategy/{candidates,scored}.go]), so returning the full ranking is a trivial sort, NOT new logic; plain strategies (DEFAULT) yield a single-element chain (empty tail). The gateway iterates the chain client-side — ZERO extra routing-svc round-trips on the failure path. **Architect alternatives**: (B) the gateway re-calls `SelectModel` per hop with an additive `repeated string exclude_models` REQUEST field, getting the next-best each time — costs +100ms (Q-E deadline) per failover hop (up to +300ms on the failing path) and keeps the engine stateless-per-call, but slower under failure; (C) pure gateway-side failover over `adapterRegistry` models, ignoring routing-svc ranking — loses cost/quality/latency awareness (failover would pick an arbitrary model, not the next-best by the user's strategy). SM strongly defaults **A** (lowest failure-path latency; keeps ranking authority in routing-svc; mirrors the ratified `SourcedStrategy` precedent; matches the proto comment "failover / A/B variants … extend the engine behind this same RPC, not the surface").

- **Q-B — "3 次失败 / 30s 超时" semantics (per-request budget vs. cross-request circuit-breaker)** ⚠️ HEADLINE. The title encodes two numbers. **SM default = per-request retry budget**: a single chat request makes at most **3 total upstream attempts** (the primary `selected_model` + up to 2 failover hops) AND is bounded by a **30s total wall-clock budget** (a parent `context.WithTimeout(30s)` wrapping the attempt loop); whichever limit hits first stops the chain → the LAST upstream error envelope is returned. The cross-request **circuit-breaker** reading ("eject a model after 3 consecutive failures for a 30s cool-down") is DEFERRED to a future story (KISS — it needs shared cross-request health state / Redis, a heavier surface; 6.3 is per-request failover, which satisfies the Epic DoD "上游故障自动 failover" + "模拟上游故障 → 自动切换到下一个模型"). **Architect**: confirm the per-request reading, or rule the circuit-breaker IN (would expand scope: shared health store + ejection window + half-open probe).

- **Q-C — Retriable error-code set**: the gateway's `writeAdapterError` collapses upstream 4xx/5xx → `502_upstream_unavailable`, and maps `DeadlineExceeded → 504_upstream_timeout` [Source: apps/api-gateway/internal/handlers/chat_completions.go:585-635]. **SM default = failover triggers on `502_upstream_unavailable` + `504_upstream_timeout` ONLY** — the exact two codes documented "即将 failover" at [Source: rest-api-spec.md §5.1.2:106-107]. Non-retriable (no failover, terminal envelope): `400_invalid_request`, `403_model_not_in_scope`, `403_ip_not_whitelisted`, `400_content_filter`, `402_*`, `429_*` — these are request/policy errors, not upstream faults; retrying the same body on a different model would not help (and policy errors must stay deterministic). **Architect**: confirm. (Note: because 4xx/5xx upstream errors COLLAPSE to 502 today, an upstream *misconfiguration* is indistinguishable from upstream-down at the gateway and WILL failover under the SM default — acceptable, since a healthy alternate model recovers the request; Architect may want a carve-out.)

- **Q-D — Does the concrete-model DEFAULT path failover?** ⚠️. A concrete `model` (e.g. `qwen-max`) with no strategy routes via `STRATEGY_DEFAULT` and gets an EMPTY `failover_chain` under Option A. **SM default = NO failover on the concrete-default path** — the user pinned a specific model; silently routing them to a DIFFERENT model on failure violates their explicit choice (and could surprise-bill a pricier model). Failover engages ONLY when a strategy is in play (quality/cost/latency header OR a `he-router-*` meta-model) — i.e. the user expressed a preference for an *outcome*, not a specific model, so substituting a comparable model is faithful to intent. A concrete-model 502/504 returns the terminal envelope (today's behaviour, zero regression). **Architect alternatives**: (i) concrete requests ALSO failover across the catalogue (max resilience, but violates the pin) — possibly behind an opt-in header `X-He-Failover: on`; (ii) concrete requests failover only within the same vendor/model-family. SM defaults the strict no-failover-on-pin reading.

- **Q-E — Streaming post-flush is non-failoverable (HTTP constraint, confirm)**: once the first SSE byte is flushed (`writer.HeadersFlushed()==true`), the HTTP 200 + response headers are committed — failover is IMPOSSIBLE (we cannot un-send bytes). **SM default**: on the streaming path, failover is attempted ONLY while `HeadersFlushed()==false` (the BR-2.5 pre-flush boundary [Source: chat_completions_stream.go:184]); a mid-stream upstream error AFTER first flush terminates the stream exactly as today (BR-2.6: inline SSE error frame + terminal `[DONE]`, NO failover). This is a constraint, not a fork — Architect to CONFIRM (and confirm that a pre-flush 502/504 on a strategy-routed stream DOES failover up to the 3/30s budget before committing headers).

- **Q-F — `X-He-Selected-Model` + response `model` echo on a failed-over request**: **SM default = the FINAL successful model** (chain[k]), NOT the originally-selected chain[0]. The header/body must be truthful about which model actually served the request. slog carries both `requested_selected` (chain[0]) and `served_model` (chain[k]) + the failover count. **Architect**: confirm (alternative: keep chain[0] for "what was intended" — rejected by SM as misleading; the OpenAI `model` field must reflect the responder).

- **Q-G — Per-attempt deadline vs. the 30s total budget**: **SM default** = each upstream attempt KEEPS its existing per-adapter deadline (Story 4.x adapter timeout — unchanged); the 30s is the TOTAL failover wall-clock budget — a parent `context.WithTimeout(ctx, 30s)` wrapping the attempt loop, so a slow first attempt eats into the budget available for hops 2-3. When the 30s parent deadline fires mid-attempt, that attempt is cancelled and failover stops with the last error. **Architect**: confirm, or rule 30s is per-attempt (would let 3×30s = 90s worst case — SM rejects as too long for an interactive chat).

- **Q-H — Billing idempotency (no double-charge on failover)** ⚠️: failover re-dispatches after a FAILED attempt. **SM default + INVARIANT**: at most ONE successful upstream response per request → at most one `tokenDeducter.TPMDeduct` (it fires only on the success path with `resp.Usage` [Source: chat_completions.go:365]). A failed attempt (502/504) yields no `resp.Usage` → no deduction. CAVEAT: a `504` attempt MIGHT have actually executed upstream (the model generated tokens we never received) — that phantom upstream cost is EATEN by the platform, NEVER billed to the user (correct: never overcharge). **Architect**: confirm the invariant (a dedicated test asserts exactly-one-deduction across a 2-failover-then-success request).

- **Q-I — Failover observability (metrics + slog)**: **SM default** = a NEW counter `he_routing_failover_total{from_model,to_model,reason}` (reason ∈ `upstream_unavailable|upstream_timeout`) + a histogram `he_routing_failover_attempts` (attempts-per-request) + a per-attempt slog line `routing_action=failover` ([Source: observability.md §11.3:33-37] — the documented label). `from_model×to_model` cardinality is bounded (~8×8 catalogue). **Architect**: confirm metric shape / trim cardinality if desired.

- **Q-J — `score_source` + `strategy_used` on a failed-over request**: the `failover_chain` is ONE ranking of ONE strategy → `score_source` (6.2 field 6) + `strategy_used` (field 5) are properties of the RANKING, set ONCE by routing-svc, UNCHANGED by which chain entry actually served. **SM default**: the header/slog `score_source` + `strategy_used` reflect the ranking (e.g. `score_source=model_pricing`, `strategy_used=STRATEGY_COST`) regardless of failover depth; the failover depth is observable via the Q-I metric/slog, not via these fields. **Architect**: confirm.

- **Q-K — keypolicy (Story 5.2) scope interaction on failover** ⚠️: the 5.2 `keypolicy` gate 403s a request whose model ∉ `scope.models`. If a failover hop picks a model outside the key's scope, dispatching to it would be wrong (the user never authorised it). **SM default**: the gateway FILTERS the `failover_chain` by the key's `scope.models` BEFORE dispatch — failover NEVER targets a scoped-out model (mirrors 6.2 Q-F: routing decision validated against keypolicy). If scope filtering empties the chain, the terminal envelope is the last upstream error (or `403_model_not_in_scope` if chain[0] itself was scoped out — but 6.2 already guarantees chain[0] passed the gate). **Architect**: confirm the gateway-side chain filter (alternative: pass the scope set into `SelectModelRequest` — rejected by 6.2 Q-F to keep the request contract stable).

- **Q-L — rate-limit (Story 5.3) re-charge on failover**: QPS/RPM are counted at request ADMISSION (once per request, in middleware upstream of the handler [Source: Story 5.3]); TPM is deducted post-success. **SM default + INVARIANT**: failover does NOT multiply rate-limit consumption — ONE request = ONE QPS/RPM tick regardless of attempt count; TPM deducts once on the successful attempt (Q-H). The retry loop lives INSIDE the handler, AFTER the rate-limit middleware, so attempts are not re-admitted. **Architect**: confirm (a test asserts a 3-attempt request consumes one QPS token, not three).

## Story

As an **api-gateway user calling `POST /v1/chat/completions` with a routing strategy (a `quality|cost|latency` header or a `he-router-*` meta-model)**,
I want **the gateway to automatically retry my request against the next-best model in the strategy's ranked candidate chain when the selected upstream model is unavailable or times out (502/504) — up to 3 attempts within a 30 second budget**,
so that **a single upstream model fault is transparent to me (my request still succeeds against a comparable model), with the `X-He-Selected-Model` header truthfully reporting which model actually served the response, and with my account billed and rate-limited exactly once regardless of how many failover hops occurred.**

### AC1: routing-svc returns the ranked `failover_chain` (additive `SelectModelResponse.failover_chain = 7`)

**Scenario**
```gherkin
GIVEN a SelectModel request with a real strategy (STRATEGY_COST / QUALITY / LATENCY, or a he-router-* meta-model)
  AND the boot catalogue holds N concrete candidates (the he-router-* virtual entries excluded — 6.2 BR2-5)
WHEN routing-svc's engine resolves the decision via the strategy's NEW optional RankedStrategy capability
THEN
- selected_model = the rank-1 model (UNCHANGED from 6.2 — chain head)
- SelectModelResponse.failover_chain = the ordered list of fallback model ids AFTER selected_model (rank-2, rank-3, …), all concrete (NEVER a he-router-* id — BR1-3 correctness gate applies to the WHOLE chain)
- the ordering is the SAME total order the strategy already computes: cost → (input+output) price ascending, tie → first-alphabetical (Q-J/6.2); quality/latency real → score; quality/latency DEGRADED → deterministic cost-then-alphabetical (6.2 BR3-2)
- a STRATEGY_DEFAULT (concrete-model passthrough) decision returns an EMPTY failover_chain (Q-D — the pinned model has no fallbacks)
- a single-concrete-candidate catalogue returns selected_model + an empty failover_chain (nothing to fall back to)
- strategy_used (field 5) + score_source (field 6) are UNCHANGED — properties of the ranking, set once (Q-J)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR1-1 | `SelectModelResponse.failover_chain = 7` is ADDITIVE (`repeated string`) — same backward-compatible pattern as `score_source=6` / `strategy_used=5` / `ab_selected_models=4`; passes `buf breaking: FILE` (fields 1-6 unchanged). ### AC2: gateway sequential failover on the NON-STREAMING path (`模拟上游故障` → `自动切换到下一个模型`)

**Scenario**
```gherkin
GIVEN a strategy-routed non-streaming request whose selected_model upstream is faulting
  AND the gateway holds the routing Decision (selected_model + failover_chain) from AC1
WHEN the gateway dispatches to selected_model and the adapter returns a retriable upstream error (502_upstream_unavailable OR 504_upstream_timeout — Q-C)
THEN
- the gateway advances to the next model in the (scope-filtered — Q-K) failover_chain and re-dispatches the SAME request body
- failover repeats until SUCCESS, or the attempt cap (3 total upstream attempts — Q-B) is reached, or the 30s total wall-clock budget (Q-B/Q-G) is exhausted, whichever comes first
- on the FIRST success: the response body is written; X-He-Selected-Model + the response `model` echo = the FINAL served model (Q-F); tokenDeducter.TPMDeduct fires EXACTLY once with that response's usage (Q-H)
- on exhaustion (chain empty / 3 attempts / 30s): the LAST upstream error envelope is written via the canonical openaierr.Write (today's terminal behaviour — zero regression for a genuinely-down ecosystem)
- a NON-retriable outcome (400_invalid_request, 403_model_not_in_scope, 400_content_filter, 402_*, 429_*) is TERMINAL — NO failover (Q-C)
- a concrete-model DEFAULT request (empty failover_chain — Q-D) does NOT failover: a 502/504 returns the terminal envelope (byte-for-byte today's behaviour)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR2-1 | Failover wraps `serveAdapterNonStream` [Source: chat_completions.go:419] as a retry LOOP: the adapter error is CLASSIFIED (the existing `writeAdapterError` mapping — `502_upstream_unavailable` / `504_upstream_timeout` are retriable) BEFORE writing; on a retriable code with a non-empty remaining chain + remaining budget, advance instead of writing. `writeAdapterError` is invoked ONLY on the final (non-retriable or exhausted) outcome — it stays the sole envelope writer (no bespoke writer; §5.1.2 discipline). |
| BR2-2 | Attempt cap = **3 total upstream attempts** (primary + ≤2 failover hops). Budget = **30s total wall-clock** via a parent `context.WithTimeout(ctx, 30s)` wrapping the loop (Q-G); each individual attempt keeps its existing per-adapter deadline. Both bounds are constants (named `MaxFailoverAttempts=3`, `FailoverBudget=30*time.Second`) — testable + tunable. |
| BR2-3 | Each hop resolves the adapter via the EXISTING `adapterRegistry.Resolve(nextModel)` [Source: chat_completions.go:340]; a chain entry that does NOT resolve to a registered adapter is SKIPPED (logged) and the next entry tried — it does not count against the upstream-attempt cap (no upstream call was made), but it DOES consume wall-clock toward the 30s budget. |
| BR2-4 | ⚠️ BILLING INVARIANT (Q-H): at most ONE successful upstream response per request → at most ONE `TPMDeduct`. Failed attempts (502/504) carry no `resp.Usage` → no deduction. A dedicated test asserts exactly-one-deduction across a 2-fail-then-succeed request. |
| BR2-5 | ⚠️ SCOPE INVARIANT (Q-K): the `failover_chain` is filtered by the key's `scope.models` (Story 5.2 keypolicy) BEFORE dispatch — failover NEVER targets a model the key is not authorised for. (chain[0]/selected_model already passed the gate via 6.2.) |
| BR2-6 | ⚠️ RATE-LIMIT INVARIANT (Q-L): the retry loop lives INSIDE the handler, AFTER the Story-5.3 rate-limit middleware → ONE request = ONE QPS/RPM tick regardless of attempt count. TPM deducts once on success (BR2-4). |

### Failover control flow (gateway-side — the load-bearing design)
```
decision := router.Decide(...)              // 6.2 — now also carries decision.FailoverChain (AC1)
chain := append([]string{decision.SelectedModel}, decision.FailoverChain...)
chain = FilterByScope(chain, keyScopeModels) // Q-K / BR2-5 — never dispatch a scoped-out model
ctx, cancel := context.WithTimeout(ctx, FailoverBudget /*30s*/); defer cancel()  // Q-G
attempts := 0
for _, model := range chain {
    handle, ok := adapterRegistry.Resolve(model)
    if !ok { slog(skip_unresolved); continue }     // BR2-3 — not an upstream attempt
    attempts++
    resp, err := dispatch(ctx, model, ...)         // serveAdapter{NonStream,Stream} core
    if err == nil { served = model; break }        // success → break; bill ONCE (Q-H)
    code, retriable := isRetriableUpstream(err)     // 502/504 only (Q-C)
    if !retriable { writeTerminal(code); return }   // non-retriable → terminal, no failover
    slog(routing_action=failover, from=model, to=next); failoverTotal.Inc()  // Q-I
    if attempts >= MaxFailoverAttempts || ctx.Err() != nil { break }  // BR2-2
}
if served == "" { writeTerminal(lastErr) ; return } // exhausted → last 502/504 envelope
w.Header().Set("X-He-Selected-Model", served)       // Q-F — the FINAL served model
// non-stream: write body + TPMDeduct(served usage) ONCE (BR2-4)
// stream:     proceed normally from the flushed point
```
