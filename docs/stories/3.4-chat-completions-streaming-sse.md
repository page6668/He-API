### AC1: SSE Happy Path — Chunked Delivery, Event Framing, `[DONE]` Terminator

**Scenario**
```gherkin
GIVEN the api-gateway binary built from apps/api-gateway/cmd/server, started on :8080, with HE_API_AUTH_SVC_URL pointing at a reachable auth-svc and HE_API_REDIS_URL pointing at a reachable Redis 7.2+ instance
AND a valid api_keys row exists (issued via the Story-3.2 IssueKeyForTest helper / Story-3.3 scripts/issue-test-key.sh) so the bearer-auth middleware admits the request
AND the Story-3.3 ChatCompletionsHandler has been extended with the Story-3.4 SSE dispatch fork (no separate route registration — same POST /v1/chat/completions)
WHEN a client issues `POST /v1/chat/completions` with header `Authorization: Bearer he-abc123XYZ...` and body:
  ```json
  {
    "model": "qwen-max",
    "messages": [
      {"role": "system", "content": "You are helpful."},
      {"role": "user", "content": "Say hi."}
    ],
    "stream": true,
    "temperature": 0.7
  }
  ```
THEN
  - the bearer-auth middleware (Story 3.2) admits the request and populates `r.Context()` with `APIKeyID` / `BearerUserID` / `Scope` (unchanged from Story 3.2 BR-1.4 — the SSE dispatch reads these via `middleware.APIKeyIDFromContext` / `middleware.BearerUserIDFromContext`; missing context values short-circuit to HTTP 500 with `500_gateway_misconfigured` per the project precedent at `apps/api-gateway/internal/handlers/2fa_disable.go:38`)
  - the handler decodes the JSON body via the **same** `http.MaxBytesReader(w, r.Body, 1<<20)` + `validateChatRequest` pipeline that Story 3.3 ships (BR-1.1; no parallel parser)
  - on validation success **with `req.Stream == true`**, the dispatch forks to `serveStream(w, r, &req, apiKeyID)` BEFORE writing any response bytes (i.e., headers + body are owned exclusively by the streaming pipeline; no half-written non-streaming response is possible)
  - the response carries headers (set BEFORE the first `Flush()`):
    - `Content-Type: text/event-stream; charset=utf-8`
    - `Cache-Control: no-cache, no-transform`
    - `Connection: keep-alive`
    - `X-Accel-Buffering: no`   (defence against any future nginx-style proxy that buffers — OpenAI sets this; we mirror)
  - the response status is HTTP 200 (NOT 206 — SSE rides on a normal 200 per spec)
  - the response carries the standard SecurityHeaders bundle from the existing Story-2.2 middleware (CSP / HSTS / X-Frame-Options); NO `Set-Cookie`, NO `X-He-Request-Id` header (request-id taxonomy lands in Story 3.6), NO `X-He-Selected-Model` (selected-model header lands when Smart Routing in Story 6.x materializes)
  - the response body is a sequence of SSE events, EACH framed exactly as `data: <single-line JSON>\n\n` (two LFs — SSE spec §9.2.6), in this exact order:
    1. Role-bootstrap chunk (first chunk per OpenAI SSE convention — only carries the assistant role, no content yet):
       ```json
       {"id":"chatcmpl-mock-<12-hex>","object":"chat.completion.chunk","created":1715000000,"model":"qwen-max","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}
       ```
    2. N content chunks (N ≥ 2 — mock chunker MUST split `handlers.MockContent` into at least 2 word-boundary pieces; default split target is ~8 chunks across the 56-char string):
       ```json
       {"id":"chatcmpl-mock-<same-12-hex>","object":"chat.completion.chunk","created":1715000000,"model":"qwen-max","choices":[{"index":0,"delta":{"content":"Hello "},"finish_reason":null}]}
       ```
    3. Terminal chunk (zero delta, `finish_reason: "stop"`):
       ```json
       {"id":"chatcmpl-mock-<same-12-hex>","object":"chat.completion.chunk","created":1715000000,"model":"qwen-max","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}
       ```
    4. Literal SSE sentinel — NOT JSON, NOT inside a `data:` JSON object — emitted as the bytes `data: [DONE]\n\n` so the OpenAI SDK iterator terminates cleanly:
       ```text
       data: [DONE]

       ```
  - the same `id` (`chatcmpl-mock-<12-hex>`) is reused across ALL chunks in the response (matches OpenAI's contract — one completion-id per request, threaded through every chunk)
  - the same `created` (Unix seconds) is reused across all chunks (timestamp captured ONCE at stream start, NOT per-chunk wall-clock — matches OpenAI's contract; the chunks are the same logical completion)
  - the same `model` value (echoed from the request body verbatim, BR-1.6 inherited from Story 3.3) is reused across all chunks
  - the structured log line is emitted exactly ONCE at stream completion (NOT per-chunk — BR-1.8 inheritance) with `event=chat_completions_stream` + `model` + `api_key_id` + `messages_count` + `chunks_emitted` + `ttfb_ms` + `total_ms` slog attributes
```

|----|------|
| BR-1.1 | The SSE dispatch lives INSIDE `ChatCompletionsHandler.ServeHTTP` as a `if validated.Stream { h.serveStream(...) ; return }` fork after `validateChatRequest` succeeds. The fork MUST be the ONLY edit to Story 3.3's existing `ServeHTTP` flow — body-size + JSON parse + role validation are SHARED with the non-streaming path (BR-2.5 inheritance: pure `validateChatRequest` function is the single validation implementation backing both ACs across Stories 3.3 + 3.4). The Story-3.3 `if req.Stream { return 501 }` branch inside `validateChatRequest` is REMOVED (it was a placeholder explicitly anticipating Story 3.4 supersession per Story 3.3 BR-2.3); the function's signature stays unchanged. |
| BR-1.2 | SSE event framing follows W3C EventSource §9.2.6 verbatim: each chunk MUST be written as exactly `data: ` + single-line JSON + `\n\n` (LF LF — NOT CR LF, NOT bare LF — the double-LF is the event terminator). Multi-line JSON payloads are NOT used (each chunk's JSON is single-line — no pretty-printing). The terminator `data: [DONE]\n\n` is a literal byte sequence — NOT a JSON object containing the string `[DONE]` — this is the OpenAI extension that the official SDK consumes to terminate its iterator. |
| BR-1.3 | The chunk shape MUST be the OpenAI `chat.completion.chunk` object: `id` / `object` / `created` / `model` / `choices[{index, delta, finish_reason}]`. The `delta` field is `{role: "assistant"}` for the first (bootstrap) chunk, `{content: "..."}` for each content chunk, `{}` for the terminal chunk. `finish_reason` is `null` for bootstrap + content chunks, `"stop"` for the terminal chunk. NO `usage` field is emitted in chunks — OpenAI's protocol places `usage` in the final non-streaming response only; for SSE, `usage` would require the optional `stream_options.include_usage` extension, which is OUT OF SCOPE for this Story (defer to Epic 4 when the real adapter can report token counts). |

| BR-1.5 | `created` is captured ONCE at stream entry via `h.now().UTC().Unix()` and threaded unchanged through every chunk (Unix seconds; ±5s skew tolerance for tests, BR-1.5 inheritance from Story 3.3). This matches OpenAI's "one completion = one created timestamp" contract — chunks share a logical completion identity. |
| BR-1.6 | `model` is echoed verbatim from `req.Model` (BR-1.6 inheritance from Story 3.3 — no remapping; smart routing's per-Story-6.x model selection is the only place that would alter this) and threaded unchanged through every chunk. |
| BR-1.7 | The chunk `object` field is the literal string `chat.completion.chunk` (NOT `chat.completion` — that is the non-streaming object Story 3.3 emits; the two are distinct OpenAI types). |
| BR-1.8 | Structured logging emits EXACTLY ONE log line per accepted streaming request, at stream completion (success OR mid-stream client-disconnect), with attributes: `event="chat_completions_stream"` + `slog.String("model", req.Model)` + `slog.String("api_key_id", apiKeyID)` + `slog.Int("messages_count", len(req.Messages))` + `slog.Int("chunks_emitted", N)` + `slog.Int64("ttfb_ms", ttfbMs)` + `slog.Int64("total_ms", totalMs)` + `slog.Bool("client_disconnected", boolean)`. The Story-3.3 marker `event=chat_completions_stream_rejected` retires entirely (no longer reachable — the 501 path is gone). |
| BR-1.9 | The handler MUST propagate `r.Context()` through every layer (`serveStream(w, r, ...)` → `streaming.NewWriter(w)` → `chunker.Stream(ctx, writer)`). `r.Context()` is the cancellation signal for client disconnects (Go's `http.Server` cancels the request context when the client closes the connection — see `net/http` docs); the chunker MUST honour `ctx.Done()` between chunks and exit cleanly (drain in-flight write, no goroutine leak, emit the BR-1.8 log line with `client_disconnected=true`). The OTel trace context from `obs.WrapHTTPHandler` (`cmd/server/main.go:258`) propagates through this same `ctx` — DO NOT substitute `context.Background()` anywhere in the streaming path. |
| BR-1.10 | The SSE response MUST be written with `http.ResponseController.Flush()` (Go 1.20+ preferred form) — NOT the legacy `w.(http.Flusher).Flush()` cast — because the latter does not survive middleware that wraps the ResponseWriter. `obs.WrapHTTPHandler` (Story 1.5 `packages/go-observability`) wraps the writer; the controller form unwraps it correctly. If `Flush` returns an error (writer is not Flushable, or the connection has dropped), the chunker exits with `client_disconnected=true` and the BR-1.8 log line. |

### AC2: TTFB Performance Budget — In-Process P95 ≤ 300ms

**Scenario**
```gherkin
GIVEN the api-gateway built with the Story-3.4 SSE pipeline wired and the Story-3.3 mock content path in place
AND a stub id factory injected via `handlers.WithIDFactory(...)` (so the test does not pay the `crypto/rand.Reader` cost which Epic 4 will eventually replace anyway)
AND a stub `now` injected via the existing `h.now` indirection (so created-timestamps are deterministic; the test does NOT measure clock-sourcing variance)
WHEN the test issues 100 in-process requests via `httptest.NewRecorder` + `http.NewRequest`, each with body `{"model":"qwen-max","messages":[{"role":"user","content":"hi"}],"stream":true}`, recording for each request the wall-clock duration from `http.HandlerFunc.ServeHTTP` invocation to the moment `Content-Type: text/event-stream` is observed in the recorder's header map AND at least one body byte has been written
THEN
  - the test asserts P95 of the 100 measurements ≤ 300 ms (the epic AC). On a developer M-series MacBook with no contention, the actual measured P95 SHOULD be well under 50 ms — the 300 ms budget exists to cover (a) the JSON-decode of large prompts, (b) future Epic-4 upstream first-byte latency, (c) CI runner variance. This Story's chunker is in-process + mock, so the 300 ms budget is loose but it is the epic-level SLO and MUST be enforced.
  - the test asserts P99 of the 100 measurements ≤ 600 ms (loose ceiling — catches gross regressions like accidentally adding a `time.Sleep` in the chunker, or accidentally calling crypto/rand on every chunk instead of once at stream entry; this is NOT the SLO, just a sanity floor)

WHEN the SAME test is repeated against a `httptest.NewServer` (real loopback TCP, not in-process recorder) to ensure the in-process recorder isn't masking a latency contribution
THEN
  - P95 ≤ 300 ms still holds (loopback TCP adds ~50µs per request — negligible against the budget)
  - The two-mode comparison (recorder vs httptest.NewServer) MUST be in the same test function so a future regression in the in-process path can't accidentally pass while the wire-level path silently exceeds the budget
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | TTFB is measured from `ServeHTTP` entry to the moment the FIRST `Flush()` succeeds (i.e., the bootstrap role chunk has been written to the wire). The bootstrap chunk is intentionally NOT batched with the first content chunk — the explicit `delta:{role:"assistant"}` chunk gives the client a sub-millisecond signal that the stream is live, which is the entire point of streaming. Future Stories MAY collapse role+content if benchmarks justify, but this Story's contract is "two separate chunks: role then first content". |
| BR-2.2 | The chunker emits ALL chunks in a single goroutine (no fan-out, no producer/consumer pattern, no buffered channel). This is the simplest correct implementation; concurrency complexity is deferred to Epic 4 where the real upstream provides a `<-chan ChatChunk` that genuinely needs a pump. For the mock, a `for i, piece := range pieces { write; flush }` loop is the entire chunker body. The slog stream-completion line is emitted by the same goroutine after the loop. |
| BR-2.3 | Between content chunks the chunker does NOT sleep (`time.Sleep`) or rate-limit. The mock's purpose is to verify the SSE pipeline mechanics — adding artificial latency to "feel like a real LLM" would be theatre and would actively obscure regressions in the pipeline. Epic 4's real upstream provides actual per-token latency; do NOT pre-emulate it here. |
| BR-2.4 | The TTFB measurement test MUST run with `-race` clean (no data races between the chunker goroutine and the test's stop-clock observation). The test reads the response headers + body bytes through `httptest.NewRecorder` (which is goroutine-safe per Go stdlib docs) and via `bufio.Scanner` on `resp.Body` for the loopback variant. |
| BR-2.5 | The TTFB SLO is an in-process / loopback measurement — NOT a production-network SLO. The "real" production SLO (incorporating client→edge TLS handshake + WAN RTT) is OUT OF SCOPE for this Story; it lands in Story 9.x when the analytics-svc materializes per-request `ttfb_ms` from `request_logs` ClickHouse data. This Story's 300 ms budget governs the gateway-internal latency contribution ONLY. |
| BR-2.6 | If the in-process P95 measurement REGRESSES the budget on the CI runner (unexpected on the mock path — would indicate a serious regression), the test fails the build and Dev MUST investigate before re-running. There is NO retry / quarantine — flaky perf assertions silently erode the SLO. The 300 ms budget is intentionally 6× the expected mock measurement so it is NOT a flake risk. |

### AC4: Mid-Stream Cancellation, Disconnect Handling, and Resource Hygiene

**Scenario**
```gherkin
GIVEN the api-gateway built with the Story-3.4 SSE pipeline
AND a stub id factory via `handlers.WithIDFactory(...)` + stub `h.now` (deterministic timing for assertions)
WHEN a Go integration test issues a streaming request via `httptest.NewServer`, reads the first chunk from the response body, then cancels the request's context via `cancel()` on a `context.WithCancel(req.Context())` set up at request-construction time
THEN
  - the gateway-side chunker observes the cancellation BEFORE writing the next chunk (the chunker MUST check `ctx.Done()` between each chunk emission per BR-1.9; the test deterministically proves this by inserting a stub time.Sleep ONLY in the test's `now` injection — NOT in the chunker — so the test can race the cancel against the chunker's `select { case <-ctx.Done(): return ; default: }` guard)
  - the chunker exits the loop without writing a partial chunk (the SSE event terminator `\n\n` is the framing boundary — a half-written `data: {...}` without the terminator is the failure mode this test guards against)
  - the structured log line carries `client_disconnected=true` AND `chunks_emitted` < total mock chunks (proving early exit)
  - NO goroutine leak: the test runs under `t.Cleanup(func() { goleak.VerifyNone(t) })` (or equivalent) — the chunker's goroutine MUST have returned by the time the test cleanup runs
WHEN a Go integration test issues a streaming request and the test client closes the underlying HTTP connection mid-stream (via `httptest.NewServer.CloseClientConnections()` or by closing the `resp.Body` reader)
THEN
  - the gateway-side `http.ResponseController.Flush()` returns a non-nil error on the next attempt (the connection is gone)
  - the chunker exits cleanly on the Flush error (BR-1.10), recording `client_disconnected=true` + `flush_error=<error string>` in the structured log line
  - no panic, no log spam, no retry loop
WHEN a Go unit test invokes the mock chunker DIRECTLY (without an HTTP layer) with a `streaming.Writer` stub that records every `WriteEvent` call
THEN
  - the recorded events match the BR-1.2/BR-1.3 contract: 1 bootstrap + N content + 1 terminal + 1 `[DONE]` sentinel
  - the order is deterministic — the same `req.Model` + injected id always produces the same event sequence (mock determinism mirrors Story 3.3 BR-4.3 input-invariance)
  - the chunks split at WORD boundaries: splitting `"Hello from He-API mock. Real upstream lands in Story 4.x."` MUST produce a chunk sequence where each non-bootstrap non-terminal `delta.content` is either a single word, or a single word followed by its trailing space — NEVER a partial word like `"He"` followed by `"llo "` (this guards against future "split by char count" regressions that would look identical in concatenation but mid-word splits stress-test SDK Pydantic parsers in ways that real-LLM token boundaries do not — real adapters split at TOKEN boundaries, which are sub-word but always within UTF-8 codepoint boundaries; for the mock, word-boundary is the closest faithful approximation)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | The chunker's emit loop is `for i, piece := range pieces { select { case <-ctx.Done(): return ; default: } ; writer.WriteEvent("", marshal(chunk)); writer.Flush() }`. The `select` MUST come BEFORE the write (NOT after) so a context cancellation prevents writing a chunk that the client will never see. Between the select and the Flush, a context cancellation MAY result in writing a chunk that the client doesn't observe — this is acceptable per the SSE spec (clients may miss the last in-flight chunk on disconnect); the test relaxation is that we don't write ADDITIONAL chunks after detecting cancellation. |
| BR-4.2 | Goroutine hygiene: the chunker is in the request goroutine (BR-2.2). There is NO `go func() { ... }()` spawn anywhere in the streaming path for this Story. Future Stories (Epic 4 real upstream) WILL introduce a producer goroutine that reads from the adapter's `<-chan ChatChunk`; goroutine-leak prevention there is Epic 4's design problem. For this Story, the absence of spawned goroutines makes leak-checking trivially pass — the test assertion is defensive (catches a future regression that adds an unnecessary goroutine). |
| BR-4.3 | Word-boundary chunking: `splitContentIntoChunks(s string, targetN int) []string` is a pure function. Implementation: split the input string on whitespace boundaries (Unicode-aware via `unicode.IsSpace`), then merge contiguous tokens to produce approximately `targetN` chunks of roughly equal byte length. For the canonical `MockContent` (10 words: "Hello", "from", "He-API", "mock.", "Real", "upstream", "lands", "in", "Story", "4.x.") with `targetN=8`, the function produces 8 chunks (some chunks containing 1 word, others 2). The exact split is deterministic and tested via a table-driven test asserting the byte-exact output for the canonical input. |
| BR-4.4 | The `streaming.Writer` interface is small and stable: `WriteEvent(event string, data []byte) error` (the `event` arg is "" for the unnamed `data: ...` events this Story emits; future Stories MAY use named events like `event: error\ndata: ...` for SSE-encoded errors) + `Flush() error` + `Close() error`. The implementation is a single struct over `http.ResponseWriter` + an `http.ResponseController` per BR-1.10. NO buffer pooling, NO write coalescing — those are premature optimizations the in-process P95 measurement does not need (AC2 budget is 6× the expected mock-path measurement). |
| BR-4.5 | `[DONE]` sentinel emission is the streaming.Writer's responsibility — it MUST be called via a dedicated `WriteDone() error` method on the Writer (NOT a `WriteEvent("done", nil)` call that the receiver would mis-parse). The method emits the literal bytes `data: [DONE]\n\n` and `Flush()`es. The OpenAI SDK iterator recognizes ONLY this exact sentinel — any variant (`data:[DONE]\n\n` without the space, or `data: [DONE]\n` with a single LF) breaks the SDK's iterator termination. The test asserts the byte-exact wire output for this sentinel via a recorder. |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Context cancelled mid-stream | n/a | n/a | Chunker exits loop on next `<-ctx.Done()` check; structured log line emitted with `client_disconnected=true` + `chunks_emitted=N_actual` (BR-1.9 / BR-4.1) |
| Flush fails mid-stream (TCP write error) | n/a | n/a | Chunker exits loop on Flush error; structured log line emitted with `client_disconnected=true` + `flush_error=<err.Error()>` (BR-1.10) |
| Writer.Close fails after stream ends | n/a | n/a | Best-effort log at WARN level (`event=sse_writer_close_failed` + `error`); do NOT panic; do NOT retry — the response is already complete (the structured log line at BR-1.8 was emitted before Close) |

| Ruling | Question | Decision | Mechanism / Where Encoded | Forward Implication |

| **AR1-R1** (was OQ1) | Word-boundary chunking vs token-boundary for the mock chunker | **APPROVE word-boundary** — preserve `BR-4.3` as written | `BR-4.3` (unchanged); `splitContentIntoChunks` uses `unicode.IsSpace` boundary detection per T2.2 | Epic 4 real adapters split at upstream-token boundaries (sub-word, codepoint-safe); the mock does NOT forward-emulate. ## Dev Notes

### Technical Constraints

- **SSE framing fidelity (BR-1.2 / BR-4.5)** — The wire output MUST conform to W3C EventSource §9.2.6 verbatim: `data: ` (with trailing space) + single-line JSON + `\n\n` (LF LF). The OpenAI SDK's iterator parser depends on this exact byte sequence; ANY deviation (`data:` without space, CRLF instead of LF, double-LF using `\r\n\r\n`) breaks SDK consumption silently. Reference: the `openai` Python SDK reads chunks via `httpx`'s SSE parser; the parser is W3C-spec-compliant + recognizes the OpenAI-specific `data: [DONE]` terminator. There is no graceful-degradation path for malformed framing — it surfaces as `openai.APIError: Could not parse server response`. The byte-exact assertion in 3.4-UNIT-001 + 3.4-UNIT-003 + 3.4-INT-007 is the load-bearing wire-contract guard.

- **Streaming response is "headers committed early" (BR-1.1)** — Once `Writer.WriteEvent` is invoked for the first time, the HTTP response headers (status 200 + Content-Type text/event-stream) are written to the wire. After this point, an OpenAI-style JSON error envelope is NO LONGER WRITABLE — the response is already a `text/event-stream`. This is why ALL validation (`MaxBytesReader`, `json.Decode`, `validateChatRequest`) runs BEFORE `serveStream` is invoked. The dispatch fork in `ServeHTTP` MUST come AFTER validation, NOT before — a wrong-order edit would let a malformed body trigger a half-written SSE response (no status code, no error envelope, just a dropped connection). The unit test `3.4-INT-007` (golden-file byte-equality on the non-streaming path) is the regression guard for this invariant — if a future edit accidentally moves the dispatch fork BEFORE validation, the non-streaming golden test fails because the non-streaming response shape changes.

- **TTFB is in-process / loopback only (BR-2.5)** — The 300 ms TTFB budget in AC2 is measured at the gateway boundary (handler entry → first byte to wire). The "real" production SLO (incorporating client→edge TLS handshake + WAN RTT) is OUT OF SCOPE for Story 3.4. Production TTFB is observed via the analytics-svc `request_logs.ttfb_ms` column (`[Source: docs/architecture/data-models.md#4-数据模型data-models]` §4.2 — ClickHouse `request_logs` table already has the `ttfb_ms UInt32` column reserved for streaming traffic, set by Story 9.1 when analytics-svc materializes). The gateway-side test budget is intentionally loose (6× the expected mock measurement) because (a) CI runner variance is unpredictable, (b) Epic 4's real upstream will add measurable latency, (c) this Story owns the gateway's contribution alone.

- **`obs.WrapHTTPHandler` ResponseWriter wrapping (BR-1.10)** — The OTel HTTP wrap (`[Source: docs/architecture/source-tree.md#6-源代码组织source-tree]` `packages/go-observability/` — Story 1.5) wraps the `http.ResponseWriter` to capture status/bytes for the span. That wrapper does NOT implement `http.Flusher` directly (the OTel wrapper from `go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp` only implements `http.Hijacker` + `http.Pusher` interfaces conditionally). The `http.ResponseController` form (Go 1.20+) IS the only correct way to flush through middleware-wrapped writers — it walks the wrapper chain looking for the underlying `http.Flusher`. The unit test `3.4-UNIT-005` asserts this — the test wraps the recorder in a no-Flusher decorator to PROVE the ResponseController fallback works. A regression that reverts to `w.(http.Flusher).Flush()` would fail this test loudly.

- **Word-boundary chunking is mock-only (BR-4.3)** — Real LLM upstreams emit chunks at TOKEN boundaries (sub-word, but always within UTF-8 codepoint boundaries — the BPE tokenizers used by Qwen / DeepSeek / Kimi / etc. produce 1-4 byte tokens). The Story 3.4 mock uses WORD boundaries (`unicode.IsSpace`-delimited tokens) because (a) word-boundary splits stress-test SDK parsers in ways that mid-token splits do not (the SDK absorbs both, but a mid-word split that accidentally violates UTF-8 codepoint boundaries would surface as a JSON-unicode-decode failure — the mock avoids this concern entirely by using word boundaries which are always codepoint-safe), (b) it produces a chunk count (~8 for the canonical `MockContent`) that is realistic for the test's "≥2 chunks" assertion without being inflated, (c) Epic 4's real adapter's per-token emit pattern will be the actual production wire contract — the mock should NOT pretend to match it.

- **The `stream` field is "boolean, default false" — the JSON-decoder zero-value is correct (BR-1.1)** — Story 3.3's `ChatRequest.Stream` is `bool` (not `*bool`); the `encoding/json` zero-value behavior maps "field omitted" or `"stream": false` to `false` — which is exactly the Story 3.3 non-streaming default. NO change to the `Stream` field type is required for Story 3.4. The dispatch test `3.4-INT-006` (omitted stream field → non-streaming response) is the regression guard.

- **Story 3.2 BR-2.8 + Story 3.3 OQ1 import-graph guard is preserved** — Story 3.3's `apikey-seed-boundary-guard` CI job (in `.github/workflows/lint.yml`) asserts no production binary depends on `apps/auth-svc/internal/apikey`. Story 3.4 introduces a NEW package `apps/api-gateway/internal/streaming/` — this package does NOT depend on `apikey` (it depends only on `net/http` + stdlib + `apps/api-gateway/internal/handlers` for `MockContent`). The CI job's invariant is preserved. Dev MUST run `go list -deps ./apps/api-gateway/internal/streaming` once during T2 implementation and verify the dependency list contains zero `apps/auth-svc/internal/apikey` entries.

- **Cold-start preservation (T5.1 / inherited from Story 3.1)** — Story 3.1 AC2 set a hard 1000-ms P95 cold-start SLO. The new `internal/streaming/` package has NO `init()` functions, NO package-level `sync.Once` allocations, NO global state beyond the `ErrFlushUnsupported` error sentinel (a one-line `errors.New` — sub-microsecond init cost). The handler constructor `NewChatCompletionsHandler` is unchanged (the SSE dispatch is a method on the existing struct, not a new constructor). No measurable cold-start impact expected; the developer MUST still run the Story-3.1 `BenchmarkColdStart` benchmark once and record the result in Dev Log per T5.1.

- **Story 3.3 non-streaming path is BYTE-FOR-BYTE preserved (BR-1.1)** — The Story 3.4 edits to `chat_completions.go` are confined to (a) removing the `if req.Stream { return 501 }` branch in `validateChatRequest` (T3.4), (b) adding the `if req.Stream { h.serveStream(...) ; return }` dispatch in `ServeHTTP` (T3.3). The non-streaming code path (`mockChatCompletionResponse(&req, h.newID(), h.now()) → writeChatJSON(w, 200, resp)`) is unchanged. The golden-file regression test 3.4-INT-007 captures the byte-exact non-streaming response BEFORE Story 3.4 implementation begins and re-asserts it AFTER — this is the load-bearing guard for "we didn't accidentally regress Story 3.3".

- **PII redaction inheritance (BR-1.8)** — Story 3.3 BR-1.8 forbids logging `messages[].content`. Story 3.4 inherits the rule AND extends it: NEVER log emitted chunk deltas. The mock's `MockContent` is non-PII, but disciplining the structured-log path to never learn the habit of logging deltas matters for Epic 4 where the real adapter MAY emit user-data-derived deltas. The test `3.4-INT-009` asserts the captured log buffer does NOT contain a sentinel string in the request `messages[].content` — this is the exact pattern Story 3.3 UNIT-016 established.

// and Content carry `omitempty` because the three chunk shapes per BR-1.3

//   - bootstrap chunk: Role="assistant", Content="" (omitted)  → delta:{"role":"assistant"}

    Content string  `json:"content,omitempty"`

### Open Questions — Architect Round 1 Rulings

These rulings are durable contracts; SM must encode each as a `BR-x.x` in the revised story so Epic 4 streaming adapters and Story 3.5+ inherit them.

- **OQ1 — Word-boundary chunking vs token-boundary**: **APPROVE word-boundary** (BR-4.3 as written). Rationale: (a) the mock's purpose is to verify the SSE pipeline mechanics, NOT to pretend to be a real BPE tokenizer; (b) word boundaries are codepoint-safe, removing a second-order UTF-8-validity failure mode that mid-byte BPE splits could introduce in test harnesses; (c) Epic 4's real adapter contract tests will be re-derived from the real adapter's emit pattern anyway (token counts are non-deterministic across upstream versions) — the mock's split granularity does NOT need to forward-emulate. SM action: no change required to BR-4.3.

- **OQ2 — Terminal chunk delta shape `{}` vs `{"content":""}`**: **APPROVE `{}` via `omitempty` on Role + Content** (current design per BR-1.3 + T2.4 chatChunkDelta types). Rationale: He-API IS the OpenAI-compatible gateway. The contract value is that `openai==1.40.*` (and any downstream SDK that follows the OpenAI spec) gets byte-identical wire output to a direct OpenAI call. The `{}` shape is OpenAI's canonical emission for the terminal chunk; matching it removes a class of "behaves slightly differently from real OpenAI" bug reports. The defensive `{"content":""}` variant is appropriate for adapters routing OpenAI-incompatible upstream to OpenAI-compatible downstream — not our role. SM action: no change required; the `omitempty` discipline on `chatChunkDelta.Role` + `chatChunkDelta.Content` IS the mechanism — preserve the existing field tags verbatim.

- **OQ3 — `WriteDone()` dedicated method vs `WriteEvent("", []byte("[DONE]"))`**: **APPROVE dedicated `WriteDone()`** (BR-4.5 as written). Rationale: (a) wire output is byte-identical either way; (b) the dedicated method is self-documenting at call sites (the chunker's tail says `w.WriteDone()` — intent is unambiguous); (c) defence against a future regression where a generic `WriteEvent("", []byte("[DONE]"))` path accidentally JSON-quotes the body (emitting `data: "[DONE]"\n\n` which breaks the OpenAI SDK iterator silently). Cost is one extra interface method — trivial. SM action: no change required.

- **OQ4 — `RegisterFirstFlushHook` on Writer vs `chunker returns firstFlushAt time.Time`**: **APPROVE the return-value approach; DROP the hook**. Rationale: the streaming `Writer` interface is a wire-format primitive (event framing, byte serialization, flush). Clock-capturing is an observability concern that belongs in the chunker (which already owns the per-chunk flush loop per T2.3 and is the natural source-of-truth for both `chunksEmitted` and "the moment of the first flush"). Bubbling `firstFlushAt time.Time` up via `Stream(ctx, writer) (chunksEmitted int, firstFlushAt time.Time, err error)` keeps the Writer interface narrow and avoids growing the interface every time a new observability dimension is added (next request would be `RegisterBytesWrittenHook`, etc.). SM action: REVISE — (a) **DROP T3.2** entirely (the Writer-interface hook extension is removed); (b) **UPDATE T2.3** signature to `func (c *MockChunker) Stream(ctx context.Context, w Writer) (chunksEmitted int, firstFlushAt time.Time, err error)` — `firstFlushAt` is set immediately before the first `w.Flush()` call inside the chunker; (c) **UPDATE T3.1** to compute `ttfbMs := firstFlushAt.Sub(start).Milliseconds()` from the chunker's return value (NOT a hook callback); (d) **UPDATE T2.3 / test 3.4-UNIT-022** to assert the returned `firstFlushAt` is set after the bootstrap chunk's `WriteEvent` but BEFORE the first content chunk (i.e., AT the first Flush — the chunker captures `firstFlushAt = time.Now()` immediately before invoking `w.Flush()` the first time); (e) **REMOVE the planned `3.4-UNIT-023`** (no hook ordering invariant to test); (f) **UPDATE Dev Notes "Data Models"** `MockChunker.Stream` signature line (currently line 777) to the new three-return signature.
