## Story

**As a** developer building on the He-API OpenAI-compatible platform,
**I want** to synthesize speech by POSTing a JSON body (`{model, input, voice, ...}`) to the standard `POST /v1/audio/speech` endpoint with the OpenAI Audio-Speech request shape, and receive the spoken audio as a binary response (`audio/mpeg` etc.), routed under the hood to Doubao (Volcano Engine) TTS,
**so that** my existing OpenAI-SDK text-to-speech code (`client.audio.speech.create(...)`) works unchanged against He-API, closing the synthesis (text→speech) half of the epic's "图像/语音多模态 API 可调通" promise.

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | **JSON ingestion + BINARY response (NEW response shape)**: the handler reads the body under `http.MaxBytesReader(w, r.Body, maxSpeechBodyBytes)` then `json.NewDecoder(...).Decode(&req)` with `DisallowUnknownFields` (the chat/embeddings idiom). The RESPONSE is the raw audio bytes (`w.Header().Set("Content-Type", mimeFor(response_format))`, `Content-Length`, `w.Write(audio)`) — the FIRST non-JSON/non-SSE body in the gateway. Non-JSON content-type or malformed JSON → `400_invalid_request` (the canonical §5.1.2 family). This does NOT touch the multipart `/v1/audio/transcriptions` path. |
| BR-1.2 | **OpenAI-speech field schema**: `model` required, non-empty, ≤ `modelMaxLen` (100, matching `he_api.models.id VARCHAR(100)`). `input` required, non-empty, ≤ `maxSpeechInputChars` (4096, OpenAI parity — AC4 BR-4.2). `voice` required, non-empty, in the resolved voice set (Q-TTS-MODELID; unknown → 400). `response_format` optional ∈ {`mp3`,`opus`,`aac`,`flac`,`wav`,`pcm`}, default `mp3`; an unsupported-in-9.7 value (e.g. `pcm` if deferred) → 400 (Q-TTS-RESPFORMAT). `speed` optional float ∈ [0.25, 4.0], default 1.0; out-of-range → 400. ### AC4: 输入/输出安全与限额 — 入参字符上限 + 二进制出参限界 + 输入内容安全 + PII 不外泄（非协商安全契约）

**Scenario**
```gherkin
GIVEN
  - `/v1/audio/speech` ingests JSON (`input` text) and returns a BINARY audio body — a NEW surface vs every JSON endpoint: an unbounded synthesis is a memory/DoS vector on the OUTPUT side; the `input` text AND the synthesized audio are user PII; the `input` text (unlike 9.6's opaque audio) IS within the 8.2 lexicon scope and MUST be scanned

Exceeding → `413_payload_too_large`. After decode, `len([]rune(input)) > maxSpeechInputChars (4096)` → `400_invalid_request` (param=`input`) — this is ALSO the billing lever (AC3), so it is a HARD cap
  - **Output audio bound**: the synthesized audio is capped at `maxSynthesizedAudioBytes` (a generous bound, e.g. a few MiB — Q-TTS-LIMITS ratifies); the adapter/gateway abort + return `502`/`413` if the upstream produces more, so a malicious/huge synthesis cannot exhaust memory.   - **Content-safety on INPUT (NEW vs 9.6)**: the `input` text is scanned by 8.2 at the per-Key strictness (8.4) BEFORE dispatch (BR-1.7) — a flagged input → `400_content_filter` (8.5), zero upstream call. (9.6's audio bytes were un-scannable; TTS input is plain text → it MUST be scanned. The synthesized OUTPUT audio is NOT scanned — it is model output, like chat completion content / the 9.6 transcript.)
  - **PII / secret discipline (NON-NEGOTIABLE)**: the `input` text AND the synthesized audio bytes are NEVER written to logs, slog fields, span attributes, error messages, or analytics records (cascade: 9.4 BR-TR-7 spans, 9.2 BR-RD-9 logs, 9.3 BR-EX-12 exports; the 9.6 audio-PII discipline; the 3.5 embeddings precedent logs only SIZE signals). Structured logs carry only non-PII signals (model, api_key_id, character_count, voice, response_format, audio_bytes_size). Error envelopes reference the field name (`input`), never the text
  - **Reject ordering (fail-closed, pre-dispatch)**: all AC4 input validations (body size, char cap, field schema) + content-safety run BEFORE the speech-capability gate dispatch / any upstream call — a rejected request makes ZERO upstream calls and incurs ZERO usage/billing (the 9.5 BR-3.6 / 9.6 BR-4.5 / 8.2 discipline)
  - **No durable audio**: the gateway streams the synthesized bytes to the response and retains NOTHING — no audio written to any disk/store/cache (no temp files, since the request is JSON not multipart — simpler than 9.6)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | **Input body cap**: `maxSpeechBodyBytes` (small, e.g. `64<<10`) read cap via `http.MaxBytesReader` BEFORE JSON decode; `>` → `413_payload_too_large`. Distinct `const` in `audio_speech.go` (the 3.5 per-endpoint-cap precedent — caps diverge per endpoint). The body is JSON (no multipart temp-file machinery — simpler than 9.6's `ParseMultipartForm`). |
| BR-4.2 | **Input char cap (HARD — billing lever)**: `len([]rune(input)) ≤ maxSpeechInputChars (4096, OpenAI parity)`; `>` → `400_invalid_request` (param=`input`). Because the char count drives cost (AC3 BR-3.4), the gateway computes it ITSELF from the validated `input` (a client cannot under-report to underpay — BR-4.5); it is enforced pre-dispatch. |
| BR-4.3 | **Output audio bound**: the synthesized audio is capped at `maxSynthesizedAudioBytes` (Q-TTS-LIMITS ratifies the exact value); the adapter (`SynthesizeResponse.audio`) and the gateway both enforce it; an over-cap synthesis → `502`/`413` + zero billing (no charge for undelivered audio). Bounds the OUTPUT memory/DoS surface that the binary response newly introduces. |
| BR-4.4 | **PII discipline (NON-NEGOTIABLE, cascade)**: the `input` text / synthesized audio bytes are NEVER logged, slog'd, span-attributed, analytics-recorded, or echoed in errors. Mirrors 9.6's audio-PII discipline + 3.5's "size signals only" + the 9.4/9.2/9.3 cascade. Logs carry model/api_key_id/character_count/voice/response_format/audio_bytes_size only. The synthesized audio (model output) is treated as PII like chat completion content (`chat_completions.go` withholds `messages[].content`). |
| BR-4.5 | **Reject ordering (fail-closed, pre-dispatch)**: body-size/char-cap/field-schema + content-safety run BEFORE the capability-gate dispatch — zero upstream call + zero usage/billing on reject (9.5 BR-3.6 / 9.6 BR-4.5 / 8.2 ordering). The char count is gateway-computed (NOT client-supplied) so it cannot be spoofed to underpay (BR-4.2). |
| BR-4.6 | **Content-safety on INPUT only (do-NOT-regress, NEW vs 9.6)**: the 8.2 scanner is fed the `input` text (a do-NOT-regress — TTS input is plain text and MUST be scanned, unlike 9.6's opaque audio); the synthesized OUTPUT audio is NOT scanned (model output, like chat completion content / the 9.6 transcript). Per-Key strictness (8.4) + the `400_content_filter` envelope (8.5) preserved. |
| BR-4.7 | **No durable audio / no temp files**: the JSON request needs no multipart temp file (simpler than 9.6); the gateway writes the synthesized bytes to the response and retains nothing on disk/store/cache. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| request body | bytes | — | ≤ `maxSpeechBodyBytes` (e.g. 64 KiB) | "Request body exceeds the maximum size." |
| `input` char count | int | yes | ≤ 4096 runes (BR-4.2) | "Field 'input' must be ≤ 4096 characters." |
| synthesized audio | bytes | — | ≤ `maxSynthesizedAudioBytes` (BR-4.3) | "Synthesized audio exceeded the maximum size." |
| any log/span/export/analytics path | — | — | `input` text / audio bytes NEVER emitted | (PII discipline BR-4.4; audited by a no-PII test) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| body > `maxSpeechBodyBytes` | 413 | "Request body exceeds the maximum size." | reject at reader (BR-4.1) |
| `input` > 4096 chars | 400 | "Field 'input' must be ≤ 4096 characters." | reject pre-dispatch (param=`input`, BR-4.2) |
| `input` trips 8.2 lexicon | 400 | "Request was blocked by the content safety filter." | canonical `400_content_filter` (BR-4.6) |
| synthesized audio over `maxSynthesizedAudioBytes` | 502 / 413 | "Synthesized audio exceeded the maximum size." | adapter/gateway abort, zero billing (BR-4.3) |
| any log/span/export path | — | `input` text / audio bytes NEVER emitted | PII discipline (BR-4.4), no-PII test |

**Examples**
- **Input**: a `POST /v1/audio/speech` with `input` of 5000 chars → **Expected**: `400_invalid_request` "Field 'input' must be ≤ 4096 characters." (param=`input`) — rejected pre-dispatch, ZERO upstream call.
- **Input**: a clean `input` "你好世界" → **Expected**: 200; the log line carries `character_count`/`voice`/`response_format`/`audio_bytes_size` but NEVER the `input` text or the audio bytes.
- **Input**: an `input` that trips the 8.2 lexicon → **Expected**: `400_content_filter` "blocked by the content safety filter." — INPUT scanned (BR-4.6), ZERO upstream call.
