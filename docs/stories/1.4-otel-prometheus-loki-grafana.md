**字面要求**: dashboard 可看到示例服务的 trace 与 metrics

**展开（Architect Round 1 Q1-Q6 仲裁完成 — 已定稿）**:

- `helm list -n monitoring` 输出 **5 个 release**：`kube-prometheus-stack` / `loki` / `promtail` / `jaeger` / `otel-collector` `[Source: docs/architecture/observability.md#11.1; docs/architecture/tech-stack.md#2.1; Architect Round 1 Q1 ruling: hybrid (umbrella + 独立 chart × 4) — 详 ## SM 决策记录 Q1 backfill; Round 1 M-2: Promtail 显式独立 release]`

- `kubectl get svc -n monitoring` 含 `prometheus-operated`（或等价）/ `grafana` / `loki` / `otel-collector` / `jaeger-query` 服务
- `kubectl get servicemonitor -n monitoring` 至少 1 个 ServiceMonitor 对应 sample-otel-app

**B. Grafana 可访问 + datasource 联通**:
- 运维通过 `kubectl port-forward svc/kube-prometheus-stack-grafana 3000:80 -n monitoring` 在本地浏览器 `http://localhost:3000` 登录（admin pwd 从 K8s Secret `kube-prometheus-stack-grafana` 中 `kubectl get secret kube-prometheus-stack-grafana -n monitoring -o jsonpath='{.data.admin-password}' | base64 -d` 获取）`[Architect Round 1 Q5 ruling: port-forward only — 本 Story 不引入 ingress; Q6 ruling: K8s Secret 自动生成密码 — OIDC 接入留 Epic 9 (observability hardening)]`
- Grafana **Configuration → Data sources** 显示至少 3 个 datasource 状态 ✅ green：
  - `Prometheus` (URL `http://<prom-svc>:9090`)
  - `Loki` (URL `http://loki:3100`)
  - `Jaeger` (URL `http://jaeger-query:16686`) `[Architect Round 1 Q2 ruling: 保留 Jaeger，per architecture §11.1]`
- 每个 datasource 点 "Save & test" 返回 success

**C. Sample 服务可观测信号完整**（字面 AC 核心证据）:
- `apps/sample-otel-app/` 部署到 `he-api-staging` namespace，pod Running，`kubectl logs` 输出结构化 JSON 日志（含 `trace_id` / `span_id` 字段，与 OTel SDK 自动注入对齐）
- 运维通过 `kubectl port-forward svc/sample-otel-app 8080:8080 -n he-api-staging` 后 `curl http://localhost:8080/hello?name=test` 触发 1 次请求（**至少 10 次以累积可见数据**）
- **Trace 可见**:
  - Grafana **Explore → Jaeger datasource** 中按 service name `sample-otel-app` 搜索 → 列表显示 ≥ 1 个 trace
  - 点开 trace 查看 span 树：含 `GET /hello` root span + 任意 children（如 `validate-input` / `compose-response` 内部 span）
  - Span 含 OTel 标准 resource attrs：`service.name=sample-otel-app` / `service.namespace=he-api-staging` / `k8s.pod.name=*` / `k8s.namespace.name=he-api-staging`
- **Metrics 可见**:
  - Grafana 打开 dashboard `Gateway 大盘`（infra/grafana-dashboards/gateway.json）→ 面板 "Request Rate" / "Error Rate" / "Latency P95" 显示 sample-otel-app 的 RED 曲线（**前提**：sample app 暴露 `/metrics` 端点 + ServiceMonitor 已 scrape）
  - PromQL `rate(http_server_request_duration_seconds_count{service_name="sample-otel-app"}[5m])` 在 Grafana **Explore** 返回非空时间序列 `[Architect Round 1 M-1: 命名遵循 OTel Semantic Conventions 1.x — Prometheus 把 OTel resource attribute service.name 转为 label service_name]`
- **Logs 可见（bonus，非字面 AC 强制）**:
  - Grafana **Explore → Loki** 输入 LogQL `{namespace="he-api-staging", app="sample-otel-app"} | json` 返回最近 5 分钟日志，含 `trace_id` 字段
- **可验证标志**:
  - 5 张截图入 dev-log：(1) `helm list` + `kubectl get pod -n monitoring`，(2) Grafana datasource 3 行 green，(3) Jaeger trace 树展开，(4) Gateway 大盘 RED 三曲线非空，(5) Loki 日志含 trace_id
  - PromQL `up{job="sample-otel-app"}` 返回 1（target healthy）

### 技术约束

- **Helm 版本**: 3.14+（chart apiVersion v2，与 1.3 一致） `[Source: docs/architecture/tech-stack.md#2.1]`
- **K8s 版本**: 1.29+（ACK 标准托管版，1.3 已部署） `[Source: docs/architecture/tech-stack.md#2.1]`
- **Prometheus**: 2.50+ / **Grafana**: 10+ / **Loki**: 3.x / **OpenTelemetry SDK**: 1.x / **Jaeger**: 1.55+ `[Source: docs/architecture/tech-stack.md#2.1; docs/architecture/observability.md#11.1; Architect Round 1 Q2 ruling]`
- **Go 版本**: 1.22+（sample-otel-app 一致 1.3 api-gateway 版本） `[Source: docs/architecture/tech-stack.md#2.1]`
- **OTel 标准**: 采用 OpenTelemetry Semantic Conventions 1.x；metric 命名 `http_server_request_duration_seconds_*`（histogram → 派生 `_count` / `_sum` / `_bucket`）/ span name 形如 `GET /hello`（HTTP method + route）`[Source: docs/architecture/observability.md#11.1]`
- **PromQL label 映射**（per Architect Round 1 M-1）: OTel resource attribute `service.name` 在 Prometheus 端被转为 label `service_name`（点号 → 下划线）；HTTP 状态码 attribute 是 `http_response_status_code`（int 类型 label，PromQL 正则匹配仍按字符串）；**禁止** 在 dashboard / alert rule 中使用旧式 `service` / `status` label — 否则 metrics 序列全部为空
- **5 大 dashboard 命名**: 严格使用 architecture §11.2 定义的 5 个名称（Gateway 大盘 / 业务大盘 / 模型大盘 / 支付大盘 / 合规大盘）；本 Story 仅实装 Gateway，其余 4 个占位 dashboard 留 title + markdown panel "Pending Epic 2-8 数据接入"（保留命名锚定）
- **架构对齐**: Metrics→Prometheus+Grafana / Logs→Loki+Promtail / Traces→OTel+Jaeger（per architecture §11.1） `[Source: docs/architecture/observability.md#11.1; Architect Round 1 Q2 ruling]`
- **Pod Security**: `monitoring` namespace 已被 1.3 设为 `pod-security.kubernetes.io/enforce: baseline`（详 `infra/k8s-base/namespace.yaml`），observability chart 默认兼容；sample-otel-app 在 `he-api-staging` (restricted) 需复用 1.3 全 6 字段 securityContext `[Source: 1.3 T8 + Architect Round 1 M-5]`
- **node-exporter 例外**（per Architect Round 1 M-3 ruling option a）: 在 staging 关闭 `nodeExporter.enabled: false`（避免 hostNetwork/hostPID/hostPath 触发 baseline PSA 违规）；节点 CPU/Mem/Disk 指标依赖 kube-state-metrics + cAdvisor 提供的 pod/container 粒度数据；prod observability (Story 1.7+) 评估 monitoring namespace PSA 重定为 privileged 或采用 Pod-level Security exception。
- **持久化** `[Architect Round 1 Q4 ruling]`: staging 阶段全 emptyDir；Prometheus retention **24h** / Loki **48h** / Jaeger 内存 **~2h（自然驱逐，受 query.maxTraces 上限约束）**；**禁止** 启用任何 chart 的 `persistence.enabled: true`；prod PVC 策略 + ESSD/OSS 选型 + retention SLO 留 Story 1.7+ 单独 ADR

### Architect Round 1 Rulings (Q1–Q6)

#### Q1 — Helm 分发策略
**RULING: Hybrid — kube-prometheus-stack (umbrella) + Loki + Promtail + OTel Collector + Jaeger，共 5 个 observability release**

- `kube-prometheus-stack` 是 CNCF 推荐入口：自带 Prometheus Operator + `ServiceMonitor`/`PrometheusRule` CRD + Grafana sidecar 加载 + Alertmanager + node-exporter + kube-state-metrics 一揽子。拆 5 chart piecemeal = 重复造轮子，且失去 Operator 自动管理 PrometheusRule/ServiceMonitor 的好处。
- Loki / Promtail / OTel Collector / Jaeger 各自独立 chart — 匹配 architecture §11.1 三大支柱"独立演进"语义。
- Promtail 必须显式列入 chart 清单（见 M-2 修复）。Promtail 在 Loki 3.x 已进入 maintenance mode；Grafana 推荐 Alloy。但 architecture/tech-stack.md L36 明确 "Loki + Promtail 3.x"，本 Story 不偏离架构定义；Alloy 迁移 = Epic 9 (observability hardening) 单独 ADR。
- 安装顺序（install.sh）: (1) kube-prometheus-stack（提供 CRD）→ 等 CRD established → (2) loki → (3) promtail → (4) jaeger → (5) otel-collector（最后，依赖 jaeger 端点） → 6) sample-otel-app（依赖 ServiceMonitor CRD）。
- ArgoCD GitOps（architecture §7.3）是目标态；本 Story `scripts/observability/install.sh` 是 bootstrap 过渡方案 — ArgoCD 自身安装 = Story 1.7+ 单独范围（见 m-2 minor）。

#### Q2 — Trace 后端
**RULING: 保留 Jaeger（per architecture §11.1）— 完全删除 Tempo 占位分支**

- `docs/architecture/11-可观测性observability.md#11.1` 表格明确写 "Traces / OpenTelemetry + Jaeger（后端）"。本 Story 不应改架构定义。
- 切换 Tempo（即使 datasource 接入更简）需走 Architect Change Proposal (TCP) 而非 Round 1 仲裁。
- staging in-memory storage 模式即可（jaeger 1.55+ all-in-one image，单 pod）。
- 所有 "Q2 若 Tempo 则…" 分支从 Story 删除（详 M-5）。

#### Q3 — Sample 服务来源
**RULING: 新建 `apps/sample-otel-app/`（保持 api-gateway 纯粹）**

- `docs/architecture/source-tree.md` L7-15 定义 api-gateway 为生产 HTTP 网关（含 OpenAI 兼容 handlers / auth / quota / safety / routing / streaming middleware）— 是 Epic 2 的入口主体。注入 OTel demo 逻辑会污染其单一职责。
- `sample-otel-app` 作为 Epic 1 reference impl 价值：成为 Epic 2-10 服务集成 OTel SDK + Prometheus exporter + 结构化 JSON 日志 的"教科书示例"；每个新服务 copy 这套骨架即可。

#### Q4 — 持久化策略
**RULING: staging 全 emptyDir + 适度留存窗口（折中，避免 Prom 6h 过短不够工作日回溯）**

- 全栈 emptyDir（Prom + Grafana + Alertmanager + Loki + Jaeger）。理由：staging 数据非生产关键，pod 重启数据可丢；PVC 引入 ESSD ¥30-80/月 + ACK PVC CSI 复杂度 + 重启 PV detach 风险，与 staging 一次性验证 + 重建 工作流冲突。
- 留存窗口调整（vs Story 原始 6h/24h/1h 占位）：
  - **Prometheus: 24h**（覆盖 1 个完整工作日故障回溯；emptyDir 模式下受 pod 内存/PV 上限约束自然衰减）
  - **Loki: 48h**（跨周末，filesystem mode in emptyDir，size 由 pod resources.limits.ephemeral-storage 设 2Gi 上限）
  - **Jaeger memory: 2h 自然窗口**（in-memory traces 受 `query.maxTraces` 默认上限约束；不强制配置 retention，由内存压力自然驱逐）
- 生产 PVC 策略 + ESSD / OSS 选型 + retention SLO = **Story 1.7+ (prod observability)** 单独 ADR，本 Story 不前置。

#### Q5 — Grafana 公网暴露
**RULING: port-forward only（Story 1.4 不引入 ingress-nginx / cert-manager 安装）**

- Architecture §7.1/§7.2 公网入口链：Cloudflare → SLB → ingress-nginx → service。完整实装需 ingress-nginx chart + cert-manager chart + Cloudflare DNS proxy + TLS cert (Let's Encrypt or 阿里云 SSL) + auth middleware（无 OIDC 则需 basic auth secret）= 一整套独立 Story，与 OTel 观测栈完全正交。
- 1.3 已预创建 `ingress-nginx` namespace（`pod-security: privileged`）+ `cert-manager` namespace 作为占位 — 属未来 Story 起点，本 Story 不安装 chart。
- 运维通过 `kubectl port-forward svc/<grafana> 3000:80 -n monitoring` 本地访问 — 安全、无公网攻击面、零 TLS/auth 复杂度。
- 公网暴露 + TLS + auth → 单独 **Story 1.7+** (ingress-nginx + cert-manager bootstrap) 范围。SM revise 在 README "Observability" 段写明 "公网暴露见 Story 1.7+（待规划）"。
- AC1.B 保留 port-forward 验收方式不变。

#### Q6 — Grafana auth
**RULING: K8s Secret 自动生成 admin password（OIDC defer 到 Epic 2.x 之后）**

- OIDC 依赖 auth-svc（Epic 2 才落地）+ 外部 IdP（架构未指定具体 provider）。本 Story 时间窗内不可达。
- kube-prometheus-stack chart 自动生成强密码（`grafana.adminPassword: ""` 触发 chart helper）入 K8s Secret `kube-prometheus-stack-grafana`。运维提取：`kubectl get secret kube-prometheus-stack-grafana -n monitoring -o jsonpath='{.data.admin-password}' | base64 -d`。

- OIDC 接入 = **Epic 9 (observability hardening)** 范围，需先有 auth-svc + ADR 选定 IdP。
