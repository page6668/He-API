## Story

**As a** the He-API gateway operating under 生成式 AI 服务备案 compliance (and the 合规/备案 officer who, on a 监管 audit, must produce 6-month-retained evidence that the bidirectional content-safety filter is actually intercepting violations — both 入参 rejections and 出参 redactions/stream-terminations — and a 备案材料 PDF summarising that activity),
**I want** the no-op `contentsafety.Recorder` seam that Stories 8.2/8.3/8.4 deliberately stubbed to finally be implemented as a DB-persisting Recorder that writes every ACTED-ON block to a new `he_api.content_safety_logs` table (with a 脱敏 excerpt that leaks neither raw user content nor the literal sensitive term), retained for 6 months by a scheduled cleanup CronJob, exempt from GDPR account-deletion by construction (compliance > individual erasure, §9.3), and queryable into an on-demand 备案材料 PDF report,
**so that** Epic-8's final two DoD lines — "治理日志保留 6 个月" and "备案材料 PDF 模板生成" — are met, the §9.3 治理日志 pipeline (`命中 → 拒绝/脱敏 → 写入 content_safety_logs`) is closed end-to-end, and the live 备案 posture is preserved by construction: the persist is FIRE-AND-FORGET (never blocks the 8.2/8.3/8.4 block decision — recorder.go:56-62), the persisting Recorder lives in a NEW package so `contentsafety` stays lexicon-only / import-cycle-free (recorder.go:9-11), and a missing DB pool degrades cleanly back to the proven `NopRecorder` (mirroring the billing-endpoints-disabled posture at main.go:488) — with NO change to the detection or gating machinery 8.2/8.3/8.4 shipped.

## Acceptance Criteria

### AC1: content_safety_logs 表 + 持久化 Recorder（双向、fire-and-forget、脱敏 excerpt）

**Scenario**
```gherkin
GIVEN a request whose §9.3 filter ACTS ON a confirmed match — an 8.2 入参 reject (400_content_filter), an 8.3 出参 redact (non-stream), or an 8.3 stream terminate — under the 8.4-resolved per-Key strictness, handing the populated contentsafety.SafetyEvent to the injected Recorder
WHEN the gateway is wired with the NEW persisting Recorder (a DB-writing implementation of contentsafety.Recorder, supplied via the existing WithSafetyRecorder option) instead of the NopRecorder default
THEN
  - exactly ONE he_api.content_safety_logs row is written per acted-on block, with: direction ∈ {input, output} (from SafetyEvent.Direction), matched_rule = SafetyEvent.MatchedRule (canonical term, ≤100 runes), action = 'blocked', user_id / api_key_id / he_request_id from the event, and created_at = NOW() — and a 脱敏 excerpt_redacted (see BR-1.4)
  - the write is FIRE-AND-FORGET: Record returns nothing and NEVER blocks or fails the 400 / redact / stream-terminate response (recorder.go:56-62) — a DB error, timeout, or full buffer logs at WARN + increments a drop metric, and the user-facing block proceeds unchanged
  - the persisting Recorder is constructed in main.go from the EXISTING gateway Postgres pool (HE_API_DB_POSTGRES_URI, the same pool buildBillingPool builds, main.go:721-731) and wired via WithSafetyRecorder; when the pool is nil (URI unset), the gateway falls back to the NopRecorder default — degraded-but-serving, mirroring the billing-endpoints-disabled posture (main.go:488)
  - BOTH directions are persisted by the ONE Recorder: the 8.3 per-redacted-choice output events (one event per redacted choice, chat_completions_safety_output.go:77-91) and the stream-terminate event each produce their own row; an A/B multi-choice response that redacts 2 choices writes 2 rows
  - 8.2/8.3/8.4 are BYTE-IDENTICAL on the response path: the persisting Recorder changes ONLY what is written to the DB, never the detection, the gating, or the block envelope — the full 8.2/8.3/8.4 suites stay green with the new Recorder wired
```

### AC2: 6-month 保留 retention CronJob + GDPR-erasure 豁免（content_safety_logs 不随用户删除）

**Scenario**
```gherkin
GIVEN content_safety_logs accumulates 治理日志 rows and §9.3 mandates "保留 6 个月" + "用户 GDPR 删除时不删除（合规优先于个人删除请求）"
WHEN (a) the scheduled retention CronJob runs, and (b) a user account is deleted via the Story-2.7 account-deletion path
THEN
  - the retention CronJob deletes ONLY rows with created_at < NOW() - INTERVAL '6 months' (a single bounded DELETE using idx_safety_logs_created_at), is idempotent (re-run within the window is a no-op), and exits 0 on success/empty / 1 on infrastructure failure — mirroring the auth-svc monthly-cost-reset cmd/cron shape (cmd binary + Helm CronJob, concurrencyPolicy: Forbid, backoffLimit: 0)
  - rows YOUNGER than 6 months are NEVER deleted by the sweep (the < cutoff bound is strict; the index makes it a range scan, not a full-table scan)
  - GDPR exemption is BY CONSTRUCTION: content_safety_logs.user_id carries NO REFERENCES he_api.users(id) FK (unlike data_export_requests' ON DELETE CASCADE), so deleting a user does NOT cascade-purge their safety logs; the §9.3 "合规优先于个人删除请求" invariant holds without any application code
  - the Story-2.7 account-deletion path does NOT separately DELETE from content_safety_logs (it is NOT in the erasure set) — a deleted user's interception records survive until the 6-month retention sweep ages them out
  - the cleanup cmd reuses the gateway Postgres pool / he_api schema; it adds NO new DB credential surface and NO new CI lane
```

### Technical Constraints
- **The seam is already built — 8.5 only fills the persisting half.** 8.2/8.3/8.4 deliberately wired `contentsafety.NopRecorder` as the default and reserved `WithSafetyRecorder` for 8.5. The `SafetyEvent` struct, `Recorder` interface, `Direction*`/`ActionBlocked` consts, and the `recordSafetyBlock` / `recordSafetyOutputBlock` call sites already exist and already populate every field (including 8.4's `Strictness`). 8.5 adds NO field to `SafetyEvent` and changes NO call site. [→ apps/api-gateway/internal/contentsafety/recorder.go:16-71], [→ apps/api-gateway/internal/handlers/chat_completions.go:282-313,400], [→ apps/api-gateway/internal/handlers/chat_completions_safety_output.go:100-118]
- **Import-cycle invariant (HARD):** `contentsafety` depends ONLY on `packages/safety-lexicon` and MUST NOT import handlers or pgx (recorder.go:9-11). The DB-writing `PersistingRecorder` therefore lives in a NEW package `apps/api-gateway/internal/safetylog`, which imports `contentsafety` (for the types) + `pgxpool`. Only `main.go` imports `safetylog`. [→ apps/api-gateway/internal/contentsafety/recorder.go:9-11]
- **Fire-and-forget (HARD, recorder.go:56-62):** `Record` returns nothing and MUST NOT block or fail the response. A DB error / timeout / full buffer is logged + dropped + metered; the 8.2/8.3/8.4 block decision is never awaited on the persist. This is the chief reliability + compliance constraint — see OQ-8.5-1 for the async-vs-sync ruling.
- **No-leak posture (HARD):** the matched term reaches ONLY the event seam, never the caller-facing envelope (8.2/8.3). 8.5 must NOT widen this: `excerpt_redacted` stores neither raw user content nor the literal sensitive term; the 备案 PDF renders canonical ids + counts, not surface 敏感词. [→ apps/api-gateway/internal/contentsafety/recorder.go:22-25]
- **Gateway DB access already exists:** the gateway builds a Postgres pool from `HE_API_DB_POSTGRES_URI` (`buildBillingPool`) for billing reads; 8.5 reuses it for the persist. A nil pool (URI unset) must degrade to `NopRecorder` — serving, not crashing — exactly as billing endpoints disable on the same condition. [→ apps/api-gateway/cmd/server/main.go:488,719-731]

### Database Design
- **content_safety_logs** is a brand-new table (migration 0014, the next free number after 0013). It is written by the gateway pool (in-process, no RPC/auth-svc boundary — unlike 8.4's proto change). Two indexes: `idx_safety_logs_user_time (user_id, created_at DESC)` (the pre-declared per-user read path) + `idx_safety_logs_created_at (created_at)` (the AC2 retention range-delete). The CHECK constraints (`direction`, `action`) are defence-in-depth; the application only ever emits the valid consts.
- **Why no `REFERENCES users(id)` FK (the load-bearing 备案 design point):** §9.3 mandates the log SURVIVES GDPR account deletion ("合规优先于个人删除请求"). `data_export_requests` uses `ON DELETE CASCADE` precisely so account deletion tidies it up — content_safety_logs needs the OPPOSITE. Omitting the FK means a `DELETE FROM users` cannot cascade into the compliance log. This is asserted as a HARD test so it cannot be "fixed" away by a later FK-tidying refactor.
- **Retention** is a strict `created_at < NOW() - INTERVAL '6 months'` delete — half-open, idempotent, index-backed. No soft-delete, no archive-then-delete (the 6-month window is the compliance floor, not a tiering policy).

### Security & Compliance Notes
- **The gravest 8.5 defect would be a silently-relaxed compliance posture**: (a) a Recorder failure that BLOCKS or alters the user-facing block (fire-and-forget violated), (b) a cascade that PURGES safety logs on user deletion (GDPR-exemption breached → 备案 retention gap), or (c) a leak of raw user content / literal 敏感词 into `excerpt_redacted` or the 备案 PDF (no-leak + 不出境 breached).
