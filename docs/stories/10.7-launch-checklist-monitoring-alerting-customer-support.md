### AC1: PagerDuty 集成——监控告警最后一公里（Alertmanager 通道接线）

**Scenario**
```gherkin
GIVEN 仓库已有多条 PrometheusRule（`infra/helm/auth-svc/templates/prometheusrule.yaml` 等）emit 告警并打 `severity`（warning/critical）+ `channel`（feishu/pagerduty）标签
  AND kube-prometheus-stack 的 `alertmanager:` 块当前仅 `enabled: true` + resources，**无 `config`（route tree + receivers）** —— 即告警「触发但无处投递」（last-mile 缺口）
  AND 通道凭据（PagerDuty routing key / 飞书 webhook / Slack webhook）的 secret 来源以 OQ-10.7-1 裁定为准（绝不明文入 committed values，沿用 BR-C-7 secret-handling 纪律）
WHEN 任一 critical 告警触发（如 `AuthAccountLockedSpike` / `GatewayErrorRateHigh`）
THEN Alertmanager 依 **§11.4 通道矩阵**把告警路由到对应 receiver：
      - **P0 (severity=critical)** → **PagerDuty**（Events API v2，integration/routing key 自 secret 注入）→ 值班手机
      - **P1 (severity=warning, channel=feishu)** → 飞书机器人 + 邮件
      - **P2/P3** → 飞书 / Slack
  AND **网关 §11.3 RED 告警规则**落地为新 PrometheusRule（`GatewayP95LatencyHigh` / `GatewayErrorRateHigh` / `UpstreamModelDown` / `DataExportSuspect`，OQ-10.7-5 裁定是否本 Story）——当前 `infra/helm/api-gateway/templates/` 无 prometheusrule.yaml
  AND 投递到 PagerDuty 的 payload **仅含运营元数据**（alert name / `severity` / `service` / `team` / annotations / `runbook_url`）——**绝不含用户 PII**（沿用 §11.5 BR-TR-7 allow-list 纪律；alert 标签集本就非 PII，与 §9.1 数据不出境一致：告警元数据非个人信息）
  AND Alertmanager route/receiver 配置经 **CI 金标门**锁定（沿用 5.4/7.2 `scripts/ci/verify-cron-schedule.sh` 范式 —— route 漂移会让 P0 告警静默丢失）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-10.7.1 | **缺口 = Alertmanager 路由/接收器，非告警规则**：PrometheusRule（emit 侧）已就位且打好 `severity`+`channel` 标签（`infra/helm/auth-svc/templates/prometheusrule.yaml` 已含 `channel: pagerduty`/`feishu`）。本 AC 补的是 **consume 侧** —— kube-prometheus-stack `alertmanager.config` 的 `route`（按 `severity`/`channel` 分流）+ `receivers`（`pagerduty_configs` / 飞书 webhook / Slack `slack_configs`）。分发机制（inline values vs `AlertmanagerConfig` CRD vs secret-referenced `alertmanagerConfiguration`）+ secret 来源 = **OQ-10.7-1 裁定**。 |
| BR-10.7.2 | **§11.4 通道矩阵为 SoT，不新造分级**：route tree 严格按 `docs/architecture/11-可观测性observability.md §11.4`：P0 critical→PagerDuty；P1→飞书+邮件；P2→飞书+Slack；P3→Slack。`severity` 值（warning/critical）+ `channel` 值（feishu/pagerduty）取自既有 PrometheusRule 标签集（auth-svc/routing-svc 已用），**不重定义**。 |
| BR-10.7.3 | **secret 绝不入库（沿用 BR-C-7 / fxrate-provider 范式）**：PagerDuty routing key、飞书 webhook URL、Slack webhook URL **绝不**明文写入 `values*.yaml`/git —— 经 K8s Secret（ExternalSecret → Vault，路径沿用 `kv/data/he-api/...` 范式，OQ-10.7-1）注入；Alertmanager 经 secret-ref 读取。dev/CI 用占位/disabled receiver，绝不持真 key。 |
| BR-10.7.4 | **PagerDuty payload 无 PII（§11.5 + §9.1 双约束）**：投递 PagerDuty/Slack 的字段限于 alert 元数据（`alertname`/`severity`/`service`/`team`/`summary`/`description`/`runbook_url`）。这些**本就非个人信息**（沿用 §11.5 BR-TR-7 「span/告警标签是 `he.*`+OTel semconv allow-list，绝不含 prompt/PII/email/IP」纪律）—— 故 PagerDuty（US SaaS）接收告警元数据**不**触 §9.1 数据不出境（出境约束针对**用户个人信息/业务数据**，非运营告警元数据）。Dev 须确保 annotations 模板不内插任何 user_id/email/IP/请求体。 |
| BR-10.7.5 | **网关 §11.3 规则补齐（OQ-10.7-5）**：§11.3 定义的 4 条核心规则（`GatewayP95LatencyHigh` warning / `GatewayErrorRateHigh` critical / `UpstreamModelDown` warning / `DataExportSuspect` critical）当前**无落地 PrometheusRule**（`infra/helm/api-gateway/templates/` 仅 deployment/service/networkpolicy/cronjob）。建议本 Story 新建 `infra/helm/api-gateway/templates/prometheusrule.yaml`（否则 PagerDuty 接线对网关 RED 信号无意义）；defer 与否 = OQ-10.7-5。`DataExportSuspect`（境外 egress >0 → critical）尤为关键，是 §9.1 的运行时哨兵。 |
| BR-10.7.6 | **路由配置 CI 金标门**：Alertmanager route/receiver 关键字面量（severity→receiver 映射、P0→pagerduty）经静态门锁定（沿用 5.4 `verify-cron-schedule.sh` + helm-lint matrix 范式）。漂移（如 critical 误路由到 Slack 而非 PagerDuty）= P0 告警静默丢失 = 上线级事故，故纳门禁。 |

**OQ-10.7-1 · Alertmanager config 分发 + secret 来源 — RATIFIED (endorse SM lean, refined):**

3. **P0 dual-channel = YES**: severity=critical routes to **PagerDuty + 飞书 mirror** (continue:true on the critical match) so a single-channel delivery failure can't silence a P0. §9.1-safe: both receive only non-PII metadata (BR-10.7.4, §11.5 allow-list, §9.1:12 "PagerDuty 仅传 metric 标识").
4. Explicit **catch-all receiver** (non-blackhole) is mandatory; `verify-alertmanager-routes.sh` gold-gate must assert `severity=critical → pagerduty` mapping + catch-all presence.

**OQ-10.7-2 · Intercom × §9.1 数据不出境 — RATIFIED (architect technical contract; ⚠️ PO sign-off required before T2 PII-bearing impl):**
- **HARD CONTRACT (arch-binding, CI/review-enforced): ZERO PII to Intercom.** Boot payload **NEVER** contains email, name, user_id, IP-derived identity, prompt, key, or any user content. The **only** identifier permitted is the non-PII `he_request_id` handle (§11.5 — opaque, registered non-PII). This satisfies §9.1 "不发任何用户内容到 SaaS".
- **Identity-Verification HMAC seam = BUILD-but-DORMANT.** Implement the console-BFF `INTERCOM_SECRET` HMAC server seam (BR-10.7.8 — secret server-only, never in bundle) so the capability exists, but it is **disabled by default** because zero-PII mode sends no identity to sign. It activates **only** if/when a compliant identity-bearing path is later approved (see PO item).
