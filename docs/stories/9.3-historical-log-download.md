### AC1: 发起异步导出任务 — `POST /v1/me/usage/logs/export` + `GET /v1/me/usage/logs/export/current` (JWT-cookie, per-user, format=json|csv, ≤90d)

**Scenario**
```gherkin
GIVEN
  - Story 9.1 shipped the ClickHouse `he_api.request_logs` MergeTree (90d TTL — the durable SoT for this download) populated by analytics-svc
  - Story 2.6 shipped `he_api.data_export_requests` (pending→processing→completed|failed|expired) + the gateway↔notification-svc data-export proxy pattern
  - A user authenticates via the JWT cookie (he_access); their user_id is the verified JWT `sub`
WHEN
  - The console calls POST /v1/me/usage/logs/export with body { "format": "csv" } (or "json"; optionally { "range_days": 90 } or { "start": <rfc3339>, "end": <rfc3339> })
THEN
  - The gateway derives user_id from the JWT (NEVER from body — BR-EX-1), proxies to notification-svc.RequestUsageLogExport, and returns 200 { export_id, status: "pending|processing|completed", format, requested_at }
  - notification-svc INSERTs a `data_export_requests` row with kind="usage_logs", format=<json|csv> (Architect-gated table strategy, Q-TABLE), enforces a per-user idempotency window scoped by (kind, format) — a repeat within the window returns the SAME export_id (BR-EX-4), publishes `usage.log.export.requested` (key=user_id) AFTER PG commit, and emits a best-effort audit event
  - GET /v1/me/usage/logs/export/current returns the user's current usage-logs export {export_id, status, format, requested_at, signed_url_expires_at|null} or null (kind-scoped — a GDPR export never masks a usage-logs export, BR-EX-7)
  - Invalid/unknown body field, bad format, range>90d, or end≤start → 400_invalid_request (param set); missing/expired JWT → 401_unauthenticated; notification-svc down → 502/503; idempotency race → 429_rate_limit_usage_log_export
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-EX-1 | **IDOR / user-from-JWT only**: user_id is taken ONLY from `middleware.UserIDFromContext` (verified JWT `sub`); a `user_id` (or any unrecognized) body field → strict 400_invalid_request. Mirrors 2.6 `account_data.go` BR-2.4 + 9.2 BR-RD-1. The export job (AC2) is fenced `WHERE user_id = ?` on every CH query. |
| BR-EX-2 | **Format**: `format` ∈ {`json`, `csv`} (required; no default — explicit user choice). Unknown/absent → 400_invalid_request, param=format. The chosen format is persisted on the request row and carried on the Kafka event (BR-EX-9) so the worker (AC2) serializes accordingly. |
| BR-EX-3 | **Range ≤ 90d**: optional `range_days` (1..90, default 90) OR explicit `start`/`end` (RFC3339, `end>start`, span ≤ 90d, both within the 90d TTL window). Out-of-range → 400_invalid_request, param=range_days\|start\|end. Bounds the dump cost + matches the request_logs TTL. |
| BR-EX-4 | **Idempotency (kind+format scoped)**: a per-user export within the idempotency window (default 24h, reuse 2.6 `defaultIdempotencyWindow`) for the SAME (kind=`usage_logs`, format) returns the existing row's export_id + status (no new Kafka publish/audit). A different format starts a NEW export. Failed rows do NOT count (TS-CONS-016 parity). Exact window value = Q-IDEMP (Architect). |
| BR-EX-5 | **Rate-limit safety-net**: a Redis Lua INCR race-guard mirrors 2.6 BR-2.5 but under a SEPARATE key namespace (`usage_log_export:{user_id}`) so usage-log exports do not consume the GDPR-export quota. Race loser → notification-svc `ResourceExhausted` → gateway 429_rate_limit_usage_log_export (NEW canonical code, registered in rest-api-spec §5.1.2). |
| BR-EX-6 | **Async contract**: the POST returns immediately with status=pending (202-style semantics but HTTP 200 to match the 2.6 envelope). The file is NOT returned inline; the user receives it via the email link (AC2). `Cache-Control: no-store` (exports are user-private). |
| BR-EX-7 | **Current-export hydration is kind-scoped**: GET .../current filters `kind='usage_logs'` so it reflects only the usage-log export lifecycle (independent of any in-flight GDPR export). Reuses the 2.6 `FindLatestForUser` repository pattern + the `has_current` rule (pending\|processing\|completed-with-live-url). |
| BR-EX-8 | **Endpoint placement**: NEW routes are siblings of 9.2's `GET /v1/me/usage/logs`, wrapped by `jwtVerifier.RequireJWT`. POST/GET-current are ALWAYS mounted (they proxy to notification-svc, not ClickHouse) — unlike the read endpoints they are not gated by `HE_API_CLICKHOUSE_DSN`. CSRF: state-mutating POST carries the internal-origin allow-list hop (2.6 BR-4.6 precedent). |
| BR-EX-9 | **Cross-service contract additions (Architect-gated)**: new RPC `RequestUsageLogExport`/`GetCurrentUsageLogExport` on `NotificationService` (Q-OWNER — vs a new analytics-facing service), new Kafka topic `usage.log.export.requested`, new proto `UsageLogExportRequestedEvent {export_id, user_id, format, range_start, range_end}`. All additive; partition key = user_id (TS-CONS-015). |

**Data Validation**
| Field (JSON body) | Type | Required | Rules | Error Message |
|-------------------|------|----------|-------|---------------|
| format | enum | yes | `json` \| `csv` | "format must be json or csv" → 400, param=format |
| range_days | int | no (def 90) | 1 ≤ range_days ≤ 90 | "range_days must be in [1,90]" → 400, param=range_days |
| start, end | rfc3339 | no | parseable RFC3339; end>start; span ≤ 90d; within TTL | "start/end must be RFC3339, end>start, span ≤ 90d" → 400, param=start\|end |
| (any other field) | — | — | strict-fields reject (DisallowUnknownFields) | "unrecognized field — user_id is derived from JWT" → 400_invalid_request |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Missing/expired JWT cookie | 401_unauthenticated | (canonical) | console redirects to /signin?return_to=/logs |
| Invalid body / format / range | 400_invalid_request | per Data Validation row | console shows inline validation; no request fired |
| Idempotency race (100ms-level) | 429_rate_limit_usage_log_export | (canonical, NEW) | console shows "an export is already in progress" |
| notification-svc unreachable | 502_notification_svc_unavailable / 503_notification_svc_unavailable | (canonical, reused from 2.6) | console inline error + retry |
| notification-svc timeout | 504_notification_svc_timeout | (canonical, reused) | console inline error + retry |

**Examples**
- **Input**: `POST /v1/me/usage/logs/export` body `{"format":"csv"}` (user A) → **Expected**: `200 { "export_id":"uuid", "status":"pending", "format":"csv", "requested_at":"…Z" }`; a `data_export_requests` row (kind=usage_logs, format=csv) committed; `usage.log.export.requested` published keyed by A's user_id.
- **Input**: same user A `POST {"format":"csv"}` again within 24h → **Expected**: SAME `export_id` (idempotent), no new Kafka publish. But `POST {"format":"json"}` → NEW export_id (different format).
- **Input**: `POST {"format":"xml"}` → **Expected**: `400_invalid_request`, param=format. `POST {"user_id":"<other>","format":"json"}` → **Expected**: `400_invalid_request` (strict-fields reject), and even if accepted the job is fenced to A.

### AC2: 异步导出生成 + 邮件链接 — analytics-svc `UsageLogExportWorker` (dump→OSS→signed-URL→email, status machine, audit)

**Scenario**
```gherkin
GIVEN
  - AC1 published `usage.log.export.requested` { export_id, user_id, format, range_start, range_end } and a `data_export_requests` row sits at status=pending (kind=usage_logs)
  - analytics-svc has the ClickHouse client (vendored since 9.1) + an OSS Uploader + a notification-svc EmailTrigger
WHEN
  - The UsageLogExportWorker (consumer group `analytics-svc.usage-log-export`) fetches the message
THEN
  - It atomically claims the row pending→processing (0-rows-affected → already-claimed → ack+skip, double-consume guard, mirrors 2.6 BR-4.2)
  - It dumps the user's `request_logs` over [range_start, range_end] (≤90d), fenced `WHERE user_id = ?`, projecting ONLY the non-PII observability columns (9.2 BR-RD-9 set), serialized as JSON-Lines (format=json) or RFC-4180 CSV with a header row (format=csv) — `client_ip`/`client_country`/`user_agent`/`error_message` (PII) and `cost_usd` (non-authoritative, H-1-R) are NEVER written (BR-EX-12)
  - It uploads to OSS at key `usage-log-exports/{user_id}/{export_id}.{ext}`, signs a 24h URL, transitions processing→completed (persisting oss_object_key + signed_url_expires_at), then triggers notification-svc.SendEmail with the `usage_log_export_ready` template (signed URL + expiry + row count, in the user's locale) and emits an audit `completed` event
  - Any stage failure → processing→failed with an operator-readable, PII-free `failure_reason` (signed URLs never logged — TS-CONS-008) + an audit `failed` event with the failed stage; the row is the source of truth (Kafka at-least-once; offsets committed after the terminal PG state)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-EX-10 | **Separate worker + topic**: a NEW `UsageLogExportWorker` (NOT the `GdprExportWorker`, which panics unless exactly 7 dumpers). It consumes `usage.log.export.requested` under consumer group `analytics-svc.usage-log-export`. Env-gated (`HE_API_ANALYTICS_USAGE_LOG_EXPORT_WORKER_ENABLED`, default false) — opt-in parity with the GDPR worker, so unwired NoOp deps never silently ACK a real job. |
| BR-EX-11 | **Single ClickHouse dump, format-aware**: one dumper over `request_logs` (reuse the 9.1 `clickhouse.Open`/sink; NO PG fan-out). It honors `range_start`/`range_end` (`ts` BETWEEN, ≤90d) + `WHERE user_id = ?`. JSON path = JSON-Lines (one object per row, BR-4.6 GDPR precedent for request_logs). CSV path = RFC-4180, header row first, deterministic column order, CRLF, fields quoted/escaped per spec. |
| BR-EX-12 | **PII + cost exclusion (non-negotiable)**: the dump projects ONLY the 9.2 BR-RD-9 non-PII set `{he_request_id, ts, model, upstream_model, status_code, is_streaming, prompt_tokens, completion_tokens, total_tokens, latency_ms_total, ttfb_ms, api_key_id, error_code}`. `client_ip`/`client_country`/`user_agent`/`error_message` (PII) and `cost_usd` (non-authoritative "0", H-1-R — see [[project_cost_source_oq5_usage_ledger]]) are EXCLUDED at the SQL projection (statically grep-auditable, mirrors `dumps.go` allow-list discipline). Whether to ADD non-PII routing fields (`routing_strategy`/`selected_by_strategy`) is Q-COLS (Architect). |
| BR-EX-13 | **Status machine + double-consume guard**: `MarkProcessing` (pending→processing, claimed=false on 0 rows), `MarkCompleted(export_id, oss_key, expires_at)`, `MarkFailed(export_id, reason)` — reuse the 2.6 `Store` interface contract verbatim (the row schema is shared). Terminal state is the source of truth; commit Kafka offset after it. |
| BR-EX-14 | **OSS + signed URL**: upload via the `Uploader` interface (PutObject + SignURL 24h), key namespaced `usage-log-exports/{user_id}/{export_id}.{ext}` (distinct from `gdpr-exports/`). The signed URL is a credential — it is emailed + persisted-as-expiry only, NEVER logged or placed in `failure_reason` (TS-CONS-008). OSS object lifecycle/expiry follows the 2.6 bucket policy + the deferred expiry-cron (BR-4.7). |
| BR-EX-15 | **Email = the delivery channel (epic AC "邮件接收链接")**: on completion, call notification-svc.SendEmail with a NEW `usage_log_export_ready` template (×10 locales, txt+html, reuse the `templates/` + SendGrid infra) carrying the signed URL, human-readable expiry (user timezone/locale), format, and row/byte count. `email_sent_at` is stamped on the row. Email-send failure → mark failed + audit (the link is otherwise undeliverable). |
| BR-EX-16 | **Audit on every transition** (BR-4.10 parity): emit audit events for requested (AC1), completed, failed (with failed-stage). Best-effort, non-blocking (TS-CONS-005). |
| BR-EX-17 | **Env-limit honesty (toolchain)**: the OSS SDK + Kafka + SendGrid live clients may not be vendored/runnable in the dev env ([[project_toolchain_env_limits]] — no docker/testcontainers locally; 2.6 shipped NoOp Uploader/Email). The worker MUST ship the integration-ready interface chain (Store/Uploader/EmailTrigger/Dumper) + the consumer loop + the status-machine guard so CI/PR testcontainers wire real impls; the ClickHouse dump itself IS runnable (client vendored in 9.1). Any NoOp wiring MUST keep the worker env-gated off (BR-EX-10) so real jobs are never silently ACK'd. |

**Data Validation**
| Field (event/dump) | Rule | Behavior on invalid |
|--------------------|------|---------------------|
| export_id / user_id (event) | non-empty | poison message → ack + skip (no requeue loop), mirrors 2.6 Process() |
| format (event) | json \| csv | unknown → mark failed (operator-visible), do not guess |
| range_start/range_end | end>start, span ≤90d | clamp to TTL window; empty → default 90d |

**Error Handling**
| Scenario | Code/Stage | Message | Action |
|----------|-----------|---------|--------|
| Row already past pending | (claimed=false) | (none) | ack + skip (double-consume guard) |
| ClickHouse dump fails | stage=ch_dump | sanitized, PII-free | processing→failed + audit failed |
| OSS upload/sign fails | stage=oss_upload / oss_sign_url | sanitized | processing→failed + audit failed |
| Email send fails | stage=email_send | sanitized | processing→failed + audit failed (link undeliverable) |
| Poison/parse | (ack+skip) | logged | no requeue |

**Examples**
- **Input**: event `{export_id, user_id:A, format:"csv", range: last 90d}` → **Expected**: OSS object `usage-log-exports/A/{export_id}.csv` (RFC-4180, header row, 13 non-PII columns, no cost/IP), row `completed` with `signed_url_expires_at = now+24h`, email to A's address with the signed link, audit `completed`.
- **Input**: ClickHouse unreachable mid-dump → **Expected**: row `failed`, `failure_reason="ch dump failed: …"` (no signed URL, no PII), audit `failed` stage=ch_dump; the POST having already returned 200, the console surfaces "export failed — please retry" via the status endpoint.

### Technical Constraints
- **Reuse the 2.6 export pipeline, do NOT duplicate it.** The whole chain already exists for GDPR exports: PG state machine, gateway↔notification-svc proxy, Kafka→analytics-svc worker, OSS upload + 24h signed URL, SendGrid email, audit. 9.3 adds a `format`-aware, request_logs-only variant. - **request_logs is the 90d SoT.** The ClickHouse `he_api.request_logs` MergeTree (`ORDER BY (user_id, ts, he_request_id)`, `TTL ts + INTERVAL 90 DAY`) is explicitly the "durable SoT for Story 9.3 download" (see migration 002 comment). Read it directly with the 9.1-vendored ClickHouse client. [→ migrations/clickhouse/002_create_request_logs.up.sql; apps/analytics-svc/internal/clickhouse/]
- **Signed URLs are credentials (TS-CONS-008).** Never log the signed URL, never put it in `failure_reason`. It is delivered to the user by EMAIL only and persisted on the row solely as `signed_url_expires_at`. The console NEVER renders the raw URL (BR-UI-3).
- **PII + cost exclusion (non-negotiable).** The export projects ONLY the 9.2 BR-RD-9 13-column non-PII set. `client_ip`/`client_country`/`user_agent`/`error_message` are PII (never exported); `cost_usd` is non-authoritative ("0", H-1-R) so per-request 消费 is NOT exported ([[project_cost_source_oq5_usage_ledger]], [[project_story_9_1_cost_gap]]). NOTE: the stale 2.6 `dumps.go` request_logs allow-list (`ts,user_id,endpoint,model,tokens_in,tokens_out,cost_usd,status_code`) predates 9.1's 21-col schema and INCLUDES cost — do NOT copy it; use the BR-RD-9 set. (Flagged as a 2.6/9.1 drift; reconciling 2.6's GDPR request_logs dump is out of 9.3 scope.)
- **IDOR fence.** user_id ONLY from `middleware.UserIDFromContext` (verified JWT sub) at the gateway; the worker dump is `WHERE user_id = ?` on every query. A spoofed `user_id` body field → strict-fields 400. [→ account_data.go BR-2.4; analyticsquery/handler.go (9.2)]
- **Async, email-delivered.** POST returns 200 + status=pending immediately; the file is delivered by email link, never inline (epic AC "邮件接收链接"). Idempotency + rate-limit protect against double-submits.
- **Toolchain env limits.** Local can't run docker/buf/atlas ([[project_toolchain_env_limits]]); 2.6 shipped NoOp OSS/Email and gated its worker off. The ClickHouse client IS vendored (9.1) so the dump is real; OSS/Kafka/SendGrid live wiring may defer to CI/PR testcontainers — ship the interface chain + keep the worker env-gated off (BR-EX-10/17). ### Database Design (WHY, not full SQL)
- **EXTEND vs new table (Q-TABLE, Architect decides).** SM-preferred: add `kind` + `format` columns to `data_export_requests` (additive migration 0015, backfill `kind='gdpr_full'`). WHY: reuses the entire lifecycle (status CHECK, `idx_data_export_requests_user_recent`, the `idx_..._status_expiry` expiry-cron index, ON DELETE CASCADE, the repo + handler). The row already carries `oss_object_key`/`signed_url_expires_at`/`email_sent_at` — exactly what a usage-log export needs. The only gaps are the export *kind* and the *format*. Trade-off: a discriminator column couples two export types in one table (mitigated by kind-scoped queries, BR-EX-7). Alternative (new `usage_log_export_requests`) keeps GDPR pristine but duplicates the state machine + repo + cron — heavier. → Architect ruling required.
- **Idempotency lookup becomes (user_id, kind, format)-scoped** so JSON and CSV exports are independent and a GDPR export never collides with a usage-log export (the existing `(user_id, requested_at DESC)` index still serves the lookup; add `kind`/`format` to the WHERE).
