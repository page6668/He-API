## Acceptance Criteria

### AC1: Sticky-trip cap-tripped circuit breaker — sentinel-hit fast path + first-cross SETNX + counter-comparison slow path emit 402 `402_quota_exhausted`

**Scenario**

```gherkin
GIVEN an API key K (UUID v4) with `monthly_cost_cap_usd = "50.00"` (Story-5.2 PATCH-set or Story-5.1 INSERT-default `null` later set) and `current_month_cost_usd` lagging the Redis counter (Story-5.2 Q-D Redis-SoT cascade-locked)
  AND `keystate:apikey:cap_tripped:{K}` MAY or MAY NOT exist in Redis (caller is naïve)
  AND the bearer hot path is invoked on `POST /v1/chat/completions` (or any `/v1/*` endpoint that flows through Story 5.2 `keypolicy.go`)
  AND Story-5.2's `keypolicy.go` middleware is wired with Story-5.4's NEW sentinel-hit fast-path branch
WHEN the request reaches the cap-enforcement branch of `keypolicy.go`
THEN
  - **Fast-path (sentinel hit)**: if `EXISTS keystate:apikey:cap_tripped:{K}` returns 1 → the middleware returns 402 `402_quota_exhausted` envelope WITHOUT performing the Redis-counter `GET` + decimal compare. The `error.message` SHALL be the existing Story-5.2 string verbatim (`"Monthly spend cap reached for this API key — pausing until the next UTC month."`). The `error.he_request_id` is the Story-3.6 canonical stamp. `Cache-Control: no-store`.
  - **Slow-path (sentinel miss; current >= cap on the counter)**: if `EXISTS keystate:apikey:cap_tripped:{K}` returns 0 AND Story-5.2's `GET usage:apikey:{K}:month_cost_usd` returns a value where `current >= cap`, the middleware:
    1. Issues `SET keystate:apikey:cap_tripped:{K} 1 NX` (best-effort; failure logs WARN + continues — fail-OPEN per Q-F).
    2. Fires the gRPC `NotificationService.NotifyMonthlyCapThreshold(api_key_id=K, threshold=TRIPPED)` in a detached-context goroutine with 500ms deadline (fire-and-forget; failure logs WARN — does NOT block the 402 response).
    3. Returns 402 `402_quota_exhausted` envelope verbatim with the existing Story-5.2 error.message.
  - **Slow-path (sentinel miss; current < cap)**: NO 402 emit; sentinel state unchanged; threshold-crossing detector evaluates per AC2 below. Original request proceeds normally.
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | The sentinel EXISTS-check is the FIRST Redis operation on the cap-enforcement branch of `keypolicy.go` — it precedes the Story-5.2 counter `GET`. Rationale: a tripped key skips the counter GET (saves one Redis round-trip on the busiest cohort — already-tripped power users). |
| BR-1.2 | The sentinel SETNX on first-crossing MUST be fire-and-forget — failure logs `apikey_cap_tripped_sentinel_write_failed` slog WARN + continues; the 402 response is emitted regardless. Fail-OPEN per Q-F (cascade-locked with Story-5.2 Q-F counter fail-OPEN). |
| BR-1.3 | The sentinel key shape is EXACTLY `keystate:apikey:cap_tripped:{api_key_id}` — no envelope, no JSON, no version-prefix. Value is the constant string `"1"` (sibling of Story-5.1 `auth:apikey:revoked:{api_key_id}` value). TTL is INTENTIONALLY ABSENT (cron-only-clear posture per Q-A). |
| BR-1.4 | The 402 envelope code is `402_quota_exhausted` — pre-existing in §5.1.2 (registered pre-Story-3.6; first-emitted by Story 5.2); Story 5.4 introduces NO new envelope codes. |
| BR-1.5 | The slog event for the sentinel-hit fast-path branch is `event="apikey_cap_tripped_sentinel_hit"` carrying attributes `{api_key_id, he_request_id}`. ### AC2: Threshold-crossing detection — fire-and-forget gRPC `NotifyMonthlyCapThreshold(api_key_id, threshold)` for WARNING_80 + TRIPPED; SETNX dedupe inside notification-svc; SendGrid template render in user's locale

**Scenario**

```gherkin
GIVEN an API key K with `monthly_cost_cap_usd = "50.00"` and a Redis counter `usage:apikey:{K}:month_cost_usd` that increases over time (billing-svc Epic 6+ writes; Story 5.4 is read-and-react)
  AND Story-5.2's `keypolicy.go` middleware has already performed `GET usage:apikey:{K}:month_cost_usd` (success → has `current` in-hand)
  AND Story-5.4's threshold-crossing detector is wired into the `keypolicy.go` post-GET branch
  AND notification-svc is reachable via gRPC (cascade-locked with Story-2.2 Q4 ratified sync-gRPC posture)
WHEN the gateway evaluates `ratio = current / cap` post-counter-GET
THEN
  - **Below 0.80**: no gRPC fire; original request proceeds. (Most-common path.)
  - **Crossing 0.80** (`current >= 0.80*cap` AND `current < cap`): gateway fires gRPC `NotifyMonthlyCapThreshold(api_key_id=K, threshold=WARNING_80)` in detached-context goroutine with 500ms deadline. Original request proceeds (200 success). notification-svc:
    1. `SETNX keystate:apikey:cap_warning_80_notified:{K} 1` (no TTL — cron-cleared).
    2. If SETNX returned 1 (first writer): proceeds to step 3; if 0 (already notified this month): returns `AlreadyNotified` (gRPC `OK` with `was_already_notified=true` — no email sent).
    3. PG `SELECT u.email, u.locale, ak.name FROM users u JOIN api_keys ak ON u.id = ak.user_id WHERE ak.id = $1` (single round-trip).
    4. Invokes `SendEmail(template=EMAIL_TEMPLATE_MONTHLY_CAP_WARNING, to_email=u.email, locale=u.locale, variables={display_name=u.email-localpart-or-display-name, key_name=ak.name, cap_usd="50.00", threshold_pct="80"})`. The locale resolution + 10-locale template fallback chain is the existing Story-2.2 deliverable.
  - **Crossing 1.00** (`current >= cap`): gateway fires gRPC `NotifyMonthlyCapThreshold(api_key_id=K, threshold=TRIPPED)` (in addition to the AC1 SETNX + 402 response). notification-svc:
    1. `SETNX keystate:apikey:cap_tripped_notified:{K} 1` (no TTL — cron-cleared).
    2. If SETNX returned 1 (first writer): proceeds to step 3; if 0 (already notified): returns `AlreadyNotified` (no email).
    3. Same PG lookup as the WARNING_80 branch.
    4. Invokes `SendEmail(template=EMAIL_TEMPLATE_MONTHLY_CAP_TRIPPED, to_email=u.email, locale=u.locale, variables={display_name, key_name, cap_usd, current_cost_usd_capped="50.00"})`. Note `current_cost_usd_capped` is the user's CAP not the precise overage — defence-in-depth per security.md §8.3 (don't leak precise spend state to the email channel).
  - **Both crossings in one request** (e.g., counter jumps from `"30.00"` directly to `"55.00"`): the detector fires BOTH gRPC calls (WARNING_80 then TRIPPED) — the dedup sentinels guarantee at-most-one email of each kind per month. (Architect Q-G may rule for collapsed-single-tripped-email instead — SM default fires both since the inbox-spam impact is minor and ops-friendly traceability is improved.)
```

| ID | Rule |
|----|------|
| BR-2.1 | Threshold ratios are HARD-CODED at 0.80 (WARNING_80) and 1.00 (TRIPPED). | BR-2.2 | The `NotifyMonthlyCapThreshold` RPC is FIRE-AND-FORGET from the gateway's perspective — failure (deadline exceeded, gRPC Unavailable, connection refused) NEVER blocks or fails the original request. Per Q-E SM default — see Architect Open Questions. |
| BR-2.3 | The SETNX dedupe key is SET inside notification-svc, NOT inside the gateway. ### AC3: Monthly cost-reset CronJob — `0 0 1 * *` UTC; PG `UPDATE he_api.api_keys SET current_month_cost_usd = 0 WHERE revoked_at IS NULL` + Redis SCAN+DEL on 3 key prefixes; idempotent on re-run

**Scenario**

```gherkin
GIVEN the K8s cluster at the moment of the cron trigger (`0 0 1 * *` UTC — 00:00 UTC on day 1 of each month)
  AND the production data plane has N api_keys rows + M Redis counter keys + P sticky-trip sentinels + Q+R dedupe sentinels (totals are deployment-state-dependent)
  AND CronJob `monthly-cost-reset` is wired with `concurrencyPolicy: Forbid` + `startingDeadlineSeconds: 200` + `backoffLimit: 0` per Q-C
WHEN the kube-scheduler triggers the CronJob
THEN
  - The K8s Job creates ONE Pod running `apps/auth-svc/cmd/monthly-cost-reset/main.go`.
  - The binary connects to PG + Redis using the same env-var-sourced credentials as the auth-svc Deployment (sibling pattern — same DSN, same Tair endpoint).
  - The binary issues `UPDATE he_api.api_keys SET current_month_cost_usd = 0 WHERE revoked_at IS NULL` (single SQL statement; idempotent).
  - The binary issues three SCAN+DEL loops against Redis (one per prefix):
    1. `SCAN MATCH usage:apikey:*:month_cost_usd COUNT 1000` → iterate → `DEL` keys in batches of 1000.
    2. `SCAN MATCH keystate:apikey:cap_tripped:* COUNT 1000` → iterate → `DEL`.
    3. `SCAN MATCH keystate:apikey:cap_*_notified:* COUNT 1000` → iterate → `DEL` (this glob covers BOTH `cap_warning_80_notified` and `cap_tripped_notified` families — single SCAN saves one pass).
  - The binary emits structured slog at each phase: `event=monthly_cost_reset_pg_update_complete` `{rows_affected}`, `event=monthly_cost_reset_redis_scan_complete` `{prefix, keys_deleted}` × 3, `event=monthly_cost_reset_complete` `{total_runtime_seconds}`.
  - On success: binary exits 0 → K8s Job completes successfully.
  - On failure (PG unavailable, Redis unavailable, partial SCAN error): binary exits 1 → K8s Job marked Failed; `backoffLimit: 0` means NO retry; on-call investigates manually (Q-C — preserves data consistency; a re-run after partial state would NOT corrupt data due to idempotency but on-call review is mandated for traceability).
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | The cron schedule is EXACTLY `0 0 1 * *` (UTC) — 00:00 UTC on day 1 of each month. The K8s CronJob `spec.schedule` MUST be EXACTLY this string (CI gate via `make verify-cron-schedule` — a `grep` on `infra/helm/auth-svc/templates/cronjob-monthly-cost-reset.yaml` asserts the literal string). |
| BR-3.2 | `concurrencyPolicy: Forbid` (Q-C SM default) — if a previous Job is still running when the next trigger fires (e.g., a 5-minute-long Job overlaps the next minute's trigger — won't happen at monthly cadence but the policy MUST be set defensively for clock-skew safety). |
| BR-3.3 | `startingDeadlineSeconds: 200` (Q-C) — if the controller misses the schedule by more than 200s, the Job is SKIPPED for this period (alert via Prometheus `kube_cronjob_status_last_schedule_time`). |
| BR-3.4 | `backoffLimit: 0` (Q-C) — Job failures are NOT retried automatically; on-call investigates. Rationale: re-running a half-completed reset would NOT corrupt data due to idempotency, but the OPERATIONAL POSTURE is "one cron, one outcome, human-verified on failure" matching the security-sensitive-cron classification. |
| BR-3.5 | The binary's PG UPDATE statement is EXACTLY `UPDATE he_api.api_keys SET current_month_cost_usd = 0 WHERE revoked_at IS NULL` — NO additional WHERE clauses (no LIMIT, no FOR UPDATE — the row-level lock is unnecessary because no concurrent writer touches `current_month_cost_usd` at the cron-trigger moment per Story-5.2 Q-D Redis-SoT ratification). |

Story-specific test focus areas (QA MUST cover):
- **Sentinel race** (BR-1.8): N=100 concurrent requests for the same key crossing the cap → exactly ONE SETNX success → exactly ONE gRPC fire → exactly ONE email sent.
- **Cron idempotency**: running the cron binary TWICE in succession → no state corruption (verifying TC-9 column-level idempotency).
- **Cron blast radius** (BR-3.1): the schedule expression literal `"0 0 1 * *"` is the ONLY scheduling source-of-truth (no config-file, no env var) — a CI golden-file gate prevents drift.
- **Email dedup race** (BR-2.3): N=10 concurrent NotifyMonthlyCapThreshold(threshold=WARNING_80) for the same `api_key_id` → exactly ONE email sent; subsequent calls return `was_already_notified=true`.
- **Redis fail-OPEN cascade** (Q-F cascade): sentinel write failure / sentinel EXISTS failure / SETNX dedup failure → gateway hot path continues; the worst-case is duplicate email (acceptable per Q-F).
- **Template injection guard** (BR-2.8): `key.name = "<script>alert(1)</script>"` flows through the HTML template render → output contains `&lt;script&gt;` not raw HTML.
- **PII discipline** (security.md §8.3 cascade): email body NEVER carries plaintext key, bcrypt hash, or precise current-month-cost (only the user's own cap value `monthly_cost_cap_usd`).
- **Money-field rendering** (BR-2.7): template variable `{{.CapUSD}}` renders the string-decimal form `"50.00"` not the float `50` or `50.0`.
- **Locale fallback** (TC-11): `users.locale="ja"` → ja template; `users.locale="invalid"` → en fallback.
- **Cluster-mode SCAN** (BR-3.7): Redis cluster with SLOT MIGRATION mid-cron → MOVED redirections handled by go-redis transparently.
- **Cron timeout** (BR-3.13): 5-minute deadline enforced; binary exits 1 on overflow.
- **Empty-state cron** (BR-3.15): zero api_keys + zero Redis keys → exit 0 with zero counts.

### Architect Open Questions (for Round 1)

The SM defaults below are stated explicitly so Architect Round 1 can ratify-or-override; each carries the rationale and the rejected alternatives. Story 5.4 Architect-Review-Required surface is dense — SEVEN open questions converge here.

- **Q-A — Sticky-trip sentinel TTL policy**: SM default = **no TTL** (cron-only-clear). Rationale: a TTL would risk the breaker silently expiring mid-month if the cron misfires AND the TTL fires; the cron-only-clear posture is fail-CLOSED (key stays paused until the cron explicitly clears) which matches the security-sensitive-ratchet. Rejected: 31-day TTL (defence-in-depth — would re-open the gate silently in the edge case).
- **Q-B — Email predicate evaluation site**: SM default = **gateway-side keypolicy.go middleware** (post-counter-GET). Rationale: the counter value is already in-hand from Story-5.2's GET — zero additional Redis round-trips. Rejected: billing-svc-side (defers the email by an Epic — billing-svc lands in Epic 6+); notification-svc Kafka consumer (adds N×fan-out reads against per-event payloads).
- **Q-C — CronJob concurrency policy + restart posture**: SM default = `concurrencyPolicy: Forbid` + `startingDeadlineSeconds: 200` + `backoffLimit: 0`. Rationale: cron-once-or-skip; manual-only retry preserves data consistency posture. Rejected: `Replace` (could clobber a partial reset); `backoffLimit > 0` (idempotency holds but the on-call review for a security-sensitive cron is mandated).
- **Q-D — Cron SCAN COUNT tuning**: SM default = `SCAN COUNT 1000`. Rationale: balances RTT overhead against per-SCAN payload; ~300 RTT at 100k api_keys is well within the 5-min deadline. Rejected: cluster-mode `KEYS` (blocks Redis event loop — anti-pattern).
- **Q-E — gRPC fire-and-forget vs Kafka emit for threshold-crossing**: SM default = **synchronous gRPC + detached-context goroutine** (Story-2.2 Q4 ratified-with-caveat for sync-SendEmail cascade). Rationale: 500ms deadline + detached-context means hot-path impact is bounded by 500ms wallclock + zero goroutine-leak risk (the goroutine exits on its own context deadline). Rejected: NEW Kafka topic `cap.threshold_crossed` (adds a NEW gateway-side Kafka producer — significant surface expansion); in-process buffer (gateway pods are stateless — eviction loses events).
- **Q-F — Sentinel-write failure posture**: SM default = **fail-OPEN** for both EXISTS-check + SETNX + dedupe SETNX. Rationale: cascades Story 5.2 Q-F (cap-check is a soft-throttle not a hard-security-boundary). Rejected: fail-CLOSED (would silently disable the breaker on Redis hiccups).
- **Q-G — `NotifyMonthlyCapThreshold` RPC vs reuse of SendEmail directly**: SM default = **NEW dedicated RPC** that encapsulates SETNX dedupe + PG fetch + SendEmail invocation. Rationale: gateway has no PG access for users/keys lookup; notification-svc owns the policy. Rejected: direct SendEmail from gateway with pre-cached identity (would extend the Story-3.2 cache value shape to carry `user_email` + `user_locale` — violates KISS + Story-5.2 M4 ratified topology).
- **Q-H — Threshold ratios (BR-2.1) — user-configurable?**: SM default = **hard-coded 0.80 + 1.00**. Rationale: KISS — product hasn't surfaced a "custom alert threshold" requirement; the surface can be expanded in a future Story. Rejected: env-var override (premature config-knob; future Story may move to per-user table).
- **Q-I — SETNX-on-claim vs SETNX-on-success (BR-2.4)**: SM default = **SETNX-on-claim** (matches Story-2.6 BR-5.8 idempotency posture verbatim). Rationale: if SendEmail fails 3 retries, the user MISSES the email for the month — better than the alternative (DEL the dedupe + re-fire on next request → potentially N attempts per month before exhausting). Rejected: SETNX-on-success (introduces "retry-flood" semantics on persistent SendGrid outage).
- **Q-J — PG-rollback on Redis-SCAN failure (BR error table)**: SM default = **NO ROLLBACK** (the PG UPDATE-to-0 is fait accompli; Redis purge is best-effort within the same Job). Rationale: an inconsistency where PG is reset but Redis isn't surfaces gracefully — Story 5.2 cache miss on the bearer hot path forces a fresh GET which returns the post-reset PG state of 0. Rejected: 2PC across PG + Redis (over-engineered for the cron path; on-call review handles the rare degraded path).
- **Q-K — `monthly_cost_reset` cron OWNER**: SM default = **auth-svc** (the table-owning service; reuses auth-svc credentials + repository code). Rationale: auth-svc is the canonical writer for `he_api.api_keys` (Stories 3.2 + 5.1); the cron is a sibling-binary alongside `apps/auth-svc/cmd/server/`. Rejected: dedicated `cron-svc` (premature — Story 5.4 is the only data-plane cron at this point; introducing a new service violates the YAGNI principle).
- **Q-L — notification-svc PG access**: **ARCHITECT ROUND 1 OVERRIDE (2026-05-26 — Wright)** — SM default REJECTED on a hard Go-language constraint. Go's `internal/` package visibility rule restricts `apps/auth-svc/internal/*` imports to packages rooted at `apps/auth-svc/`; with separate `go.mod` per app under `go.work`, the cross-module import is a compile-time failure. The Story-2.6 SM-default-cited precedent ("analytics-svc reads PG directly") was a citation error — verified via `apps/notification-svc/internal/handlers/data_export.go` uses notification-svc's OWN `internal/repository/data_export_requests.go`, NOT a cross-app import. **Architect RULED Fix-A**: NEW gRPC RPC `AuthService.GetCapNotificationContext(api_key_id) returns (GetCapNotificationContextResponse{user_email, user_locale, user_display_name, key_name})` on the auth-svc service surface (Story-5.1 service extended). Preserves auth-svc as sole canonical reader of `api_keys` (PII surface boundary); adds one detached-context gRPC hop on the email-emit path (NOT on the gateway hot path). Transcribed into T0.1 sub-bullet (b), T2.4 sub-bullet, T2.8 (entirely rewritten), Accumulated Context table, Source-Tree Touchpoints, and deliverable_bindings. **SM default REJECTED + Fix A APPLIED (Round 1 revision)**.
