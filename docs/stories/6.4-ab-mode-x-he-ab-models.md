### Architect Open Questions (gathered for Architect Round 1)

> SM defaults are stated; the Architect rules IN/DEFER/OVERRULE. **Q-A + Q-B are the headline forks.**

- **Q-A — The A/B RESPONSE shape: how do TWO models' outputs appear in ONE OpenAI-compatible response?** ⚠️ HEADLINE. The Epic AC says `响应包含两侧结果` (the response contains both sides' results), but an OpenAI `chat.completion` has a SINGLE top-level `model` string and a `choices[]` array. **SM default = Option A**: keep the body a valid OpenAI `chat.completion`; carry BOTH models' outputs in `choices[]` (leg A's choices first, then leg B's, with `index` re-assigned 0,1,…); attribute each choice to its source model via an **additive per-choice `x_he_model` string field** (He-API extension convention — appended after OpenAI-canonical fields, precedent: Story 4.7 `capabilities` / Story 3.6 `error.he_request_id`; OpenAI SDKs ignore unknown fields — Pydantic `extra="allow"`, verified at 4.7-CONTRACT-001/002); `usage` = the SUMMED usage of both legs; top-level `model` = leg A (the first X-He-AB-Models id); a NEW **response header `X-He-AB-Models: modelA,modelB`** echoes the served leg ids in order. **Architect alternatives**: (B) a non-OpenAI envelope `{"object":"he.ab_comparison","results":[{"model":"a","completion":{…full chat.completion…}},{…}]}` — cleaner separation, but the body is NO LONGER a `chat.completion`, breaking OpenAI-SDK parsing (the product's core value is OpenAI-compat); (C) per-leg `usage` breakdown surfaced via an additive `x_he_usage_breakdown` array alongside the summed top-level `usage`. SM strongly defaults **A** (stays OpenAI-compatible; the `x_he_model` per-choice attribution + `X-He-AB-Models` response header make the mapping unambiguous; mirrors the ratified He-API extension-field convention).

- **Q-B — Is A/B supported on the STREAMING path, or non-streaming only in 6.4?** ⚠️ HEADLINE. Interleaving two models' SSE chunk streams into one response — with two `choices` indices, the `[DONE]` terminator, and the 6.3 post-flush boundary — is genuinely hard and has no OpenAI precedent. **SM default = A/B is NON-STREAMING ONLY in 6.4**: `stream=true` + an `X-He-AB-Models` header → **`400_invalid_request`** ("A/B mode is not supported with streaming responses") emitted via the canonical `openaierr.Write`. The Epic AC (`同时调用 2 个模型` / `响应包含两侧结果`) is satisfied by the non-streaming comparison; streaming A/B is DEFERRED (KISS — it needs an interleaving/multiplexing design the Epic DoD does not require). **Architect alternatives**: (i) `stream=true` + A/B → silently IGNORE the A/B header and serve a normal single-model stream (rejected by SM — silently dropping an explicit user intent is surprising); (ii) land streaming A/B now with both legs multiplexed into `choices[0]`/`choices[1]` chunk indices (heavier; out of Epic-6 DoD scope). SM defaults the explicit-400 reading.

- **Q-C — Parallel vs sequential leg dispatch**: the title says `同时调用` ("call simultaneously"). **SM default = PARALLEL** — both legs dispatched concurrently via `errgroup.Group` (or two goroutines + a `sync.WaitGroup`), each through the non-writing dispatch primitive (Q-G); the handler waits for BOTH to settle, then merges. Wall-clock latency ≈ `max(legA, legB)`, NOT `legA + legB`. **Architect**: confirm (a sequential reading would double latency and contradicts `同时`).

- **Q-D — Do A/B legs FAILOVER (does each leg fall back over a chain)?** **SM default = NO per-leg failover**. The A/B models are EXPLICIT concrete pins — the user named exactly `modelA,modelB` to compare THOSE two. Substituting a different model on a leg's 502/504 would silently compare a model the user did not ask for (and surprise-bill it) — exactly the 6.3 Q-D `concrete-default does NOT failover` ruling, applied per leg. So each leg is a single-attempt concrete dispatch; a leg's 502/504 is TERMINAL for that leg (handled by Q-E partial-failure), not a failover trigger. This is what 6.3 meant by "Story 6.4 (A/B legs fail independently)" — leg A's failure does not abort leg B, and neither leg failovers. **Architect alternatives**: (i) each leg failovers over its OWN ranked chain (would need routing-svc to return a per-leg `failover_chain` — a bigger contract change; contradicts the explicit-pin intent); (ii) A/B legs MAY themselves be `he-router-*` meta-models that resolve-then-pin (out of 6.4 scope — Q-H restricts to concrete ids). SM defaults strict no-per-leg-failover.

- **Q-E — Partial failure: one leg succeeds, one fails** ⚠️. After Q-D (no per-leg failover), a leg can return a terminal 502/504. **SM default = best-effort ≥1-leg**: if AT LEAST ONE leg succeeds, return `200` with the successful leg(s)' choices in the merged body, and surface the failed leg via an additive per-leg marker — a `choices` entry carrying `finish_reason:"he_upstream_error"` + `x_he_model` + an `x_he_error` object (the failed leg's §5.1.2 envelope), so the response is STILL a parseable `chat.completion` and the client sees both legs' fate; the `X-He-AB-Models` response header lists only the SUCCESSFULLY-served ids; billing charges ONLY the successful leg(s) (Q-F). If BOTH legs fail, write the canonical terminal envelope (the last/representative upstream error — today's 6.3 terminal behaviour). **Architect alternatives**: (i) all-or-nothing — if EITHER leg fails, fail the whole request (simpler, but throws away a good result the user paid the prompt for); (ii) return `200` with only the successful choices and a `X-He-AB-Partial: true` header, omitting the failed leg entirely (loses the failure detail). SM defaults best-effort-with-annotation; this is a genuine UX decision for the Architect.

- **Q-F — Billing: A/B bills BOTH legs (dual-charge)** ⚠️ INVARIANT. A/B genuinely makes TWO real upstream calls → two real costs. **SM default + INVARIANT**: `tokenDeducter.TPMDeduct` is called for EACH successfully-served leg (or once with the SUMMED `total_tokens` of all successful legs) — the user is charged for exactly the upstream work that ran. A failed leg (Q-E) carries no usage → not charged. This DIFFERS from 6.3 failover (which bills ONCE because only one model ultimately serves). The `X-He-Cost-Usd` response header (§5.1.1:48) reflects the COMBINED cost. A dedicated test asserts `deducted == legA.total + legB.total` on a both-succeed request, and `== legA.total` on a one-leg-fails request. **Architect**: confirm the dual-charge invariant (this is the single most important correctness fact for A/B — the user opted into 2 calls by sending 2 models).

- **Q-G — The non-writing dispatch primitive (how two legs are collected before the merge)**: `serveAdapterNonStream` [Source: apps/api-gateway/internal/handlers/chat_completions.go:456-518] WRITES directly to `w` (sets `X-He-Selected-Model`, calls `writeChatJSON`, then `TPMDeduct`) — so it cannot be called twice for one response. **SM default**: extract a pure **`dispatchAdapterOnce(ctx, req, servedModel, handle) (*ChatResponse, *Usage, error)`** that performs the adapter `Chat()` + chunk-drain + `adapterChunkToResponse` but RETURNS the response WITHOUT writing or billing; `serveAdapterNonStream` (single-model path) becomes a thin wrapper that writes + bills its result (zero regression for 6.2/6.3); the A/B path calls `dispatchAdapterOnce` per leg in parallel, then a NEW `mergeABResponses(legs) *ChatResponse` builds the merged body, and the handler writes once + bills per leg (Q-F). **Architect**: confirm the refactor shape (keeps the single-model write+bill path byte-identical while making the dispatch re-usable).

- **Q-H — Exactly 2 models, or N?** The header example is `qwen-max,deepseek-v3` (two); the Epic AC says `同时调用 2 个模型` (call 2 models). **SM default = EXACTLY 2** concrete catalogue ids: parse the comma-separated `X-He-AB-Models`, trim/normalise, de-dup; if the resulting count ≠ 2 → `400_invalid_request` ("X-He-AB-Models requires exactly 2 distinct models"). A `he-router-*` meta-model or an id absent from the catalogue → `400_invalid_request` (each leg must be a concrete, routable model). The proto `ab_models` is `repeated` (allows N) but 6.4 enforces 2 at the gateway. **Architect alternatives**: (i) allow N≥2 legs (generalises the merge + dual-billing to N-billing — more flexible but unbounded fan-out / cost; the Epic only asks for 2); (ii) allow the two ids to be the SAME model (compare run-to-run variance) — SM de-dups to 1 → 400 under the default; Architect may allow duplicates. SM defaults exactly-2-distinct-concrete.

- **Q-I — Precedence: A/B header vs `X-He-Routing-Strategy` / `he-router-*` meta-model**: when `X-He-AB-Models` is present AND a strategy/meta-model is also specified. **SM default = A/B WINS and OVERRIDES selection** — the presence of `X-He-AB-Models` makes the request a dual-dispatch over the 2 named models; the `model` field + `X-He-Routing-Strategy` header are IGNORED for selection (the 2 A/B ids ARE the selection). slog WARN `ab_overrides_strategy` when both are present. So the cascade-locked 6.2 precedence (meta-model > header > default) applies ONLY when no A/B header is present; A/B sits ABOVE it. **Architect alternatives**: (i) each A/B leg is itself routed via the strategy (the strategy picks each leg from a pool — contradicts "the user named the 2 models"); (ii) `400` on A/B + strategy conflict (rejected by SM — over-strict; A/B is simply the more specific intent). SM defaults A/B-overrides.

- **Q-J — Rate-limit: one A/B request = ONE QPS/RPM tick** INVARIANT. QPS/RPM are counted at request ADMISSION (once per HTTP request, in the Story-5.3 middleware UPSTREAM of the handler). **SM default + INVARIANT**: the A/B fan-out lives INSIDE the handler, AFTER the rate-limit middleware → one A/B request consumes ONE QPS/RPM token regardless of the 2 upstream calls; TPM reflects BOTH legs' tokens (Q-F). A test asserts a 2-leg A/B request consumes one QPS token, not two. **Architect**: confirm (consistent with 6.3 Q-L).

- **Q-K — keypolicy (Story 5.2) scope interaction**: the 5.2 `keypolicy` gate 403s a request whose model ∉ `scope.models`. **SM default**: BOTH A/B leg ids MUST pass the key's `scope.models` gate BEFORE dispatch; a leg outside scope → `403_model_not_in_scope` for the WHOLE request (NOT a silent drop) — the user explicitly named that model, so 403 is the honest answer (contrast 6.3, which silently scope-FILTERS the failover tail because the user did not name those fallbacks). Reuse the 6.3 scope source; the validation is "both legs in scope" not "filter the chain". **Architect**: confirm (alternative: drop the out-of-scope leg and run A/B as a degenerate single-leg — rejected by SM as surprising).

## Story

As an **api-gateway user calling `POST /v1/chat/completions` who wants to compare two models on the same prompt**,
I want **to send `X-He-AB-Models: modelA,modelB` and have the gateway call BOTH models in parallel and return BOTH of their outputs in a single OpenAI-compatible response — each output attributed to its source model, billed for both real upstream calls, but admitted as one request**,
so that **I can A/B-compare two models' answers in one round-trip without firing two separate requests or correlating two responses myself, with the `X-He-AB-Models` response header truthfully reporting which models served and my account charged for exactly the two upstream calls that actually ran.**

## Acceptance Criteria

> These ACs encode the SM DEFAULTS. **Q-A … Q-K are Architect forks** — the AC text below is the SM-default scope; bullets marked ⚠️ Architect may overrule become LOCKED after Round 1. Behaviour-defining anchors: response shape = OpenAI `chat.completion` with both legs in `choices[]` + per-choice `x_he_model` + `X-He-AB-Models` response header (Q-A Option A); A/B is NON-STREAMING-only — `stream=true` + header → `400` (Q-B); legs dispatched in PARALLEL (Q-C); legs are concrete pins with NO per-leg failover (Q-D); partial failure = best-effort ≥1-leg with annotation (Q-E); BOTH legs billed (Q-F INVARIANT); exactly-2 distinct concrete ids (Q-H); A/B overrides strategy (Q-I); ONE rate-limit tick (Q-J); both legs must pass scope (Q-K).

### AC1: gateway parses `X-He-AB-Models` and routing-svc returns the A/B decision (`ab_models` → `is_ab_test` + `ab_selected_models`)

**Scenario**
```gherkin
GIVEN an authenticated POST /v1/chat/completions request carrying header X-He-AB-Models: modelA,modelB
WHEN the gateway parses the header
THEN
- the value is split on ",", each id trimmed + normalised + de-duplicated; the result MUST be EXACTLY 2 distinct ids (Q-H)
- a count ≠ 2 (0, 1, 3+, or 2-but-duplicate) → 400_invalid_request ("X-He-AB-Models requires exactly 2 distinct models") via openaierr.Write
- the gateway calls routing-svc SelectModel with ab_models=[modelA,modelB] populated (the EXISTING field 4 — was empty per 6.2 Q-N) within the 100ms deadline (6.2 Q-E)
- routing-svc resolves the A/B decision: validates each id is a concrete catalogue model (NEVER a he-router-* virtual entry — BR1-2 correctness gate), sets is_ab_test=true (field 3 — was always false) and ab_selected_models=[modelA,modelB] (field 4 — the resolved concrete leg ids, was empty)
- an ab_models id that is unknown to the catalogue OR is a he-router-* id → 400_invalid_request (each leg must be concrete + routable — Q-H)
- the SelectModelRequest/Response CONTRACT is REUSED verbatim — the 3 fields are 6.1-preshaped (no new field numbers, no buf breaking change)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR1-1 | `X-He-AB-Models` is parsed at the gateway (NEW const `ABModelsHeader = "X-He-AB-Models"` in `routingclient`); the gateway POPULATES `SelectModelRequest.ab_models` (the 6.1-preshaped field 4 — 6.2 left it empty per Q-N, BR1-4). The request contract is REUSED — NO new request field. |
| BR1-2 | ⚠️ CORRECTNESS GATE (inherits 6.2 BR2-5): every `ab_selected_models` id MUST be a concrete catalogue id — `he-router-*` virtual entries are NOT routable A/B legs (they would miss `adapterRegistry.Resolve` → hot-path failure). routing-svc rejects a `he-router-*` leg via the existing `concreteCandidates()`/catalogue check → the gateway surfaces `400_invalid_request`. A dedicated test asserts a `he-router-*` leg is rejected, not dispatched. |
| BR1-3 | `is_ab_test` (response field 3) is set TRUE on the A/B path (was always false in 6.1/6.2/6.3); `ab_selected_models` (response field 4) carries the 2 resolved concrete leg ids. The gateway READS `is_ab_test` to fork into the A/B dispatch path (BR2-1). A non-A/B request (no header) → `is_ab_test=false`, `ab_selected_models` empty → the 6.3 single-model path UNCHANGED. |
| BR1-4 | EXACTLY 2 distinct concrete ids (Q-H). The proto `ab_models` is `repeated` (N-capable) but 6.4 ENFORCES 2 at the gateway parse step + asserts 2 in the routing-svc handler. de-dup happens BEFORE the count check (`a,a` → 1 → 400). |
| BR1-5 | A/B header presence OVERRIDES strategy selection (Q-I): when `X-He-AB-Models` is present, the `model` field + `X-He-Routing-Strategy` header are IGNORED for selection; slog WARN `ab_overrides_strategy` if a strategy/meta-model was ALSO specified. The cascade-locked 6.2 precedence applies only on the non-A/B path. |

### AC2: gateway dispatches BOTH legs in PARALLEL and MERGES them into one OpenAI-compatible response (`同时调用 2 个模型` → `响应包含两侧结果`)

**Scenario**
```gherkin
GIVEN the gateway holds the A/B decision (is_ab_test=true, ab_selected_models=[modelA,modelB]) from AC1, stream=false
  AND both legs pass the key's scope.models gate (Q-K)
WHEN the gateway dispatches the A/B request
THEN
- both legs are dispatched in PARALLEL (errgroup / concurrent goroutines — Q-C); each leg resolves its adapter via the EXISTING adapterRegistry.Resolve(legModel) and runs the SAME request body through the NON-WRITING dispatchAdapterOnce primitive (Q-G), which RETURNS the leg's ChatResponse + Usage without writing or billing
- the handler waits for BOTH legs to settle, then mergeABResponses builds ONE chat.completion: choices[] = legA.choices followed by legB.choices with index re-assigned (0,1,…); each choice carries an additive x_he_model = the leg's served model id (Q-A); usage = SUMMED total/prompt/completion tokens of the successful legs; top-level model = legA's id; id = a single chatcmpl id
- the response carries a NEW header X-He-AB-Models: modelA,modelB (the served leg ids, in order) + X-He-Cost-Usd = the COMBINED cost (Q-F); X-He-Selected-Model is NOT set on the A/B path (it names a single model; the A/B mapping lives in choices[].x_he_model + the X-He-AB-Models header)
- the merged body remains a valid OpenAI chat.completion — an OpenAI SDK parses it (unknown x_he_model ignored via Pydantic extra=allow; 4.7-CONTRACT precedent)
- BOTH legs are BILLED (Q-F INVARIANT): TPMDeduct charges legA.total_tokens + legB.total_tokens (the two real upstream calls)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR2-1 | The gateway forks on `resp.GetIsAbTest()` AFTER the routing decision in `chat_completions.go` (BEFORE the `dispatchNonStreamWithFailover` call at [Source: chat_completions.go:529]): A/B path → `dispatchAB(...)`; non-A/B → the UNCHANGED 6.3 failover path. |
| BR2-2 | ⚠️ NON-WRITING PRIMITIVE (Q-G): extract `dispatchAdapterOnce(ctx, req, servedModel, handle) (*ChatResponse, usage, error)` from `serveAdapterNonStream` [Source: chat_completions.go:456-518] — it does the `Chat()` + drain + `adapterChunkToResponse` but does NOT write `w` and does NOT bill. `serveAdapterNonStream` becomes a thin wrapper (write + `X-He-Selected-Model` + `TPMDeduct`) so the 6.2/6.3 single-model path is BYTE-IDENTICAL (zero regression). |
| BR2-3 | ⚠️ PARALLEL (Q-C): legs run concurrently via `errgroup.Group` (or `sync.WaitGroup`); the handler blocks until BOTH settle. Wall-clock ≈ `max(legA, legB)`. Each leg keeps its existing per-adapter deadline; the A/B request keeps its overall request context. NO new shared mutable state between legs (each writes its own result slot — `-race` clean). |
| BR2-4 | ⚠️ MERGE (Q-A Option A): `mergeABResponses` produces a valid `chat.completion`: `choices` = concatenation with re-indexed `index`; per-choice additive `x_he_model`; `usage` summed; single `id`/`created`/`object="chat.completion"`; top-level `model` = leg A. The additive `x_he_model` follows the He-API extension convention (appended last; precedent Story 4.7 capabilities / 3.6 error.he_request_id). |
| BR2-5 | ⚠️ DUAL-BILLING (Q-F INVARIANT): `TPMDeduct` charges the SUM of the successful legs' `total_tokens` (two real upstream calls → two real costs). A failed leg (AC3) carries no usage → not charged. `X-He-Cost-Usd` reflects the combined cost. Differs from 6.3 failover (bills once). |
| BR2-6 | ⚠️ SCOPE (Q-K): BOTH leg ids MUST pass the key's `scope.models` gate BEFORE dispatch; an out-of-scope leg → `403_model_not_in_scope` for the WHOLE request (NOT a silent drop — the user named it). Reuse the 6.3 scope source. |
| BR2-7 | `X-He-Selected-Model` is NOT emitted on the A/B success path (it names one model; A/B has two). The A/B mapping is `choices[].x_he_model` + the `X-He-AB-Models` response header. (Non-A/B paths keep `X-He-Selected-Model` per 6.2 BR1-2.) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| an A/B leg id ∉ key scope.models | 403 | `403_model_not_in_scope` | terminal — openaierr.Write; no dispatch (Q-K) |
| a leg's adapter does not resolve in adapterRegistry | 502 | `502_upstream_unavailable` | that leg fails → Q-E partial-failure handling (no panic — BR2-3) |
| both legs succeed | 200 | (merged chat.completion) | write merged body + X-He-AB-Models header; TPMDeduct sum (Q-F) |

### AC3: partial failure — legs fail INDEPENDENTLY (one leg down, the other still returns)

**Scenario**
```gherkin
GIVEN an A/B request whose two legs are dispatched in parallel (AC2)
WHEN one leg returns a terminal upstream error (502_upstream_unavailable / 504_upstream_timeout) and the other succeeds
THEN
- the legs do NOT failover (Q-D — they are explicit concrete pins; mirrors 6.3 concrete-default-no-failover); the failed leg's error is terminal FOR THAT LEG only
- the request returns 200 with a merged chat.completion containing the SUCCESSFUL leg's choices PLUS a marker choice for the failed leg: finish_reason="he_upstream_error", x_he_model=the failed leg's id, and an additive x_he_error object carrying the failed leg's §5.1.2 envelope (so the body is STILL a parseable chat.completion and the client sees both legs' fate) — Q-E
- the X-He-AB-Models response header lists ONLY the successfully-served id; only the successful leg is billed (Q-F)
WHEN BOTH legs fail
THEN
- the canonical terminal §5.1.2 envelope is written ONCE (the representative/last upstream error — today's 6.3 terminal behaviour via openaierr.Write); nothing is billed; status reflects the upstream code (502/504)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR3-1 | ⚠️ NO per-leg failover (Q-D): each A/B leg is a single concrete dispatch; a leg's 502/504 does NOT trigger the 6.3 `failover_chain` loop (the user pinned exactly these 2 models). "Fail independently" = leg A's failure does not abort leg B. |
| BR3-2 | ⚠️ BEST-EFFORT ≥1-leg (Q-E): if ≥1 leg succeeds → `200` with the successful leg(s) + a failed-leg marker choice (`finish_reason:"he_upstream_error"` + `x_he_model` + `x_he_error`{the 5-field envelope}). The body stays a valid `chat.completion`. |
| BR3-3 | If BOTH legs fail → ONE terminal envelope via the canonical `openaierr.Write` (reuse the 6.3 `writeFailoverTerminal`/terminal path); zero billing; the representative upstream error code (prefer 504 if any leg timed out, else 502 — Architect may rule the precedence). |
| BR3-4 | A leg whose adapter does not resolve in `adapterRegistry` (BR2-6 / [chat_completions.go:545] precedent) is treated as a failed leg (its marker carries `502_upstream_unavailable`), NOT a panic. |
| BR3-5 | The retriable-code classification reuses the 6.3 `isRetriableUpstream` helper [Source: chat_completions.go:571/618] to decide a leg's error code (502/504); a NON-retriable leg error (e.g. `400_content_filter` on one leg's content) is surfaced in that leg's `x_he_error` marker unchanged (still best-effort for the other leg). |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| one leg 502/504, other leg 200 | 200 | (merged: success choice + failed-leg marker choice) | best-effort; bill the success leg only (Q-E/Q-F) |
| both legs 502 | 502 | `502_upstream_unavailable` | terminal envelope once; zero billing (BR3-3) |
| both legs fail, ≥1 timed out | 504 | `504_upstream_timeout` | terminal envelope once (representative code — BR3-3) |
| one leg non-retriable (e.g. 400_content_filter), other 200 | 200 | (merged: success + the failed leg's envelope in x_he_error) | best-effort (BR3-5) |

### AC4: streaming guard + observability + zero non-A/B regression

**Scenario**
```gherkin
GIVEN the A/B path instrumented + the existing suites
WHEN a request combines stream=true with an X-He-AB-Models header
THEN
- the gateway returns 400_invalid_request ("A/B mode is not supported with streaming responses") via openaierr.Write — A/B is NON-STREAMING-only in 6.4 (Q-B); the guard fires BEFORE any upstream dispatch

- a non-PII slog line {event:"chat_completions_ab", ab_models:[a,b], served_models:[...], failed_models:[...], he_request_id} is emitted (NEVER user_id / message content — BR4-1)

- a request WITHOUT X-He-AB-Models is byte-for-byte the 6.3 path: ZERO A/B overhead, ZERO extra upstream calls, X-He-Selected-Model present per 6.2 BR1-2
- the full existing suite is green: 6.3 failover + 6.2 routing (strategy precedence, X-He-Selected-Model, score_source) + 6-vendor adapter matrix (4.1-4.6 INT-009) + 4.7-INT-001 + SSE §5.1.1.1 shape + keypolicy(5.2) + rate-limit(5.3, ONE tick per A/B request — Q-J) + cap(5.4)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR4-1 | slog discipline = non-PII only (`ab_models`, `served_models`, `failed_models`, `he_request_id`) — NEVER `user_id` / message content [Source: coding-standards.md §12.1; 6.2 BR4-2 / 6.3 BR4-1]. |
| BR4-2 | The streaming guard (Q-B) fires at the top of the handler's stream fork — before any routing/dispatch — when `req.Stream && abHeaderPresent`; reuses the canonical `openaierr.Write` (no new envelope code; reuses `400_invalid_request`). |
| BR4-3 | ⚠️ RATE-LIMIT INVARIANT (Q-J): the A/B fan-out lives INSIDE the handler, AFTER the Story-5.3 rate-limit middleware → ONE A/B request = ONE QPS/RPM tick. TPM reflects both legs (Q-F). A test asserts one QPS tick per 2-leg request. |
| BR4-4 | A/B metrics reuse the `routingclient`/handler metrics struct pattern [Source: apps/api-gateway/internal/routingclient/metrics.go]; `outcome` label cardinality is 3 (both_ok/partial/both_failed). |
| BR4-5 | NO new §5.1.2 envelope code — A/B reuses `400_invalid_request` (parse/streaming/scope-count) + `403_model_not_in_scope` (Q-K) + `502/504` (leg failure). The canonical `openaierr.Write` stays the sole envelope writer. |

- **Hot-path discipline — non-A/B path UNCHANGED**: a request WITHOUT `X-He-AB-Models` MUST be byte-for-byte the 6.3 path — ZERO extra latency, ZERO extra upstream calls. The A/B fork engages ONLY when `is_ab_test==true`. The `ab_models` field is computed by the gateway from the header and sent in the SAME `SelectModel` call 6.2 already makes (no extra RPC). - **Parallel + non-writing primitive (Q-C/Q-G — the load-bearing refactor)**: `serveAdapterNonStream` [chat_completions.go:456-518] WRITES to `w` + bills today, so it cannot serve two legs. Extract `dispatchAdapterOnce` (returns `*ChatResponse`+usage, NO write/bill); `serveAdapterNonStream` becomes a thin write+bill wrapper (single-model path BYTE-IDENTICAL). The A/B path calls `dispatchAdapterOnce` per leg in PARALLEL (`errgroup`), then `mergeABResponses` + ONE write + per-leg bill.
- **Dual-billing (Q-F INVARIANT)**: A/B charges BOTH legs (`TPMDeduct == legA.total + legB.total`) — two real upstream calls. Contrast 6.3 failover (bills ONCE — only one model ultimately serves). `X-He-Cost-Usd` = combined. This is the single most important correctness fact for A/B.
- **Rate-limit (Q-J INVARIANT)**: the A/B fan-out is INSIDE the handler, AFTER the 5.3 rate-limit middleware → ONE A/B request = ONE QPS/RPM tick. [→ 6.3 Q-L precedent]
- **Scope (Q-K)**: BOTH legs must pass the 5.2 `scope.models` gate BEFORE dispatch — an out-of-scope leg → `403_model_not_in_scope` for the whole request (the user named it; NOT a silent drop — contrast 6.3, which silently scope-filters the un-named failover tail).
- **No per-leg failover (Q-D)**: A/B legs are explicit concrete pins → each is a single-attempt dispatch; a leg's 502/504 is terminal for that leg (Q-E partial-failure), NOT a 6.3 `failover_chain` trigger. "Fail independently" = leg A's failure doesn't abort leg B.
- **Streaming (Q-B)**: A/B is NON-STREAMING-only in 6.4. `stream=true` + `X-He-AB-Models` → `400_invalid_request` at the handler's stream fork, BEFORE any dispatch.
- **slog discipline** = non-PII only (`ab_models`/`served_models`/`failed_models`/`he_request_id`) — NEVER `user_id` / message content [→ coding-standards.md §12.1; 6.2 BR4-2 / 6.3 BR4-1].
- **No panic on the A/B path**; an unresolved leg / a failed leg degrades to the partial-failure marker, never a hang or panic [→ coding-standards.md §12.1].

### Implementation Summary

Story 6.4 lands A/B mode on the Story-6.2/6.3 routing hot path: when a caller sends `X-He-AB-Models: modelA,modelB`, the gateway dispatches BOTH models in parallel and returns BOTH outputs in one OpenAI-compatible `chat.completion`. The gateway parses the header into exactly-2-distinct concrete legs (`routingclient.ParseABModels`, dedup-before-count, Q-H), populates the 6.1-preshaped `SelectModelRequest.ab_models` on the SAME `SelectModel` call via a new `Decider.DecideAB` (no extra RPC), and routing-svc validates each leg is a concrete catalogue model (`Engine.ResolveABModels` — rejects `he-router-*`/unknown as `InvalidArgument`→400, BR1-2) and echoes `is_ab_test=true` + `ab_selected_models`. The load-bearing refactor extracts a NON-WRITING `dispatchAdapterOnce` primitive (Q-G) out of `serveAdapterNonStream` so two legs can be COLLECTED before merging; the single-model path becomes a thin write+bill wrapper and stays byte-identical (zero 6.2/6.3 regression). `dispatchAB` scope-gates BOTH legs against `claims.ScopeModels` (Q-K/Architect High-2), dispatches them concurrently via `sync.WaitGroup` (Architect High-1 — errgroup is absent from `apps/api-gateway/go.mod`) with one result slot per leg (`-race` clean, no shared mutable state), then `mergeABResponses` builds one `chat.completion`: re-indexed `choices[]`, additive per-choice `x_he_model`, summed `usage`, top-level `model`=legA, plus an `X-He-AB-Models` response header of the served ids (no `X-He-Selected-Model` — BR2-7). DUAL-BILLING (Q-F INVARIANT): ONE `TPMDeduct` of the summed successful-leg `total_tokens`. Legs do NOT failover (Q-D, concrete pins) and fail INDEPENDENTLY (Q-E): a leg's terminal 502/504 (or an unresolved adapter — no panic, BR3-4) becomes a marker choice (`finish_reason:"he_upstream_error"` + `x_he_model` + `x_he_error` §5.1.2 envelope) while the other leg still serves and is billed; if BOTH fail, ONE terminal envelope is written (representative code 504>502, BR3-3) and nothing is billed. A streaming guard rejects `stream=true`+A/B with `400_invalid_request` before any dispatch (Q-B); observability adds a non-PII `chat_completions_ab` slog line (BR4-1) + `he_routing_ab_total{outcome}` with 3-value cardinality (BR4-4).
