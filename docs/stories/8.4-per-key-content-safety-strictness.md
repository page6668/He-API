## Story

**As a** the He-API gateway operating under 生成式 AI 服务备案 compliance (and the API-Key owners who need to tune how aggressively the bidirectional content-safety filter blocks for THEIR key — a 备案-conservative production key wants block-everything, an internal/experimental key may tolerate only the high-severity 政治/暴恐 categories),
**I want** a per-Key 内容安全严格度 (`strict` / `default` / `loose`) that is stored on the `api_keys` row, configurable via the existing `PATCH /v1/me/keys/{api_key_id}` config path, carried onto the request hot path through the Story-5.2 `CachedClaims` seam, and applied as a **severity threshold** that gates BOTH the Story-8.2 入参 reject AND the Story-8.3 出参 redact/stream-guard — using the ratified 8.1 mapping (`loose`=block high only · `default`=block high+medium · `strict`=block all three),
**so that** Epic-8's DoD line "严格度可按 Key 配置" is met, the §9.3 severity metadata that 8.1/8.2/8.3 have carried-but-not-gated finally drives the block decision, and the live 备案 filter posture is preserved by construction (a key with no explicit setting fails CLOSED to the strict block-all behaviour 8.2/8.3 ship today) — all reusing the proven 5.2 config seam (PATCH → auth-svc `UpdateApiKey` → `config_updated` sentinel → gateway cache purge) and the in-process `contentsafety.Scanner` core, with NO new endpoint, NO new cache machinery, and NO fork of the lexicon.

## Epic Context
**Epic**: 8 - 内容安全与合规准备
双向敏感词过滤 + 治理日志 + 备案材料归档。

**Epic DoD**: 入参/出参敏感词过滤上线 · **严格度可按 Key 配置** · 备案材料 PDF 模板生成。

**Story 8.4 Deliverables** (the THIRD Epic-8 DoD line — the per-Key strictness knob that 8.2/8.3 deliberately deferred; both currently block on ANY confirmed match = the future "strict" posture):
- A new additive `api_keys.content_safety_strictness` column (enum `strict`/`default`/`loose`, NOT NULL, default = the no-regression posture — see OQ-8.4-1) via migration `0013_*`, surfaced through the auth-svc `ValidateApiKey` / `UpdateApiKey` RPCs (additive proto fields) and the gateway `CachedClaims` (a new `omitempty` field, mirroring the 5.2 `MonthlyCostCapUSD` carry).
- The user-facing **config path**: an additive `content_safety_strictness` field on `PATCH /v1/me/keys/{api_key_id}` (validated against the enum at the gateway BEFORE the RPC, mirroring the 5.2 cap/scope validation), persisted by auth-svc `UpdateApiKey`, riding the EXISTING `config_updated` sentinel (≤300s cache coherency) + audit emission — NO new endpoint.
- A pure **severity-gating seam** in `internal/contentsafety` (`Strictness` type + `MinSeverity(level)` + a severity-rank comparison) consumed by all THREE existing filter decision points: the 8.2 input reject (chat_completions.go), the 8.3 non-stream redact (`redactResponse`), and the 8.3 stream `StreamGuard`. A confirmed match now blocks ONLY when its `Match.Severity` meets the Key's threshold; the scan returns the first AT-OR-ABOVE-threshold hit (a sub-threshold match no longer short-circuits and hides a later qualifying one).
- The per-request strictness is read from `middleware.CacheValueFromContext` (the seam 8.2 reserved for 8.4) and **fails CLOSED** to the strict posture when absent/empty/unknown (a pre-8.4 cached entry, a NULL, or a corrupt value never silently relaxes a 备案 gate).

> **Scope boundary (explicit)**: 8.4 adds the **severity-gating layer + the per-Key config storage/path** only. OUT of scope and owned elsewhere: the actual `content_safety_logs` DB write + excerpt redaction + 6-month retention + 备案 PDF (Story 8.5 — 8.4 makes the gated decision and hands the SAME `SafetyEvent` to the no-op `Recorder`, optionally annotated with the effective strictness); the §9.3 layer-3 BERT 分类器 (later epic); tool-arg/multimodal scanning (Epic 9). 8.4 does NOT change the scanner's detection/no-false-negative machinery (8.2/8.3) — it ONLY adds a post-detection severity gate. The `loose`/`default`/`strict` mapping is the one RATIFIED by 8.1 OQ-8.1-5 (`loose`=high · `default`=high+medium · `strict`=all); 8.4 confirms + applies it (8.1 BR-1.4 explicitly reserved the application to 8.4).

### AC2: 严格度→严重度 gating mapping applied to BOTH directions (severity threshold gate)

**Scenario**
```gherkin
GIVEN a confirmed scanner Match{Severity ∈ {high, medium, low}} on EITHER the 入参 path (8.2) OR the 出参 path (8.3 non-stream redact + stream guard), and the Key's resolved strictness level
WHEN the gateway applies the RATIFIED 8.1 mapping (loose → minSeverity=high · default → minSeverity=medium · strict → minSeverity=low) via the pure contentsafety severity-rank comparison Blocks(matchSeverity, level)
THEN
  - a match BLOCKS only when rank(match.Severity) ≥ rank(minSeverity(level)) — i.e. loose blocks ONLY high; default blocks high+medium; strict blocks all three (the current 8.2/8.3 block-all behaviour == strict)
  - the scan returns the FIRST AT-OR-ABOVE-THRESHOLD hit: a sub-threshold match (e.g. a low term under loose) does NOT short-circuit the scan and does NOT hide a later qualifying match (e.g. a high term later in the same text) — the fail-fast contract becomes "first QUALIFYING hit", not "first ANY hit"
  - the SAME threshold gates all THREE decision points consistently for a given request: the 8.2 input reject (chat_completions.go:486-495), the 8.3 non-stream redactResponse (chat_completions_safety_output.go:71-85), and the 8.3 StreamGuard (streamguard.go Observe) — one Key, one posture, both directions
  - detection (the no-false-negative scanner machinery from 8.2/8.3) is UNCHANGED — 8.4 adds ONLY a post-detection severity gate; a term is still DETECTED identically, it is just not ACTED ON when below the Key's threshold
  - a strict-level key is BYTE-IDENTICAL to the pre-8.4 behaviour (block-all = the shipped 8.2/8.3 posture) — strict is the zero-regression baseline
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | The mapping is the one RATIFIED by **8.1 OQ-8.1-5** and reserved for 8.4 by 8.1 BR-1.4: `loose`=block high only · `default`=block high+medium · `strict`=block all three. Severity rank: high(3) > medium(2) > low(1); `minSeverity`: loose→high · default→medium · strict→low. `Blocks(sev, level) := rank(sev) ≥ rank(minSeverity(level))`. ### Technical Constraints

- **Canonical design source**: the §9.3 内容安全 filter carries per-term `severity`; Epic-8 DoD line 2 = "严格度可按 Key 配置". 8.1 SHIPPED the severity metadata and EXPLICITLY reserved its application: "Severity is the field Story 8.4 maps onto per-Key strictness (loose / default / strict)" and "The severity→strictness PRE-STAGE mapping is RESERVED for Story 8.4 and is NOT enforced or applied in 8.1 … The intended (8.4-confirmable) mapping: `loose`=block high only; `default`=block high+medium; `strict`=block all three." 8.2 and 8.3 then both shipped block-on-ANY-match (= the future "strict" posture) and carried `Match.Severity` into the event WITHOUT gating on it. **8.4 finally applies the gate.** [Source: docs/stories/8.1-sensitive-word-lexicon-zh-en-extensible.md:63 (BR-1.4), :520 (OQ-8.1-5 APPROVED)], [Source: apps/api-gateway/internal/handlers/chat_completions.go:306], [Source: apps/api-gateway/internal/handlers/chat_completions_safety_output.go:105]
- **Severity enum is a ratified closed set** `{high, medium, low}` (lexicon.go:79-83), validated at lexicon construction (panic on unknown). The mapping rank: high(3) > medium(2) > low(1); `minSeverity`: loose→high, default→medium, strict→low; `Blocks(sev, level) := rank(sev) ≥ rank(minSeverity(level))`. The strictness LEVELS `{strict, default, loose}` are a DIFFERENT closed set (the user-facing knob) — do not conflate the two enums. [Source: packages/safety-lexicon/lexicon.go:73-89,118-122]
- **The 5.2 per-Key-config seam is the spine of 8.4** — strictness is a per-Key scalar policy field exactly like `monthly_cost_cap_usd`, and threads through the IDENTICAL path 5.2 built: dedicated `api_keys` column → auth-svc `ValidateApiKey` response field → gateway `CachedClaims` (JSON in Redis, `omitempty` backward-compat) → `applyContext`/`CacheValueFromContext` on the hot path; and the write path PATCH → auth-svc `UpdateApiKey` (present-only merge) → `config_updated` sentinel → gateway cache purge. 8.4 adds ONE field to each of these existing structures — it does NOT invent a new config mechanism. - **Cache coherency is ALREADY solved (do not rebuild it)**: the gateway's `sentinelExists` returns true for EITHER `auth:apikey:revoked:{id}` OR `auth:apikey:config_updated:{id}` (bearer_auth.go:485-492), and the cache-hit path purges + falls through to a fresh RPC when it does (:307-349). auth-svc `UpdateApiKey` already SETs `config_updated` on every commit (update.go:338-349). So a strictness change is eventually-consistent within the ≤300s positive-cache TTL with ZERO new code — the SAME contract 5.2 shipped for the cap. The 备案 implication (≤300s lag on a strictness change) is the documented 5.2 behaviour, not a new 8.4 risk. [Source: apps/api-gateway/internal/middleware/bearer_auth.go:77-89,307-349,485-492], [Source: apps/auth-svc/internal/apikey/deps.go:41-46]
- **Three decision points, one gate**: today all three call `Scanner.ScanText` and act on the FIRST ANY-severity hit — input reject (chat_completions.go:488), non-stream redact (chat_completions_safety_output.go:72), stream guard (streamguard.go:91). This is the load-bearing change (OQ-8.4-2). The omitempty `CachedClaims` field means a pre-8.4 Redis entry deserializes the field as "" during a rollout — that MUST map to strict, never to a relaxed posture.
