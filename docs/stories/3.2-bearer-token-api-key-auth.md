### AC1: Gateway Bearer-Auth Middleware — Request / Response Contract

**Scenario**
```gherkin
GIVEN the api-gateway binary built from apps/api-gateway/cmd/server, started on :8080, with HE_API_AUTH_SVC_URL pointing at a reachable auth-svc and HE_API_REDIS_URL pointing at a reachable Redis 7.2+ instance
AND an api_keys row exists in the gateway-reachable Postgres with key_prefix='he-abc123', key_hash=bcrypt('he-abc123XYZ...', cost=12), revoked_at=NULL, scope='{}'::jsonb (issued via the test-only IssueKeyForTest helper)
WHEN a client issues `POST /v1/chat/completions` with header `Authorization: Bearer he-abc123XYZ...` and a syntactically-valid OpenAI chat body
THEN
  - the middleware extracts the token by stripping the `Bearer ` prefix (case-insensitive — RFC 6750 §2.1)
  - the middleware checks Redis at key `auth:apikey:{sha256(plaintext_key)}` first; on miss it calls `authv1connect.AuthServiceClient.ValidateApiKey(ctx, &ValidateApiKeyRequest{plaintext_key, client_ip, user_agent})` via the existing connectrpc client
  - auth-svc looks up by `key_prefix` (first 16 chars, per the indexed `idx_api_keys_hash` companion + the `key_prefix` column in `data-models.md §4.1`), bcrypt-compares ALL candidate rows' `key_hash` against the supplied plaintext, finds a match, and returns `ok=true, api_key_id, user_id, team_id, scope, revoked=false`
  - the gateway SETEXs `auth:apikey:{sha256(plaintext_key)}` → `{api_key_id, user_id, team_id, scope}` for 300 seconds, populates `r.Context()` with `WithAPIKeyID` / `WithUserID` / `WithScope`, and invokes the inner handler (the Story-3.3-placeholder `/v1/chat/completions` returns 501 — confirming the middleware chain executed)
  - the response carries NO `Set-Cookie`, NO `X-He-Request-Id` (request-id taxonomy lands in Story 3.6), and the standard SecurityHeaders bundle (CSP / HSTS / X-Frame-Options) from the existing Story-2.2 middleware
WHEN a client issues the same request with header `Authorization: Bearer he-doesnotexist`
THEN
  - auth-svc returns `ok=false, reason=NOT_FOUND`
  - the gateway does NOT SETEX a negative result (cache only positives — BR-1.6)
  - the gateway short-circuits with HTTP 401, `Content-Type: application/json; charset=utf-8`, body exactly:
    ```json
    {"error":{"code":"401_invalid_api_key","message":"Invalid API key provided.","type":"invalid_request_error","param":null,"he_request_id":null}}
    ```
  - the inner handler is NEVER invoked (assertion: place a panic-on-call sentinel in the test wiring; the test passes only if the panic does NOT fire)
WHEN the client omits the Authorization header entirely (or supplies a non-Bearer scheme like `Basic foo`)
THEN
  - the gateway short-circuits with the same 401 envelope as above (code `401_invalid_api_key`, message `Missing or malformed Authorization header.`) — no auth-svc RPC is issued (fail-fast at the middleware boundary)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | Token extraction MUST be case-insensitive on the `Bearer ` scheme prefix per RFC 6750 §2.1 (e.g., `bearer he-...`, `BEARER he-...` all accepted); the token portion is treated as opaque case-sensitive. **Implementation (per Architect OQ3 ruling)**: Promote the existing `stripBearer` stub at `apps/api-gateway/internal/middleware/jwt_verify.go:233` to an exported `middleware.StripBearer(h string) string` helper using case-insensitive scheme-prefix matching (e.g., compile-once `(?i)^Bearer\s+` regex OR `strings.EqualFold` on the first 7 chars). The current stub uses case-sensitive `strings.TrimPrefix(h, "Bearer ")` which violates RFC 6750 §2.1 — fix in this Story while both auth paths converge on the helper. Per the Architect note, the stub is currently unused by `jwt_verify.go`'s caller chain (line comment "future Authorization-header consumers"), so the promotion + behaviour-fix introduces zero regression risk. |
| BR-1.2 | The middleware MUST emit a single auth-svc RPC per cache-miss request; concurrent requests for the same key during cache miss are allowed to issue parallel RPCs (no in-flight singleflight in this Story — defer to a future perf Story if Grafana shows thundering herd). |
| BR-1.3 | On any auth-svc RPC error other than `ok=false` (e.g., DEADLINE_EXCEEDED, UNAVAILABLE), the gateway MUST emit HTTP 503 with `{"error":{"code":"503_auth_unavailable","message":"Authentication service temporarily unavailable.","type":"server_error","param":null,"he_request_id":null}}` — distinct from 401 so clients can retry vs treat-as-credential-error. The auth-svc UNAVAILABLE branch MUST log at WARN with `slog.String("error", err.Error())` so SRE alerts route correctly. |
| BR-1.4 | The middleware MUST NOT apply to `/health`, `/healthz` (probeMux bypass — already mounted before this chain per Story 3.1 BR-1.3), nor to `/v1/auth/*`, `/v1/me*`, `/v1/account/data-export*`, nor `/.well-known/jwks.json`. Application rule: middleware is wrapped ONLY on `/v1/chat/completions`, and (when Stories 3.3-3.6 land) `/v1/models`, `/v1/embeddings`, `/v1/audio/*`, `/v1/images/*`, `/v1/usage`, `/v1/balance`. Concrete implementation: per-route `mux.Handle("POST /v1/chat/completions", bearerAuth.RequireAPIKey(http.HandlerFunc(chatPlaceholder)))` — NOT global wrapping of the whole mux. |
| BR-1.5 | The cache key MUST be `auth:apikey:` + lowercase hex of `sha256(plaintext_key)` — NOT the plaintext itself (defence in depth: a Redis-dump compromise must NOT yield plaintext keys). 64-char hex suffix; total key length ≤ 75 chars (well under Redis 512 MB key limit). |
| BR-1.6 | Cache ONLY positive validations. Negative results (NOT_FOUND, revoked) MUST NOT be cached — otherwise a transient typo locks out the user for 5 minutes; AND a freshly-revoked key MUST stop working within the existing cache TTL window (max 5 min) without us also having to invalidate negative-cache entries. |
| BR-1.7 | The middleware MUST run BEFORE quota / rate-limit / content-safety middlewares (Stories 5.x / 8.x) — auth comes first; an unauthenticated request never consumes quota. The Story 3.2 wiring places `RequireAPIKey` immediately inside the SecurityHeaders + CSRF chain on the `/v1/chat/completions` route; downstream Stories chain quota/safety wrappers INSIDE `RequireAPIKey`. |
| BR-1.8 | The middleware MUST place `api_key_id` (string UUID), `user_id` (string UUID), `team_id` (string UUID, may be empty), and `scope` (JSON-encoded string, may be `{}`) into `r.Context()` via four package-private context keys + four exported `WithX` / `XFromContext` helpers — same pattern as `jwt_verify.go` (`WithUserID`, `UserIDFromContext`). Downstream Story-3.3+ handlers depend on `APIKeyIDFromContext` + `UserIDFromContext`. |
| BR-1.9 | The middleware MUST NOT mutate the `Authorization` header (no strip, no rewrite) — downstream handlers can re-read it if needed for upstream LLM provider passthrough (out of scope here, but the contract must not foreclose it). |
| BR-1.10 | The placeholder `/v1/chat/completions` handler (this Story only — Story 3.3 supersedes) MUST emit HTTP 501 + `{"error":{"code":"501_not_implemented","message":"Chat completions endpoint not yet implemented.","type":"server_error","param":null,"he_request_id":null}}` so integration tests can assert "middleware passed through to inner handler" without depending on Story-3.3 mock-data behaviour. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `Authorization` header | string | yes | matches `(?i)^Bearer\s+(.+)$`; token portion non-empty | 401 → `401_invalid_api_key` / "Missing or malformed Authorization header." |
| Token format | string | yes | byte-length ∈ [10, 256]; token outside this range = treated as malformed; auth-svc still does the bcrypt compare ONLY if length passes (defence vs accidental DoS from oversized inputs) | 401 → `401_invalid_api_key` / "Invalid API key provided." |

> **Defence-in-depth note (per Architect Round 1 Minor m-1)**: AC1's `[10, 256]` byte-length gate is a generic RFC 6750 DoS defence at the gateway boundary; AC2 BR-2.6's `^he-[A-Za-z0-9]{10,253}$` regex is the format-specific narrowing at the auth-svc layer. The two gates intentionally overlap incompletely — AC1 short-circuits oversized inputs without burning a connectrpc round-trip; AC2 short-circuits non-`he-` payloads without burning bcrypt cost. The lower-bound mismatch (AC1 admits a 10-char non-`he-` token; AC2 rejects it as NOT_FOUND) is by design, not a bug.

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Missing Authorization header | 401 | `Missing or malformed Authorization header.` | Short-circuit at middleware; no RPC |
| Malformed Authorization header (non-Bearer / empty token) | 401 | `Missing or malformed Authorization header.` | Short-circuit at middleware; no RPC |
| Token length out of [10, 256] | 401 | `Invalid API key provided.` | Short-circuit at middleware; no RPC |
| auth-svc returns ok=false / NOT_FOUND | 401 | `Invalid API key provided.` | No SETEX; emit 401; structured log at INFO with `slog.String("key_prefix", first12chars)` (never plaintext) |
| auth-svc returns ok=false / REVOKED | 401 | `Invalid API key provided.` | Same envelope as NOT_FOUND (anti-enumeration: never reveal whether a key was once valid); no SETEX |
| auth-svc connect error (UNAVAILABLE, DEADLINE_EXCEEDED) | 503 | `Authentication service temporarily unavailable.` | Log at WARN; client retries |
| Redis GET error | n/a | n/a | Log at WARN; fall through to RPC path (Redis is a perf optimisation, not a correctness gate); a Redis outage MUST degrade to "every request hits auth-svc" rather than "every request fails" |

**Examples**
- Input: `Authorization: Bearer he-abc123XYZ...` (valid, unrevoked, cache miss) → 501 (placeholder downstream) + cache SETEX `auth:apikey:{sha256}` TTL=300s
- Input: `Authorization: Bearer he-abc123XYZ...` (valid, cache hit) → 501 (placeholder downstream); zero auth-svc RPC; context populated from cached JSON
- Input: `Authorization: bearer he-abc123XYZ...` (lowercase scheme) → identical to canonical-case path (BR-1.1)
- Input: `Authorization: Bearer he-doesnotexist` → 401 + `401_invalid_api_key`; no SETEX
- Input: `Authorization: Bearer he-revoked123...` (matches a row with revoked_at IS NOT NULL) → 401 + `401_invalid_api_key`; no SETEX (anti-enumeration parity with NOT_FOUND)
- Input: no Authorization header → 401 + `401_invalid_api_key` / "Missing or malformed Authorization header."; no RPC
- Input: `Authorization: Basic dXNlcjpwYXNz` → 401 + same envelope as no header

WHEN the gateway-side connectrpc client invokes `AuthService.ValidateApiKey({plaintext_key:'he-KNOWNVALUE...', client_ip:'203.0.113.7', user_agent:'openai-python/1.0'})`
THEN
  - auth-svc SELECTs `id, user_id, team_id, key_hash, scope, revoked_at, monthly_cost_cap_usd` FROM api_keys WHERE key_prefix = $1 (the supplied token's first 12 chars), expecting 0..N rows
  - for each candidate row (in id-sorted order for determinism), bcrypt.CompareHashAndPassword(key_hash, plaintext_key) is invoked; the first match wins (constant-time within the bcrypt primitive)
  - on match AND revoked_at IS NULL: response `{ok:true, api_key_id, user_id, team_id (may be empty string when NULL), scope (JSON string), reason:REASON_UNSPECIFIED}`; auth-svc UPDATEs api_keys.last_used_at=NOW() in a fire-and-forget goroutine (failure here MUST NOT fail the validation — log at DEBUG, swallow)
  - on match AND revoked_at IS NOT NULL: response `{ok:false, reason:REASON_REVOKED}`
  - on zero matches across all candidate rows: response `{ok:false, reason:REASON_NOT_FOUND}`
  - on PG connection error: connectrpc returns `connect.CodeUnavailable` + wrapped error (NOT a gRPC-level `ok=false` — keeps the AUTH error space separate from the INFRA error space, per BR-1.3)
  - all paths emit an OTel span `auth.ValidateApiKey` with attributes `{auth.key_prefix, auth.candidates_count, auth.matched (bool), auth.outcome}` — plaintext key MUST NOT appear in any span attribute, log, or error message (defence in depth — also enforced by repo-level golangci-lint custom rule pending Epic 9, manually code-reviewed for now)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | `key_prefix` is NOT unique (per `data-models.md §4.1` schema — only `idx_api_keys_user_id` and `idx_api_keys_hash` indices; no UNIQUE on `key_prefix`). Collisions are statistically possible (base62 prefix space ≪ 2^256 plaintext space). Lookup MUST iterate ALL matching rows; first-bcrypt-match wins. |
| BR-2.2 | `key_hash` is bcrypt with cost=12, matching `users.password_hash` from Story 2.2. Cost=12 produces ~150-250 ms per compare on a 2 vCPU runner; an attacker bypassing the prefix index would face 150-250 ms per guess — acceptable rate limit + downstream CDN/WAF (Story 8.x) handles wider abuse. |
| BR-2.3 | The bcrypt-compare iteration order MUST be deterministic (ORDER BY id ASC) so multi-candidate behaviour is reproducible in tests. The iteration ceiling is `max_candidates = 100` (hard cap); zero realistic prefix collision count exceeds 1, but the cap defuses a hypothetical DoS where an attacker correlates colliding prefixes. Exceeding the cap → log at ERROR with key_prefix + count, treat as NOT_FOUND for the response (fail closed). |
| BR-2.4 | Anti-enumeration: response shape for `REASON_NOT_FOUND` and `REASON_REVOKED` MUST be byte-identical EXCEPT for the `reason` enum (which is internal-only, used by SRE alerting, never surfaced to the HTTP client per BR-1 in AC1). |
| BR-2.5 | `last_used_at` UPDATE is FIRE-AND-FORGET (separate goroutine using a fresh DB connection from the pool; 1-second timeout; failure logged at DEBUG and dropped). Synchronous UPDATE would add ~5-15 ms per request — unacceptable for the hot path. Stale `last_used_at` is acceptable; the field is observability-only. |
| BR-2.6 | The auth-svc handler MUST validate `plaintext_key` syntactically before any DB lookup: regex `^he-[A-Za-z0-9]{10,253}$` (matches the architecture's `he-` + base62(32 bytes) ≈ 46 chars total format, with slack). Non-matching = immediately return `ok=false, reason=REASON_NOT_FOUND` (no DB query); prevents the bcrypt-DoS-via-oversized-input scenario from AC1 BR data validation. |
| BR-2.7 | `client_ip` + `user_agent` request fields are INFORMATIONAL ONLY in this Story (forwarded for future audit-svc logging when Story 9.x lands). They MUST NOT affect the validate outcome (no IP whitelist enforcement here — that lands in Story 5.x per the `scope.ip_whitelist` JSONB field). |
| BR-2.8 | Test seeding: `apps/auth-svc/internal/apikey/seed_test.go` exposes `IssueKeyForTest(t *testing.T, db *pgx.Conn, userID string) (plaintextKey, apiKeyID string)` — bcrypts cost=4 (NOT 12) for test speed (cost=12 takes 200 ms per call, killing parallel-test throughput). The test helper MUST be in a `_test.go` file so it cannot be linked into the production binary (compile-time enforcement). |

### AC4: Redis Cache Layer — Hit / Miss / Invalidation Semantics

**Scenario**
```gherkin
GIVEN the api-gateway started with HE_API_REDIS_URL=redis://redis:6379/0 (default per Helm chart env)
AND an api_keys row exists with plaintext key 'he-CACHETEST...' issued via IssueKeyForTest
AND the Redis instance is empty (no `auth:apikey:*` keys present at test start)
WHEN the first request `POST /v1/chat/completions` with `Authorization: Bearer he-CACHETEST...` arrives
THEN
  - the middleware computes `cache_key = "auth:apikey:" + hex(sha256("he-CACHETEST..."))`
  - GET cache_key → MISS (nil)
  - the middleware invokes auth-svc.ValidateApiKey → ok=true, {api_key_id, user_id, team_id, scope}
  - the middleware SETs `cache_key` → `JSON({api_key_id, user_id, team_id, scope})` with EX=300 (5 minutes, per security.md §8.2)
  - the middleware proceeds to invoke the inner handler with context populated from the auth-svc response
WHEN a second request with the SAME bearer arrives 30 seconds later
THEN
  - GET cache_key → HIT (returns the cached JSON)
  - the middleware decodes the JSON, populates context, proceeds to inner handler
  - NO auth-svc RPC is issued (assert: place a `httptest` counter on the auth-svc test stub; counter MUST remain at 1 after the second request)
  - the response latency is observably lower (p50 < 5 ms with cache hit vs 20-200 ms with cache miss — informational; not a hard gate in this Story, but a `BenchmarkBearerAuthCacheHit` MUST be authored so future regressions are catchable)
WHEN the operator revokes the key via direct SQL `UPDATE api_keys SET revoked_at = NOW() WHERE id = '...'` (production "revoke key" UX lands in Epic 5; for this Story, we model the revocation as direct SQL)
THEN
  - the cached entry remains live for up to 300 seconds (cache TTL) — this is the documented "revocation lag" trade-off per security.md §8.2 design
  - immediate revocation is OUT OF SCOPE for this Story (would require either a Redis pub/sub channel invalidation OR an auth-svc-emitted Kafka audit.event consumer — both deferred to a future Story)
  - after TTL expires (≥ 300 s), the next request misses cache, calls auth-svc, gets `ok=false, reason=REVOKED`, returns 401 to the client
  - documentation Note (this Story): the api_keys-revoke-immediate semantics are a known gap, tracked as an explicit limitation in `docs/architecture/security.md §8.2` (SM adds a "Revocation Lag Note" sub-section in this Story's T4)
WHEN Redis is unreachable (connection refused, timeout)
THEN
  - the cache GET returns an error; the middleware logs at WARN with `slog.String("error", err.Error())` once per minute (rate-limited via `slog.WithGroup("redis_outage")` + per-key dedup — simple time-bucketed counter, not a sliding window)
  - the middleware FALLS THROUGH to the auth-svc RPC path — degraded but functional
  - on cache SET error after RPC success: log at WARN, continue (do NOT fail the request — Redis is a perf path, not a correctness gate per BR-1 in AC1)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | Cache TTL = 300 seconds (5 minutes) — sourced verbatim from `security.md §8.2`. NOT a configurable env var in this Story (premature configurability; future Story can promote it if SRE asks). |
| BR-4.2 | Cache value MUST be a JSON object (not a binary protobuf) — debuggability via `redis-cli GET auth:apikey:...` is non-negotiable for SRE 2 AM debugging; the marginal serialization cost is invisible vs the bcrypt-compare-saved cost. |
| BR-4.3 | The Redis client MUST be `github.com/redis/go-redis/v9` — same library auth-svc uses from Story 2.2 onwards; pinning to v9 avoids transitive version skew. |
| BR-4.4 | Redis connection params: `MaxRetries=2, DialTimeout=2s, ReadTimeout=1s, WriteTimeout=1s, PoolSize=10, MinIdleConns=2` — modest defaults tuned for the gateway's per-instance request volume (~100 RPS per pod at MVP). Tuning is a Story 9.x concern. |
| BR-4.5 | The cache key SHA-256 hash MUST use Go stdlib `crypto/sha256` (not the bcrypt hash) — sha256 is constant-time-ish enough vs bcrypt's 150-250 ms; we want sub-microsecond key derivation. |
| BR-4.6 | The middleware MUST NOT add an `X-Cache: HIT` / `MISS` response header in this Story — cache observability lives in OTel span attributes (`auth.cache.hit=true/false`), not response headers (avoids leaking timing channels to clients). |
| BR-4.7 | Redis client construction MUST be deferred until the first request that needs it (lazy via `sync.Once`) so a Redis-misconfigured environment does NOT prevent cold-start (Story 3.1 cold-start ≤ 1000 ms gate stays intact). |
| BR-4.8 | The cache layer MUST NOT cache the `client_ip` or `user_agent` request fields — those are per-request informational fields (AC2 BR-2.7); caching them would tie the cache entry to a single client identity and defeat the cache. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| Cache key | string | yes | format `auth:apikey:` + 64-char lowercase hex | n/a (gateway-derived) |
| Cache value | string (JSON) | yes | parseable JSON with keys `api_key_id`, `user_id`, `team_id`, `scope` | If JSON parse fails on read: log at WARN, treat as cache miss, fall through to RPC |
| Cache TTL | int (seconds) | yes | = 300 (BR-4.1) | n/a (constant) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Redis GET error | n/a | Logged at WARN, dedup'd to ≤ 1/minute | Fall through to RPC path |
| Redis SET error (after successful RPC) | n/a | Logged at WARN, no dedup | Return 200 (cache failure is non-fatal) |
| Cache JSON parse error | n/a | Logged at WARN | Treat as cache miss; fall through to RPC; the corrupted key gets overwritten on the next SET |
| Redis fully unreachable | n/a | OTel span attr `auth.cache.error=connection_refused` | Every request hits auth-svc; gateway stays correct, latency degrades |

**Examples**
- Cache MISS path: `GET auth:apikey:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` → nil → call auth-svc → SET with EX=300 → 501 (placeholder inner handler) — 1 RPC, 1 SET
- Cache HIT path: `GET auth:apikey:e3b0c4...` → JSON value → decode → 501 (placeholder inner handler) — 0 RPC, 0 SET
- Revocation lag path: revoke at t=0, request at t=10s → cache HIT, 501 (stale-valid behaviour); request at t=305s → cache MISS, RPC returns ok=false → 401 to client
- Redis outage path: 5 consecutive requests with Redis down → 5 RPC calls, 0 SET; gateway logs 1 WARN (deduplicated)

### Database Design

**Why a SEPARATE `api_keys` table instead of extending `users`?**
- A user can hold N keys (Pro plan default = 5 keys; Team plan = unlimited per Epic 5 PRD).
- Per-key scope (`scope.models`, `scope.ip_whitelist`) requires the row-per-key granularity.
- Per-key revocation (`revoked_at`) is independent of user account status (`users.status`).
- Per-key cost cap (`monthly_cost_cap_usd`) is also per-row.

**Why `key_prefix` indexed but NOT unique?**
- Lookup-by-prefix lets us avoid bcrypt-comparing every row in the table (which would be O(N) per request) — the prefix index is O(log N) selection of candidate rows.
- Uniqueness is statistically near-guaranteed (base62^12 ≈ 3.2 × 10^21 collision space) but NOT enforced — the bcrypt-compare iteration (AC2 BR-2.1) handles the multi-candidate case correctly with deterministic ORDER BY id ASC.

**Why bcrypt cost=12 for `key_hash` (matching `users.password_hash`)?**
- Same threat model: an attacker exfiltrating the DB faces ≥ 150 ms per guess attempt.
- Operational symmetry with password hashing simplifies key rotation tooling (single bcrypt cost knob).
- Cost=12 produces ~250 ms per Validate call on the 2 vCPU runner — this is why the Redis cache (300s TTL) exists: the hot path MUST avoid bcrypt on every request.

**Why `scope` as JSONB (not normalized into `api_key_scopes` join table)?**
- `scope` is read-only-ish (set at key issuance, rarely mutated) and tiny (typical payload < 200 bytes).
- JSONB queries (`scope @> '{"models":["qwen-max"]}'`) outperform a 4-way join for the gateway hot path.
- Future flexibility: adding a new scope dimension (e.g., `scope.regions`, `scope.max_qps_override`) requires no schema change.

service AuthService {
  // ... existing 14 RPCs ...

  // Story 3.2 — API Key validation for the api-gateway Bearer-auth middleware.
  // Called per request on cache miss; bcrypt-compares the supplied plaintext
  // against api_keys rows matching the 12-char key_prefix. Returns ok=true with
  // identity + scope on match; ok=false with REASON for not-found / revoked.

  // AC2 BR-2.6 / BR-2.10 + docs/architecture/coding-standards.md §12.3.
  rpc ValidateApiKey(ValidateApiKeyRequest) returns (ValidateApiKeyResponse);
}

message ValidateApiKeyRequest {
  // The full plaintext bearer token (e.g., 'he-abc123XYZ...'). auth-svc applies
  // syntactic regex BEFORE any DB query (AC2 BR-2.6).
  string plaintext_key = 1;
  // Client-attribution metadata. Informational only in 3.2 (BR-2.7) — forwarded
  // for future audit-svc logging when Story 9.x lands.
  string client_ip = 2;
  string user_agent = 3;
}

message ValidateApiKeyResponse {
  bool ok = 1;
  // Populated when ok=true.
  string api_key_id = 2;     // UUID of the matched api_keys row
  string user_id = 3;        // UUID; the key's owner
  string team_id = 4;        // UUID or empty string when api_keys.team_id IS NULL
  string scope = 5;          // JSON-encoded string of api_keys.scope JSONB column
  // Populated for SRE alerting + downstream metric attribution.
  // NEVER surfaced to the HTTP client (gateway maps ALL ok=false to 401 per
  // AC1 + AC2 BR-2.4 anti-enumeration).
  ApiKeyValidationReason reason = 6;
}

enum ApiKeyValidationReason {
  API_KEY_VALIDATION_REASON_UNSPECIFIED = 0;  // ok=true path
  API_KEY_VALIDATION_REASON_NOT_FOUND = 1;    // no matching prefix / no bcrypt match / regex reject
  API_KEY_VALIDATION_REASON_REVOKED = 2;      // match found but revoked_at IS NOT NULL
}

### Open Questions for Architect (Round 1)

1. **Cache-key derivation choice**: Story uses `sha256(plaintext_key)` for the Redis cache key (BR-1.5). An alternative is `sha256(key_hash)` (the bcrypt hash) — this would let the cache survive a key-rotation event where the plaintext changes but the underlying api_keys.id stays. SM chose plaintext-sha256 for simplicity (no extra DB lookup to map plaintext → key_hash before cache GET); Architect MAY override to key_hash-sha256 if the future "rotate plaintext, keep ID" UX is on the roadmap. Default = plaintext-sha256.

2. **Negative-cache exclusion**: BR-1.6 says positives-only cache. An attacker probing with random tokens incurs bcrypt cost on every miss (no cache absorption). The mitigation is the regex pre-filter (BR-2.6) which short-circuits ~99% of garbage inputs BEFORE bcrypt. SM judges this acceptable; Architect MAY require a bounded negative cache (e.g., 30s TTL, 10K-entry LRU) if the threat model expects sustained probing.

3. **`stripBearer` helper duplication vs promotion**: `jwt_verify.go:233` exports `stripBearer` package-private. Story 3.2's `bearer_auth.go` also needs it. SM recommends Dev inline a small copy rather than refactoring the JWT path (no behaviour change to existing code). Architect MAY require promoting to exported `middleware.StripBearer` for DRYness.

4. **`teams` FK temporal deferral**: BR-3.1 drops `REFERENCES teams(id)` from the architecture-spec schema because the `teams` table doesn't exist yet. SM annotates this in the data-models.md Change Log (T6.3). Architect SHOULD confirm the right Epic for landing `teams` (Epic 5 "key/quota/ratelimit" OR Epic 7 "billing/payment" — both touch teams) so the follow-up `ALTER TABLE api_keys ADD CONSTRAINT` ticket has a home.

5. **Revocation-lag acceptance**: AC4 documents the 5-min revocation lag as a known limitation (cache TTL bounded). For an MVP this is acceptable; for SOC-2 / enterprise customers it may not be. SM defers the immediate-revocation work (Redis pub/sub OR Kafka audit.event consumer) to a future Story but does NOT name it explicitly — Architect SHOULD confirm whether to spawn a tracked follow-up Story now or wait for customer feedback.

6. **Placeholder `/v1/chat/completions` 501 handler**: Story 3.2 owns the placeholder; Story 3.3 supersedes with real logic. The placeholder lives in `apps/api-gateway/cmd/server/main.go` inline (small enough) OR in `apps/api-gateway/internal/handlers/chat_placeholder.go`. SM recommends INLINE in main.go with a `TODO(story-3.3)` comment for minimal blast radius; Dev may relocate if it grows. Architect MAY mandate the handlers/ directory location for consistency.

### Implementation Summary

Story 3.2 delivers the Bearer-token API-key authentication path on `POST /v1/chat/completions`. The gateway middleware (`apps/api-gateway/internal/middleware/bearer_auth.go`) extracts the `Authorization: Bearer <token>` header via the newly-promoted exported `middleware.StripBearer` helper (RFC 6750 §2.1 case-insensitive), computes a `auth:apikey:<sha256_hex(plaintext)>` cache key, attempts a Redis GET, and on miss invokes the new `he.auth.v1.AuthService.ValidateApiKey` RPC. The auth-svc handler (`apps/auth-svc/internal/apikey/validate.go`) applies a regex pre-filter (`^he-[A-Za-z0-9]{10,253}$`) before any DB query (BR-2.6), bcrypt-compares the plaintext against rows that share the 12-char `key_prefix` in id-ascending order (BR-2.1 / BR-2.3), fires a goroutine to UPDATE `last_used_at` (BR-2.5 fire-and-forget), and emits an `auth.ValidateApiKey` OTel span with `{auth.key_prefix, auth.candidates_count, auth.matched, auth.outcome}` attributes — plaintext is NEVER referenced in span attributes, log fields, or returned errors (TC-9 / BR-2.10).

A new Atlas migration `migrations/postgres/0006_create_api_keys.sql` lands the `he_api.api_keys` table — schema-qualified, forward-only DDL per the M2 ruling and the `atlas migrate down 1` dynamic-rollback contract; `team_id` is nullable with NO FK constraint (Epic 5 lands the `→ he_api.teams(id)` ALTER per the OQ4 follow-up marker recorded in `data-models.md §4.5 Change Log`).
