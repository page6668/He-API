## Epic Context
**Epic**: 4 - 6 家中国大模型适配器
**Goal**: 实现 6 家中国主流 LLM 的 plugin 适配器，规范化为 OpenAI 协议；并验证流式/非流式/token 用量准确透传

**Story Deliverables**:
- New K8s service `apps/adapters/deepseek/` — Go Connect-RPC server implementing `he.adapter.v1.AdapterService/Chat` (server-streaming RPC). First real adapter; sets the template Stories 4.2-4.6 inherit.
- New proto module `packages/proto/he/adapter/v1/adapter.proto` — `AdapterService.Chat(ChatRequest) returns (stream ChatChunk)` (the `rest-api-spec.md §5.2 ModelAdapterService` sketch promoted to a concrete Buf-managed proto under the architecture-ratified `he/<domain>/v1/<service>.proto` layout).
- Upstream HTTPS client against `https://api.deepseek.com/v1/chat/completions` (DeepSeek's API is OpenAI-protocol-native; the adapter is primarily a wire-shape pass-through + token-usage normaliser).
- Gateway↔adapter wiring in `apps/api-gateway/`: a model-id → adapter-endpoint resolver (in-process map for Story 4.1; routing-svc handles strategy in Epic 6) + a Connect-RPC client invoked from `ChatCompletionsHandler` when `req.Model == "deepseek-v3"`. Replaces the Story-3.3 / 3.4 mock for that specific model id ONLY (other model ids continue to return the mock until Stories 4.2-4.6 land).
- BOTH paths exercised end-to-end:
  - non-streaming: api-gateway returns OpenAI `chat.completion` JSON with upstream-reported `usage.{prompt_tokens, completion_tokens, total_tokens}` (BR-3.x — `< 1%` delta from DeepSeek's reported counts per Epic DoD line 2).
  - streaming: api-gateway forwards adapter chunks via SSE per `rest-api-spec.md §5.1.1.1`; the terminal chunk carries `usage` (DeepSeek's `stream_options.include_usage=true` convention).
- Token-usage tap (BR-3.x): the adapter MUST capture `usage` from upstream and thread it into the gRPC tail-chunk (streaming) or terminal response (non-streaming); the gateway MUST surface it verbatim on the wire.
- Test surface: unit (proto serialisation invariants + token-usage normalisation pure functions) + integration (Toxiproxy fault injection: upstream 5xx, slow loris, mid-stream RST) + contract (OpenAI Python SDK `client.chat.completions.create(model="deepseek-v3", stream=False/True)`) + end-to-end (real `api.deepseek.com` exercise guarded by `HE_API_DEEPSEEK_LIVE=1` opt-in env var so CI does not consume vendor quota on every PR).
- Helm chart `infra/helm/adapter-deepseek/` + `apps/adapters/deepseek/Dockerfile` + ArgoCD app definition (`infra/argocd/applications/adapter-deepseek.yaml`).
- DeepSeek API key wiring via Vault per ADR-? (see OQ3 in Dev Notes / Open Questions for Architect).

### AC2: Streaming `/v1/chat/completions` via DeepSeek adapter (SSE forward chain)

**Scenario**
```gherkin
GIVEN the same setup as AC1 (gateway built, adapter deployed, registry mapping deepseek-v3, valid bearer key, DeepSeek upstream reachable)
AND DeepSeek upstream's `https://api.deepseek.com/v1/chat/completions` endpoint accepts `stream=true` in the request body and responds with `text/event-stream` (DeepSeek follows OpenAI's SSE shape verbatim — `data: <json>\n\n` framing + `data: [DONE]\n\n` terminator + `stream_options.include_usage=true` opt-in for the tail-usage chunk)
WHEN the test issues a `POST /v1/chat/completions` request with `stream=true` in the body: `{"model":"deepseek-v3","messages":[{"role":"user","content":"Tell me a haiku."}],"stream":true,"stream_options":{"include_usage":true}}`
THEN
  - the response status is 200 OK
  - the response headers conform to `rest-api-spec.md §5.1.1.1`: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `Connection: keep-alive`, `X-Accel-Buffering: no`, `X-He-Request-Id: req_<12 hex>`, `X-He-Selected-Model: deepseek-v3` (the Story-3.4 streaming-writer discipline is preserved; the adapter does NOT set the response headers — the gateway does, then forwards adapter chunks into the streaming writer)
  - the SSE stream emits N ≥ 2 chunks of shape `data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":<int>,"model":"deepseek-v3","choices":[{"index":0,"delta":{...},"finish_reason":null|"stop"|"length"|"tool_calls"|"content_filter"}]}` followed by a tail chunk of shape `data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":<int>,"model":"deepseek-v3","choices":[],"usage":{"prompt_tokens":<int>,"completion_tokens":<int>,"total_tokens":<int>}}` followed by the literal `data: [DONE]\n\n` terminator (`stream_options.include_usage=true` per OpenAI SDK convention surfaces the tail-usage chunk BEFORE `[DONE]`)
  - the SDK call `for chunk in client.chat.completions.create(model="deepseek-v3", messages=[...], stream=True, stream_options={"include_usage": True}): ...` iterates without raising `openai.APIError`; the loop's final non-DONE iteration's `chunk.usage` is non-None with `prompt_tokens`/`completion_tokens`/`total_tokens` all positive integers
  - the response's first byte arrives within `TTFB_BUDGET_MS = 500` (informal regression marker, BR-2.7 — NOT an AC failure if exceeded; QA captures p95)
WHEN the adapter is invoked with `stream=true` and upstream succeeds
THEN
  - the adapter's outbound HTTPS request to DeepSeek MUST set `Accept: text/event-stream` AND include `stream:true` + `stream_options:{include_usage:true}` in the request body
  - the adapter's response chunks are emitted via Connect-RPC server-streaming (`stream.Send(&adapterv1.ChatChunk{...})`); the LAST chunk carries `usage` (terminal-chunk convention — BR-2.4)
  - the gateway's streaming-writer forwards each adapter chunk as a single `data: <json>\n\n` SSE event WITHOUT re-buffering or coalescing (the chunk-level forward MUST be 1:1)
WHEN upstream returns 5xx BEFORE the first SSE frame is emitted
THEN
  - the response status is 502 Bad Gateway with the §5.1.2 JSON envelope (the gateway has not yet committed to streaming mode — it MUST emit a JSON error, NOT an SSE error frame; BR-2.5 emit-before-flush boundary)
WHEN upstream returns 5xx OR a mid-stream RST AFTER the first SSE frame has been emitted
THEN
  - the gateway emits a terminal SSE error frame: `data: {"error":{"code":"502_upstream_unavailable","message":"Upstream model service interruption during streaming.","type":"server_error","param":null,"he_request_id":"req_<12 hex>"}}\n\n` followed by `data: [DONE]\n\n` (BR-2.6 — replay is impossible mid-stream; we surface the failure via the SSE channel)
  - the structured log emits `event=adapter_chat_stream_interrupted` with `chunks_emitted_before_failure=<int>` + `error.code=502_upstream_unavailable`
WHEN the client disconnects mid-stream (request context cancelled)
THEN
  - the adapter's outbound HTTPS connection is cancelled within 200ms (`req.Context()` propagated to `http.NewRequestWithContext`)
  - the adapter emits a structured log `event=adapter_chat_stream_client_disconnect` with `chunks_emitted=<int>` + `client_disconnect=true`
  - the gateway emits a structured log `event=chat_completions_stream` with `client_disconnected=true` (Story 3.4 BR-3.4 invariant preserved)
```

### AC3: Token-usage accuracy — adapter-reported `usage` matches upstream-reported `usage` within < 1% delta

**Scenario**
```gherkin
GIVEN the same setup as AC1 + AC2 (gateway built, adapter deployed, registry mapping deepseek-v3, valid bearer key, DeepSeek upstream reachable — live or mocked)
AND a fixture set of ~20 prompt-response pairs spanning: English short (1-token completion), English long (256+ token completion), Chinese short, Chinese long, code-block continuation, JSON-structured-output, empty-string continuation, max-tokens-bounded (max_tokens=10), max-tokens-bounded (max_tokens=4096), system+user multi-turn, tool-call-response, content-filter-triggered, stop-sequence-truncated
WHEN the test exercises BOTH `stream=false` and `stream=true` paths against each fixture
THEN
  - for each fixture, the adapter-reported `usage.prompt_tokens` matches the upstream-reported value with `abs(delta) / upstream_value < 0.01` (< 1%, per Epic 4 DoD line 2: "Token 用量准确（与上游官方计量误差 < 1%）")
  - for each fixture, the adapter-reported `usage.completion_tokens` matches the upstream value with `< 1%` delta
  - for each fixture, `usage.total_tokens == usage.prompt_tokens + usage.completion_tokens` (exact equality — NO derived-field drift)
  - the SDK-surfaced `chunk.usage.{prompt_tokens, completion_tokens, total_tokens}` on the streaming path's tail chunk equals the adapter-reported values byte-for-byte
WHEN upstream returns a response WITHOUT `usage` field (DeepSeek failure mode)
THEN
  - the adapter MUST surface this as Connect-RPC `Code.Unavailable` with metadata `validation_failure=missing_usage` (BR-3.4)
  - the gateway returns 502 (BR-1.4 mapping) — AC3 treats missing-usage as a HARD failure, NOT a degraded-mode pass
WHEN upstream returns a response with `usage.completion_tokens=0` but `choices[0].finish_reason ∈ {"stop","length"}` AND `choices[0].message.content` is non-empty
THEN
  - this is a vendor-side bug (zero tokens for non-empty content); the adapter MUST log `event=adapter_chat_response_invalid` with `validation_failure=zero_completion_tokens_with_content` AND still forward the upstream values verbatim (DO NOT re-tokenise to "fix" the count — re-tokenisation introduces our own tokeniser as a source of drift; AC3 trusts upstream's count as the oracle)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | Token-usage authority: **upstream is the oracle**. The adapter MUST NOT re-tokenise the request or response to "verify" or "correct" the upstream count. Reason: re-tokenisation requires us to embed a vendor-specific tokeniser (DeepSeek uses a custom BPE variant; the tokeniser library distribution + version-pinning + correctness verification cost exceeds the < 1% accuracy delta we'd gain). Trusting upstream's `usage` aligns with how OpenAI / Anthropic / Google clients work — the API call's own response IS the billing oracle. |
| BR-3.2 | Adapter `usage.Normaliser` interface (`apps/adapters/deepseek/internal/usage/normaliser.go`): `Normalise(raw RawUsage) (NormalisedUsage, error)`. For DeepSeek, the implementation is identity-mapping (DeepSeek's `usage` JSON shape == OpenAI's `usage` JSON shape). Stories 4.2-4.6 supply non-identity normalisers for vendors whose `usage` JSON shape differs (e.g., Qwen uses `input_tokens` / `output_tokens` — the Qwen Normaliser maps these to `prompt_tokens` / `completion_tokens`). The interface is the seam Stories 4.2-4.6 inherit. |
| BR-3.3 | `usage` field-presence contract: `prompt_tokens` MUST be a positive integer; `completion_tokens` MUST be a non-negative integer; `total_tokens` MUST equal `prompt_tokens + completion_tokens` (exact). If any of these constraints fail, `Normalise` returns an error; the adapter surfaces Connect-RPC `Code.Unavailable` with `validation_failure=usage_constraint_violation`. |
| BR-3.4 | Missing-usage handling: if upstream's response (non-streaming) or terminal SSE chunk (streaming) omits the `usage` object entirely, the adapter MUST treat this as a HARD failure (Connect-RPC `Code.Unavailable` + `validation_failure=missing_usage`). Reason: billing-svc (Epic 7) and quota-svc (Epic 5) consume `usage` synchronously via the `usage.recorded` Kafka topic; a missing-usage response would either crash billing (NPE) or silently drop the billing event. Better to surface the failure now as 502 than to ship a half-billed call. |
| BR-3.5 | Cost calculation is OUT OF SCOPE for Story 4.1 (OQ5 — SM lean: adapter reports usage only; billing-svc computes cost). The adapter's `NormalisedUsage` carries `prompt_tokens` + `completion_tokens` + `total_tokens` ONLY; `cost_usd` is NEVER populated by the adapter. ### Open Questions for Architect

Status: All seven OQ1–OQ7 were DEFERRED to Architect Round 2 per Recommendation 3 of the Round 1 review ("Defer OQ1–OQ7 rulings to next Architect round … those rulings belong to a substantive Round 1 review, which cannot start until the Story body exists"). Architect Round 2 ratifies these BEFORE Stories 4.2-4.6 inherit the contract. SM's leans are restated below for ease-of-review:

1. **OQ1 — Proto package name**: `he.adapter.v1` (Story-1.5 `he/<domain>/v1/` domain-based layout, matches the gateway↔adapter contract semantics) vs `he.model.v1` (matches the `models` table colloquial name). **SM lean**: `he.adapter.v1` — the proto describes the gateway↔adapter contract, NOT model metadata; model metadata is a `models` table concern that belongs to Story 4.7. **Architect should rule.**

2. **OQ2 — Connect-RPC vs gRPC-over-HTTP/2 for the gateway↔adapter call**: Story 1.5 ratified connect-go for ALL internal services per `coding-standards.md §12.1`. Server-streaming over Connect-RPC has documented buffer-flush quirks vs grpc-go's native `http2.Framer` access (see `connectrpc/connect#XXX` upstream issue tracker; Story 1.5 reference impl uses connect-go for unary RPCs only). **SM lean**: Connect-RPC (consistency with the project-wide ratification); fall back to grpc-go only if Architect Round 2 surfaces a concrete buffer-flush blocker during Toxiproxy chaos testing (T4.3). **Architect should rule.**

3. **OQ3 — Vault secret-engine path for upstream DeepSeek API key**: `kv/data/he-api/adapters/deepseek/` (groups secrets per service) vs `kv/data/he-api/upstream/deepseek/` (groups all six vendor keys under one `upstream/` prefix so the Vault policy scopes Epic 4 broadly). **SM lean**: `kv/data/he-api/upstream/deepseek/` — Epic 4's six vendor keys are operationally a unit (operator rotates them together when DeepSeek/Qwen/Kimi/GLM/Doubao/Ernie support contracts renew); the `upstream/` prefix lets a single Vault policy + a single External Secrets Operator ClusterSecretStore cover them all. **Rotation**: manual (DeepSeek does NOT support API-key auto-rotation; Vault dynamic-secret is N/A). **Architect should rule.**

4. **OQ4 — Adapter-registry resolution policy**: (a) in-process `map[string]string` (model-id → adapter-grpc-host) loaded from env vars at startup; (b) K8s `Service` DNS resolution (`adapter-deepseek.adapters.svc.cluster.local:8080`) + an in-process model-id → service-name map; (c) routing-svc gRPC call (defers actual routing to Epic 6 smart-routing). **SM lean**: option (b) — in-process model-id → service-name map (no routing-svc dep yet) + K8s DNS resolution for the service-name → endpoint hop. routing-svc is the obvious seam Story 4.7 / Epic 6 will graft onto; Story 4.1 makes the seam explicit by isolating it in `apps/api-gateway/internal/adapterclient/registry.go`. **Architect should rule on the exact seam shape so Stories 4.2-4.6 inherit the same structure.**

5. **OQ5 — Cost calculation responsibility**: (a) adapter computes `(token × upstream-price × (1 + markup))` and reports a `cost_usd` field; (b) adapter reports `usage` only and billing-svc computes cost. **SM lean**: (b) — single responsibility (adapter knows tokens, billing-svc knows pricing tables); confirmed alignment with `data-models.md §4.1 model_pricing` ownership. Story 4.1's adapter NEVER emits `cost_usd`; the gateway's `X-He-Cost-Usd` header stays unset until Epic 7 billing-svc integration. **Architect should rule.**

6. **OQ6 — Upstream SSE decoder strictness**: (a) bufio.Scanner with custom `SplitFunc` tolerant of `data:` vs `data: ` whitespace AND `\n\n` vs `\r\n\r\n` vs `\n` terminators; (b) strict-RFC-conforming (`data: <json>\n\n` ONLY, error on deviation). **SM lean**: (b) strict-RFC with a documented fallback path for upstream-vendor-specific quirks Stories 4.2-4.6 may need (BR-2.8 — silent coercion masks vendor protocol drift). DeepSeek's framing matches OpenAI's spec exactly per draft-time `curl` exploration; strict-RFC is safe for Story 4.1. **Architect should rule on the policy so Stories 4.2-4.6 inherit the same strictness.**

7. **OQ7 — HTTP/2 to upstream**: (a) force HTTP/2 via `golang.org/x/net/http2` (DeepSeek confirms HTTP/2 support); (b) let `http.DefaultTransport`'s TLS-NPN negotiate (typically yields HTTP/2 anyway for HTTPS endpoints). **SM lean**: (a) force HTTP/2 explicitly so the wire-protocol decision is in-code-and-test-coverage, NOT incidental. The streaming path's connection-multiplexing benefits from explicit HTTP/2 + the `H2C-style` test fakes are cleaner. **Architect should rule.**

8. **OQ8** (new — surfaced by BR-1.5 authoring): **`requestid.FromContext` accessor sharing across services**: The adapter needs `requestid.FromContext(ctx) (string, bool)` to extract the `he_request_id` for log-tagging. Options: (a) adapter imports `github.com/he-api/he-api/apps/api-gateway/internal/middleware/requestid` directly (cross-service internal-import — Go convention typically frowns on this); (b) lift the extractor into `packages/go-observability/requestid` so both gateway + adapter import the shared package; (c) duplicate the extractor in `apps/adapters/deepseek/internal/requestid/` (DRY violation). **SM lean**: (b) — lift to `packages/go-observability/requestid` so all Epic 2-10 Go services share one accessor. Story 4.1 lands the move; Story 3.6 follow-up cleanup migrates the gateway's existing import to the shared package. **Architect should rule.**

```proto
syntax = "proto3";
package he.adapter.v1;

option go_package = "github.com/he-api/he-api/packages/proto/gen/go/he/adapter/v1;adapterv1";

service AdapterService {
  rpc Chat(ChatRequest) returns (stream ChatChunk);
}

message ChatRequest {
  string model = 1;
  repeated ChatMessage messages = 2;
  bool stream = 3;
  optional double temperature = 4;
  optional int32 max_tokens = 5;
  bytes tools_json = 6;             // passthrough — adapter forwards verbatim, JSON-encoded
  bytes tool_choice_json = 7;       // passthrough
  bytes response_format_json = 8;   // passthrough
  string he_request_id = 9;         // propagated from gateway; BR-1.5
  // Stream-only knobs:
  bool stream_include_usage = 10;   // BR-2.9 — adapter forces true on stream=true
}

message ChatMessage {
  string role = 1;     // "system" | "user" | "assistant" | "tool"
  string content = 2;
}

message ChatChunk {
  string id = 1;                    // "chatcmpl-<adapter-suffix>"
  string object = 2;                // "chat.completion" (non-streaming terminal) | "chat.completion.chunk" (streaming)
  int64 created = 3;                // Unix seconds
  string model = 4;                 // "deepseek-v3"
  repeated Choice choices = 5;
  optional Usage usage = 6;         // BR-2.4 — terminal chunk only
  optional string finish_reason = 7; // mirrored on terminal chunk for non-streaming convenience
}

message Choice {
  int32 index = 1;
  Delta delta = 2;                  // streaming chunks use delta; non-streaming terminal collapses message into delta
  optional string finish_reason = 3;
}

message Delta {
  optional string role = 1;
  optional string content = 2;
}

message Usage {
  int32 prompt_tokens = 1;
  int32 completion_tokens = 2;
  int32 total_tokens = 3;
}
```

- **OQ1 — Proto package name → `he.adapter.v1`** (SM lean confirmed).
  Rationale: `source-tree.md §6` ratifies the layout `packages/proto/he/<domain>/v1/<service>.proto` (Story 1.5 Architect Q4 ruling, 2026-05-11). - **OQ2 — Connect-RPC vs gRPC-over-HTTP/2 → Connect-RPC** (SM lean confirmed; binding).
  Rationale: `coding-standards.md §12.1` carries an unambiguous mandate: "**gRPC**: 全部用 connect-go". Connect-go supports server-streaming via `connect.ServerStreamForClient[T]` (Story 4.1 Dev Notes line 696 already references the correct API). The "buffer-flush quirks vs grpc-go's http2.Framer" concern is **not a known blocker** for OpenAI-protocol-shaped SSE traffic (chunk sizes < 4 KiB, no backpressure scenarios — DeepSeek's SSE framing is small-frame friendly). If T4.3 Toxiproxy chaos testing surfaces a concrete buffer-flush regression, that becomes a new architecture decision (raise as ADR-2.1 candidate) — do NOT silently switch to grpc-go mid-implementation.
