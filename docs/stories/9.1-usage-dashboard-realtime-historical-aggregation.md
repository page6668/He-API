### ClickHouse Design Notes (WHY, not full SQL — §4.2 is the SoT)

- **request_logs (MergeTree)** is the raw per-request store; the realtime "今日" read hits it directly (Q-RT — the MV lags on async merge so it is wrong for "real-time"). 90-day TTL = the durable SoT feeding 9.3 download.
- **request_logs_hourly_agg (SummingMergeTree MV)** pre-aggregates per (user_id, model, hour); month/quarter reads hit it (cheap over wide windows). SummingMergeTree merges async → counts are eventually-correct; the dashboard tolerates this.
- **success_rate** = `countIf(status_code < 400) / count()` — REQUIRES failed-request rows in request_logs (BR-ING-2). The hourly_agg as defined in §4.2 sums `request_count` but does NOT carry a success/error split. **Architect Q-AGG RULING (H-2)**: **ADD `success_count UInt64 = countIf(status_code < 400)` to the MV** — a count is sum-compatible, so SummingMergeTree merges it correctly, and month/quarter success_rate = `sum(success_count)/sum(request_count)` is computable cheaply from the MV (today reads request_logs directly). Small additive §4.2 amendment (§4.5 Change Log row).
- **avg/p95 latency columns are DROPPED from the 9.1 MV (H-2 — pre-existing §4.2 defect corrected).** `avg(latency_ms_total)` and `quantile(0.95)(...)` stored as plain columns are **summed** on SummingMergeTree background merge → statistical garbage (cannot average averages or sum quantiles). 9.1's AC consumes no latency aggregate, so the realized MV omits them. A future latency story may re-introduce them as `AggregateFunction` state (`avgState()`/`quantileState(0.95)()`, read with `-Merge`). Recorded as a §4.2 correction in the §4.5 Change Log. Do NOT ship the verbatim avg/quantile SummingMergeTree.
- **Dedup (Q-DEDUP)**: §4.2 says MergeTree (no dedup). At-least-once Kafka → possible dup rows. SM default: tolerate for the approximate dashboard; exact dedup is 9.3's concern. ReplacingMergeTree(ts) keyed by he_request_id is the clean fix but changes §4.2 — Architect rules.
- **Timezone (Q-TZ)**: ts stored UTC (DateTime64). Period boundaries in users.timezone → the query computes the boundary timestamp server-side (Go `time.LoadLocation(user.timezone)`) and passes UTC bounds to ClickHouse. Whole-hour-aligned tz works cleanly with the UTC-hour MV buckets; sub-hour offsets (rare) approximate at the hour boundary — acceptable, or UTC-only MVP cut. **The SAME computed bounds are reused for the PG `usage_ledger` 消费 SUM (one bounds computation, two stores, identical windows — R2-1).**
- **消费 (cost) source — PG `usage_ledger`, NOT ClickHouse (H-1-R, supersedes H-1)**: money has exactly ONE SoT. Per-request cost is computed once by billing-svc (HALF-UP, from `usage.recorded`) and persisted in PG `he_api.usage_ledger` (`cost_usd NUMERIC(12,4) NOT NULL`); `billing_read.go` already runs `SELECT SUM(cost_usd) … WHERE user_id=$1 AND ts >= <window>`. The dashboard 消费 **reads that SUM** (IDOR-fenced, gateway `pgxpool`, R2-6) — it does NOT recompute a second number. The gateway has NO USD pricing on the hot path (`chat_completions_ab.go` — "no USD pricing"; `X-He-Cost-Usd` ABSENT per ratified OQ5), so `request_logs.cost_usd` is non-authoritative (always 0; reserved for the 9.3 raw-row download). **Per-metric SoT split**: 请求数/成功率/Token ← ClickHouse (these REQUIRE the failed-request rows only the 9.1 pipeline carries); 消费 ← PG `usage_ledger`. No single number is sourced from two stores → zero PG↔CH skew; the two reads degrade independently (R2-4). **Staleness**: 消费 reflects billed-to-date and lags by the billing-pipeline interval (`usage.recorded`→billing-svc→`usage_ledger`) — coarser than the ≤~10s volume-metric SLA (R2-5). `[→ apps/api-gateway/internal/.../billing_read.go] [→ data-models.md §4.x usage_ledger]`

- **H-1 — Q-COST dual-store read is an anti-pattern; OVERRULE the `usage_ledger` fallback** (BR-ING-8, BR-RD-... , AC2/AC3, Q-COST):

### The ruling (H-1-R) — supersedes H-1

**Governing principle (non-negotiable): money has exactly ONE source of truth.** Per-request cost is computed once by billing-svc and persisted in `usage_ledger`. A dashboard must **read** that number — never recompute a second, parallel one that can disagree with the user's invoice.

I evaluated QA's three options:

- **(a) Add a gateway cost-computation seam** (mirror the 6.2 `pricing.Provider` snapshot) → **REJECTED.** It manufactures a *second* cost number on the hot path that can drift from the billed `usage_ledger` SoT (different rounding, snapshot staleness) → "why doesn't my dashboard match my invoice" support tickets. It also duplicates billing-svc's pricing logic and expands the largest story in the backlog. Recomputing money you already have authoritatively is the worse anti-pattern.
- **(b) Ship $0 消费 for 9.1, fast-follow** → **REJECTED.** 消费 is one of the four metrics the *literal* Epic-9 AC names. Shipping a permanently-$0 card when an exact SoT is already queryable is a visible product defect, not an honest MVP cut.
- **(c) Read 消费 from PG `usage_ledger`** → **ADOPTED.** This is what H-1 wrongly overruled. The billed money SoT already exists, is per-user, is time-stamped, and is already aggregated by `billing_read.go`.

**My Round-1 concern about (c) — "a dashboard shouldn't read two stores" — was right in spirit but I mis-applied it.** The skew failure mode I feared only arises when a *single number* is sourced from two stores. Here each metric has exactly one SoT:

> **ClickHouse `request_logs` / `request_logs_hourly_agg`** → 请求数 / 成功率 / Token (the volume metrics — these REQUIRE the failed-request rows that only the 9.1 ingestion pipeline carries; this is why the pipeline exists at all).
> **PG `usage_ledger`** → 消费 (the billed money number — the OLTP money SoT).

This is the textbook **OLAP-for-analytics + OLTP-for-money** separation, not a fragile cross-read. The two reads **degrade independently**: if PG is unavailable the 消费 cell renders `"—"` (cost unavailable) while the CH-sourced cells still render; if CH is unavailable the volume cells return `503_clickhouse_unavailable` (AC2 unchanged) while 消费 can still render. No single number is ever sourced from two stores, so there is **zero PG↔CH skew** on any value.

**OQ5 is preserved** — H-1-R changes nothing on the client-facing response; `X-He-Cost-Usd` stays ABSENT. **billing-svc and `usage_ledger` are untouched** (read-only). **No new infrastructure** — the SUM query already exists.
