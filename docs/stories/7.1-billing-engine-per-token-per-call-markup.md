## Architect Open Questions (gathered for Architect Round 1)

- **Q-PRODUCER — who emits `usage.recorded`?** service-topology §3.2 line 42 literally reads "billing-svc 写入 Kafka topic `usage.recorded`", but the gateway is the only component holding the per-request token counts + he_request_id + selected_model at response time. SM default: **the api-gateway is the PRODUCER** (emits after each successful completion); billing-svc is the CONSUMER (per data-models §4.4 which lists billing-svc/audit-svc/analytics-svc as *consumers*). SM reads the topology line as a documentation imprecision and proposes correcting it. Architect ratifies the producer + the doc fix.
- **Q-GATE — sync pre-flight 402 gate IN vs deferred?** SM default: **IN** — a fast Redis-read `402_balance_insufficient` gate on the chat hot path (reject when `balance:user:{id}:realtime` ≤ 0 before upstream dispatch), fail-OPEN on Redis outage. The `BillingService.CheckBalance` gRPC (PG-authoritative) exists for console/reconciliation callers. Architect alternative: defer ALL balance enforcement to Story 7.8 (tiers/Beta) and ship 7.1 as deduction-only (post-paid, balance can run arbitrarily negative until 7.8). SM counters that an unbounded free-tier hole between 7.1 and 7.8 is a commercial risk; a cheap Redis gate closes it now.
- **Q-PERCALL — 按调用 flat-fee.** The title says "按 token / 按调用" but `model_pricing` (§4.1) has no per-call column. SM default: **per-token is the primary + only-wired mode in 7.1**; per-call is realised as a configurable flat `per_call_price_usd` that is OFF by default and requires a NEW nullable `model_pricing.per_call_price_usd` column (additive). Architect alternatives: (a) add the column now (additive, cheap) and wire both modes; (b) scope per-call entirely to a later Story and ship per-token-only. SM defaults to (a)-column-additive-but-OFF so the schema is forward-compatible without 7.1 carrying untested per-call billing.
- **Q-CH — cost in `UsageEvent` vs gateway-computed.** Epic 9's audit-svc writes `request_logs.cost_usd` (ClickHouse). For audit-svc to have the cost, EITHER (a) the `UsageEvent` carries a `cost_usd` field that billing-svc computes and... no — billing-svc consumes the SAME event audit-svc consumes, so billing-svc cannot enrich it for audit-svc. SM default: **the `UsageEvent` carries raw inputs (tokens + model_id + markup snapshot ref); each consumer computes cost from the shared `internal/pricing` logic** (lifted to a shared `packages/pricing-core/` so gateway/billing-svc/audit-svc agree byte-for-byte). Architect alternative: the GATEWAY computes cost and stamps it into `UsageEvent.cost_usd` (single source of truth, no recompute drift) — SM leans toward this (simpler, no shared-lib coupling) but flags that it moves pricing-snapshot ownership onto the gateway.
- **Q-LEDGER — `usage_ledger` canonical placement.** SM proposes a NEW `he_api.usage_ledger` table (one row per billed request, unique on `he_request_id`, carries tokens + cost + model + ts) as the billing-accuracy SoT + idempotency fence. It is not in data-models §4.1 today. Architect ratifies whether it lands in §4.1 canonically (SM default YES) or whether ClickHouse `request_logs` is intended to be the only per-request record (SM counter: ClickHouse is 90-day-TTL OLAP + Epic-9 scope; billing needs a durable, transactional, OLTP idempotency fence that request_logs cannot provide).
- **Q-RECON — Redis↔PG reconciliation cadence.** SM default: **PG-authoritative; Redis realtime mirror reconciled lazily** (every deduction UPSERTs Redis from the post-deduction PG value; a periodic 60s sweep is OUT for 7.1 — added if drift is observed). Architect may mandate a periodic reconciliation job now.
- **Q-KCLIENT — Kafka client library.** Align with notification-svc's existing choice (`internal/audit/kafka.go`). SM default: **REUSE whatever notification-svc uses** for consistency. Architect confirms (no new dependency).
- **Q-ROUND — money rounding policy.** SM default: **HALF-UP to NUMERIC(12,4)** at cost-compute time, once per ledger row (no compounding). Architect ratifies (alternative: round-half-even / banker's rounding — SM defaults HALF-UP per the conservative bill-the-customer-fairly-but-never-under direction).

The gate is fail-OPEN (Redis down → allow, never block paying traffic on a cache outage — parity with the 5.x fail-open ratelimit posture).

### AC1: 计费引擎 — per-token + markup cost computation (按 token + markup 5-15%)

**Scenario**
```gherkin
GIVEN
  - The he_api.model_pricing table is seeded (Story 6.2 `0007`) with one latest-effective_at row per concrete model carrying upstream_price_per_1k_input_tokens, upstream_price_per_1k_output_tokens, markup_percent ∈ [5.00, 15.00] (DEFAULT 10.00)
  - billing-svc has loaded a pricing snapshot at boot + refreshes it every 60s (REUSE the Story 6.2 routing-svc internal/pricing snapshot pattern — NEVER a per-event PG query)
  - A successful chat completion consumed prompt_tokens=1500, completion_tokens=800 on model `qwen-max` whose pricing row is (input=0.0080, output=0.0240, markup=10.00)
WHEN
  - billing-svc.internal/pricing.ComputeCost("qwen-max", 1500, 800, BILLING_MODE_PER_TOKEN) is invoked
THEN
  - base_cost = (1500/1000 × 0.0080) + (800/1000 × 0.0240) = 0.0120 + 0.0192 = 0.0312
  - cost_usd = base_cost × (1 + 10.00/100) = 0.0312 × 1.10 = 0.03432
  - rounded HALF-UP to NUMERIC(12,4) → **0.0343**
  - the function returns a Decimal `0.0343`; NO floating-point arithmetic is used on the money path (string/Decimal only — Q-Spec-4 cascade-lock)
  - markup boundaries hold: markup=5.00 → ×1.05; markup=15.00 → ×1.15; a row with markup outside [5,15] is a pricing-data error (slog WARN + use the row as-is — billing never silently drops a charge, Q-ROUND-out-of-range)
  - a model with NO pricing row → ComputeCost returns a typed `ErrNoPricing`; the event is dead-lettered / parked (NOT silently zero-charged — see AC2 error handling), and an alert metric fires
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-C-1 | Cost formula (per-token): `cost_usd = (prompt_tokens/1000 × price_in + completion_tokens/1000 × price_out) × (1 + markup_percent/100)`, rounded HALF-UP to NUMERIC(12,4). The division by 1000 and the markup multiply are done in Decimal (e.g. `shopspring/decimal` or equivalent — Q-DECIMAL aligns the lib with any existing money lib in the repo), NEVER float64. |
| BR-C-2 | The markup is the per-model `model_pricing.markup_percent` of the LATEST `effective_at` row ≤ the event timestamp (point-in-time pricing — a price change does not retro-bill past requests). For 7.1 the snapshot uses latest-effective_at globally (parity with 6.2); strict point-in-time-at-event-ts is Q-PIT (SM default: latest snapshot is sufficient for 7.1 since pricing is near-static). |
| BR-C-3 | Per-call mode (按调用, Q-PERCALL): if enabled for a model, `cost_usd = per_call_price_usd` (flat, token-independent) ADDED to OR REPLACING the per-token cost (Architect rules add-vs-replace). SM default: per-call is OFF for all models in 7.1 (the column lands additive+nullable but unused); per-token is the only billed mode. |
| BR-C-4 | Pricing snapshot staleness is bounded by the 60s refresh; a stale price → a slightly-off charge on the very next request after a price change, self-correcting within 60s. Acceptable per the 6.2 precedent (pricing is operator-controlled, low-churn). |
| BR-C-5 | The cost engine is a PURE function of (model_id, prompt_tokens, completion_tokens, mode, pricing_snapshot) — no I/O, no clock, fully unit-testable with golden vectors. This is the seam QA's golden-vector suite targets. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| prompt_tokens | uint32 | yes | ≥ 0 | n/a (0 is valid — a refusal/empty completion still bills input) |
| completion_tokens | uint32 | yes | ≥ 0 | n/a (0 is valid — embeddings-style / blocked output) |
| model_id | string | yes | must resolve to a model_pricing row | `ErrNoPricing` → dead-letter (AC2) |
| markup_percent | NUMERIC(5,2) | from pricing | warn if ∉ [5,15] but bill as-is | slog WARN `billing_markup_out_of_range` |

**Examples**
- **Input**: deepseek-v3 (input=0.0014, output=0.0028, markup=15.00), prompt=10000, completion=5000 → base=(10×0.0014)+(5×0.0028)=0.0140+0.0140=0.0280 → ×1.15=0.0322 → **0.0322**.
- **Input**: prompt=1, completion=0, price_in=0.0080, markup=10 → base=(0.001×0.0080)=0.000008 → ×1.10=0.0000088 → HALF-UP NUMERIC(12,4) → **0.0000** (sub-0.5-mill rounds to zero — documented; a true per-request minimum-charge floor is OUT for 7.1).

### AC2: 余额扣减 — exactly-once async deduction (每次调用消费扣减余额)

**Scenario**
```gherkin
GIVEN
  - The api-gateway has served a successful POST /v1/chat/completions (he_request_id=H, user_id=U, api_key_id=K, model=M, prompt_tokens=P, completion_tokens=C)
  - he_api.balances has (or will lazily get) a row for user U; he_api.usage_ledger is empty for H
WHEN
  - the gateway emits ONE usage.recorded UsageEvent {he_request_id:H, user_id:U, api_key_id:K, model:M, prompt_tokens:P, completion_tokens:C, ts} AFTER the response is fully flushed (non-stream: after body write; stream: after the final SSE chunk; A/B: ONE event per leg)
  - billing-svc consumes the event
THEN
  - billing-svc opens ONE PG transaction:
    1. INSERT INTO usage_ledger (he_request_id, user_id, api_key_id, model, prompt_tokens, completion_tokens, cost_usd, ts) VALUES (...) ON CONFLICT (he_request_id) DO NOTHING
    2. IF zero rows inserted (redelivery) → ROLLBACK + ACK the Kafka offset + return (exactly-once: NO second deduction)
    3. ELSE compute cost_usd via AC1, write it into the ledger row, and UPDATE balances SET current_usd = current_usd - cost_usd, updated_at=NOW() WHERE user_id=U (UPSERT a zero row first if absent)
    4. COMMIT (ledger-insert + balance-deduction are atomic — both or neither)
  - AFTER commit (best-effort, non-transactional): DECRBYFLOAT balance:user:U:realtime by cost_usd; INCRBYFLOAT usage:apikey:K:month_cost_usd by cost_usd (the Story 5.2-promised writer); UPDATE api_keys SET current_month_cost_usd = current_month_cost_usd + cost_usd WHERE id=K (the Story 5.4 cap-gate input)
  - the Kafka offset is committed only after the PG transaction commits (at-least-once consume + idempotent apply = effectively exactly-once)
  - balance deduction is observable: Prometheus he_billing_deductions_total{result} + he_billing_deduct_amount_usd histogram + non-PII-safe slog billing_deduct{he_request_id, user_id, model, cost_usd}
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-D-1 | **Exactly-once** is enforced by `usage_ledger` UNIQUE(he_request_id) + `INSERT ... ON CONFLICT DO NOTHING`. Kafka redelivery (consumer restart/rebalance) re-presents the event; the conflicting insert yields zero rows → the consumer ACKs and skips. NO deduction is ever applied twice for the same he_request_id. |
| BR-D-2 | The ledger-insert and the balance-UPDATE are in **ONE PG transaction**. A crash mid-transaction rolls back BOTH (no orphan ledger row, no phantom charge). The Kafka offset is committed only post-PG-commit, so a crash before offset-commit re-delivers and BR-D-1 dedups it. |
| BR-D-3 | **PG is authoritative.** The Redis realtime mirror + month_cost counters + api_keys.current_month_cost_usd are updated AFTER commit, best-effort. A Redis failure post-commit logs `billing_redis_mirror_failed` + increments a counter but does NOT roll back the durable PG charge (the next reconciliation / next deduction UPSERT re-syncs Redis). |
| BR-D-4 | The gateway producer is **fire-and-forget**: emitting usage.recorded MUST NOT block or fail the user's chat response (the response already succeeded — billing is downstream). A producer error logs `billing_emit_failed` + increments he_billing_emit_failures_total. (Durability of the emit itself: SM default relies on Kafka producer acks=all + the gateway's at-least-once retry; a truly-lost event is a missed charge, bounded + alertable — Q-EMIT-DURABILITY whether an outbox is needed; SM defaults NO outbox for 7.1.) |
| BR-D-5 | **balances row is lazily created** (UPSERT `INSERT ... ON CONFLICT (user_id) DO UPDATE`) on first deduction — no backfill migration for existing users (Q-LAZY). |
| BR-D-6 | Deduction always uses `current_usd` (USD). RMB / multi-currency is Story 7.2 — `current_rmb` is left at its DEFAULT 0 and untouched by 7.1. |
| BR-D-7 | A failed completion (4xx/5xx returned to the user, or both A/B legs failed) emits **NO** usage.recorded event → no charge (you only bill for served tokens). A partial A/B (one leg ok) emits ONE event for the successful leg only (parity 6.4 partial-billing). |
| BR-D-8 | `ErrNoPricing` (AC1) on consume → the event is parked to a dead-letter topic `usage.recorded.dlq` (or retried with backoff — Q-DLQ) + alert; the user is NOT charged and the request is NOT lost from the audit trail. Billing never silently zero-charges a billable request. |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| Kafka redelivery (same he_request_id) | usage_ledger ON CONFLICT → zero rows → ACK + skip (BR-D-1) |
| PG down during consume | do NOT ACK the offset → Kafka redelivers when PG recovers (at-least-once + idempotent) |
| Redis down after PG commit | log `billing_redis_mirror_failed` + counter; PG charge stands; reconcile later (BR-D-3) |
| No pricing row for model | dead-letter `usage.recorded.dlq` + alert; no charge applied (BR-D-8) |
| Gateway Kafka producer error | log `billing_emit_failed` + counter; user response UNAFFECTED (BR-D-4) |

**Examples**
- **Input**: event H consumed once → ledger gets 1 row, balance debited 0.0343, Redis mirrored. Event H redelivered → ON CONFLICT, zero rows, ACK, balance UNCHANGED. ✅ exactly-once.
- **Input**: A/B request (legs qwen-max + deepseek-v3 both succeed) → TWO events (H#a, H#b with distinct ledger keys, e.g. `H:legA`/`H:legB` — Q-ABKEY on the dedup-key shape) → TWO ledger rows → balance debited (costA + costB). ✅ dual-billing parity with 6.4.

### AC3: 账单准确 — usage ledger SoT + balance query + pre-flight gate (账单准确)

**Scenario**
```gherkin
GIVEN
  - he_api.usage_ledger accumulates one row per billed request (the durable, transactional billing SoT)
  - he_api.balances holds the authoritative current_usd per user
WHEN
  - a client calls GET /v1/balance (JWT-cookie or bearer)
  - OR a client calls GET /v1/usage (current-month aggregate)
  - OR a new chat request arrives and the pre-flight gate (Q-GATE) evaluates the balance
THEN
  - **GET /v1/balance** → 200 {"current_usd": "12.3400", "currency": "USD", "updated_at": "<RFC3339>"} — current_usd serialized as a STRING-decimal (Q-Spec-4 cascade-lock; NEVER a JSON number); read from PG balances (authoritative), NOT Redis
  - **GET /v1/usage** → 200 {"period": "2026-06", "total_cost_usd": "4.5600", "total_requests": 132, "total_tokens": 845000, "by_model": [...]} — aggregated from usage_ledger WHERE user_id=U AND ts in current UTC month (string-decimal money)
  - **Pre-flight gate** (SM default IN): on POST /v1/chat/completions, BEFORE upstream dispatch, read balance:user:U:realtime (fast Redis); if ≤ 0 → reject with 402 `402_balance_insufficient` (§5.1.2 first-emission) BEFORE any upstream cost is incurred; if Redis is unavailable → fail-OPEN (allow the request — never block paying traffic on a cache outage)
  - **Billing accuracy invariant**: SUM(usage_ledger.cost_usd WHERE user_id=U) reconciles against (total recharged − balances.current_usd) within rounding tolerance — this is the reconciliation assertion QA verifies and the foundation 7.7's monthly PDF invoice reads
  - **Accuracy** means: every billed request appears EXACTLY once in usage_ledger (BR-D-1); cost_usd matches the AC1 golden computation; the SUM of ledger costs equals the total deducted from balance (no drift, no double-count, no missing charge)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-A-1 | `usage_ledger` is the **billing SoT** — durable, transactional, OLTP, unbounded retention (NOT the 90-day-TTL ClickHouse request_logs). 7.7's monthly invoice + 7.2's re-pricing + reconciliation all read it. (Q-LEDGER ratifies canonical placement.) |
| BR-A-2 | GET /v1/balance reads PG `balances` (authoritative), NOT Redis — a user checking their balance must see the durable truth, not a possibly-stale cache. (Redis realtime is only for the hot-path gate where speed > strict-accuracy.) |
| BR-A-3 | Money fields on ALL billing REST responses are **string-decimals** (`"12.3400"`) per Q-Spec-4 (the §4.4 + Story 5.1 cascade-lock); a JSON-number money field is a contract violation. |
| BR-A-4 | The `402_balance_insufficient` gate is **fail-OPEN** (Redis down → allow) — parity with the 5.x ratelimit/keypolicy fail-open posture. Rationale: blocking paying customers on a cache outage is worse than briefly serving a near-zero-balance request (which the async deduction + monthly cap-gate still account for). |
| BR-A-5 | GET /v1/usage aggregates the **current UTC calendar month** (`ts >= date_trunc('month', now() at time zone 'UTC')`) — aligns with the Story 5.4 monthly-cap reset boundary (00:00 UTC on the 1st). |
| BR-A-6 | The pre-flight gate threshold is `balance ≤ 0` for 7.1 (hard-zero). A configurable low-balance soft-threshold + auto-recharge trigger is Story 7.7; subscription-tier free-quota is Story 7.8. |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Balance ≤ 0 on pre-flight | 402 | `402_balance_insufficient` — "Insufficient balance. Please top up to continue." | reject before upstream dispatch (BR-A-4) |
| GET /v1/balance, no balances row | 200 | — | return `{"current_usd": "0.0000", ...}` (lazily-absent row reads as zero) |
| GET /v1/usage, no ledger rows this month | 200 | — | return zero-aggregate `{"total_cost_usd": "0.0000", "total_requests": 0, ...}` |
| Redis down on pre-flight gate | (allow) | — | fail-OPEN; slog `billing_gate_fail_open` + counter |

**Examples**
- **Input**: user U with balance 0.05 USD makes a chat request costing 0.0343 → served (gate sees 0.05 > 0) → balance → 0.0157 → ledger +1 row. Next request costing 0.0343 → gate sees 0.0157 > 0 → served → balance → −0.0186 (bounded negative, BR per data_sync_analysis). Following request → gate sees −0.0186 ≤ 0 → **402_balance_insufficient**. ✅
- **Input**: GET /v1/usage for a user with 132 billed requests this month → `{"period":"2026-06","total_cost_usd":"4.5600","total_requests":132,...}` summed from usage_ledger. ✅

### Database Design (WHY, not full SQL)
- **`balances`** is keyed by `user_id` (one row per user; lazily UPSERT-created on first deduction — Q-LAZY avoids a backfill migration). `current_usd` is the authoritative money truth.
- **`usage_ledger`** is the billing accuracy SoT + idempotency fence. `UNIQUE(he_request_id)` is what makes the at-least-once Kafka consume effectively exactly-once (BR-D-1). It is OLTP + durable + unbounded-retention — deliberately NOT the ClickHouse `request_logs` (90-day TTL, OLAP, Epic-9). The ledger-insert + the balance-UPDATE share ONE transaction (BR-D-2). `[→ data-models.md §4.2 request_logs TTL 90 DAY; this Story Q-LEDGER]`
- **Why async-Kafka deduction (not sync gRPC on the hot path)**: deduction happens AFTER the response is served (you bill served tokens). Putting a synchronous DeductBalance on the chat critical path would add latency + a failure mode that could fail a successful completion. The async path decouples billing durability from response latency. The sync `CheckBalance` exists only as a PG-authoritative read for console/reconciliation. `[→ service-topology.md §3.2 + §3.3 sync-vs-async boundary]`
