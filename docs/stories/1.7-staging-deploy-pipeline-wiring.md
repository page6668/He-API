## Epic Context
**Epic**: 1 - 项目地基与云基础设施
建立 monorepo、CI/CD、云资源、可观测性基础，为后续所有 Epic 提供可落地的工程地基。

本故事是 Epic 1 的**部署接线收尾工作包**：代码完整、测试全绿、Phase C 通过 ≠ 可部署。部署前静态审计（`docs/runbooks/deployment-prerequisites-and-audit.md` PART B）发现运行时部署管线端到端是 stub —— `build-images`（17 个里只构建 3 个）→ `deploy-staging`（只 bump api-gateway 一个 tag）→ **ArgoCD 同步 = 占位 echo**。本故事补齐 B1–B7 让 **staging 可端到端部署**。

**Story Deliverables**:
- B1 — 真实 `argocd app sync`（替换 `deploy-staging.yml:96` 占位 echo）
- B2 — `build-images.yml` 矩阵覆盖全部 17 个可部署镜像
- B3 — 补 4 个缺失 ArgoCD Application + 所有 app 读 `values-staging.yaml` + 定义 `he-api` AppProject
- B4 — 替换镜像占位符 + 消除 `tag: latest`（改 `:SHA`）
- B5 — Ingress 模板 + staging DNS/TLS
- B6 — 3 个 cron Dockerfile + billing-svc Deployment 模板
- B7 — payment-svc Helm chart 接入 5 支付密钥
- B7b（AC8） — analytics-svc Helm chart 补建（解除 B2/B3 deploy 链悬空；Architect H-1 裁定 Option 1）

**OUT OF SCOPE（明确不做）**:
- **B8 — prod 环境接线**（`envs/prod` 数据层、`values-prod`、prod ArgoCD app）。staging 端到端跑通后另起故事。
- Vault / ESO 密钥注入（Epic 9）—— staging 沿用手建 K8s Secret / Terraform 渲染。
- 实际 `terraform apply` 与真实集群部署执行（属运维 PART A，本故事只交付**可部署的工程接线**，验证以静态为主）。

## Acceptance Criteria

### AC1 (B1): ArgoCD 同步换成真实 `argocd app sync`

**Scenario**
```gherkin
GIVEN deploy-staging.yml 的 trigger-argocd-sync job 当前是占位 echo
  AND vars.ARGOCD_ENDPOINT 已配置 (HAS_ARGOCD == 'true')
WHEN build-images 成功后触发 deploy-staging
THEN "Trigger ArgoCD sync (real)" step 执行真实 argocd CLI
  AND 对 he-api AppProject 下所有应用执行 `argocd app sync`（不再是 echo 占位）
  AND 使用 ARGOCD_AUTH_TOKEN（GitHub secret）+ ARGOCD_ENDPOINT（GitHub var）登录，--grpc-web，禁用明文 token
  AND 同步后执行 `argocd app wait <app> --health --timeout` 以确认 rollout
  AND HAS_ARGOCD != 'true' 时仍走 fallback skip（不破坏无凭据的 CI）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR1.1 | 占位字符串 `ArgoCD sync placeholder (real CLI wired in Story 1.4)` 必须从仓库中消失（grep 断言 0 命中）|
| BR1.2 | argocd 凭据只能来自 `secrets.ARGOCD_AUTH_TOKEN` + `vars.ARGOCD_ENDPOINT`；禁止硬编码 endpoint/token |
| BR1.3 | sync 失败（任一 app 非 Healthy/Synced）必须使 job 失败（非零退出），不得吞错 |
| BR1.4 | sync 目标 app 列表与 B3 的 ArgoCD Application 清单一致（单一来源，避免漏 sync 新增服务）|

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| ARGOCD_ENDPOINT 未配置 | n/a | "ArgoCD endpoint not configured — skipping sync" | 走 fallback skip step（保持现有契约）|
| argocd 登录失败 | 非零 | argocd CLI stderr | job fail，不进入 sync |
| app sync/wait 超时或不健康 | 非零 | argocd app wait 输出 | job fail |

### AC2 (B2): build-images 矩阵覆盖全部可部署镜像

**Scenario**
```gherkin

THEN PR 校验（build-image-pr）与 main 推送（build-image-main）矩阵都覆盖全部 17 个目标镜像
  AND 每个矩阵条目能正确定位其 Dockerfile（context 非 apps/<svc>/Dockerfile 的 cron 镜像需带 context/dockerfile 覆盖字段）
  AND main 分支推送时镜像 tag 一律为 :${github.sha}（不可变 tag，Story 1.2 1.2-UNIT-013 契约）
  AND Story 1.5 Q8 "单一 append 点" 契约保持（svc 仍只在 &svc_list 一处声明，1.5-UNIT-216 no-duplicate-entries 不回归）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR2.1 | "17 个" = 对 `apps/**/Dockerfile` 清单逐一核账后的可部署镜像全集（含 B6/B7 新增的 cron 与 payment-svc）；最终矩阵条目数 == Dockerfile 目标数，CI 加计数断言防漏 |
| BR2.2 | sample-otel-app / sample-grpc-app 可保留在矩阵中（样例镜像不计入 17，但不删除）|
| BR2.3 | 子目录 cron 镜像（如 `apps/billing-svc/cmd/fx-refresh`、`apps/api-gateway/cmd/safety-log-retention`）的 context/dockerfile 路径必须显式声明，不能假设 `apps/<svc>` |
| BR2.4 | image-sha artifact 现仅 api-gateway 上传；多镜像部署后该契约可保留或扩展，但不得破坏 deploy-staging 的 image-sha 下载步骤 |

**Error Handling**
| Scenario | Code | Message | Action |

| 某镜像 build 失败 | 非零 | docker build stderr | fail-fast: false，单镜像失败不阻断其余，但 job 整体 fail |
| HAS_ACR != 'true' | n/a | "ACR_USERNAME not configured — skipping push" | 保持现有 skip 分支（无凭据 CI 只校验不推送）|

### AC4 (B4): 消除镜像占位符与 `tag: latest`

**Scenario**
```gherkin
GIVEN auth-svc/values-staging.yaml 用 $$ACR_REGISTRY 且 tag: latest
  AND api-gateway/values-staging.yaml 用 ${ACR_REGISTRY}（语法不一致）
WHEN 标准化镜像引用并接入 SHA tag bump
THEN 镜像 repository 占位符语法统一（单一约定，由 deploy-staging 的替换/yq 步骤可解析）
  AND 任何 values*.yaml 中不再出现 tag: latest 或任何移动 tag（grep 断言 0 命中）
  AND staging 镜像 tag 由 deploy-staging 的 helm-values bump 步骤写入 :${github.sha}
  AND deploy-staging 的 update-helm-values 从"只 bump api-gateway"扩到 bump 所有 staging app（与 B2/B3 服务集对齐）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR4.1 | 不可变 tag 原则（Story 1.2 1.2-UNIT-013）：staging 镜像 tag 永远是 git SHA，禁止 latest / 浮动语义 tag |
| BR4.2 | 占位符约定二选一并全仓统一：① 真实 ACR registry 写入 values（推荐 secret/var 注入），或 ② deploy-time 替换 token（需在 install/部署脚本中真实 wired，不能只是注释）|
| BR4.3 | api-gateway/values-staging.yaml 的 Architect 白名单注释（image/service/networkPolicy/serviceAccount）需随 bump 范围扩展而更新，且 image.tag 字段保持 yq-bump 可写 |
| BR4.4 | values.yaml（默认）保留语义版本（如 0.1.0/0.0.1）；只有 values-staging.yaml 走 SHA bump |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| 占位符未被替换就部署 | ImagePullBackOff | k8s 拉取失败 | 静态校验阶段 grep 阻止占位符进入已 sync 路径 |
| bump 步骤漏服务 | app 用旧/错 tag | — | bump 服务列表与 B3 Application 列表单一来源对齐 |

  AND TLS 证书来源明确（cert-manager Issuer/ClusterIssuer 或预置 Secret），并在 Dev Notes 记录前置依赖

**Business Rules**
| ID | Rule |
|----|------|
| BR5.1 | Ingress 默认 enabled: false（values.yaml），仅 values-staging.yaml 显式开启 staging hosts；prod 留给 B8 |
| BR5.2 | api-gateway/values-staging.yaml 的"FORBIDDEN: ingress.*"白名单（Architect Round 1 Q1）必须由本故事正式解禁并更新注释——ingress 归 1.7 不再归 1.4 |

### AC8 (B7b): analytics-svc Helm chart 补建（解除 deploy 链悬空）

> **来源**：Architect Round 1 H-1 裁定 Option 1（SM ruling 2026-06-16）。`apps/analytics-svc` 已有 app code + Dockerfile，且已被列入 B2 镜像集（Dev Notes "17 镜像"）与 B3 Application 集，但 `infra/helm/analytics-svc/` **不存在**——若 Application `source.path` 指向不存在的 chart 将 sync 失败，并使 T8.1（build ⊆ Application ⊆ values-staging 三处计数一致）不可闭合。本 AC 补建 chart 使该不变式成立。

**Scenario**
```gherkin
GIVEN apps/analytics-svc 已有 server + Dockerfile，但 infra/helm/ 下无 analytics-svc chart
  AND analytics-svc 已被 B2 镜像集 / B3 ArgoCD Application 集引用（deploy 链已承诺该服务）
WHEN 新建 analytics-svc Helm chart（复用 auth-svc 结构）
THEN infra/helm/analytics-svc/ 含 Chart.yaml + templates（deployment/service/serviceaccount/_helpers/networkpolicy）+ values.yaml + values-staging.yaml
  AND chart 形态与 auth-svc 对齐（Pod Security Restricted、OTel env、probes、serviceaccount；无支付密钥，区别于 payment-svc B7）
  AND analytics-svc 在 B2 矩阵 / B3 Application / B4 SHA bump / values-staging 四处清单中闭环（与 payment-svc 同等地位）
  AND B3 的 analytics-svc Application `source.path` 指向本 chart（不再悬空）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR8.1 | analytics-svc chart 复用 auth-svc chart 结构（BR7.2 同款），**不含**支付密钥 secretRef——它不是支付服务，envFrom 仅注入其自身所需 env/config |
| BR8.2 | analytics-svc 加入后，"镜像 / Application / values-staging / SHA bump" 四处清单与 B2/B3/B4 单一来源同步（与 BR7.4 同等约束）|
| BR8.3 | 本 AC 只补 **chart**，不改变 B2 镜像计数——analytics-svc Dockerfile 已存在并已计入"17 镜像"，故 M-1 的 17 计数不受本 AC 影响 |
| BR8.4 | analytics-svc 的 staging env/依赖（DB/ClickHouse 等下游）若有前置，记入 Dev Notes 前置依赖边界，不在本故事执行真实接库 |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Application 指向缺失 chart | sync 失败 | argocd "path not found" | 本 AC 必须先于/随 Application 落地（BR3.6）|
| chart 渲染缺 values-staging | helm 渲染错 | — | 同 B3/B4，补 values-staging overlay |

### ⚠️ 已发现的前置缺陷（PRE-EXISTING · 非本故事引入 · 非本故事修复 → 建议独立 Dockerfile-hardening 故事）
矩阵 `context` 字段忠实匹配每个 Dockerfile 的**现有设计**（约定见下），1.7-BLIND-DATA-001 证明每条目都能定位到存在的 Dockerfile。但实际 `docker build` 的成功是运维 PART A（本故事静态范围内不执行 docker build）：
- **`apps/<svc>` context 的 Dockerfile（api-gateway / auth-svc / notification-svc / analytics-svc + sample-grpc-app + 2 个 cron）** 做 `COPY . .` + `go build ./cmd/server`，但这些模块的 `go.mod` 含 `replace … => ../../packages/…` 指向**构建上下文之外**的目录 → 以 `context: apps/<svc>` 构建时 replace 目标缺失，`go build` 会失败。
- 这是**前序遗留缺陷**：`sample-grpc-app`（1.7 之前就在矩阵里、context 也是 `apps/<svc>`）同样含该 replace，说明此问题先于本故事存在（build-images 此前只构建 api-gateway + 2 样例，且 fail-fast:false / 不 gate 合并）。
- **可工作的对照约定**：较新的服务（billing/payment/routing/6 适配器）的 Dockerfile 用 **repo-root context** + `go build ./apps/<svc>/cmd/server`（含 go.work + packages → replace 可解析）。根因修复 = 把上述 5 个旧 `apps/<svc>`-context Dockerfile 迁移到 root-context 约定（编辑他故事 owned 的 Dockerfile，属 unsolicited refactor，本故事不做）。
