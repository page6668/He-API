### AC1: 邮箱注册（signup）+ bcrypt 密码哈希 + users INSERT + 验证邮件发送

**Scenario**
```gherkin
GIVEN 海外访问者打开 `/{locale}/(auth)/signup` 页面（locale 由 Story 2.1 cookie-first 协商；ar 走 RTL）
  AND email 输入框留白且未在 users 表内存在
  AND 密码 ≥ 10 chars 且不在 HaveIBeenPwned 已泄露密码库（Q5 sm_proposal=a；本 Story 经 k-anonymity API 实时检查，离线不可用时 fail-closed 拒绝注册）
  AND 客户端 IP 在过去 5 分钟内 signup 请求次数 < 5 次（Redis ratelimit `ratelimit:signup:ip:{ip}` 计数器）
WHEN 用户点击「Sign up」按钮 → console Server Action `registerUser({email, password, locale})` → console BFF (Q1 待仲裁；sm_proposal=b 经 api-gateway REST `POST /v1/auth/signup`) → auth-svc gRPC `RegisterUser(email, password, locale)`
THEN auth-svc 执行以下操作（事务边界 = PG 事务 + 邮件发送后置）：
  - bcrypt.HashPassword(password, cost=12) → password_hash
  - INSERT INTO users (id=gen_random_uuid(), email, password_hash, email_verified_at=NULL, locale, status='active', created_at=NOW(), updated_at=NOW())
  - 生成 32 bytes crypto random token；SHA-256(token) → token_hash
  - 写入 Redis `auth:email_verify:{token_hash}` → JSON{user_id, expires_at=NOW+24h, attempts=0}，TTL=86400s（Q2 sm_proposal=a）
  - gRPC notification-svc `SendEmail(template_id='email_verification', to=email, locale=locale, vars={token, link=https://console.he-api.com/{locale}/verify-email?token={token}})`（Q4 sm_proposal=c）
  - Kafka publish `audit.event` event_type='auth.signup'，payload={user_id, email_hash=SHA256(email), ip, ua, ts}
  - 返回 gRPC RegisterUserResponse{user_id, status='pending_verification'}
  - api-gateway 透传 200 OK + body {message:'verification_email_sent'}（不返回 user_id 给前端，防用户枚举）
  - console 重定向至 `/{locale}/(auth)/signup/check-inbox?email={masked_email}` 页（仅显示 'We sent a verification link to {masked_email}'）
```

### AC2: 邮件验证（verify-email）+ users.email_verified_at 写入 + 重发验证邮件（resend-verification）

**Scenario**
```gherkin
GIVEN 用户已完成 AC1 signup，收件箱收到验证邮件，点击邮件中链接 `https://console.he-api.com/{locale}/verify-email?token={token}`
  AND token 长度 = 64 chars (base64url 32 bytes)，未过期 (24h TTL 内)，未消费
WHEN console verify-email page (Server Component) → Server Action `verifyEmail(token)` → console BFF (Q1) → api-gateway `GET /v1/auth/verify-email?token={token}` → auth-svc gRPC `VerifyEmail(token)`
THEN auth-svc 执行：
  - SHA-256(token) → token_hash
  - Redis GET `auth:email_verify:{token_hash}` → 解析 JSON{user_id, expires_at, attempts}
  - 检查 expires_at > NOW；attempts < 5（防 token 爆破）
  - UPDATE users SET email_verified_at = NOW(), updated_at = NOW() WHERE id = user_id AND email_verified_at IS NULL
  - Redis DEL `auth:email_verify:{token_hash}`（一次性消费）
  - Kafka publish `audit.event` event_type='auth.verify_email'，payload={user_id, ip, ua, ts}
  - 返回 gRPC VerifyEmailResponse{user_id, email_verified_at}
  - api-gateway 透传 200 + body {message:'email_verified'}
  - console 渲染成功页 + CTA "Sign in to your account" → 链接 `/{locale}/(auth)/signin?email={user.email}`（pre-fill email）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | Token 一次性消费：Redis DEL 后无法重复验证；用户访问已消费 token → 显示 "This link has already been used" + CTA "Sign in" |
| BR-2.2 | Token 过期（>24h）：Redis 自然 TTL 过期 → GET 返回 nil → 显示 "This link has expired" + CTA "Resend verification email" → 触发 ResendVerification RPC |
| BR-2.3 | email_verified_at 设置后**不可清除**（除非 Story 2.7 物理删除）；重复 VerifyEmail 调用对已验证账户：返回 200 + {message:'already_verified'}（幂等） |
| BR-2.4 | ResendVerification RPC：输入 email + 客户端 IP；后端校验 IP rate limit (3 次/15min/IP) + email-level rate limit (1 次/60s/email)；对未注册 email 返回与已注册相同的成功响应（防枚举）；对已验证 email 返回 {message:'already_verified'}（防枚举可选：也可统一成功响应；待 Q5 / Architect 在 BR-2.4 处给出 ruling） |
| BR-2.5 | Token 爆破检测：单个 token 校验失败 attempt count 增至 5（极少触发；token 64 chars 实际不可爆破）→ 立即 DEL token + 触发 audit 事件 `auth.verify_email_brute_force` |
| BR-2.6 | 邮件链接的 locale 段沿用用户注册时所选 locale（不查询当前浏览器 Accept-Language），保证用户在不同设备打开邮件时看到一致语言 |

| Field | Type | Required | Rules | Error Message (i18n key) |

| token | string | yes | 长度 = 64；base64url 字符集（A-Za-z0-9_-） | `auth.errors.invalidToken` |
| email (ResendVerification only) | string | yes | RFC 5322 简化版 | `auth.errors.invalidEmail` |

### AC3: 密码登录（signin）+ JWT RS256 颁发 + httpOnly cookie 设置 + 受保护页访问

**Scenario**
```gherkin
GIVEN 用户已完成 AC1 signup 且 AC2 email 已验证（users.email_verified_at IS NOT NULL）
  AND users.status='active' （非 'locked' / 'suspended' / 'pending_deletion'）
  AND 客户端在过去 15min 内 signin 失败次数 < 5（Redis `ratelimit:signin:email:{email_hash}` 计数器 < 5）
WHEN 用户在 `/{locale}/(auth)/signin` 提交 {email, password} → console Server Action `signin({email, password})` → console BFF (Q1) → api-gateway `POST /v1/auth/signin` → auth-svc gRPC `LoginUser(email, password)`
THEN auth-svc 执行：
  - SELECT id, password_hash, email_verified_at, status, totp_enabled FROM users WHERE email = $1 LIMIT 1
  - 若 row 不存在：执行 dummy bcrypt.CompareHashAndPassword 以消耗等量时间（防 timing-side-channel），返回 401 `401_invalid_credentials`
  - 若 status != 'active'：返回对应错误（'locked' → 423 `423_account_locked`；'suspended' → 403 `403_account_suspended`；'pending_deletion' → 410 `410_account_deleted`）
  - 若 email_verified_at IS NULL：返回 403 `403_email_not_verified` + 提示 "Please verify your email first" + CTA Resend
  - bcrypt.CompareHashAndPassword(password_hash, password) → 失败则：Redis INCR `ratelimit:signin:email:{email_hash}`；若 ≥ 5 → UPDATE users SET status='locked', locked_until=NOW()+1h；返回 401 `401_invalid_credentials`（不暴露失败原因）
  - 若 totp_enabled=true（Story 2.4 启用）：返回 200 + {status:'requires_2fa', mfa_token:<short-lived JWT for 2FA challenge>}；本 Story 因 totp_enabled 默认 FALSE 该分支不触发，但 hook 必须存在
  - 否则：签发 JWT RS256 access_token（sub=user_id, iat, exp=NOW+15min, jti=uuid）+ refresh_token（sub=user_id, exp=NOW+30d, jti=uuid, family_id=uuid）；refresh_token jti 存入 Redis `auth:refresh:{family_id}` 用于轮换检测
  - UPDATE users SET updated_at = NOW() WHERE id = user_id（不更新 last_login_at — data-models.md §4.1 暂无此列，待 Story 2.5 资料管理时若需要再加）
  - Redis DEL `ratelimit:signin:email:{email_hash}`（成功登录清零失败计数）
  - Kafka publish `audit.event` event_type='auth.signin_success'，payload={user_id, ip, ua, ts}
  - 返回 gRPC LoginUserResponse{access_token, refresh_token, expires_in=900}
  - api-gateway 透传 200 OK；设置两个 Set-Cookie：
    * `he_access` (access_token)，Path=/，HttpOnly，Secure（prod/staging），SameSite=Lax，Domain=.he-api.com（prod）/.staging.he-api.com（staging）/undefined（dev），Max-Age=900
    * `he_refresh` (refresh_token)，Path=/v1/auth/refresh（窄路径），HttpOnly，Secure，SameSite=Strict，Max-Age=2592000
  - console 重定向到 `/{locale}/dashboard`（本 Story 范围内 dashboard 不存在 → 临时重定向到 Story 2.1 Demo 页 `/{locale}/`；Epic 3+ 实际 dashboard 落地后修正）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | bcrypt.CompareHashAndPassword 必须用 timing-safe 比较；明文密码**绝不**写入日志/Sentry/audit；audit 仅记录 success/failure boolean |
| BR-3.2 | 用户枚举防护：对不存在的 email，必须执行 dummy bcrypt compare（计算开销 ~100-200ms）以保证响应时间分布与真实用户一致；返回 401 `401_invalid_credentials` 而非 404 |
| BR-3.3 | 软锁定：登录失败 5 次/邮箱/15min → users.status='locked' + locked_until=NOW+1h；锁定期间所有 signin 返回 423 `423_account_locked` + Retry-After；锁定期满后由 auth-svc 在下次 signin 时 self-heal（status='active'，清零失败计数）（避免独立 cron job） |
| BR-3.4 | bcrypt cost=12（与 BR-1.2 / security.md §8.2 同 cost 规约）；compare 耗时 ~100-200ms 上限作为 SLO（auth-svc /metrics 上报） |
| BR-3.5 | JWT access_token：RS256，TTL 15min；refresh_token RS256，TTL 30 天；refresh_token family rotation 检测（reuse 检测 → 全 family 撤销，Story 2.4 后续启用，本 Story 留 hook） |
| BR-3.6 | JWT claims 最小化：仅 sub (user_id)、iat、exp、jti、aud="he-api"；**不**携带 email/locale/role/scope（这些数据 api-gateway 在校验时从 PG/cache 读取，避免 JWT 体过大 + 减少撤销复杂度） |
| BR-3.7 | Cookie 安全：access_token + refresh_token 均 HttpOnly（JS 无法读取，防 XSS 提取）；Secure 在 prod/staging 强制 HTTPS；SameSite=Lax（access） / Strict（refresh，仅 /v1/auth/refresh 路径） |
| BR-3.8 | Signin 速率限制：每 IP 10 次/15min + 每邮箱 5 次/15min（双重限制）；超限优先返回 429 `429_rate_limit_signin_ip` 或 `429_rate_limit_signin_email` |
| BR-3.9 | refresh_token jti 必须在 Redis `auth:refresh:{family_id}` 中存在；token 被使用一次后立即 DEL 旧 jti + SET 新 jti（rotation）；检测到旧 jti 重用 → 整 family 撤销并强制 user 重新登录 |
| BR-3.10 | i18n：signin 页全部文案走 `auth.json` `signin.*` key 集；email 字段不可禁用（pre-fill from query param ?email=）；提交后整页重定向（不 keep 在 signin 页） |

### AC4: 速率限制 + 用户枚举防护 + 暴力破解软锁 + 审计日志 + 安全 headers

**Scenario**
```gherkin
GIVEN auth-svc + api-gateway + console BFF 链路就位（AC1/AC2/AC3 已实现）
WHEN 攻击者尝试以下任一行为：
  (1) 从同一 IP 在 5min 内 signup 6+ 次
  (2) 对同一 email 在 15min 内 signin 失败 5+ 次
  (3) 使用脚本枚举 email（signup 大量随机邮箱）
  (4) 使用脚本爆破密码（同一 email 不同密码）
  (5) 通过 timing attack 推断 email 是否注册（measure response 时间）
  (6) 重放或篡改 JWT / verification token
  (7) 缺失 / 错误的 CSRF / Origin / Referer header
THEN 系统执行：
  - (1) IP rate limit 触发 → 429 + Retry-After 5min（per BR-1.7）
  - (2) 5 次失败后 users.status='locked' + locked_until=NOW+1h → 423（per BR-3.3）
  - (3) signup 对已存在 email 返回与首次注册相同响应 + dummy 计算（per BR-1.4）
  - (4) 同一 email rate limit 触发 → 429（per BR-3.8）；持续失败触发 BR-3.3 软锁
  - (5) dummy bcrypt compare for 不存在 email；响应时间方差应 < 50ms（per BR-3.2）
  - (6) JWT 签名校验失败 → 401；verification token 校验失败 → 410；audit 记录爆破尝试
  - (7) api-gateway 强制 Origin/Referer 校验（Same-Origin Policy）+ 状态变更类 POST 必须含合法 Origin 或 CSRF token
  - 所有事件经 Kafka topic `audit.event` 写入 ClickHouse `request_logs`（per data-models.md §4.2 — 本 Story 沿用既有 ClickHouse 链路）
  - 安全 response headers（全局，api-gateway middleware 统一注入）：
    * Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
    * X-Content-Type-Options: nosniff
    * X-Frame-Options: DENY
    * Referrer-Policy: strict-origin-when-cross-origin
    * Content-Security-Policy: default-src 'self'; ... （Epic 3+ 完善，本 Story 落地基础值）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | Rate limit 计数器统一在 Redis：`ratelimit:signup:ip:{ip}` / `ratelimit:signin:email:{email_hash}` / `ratelimit:signin:ip:{ip}` / `ratelimit:resend:ip:{ip}` / `ratelimit:resend:email:{email_hash}`；TTL = 限制窗口；超限 INCR 返回 429 |
| BR-4.2 | email_hash = SHA-256(lower(trim(email)))；用于 Redis key 不暴露明文 email（与 audit 日志 email_hash 同算法） |
| BR-4.3 | Dummy bcrypt compare 必须使用真实的 bcrypt hash（预生成的静态 hash）+ 真实的 CompareHashAndPassword 调用；不能用 sleep 模拟（攻击者可用 statistical analysis 区分） |
| BR-4.4 | 软锁 self-heal：用户在 locked_until > NOW 期间 signin 始终返回 423；NOW > locked_until 时下次 signin 自动 UPDATE status='active' + 清零失败计数（在同一事务内）；无独立 cron job |
| BR-4.5 | Audit 事件 schema：`{event_type, user_id, email_hash, ip, ua, ts, success bool, error_code, metadata jsonb}`；event_type ∈ {auth.signup / auth.signup_duplicate_attempt / auth.verify_email / auth.verify_email_brute_force / auth.signin_success / auth.signin_failure / auth.account_locked / auth.email_send_failed} |
| BR-4.6 | CSRF 防护：状态变更 POST（signup/signin/verify-email/resend）必须经 Origin header 校验（仅接受 he-api.com 子域）；console Server Action 本身已有 Next.js 内置 CSRF 防护（基于 _next 路径）|
| BR-4.7 | 安全 response headers 集中在 api-gateway middleware 统一注入；与 Epic 3+ /v1/chat/completions 共享同一 middleware；本 Story 是该 middleware 第一次启用 |
| BR-4.8 | 监控指标（OTel + Prom，per Story 1.4 / 1.5 既有 observability 体系）：`auth_signup_total{result}` / `auth_signin_total{result, error_code}` / `auth_verify_email_total{result}` / `auth_account_locked_total` / `auth_rate_limit_triggered_total{endpoint, key_type}` |
| BR-4.9 | Alert 规则（落到 Grafana Alertmanager）：5min 内 `auth_signin_total{result="failure"}` > 100 → 飞书告警；5min 内 `auth_account_locked_total` > 10 → PagerDuty（疑似暴破活动） |

| Scenario | Code | Message (i18n key) | Action |
|----------|------|---------------------|--------|
| 任意 rate limit 触发 | 429 | `auth.errors.tooManyAttempts{Variant}` | 返回 Retry-After header（秒）+ Body {error: {code, retry_after_seconds}}；前端 UI 显示倒计时 |
| CSRF / Origin 校验失败 | 403 `403_csrf_check_failed` | （仅记 audit，不返回用户可读消息，避免攻击者调试） | 拒绝请求 + audit `auth.csrf_violation` |

### Technical Constraints

> Story-specific constraints unique to 2.2. Do NOT re-state general standards (those live in `docs/architecture/coding-standards.md` + `docs/architecture/tech-stack.md` + `docs/architecture/security.md`).

- **TS-CONS-001 [bcrypt cost=12 不可降级]**：用户密码 + API Key（Epic 5）必须 bcrypt cost=12；本 Story `auth-svc/internal/password/password.go` 中 const `BcryptCost = 12`；性能 SLO 单次 compare ≤ 250ms (typical pod 2 vCPU)；**禁止**降级到 cost=10 即使为 dev/test 提升速度。
  - [Source: docs/architecture/security.md §8.1 — "密码 bcrypt cost=12"]
- **TS-CONS-002 [JWT RS256 强制]**：access_token + refresh_token 均 RS256；**禁用** HS256 / 对称密钥；私钥 4096-bit RSA；JWT lib 选 `github.com/golang-jwt/jwt/v5`。
  - [Source: docs/architecture/security.md §8.1 — "JWT (RS256) for OAuth session"]
- **TS-CONS-003 [JWT 私钥仅 K8s Secret]**：本 Story 不引入 Vault（与 Story 1.6 M-1 ruling 一致）；私钥经 Terraform `tls_private_key` 生成 → K8s Secret `he-api-auth-jwt-keys`；公钥经 ConfigMap `he-api-auth-public-keys` 分发；轮转走 1.6 文档化的 RTO ≤ 2h 路径。
  - [Source: docs/architecture/database-bootstrap.md §3 + Story 1.6 M-1 ruling]
- **TS-CONS-004 [HIBP k-anonymity fail-closed]**：HaveIBeenPwned API 不可达时 signup 返回 503 `503_hibp_unavailable`；**禁止** fail-open（允许任意弱密码通过）；timeout = 3s；本 Story `auth-svc/internal/password/hibp.go` 实现 k-anonymity 客户端（仅传 SHA-1 hash 前 5 字符）。
  - [Source: Q5 sm_proposal=a（待 Architect Round 1 仲裁）]
- **TS-CONS-005 [明文密码绝不落盘]**：密码明文仅在 RegisterUser/LoginUser handler 内的局部变量存在；**禁止**写入 audit / log / Sentry / Kafka payload / metrics label；audit 仅记 success bool + error_code；用 `passwordsd []byte` + `defer wipe(passwordsd)` 在使用后立即 zero memory。
  - [Source: docs/architecture/security.md §8.1 + OWASP ASVS L2 V2.3.3]
- **TS-CONS-006 [Token 仅存哈希]**：email verification token 在 Redis 仅存 SHA-256 哈希后的形式（`auth:email_verify:{sha256(token)}`）；明文 token 仅返回邮件给用户；**禁止**任何 verification token 明文在 Redis / PG / log。
  - [Source: Q2 sm_proposal=a + OWASP ASVS L2 V3.4.1]
- **TS-CONS-007 [Cookie 安全属性]**：access_token cookie `he_access`（HttpOnly + Secure-env-gated + SameSite=Lax + Domain=.he-api.com prod/.staging.he-api.com staging/undefined dev + Path=/ + Max-Age=900）；refresh_token cookie `he_refresh`（同上但 SameSite=Strict + Path=/v1/auth/refresh + Max-Age=2592000）；本 Story 在 api-gateway `Set-Cookie` builder 中实现，与 Story 2.1 LocaleSwitch cookie 函数风格一致（per env 切换）。
  - [Source: BR-3.7 + 类比 Story 2.1 Q4 ruling]
- **TS-CONS-008 [auth-svc 不直接持有 DB 凭据]**：auth-svc pod env vars `HE_API_DB_POSTGRES_URI` + `HE_API_DB_REDIS_URI` 经 `envFrom: secretRef: he-api-db-creds`（Story 1.6 既有）挂载；**禁止** auth-svc 自带 DB 凭据。

### Database Design

> **users 表 — 首次落地（per data-models.md §4.1 完整 schema）**：

```sql
-- migrations/postgres/0002_create_users.sql (Atlas versioned mode per Story 1.6 Q1 ruling)

CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash TEXT,                           -- bcrypt cost=12; nullable for future OAuth-only users (Story 2.3)
  email_verified_at TIMESTAMPTZ,                -- NULL until AC2 verify
  oauth_provider VARCHAR(50),                   -- google / github / null (Story 2.3 启用)
  oauth_subject VARCHAR(255),                   -- (Story 2.3 启用)
  locale VARCHAR(10) NOT NULL DEFAULT 'en',     -- en / zh-CN / ja / ... (与 Story 2.1 he_locale cookie 同集合)
  timezone VARCHAR(50) NOT NULL DEFAULT 'UTC',  -- (Story 2.5 资料管理时启用编辑)
  totp_secret_encrypted TEXT,                   -- (Story 2.4 启用)
  totp_enabled BOOLEAN NOT NULL DEFAULT FALSE,  -- (Story 2.4 启用) — 本 Story LoginUser 必须读取此字段以决定是否进入 2FA 分支
  status VARCHAR(20) NOT NULL DEFAULT 'active', -- active / locked / suspended / pending_deletion
  locked_until TIMESTAMPTZ,                     -- (Q5 待仲裁；sm_proposal=a 加此列 — 软锁自动解除时间戳)
  pending_deletion_at TIMESTAMPTZ,              -- (Story 2.7 启用)
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_oauth ON users(oauth_provider, oauth_subject) WHERE oauth_provider IS NOT NULL;
CREATE INDEX idx_users_status_locked ON users(status, locked_until) WHERE status = 'locked';
```

**设计决策 (WHY)**：
- **schema 与 data-models.md §4.1 完全对齐**：避免本 Story 与 architecture 文档 drift；§4.1 中 status enum 默认值在文档中是 `'active'`，本 Story 严格遵循
- **password_hash 可空**：为 Story 2.3 OAuth-only 用户预留（OAuth 注册时不设密码）；本 Story RegisterUser 总是设置 password_hash NOT NULL
- **totp_enabled 默认 FALSE**：Story 2.4 落地时启用编辑路径；本 Story LoginUser 读取此字段决定是否走 2FA 分支（hook 已就位但分支不触发）
- **locked_until 列（Q5 sm_proposal=a 待仲裁）**：用 TIMESTAMPTZ 单列承担软锁过期时间；UPDATE users SET status='locked', locked_until=NOW+1h；self-heal 在下次 signin 时执行 `WHERE status='locked' AND locked_until < NOW()` → UPDATE 回 'active'；无独立 cron job（per BR-3.3 / BR-4.4）
  - **若 Architect 否决 locked_until 列**：备选方案 → 锁定状态完全经 Redis（`auth:locked:{email_hash}` TTL=3600s）；优点：无需 schema 变更；缺点：PG users.status 与 Redis 状态可能短暂不一致（轻量；只有 Redis 启动时 user 已锁的场景）；SM 倾向 locked_until 列方案
- **idx_users_email**：email UNIQUE + 索引；signup 查询 + signin 查询全经此索引；查询计划 explain 应显示 Index Scan
- **idx_users_oauth (partial)**：仅 OAuth 用户启用；本 Story 索引提前落地但不使用，Story 2.3 启用
- **idx_users_status_locked (partial)**：用于 self-heal 路径快速查询所有需要解锁的 user（虽然 self-heal 是 per-request 而非 batch；保留为运维查询能力）

### Data Models

> 本 Story 引入 gRPC protobuf message + REST DTO + zod schema + Go struct 多层数据模型；详细列出。

**Protobuf Messages（packages/proto/he/auth/v1/auth.proto）**:

```protobuf
syntax = "proto3";
package he.auth.v1;

service AuthService {
  rpc RegisterUser(RegisterUserRequest) returns (RegisterUserResponse);
  rpc VerifyEmail(VerifyEmailRequest) returns (VerifyEmailResponse);
  rpc ResendVerification(ResendVerificationRequest) returns (ResendVerificationResponse);
  rpc LoginUser(LoginUserRequest) returns (LoginUserResponse);
  rpc RefreshToken(RefreshTokenRequest) returns (RefreshTokenResponse);
}

message RegisterUserRequest {
  string email = 1;
  string password = 2;        // 明文，仅在 in-RPC handler 内存内活
  string locale = 3;          // 缺省 'en'
  string client_ip = 4;       // 由 api-gateway 注入
  string user_agent = 5;
}

message RegisterUserResponse {
  string user_id = 1;
  string status = 2;          // 'pending_verification' | 'duplicate_attempt_silent'
}

message VerifyEmailRequest { string token = 1; string client_ip = 2; string user_agent = 3; }
message VerifyEmailResponse { string user_id = 1; google.protobuf.Timestamp email_verified_at = 2; bool already_verified = 3; }

message ResendVerificationRequest { string email = 1; string client_ip = 2; }
message ResendVerificationResponse { string status = 1; } // 通用成功响应（防枚举）

message LoginUserRequest {
  string email = 1;
  string password = 2;
  string client_ip = 3;
  string user_agent = 4;
}

message LoginUserResponse {
  enum Status { OK = 0; REQUIRES_2FA = 1; }
  Status status = 1;
  string access_token = 2;
  string refresh_token = 3;
  int32 expires_in = 4;
```
