### AC1: TOTP Enrollment (Init + Verify) — opt-in from Settings → Security

**Scenario**
```gherkin
GIVEN
  - User is authenticated (he_access cookie valid per Story 2.2 BR-3.7) AND `users.totp_enabled = FALSE`
  - User navigates to `/{locale}/(console)/settings/security` (P-11 Security sub-page per front-end-spec §P-11 line 543)
  - User has a TOTP authenticator app (Google Authenticator / Authy / 1Password / Microsoft Authenticator) ready
WHEN
  - User clicks "Enable two-factor authentication" CTA on Settings → Security
  - Console BFF Server Action `enrollTOTPInit({})` → POST `/v1/auth/2fa/enroll/init` (api-gateway, JWT-protected) → auth-svc gRPC `EnrollTOTPInit(user_id)`
  - User scans the displayed QR code with their authenticator app
  - User enters the first 6-digit code shown by their app
  - Console BFF Server Action `enrollTOTPVerify({code, ack_recovery_codes_saved: true})` → POST `/v1/auth/2fa/enroll/verify` → auth-svc gRPC `EnrollTOTPVerify(user_id, code, ack)`
THEN
  - auth-svc EnrollTOTPInit:
    - Generates 160-bit (20-byte) cryptographic random secret via `crypto/rand` (RFC 6238 / RFC 4226)
    - Generates 10 fresh recovery codes (10-char base32 each, ~50 bits entropy per code, ~500 bits aggregate)
    - Encrypts both secret and recovery-codes with KMS data key (envelope encryption per BR-5.2 / Architect Q1)
    - Stores encrypted blob in Redis key `auth:2fa:enroll:{user_id}` with TTL=600s (10-min enrollment window)
    - Returns `EnrollTOTPInitResponse{otpauth_uri, qr_code_png_base64, recovery_codes[10], expires_at}` — `recovery_codes` are returned in plaintext ONLY in this response (never re-exported)
    - Emits Kafka `audit.event` with `audit_event_type='2fa.enroll.initiated'`
  - auth-svc EnrollTOTPVerify:
    - Reads pending enrollment from Redis via GETDEL one-shot (`auth:2fa:enroll:{user_id}`); rejects if absent/expired (`409_enroll_expired`)
    - Validates submitted 6-digit code against the staged secret using ±1 30s window (RFC 6238 §5.2) and constant-time comparison (BR-5.5)
    - On success, in a single PG transaction:
      - `UPDATE users SET totp_secret_encrypted=$1, totp_enabled=TRUE, totp_enrolled_at=NOW(), updated_at=NOW() WHERE id=$user_id`
      - `INSERT INTO mfa_recovery_codes (id, user_id, code_hash, created_at) VALUES (...)` × 10 (bcrypt cost per Architect Q4)
    - On failure, increments `ratelimit:2fa:enroll:verify:{user_id}` (3/15min per BR-5.1); does NOT consume Redis pending key (allows retry within TTL window)
    - Emits Kafka `audit.event` with `audit_event_type='2fa.enrolled'` (success) or `'2fa.enroll.failed'` (failure)
    - notification-svc `SendEmail(template='2fa_enabled', to=user.email, vars={time, ip, ua_summary, locale})` — out-of-band security alert per BR-5.9
  - Console displays success toast + the recovery codes panel locks (no re-display); user must click "I have saved my recovery codes" checkbox (BR-1.7) before being routed back to Settings → Security with the section now showing the enrolled state (date + "Disable" + "Regenerate recovery codes" actions)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | Enrollment is opt-in — `users.totp_enabled` defaults to FALSE on registration (already wired by Story 2.2 migration `0002_create_users.sql`). This Story does NOT auto-prompt or force enrollment. |
| BR-1.2 | TOTP secret entropy: 160 bits (20 bytes), generated via `crypto/rand.Read` (Go) — NEVER `math/rand`. Per RFC 4226 §4 minimum, and matches Google Authenticator / Authy expected length. |
| BR-1.3 | `otpauth://` URI per RFC 6238 / KeyURI Format: `otpauth://totp/He-API:{user.email}?secret={base32}&issuer=He-API&algorithm=SHA1&digits=6&period=30`. Algorithm choice (SHA1 vs SHA256) is Architect Q3 — defaults to SHA1 for broadest authenticator compat unless Architect rules otherwise. |
| BR-1.4 | QR code: server-rendered PNG, base64-encoded into response. Resolution: 256×256, error-correction level Q. Avoid client-side QR libraries (XSS surface + bundle size). |
| BR-1.5 | Pending-enrollment storage: Redis `auth:2fa:enroll:{user_id}` carries the **KMS-encrypted** secret + recovery codes blob — never plaintext. TTL=600s. GETDEL on verify (one-shot, prevents replay/race). |
| BR-1.6 | Persist-to-PG happens ONLY after the user successfully validates one TOTP code. The "init" step writes to Redis only — this prevents partially-enrolled accounts (BR-1.6 prevents Story-2.5 / 2.6 GDPR-export from accidentally exfiltrating an unconfirmed secret). |
| BR-1.7 | UI MUST require the `ack_recovery_codes_saved: true` flag on verify — this is the explicit user acknowledgement that they have copied/printed/screenshot the 10 codes. Server rejects with `400_recovery_codes_not_acknowledged` if false. |
| BR-1.8 | Re-enrollment when `totp_enabled=TRUE` is forbidden — must Disable first (AC4). Init endpoint returns `409_already_enrolled` if user is already enrolled. |
| BR-1.9 | After verify, the 10 plaintext recovery codes are NEVER returned again — even regenerate (AC3) issues fresh codes and invalidates all prior. Lost codes + lost TOTP device = support-ticket support-driven recovery (out of scope for this Story; falls back to Story 2.7 account-deletion-with-recovery as last resort). |
| BR-1.10 | Audit event MUST include: `user_id`, `audit_event_type`, `client_ip_hash` (per Story 2.3 m-4 IPv4 /24 + IPv6 /64 prefix hash), `user_agent_hash` (sha256 full-string), `outcome`, `ts`. PII redaction: never log secret, otpauth_uri, recovery codes (BR-5.8). |
| BR-1.11 | Idempotency: If user races two "Enable 2FA" clicks, the second `EnrollTOTPInit` overwrites the Redis pending blob (re-issues fresh secret + codes). The user sees fresh QR; previous QR becomes invalid. No PG state mutation until verify. |
| BR-1.12 | Anti-enumeration: All error responses from `EnrollTOTPInit` / `EnrollTOTPVerify` use generic error codes — never leak whether a user_id exists (since the endpoint is JWT-protected, leakage surface is already minimal, but maintain parity with Story 2.2 BR-2.4). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `code` (verify) | string | yes | `^\d{6}$` (exactly 6 ASCII digits, leading zeros allowed) | `400_invalid_totp_format` — "TOTP code must be exactly 6 digits" |
| `ack_recovery_codes_saved` (verify) | bool | yes | must be `true` | `400_recovery_codes_not_acknowledged` — "Please confirm you have saved your recovery codes" |
| `user_id` (gRPC) | uuid | yes | matches JWT `sub` claim — api-gateway middleware enforces | `403_user_id_mismatch` (rejected at gateway) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| User already enrolled (totp_enabled=TRUE) | 409 `409_already_enrolled` | "Two-factor authentication is already enabled. Disable it first to re-enroll." | Surface as toast on Settings → Security; do NOT re-display QR |
| Pending Redis blob expired (>10min between init and verify) | 409 `409_enroll_expired` | "Enrollment window expired. Please restart enrollment." | Console resets wizard to Step 1, calls EnrollTOTPInit again |
| Invalid TOTP code | 400 `400_invalid_totp_code` | "Incorrect code. Please check your authenticator app and try again." | Increment `ratelimit:2fa:enroll:verify:{user_id}` counter; allow retry within TTL |
| Verify rate-limit exhausted (3 failures / 15min) | 429 `429_rate_limit_enroll` | "Too many failed attempts. Please wait and try again." | Include `Retry-After` header (seconds until counter expires) |
| KMS encryption failure | 503 `503_kms_unavailable` | "Service temporarily unavailable. Please try again." | Internal — alert ops; audit event `2fa.enroll.failed` with `failure_reason='kms_error'` |
| Missing/false `ack_recovery_codes_saved` | 400 `400_recovery_codes_not_acknowledged` | "You must acknowledge saving your recovery codes" | Console highlights checkbox + disables Submit until checked |

**UI Interaction**
| Trigger | Behavior |
|---------|----------|
| Click "Enable two-factor authentication" on Settings → Security | Open multi-step Modal: Step 1 (intro + "what you'll need" — authenticator app) → Step 2 (display QR + manual-entry fallback string + "I've added the account" CTA) → Step 3 (input 6-digit code + Verify) → Step 4 (display 10 recovery codes in a grid; "Copy all" + "Download .txt" + checkbox "I have saved my recovery codes") → Step 5 (success + Close) |
| Step 2: User clicks "Manual entry" toggle | Display base32-encoded secret in a copyable read-only input (for users who can't scan QR — e.g., copying into desktop authenticator) |
| Step 3: Auto-submit on 6th digit entered | Triggers verify; on success advances to Step 4, on failure clears input + shows error toast |
| Step 4: User attempts to close modal before checking the ack box | Show confirmation dialog "Recovery codes will not be shown again. Are you sure?" — if user confirms close anyway, the 2FA enrollment IS still active (codes are persisted PG-side); user just loses the plaintext display |
| Modal close via ESC / outside-click | Same confirmation as above |
| RTL locale (Arabic) | QR + 6-digit input + Step indicator are LTR within RTL container (per WCAG 2.1 SC 1.3.2 Meaningful Sequence) |

- **Input**: User on Settings → Security, totp_enabled=FALSE, clicks Enable → enters first 6-digit code "047281" from their Authenticator app, checks ack box, clicks Verify
  **Expected**: `users.totp_enabled=TRUE`, `users.totp_enrolled_at` populated, 10 rows in `mfa_recovery_codes`, success toast, Settings page re-renders showing enrolled state

### AC2: TOTP Login Challenge — covers both password path (Story 2.2) AND OAuth path (Story 2.3)

**Scenario**
```gherkin
GIVEN
  - User with `users.totp_enabled = TRUE` (enrolled via AC1)
  - User has NOT got a valid he_access cookie (or it expired)
WHEN — Path A (password login):
  - User submits {email, password} on `/{locale}/(auth)/signin` (Story 2.2)
  - Console BFF Server Action `signin({email, password})` → api-gateway POST `/v1/auth/signin` → auth-svc gRPC `LoginUser(email, password)`
WHEN — Path B (OAuth login):
  - User clicks "Continue with Google" or "Continue with GitHub" on `/{locale}/(auth)/signin` (Story 2.3)
  - Console BFF → api-gateway GET `/v1/auth/oauth/{provider}/initiate` → ... (full Story 2.3 flow) → callback → auth-svc gRPC `CompleteOAuth(...)`
THEN — auth-svc (both LoginUser and CompleteOAuth):
  - After password (Story 2.2) or OAuth identity (Story 2.3) is verified, checks `users.totp_enabled`:
    - If FALSE: proceed normally — issue access_token + refresh_token (Story 2.2 BR-3.7 cookie matrix, unchanged)
    - If TRUE: do NOT issue access/refresh tokens; instead issue an **mfa_token** (short-lived 5-min JWT, RS256-signed; claims: `sub={user_id}, purpose='2fa_challenge', login_method='password'|'oauth_google'|'oauth_github', client_ip_hash, user_agent_hash, jti={random_128bit}, iat, exp=iat+300, return_to`); write JTI to Redis `auth:2fa:challenge:{sha256(jti)}` with TTL=300s (single-use registry, BR-5.4)
  - LoginUser returns `LoginUserResponse{status='requires_2fa', mfa_token=...}` (the `status` enum was wired by Story 2.2 T0.1 — this Story implements the previously-stubbed branch)
  - CompleteOAuth returns `CompleteOAuthResponse{requires_2fa=TRUE, mfa_token=...}` (Story 2.3 already returned `Requires_2Fa=true` without an mfa_token — this Story fills the mfa_token issuance)
THEN — api-gateway:
  - Translates gRPC response → HTTP 200 + sets `he_mfa` cookie (value=mfa_token, Path=/v1/auth/2fa, HttpOnly, Secure, SameSite=Lax, Max-Age=300, Domain=console.he-api.com)
  - For password path: returns JSON `{status:'requires_2fa'}` body → Console Server Action redirects to `/{locale}/2fa-challenge?return_to={return_to}`
  - For OAuth path: 302 to `/{locale}/2fa-challenge?return_to={stored.return_to}` (replaces the placeholder redirect that Story 2.3 T1.9 wired)
THEN — User on `/{locale}/2fa-challenge`:
  - Page reads `he_mfa` cookie server-side (Next.js Server Component); if absent or expired → 302 to `/{locale}/(auth)/signin?error=session_expired`
  - User enters 6-digit code from authenticator app
  - Console Server Action `submitChallenge({code})` → api-gateway POST `/v1/auth/2fa/challenge` (carries `he_mfa` cookie) → auth-svc gRPC `ChallengeTOTP(mfa_token, code, client_ip, user_agent)`
THEN — auth-svc ChallengeTOTP:
  - Validates `mfa_token` JWT signature (RS256 with same JWKS as access_token, or separate key per Architect Q2)
  - Validates JTI present in Redis `auth:2fa:challenge:{sha256(jti)}` (NOT a GETDEL on the first read — allows retries within mfa_token lifetime; DEL is performed AFTER successful code validation, OR on `ratelimit:2fa:challenge:{user_id}` exhaustion)
  - Validates `client_ip_hash` and `user_agent_hash` claims match current request (BR-5.4, parallel to Story 2.3 OAuth state binding) — mismatch → reject `401_mfa_token_binding_mismatch`
  - KMS-decrypts `users.totp_secret_encrypted`
  - Validates 6-digit code against TOTP secret with ±1 30s window (RFC 6238 §5.2) using constant-time compare (BR-5.5)
  - On success:
    - DELETEs JTI from Redis (consumes single-use mfa_token)
    - `UPDATE users SET totp_last_used_at=NOW() WHERE id=$user_id`
    - Issues access_token + refresh_token (per Story 2.2 BR-3.7 cookie matrix) — INCLUDING `aal=2` claim (Authentication Assurance Level 2 per NIST SP 800-63B §4) so downstream services know this session passed 2FA
    - Returns `ChallengeTOTPResponse{access_token, refresh_token, expires_in=900, aal=2}`
    - Emits Kafka `audit.event` `2fa.challenge.success`
  - On failure:
    - Increments `ratelimit:2fa:challenge:{user_id}` (5/15min per BR-5.1 — matches Story 2.2 signin lockout threshold)
    - Does NOT consume JTI yet (allow retry within mfa_token's 5-min lifetime, up to ratelimit ceiling)
    - On 5th failure: DELETE JTI + `UPDATE users SET status='locked', locked_until=NOW+1h` (reuses Story 2.2 BR-3.3 soft-lock with self-heal) + Kafka `audit.event` `2fa.challenge.locked`
    - Returns `401_invalid_totp_code` (generic — does not distinguish wrong-code vs locked vs other failure to prevent enumeration)
THEN — api-gateway on success:
  - Sets `he_access` + `he_refresh` cookies per Story 2.2 cookie matrix; clears `he_mfa` cookie (Max-Age=0)
  - 200 JSON `{status:'ok'}` for password path → Console redirects to `return_to`
  - 302 to `return_to` for OAuth path
```

| ID | Rule |
|----|------|
| BR-2.1 | `mfa_token` lifetime = 300s (5min). This is a hard cap — even if user is slow to read code, they must complete within 5min or restart signin. Mirrors short-lived OTP industry norm (Microsoft / Google ~5min). |
| BR-2.2 | `mfa_token` JTI is **single-use after success**: Redis DELETE happens AFTER the code is validated and tokens are issued — this prevents replay of the same `mfa_token` to mint multiple sessions. |
| BR-2.3 | `mfa_token` binding: signed claims include `client_ip_hash` + `user_agent_hash` (computed via Story 2.3 m-4 helpers `HashClientIP` /24 + `HashUserAgent` sha256). Mismatch on challenge → 401 (prevents stolen `he_mfa` cookie from being used elsewhere). |
| BR-2.4 | TOTP validation window: ±1 30s period (i.e., current period plus previous and next). RFC 6238 §5.2 recommendation balances clock drift vs replay window. |
| BR-2.5 | Constant-time comparison: use `crypto/subtle.ConstantTimeCompare` for all 6-digit code matching to defeat timing oracles (BR-5.5). |
| BR-2.6 | Rate limit: `ratelimit:2fa:challenge:{user_id}` Redis counter, 5 failures/15min → soft-lock `users.status='locked' + locked_until=NOW+1h` (reuses Story 2.2 BR-3.3 framework). Self-heal on next signin attempt when `NOW > locked_until`. |
| BR-2.7 | If `users.status='locked' AND locked_until > NOW()` is detected BEFORE the 2FA branch is reached (i.e., during password verify or OAuth identity load), return `423_account_locked` with `Retry-After` — do NOT issue an mfa_token, do NOT reveal whether 2FA was about to be required (BR-5.10). |
| BR-2.8 | AAL2 claim: issued access_token MUST carry `aal=2` claim — downstream services (billing-svc / payment-svc / GDPR delete flow in Story 2.7) can require `aal>=2` for sensitive operations. Stories 2.5/2.7 are responsible for enforcing; this Story is responsible for issuing. |
| BR-2.9 | OAuth path: when CompleteOAuth determines `requires_2fa=TRUE`, the OAuth state cookie `he_oauth_state` from Story 2.3 is consumed (GETDEL of `auth:oauth:state:{sha256(state_id)}`) BEFORE issuing the mfa_token — this prevents an attacker from using a leaked OAuth state to bypass 2FA. State is consumed; the new mfa_token is the only path forward. |
| BR-2.10 | After successful challenge, `return_to` MUST be revalidated against the same allow-list used by Story 2.3 BR-1.5 (open-redirect protection). |
| BR-2.11 | OAuth account-linking (Story 2.3 LinkOutcome enum) decisions happen BEFORE the 2FA branch — i.e., if linking decision branches to `LINKED_NEW_OAUTH_IDENTITY` or `MERGED_EXISTING_USER`, the 2FA check still applies. There is no "trusted device" or "first-time-OAuth bypass". |
| BR-2.12 | If a user is `totp_enabled=FALSE` but a stale `he_mfa` cookie is present (impossible legitimate scenario — but defensive), the challenge endpoint rejects with `401_mfa_token_invalid` (since their user record has no secret to decrypt). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `code` (challenge) | string | yes | `^\d{6}$` | `400_invalid_totp_format` |
| `mfa_token` (he_mfa cookie) | JWT (RS256) | yes | Signature valid + `exp > NOW` + JTI exists in Redis + `purpose='2fa_challenge'` claim | `401_mfa_token_invalid` (generic) |
| `client_ip_hash` (computed) | string | yes | Matches token claim | `401_mfa_token_binding_mismatch` |
| `user_agent_hash` (computed) | string | yes | Matches token claim | `401_mfa_token_binding_mismatch` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| `mfa_token` expired / JTI not in Redis | 401 `401_mfa_token_invalid` | "Your verification session has expired. Please sign in again." | Clear `he_mfa` cookie; redirect to `/(auth)/signin` |
| IP/UA binding mismatch | 401 `401_mfa_token_binding_mismatch` | "Your verification session has expired. Please sign in again." | Same as above — but emit `2fa.challenge.binding_failed` audit event (security alert) |
| Invalid 6-digit code | 401 `401_invalid_totp_code` | "Incorrect code. Please try again." | Increment counter; allow retry within mfa_token TTL |
| Rate limit (5 failures / 15min) | 423 `423_account_locked` | "Too many failed attempts. Your account is temporarily locked." | Include `Retry-After` (seconds); clear `he_mfa` cookie; user must wait or pass through self-heal at next signin |
| Account already locked (BR-2.7) | 423 `423_account_locked` | "Account is temporarily locked. Please try again later." | Returned BEFORE 2FA branch — Story 2.2 BR-3.3 path |

**UI Interaction**
| Trigger | Behavior |
|---------|----------|

### AC3: Recovery Codes (One-time backup factor)

**Scenario**
```gherkin
GIVEN
  - User completed AC1 enrollment (has 10 unused rows in `mfa_recovery_codes` for their `user_id`)
  - User has lost access to their TOTP device (phone broken / lost / authenticator app reset)
  - User has the printed/saved 10 recovery codes from enrollment
WHEN — User Path (Use a code):
  - User is on `/{locale}/2fa-challenge` (after submitting password or OAuth) — clicks "Use a recovery code instead" link
  - Toggles to alternate input panel (single long-text input)
  - Enters one of their saved recovery codes (10-char base32, may include human-readable hyphen formatting like "ABCD-EFGH-J2" which UI strips)
  - Console BFF Server Action `submitRecoveryCode({code})` → POST `/v1/auth/2fa/recovery` → auth-svc gRPC `UseRecoveryCode(mfa_token, code, client_ip, user_agent)`
THEN — auth-svc UseRecoveryCode:
  - Validates `mfa_token` same as AC2 (signature + JTI + IP/UA binding)
  - Normalizes input: uppercase + strip non-alphanumeric → 10-char base32
  - Fetches ALL unused rows: `SELECT id, code_hash FROM mfa_recovery_codes WHERE user_id=$1 AND used_at IS NULL FOR UPDATE`
  - For each row: bcrypt-compare normalized input vs `code_hash`; on match capture `row_id`
  - If a match was found AND row count of "row to mark used" is exactly 1 after atomic:
    - `UPDATE mfa_recovery_codes SET used_at=NOW(), used_from_ip_hash=$2, used_from_ua_hash=$3 WHERE id=$row_id AND used_at IS NULL` (returning row count; race-protection — if another concurrent challenge already used it, returns 0)
    - Commits transaction
  - Counts remaining unused codes: `SELECT count(*) FROM mfa_recovery_codes WHERE user_id=$1 AND used_at IS NULL`
  - On success:
    - Issues access + refresh tokens (same as AC2)
    - Returns `UseRecoveryCodeResponse{access_token, refresh_token, expires_in=900, aal=2, recovery_codes_remaining=N, recovery_codes_low=N<=3}`
    - DELETE JTI from Redis (single-use)
    - Kafka audit `2fa.recovery.used` with `remaining_count`
    - notification-svc `SendEmail(template='2fa_recovery_used', to=user.email, vars={time, ip, remaining_count, locale})` — out-of-band alert (per BR-5.9 — every recovery use is a security event)
  - On failure (code didn't match any unused row):
    - Increments `ratelimit:2fa:recovery:{user_id}` (3 failures/15min per BR-5.1 — stricter than TOTP because codes are lower entropy)
    - Does NOT consume JTI
    - Returns `401_invalid_recovery_code` (generic; constant-time comparison BR-5.5)
WHEN — User Path (Regenerate codes from Settings):
  - User authenticated (he_access valid + aal=2) navigates to Settings → Security → "Regenerate recovery codes"
  - Modal asks for re-verification: either current TOTP code OR password (defense-in-depth even with valid session)
  - User submits → Server Action `regenerateRecoveryCodes({verification_factor, value})` → POST `/v1/auth/2fa/recovery-codes/regenerate` → auth-svc gRPC `RegenerateRecoveryCodes(user_id, factor, value)`
THEN — auth-svc RegenerateRecoveryCodes:
  - Verifies factor: TOTP code (decrypt secret + validate ±1 window) OR password (bcrypt compare)
  - On success, in a single PG transaction:
    - `UPDATE mfa_recovery_codes SET used_at=NOW(), used_from_ip_hash=$, used_from_ua_hash=$, regenerated_at=NOW(), regenerated_reason='user_initiated' WHERE user_id=$1 AND used_at IS NULL` (mark all current codes as consumed for audit; do NOT physically delete to preserve forensic trail)
    - `INSERT INTO mfa_recovery_codes (id, user_id, code_hash, created_at) VALUES (...)` × 10 fresh codes
  - Returns `RegenerateRecoveryCodesResponse{recovery_codes[10]}` — plaintext ONCE
  - Kafka audit `2fa.recovery.regenerated` with `previous_unused_count`, `regeneration_reason='user_initiated'`
  - notification-svc `SendEmail(template='2fa_recovery_regenerated', to=user.email, vars={time, ip, locale})` — out-of-band alert
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | Recovery code format: 10 chars, base32 alphabet (Crockford or RFC 4648 — Architect Q3 may rule, defaults to RFC 4648 to match TOTP secret encoding). Entropy ≈ 50 bits per code, ≈ 500 bits per set of 10. |
| BR-3.2 | Recovery codes are bcrypt-hashed at rest (Architect Q4: cost 12 to match password — codes are higher entropy than passwords so cost-12 is conservative; alternative argon2id deferred). Plaintext is RETURNED ONLY ONCE (during AC1 enrollment or AC3 regeneration). |
| BR-3.3 | Single-use: atomic `UPDATE ... WHERE id=$row_id AND used_at IS NULL` with row-count check prevents two concurrent challenges from using the same code (race condition). |
| BR-3.4 | Display format: codes are displayed in groups of 4-3-3 (e.g., "ABCD-EFGH-J2K") for human readability. Validation strips non-alphanumeric — users can type with or without hyphens. |
| BR-3.5 | Regeneration: marks all unused codes as `used_at=NOW(), regenerated_reason='user_initiated'` (preserves forensic trail) and issues 10 fresh codes. Previously-used codes are NOT touched. |
| BR-3.6 | Rate limit: `ratelimit:2fa:recovery:{user_id}` = 3 failures/15min → 423 lock (stricter than TOTP because each guess is more valuable to attacker — 1 in 2^50 vs 1 in 10^6). |
| BR-3.7 | Low-codes warning: if `count(unused) <= 3` after a successful use, UI shows persistent banner on dashboard "Only X recovery codes remaining — regenerate now". This banner persists until user regenerates or dismisses. |
| BR-3.8 | Recovery use ALWAYS sends an out-of-band email (no opt-out). This is a deviation from normal-login emails (which are NOT sent per industry norm) — recovery code use is a higher-severity event. |
| BR-3.9 | After AC4 (Disable 2FA), all `mfa_recovery_codes` rows for the user are physically deleted (not just marked used) — clean slate for re-enrollment. |
| BR-3.10 | If all 10 codes are used and TOTP device is also unavailable: user is locked out → falls back to support-ticket-driven account recovery (Story 2.7 account-deletion-with-recovery is the last-resort path; out of scope for this Story). Console displays an info banner once `count(unused) = 0`: "You have used all recovery codes. Regenerate now while you can still sign in." |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `code` (use) | string | yes | After strip-non-alphanumeric and uppercase: exactly 10 chars matching `^[A-Z2-7]{10}$` (RFC 4648 base32 alphabet) | `400_invalid_recovery_code_format` |
| `verification_factor` (regenerate) | enum | yes | `'totp_code'` \| `'password'` | `400_invalid_factor` |
| `value` (regenerate) | string | yes | 6-digit TOTP OR plaintext password | factor-specific error |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Recovery code didn't match any unused row | 401 `401_invalid_recovery_code` | "Invalid recovery code. Please check and try again." | Counter increments; constant-time comparison ensured |
| Rate limit exhausted (3/15min) | 423 `423_account_locked` | "Too many failed attempts. Account locked." | Same lockout path as BR-2.6 |
| Regenerate with wrong TOTP code | 401 `401_invalid_totp_code` | "Incorrect code." | Counter increments per AC2 rate limit |
| Regenerate with wrong password | 401 `401_invalid_credentials` | "Incorrect password." | Counter increments per Story 2.2 BR-3.3 signin lockout (shared counter) |
| User has 0 unused codes left | 410 `410_no_recovery_codes` | "All recovery codes have been used. Please regenerate or contact support." | Specific error to differentiate from "code wrong" — only when listing returns empty before any comparison |

**UI Interaction**
| Trigger | Behavior |
|---------|----------|
| Click "Use a recovery code instead" on `/2fa-challenge` | Toggle from 6-digit input to long-text input + hint "Enter one of your saved recovery codes (10 characters, may include hyphens)" |
| Input auto-formats | As user types, strip non-alphanumeric, uppercase, then re-insert hyphens at positions 4 and 7 for readability |
| Successful recovery + remaining <=3 | After redirect to dashboard, show persistent yellow banner "You have N recovery codes left. [Regenerate now →]" |
| Settings → Security shows "X recovery codes remaining" | If <=3: text turns yellow + "Regenerate" button is visually emphasized |
| Regenerate modal | Two tabs: "TOTP code" (default if user has device) / "Password" (fallback); after success, display new 10 codes with same Copy/Download/Ack-checkbox pattern as AC1 Step 4 |

**Examples**
- **Input**: User enters recovery code "ABCD-EFGH-J2" (with hyphens) when 10 codes are unused
  **Expected**: Strip hyphens → "ABCDEFGHJ2" → bcrypt-match against 10 rows → match found at row 3 → atomic mark used → access + refresh tokens issued (aal=2) → `recovery_codes_remaining=9` → success
- **Input**: Attacker races two concurrent recovery code submissions with the same code
  **Expected**: First wins (row marked used); second `UPDATE ... WHERE used_at IS NULL` returns 0 rows → treated as no-match → counter increments
- **Input**: User regenerates codes; clicks Regenerate again immediately
  **Expected**: Old codes (just-regenerated set) are marked used + 10 brand-new codes issued; audit event emitted; old plaintext is irretrievable

### AC4: 2FA Disable (Requires Re-Authentication)

**Scenario**
```gherkin
GIVEN
  - Authenticated user (he_access valid + aal=2) with `users.totp_enabled = TRUE`
  - User navigates to `/{locale}/(console)/settings/security`
WHEN
  - User clicks "Disable two-factor authentication" CTA
  - Confirmation modal opens, asking for re-authentication via EITHER:
    - Current 6-digit TOTP code, OR
    - Current password (in case user has lost device but still has session via "remember me" or recovery-code login)
  - User submits → Server Action `disable2FA({verification_factor: 'totp'|'password', value})` → POST `/v1/auth/2fa/disable` (api-gateway, JWT-protected with aal=2 requirement) → auth-svc gRPC `DisableTOTP(user_id, factor, value, client_ip, user_agent)`
THEN — auth-svc DisableTOTP:
  - Re-verifies user JWT carries `aal=2` (this Story's gateway middleware enforces — drops to 403 if `aal=1`)
  - Validates the submitted factor:
    - factor='totp': KMS-decrypt `users.totp_secret_encrypted` + RFC 6238 validate ±1 window
    - factor='password': bcrypt-compare against `users.password_hash` (Story 2.2 BR-3.x)
  - Enforces rate-limit `ratelimit:2fa:disable:{user_id}` = 3 failures/hour (BR-4.4); on exhaustion → 423 lock (1h)
  - On success, in a single PG transaction:
    - `UPDATE users SET totp_enabled=FALSE, totp_secret_encrypted=NULL, totp_enrolled_at=NULL, totp_last_used_at=NULL, updated_at=NOW() WHERE id=$user_id`
    - `DELETE FROM mfa_recovery_codes WHERE user_id=$user_id` (physical delete per BR-3.9 — clean slate)
  - Emits Kafka `audit.event` with `audit_event_type='2fa.disabled'` and **severity=HIGH** (security downgrade)
  - notification-svc `SendEmail(template='2fa_disabled', to=user.email, vars={time, ip_summary, ua_summary, locale, disable_method: 'totp'|'password'})` — out-of-band alert per BR-5.9 / OWASP ASVS L2 §6.5
  - Returns `DisableTOTPResponse{ok=true}`
THEN — Console:
  - Modal shows success toast
  - Settings → Security re-renders with the "Enable 2FA" CTA visible again (totp_enabled=FALSE state)
  - Dashboard does NOT show 2FA-related banners
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | Disable requires `aal=2` session — i.e., the user MUST have completed 2FA challenge during this session (or recovery code use). A user who is only `aal=1` (somehow) cannot disable 2FA. This blocks the trivial attack "stolen cookie disables defender's 2FA". |
| BR-4.2 | Even with `aal=2`, the modal STILL requires re-verification (TOTP code or password). This is defense-in-depth — the JWT could have been issued legitimately at signin time but the session is now hijacked. |
| BR-4.3 | TOTP secret is set to NULL (not retained for "easy re-enable") — re-enabling requires fresh enrollment (new secret, new recovery codes). Per zero-secret-retention principle in security.md §8.1. |
| BR-4.4 | Rate limit `ratelimit:2fa:disable:{user_id}` = 3 failures/hour → 423 lock 1h (BR-2.6 reuse). |
| BR-4.5 | Disable emits an out-of-band email NOT just to the current email — also to any historical recovery email if set (Story 2.5 may introduce alternate email; this Story sends only to the canonical `users.email`). |
| BR-4.6 | If the user has active console sessions on other devices, their access_token is NOT immediately revoked (would be a heavy ops choice). The `aal=2` claim in older tokens remains valid until their natural 15-min expiry; refresh_token rotation will then yield new tokens at `aal=1` (since 2FA is disabled). Stories 2.5 / Active sessions management may add explicit "sign out all" — out of scope here. |
| BR-4.7 | The 2FA disable audit event is HIGH severity — audit-svc routes to ops alerting (per data-models.md §4.4 `audit.event` Kafka topic; severity classification is Architect Q5 follow-up). |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| `verification_factor` | enum | yes | `'totp'` \| `'password'` | `400_invalid_factor` |
| `value` (factor='totp') | string | yes | `^\d{6}$` | `400_invalid_totp_format` |
| `value` (factor='password') | string | yes | non-empty, min 1 char (we don't validate password complexity here — Story 2.2 already verified the stored hash) | `400_invalid_password_format` |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Session `aal=1` (no 2FA in current session) | 403 `403_aal2_required` | "Please sign out and sign in with two-factor authentication to disable 2FA." | Modal closes; toast directs user to re-signin |
| Wrong TOTP code | 401 `401_invalid_totp_code` | "Incorrect code." | Counter increments |

### AC5: Security & Rate Limiting (Cross-Cutting)

**Scenario**
```gherkin
GIVEN AC1-AC4 are implemented
WHEN any 2FA endpoint is invoked
THEN — Rate limits enforced (Redis):
  - `ratelimit:2fa:enroll:init:{user_id}` = 3/hour — prevents QR-DoS / KMS-call-floods
  - `ratelimit:2fa:enroll:verify:{user_id}` = 3 failures/15min — prevents brute force of the 6-digit code window during enrollment
  - `ratelimit:2fa:challenge:{user_id}` = 5 failures/15min → soft-lock 1h (BR-2.6 — reuses Story 2.2 BR-3.3)
  - `ratelimit:2fa:recovery:{user_id}` = 3 failures/15min → soft-lock 1h (BR-3.6 — stricter; codes are weaker entropy)
  - `ratelimit:2fa:disable:{user_id}` = 3 failures/hour → soft-lock 1h (BR-4.4)
  - All counters use Redis INCR + EXPIRE pattern (Story 2.2 ratelimit framework reuse)
AND — KMS envelope encryption:
  - TOTP secret persisted to `users.totp_secret_encrypted` is wrapped with a KMS data key (Architect Q1 — likely K8s Secret bootstrap path mirroring Story 2.3 Q5 ruling "Vault deferred")
  - Recovery code plaintext NEVER persists; only bcrypt hashes
AND — Audit logging (Kafka `audit.event` topic, schema per data-models.md §4.4):
  - `2fa.enroll.initiated` (LOW severity)
  - `2fa.enrolled` (MEDIUM)
  - `2fa.enroll.failed` (LOW)
  - `2fa.challenge.success` (LOW)
  - `2fa.challenge.failed` (LOW)
  - `2fa.challenge.locked` (HIGH — possible attack)
  - `2fa.challenge.binding_failed` (HIGH — possible cookie theft)
  - `2fa.recovery.used` (HIGH — out-of-band event)
  - `2fa.recovery.regenerated` (MEDIUM)
  - `2fa.disabled` (HIGH — security downgrade)
AND — PII redaction in structured logs (slog JSON via packages/go-observability):
  - NEVER log: secret (encrypted or plaintext), otpauth_uri, recovery codes (plaintext), mfa_token full value, password
  - Log: user_id (UUID), audit_event_type, outcome, client_ip_hash (NOT raw IP), ua_hash (NOT raw UA), ts, http_status
AND — Constant-time comparison:
  - All 6-digit code matching (`crypto/subtle.ConstantTimeCompare`)
  - All bcrypt comparisons are constant-time by design
AND — Out-of-band email alerts (notification-svc gRPC SendEmail):
  - On `2fa.enrolled` (welcome + security context)
  - On `2fa.recovery.used` (every use)
  - On `2fa.recovery.regenerated`
  - On `2fa.disabled` (HIGH severity)
  - NOT on `2fa.challenge.success` — too noisy; users expect normal login
AND — OWASP ASVS L2 §6 / NIST SP 800-63B AAL2 compliance verified by final-verify CI workflow
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-5.1 | All rate limits in Redis; key naming `ratelimit:2fa:{operation}:{user_id}` (or `:ip_hash}` for unauth-pre-2fa). Counter TTL matches the window (15min / 1hour). |
| BR-5.2 | KMS envelope encryption: TOTP secret is encrypted by a per-secret data-encryption-key (DEK) which is itself wrapped by a master KMS key. Bootstrap path (Architect Q1): K8s Secret holds master AES-256-GCM key; production target = Aliyun KMS or Vault Transit (decision deferred but interface MUST abstract via `internal/kms/`). |
| BR-5.3 | Per-secret nonces: AES-256-GCM nonce is 96-bit crypto/rand per encrypt call; stored alongside ciphertext (length-prefixed binary blob → base64-encoded TEXT in PG). NEVER reuse nonce with same key. |
| BR-5.4 | `mfa_token` JTI registry: Redis key `auth:2fa:challenge:{sha256(jti)}` (hashed-key pattern per data-models.md §4.3 convention). Stores `{user_id, expires_at, attempt_count}`. TTL=300s matching JWT expiry. |
| BR-5.5 | Constant-time comparison for all secret/code matching. Avoid early-return bugs that leak length or prefix-match timing. |
| BR-5.6 | RFC 6238 §5.2 anti-drift window: ±1 30s period (i.e., 3 windows total: previous, current, next). Step T - 1, T, T + 1 all valid. |

### Technical Constraints

- **TOTP standards**: RFC 6238 (Time-based One-Time Password) + RFC 4226 (HOTP underlying). Default algorithm SHA1 / 6 digits / 30s period for broadest authenticator-app compatibility (Architect Q3 may override). [→ packages/proto/he/auth/v1/auth.proto extension; T0.1]
- **Cryptography**: `crypto/rand` for all randomness (NEVER `math/rand`). `crypto/subtle.ConstantTimeCompare` for all secret/code comparison. AES-256-GCM for envelope encryption with 96-bit nonce. [Source: docs/architecture/coding-standards.md §12.3 line 28 "所有 PII 在日志输出前脱敏" + §12.1 line 6 "禁用 panic 在业务路径"]
- **KMS bootstrap path**: K8s Secret–delivered master key + per-secret AES-256-GCM nonce; production target is Architect Q1 (Aliyun KMS vs Vault Transit). Abstraction `internal/kms/` MUST allow zero-downtime swap. [Source: docs/architecture/tech-stack.md §2.1 line 40 "密钥管理 HashiCorp Vault" — Vault deferred per Story 2.3 Q5 ruling; Story 2.4 continues bootstrap path]
- **Performance budget**: Each 2FA endpoint p95 latency ≤ 200ms (includes KMS decrypt round-trip). KMS decrypt should be cached per-request (single decrypt per challenge) but NEVER cached cross-request (defeats the purpose of envelope encryption). [Source: docs/architecture/10-性能与可扩展性performance-scalability.md §10.1]
- **AAL2 compliance**: NIST SP 800-63B §4 Authentication Assurance Level 2 — issued access_token after 2FA challenge MUST carry `aal=2` claim. Downstream services consuming JWT can require `aal>=2` for sensitive ops. [Source: rest-api-spec.md §5.2 + security.md §8.1]
- **Constant-time bcrypt**: `golang.org/x/crypto/bcrypt` is constant-time by design. Recovery code bcrypt cost target = same as password (12) per BR-3.2 / Architect Q4.
- **mfa_token lifetime**: Hard 300s (5min). NO extending or refreshing; expiry = restart signin from scratch. [BR-2.1]
- **Replay protection**: Redis JTI registry `auth:2fa:challenge:{sha256(jti)}` — single-use after successful validation (BR-5.11). Failed validations do NOT consume JTI (allow retry within mfa_token TTL up to ratelimit ceiling).
- **No backwards-compat shims**: Story 2.2 wired `LoginUserResponse.status='requires_2fa'` enum as a stub (asserting it was never reached). This Story implements that branch — DELETE the stub assertion in 2.2 tests; do NOT leave a behind-compatibility flag. [Source: docs/stories/2.2-email-signup-password-login-email-verification.md task T0.1 + LoginStatus enum]
- **Service boundaries**: All 2FA business logic lives in auth-svc. api-gateway is a thin reverse-proxy + cookie translator only. console BFF is a thin Server Action wrapper. NO secrets / KMS / TOTP logic at the gateway or console layer. [Source: docs/architecture/3-服务拓扑service-topology.md §3.1 line 8 "auth-svc: 2FA、Key 管理"]
- **Audit topology**: All 2FA state changes → Kafka topic `audit.event` (per data-models.md §4.4) → audit-svc → ClickHouse. Story 2.2 P5 wired the Kafka publisher; this Story extends event taxonomy with 10 new types. [Source: docs/architecture/data-models.md §4.4]

### Database Design

- **NO new tables on `users`** — the `totp_secret_encrypted` + `totp_enabled` columns landed in Story 2.2 migration `0002_create_users.sql` (data-models.md §4.1 lines 16-17 anticipated this Story).
- **2 new columns on `users` via ALTER**: `totp_enrolled_at TIMESTAMPTZ`, `totp_last_used_at TIMESTAMPTZ`. Both nullable; populated by AC1 (enroll) and AC2 (challenge success).
- **1 new table**: `mfa_recovery_codes` per T0.3. Design decisions:
  - **FK ON DELETE CASCADE** — when a user is deleted (Story 2.7), recovery codes cascade. No orphans.
  - **Partial index** `idx_mfa_recovery_user_unused ON (user_id) WHERE used_at IS NULL` — only 10 rows × N users per index; massively smaller than full index; query pattern is always "list unused for this user".
  - **bcrypt-hashed codes**: code plaintext NEVER persists. Cost per Architect Q4 (default 12).
  - **Forensic trail**: `used_at` + `used_from_ip_hash` + `used_from_ua_hash` + `regenerated_at` + `regenerated_reason` retained even when used. Physical delete only on Disable (BR-3.9).
  - **No `code_id` user-facing identifier** — codes are identified by their hash match, not by lookup-by-id. Defense against partial-info leakage.

### Open Architect Questions (5)

> SM has proposals (sm_proposal); Architect rules in Round 1 review. Each Q materially shapes implementation — Dev should NOT begin AC implementation until rulings land.

**Q1: KMS bootstrap path for `users.totp_secret_encrypted` envelope encryption**

- Options:
  - (a) **K8s Secret–delivered master key + per-secret AES-256-GCM nonce** (bootstrap, mirrors Story 2.3 Q5 ruling for OAuth client secrets — "K8s Secret 沿用，Vault deferred")
  - (b) **Aliyun KMS direct** (cloud-managed; key rotation handled by Aliyun console; integration cost = Aliyun SDK + IAM RAM policy)
  - (c) **HashiCorp Vault Transit secrets engine** (Vault unified path per tech-stack.md §2.1 line 40 — defers to Vault infra not yet deployed)
- **sm_proposal**: (a) K8s Secret bootstrap matching Story 2.3 Q5 ruling rationale — "Vault deferred + cloud-KMS direct integration introduces secondary infra dependency outside current Epic 2 scope; AES-256-GCM with K8s Secret–delivered master key is cryptographically equivalent given strict per-secret nonce handling (NIST SP 800-38D)". Production target = Vault Transit (post-Epic 2 follow-up). Risk: master key rotation requires re-encrypting all `users.totp_secret_encrypted` rows (manageable via DBA script; documented as runbook).
- **Impact**: Affects `internal/kms/` abstraction shape (T0.4); affects `infra/helm/auth-svc/values.yaml` env vars; affects KMS-error error code (`503_kms_unavailable` may be `404_kms_key_missing` if K8s Secret missing on rotation; semantic differs).

**Q2: `mfa_token` signing-key strategy**

- Options:
  - (a) **Separate RS256 keypair for mfa_token** (rotation-independent from access_token RS256 keypair; lower blast radius if access_token key leaks)
  - (b) **Reuse main access_token RS256 keypair**, discriminated by `purpose='2fa_challenge'` claim (single keypair; smaller ops surface; aligned with Story 2.2 JWKS endpoint design)
- **sm_proposal**: (b) Reuse keypair + `purpose` discrimination — Story 2.2 JWKS endpoint `/.well-known/jwks.json` already publishes the keys at api-gateway; introducing a second key mechanism doubles JWKS rotation operational complexity. The 5-min TTL + JTI single-use + ip/ua binding (BR-2.3) provide sufficient defense-in-depth without separate key. Constraint: `internal/jwt/` MUST validate `purpose` claim — accepting an access_token where mfa_token is expected (or vice versa) is a defect.
- **Impact**: Affects T0.7 jwt.IssueMFAToken signing call; affects T2.4 ChallengeTOTP `ParseMFAToken` strict purpose-claim check.

**Q3: TOTP HMAC algorithm + recovery-code base32 alphabet**

- Options (algo):
  - (a) **SHA1** (RFC 6238 default; Google Authenticator / Authy / Microsoft Authenticator universal compat)
  - (b) **SHA256** (some authenticators support; ~50% support gap in older apps)
  - (c) **SHA512** (rarely supported)
- Options (recovery-code alphabet):
  - (i) **RFC 4648 base32** (`A-Z2-7` — most common; matches TOTP secret encoding)
  - (ii) **Crockford base32** (`0-9A-HJKMNPQRTV-Z` — human-friendly: avoids I/L/O/U; common in API keys / order numbers)
- **sm_proposal**: algo=(a) SHA1 — universal authenticator compat dominates; security gap between SHA1-HMAC and SHA256-HMAC in this context is negligible (RFC 6238 §3 explicit). alphabet=(i) RFC 4648 — matches TOTP secret encoding throughout the codebase (single base32 implementation), avoid confusion of two alphabets.
- **Impact**: Affects T0.5 otpauth URI `algorithm=SHA1` param; affects T0.6 base32 alphabet constant.

**Q4: Recovery code bcrypt cost**

- Options:
  - (a) **cost=12** (matches password per Story 2.2; conservative)
  - (b) **cost=10** (recovery codes are ~50-bit entropy vs password's ~30-bit average; lower cost acceptable; faster bulk-insert during enrollment + faster bulk-compare during use)
  - (c) **argon2id (memory-hard)** (uniform with future password migration to argon2id)
- **sm_proposal**: (a) cost=12 — uniform crypto policy with password (Story 2.2 BR-3.x); the 10-row bulk-compare during recovery use is bounded (10 bcrypt-compares × cost=12 ≈ 250ms — well within 200ms p95 budget if parallelized; serial is borderline → use `errgroup` to parallelize per T3.2). argon2id deferred to a future Epic-level password migration (out of scope here).
- **Impact**: Affects T0.6 `HashCode` cost constant; affects T3.2 implementation (parallelize bcrypt compare via errgroup or accept serial latency).

**Q5: Rate-limit dimensionality (per-user vs per-user+IP vs per-IP)**

- Options:
  - (a) **Per-user only** (matches Story 2.2 signin lockout; protects targeted user)
  - (b) **Per-user + per-IP** (defense-in-depth; protects against credential-stuffing from one IP across many user accounts AND brute-force against one user from many IPs)
  - (c) **Per-IP only** (CGNAT-hostile; large NAT pools share one IP)
- **sm_proposal**: (a) Per-user only — matches Story 2.2 BR-3.3 framework + Story 2.3 OAuth ratelimit pattern. The mfa_token JTI single-use property + 5-min TTL already constrains the attack window per-user; adding per-IP layer doubles Redis ops without commensurate security gain. CGNAT-hostility (c) is unacceptable. Epic 5 quota-svc will introduce a global anti-credential-stuffing per-IP layer (out of scope here).
- **Impact**: Affects T0.9 `Mfa()` helper signature (no `ipHash` arg); affects T5.1 ratelimit tests (no per-IP cases).
