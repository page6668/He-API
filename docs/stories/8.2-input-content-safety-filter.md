## Story

**As a** the He-API gateway operating under 生成式 AI 服务备案 compliance (and the operators who must demonstrate 入参敏感词拦截 for the 备案 audit),
**I want** the §9.3 入参 Filter (Bloom 快速排除 → 词典匹配) wired into the `POST /v1/chat/completions` request path so every inbound message body is scanned against the Story-8.1 `safety-lexicon` SoT, and any request carrying a sensitive term is **rejected before upstream dispatch** with the canonical `400_content_filter` envelope plus a structured interception event,
**so that** prohibited content never reaches a model vendor, the user gets a deterministic compliance error, and Story 8.5 (治理日志) can persist the interception record for 备案 — all reusing 8.1's single lexicon (no fork, no second wordlist) and the existing error taxonomy (no new code).

## Epic Context
**Epic**: 8 - 内容安全与合规准备
双向敏感词过滤 + 治理日志 + 备案材料归档。

**Epic DoD**: 入参/出参敏感词过滤上线 · 严格度可按 Key 配置 · 备案材料 PDF 模板生成。

**Story 8.2 Deliverables** (the FIRST half of "入参/出参过滤上线" — INPUT direction only):
- A consumer-owned **scanner** (in-gateway `internal/contentsafety/`) that segments free request text and resolves it against `safetylexicon.DefaultLexicon` — implementing the §9.3 入参 Filter layers (1) Bloom 快速排除 + (2) 词典匹配. 8.1 deliberately punted segmentation to the consumer (8.1 BR-3.4); 8.2 owns it.
- A **reject-before-dispatch** guard in the `POST /v1/chat/completions` handler: a confirmed hit returns the canonical `400_content_filter` envelope (already in rest-api-spec §5.1.2 + the runtime taxonomy — REUSED, not added), with no routing, no upstream call, no billing/usage charge.
- A structured **interception-event seam** (`Recorder` interface, no-op default) carrying `{direction:input, matched_rule, category, severity, action:blocked, user_id, api_key_id, he_request_id}` — the binding surface Story 8.5 implements to write `content_safety_logs`.
- A **minimal additive accessor** on the 8.1 lexicon (term-length introspection) so the scanner's window bound is the corpus truth, not a magic constant (no-false-negative safety).

> **Scope boundary (explicit)**: Story 8.2 is **INPUT direction only**. OUT of scope and owned elsewhere: §9.3 layer (3) the BERT 模型分类器 (later epic, as 8.1 noted); the **出参/streaming filter** (Story 8.3); **per-Key 严格度** loose/default/strict mapping (Story 8.4 — 8.2 blocks on ANY confirmed match = the future "strict" posture); the actual **`content_safety_logs` DB write + excerpt redaction + 6-month retention + 备案 PDF** (Story 8.5 — 8.2 makes ZERO DB changes and supplies only the event shape). Multimodal/tool-arg content scanning is deferred (8.2 scans string `messages[].content` only; multipart arrays land in Epic 9).

## Acceptance Criteria

### AC1: 命中拦截 + 400_content_filter 错误码 (Hit interception + canonical error envelope)

**Scenario**
```gherkin
GIVEN an authenticated POST /v1/chat/completions whose request body has been JSON-parsed and passed validateChatRequest
WHEN the gateway scans every messages[].content string (each Normalize-d via safetylexicon.Normalize) against safetylexicon.DefaultLexicon, BEFORE any routing decision or stream/adapter dispatch
THEN
  - on the FIRST confirmed Lookup hit the request is REJECTED with the canonical §5.1.2 envelope: code "400_content_filter", type "invalid_request_error", HTTP 400, a non-content-leaking message, and the he_request_id — emitted via the existing openaierr.Write (the code is ALREADY registered; 8.2 does NOT add a code)
  - the rejection happens BEFORE routing-svc is consulted and BEFORE any adapter / mock / failover dispatch — zero upstream vendor call, zero tokens, zero billing/usage metering for the blocked request
  - a request whose every message is clean passes through BYTE-IDENTICALLY to the pre-8.2 behaviour (no regression on the success path, the A/B path, or the streaming path)
  - the envelope param field carries NO sensitive substring (the matched term is logged to the 8.5 seam, NOT echoed to the caller — avoid leaking the lexicon)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | The scan runs in `ChatCompletionsHandler.ServeHTTP` AFTER `validateChatRequest` returns valid (chat_completions.go:403-406) and BEFORE the A/B guard / `routeOrWriteError` (chat_completions.go:412/435). This is the established "reject-before-upstream" seam (precedent: the inline A/B guard at chat_completions.go:412, and the `billinggate` 402 guard). [Source: apps/api-gateway/internal/handlers/chat_completions.go:403-435] |
| BR-1.2 | The error code `400_content_filter` is REUSED, not introduced — it already exists in `openaierr.CodeMetadata` (`{400, "invalid_request_error"}`) AND in rest-api-spec §5.1.2 line 124 ("命中内容安全过滤"). 8.2 only becomes its FIRST caller. Adding it again = a contract regression. [Source: apps/api-gateway/internal/openaierr/codes.go:25], [Source: docs/architecture/rest-api-spec.md:124] |
| BR-1.3 | A blocked request incurs NO usage/billing side-effect because the reject precedes dispatch — there is no upstream token cost to meter. T6 must assert no usage-emit / no billing-charge fires on the blocked path (the metering happens downstream of dispatch). |
| BR-1.4 | The scan is severity-AGNOSTIC in 8.2: ANY confirmed match blocks (equivalent to the future "strict" posture). Per-Key 严格度 (loose=high / default=high+medium / strict=all, 8.1 BR-1.4) is Story 8.4 and is NOT applied here. The `Match.Severity` is carried into the 8.5 event but does not gate the 8.2 decision. |
| BR-1.5 | The scan covers EVERY message's `content` regardless of `role` (system / user / assistant / tool) — all are client-supplied in the inbound array, so all are an injection surface. Tool/function-call JSON args (`Tools`/`ToolChoice`, currently `json.RawMessage` passthrough) and multipart content arrays are OUT (string `content` only; multimodal = Epic 9). [Source: apps/api-gateway/internal/handlers/chat_completions.go:82-98] |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Confirmed sensitive term in any message content | `400_content_filter` | `Request was blocked by the content safety filter.` | HTTP 400 envelope via openaierr.Write; param=nil (no leak); return before dispatch; emit 8.5 event |
| Clean request (no confirmed match) | (none) | n/a | Proceed unchanged to the A/B guard / routing / dispatch fork |
| Scan invoked but lexicon is the in-process DefaultLexicon | (none) | n/a | No runtime-failure mode — the lexicon is immutable, constructed at package init (panics there if bad); Lookup never errors, so there is no fail-open/closed branch to design (unlike the Redis-backed billinggate) |

**Examples**
- **Input**: `messages: [{role:"user", content:"… <a known political term> …"}]`
  **Expected**: `HTTP 400 {"error":{"code":"400_content_filter","type":"invalid_request_error","param":null,"he_request_id":"req_…"}}`; no vendor call; 8.5 event `{direction:"input", matched_rule:<canonical>, action:"blocked"}`
- **Input**: `messages: [{role:"user", content:"write a haiku about spring"}]`
  **Expected**: passes through; existing success body byte-identical

### AC2: 扫描策略 — 分词/滑窗 + Bloom 预筛 + 无漏报 (Segmentation: ASCII tokenize + CJK windowing, Bloom-prefiltered, NO false-negative)

**Scenario**
```gherkin
GIVEN a normalized message content string containing a sensitive term embedded in surrounding text (CJK has no word boundaries; ASCII/Latin is space/punctuation-delimited)
WHEN the contentsafety scanner segments and resolves it
THEN
  - ASCII/Latin runs are tokenized on word/punctuation boundaries and each token is resolved
  - CJK (and other unsegmented) runs are scanned by a sliding window whose lengths are bounded by the CORPUS term-length set (an additive 8.1 accessor), NOT a magic constant
  - each candidate is first checked with MightContain (Bloom layer-1 fast-exclude, 98%+ traffic) and only Bloom-positives are confirmed with the authoritative Lookup (layer-2) — matching the §9.3 Bloom-then-dictionary pipeline
  - the NO-FALSE-NEGATIVE invariant holds: any stored term appearing anywhere in any message content (after the shared Normalize: full/half-width, ASCII case, zero-width, padding) IS detected — a missed match is a compliance failure, the gravest defect class (inherited from 8.1's security posture)
  - normalization is the SHARED safetylexicon.Normalize entrypoint (8.1 BR-2.2) applied identically by this consumer, so producer/consumer normalization cannot drift
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | The scanner is consumer-owned (8.1 BR-3.4: "Substring scanning / tokenization / sliding-window over free text is the consumer's job (8.2/8.3)"). 8.1 supplies whole-term membership only (`Lookup`/`MightContain`); 8.2 supplies segmentation. The scanner lives in `apps/api-gateway/internal/contentsafety/` (in-gateway, billinggate-placement precedent) — NOT a new top-level module (the consumer is the gateway, not a cross-service shared lib). |
| BR-2.2 | The window length bound MUST come from the corpus, not a constant — else a stored term longer than the constant is a silent false-negative. 8.1 exposes neither term-length nor enumeration today, so 8.2 adds a MINIMAL additive accessor to the 8.1 lexicon (proposal: `func (l Lexicon) TermLengths() []int` — the sorted distinct rune-lengths present, so the scanner windows ONLY realized lengths). Additive, pure, re-runs the existing safety-lexicon CI lane. [Source: packages/safety-lexicon/lexicon.go:277-291 (current accessors: Len/CountByLang/Categories — no length surface)] |
| BR-2.3 | Bloom is the layer-1 prefilter PER CANDIDATE (not per-request): `MightContain(window)` cheaply excludes ~98% of windows before the map-backed `Lookup`. This is the documented §9.3 "Bloom 快速排除非命中（98%+ 流量）→ 词典匹配" split realized at the windowing grain. [Source: docs/architecture/9-合规架构compliance-architecture.md:29-33] |
| BR-2.4 | S⇄T (simplified⇄traditional Chinese) folding remains DEFERRED (8.1 OQ-8.1-4 ruling: "DEFER to 8.2/8.3"). 8.2 MUST record whether it picks up the deferred S⇄T fold or carries it forward again — a traditional-variant query will not match the simplified-seeded placeholder corpus until folding is added. Leetspeak/pinyin/homoglyph evasion stays OUT (layer-3 classifier). |
| BR-2.5 | The scanner is PURE over immutable state (the lexicon is immutable after init; no I/O, no `time`/`rand` in the scan) → deterministic verdict and safe for concurrent request handling without locks, mirroring 8.1 BR-3.5. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| message content (per message) | string | yes | scanned as-is after Normalize; empty content → no candidates, no match (never an error) | n/a (clean) |
| window length set | []int | yes (from 8.1) | derived from `TermLengths()`; scanner MUST NOT hardcode an upper bound | n/a (build-time contract) |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Term embedded mid-text in a CJK run | `400_content_filter` | (per AC1) | Detected via windowing — covered by a no-false-negative test over an embedded-term corpus sample |
| Width/case/zero-width evasion of a known term | `400_content_filter` | (per AC1) | Normalize folds it to canonical before Lookup — detected (false-negative-prevention test) |
| Empty / whitespace-only content | (none) | n/a | No candidate resolves; request proceeds (not an error) |

**Examples**
- **Input**: content `"前缀<known zh term>后缀"` (term embedded, no boundary)
  **Expected**: windowing surfaces `<known zh term>`; `Lookup` confirms; blocked
- **Input**: content with a known English term written `Ｂａｄ‌Word` (full-width + zero-width)
  **Expected**: `Normalize` → `badword`; `Lookup("badword")` confirms; blocked (no false-negative)

### AC3: 拦截事件 seam (Structured interception event for Story 8.5 — zero-DB this story)

**Scenario**
```gherkin
GIVEN a confirmed input hit (AC1) carrying its Match{Category, Severity, Canonical} and the request context (user_id, api_key_id, he_request_id)
WHEN the handler rejects the request
THEN
  - it constructs a structured SafetyEvent{direction:"input", matched_rule:Match.Canonical, category, severity, action:"blocked", user_id, api_key_id, he_request_id, created_at} and passes it to an injected Recorder interface
  - the DEFAULT Recorder is a no-op (or slog-only) implementation — Story 8.2 makes ZERO database changes and writes NO content_safety_logs row; the persisting implementation is supplied by Story 8.5
  - the event field shapes EXACTLY match the content_safety_logs columns (direction VARCHAR(10), matched_rule VARCHAR(100), action VARCHAR(20)) so 8.5 binds with no contract change; matched_rule is Match.Canonical (≤100 runes by 8.1's High#2 cap — fits the column)
  - excerpt_redacted (the redacted hit snippet) is NOT produced by 8.2 (8.5's job) — 8.2 deliberately does not place raw user text into the event
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-3.1 | The `Recorder` is a small interface (`Record(ctx, SafetyEvent)`) injected into `ChatCompletionsHandler` with a no-op default wired in `main.go`. This is the binding seam for 8.5; it keeps 8.2 zero-DB and unit-testable (a fake Recorder asserts the event shape). Precedent: dependency-injected collaborators on the handler (the adapterRegistry / routing client fields). |
| BR-3.2 | `matched_rule` = `Match.Canonical` (8.1 BR-3.3: the stable, query-independent value, capped ≤100 runes to fit `content_safety_logs.matched_rule VARCHAR(100)` per 8.1 Architect High#2). `direction` is the literal `"input"`; `action` is the literal `"blocked"`. [Source: docs/architecture/data-models.md:142-154] |
| BR-3.3 | 8.2 records the FIRST confirmed match only (fail-fast reject). Enumerating all matches in a request is unnecessary work on the reject path and risks unbounded scanning — first-hit-and-reject is the KISS posture. (8.5 may later choose richer logging; 8.2's event carries one matched_rule.) |
| BR-3.4 | ZERO migration in this story. `content_safety_logs` already exists in the data model (Epic-8 orbit); 8.2 neither creates nor writes it. The creation-gate data-sync indicator resolves to **no DB writes**. [Source: docs/architecture/data-models.md:142-154] |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| SafetyEvent.direction | string | yes | literal `"input"` | n/a (compile-time constant) |
| SafetyEvent.matched_rule | string | yes | == Match.Canonical, ≤100 runes (8.1 cap) | n/a (8.1-guaranteed) |
| SafetyEvent.action | string | yes | literal `"blocked"` | n/a |
| SafetyEvent.{user_id, api_key_id, he_request_id} | string | yes | from middleware context helpers | n/a |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| Recorder is the no-op default (8.5 not yet wired) | (none) | n/a | Event constructed + handed to no-op; request still 400s; no persistence (expected this story) |
| Recorder.Record itself errors (future 8.5 impl) | (none) | n/a | Out of 8.2 scope; the interface contract is fire-and-forget on the reject path — 8.5 owns its own failure policy |

**Examples**
- **Input**: hit on a `high`/`political` term for user `u-1`, key `k-1`, request `req_abc`
  **Expected**: `Recorder.Record` receives `{direction:"input", matched_rule:"<canonical>", category:"political", severity:"high", action:"blocked", user_id:"u-1", api_key_id:"k-1", he_request_id:"req_abc"}`; no DB row written (no-op default)

### Technical Constraints

- **Canonical design source**: the §9.3 入参 Filter pipeline — `1. Bloom filter 快速排除非命中（98%+ 流量）→ 2. 词典匹配（基础关键词列表）→ [3. 模型分类器 — OUT] → 4. 命中 → 拒绝 + 写入 content_safety_logs`. **Story 8.2 implements layers (1)+(2) + the 拒绝 (reject), and surfaces the event for the 写入 (Story 8.5 persists).** [Source: docs/architecture/9-合规架构compliance-architecture.md:26-44]
- **Consumer of 8.1, not a fork**: 8.2 resolves against `safetylexicon.DefaultLexicon` — the single SoT. 8.1 BR-3.4 deliberately deferred segmentation to the consumer; 8.2 owns the scanner. The public 8.1 API is `Normalize`, `MightContain`, `Lookup` (→ `Match{Category, Severity, Canonical}`), `Len`, `CountByLang`, `Categories`. [Source: packages/safety-lexicon/lexicon.go:148-291], [Source: docs/stories/8.1-sensitive-word-lexicon-zh-en-extensible.md AC3/BR-3.4]
- **The 8.1 API gap (load-bearing design point)**: the lexicon exposes ONLY whole-term membership — it has NO term-enumeration or term-length surface (verified: accessors are `Len`/`CountByLang`/`Categories` only). A substring scanner that windows free CJK text needs the corpus length set to bound its window safely; bounding by a magic constant risks a false-negative (a compliance breach) for any longer term. 8.2 therefore adds ONE minimal additive accessor to 8.1 (`TermLengths()` proposal). This crosses the 8.1/8.2 boundary → **OQ-8.2-2 for the Architect**. [Source: packages/safety-lexicon/lexicon.go:277-291]
- **Reject-before-dispatch seam**: the scan goes in `ChatCompletionsHandler.ServeHTTP` between `validateChatRequest` (chat_completions.go:403-406) and the A/B guard / `routeOrWriteError` (chat_completions.go:412/435) — the established inline-guard seam (the A/B 400 guard at :412 is the immediate precedent; `billinggate` is the middleware precedent for early reject). [Source: apps/api-gateway/internal/handlers/chat_completions.go:403-435], [Source: apps/api-gateway/internal/middleware/billinggate/billinggate.go]
- **Error envelope is REUSED**: `400_content_filter` already lives in `openaierr.CodeMetadata` `{400, "invalid_request_error"}` AND in rest-api-spec §5.1.2 (line 124). Call it via `openaierr.Write(w, ctx, http.StatusBadRequest, "400_content_filter", msg, nil)` — signature `Write(w, ctx, status, code, message string, param *string)`. Do NOT add the code (the header in codes.go forbids re-adding §5.1.2 rows; a duplicate is a contract regression). [Source: apps/api-gateway/internal/openaierr/codes.go:25], [Source: apps/api-gateway/internal/openaierr/errors.go:56], [Source: docs/architecture/rest-api-spec.md:124]
- **Single inbound text surface**: the gateway is OpenAI-protocol-only — `POST /v1/chat/completions` (main.go:410) is the ONLY inbound LLM-text route (Epic-4 DoD: "6 家模型均可通过 /v1/chat/completions 以 OpenAI 协议调通"). There is NO Anthropic `/v1/messages` surface to also filter. Scope is one route. [Source: apps/api-gateway/cmd/server/main.go:410], [Source: docs/architecture/rest-api-spec.md:295]
- **No runtime failure mode**: unlike `billinggate` (Redis-backed, fails open), the lexicon is in-process + immutable (panics at init if bad), so `Lookup` never errors at request time. There is NO fail-open/closed branch to design — the scan is a pure, deterministic in-memory function.
- **Toolchain limits**: pure-Go + httptest; no `buf`/`atlas`/`docker` needed (zero proto/DB/migration). Do NOT re-run workspace `go mod tidy` (otel pin gotcha). [Source: memory project_otel_version_pin_gotcha], [Source: memory project_toolchain_env_limits]

#### Medium Issues (1)

- **Redundant normalization on the hot path** (AC2 scanner / AC4 perf budget): The scanner Normalizes the full content string once, then cuts windows from the already-normalized text — but `MightContain` calls `l.bloom.test(Normalize(term))` (lexicon.go:259-261) and `Lookup` calls `Normalize(term)` again (lexicon.go:267-275). So each candidate window is re-normalized up to 2× more after already being canonical. Normalize does full/half-width folding + zero-width strip + ASCII case-fold — non-trivial per-window cost, and the scanner emits many windows per CJK run. This is in direct tension with AC4's proposed P99 < 50µs ceiling.
  - Fix (Dev, during T2/T4): Normalize is idempotent, so correctness is unaffected — but the perf budget should be measured WITH the redundant calls, OR Dev adds a normalized-input fast path (e.g. resolve windows against the lexicon's internal `exact`/`bloom` on the already-canonical substring without re-Normalizing). If a fast path requires a second additive 8.1 surface, prefer instead to accept the cost and set the AC4 ceiling from the real benchmark (soft-gate). Document the choice in the Dev Log. Do NOT let this become a silent false-negative source (any fast path must still go through canonicalized membership).

#### Low Issues (2)

- **matched_rule determinism under overlapping terms** (BR-4.3 / AC3): "first-hit on a deterministic segmentation order" fixes message order and text order, but does not specify the window-LENGTH iteration order at a single position. If both `AB` and `ABC` are stored and content contains `ABC`, which canonical is reported depends on whether lengths are tried ascending or descending. The determinism test passes either way (same input→same output), but the REPORTED `matched_rule` (the 8.5 event) is order-sensitive. Recommendation: pin a documented length order at a position (suggest longest-match-first, the conventional dictionary-scan choice) and add a test asserting the chosen canonical on an overlapping-term fixture.
- **Tool-arg / multimodal deferral should be a tracked gap, not silent scope-out** (OQ-8.2-3 / BR-1.5): Deferring `Tools`/`ToolChoice` and multipart content is the correct KISS call for 8.2, but function-call arguments are a genuine inbound injection surface for a 备案 gate.
