**Goal**: 实现 6 家中国主流 LLM 的 plugin 适配器，规范化为 OpenAI 协议；并验证流式/非流式/token 用量准确透传

### Open Questions for Architect

Status: All six OQ-4.2-1..6 are STORY-CREATION-TIME open questions for Architect Round 1 ruling. SM's leans are restated below for ease-of-review. Architect Round 1 should also ratify the BR-3.2 `usage.Normaliser` interface LIFT (T0.8) — listed as a sub-question of OQ-4.2-3 since it directly affects the Normaliser implementation's import surface.

1. **OQ-4.2-1 — DashScope endpoint choice**: `/compatible-mode/v1/chat/completions` (OpenAI-shape; identity Normaliser; minimal `translate.go`; matches DeepSeek's template most closely) vs `/api/v1/services/aigc/text-generation/generation` (DashScope native; non-identity Normaliser per field-rename; full `translate.go` transformation; potential `event: ping` SSE heartbeat). **SM lean**: **compat-mode** — minimises divergence from Story-4.1 template; the only cost is losing DashScope-native-only features (function-call shape extensions, vision-input shape) which are NOT in Story 4.2 scope (Epic 9 multimodal); compat-mode's `usage` shape aligns with OpenAI so the Normaliser is identity-mapping (same structure as Story-4.1 deepseek). **Architect should rule** — the ruling cascades to OQ-4.2-3 (translate.go content), BR-2.3 (SSE decoder shape), BR-3.2 (Normaliser implementation), and the file structure of `apps/adapters/qwen/internal/upstream/types.go`.

2. **OQ-4.2-2 — Adapter service granularity**: single `adapter-qwen` service for BOTH `qwen-max` + `qwen-plus` (BR-1.10 SM lean) vs per-model services (`adapter-qwen-max` + `adapter-qwen-plus` — each its own K8s Deployment, Helm chart, ArgoCD app). **SM lean**: **single service** — matches DashScope's own API surface (one endpoint, model selected via body field); matches the per-vendor blast-radius isolation goal of namespace `he-api-adapters` (Story 4.1 M4); avoids doubling Helm chart count from 6 → 11+ (Kimi has 3 sizes, Doubao has 2 variants). **Architect should rule** — the ruling cascades to **Stories 4.3 (Kimi: `moonshot-v1-8k`/`32k`/`128k`) + Story 4.5 (Doubao: `pro`/`lite`)**: both Stories will inherit whatever granularity Story 4.2 ratifies. If per-model is ratified, the Helm chart count + namespace + ArgoCD app count all multiply, and the registry-loader logic gains complexity (each model id reads a separate env var).

3. **OQ-4.2-3 — `upstream/translate.go` content divergence**: IF compat-mode (OQ-4.2-1 SM lean), the `translate.go` is identity-mapping (DeepSeek-like); IF native, the `translate.go` does full request-shape transformation. **Cascade from OQ-4.2-1** — listed as a separate OQ for documentation parity with Story 4.1 (which had 7 OQs). **Sub-question OQ-4.2-3a**: should the `usage.Normaliser` interface be LIFTED from `apps/adapters/deepseek/internal/usage/` to a shared location (T0.8)? SM lean: **YES, lift to `apps/adapters/_shared/usage/`** (the `_shared` prefix signals cross-adapter internal use without elevating to a top-level `packages/` module). **Architect should rule on both the cascade and the lift.**

4. **OQ-4.2-4 — DashScope-specific upstream-error mapping**: should upstream 429 (DashScope rate-limit) map to `502_upstream_unavailable` per Story-4.1 BR-1.4 default (all 4xx = OUR misconfig) OR carve out a Qwen-specific mapping (e.g., 429 → 502 with `upstream_error_kind=rate_limit_throttle` slog attribute for ops visibility)? **SM lean**: **KEEP the Story-4.1 BR-1.4 mapping (429 → 502) BUT ADD the slog attribute** for ops visibility (BR-4.4 introduces `upstream_error_kind`). The user-facing rate-limit envelope code `429_*` is Epic-5 territory (OUR rate-limiter, distinct from upstream's); exposing upstream 429 to the user would conflate two distinct rate-limit surfaces. **Architect should rule.**

5. **OQ-4.2-5 — DashScope HTTP/2 support + `golang.org/x/net/http2` Transport configuration**: Story-4.1 OQ7 ratified forced HTTP/2 to DeepSeek (`AllowHTTP=false` + custom `Transport`). Does DashScope's `dashscope.aliyuncs.com` support HTTP/2? Draft-time `curl --http2 -v https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` exploration is needed; if NO HTTP/2 support, the Qwen adapter MUST allow ALPN fallback to HTTP/1.1 (a divergence from Story-4.1 OQ7). **SM lean**: **try HTTP/2 first, fall back to HTTP/1.1 gracefully via ALPN** — use `http.Transport` with `ForceAttemptHTTP2 = true` (Go stdlib mechanism) instead of `http2.Transport` (forced); this lets the client negotiate down if upstream lacks HTTP/2. **Architect should rule** — the ruling cascades to ALL of Stories 4.3-4.6 (each vendor needs HTTP/2-support verification).

6. **OQ-4.2-6 — Env-var naming convention**: `QWEN_UPSTREAM_API_KEY` (model-family name; matches the registry key + source-tree directory + Helm chart name) vs `DASHSCOPE_UPSTREAM_API_KEY` (matches the upstream vendor's actual platform name; Qwen is the model family, DashScope is the platform). **SM lean**: **`QWEN_UPSTREAM_API_KEY`** — model-name-based for consistency with model-id naming used everywhere else (registry key `qwen-max`/`qwen-plus`, source-tree `apps/adapters/qwen/`, Helm chart `adapter-qwen`). **Architect should rule** — the ruling cascades to **Stories 4.5 (Doubao: model-family vs Volcano-Engine vendor platform) + Story 4.6 (Ernie: model-family vs Wenxin Yiyan / Qianfan platform names)**.
