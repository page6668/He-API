### AC1: 用户可订阅升降级 — subscription upgrade / downgrade / cancel

**Scenario**
```gherkin
GIVEN
  - User U is authenticated (bearer API key or JWT-cookie) and has an active subscription on plan P_old (e.g. "free") in he_api.subscriptions (status='active'), or no subscription row (resolves to "free", Q-PLAN-DEFAULT)
  - The plan catalogue (Q-PLAN-CATALOG) defines Free / Pro / Team / Enterprise with their entitlements
  - The 7.3 provider subscription rail is live (Stripe/PayPal subscription + the payment.completed/subscription webhook lifecycle)
WHEN
  - U calls PUT /v1/billing/subscription { "plan": P_new } to change to a different valid plan, OR DELETE /v1/billing/subscription to cancel
THEN
  - billing-svc validates P_new is a known plan in the catalogue (unknown → 400_invalid_plan, no change)
  - for an UPGRADE (P_new ranks above P_old): payment-svc UpdateProviderSubscription(ext_sub_id, P_new) updates the provider subscription with proration (Stripe proration_behavior — provider-computed, NO He-API-issued credit); on the provider-confirmed webhook, subscriptions.plan transitions to P_new (status stays active); the entitlement applies IMMEDIATELY (optimistic on confirmed update, Q-UPGRADE-DOWNGRADE)
  - for a DOWNGRADE (P_new ranks below P_old): the change is scheduled for current_period_end (the user KEEPS P_old's entitlement until the period rolls); the provider subscription is updated to take effect at period end; subscriptions reflects the pending downgrade; at period roll the entitlement drops to P_new
  - for CANCEL (DELETE): the subscription is cancelled at current_period_end → reverts to "free" at period end (no mid-period refund — Q-REFUND deferral holds)
  - GET /v1/billing/subscription returns the caller's current plan, the resolved entitlements (limits + included-credit + features), status, and next-billing/period-end — money fields as string-decimals
  - a successful plan change emits a receipt/confirmation email via the 7.3 payment.completed → notification-svc path (REUSE; no new email path)
  - **ownership invariant**: PUT/DELETE operate ONLY on the authenticated user's own subscription (user_id server-resolved) — there is no target-user parameter (cross-user mutation impossible, BR-S-7)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-S-1 | `P_new` MUST be a known plan in the catalogue (Free/Pro/Team/Enterprise); an unknown/empty plan → `400_invalid_plan`, no mutation. |
| BR-S-2 | **Upgrade = immediate** (entitlement applies on the provider-confirmed update); **downgrade & cancel = deferred to current_period_end** (the user keeps the higher entitlement until the period rolls — no mid-period downgrade, no mid-period refund). Q-UPGRADE-DOWNGRADE. |
| BR-S-3 | The plan transition is CONFIRMED on the 7.3 provider webhook (mirrors 7.3 "credit only on confirmed webhook") — billing-svc does NOT optimistically mutate subscriptions.plan before the provider confirms the billing change. The entitlement MAY apply optimistically on an upgrade once the provider call returns success (Q-UPGRADE-DOWNGRADE Architect knob). |
| BR-S-4 | Proration is PROVIDER-COMPUTED (Stripe proration_behavior) — He-API issues NO proration credit/charge itself (7.3 Q-AMOUNT "amount is provider truth" cascade; NO new credit path, BR-S-5). |
| BR-S-5 | The subscription CHARGE reuses the 7.3 provider rail + exactly-once credit verbatim — 7.8 introduces NO new money SoT and NO new credit path. |
| BR-S-6 | `team` is selectable as a per-user tier; POOLED team entitlement is OUT (Q-TEAM-PLAN — blocked on the teams realisation). |
| BR-S-7 | PUT/DELETE /v1/billing/subscription act on the authenticated user's OWN subscription only (user_id server-resolved, never path/body-supplied) — cross-user mutation is impossible. |
| BR-S-8 | A user with no active subscription resolves to `free` (Q-PLAN-DEFAULT); a past_due/cancelled subscription degrades to `free`, never to unlimited. |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| plan | string | yes (PUT) | MUST be one of {free, pro, team, enterprise} (catalogue keys) | `400_invalid_plan` — "Unknown subscription plan." |

**Error Handling**
| Scenario | Code | Message (en) | Action |
|----------|------|--------------|--------|
| Unknown / empty plan | 400 | `400_invalid_plan` — "Unknown subscription plan." | reject PUT; no mutation (BR-S-1) |
| Provider subscription update fails | 402 | `402_payment_failed` (REUSE 7.3) — provider-domain failure, not 5xx | no plan transition; surface to caller; subscriptions unchanged |
| No active subscription on DELETE | 200 (idempotent) | — | already free / cancelled → idempotent no-op (no error) |
| Same-plan PUT (P_new == P_old) | 200 (idempotent) | — | no-op; return current subscription |

**Examples**
- **Input**: U on `free` → PUT {plan:"pro"} → payment-svc updates the Stripe subscription (prorated) → webhook confirms → subscriptions.plan="pro", entitlement applies immediately → U now gets the Pro rate-limit/quota ceiling. ✅ immediate upgrade.
- **Input**: U on `pro` (period ends 2026-07-09) → PUT {plan:"free"} on 2026-06-20 → downgrade scheduled for 2026-07-09; U keeps Pro limits until then; on 2026-07-09 the entitlement drops to free. ✅ deferred downgrade.

### AC2: Beta 模式开启时进入 Sandbox 限额 — global Beta-mode → Sandbox ceiling

**Scenario**
```gherkin
GIVEN
  - he_api.feature_flags holds a `beta_mode` row (realised by 0012, Q-BETA-MIGRATION); the plan catalogue defines a SandboxCeiling (Q-BETA-GATE)
  - flag:beta_mode (Redis §4.3) is the runtime read; PG feature_flags is the cold-start SoT; Unleash (tech-stack §2.1) is the live push
  - Users on various plans (free … enterprise) are issuing POST /v1/chat/completions
WHEN
  - An operator flips beta_mode to ON via the admin surface (Q-ADMIN-BETA — Unleash console SoT by default); the flip propagates to every gateway pod (PG cold-start + Redis runtime + Unleash push) within the propagation window
THEN
  - the gateway, on EVERY chat request, reads flag:beta_mode = ON and applies the global SANDBOX ceiling: effective_limit = min(plan_limit, sandbox_limit) per axis (rpm/tpm/qps/quota) — even an Enterprise user is capped at the sandbox ceiling during Beta (Q-BETA-GATE composition; Q-BETA-SCOPE = global in 7.8)
  - a request exceeding the sandbox ceiling is throttled with the EXISTING 5.3 rate-limit envelopes (429_rate_limit_{qps,rpm,tpm}) / the 5.4 cap (402_quota_exhausted) — 7.8 reconfigures the LIMIT VALUES, it does NOT add a new throttle envelope
  - when beta_mode is flipped OFF, the sandbox ceiling is removed within the propagation window and each user's plan ceiling stands alone again
  - **global invariant**: "可全局生效" — a single flag flip caps (or uncaps) the ENTIRE platform without per-user reconfiguration; no user is exempt unless the Architect rules a tier-exemption (Q-BETA-GATE)
  - **admin invariant**: the WRITE/flip surface is admin-gated; a normal bearer key / non-admin caller CANNOT flip beta_mode (Q-ADMIN-BETA, BR-B-4)
  - every flip is audit-logged (audit.event)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-B-1 | beta_mode ON → `effective_limit = min(plan_limit, sandbox_limit)` per axis (a hard global CEILING, not an override or addition — Q-BETA-GATE). beta_mode OFF → the plan ceiling stands alone. |
| BR-B-2 | The flag is read from Redis `flag:beta_mode` at runtime; a gateway pod cold-starts from the PG `feature_flags` row; Unleash pushes live changes. PG is the authoritative store (Redis + Unleash are derived runtime mirrors). |
| BR-B-3 | Beta scope is GLOBAL in 7.8 ("可全局生效"); the `feature_flags.variants` 灰度-cohort column is wired-ready but cohort targeting is DEFERRED (Q-BETA-SCOPE). |
| BR-B-4 | The flip WRITE surface is ADMIN-gated (Q-ADMIN-BETA — Unleash console RBAC by default; a He-API admin REST endpoint, if ratified, requires an admin scope/role, NOT a normal bearer key). The gateway READ path is internal/pod-local. |
| BR-B-5 | Beta throttling REUSES the existing 5.3/5.4 envelopes (429_rate_limit_* / 402_quota_exhausted) — 7.8 changes the limit VALUES the limiter reads, never the envelope shapes. |
| BR-B-6 | The propagation window (flip → every-pod-effective) is bounded by the gateway's Redis-read cadence + Unleash push latency — an explicit Architect knob, not unbounded. |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| Non-admin attempts to flip beta_mode | reject (admin authz — Q-ADMIN-BETA; if a He-API endpoint exists → 403/admin-forbidden envelope; via Unleash → Unleash RBAC denies) |
| Redis flag:beta_mode unavailable | fall back to the PG feature_flags row (cold-start SoT); if PG also unavailable, default beta_mode=OFF only if the last-known value is unknown (fail-safe: a booting pod with no signal does NOT trap users in sandbox) — Architect ratifies the unavailable-direction (Q-BETA-GATE) |
| Request exceeds sandbox ceiling (beta ON) | existing 429_rate_limit_* / 402_quota_exhausted envelope (BR-B-5) |

**Examples**
- **Input**: beta_mode ON, sandbox_limit rpm=60. An Enterprise user (plan rpm=10000) issues 80 rpm → throttled at 60 (min(10000,60)) with 429_rate_limit_rpm. ✅ global sandbox ceiling.
- **Input**: beta_mode flipped OFF → within the propagation window the same Enterprise user is no longer capped at 60; their plan rpm=10000 stands. ✅ uncap.

### AC3: 套餐权益解析与执行 — tier entitlement resolution + hot-path enforcement (the backbone AC1 + AC2 both depend on)

**Scenario**
```gherkin
GIVEN
  - The plan catalogue (Q-PLAN-CATALOG) maps each plan → an Entitlement (rpm/tpm/qps ceilings, monthly_included_credit / quota, feature gates)
  - billing-svc is the SOLE writer of the cached entitlement snapshot entitlement:user:{id} (Q-ENTITLEMENT-ENFORCE); the gateway is the reader
  - User U has a resolved plan (from subscriptions.status='active', else free — Q-PLAN-DEFAULT)
WHEN
  - U issues POST /v1/chat/completions (the hot path), AND/OR U's plan changes (AC1) / beta_mode flips (AC2)
THEN
  - the gateway entitlement middleware resolves U's effective entitlement from the cached snapshot (NOT a per-request PG read) and feeds the limit values into the existing 5.3 Lua rate-limiter + the 5.4 monthly-cap gate
  - the entitlement is resolved SERVER-SIDE from subscriptions keyed by the authenticated user_id — a client-asserted plan/limit is IGNORED (privilege-escalation guard, BR-E-1)
  - **fail-safe-low**: on a cache MISS or resolution uncertainty, the gateway enforces the FREE ceiling (the lowest), NEVER fail-open-high (BR-E-2)
  - on a plan change (AC1) or a provider webhook flipping subscriptions.status, billing-svc REFRESHES the snapshot + sets a cross-pod invalidation sentinel (5.1 revoke-sentinel precedent) so the gateway converges to the true entitlement within the bounded stale window (BR-E-3)
  - beta_mode (AC2) composes on top: the gateway applies min(resolved_plan_limit, sandbox_limit) when ON (BR-B-1)
  - the resolved entitlement is observable via GET /v1/billing/subscription (the user sees their own limits) and the catalogue via GET /v1/billing/plans (public)
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-E-1 | The entitlement is resolved SERVER-SIDE from `subscriptions` (status='active') keyed by the authenticated user_id; a client-asserted plan/limit is NEVER trusted (tier privilege-escalation guard). |
| BR-E-2 | **Fail-safe-LOW**: a cache miss / resolution failure / uncertainty enforces the FREE ceiling (the lowest), never fail-open-high — a cache hiccup throttles, it never grants Enterprise limits (Q-ENTITLEMENT-ENFORCE, security-correct direction). |
| BR-E-3 | The cached snapshot `entitlement:user:{id}` is written ONLY by billing-svc (single trusted writer) on every subscriptions transition + a bounded TTL + a cross-pod invalidation sentinel (5.1 `auth:apikey:revoked` precedent [→ data-models.md §4.3]); the enforced ceiling converges to the true plan within the stale window. |
| BR-E-4 | 7.8 supplies the LIMIT VALUES the 5.3 per-key/per-user Lua limiter + the 5.4 cap read — it does NOT change the limiter key shapes, the Lua scripts, or the throttle envelopes (the 5.3/5.4 substrate is reused verbatim). |
| BR-E-5 | The plan catalogue is the single SoT for plan→limits (version-controlled code, Q-PLAN-CATALOG) — no per-pod drift; the public `GET /v1/billing/plans` renders the same catalogue. |
| BR-E-6 | The entitlement resolution must not regress the gateway hot-path latency budget — a cached-snapshot read only, no synchronous PG/billing-svc call on the request path (performance indicator, Decision 8B). |

**Error Handling**
| Scenario | Code/Action |
|----------|-------------|
| Entitlement cache miss for U | resolve free ceiling (fail-safe-low, BR-E-2); async-refresh the snapshot from billing-svc |
| Client supplies a plan/limit hint in the request | ignored — server-resolved entitlement only (BR-E-1) |
| billing-svc unavailable for a refresh | the last cached snapshot stands until TTL; on TTL expiry with no refresh → free ceiling (fail-safe-low) |

**Examples**
- **Input**: a malicious client sends `X-Plan: enterprise` / a body plan hint with a Free subscription → IGNORED; the gateway resolves `free` from subscriptions and throttles at free limits. ✅ privilege-escalation blocked.
- **Input**: U upgrades free→pro (AC1) → billing-svc refreshes entitlement:user:U + sentinel → within the stale window the gateway enforces Pro limits. U then cancels → the snapshot is invalidated → the gateway converges to free (never keeps Pro). ✅ stale-cache convergence both directions.
