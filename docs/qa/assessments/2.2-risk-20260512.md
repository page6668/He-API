## Detailed Risk Analysis — Security (16 risks)

### SEC-008: Brute-force Password Attack — **Critical (20)**

**Category:** Security · **Probability:** 4 (Likely — automated credential-stuffing is industry baseline) · **Impact:** 5 (Critical — account takeover) · **Risk Score:** 20

**Description:** Attacker enumerates passwords against a known/discovered email via repeated `/v1/auth/signin` calls. Without rate limit + soft-lock, even bcrypt cost=12 (~150ms/compare) allows several attempts/sec/IP — sufficient to crack top-1k passwords against a non-trivial user base within hours.

**Mitigation Strategy:**
- **Prevention:** Dual-key Redis rate limit (`ratelimit:signin:email:{email_hash}` 5/15min + `ratelimit:signin:ip:{ip}` 10/15min per BR-3.8 + BR-4.1). Soft-lock at 5 failed attempts: `users.status='locked'` + `locked_until=NOW+1h` (BR-3.3). Locked status returns 423 with `Retry-After`; self-heal at `locked_until <= NOW` runs in the same TX as the next successful signin (BR-4.4).
- **Detection:** Prom counter `auth_signin_total{result="failure"}` + `auth_account_locked_total` + alert rule (BR-4.9) fires Feishu webhook at >100 failures/5min and PagerDuty at >10 lock events/5min.
- **Response:** Triage Grafana dashboard `auth-svc → Account Security`; if coordinated attack pattern (>50 distinct emails locked from <5 IPs), trigger IP allowlist or emergency rate-limit tightening via Helm value rollback.
- **Owner:** Dev (auth-svc) implementation + Ops on-call rotation.

**Test Requirements:**
- P0: **2.2-UNIT-131** (per-email rate limit check), **2.2-UNIT-139** (5th-failure soft-lock trigger), **2.2-INT-041** (soft-lock activation integration), **2.2-INT-042** (subsequent 423 with Retry-After), **2.2-INT-049** (per-IP rate limit), **2.2-BLIND-CONCURRENCY-002** (5 parallel failures hit lock exactly once), **2.2-E2E-023** (locked-account UX).
- P1: **2.2-INT-068** (Alertmanager rules present).

**References:**
- [Source: BR-3.3, BR-3.8, BR-4.1, BR-4.4, BR-4.8, BR-4.9 in Story 2.2 ACs]
- [Source: docs/architecture/security.md §8.1 — auth layer; OWASP ASVS L2 V2.2.1 / V11.1.4]
- [Mitigation tests in: docs/qa/assessments/2.2-test-design-20260512.md §AC3, §AC4, §Blind-Spot]

### SEC-005: Email Enumeration via Signup — **High (16)**

**Category:** Security · **Probability:** 4 · **Impact:** 4

**Description:** Attacker probes `/v1/auth/signup` with candidate emails. If response differs (e.g., 200 vs 409, body differs, latency differs) between "new email" and "existing email", attacker harvests valid email list — directly fueling SEC-006 (signin enumeration) + downstream phishing.

**Mitigation Strategy:**
- **Prevention:** Per BR-1.4: existing-email signup returns the SAME 200 + `{message:'verification_email_sent'}` response shape AND consumes equivalent CPU time via dummy bcrypt + dummy Redis SETEX (NOT sleep — BR-4.3 mandates real CPU work, since statistical analysis differentiates sleep from CPU). `users.status='pending_deletion'` rows take the same path (BR-1.5). Audit event `auth.signup_duplicate_attempt` (not surfaced to attacker) enables internal monitoring.
- **Detection:** Audit log mining of `auth.signup_duplicate_attempt` rate per IP; alert if single IP submits > 50 unique emails / hour.
- **Response:** Block offending IP at api-gateway middleware (manual op) + permanent record in audit.
- **Owner:** Dev (auth-svc).

**Test Requirements:**
- P0: **2.2-UNIT-037** (response shape parity unit), **2.2-UNIT-039** (audit event correctness), **2.2-UNIT-044** (no `user_id` leakage in response), **2.2-INT-002** (timing parity ±50ms integration), **2.2-BLIND-CONCURRENCY-001** (race-free duplicate handling), **2.2-E2E-003** (UI parity).

**References:** [Source: BR-1.4, BR-1.5, BR-4.3 + OWASP ASVS L2 V3.2.3]

### SEC-006: Email Enumeration via Signin — **High (16)**

**Category:** Security · **Probability:** 4 · **Impact:** 4

**Description:** Signin error responses for "unknown email" vs "wrong password" differ in code or latency → attacker harvests registered emails. Even subtle timing diff (e.g., 1ms when no row vs 150ms when row exists + bcrypt called) is statistically detectable.

**Mitigation Strategy:**
- **Prevention:** Per BR-3.2: non-existent email path calls `password.Compare` against a pre-generated dummy bcrypt hash (real CPU work, NOT sleep). Response code = `401_invalid_credentials` (NOT 404). Same code used for wrong-password path. Statistical timing parity SLO: p99 variance < 50ms across 100-iter samples (BR-4.3).
- **Detection:** E2E timing-attack probe (2.2-E2E-031) in CI run; regression guard against future code paths that bypass dummy bcrypt.
- **Response:** If probe fails regression — block release; trace divergence (likely a new branch added before dummy-compare).
- **Owner:** Dev (auth-svc).

**Test Requirements:**
- P0: **2.2-UNIT-132** (dummy bcrypt path), **2.2-UNIT-133** (statistical timing parity unit), **2.2-INT-045** (integration parity), **2.2-E2E-031** (E2E probe p99 <50ms).

**References:** [Source: BR-3.2, BR-4.3 + OWASP ASVS L2 V3.2.3 + NIST SP 800-63B §5.2.2]

### SEC-003: JWT Algorithm-Confusion — **High (15)**

**Category:** Security · **Probability:** 3 · **Impact:** 5

**Description:** Classic `alg=none` and `alg=HS256` (with public key used as HMAC secret) attacks: if `jwt.Verify` does not pin algorithm to RS256, an attacker forges tokens trivially. The public key is **published at JWKS endpoint** (Q1 ruling); attacker can read it then HMAC-sign with it.

**Mitigation Strategy:**
- **Prevention:** TS-CONS-002 — auth-svc + api-gateway verifier MUST pin `expected_alg = "RS256"` and reject any other (incl. `none`, `HS256`, `HS384`, etc.). Use `github.com/golang-jwt/jwt/v5` with `WithValidMethods([]string{"RS256"})` (or equivalent allowlist).
- **Detection:** Unit test **2.2-UNIT-115** asserts HS256-signed token is rejected by the auth-svc verify path; same test repeated on api-gateway side.
- **Response:** If detected in prod — rotate key per Q3 (RTO 2h) + audit all issued tokens via Redis family registry, force-revoke suspicious sessions.
- **Owner:** Dev (auth-svc + api-gateway shared JWT lib).

**Test Requirements:** P0: **2.2-UNIT-110**, **2.2-UNIT-115**, **2.2-UNIT-117**.
**References:** [Source: TS-CONS-002 + OWASP JWT cheat-sheet + CVE-2015-9235 historical context]

### SEC-009: Verification-Token Replay / Brute-force — **High (15)**

**Category:** Security · **Probability:** 3 · **Impact:** 5

**Description:** Two scenarios: (a) one-shot semantic broken → token usable multiple times → attacker who intercepts link (e.g., misforwarded email) keeps replaying to claim/re-claim account; (b) predictable token → attacker brute-forces token-space for known recipient.

**Mitigation Strategy:**
- **Prevention:** Per Q2 ruling + TS-CONS-006: token = 32 bytes from `crypto/rand`, base64url-encoded to 64 chars (effective 256 bits — un-bruteforceable). Stored as SHA-256 hash only in Redis (`auth:email_verify:{hash(t)}`), never plaintext. TTL=86400s (24h). DEL-after-use on successful verify (BR-2.1). Attempts counter caps at 5 → token DEL'd + audit `auth.verify_email_brute_force` (BR-2.5).
- **Detection:** Audit event mining + alert on rate of `verify_email_brute_force` events.
- **Response:** Manual invalidation of any suspicious user's tokens via Redis DEL; force re-signup.
- **Owner:** Dev (auth-svc).

**Test Requirements:**
- P0: **2.2-UNIT-070** (length), **2.2-UNIT-071** (CSPRNG source), **2.2-UNIT-072** (hash format), **2.2-UNIT-074** (Redis SET semantics), **2.2-UNIT-077** (brute lockout), **2.2-INT-021** (one-shot), **2.2-INT-024** (DEL-before-SET atomicity).
- P2: boundary scenarios **2.2-BLIND-BOUNDARY-006/007**.

**References:** [Source: Q2 ruling + TS-CONS-006 + OWASP ASVS L2 V3.4.1]

### SEC-010: Refresh-Token Replay (no family rotation) — **High (15)**

**Category:** Security · **Probability:** 3 · **Impact:** 5

**Description:** Refresh tokens TTL=30d are long-lived — if leaked (e.g., from a misconfigured logging system, browser exfiltration before HttpOnly takes effect, MITM on non-HTTPS dev/staging) attacker indefinitely re-derives access tokens. Without reuse-detection, the legitimate user and attacker silently coexist.

**Mitigation Strategy:**
- **Prevention:** Per BR-3.9: each refresh has a `family_id` claim + `jti`. Redis tracks active jti per family (`auth:refresh:{family_id}:{jti}`). On `RefreshToken` RPC: DEL old jti, SET new jti (atomic, ideally via Lua/MULTI). If presented jti not in family → entire `auth:refresh:{family_id}:*` keys DEL'd (family revoked, all derived sessions killed) + audit `auth.refresh_family_compromised`.
- **Detection:** Counter `auth_refresh_family_compromised_total` (extend BR-4.8 set); Sentry capture on every reuse event.
- **Response:** Force user notification on next signin ("Recent suspicious activity — please change password") — Story 2.7+ scope; for 2.2 just revoke.
- **Owner:** Dev (auth-svc).

**Test Requirements:** P0: **2.2-UNIT-113**, **2.2-UNIT-118**, **2.2-UNIT-119**, **2.2-INT-047** (rotation happy path), **2.2-INT-048** (replay → family revoke), **2.2-BLIND-CONCURRENCY-003** (concurrent reuse race).

**References:** [Source: BR-3.9 + Auth0 refresh-token rotation pattern + OAuth 2.0 BCP RFC 9700]

### SEC-013: HIBP Fail-Open — **High (15)**

**Category:** Security · **Probability:** 3 · **Impact:** 5

**Description:** If HaveIBeenPwned API is unreachable and the HIBP client falls back to permissive accept, weak/breached passwords are admitted to the system permanently — undermining the entire NIST SP 800-63B premise (Q5 ruling).

**Mitigation Strategy:**
- **Prevention:** TS-CONS-004 — HIBP client returns `ErrHIBPUnavailable` on HTTP 5xx, timeout (3s), DNS failure. RegisterUser path treats this as `503_hibp_unavailable` to user (NOT bypass). User must retry later.
- **Detection:** Counter `auth_hibp_check_total{result="unavailable"}` (extend BR-4.8); alert if >5% of signups encounter unavailable in any 15-min window.
- **Response:** Investigate HIBP API health; if persistent outage (>1h), discuss with Architect whether to temporarily lower password policy to `len ≥ 12 + 3 character classes` (would require a Story revise — not an in-code bypass).
- **Owner:** Dev (auth-svc).

**Test Requirements:** P0: **2.2-UNIT-009**, **2.2-UNIT-010**, **2.2-UNIT-034**, **2.2-INT-004**, **2.2-BLIND-ERROR-001**.

### SEC-012: CSRF (no Origin check) — Medium (12)

**Category:** Security · **Probability:** 3 · **Impact:** 4

**Description:** Without Origin/Referer validation, a malicious site can submit signup/signin/resend forms cross-origin from a logged-in victim's browser — particularly dangerous if Next.js Server Action implicit CSRF protection is bypassed (e.g., direct REST POST to api-gateway).

### SEC-001: Plaintext Password Logged — Medium (10)

### SEC-002: Weak bcrypt Cost — Medium (10)

**Category:** Security · **Probability:** 2 · **Impact:** 5

**Description:** Dev under perf pressure (250ms SLO violated under sized pod) may be tempted to lower bcrypt cost. Even `cost=10` is ~16× faster — but ~16× weaker against offline cracking after a future DB breach. TS-CONS-001 explicitly forbids this.

- **Owner:** Dev (auth-svc).

### SEC-014: SQL Injection — Medium (10)

**Category:** Security · **Probability:** 2 · **Impact:** 5

**Description:** Although Go `pgx`/`database/sql` parameterized queries are the standard, a Dev shortcut (e.g., `fmt.Sprintf("WHERE email='%s'", email)`) bypasses defense. With direct database write access in a Story creating the `users` table, this is high-impact.

- **Owner:** Dev (auth-svc).

**Test Requirements:** P0: **2.2-UNIT-026**.

### SEC-016: Pending-Deletion Email Reuse — Medium (8)

**Category:** Security · **Probability:** 2 · **Impact:** 4

**Description:** Story 2.7 introduces `status='pending_deletion'` (grace period for user-initiated account deletion). If RegisterUser allows reuse during this window, a deleted account's identity can be hijacked by anyone who knows the email (or by the same user mid-deletion-reversal flow).

**Mitigation Strategy:**
- **Prevention:** BR-1.5 — `pending_deletion` rows take SAME response path as BR-1.4 duplicate (no signal, no row reuse). Architect Round 1 Q5 ruling confirms `locked_until` schema + status enum includes `pending_deletion`.

## Detailed Risk Analysis — Technical (4 risks)

### DATA-001: PG/Redis/SendGrid Sequencing Orphan State — Medium (9)

**Category:** Technical · **Probability:** 3 · **Impact:** 3

**Description:** RegisterUser writes to PG (users row), Redis (verification token), and notification-svc (SendEmail) in sequence. If a downstream call fails after upstream commit, state diverges: user exists but no token; or user + token exist but email never sent. AC1 Error Handling row 7 explicitly accepts the "user persisted, email failed" case (covered by Resend flow) — but other failure modes need explicit handling.

**Mitigation Strategy:**
- **Prevention:** Sequence: PG INSERT (commit) → Redis SET → notification-svc SendEmail → audit publish. On Redis failure post-PG-commit: surface `502_auth_svc_unavailable` to user (row remains, Resend recovers). On SendEmail failure: surface `500_email_send_failed` per AC1 row 7. On audit failure: silent warn (TS-CONS-009).
- **Detection:** **2.2-INT-005**, **2.2-BLIND-DATA-001**, **2.2-BLIND-DATA-002** assert observable state at each failure point.
- **Response:** Production: user-driven Resend flow heals most cases. Operational: data quality dashboard checks `count(users) where email_verified_at IS NULL AND created_at < NOW-7d` (zombies older than a week — Story 2.6 GDPR cleanup target).
- **Owner:** Dev (auth-svc).

**Test Requirements:** P0: **2.2-INT-005**, **2.2-BLIND-DATA-001**, **2.2-BLIND-DATA-002**.

### DATA-002: Soft-Lock Race Under Load — Medium (9)

**Category:** Technical · **Probability:** 3 · **Impact:** 3

**Description:** 5 parallel failed signins from same email could increment ratelimit counter past 5 simultaneously, each goroutine independently triggering UPDATE status='locked' — resulting in multiple `locked_until` writes (last writer wins; technically benign but logically wrong) + multiple `auth.account_locked` audit events. Worse: 5 concurrent signins on a soft-locked-but-expired account could each trigger self-heal UPDATE before reading the prior heal.

**Mitigation Strategy:**
- **Prevention:** Self-heal UPDATE uses conditional clause `WHERE status='locked' AND locked_until <= NOW()` (BR-4.4) — only first goroutine matches, others see 0 rows affected. Soft-lock SET uses `UPDATE WHERE status='active'` (or absorbs the redundant lock by INSERT-on-conflict-style — implementation note: prefer SELECT FOR UPDATE in same TX or rely on idempotent UPDATE).
- **Detection:** **2.2-BLIND-CONCURRENCY-002** (5 parallel failures → exactly one lock), **2.2-BLIND-DATA-003** (5 parallel self-heal → exactly one transitions).
- **Response:** If audit shows duplicate `auth.account_locked` for same user_id within 1s — race is happening, escalate to Architect for transaction-isolation review.
- **Owner:** Dev (auth-svc).

**Test Requirements:** P0: **2.2-BLIND-CONCURRENCY-002**, **2.2-BLIND-DATA-003**.

**References:** [Source: BR-3.3 + BR-4.4]
