### Story-level Scenario-ID convention

- `3.3-UNIT-{NNN}` — Go testify-style or stdlib `testing` unit; in-process composition only. Uses `httptest.NewRecorder` + `httptest.NewRequest` for the HTTP boundary; stubs the bearer-auth context via `middleware.WithAPIKeyID(...)` / `middleware.BearerWithUserID(...)` directly (NO auth-svc reach) so handler logic is tested in isolation.
- `3.3-INT-{NNN}` — Go integration; wires the real Story-3.2 `middleware.NewAPIKeyAuthenticator` + the new handler against `httptest.NewServer` with a stubbed auth-svc upstream + `alicebob/miniredis/v2` for cache. NO real Postgres / real Redis (those are Story 3.2's surface; 3.3 only borrows the wired-up middleware as a black-box dependency).
- `3.3-E2E-{NNN}` — Python `pytest` against a real-binary gateway. Located in `apps/api-gateway/tests/openai_sdk_contract_test.py`. Env-guarded via `pytest.skipif` on `HE_API_TEST_GATEWAY_URL` (BR-3.1) so unit-only runs don't fail.
- `3.3-BLIND-{CATEGORY}-{NNN}` — blind-spot scenarios tagged `[BLIND-SPOT]` per `blind-spot-categories.yaml`. Categories applicable to this Story (backend_api per `applicability.backend_api`): **BOUNDARY, ERROR, CONCURRENCY, DATA, RESOURCE** (high-priority) + **FLOW** (medium-priority).
