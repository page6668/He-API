# Test Design: 7.4 — USDC（Coinbase Commerce）集成

2026-06-09 | Turing (QA) | Level: **Comprehensive** | security_focus: **true**

> **Scope discipline (the defining lens of this design).** Story 7.4 adds the THIRD payment channel by plugging ONE `coinbase.PaymentProvider` impl into the seam Story 7.3 stood up and the Architect ratified. The exactly-once credit machinery, the `recharge_orders` pending→paid state-machine, the amount-integrity guard, the `payment.completed` producer, the provider-agnostic `credit.go` applier, the Redis mirror, and the envelope codes are **REUSED VERBATIM** and already adversarially proven by 7.3's 62-scenario suite. This design therefore **focuses the genuinely-new + risk-bearing surface**: `coinbase.CreateCheckout`, `coinbase.VerifyWebhook` (a NEW `X-CC-Webhook-Signature` HMAC scheme with **NO timestamp** → replay defence rests on the state-machine ALONE), the charge-lifecycle → `VerifiedEvent` mapping (credit on `charge:confirmed` only), and the crypto underpay/delayed/wrong-coin lanes the 7.3 fiat spine did not model. Inherited invariants are **re-asserted for the coinbase path** (not re-proven from scratch) so 7.4 is also the proof-of-reuse for 7.5/7.6.

**Level mix rationale (shift-left).** The new surface is provider-impl logic — request-shaping, signature HMAC, lifecycle→Kind mapping, money parsing — all unit-testable with `httptest`-mocked Coinbase + table-driven adversarial vectors (29 unit). The credit, idempotency, atomicity, raw-body integrity, and route-auth invariants are component-boundary concerns proven at integration with `pgxmock`/`miniredis` (23 int). E2E is reserved for the two highest-value full-stack lanes — the recharge→confirm→credit happy path and the forged-webhook security proof (2 e2e). Heavy E2E is deliberately avoided: the spine it would exercise is already covered by 7.3.

### AC3: Coinbase webhook 安全 — X-CC-Webhook-Signature verification + inherited exactly-once backbone

| ID | Lvl | Pri | Test | Why (level justification) |
| --- | --- | --- | --- | --- |
| 7.4-UNIT-020 | U | P0 | Valid signature: `VerifyWebhook` computes lowercase-hex `HMAC-SHA256(rawBody, WEBHOOK_SECRET)`, constant-time matches `X-CC-Webhook-Signature` → parses + maps → `VerifiedEvent` | Pure crypto + parse; deterministic with a known secret/body/digest vector |
| 7.4-UNIT-021 | U | P0 | **[FORGED]** Invalid signature → `provider.ErrSignatureInvalid`; the body is **NEVER** parsed into any money action | Adversarial pure unit; the load-bearing forgery fence (BR-W-1) |
| 7.4-UNIT-022 | U | P0 | **[FORGED]** Absent `X-CC-Webhook-Signature` header → `ErrSignatureInvalid` | Adversarial pure unit; missing-credential path |
| 7.4-UNIT-023 | U | P0 | **[FORGED]** Tampered body (signature computed over different bytes than received) → `ErrSignatureInvalid` | Adversarial pure unit; amount/charge tamper detection at the HMAC layer |
| 7.4-UNIT-024 | U | P1 | Constant-time compare via `hmac.Equal` (NOT `==`/`bytes.Equal` on the hex string) — timing-safe | Defensive contract assertion; unit-asserts the compare primitive |
| 7.4-UNIT-025 | U | P1 | **[FORGED]** Empty raw body (+ any signature) → `ErrSignatureInvalid` / no-op (never a credit) | Boundary adversarial unit |
| 7.4-UNIT-026 | U | P2 | Signature format: uppercase-hex or non-hex header → reject (lowercase-hex contract, BR-W-2) | Pure format-guard branch; low-likelihood, cheap |
| 7.4-UNIT-027 | U | P1 | Secret discipline: on any Coinbase/verify error, neither `COINBASE_COMMERCE_API_KEY` nor `_WEBHOOK_SECRET` appears in the error/log (generic wrapping); payload carries NO card PAN (crypto no-PAN, trivially true) | Pure assertion over error strings; secret-leak + PCI boundary (BR-W-6/W-7) |
| 7.4-INT-020 | I | P0 | The `POST /v1/billing/webhooks/coinbase` route is mounted **OUTSIDE** the bearer/JWT chain (reachable with no auth token — the signature is the sole credential, 4.7 `/public/*` precedent) | Route-auth wiring is an integration concern (middleware chain) |
| 7.4-INT-021 | I | P0 | Raw-body integrity: the gateway `billing_webhook.go` proxy forwards the EXACT bytes Coinbase signed (byte-for-byte, no re-serialize/normalize) so the downstream HMAC verifies | Cross-process byte-fidelity (gateway→payment-svc); only provable at the boundary (BR-W-3) |
| 7.4-INT-022 | I | P0 | **[FORGED]** Forged-signature POST → `400_webhook_signature_invalid`, **zero** `recharge_orders` mutation, **zero** balance change | End-to-end forgery rejection across handler→applier→PG (no-side-effect proof) |
| 7.4-INT-023 | I | P0 | **[REPLAY — no-timestamp lane]** A captured VALID `charge:confirmed` re-POSTed later (signature STILL valid — no freshness window) → the `recharge_orders` pending→paid state-machine makes it a no-op credit → **exactly one** credit total | ⚠️ The signature alone cannot detect replay (BR-W-4); the state-machine is the SOLE fence — must be proven at the persistence boundary. **P0.** |
| 7.4-INT-024 | I | P0 | Provider 2xx discipline: verified+already-processed → **200** (Coinbase stops retrying); verification failure → **400**; transient processing error (PG down) → **5xx** (Coinbase redelivers) | HTTP-status contract across the handler; drives at-least-once redelivery correctness (BR-W-5) |
| 7.4-INT-025 | I | P0 | **[SEAM PARITY / proof-of-reuse]** `coinbase` satisfies the SAME `PaymentProvider` contract (Name/CreateCheckout/VerifyWebhook); the recharge handler + `credit.go` stay provider-agnostic — **no `"coinbase"` branch leaks downstream** | Architectural-invariant assertion (the proof 7.5/7.6 can follow the additive pattern); a static/integration check of the call graph (BR-A-1 / BR-C-5) |
| 7.4-E2E-020 | E | P0 | **[FORGED — security E2E]** Forged Coinbase signature, full stack → 400, zero balance change, zero `recharge_orders` mutation | Highest-severity fraud path; deserves a full-stack proof beyond the integration check |

## Blind Spot Scenarios [BLIND-SPOT]

> Backend-API + cross-service story → applicable categories: **BOUNDARY, ERROR, CONCURRENCY, DATA, RESOURCE, FLOW**. Money-correctness + forgery-resistance concentrate the high-value blind spots in DATA (exactly-once, atomicity, amount-integrity) and ERROR (the new external Coinbase dependency).

| 7.4-BLIND-BOUNDARY-001 | BOUNDARY | P0 | U | `amount ≤ 0` / `"0.00"` → `400_invalid_payment_request` before any provider call | BOUNDARY-002 |
| 7.4-BLIND-BOUNDARY-002 | BOUNDARY | P1 | U | `amount` unparseable / non-decimal (`"abc"`, `""`) → `400_invalid_payment_request` | BOUNDARY-001/005 |
| 7.4-BLIND-BOUNDARY-003 | BOUNDARY | P1 | U | `currency` ∉ enabled set (e.g. `"EUR"`) → `400_unsupported_currency` (MVP {USD}) | BOUNDARY-005 |
| 7.4-BLIND-BOUNDARY-004 | BOUNDARY | P1 | U | `provider` ∉ {stripe,paypal,coinbase} (e.g. `"usdc"`, `"btc"`) → `400_unsupported_payment_provider` | BOUNDARY-005 |
| 7.4-BLIND-BOUNDARY-005 | BOUNDARY | P2 | U | `amount` at sane ceiling `+1` → reject (overflow / abuse guard) | BOUNDARY-004 |
| 7.4-BLIND-ERROR-001 | ERROR | P0 | U | Coinbase `POST /charges` returns 4xx → wrapped error (**no secret leak**) → `402_payment_failed`; no order left dangling-as-paid | ERROR-002 |

| 7.4-BLIND-ERROR-004 | ERROR | P1 | U | Coinbase returns malformed JSON / missing `hosted_url` → error (no half-built `CheckoutResult`, no pending order claimed) | ERROR-003 |
| 7.4-BLIND-ERROR-005 | ERROR | P0 | I | PG down while applying credit → **5xx, do NOT ACK** → Coinbase redelivers; idempotent re-apply credits exactly once | ERROR-002/004 |
| 7.4-BLIND-DATA-001 | DATA | P0 | I | **Exactly-once**: the SAME `charge:confirmed` delivered twice → zero-row UPDATE on the 2nd → **one** credit | DATA-001 |
| 7.4-BLIND-DATA-002 | DATA | P0 | I | **Atomicity**: status-flip + balance-credit commit in ONE tx; a forced failure mid-apply → BOTH rolled back (no half-credit), redelivery re-credits once | DATA-001 |
| 7.4-BLIND-DATA-003 | DATA | P0 | I | **Underpay**: `charge:confirmed` with `settled < intent` (49.50 for a $50 charge) → inherited amount-integrity guard parks (stay pending + alert) + **NO credit** | DATA-001 |
| 7.4-BLIND-DATA-004 | DATA | P1 | I | **Overpay**: `settled > intent` → park (settled≠intent; partial/refund DEFERRED, Q-UNDERPAY) | DATA-001 |
| 7.4-BLIND-DATA-005 | DATA | P1 | I | **Wrong-coin**: a non-USDC / non-USD-equivalent settlement → treated as currency/amount mismatch → park (Q-COINS) | DATA-002 |
| 7.4-BLIND-CONCURRENCY-001 | CONCURRENCY | P0 | I | Two simultaneous `charge:confirmed` deliveries for the same order race → the pending→paid row lock yields **exactly one** credit | CONCURRENCY-002 |
| 7.4-BLIND-CONCURRENCY-002 | CONCURRENCY | P1 | I | A Coinbase charge id equal in value to a Stripe/PayPal charge id does NOT collide — `UNIQUE(payment_provider, external_order_id)` is per-provider | CONCURRENCY-002 |
| 7.4-BLIND-RESOURCE-001 | RESOURCE | P1 | I | Best-effort Redis mirror `INCRBYFLOAT` fails AFTER the PG commit → the durable PG credit stands, failure logs+alerts, the Redis connection is released (no leak) | RESOURCE-001 |
| 7.4-BLIND-FLOW-001 | FLOW | P1 | I | Out-of-order delivery: `charge:confirmed` arrives BEFORE `charge:created`/`charge:pending` → still credits exactly once; late `pending` is a no-op | FLOW-003 |

## Execution Order

1. **P0 Unit** — signature verify (021/022/023), lifecycle mapping (010/011/013/015/016), request/response shaping (001/002/005), boundary/error guards (BOUNDARY-001, ERROR-001)
2. **P0 Integration** — exactly-once + atomicity + underpay (DATA-001/002/003), replay (INT-023), credit-one-tx (INT-010), USD pass-through (INT-011), pending no-credit (INT-012), forged (INT-022), route-auth (INT-020), raw-body (INT-021), 2xx discipline (INT-024), seam parity (INT-025), PG-down (ERROR-005), concurrency (CONCURRENCY-001), registry/recharge (INT-001/002)
3. **P0 E2E** — recharge→confirm→credit (E2E-001), forged security (E2E-020)
4. **P1** (incl. blind-spot) — remaining unit/integration
5. **P2** — UNIT-026, BOUNDARY-005
