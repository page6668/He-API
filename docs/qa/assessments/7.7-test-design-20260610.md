# Test Design: 7.7 — 自动充值 + 余额预警 + 月度账单 PDF

2026-06-10 | Turing (QA) | Level: **Comprehensive** | security_focus: **true**

> **✅ Design complete — P0 + P1 + P2 tranches delivered.** Per the prioritized-output rule the **P0 (critical / must-test)** lane was designed first (above) as a self-contained gating batch; this finalized revision adds the **P1 (core journeys / important variations)** and **P2 (secondary / ops / reversibility)** tranches plus the BOUNDARY/FLOW/RESOURCE blind-spot long tail. With the design complete the **two-phase status transition (AwaitingTestDesign → TestDesignComplete → Approved)** is now executed and the `*develop-story` handoff issued. The scoped **Risk Profile is complete** (`docs/qa/assessments/7.7-risk-profile-20260610.md`, 17 risks: 0 Critical / 2 High / 13 Medium / 2 Low) and every risk maps to ≥1 scenario below.

> **Scope discipline (the defining lens of this design).** Story 7.7 is the operational-convenience layer **on top of** the money primitives — it adds **no new money SoT and no new credit path**. The auto-recharge CREDIT flows through the **7.3 exactly-once webhook fence VERBATIM** (`recharge_orders` pending→paid + `balances.current_usd += settled` in ONE PG tx) — already adversarially proven by the 7.3/7.4/7.5/7.6 suites. This design does **NOT** re-prove that spine; it re-asserts each inherited invariant **once** for the 7.7 trigger path and **focuses the genuinely-new surface**, which is concentrated in five first-on-the-platform capabilities (all Architect-ratified, Round 1, 2026-06-10):
>
> 1. **⭐ FIRST off-session / merchant-initiated charge** — `PaymentProvider.ChargeOffSession(pmToken, amountUSD)` confirms a Stripe `off_session` PaymentIntent with **no user present** against a **stored reusable charge-authorization token** (Stripe-card-only; non-card → `ErrOffSessionUnsupported`). The 7.3 seam was on-session checkout-redirect only.
> 2. **⭐ FIRST stored charge-authorization token** — `he_api.payment_methods` holds ONLY the opaque Stripe PaymentMethod token (PCI §8.4 SAQ-A: token-only, **NEVER a PAN**); the token is a **standing authorization to pull funds** → cross-user-binding rejection + token-never-logged + token-only-no-PAN are first-class **P0 security lanes**.
> 3. **⭐ FIRST auto-recharge storm fence** — the dominant correctness risk. Concurrent debits each tripping the threshold MUST fan out into **AT MOST ONE** in-flight top-up. Architect ruling (Q-TRIGGER): Redis `SETNX autorecharge:lock:user:{id}` is the TTL-bounded fast gate **AND** a DB-level pending-auto-order guard is the **durable fence** (must survive Redis loss). BOTH are load-bearing — the money-IN analogue of the 7.1 exactly-once debit fence.
> 4. **⭐ FIRST scheduled monthly billing job + FIRST PDF artefact** — a dedicated `apps/billing-svc/cmd/monthly-invoice/main.go` **K8s CronJob binary** (`0 0 1 * *` UTC, Architect OVERRULE of the in-process default; mirrors `cmd/fx-refresh`). `invoices` UNIQUE(user_id, period) + INSERT ON CONFLICT DO NOTHING is the **exactly-one-per-user-month** fence (guards CronJob retry/backoff). PDF via pure-Go `go-pdf/fpdf` → the gdpr_export OSS `Uploader` precedent → owner-only proxy-stream (IDOR → 404).
> 5. **FIRST proactive low-balance alert** — REUSES the 5.4 `cap_threshold.go` once-per-episode SETNX dedupe + localized SendGrid template VERBATIM; the genuinely-new bit is the **suppress-when-auto-recharge-succeeds** branch and the Q-ALERT-THRESHOLD env-default fallback (auto-recharge OFF/unset).

**Level mix rationale (shift-left).** The new logic is provider-impl + decision logic — off-session request-shaping, the storm-fence decision, the Q-ALERT-THRESHOLD resolution, the period-boundary + aggregation math, the auto-disable counter, money string-decimal discipline — all unit-testable with `httptest`-mocked Stripe + an ephemeral SetupIntent/PaymentMethod fixture (no real Stripe key, `[[project_toolchain_env_limits]]`). The **load-bearing invariants are component-boundary concerns** and concentrate at integration: the **storm fence** (Redis `miniredis` + `pgxmock` — concurrent debits → one `recharge_orders`), the **durable DB pending-order guard** (Redis-loss path), the **7.3 credit reuse** (Kafka → applier → PG one-tx), **invoice exactly-once** (cron retry → ON CONFLICT), **accuracy reconciliation** (vs `GET /v1/usage`), and the **IDOR / cross-user-binding** authorization guards. E2E is reserved for the three highest-value full-stack proofs (auto-recharge journey incl. at-most-one burst, invoice journey incl. exactly-once-on-rerun, and the adversarial security lane). Heavy E2E is deliberately avoided — the credit spine it would exercise is already owned by 7.3/7.4/7.5/7.6.
