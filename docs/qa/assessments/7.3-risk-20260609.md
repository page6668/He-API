## Executive Summary

**Total Risks Identified:** 23
**Risk Distribution:**
- Critical (20-25): **0**
- High (13-19): **2**
- Medium (6-12): **20**
- Low (1-5): **1**

**Top 3 Risks:**
1. **SEC-001**: Forged webhook mints free balance (Score: **15** High)
2. **DATA-001**: Double-credit on webhook redelivery — exactly-once failure (Score: **15** High)
3. **SEC-007** / **TECH-003**: Raw-body normalization breaks HMAC / PayPal thin-REST verification gaps (Score: **12** Medium, tied)

**Inherent profile:** This story credits money on an inbound, unauthenticated-but-signed surface that providers deliver **at-least-once**. The two dominant risks are co-equal: **forgery** (a fabricated webhook = direct financial fraud) and **double-credit** (a redelivered genuine webhook = financial-integrity defect). Both are *fully mitigable* by the Architect-ratified design (mandatory signature verification + the `recharge_orders` pending→paid state-machine + `UNIQUE(provider, external_order_id)`), so residual risk after the P0 test lanes pass is **Low** — but the inherent score is High because this is a *first-realisation* surface with no prior pattern in the codebase to lean on.

**Recommendation:** Proceed with development — **Conditional**. Conditions: (1) every P0 adversarial scenario (forged / replay / tamper / double-credit / atomicity) is GREEN before merge; (2) the two deferred operational gaps (OPS-003 no-reconciliation, OPS-001 pending-leak) are explicitly accepted by PO as conscious post-MVP follow-ups, not silent omissions.

## Detailed Risk Analysis

### SEC-001: Forged webhook mints free balance — **HIGH (15)**

**Category:** Security · **P:** 3 (Possible — first webhook surface, no prior pattern) · **I:** 5 (Critical — direct financial fraud)

**Description:** The webhook routes are mounted OUTSIDE the bearer/JWT chain (the provider signature is the sole credential). An attacker POSTs a fabricated `payment_intent.succeeded`/`checkout.session.completed` to `/v1/billing/webhooks/{stripe,paypal}`. If signature verification is missing, ordered-after-parsing, or wrong, the forged body credits free balance.

**Mitigation:**
- **Prevention:** Mandatory provider-signature verification **BEFORE any body processing** (BR-W-1). Stripe `webhook.ConstructEvent` (HMAC-SHA256 over `timestamp.payload`, constant-time, timestamp tolerance); PayPal `verify-webhook-signature`. Unverified → 400, body NEVER parsed into a money action.
- **Detection:** `payment_webhook_rejected{reason:'signature'}` metric + non-PII slog; alert on a rejection-rate spike.
- **Response:** Rotate the webhook signing secret; the `recharge_orders` state-machine bounds blast radius (a forged event for a non-existent order finds no pending row).
- **Owner:** Dev

**Test Requirements:** `7.3-UNIT-006` (invalid/absent/tampered → reject, body never parsed), `7.3-INT-018` (forged → `400_webhook_signature_invalid` + metric, zero DB mutation), **`7.3-E2E-003`** (forged E2E → 400, zero balance change). **[P0]**

**References:** SM `security_analysis` vector 1; Architect Q-WEBHOOK-VERIFY ruling; Story 4.7 `/public/*` precedent; security.md §8.4.

### DATA-001: Double-credit on webhook redelivery — **HIGH (15)**

**Category:** Data/Financial · **P:** 3 (Possible — providers redeliver at-least-once *by design*; the fence MUST hold) · **I:** 5 (Critical — financial-integrity defect, every redelivery doubles funds)

**Description:** Stripe + PayPal redeliver webhooks on any non-2xx and on their own retry policy. A genuine `paid` event delivered twice must credit balance exactly once. A missing/incorrect idempotency fence credits on every redelivery.

**Mitigation:**
- **Prevention:** The credit applies ONLY on a `pending→paid` transition — `UPDATE recharge_orders SET status='paid',paid_at=NOW() WHERE id=$1 AND status='pending'`; zero rows ⇒ already-credited ⇒ skip. Status-flip + balance-credit in ONE PG tx. PLUS `UNIQUE(payment_provider, external_order_id)` so two orders cannot bind one charge.
- **Detection:** Reconciliation invariant `SUM(paid order amounts, USD-equiv) − SUM(usage_ledger debits) ↔ balances.current_usd`; alert on drift.
- **Response:** The UNIQUE constraint + state-machine make a double-credit structurally impossible once correct; a drift alert triggers manual reconcile.
- **Owner:** Dev

**Test Requirements:** **`7.3-INT-013`** (same event twice → one credit), **`7.3-INT-016`** (UNIQUE fence), `7.3-E2E-004` (replay → idempotent no-op). **[P0]**

**References:** SM `data_sync_analysis` item 2; Architect Q-CREDIT-IDEMPOTENCY ruling (UNIQUE upgrade APPROVED); 7.1 exactly-once-debit mirror.

### SEC-002: Replay of a captured valid webhook — **MEDIUM (12)**

**Category:** Security · **P:** 3 · **I:** 4

**Description:** A captured valid webhook is re-POSTed (possibly much later) to double-credit. Distinct from DATA-001 because the signature is *genuine*.

**Mitigation:** Defence in depth — (a) Stripe timestamp-tolerance rejects a stale signature (freshness); (b) the `pending→paid` state-machine makes a still-fresh duplicate a no-op credit. Neither is relied on alone (BR-W-4).

**Test Requirements:** `7.3-UNIT-007` (stale-timestamp reject), `7.3-INT-013` (duplicate no-op), **`7.3-E2E-004`** (replay E2E). **[P0]**

### SEC-007: Raw-body normalization breaks HMAC — **MEDIUM (12)**

**Category:** Security · **P:** 3 (the gateway is a NEW proxy hop; the temptation to `json.Unmarshal` is real) · **I:** 4

**Description:** HMAC verification requires the EXACT raw bytes the provider signed. Per the Architect Q-WEBHOOK-INGRESS ruling, the gateway hosts the public route as a **transparent reverse proxy** forwarding bytes verbatim to payment-svc's own HTTP webhook handler. If any middleware (gateway included) re-serializes/normalizes the body, verification fails — best case rejects ALL webhooks (availability outage on the credit path), worst case a normalization that "happens to" pass weakens the credential.

**Mitigation:** **Prevention:** `httputil.ReverseProxy` (or byte-faithful forward); the gateway handler must NOT buffer-decode. **Detection:** the byte-faithful-proxy test asserts a re-serialized body FAILS HMAC. **Owner:** Dev.

**Test Requirements:** **`7.3-INT-012`** (re-serialized body FAILS HMAC — proves no-deserialize contract), `7.3-INT-011` (routes outside bearer). **[P0]**

**References:** Architect ruling Q-WEBHOOK-INGRESS + Low-item m1 resolution.

### TECH-003: PayPal thin-REST client verification gaps — **MEDIUM (12)**

**Category:** Technical · **P:** 3 (PayPal's official Go SDK is unmaintained → hand-rolled `net/http` client per Q-SDK ruling) · **I:** 4

**Description:** PayPal verification (`/v1/notifications/verify-webhook-signature` — transmission id/time/cert-url/auth-algo) is built on a thin REST client, not a battle-tested SDK. Edge cases (cert-chain rotation, clock skew, malformed transmission headers) can silently mis-verify.

**Mitigation:** **Prevention:** mirror the Stripe verification contract exactly through the `PaymentProvider.VerifyWebhook` seam (parity). **Detection:** adversarial parity tests with the Stripe lane. **Response:** fail-closed (unverified → 400). **Owner:** Dev.

**Test Requirements:** **`7.3-UNIT-008`** (PayPal valid→ok / invalid→reject, parity with Stripe), `7.3-INT-005` (PayPal seam parity). **[P0/P1]**

### SEC-003: Amount tampering — **MEDIUM (10)**

**P:** 2 · **I:** 5 · **Mitigation:** credit the **provider-confirmed settled amount** from the verified webhook, NEVER the client-supplied create-order intent. On `settled ≠ intent`: leave `status='pending'` (NOT `paid`, no new enum), emit `payment_amount_mismatch` alert, 200-ACK the provider (m2 ruling). **Tests:** **`7.3-INT-017`**, `7.3-E2E-005`. **[P0]**

Registered in `docs/dev/secrets`. **Tests:** `7.3-UNIT-010` (constant-time compare + secrets absent from slog). **[P1]**

### OPS-003: No reconciliation sweep — **MEDIUM (9)**

**P:** 3 · **I:** 3 · **Description:** Q-RECON deferred — 7.3 relies solely on webhooks. A permanently-lost webhook (provider gives up after its retry budget) leaves a paid-at-provider order stuck `pending` → un-credited funds the user paid for. **Mitigation:** **Detection:** alert on aged-`pending` orders with a known provider charge; **Response:** a periodic reconcile job is the named follow-up (addable without schema change). **Owner:** PO must consciously accept the defer. **Tests:** out-of-scope for 7.3 (flagged). **[accept-risk]**

### SEC-005: Cross-user order binding — **MEDIUM (8)**

**P:** 2 · **I:** 4 · **Mitigation:** `recharge_orders` binds order→user SERVER-SIDE at create time (from the authenticated session, never client-supplied); the webhook resolves the user via OUR order id (provider metadata), never a client-asserted user_id. **Tests:** `7.3-INT-003`, **`7.3-E2E-006`**. **[P0/P1]**

### TECH-005: Kafka offset-after-commit bug — **MEDIUM (8)**

**P:** 2 · **I:** 4 · **Mitigation:** consumer commits its offset ONLY post-PG-commit (at-least-once + idempotent apply — 7.1 BR-D-2 cascade). **Tests:** `7.3-INT-020`, `7.3-BLIND-ERROR-002` (PG-down → offset not committed → redelivery). **[P0]**

### BUS-002: Provider checkout failure UX — **MEDIUM (8)**

**P:** 2 · **I:** 4 · **Mitigation:** provider `CreateCheckout` error → `402_payment_failed` (not 502), no dangling-as-paid order; the credit fires only on a confirmed webhook, so a failed checkout never credits. **Tests:** `7.3-INT-006`, `7.3-BLIND-ERROR-001`. **[P1]**

### OPS-001: Pending-order leak — **MEDIUM (8)**

**P:** 4 (every abandoned checkout leaves a pending row) · **I:** 2 (inert — no credit until paid) · **Mitigation:** Q-PENDING-CLEANUP deferred; pending rows are harmless for correctness. A `pending→expired` cron (reuse 5.4/7.2 CronJob pattern) is the named follow-up. **Owner:** PO accept. **[accept-risk]**

### DATA-004: CNY→USD conversion drift — **MEDIUM (6)**

**P:** 2 · **I:** 3 · **Mitigation:** `shopspring/decimal` HALF-UP, never float; conversion at the latest 7.2 `fx_rate` at settlement. **Lower exposure:** the endpoint enables USD-ONLY in 7.3 (m3), so the path is built+tested but not user-reachable until 7.5/7.6. **Tests:** `7.3-UNIT-003`. **[P0 unit, low live exposure]**

### DATA-005: Redis mirror drift — **MEDIUM (6)**

**P:** 3 · **I:** 2 · **Mitigation:** PG is authoritative; Redis `balance:user:{id}:realtime` is a DERIVED best-effort mirror INCR'd post-commit; a failure logs+alerts and self-heals on reconcile (7.1 BR-D-3). `GET /v1/balance` reads PG, so a stale mirror never produces an authoritative wrong answer. **Tests:** `7.3-BLIND-ERROR-003`. **[P1]**

### BUS-001: RAIL/TIER boundary breach — **MEDIUM (6)**

**P:** 2 · **I:** 3 · **Mitigation:** Q-SUBSCOPE ruling — a paid subscription marks `subscriptions.status=active` ONLY; NO balance credit, NO entitlement/rate-limit/Beta flip (that is 7.8 reading this row). **Tests:** **`7.3-INT-010`** (asserts no balance credit + no entitlement change). **[P0 boundary]**

### OPS-002: Amount-mismatch disposition runbook — **MEDIUM (6)**

**P:** 3 · **I:** 2 · **Mitigation:** the `payment_amount_mismatch` alert (m2) parks the order `pending`; document the manual-disposition step in `docs/dev` so an on-call knows the parked-order workflow. **Owner:** PO/Dev. **[doc follow-up]**

### OPS-004: Migration 0010 reversibility — **MEDIUM (6)**

**P:** 2 · **I:** 3 · **Mitigation:** additive (CREATE TABLE + indexes only, no ALTER/DROP), reversible (Atlas dynamic down drops subscriptions then recharge_orders), non-destructive; `atlas.sum` row; `atlas migrate validate` + round-trip up/down in CI. **Tests:** `7.3-INT-016` (UNIQUE), T6.2. **[P0 CI]**

### TECH-004: otel version-pin breakage — **LOW (4)**

**P:** 2 · **I:** 2 · **Mitigation:** `go get pkg@ver` for new payment-svc deps; do NOT re-tidy the workspace ([[project_otel_version_pin_gotcha]]). **[Dev discipline]**

## Risk Mitigation Roadmap

### Immediate Actions (Before / Early Development)
1. **SEC-001 / SEC-007:** Land signature-verification + byte-faithful proxy FIRST — they gate the entire webhook surface (T3.1/T3.2/T3.3 before T4.x credit).
2. **DATA-001 / DATA-002 / DATA-003:** Build the `pending→paid` state-machine + UNIQUE fence + one-tx atomicity as the credit core; do NOT credit outside it.
3. **SEC-004 / SEC-006:** Wire secrets env-only + slog redaction + PCI no-PAN assertion before any provider call.

### During Development
