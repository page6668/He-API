### Why "Comprehensive"

Decision 8B locks **Comprehensive** because:

- Epic-level override `epic-4-model-adapters.yaml` line 9 mandates Comprehensive for **all** Epic-4 vendor adapters regardless of per-Story complexity count.
- Per-Story complexity post-ratification = 2 (`api_changes` + `cross_service`; `new_patterns` flips FALSE after option-b scope removal). Rule 2 (Standard) is satisfied at 2, but the Epic-level override supersedes.
- Rule 4 (via `security_sensitive`) NOT triggered: `security_sensitive = false`.

Story 4.6 carries two Story-specific concerns that strengthen the Comprehensive routing even under the pure-REUSE option-a path:

1. **SIX-vendor cross-vendor regression matrix close-out (4.6-INT-009)** — the FIRST integration test that exercises ALL TEN model-id entries (`deepseek-v3`, `qwen-{max,plus}`, `moonshot-v1-{8k,32k,128k}`, `glm-4`, `doubao-{pro,lite}`, `ernie-4.0`) in one dispatch matrix. Test failure here = latent Stories 4.1-4.5 dispatch bug surfacing at the cumulative invariant. **Epic-4 DoD line 1 ("6 家模型均可通过 /v1/chat/completions 以 OpenAI 协议调通") is satisfied if and only if 4.6-INT-009 passes.**

2. **Phase-0 empirical-verification gating (OQ-4.6-1 / OQ-4.6-3 / OQ-4.6-4 / OQ-4.6-5 + Medium Issue m-2)** — Architect Round 1 conditioned the ratification on Dev capturing three `curl` outputs in `docs/dev/logs/4.6-dev-log.md` Phase 0 BEFORE T1.5 / T2.3 unblock (non-streaming response shape; streaming `stream_options.include_usage`; HTTP/2 ALPN). QA tests 4.6-UNIT-001 / 4.6-UNIT-008 / 4.6-UNIT-009 / 4.6-UNIT-016 must assert against the EMPIRICALLY-CONFIRMED Qianfan v2 behaviour, not the SM-leaned defaults. If any Phase-0 result contradicts the ratification (e.g., Qianfan v2 returns a different upstream-request-id header than `x-bce-request-id`), Dev must update the test fixture before T1.5 lands code.
