### Verification-mode mapping (this is a static GitOps deploy-wiring story)

Per story §Tasks/Subtasks + Dev Notes (`toolchain env limits`: no docker/atlas/buf locally), verification
is **static**. The three classic levels map as:

| Level | Meaning here | Mechanisms |
|-------|--------------|-----------|
| **Unit (U)** | single-artifact static assertion | `grep`/raw-text regex, single-file YAML parse, single `helm lint`, single workflow `actionlint`, Dockerfile existence + syntax |
| **Integration (I)** | cross-artifact render / cross-file consistency | `helm template <chart> -f values.yaml -f values-staging.yaml \| kubeconform -strict`, build-matrix expansion vs Dockerfile set, secretRef-keyname ↔ provider-code cross-check |
| **E2E (E)** | full static deploy-chain coherence | T8.1 tri-count closure (build ⊆ Application ⊆ values-staging), `project: he-api` reference closure, B8 out-of-scope boundary guard |

> **Skeleton convention** (matches siblings 1.2/1.6): all scenarios become vitest cases in
> `packages/shared-types/__tests__/1.7-staging-deploy-pipeline-wiring.test.ts` using the shared
> `readRepoFile` / `repoFileExists` / `loadYaml` / `readdirSync` helpers. Static (U/I) scenarios are
> real, passing-on-delivery assertions; scenarios needing a live cluster / real `argocd`/`docker`
> stay `test.skip` with a pointer to the dev log (none here strictly require runtime — all are
> statically assertable, which is the point of this story).

### Blind-spot category applicability (rationale)

Story type = **infra/config (deploy wiring)**. Applied: **ERROR** (every external dependency:
argocd endpoint, ACR registry, K8s Secret, referenced values file, Dockerfile), **BOUNDARY** (missing/
empty config inputs), **FLOW** (no-credentials CI skip paths — the non-happy "deploy without secrets"
branch), **DATA** (single-source-of-truth consistency across the four lists; no orphan/dangling refs).
**CONCURRENCY** and **RESOURCE** are **N/A** for a static-config deliverable (no runtime locks,
connections, or parallel mutation) — the parallel-build partial-failure concern is covered under
ERROR-003/004 instead. This omission is intentional, not a gap.

## Risk Coverage

No `risk-profile` document exists yet for 1.7. Given **Comprehensive** level (security-sensitive),
`*risk-profile 1.7` is the companion task and is **recommended before development** — the security
surfaces designed-against here (cluster sync credentials → AC1; TLS issuer/secret → AC5; 5 payment
secrets no-plaintext → AC7) are exactly the items a risk profile would score HIGH. P0 scenarios above
pre-emptively mitigate them; the risk profile would formalize likelihood × impact.

1. **P0 Unit** — placeholder/latest greps (001, 030, 080), credential hygiene (003, 061), existence
   (020–022, 040, 050–051, 054, 060, 070), immutability (011), schedule-lock (055), no-payment-secret (071)
2. **P0 Int** — render+kubeconform (002-int, 006, 008, 010, 011), single-source consistency (001, 005), keyname cross-check (009), dangling guards (003, 004), blind DATA-001
3. **P0 E2E** — tri-count closure (E2E-003), four-list parity (E2E-001, E2E-002), project closure (BLIND-DATA-002), B8 boundary (E2E-005)
4. **P1** (incl. blind-spot scenarios) — syncPolicy/labels reuse, comment de-drift, skip-path preservation, partial-failure semantics, chart-structure conformance
5. **P2** — sample retention, TLS-source doc, internal-svc-not-exposed, count-invariance
