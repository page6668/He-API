### Story-level Scenario-ID convention

- `3.2-UNIT-{NNN}` — Go (testify-style table) unit test; in-process composition only. Mocks: `httptest.NewServer` for the auth-svc stub, `github.com/alicebob/miniredis/v2` for in-memory Redis, pgx mock via `pgxmock` OR `testcontainers-go` for repository layer.
- `3.2-INT-{NNN}` — Go integration test; requires a real Postgres 16 (testcontainers-go) AND/OR real Redis 7.2 (testcontainers-go). Located in `apps/{svc}/internal/{pkg}/*_test.go` (test build tag NOT required; tests are colocated and parallel-safe via per-test container instances).
- `3.2-E2E-{NNN}` — Real-binary tests in `apps/api-gateway/internal/integration/bearer_auth_e2e_test.go` — spawns auth-svc + gateway child processes + testcontainers PG + Redis; budget ≤ 30s wall-clock per `go test -run=^TestBearerAuthE2E$`.
- `3.2-SEC-{NNN}` — Security-focused cross-cutting scenarios. May execute at UNIT (TC-9 log-scan) or INTEGRATION (anti-enumeration parity) level — the level is annotated per scenario.
- `3.2-BLIND-{CATEGORY}-{NNN}` — blind-spot scenarios tagged `[BLIND-SPOT]` per `blind-spot-categories.yaml`. Categories: BOUNDARY, ERROR, FLOW, CONCURRENCY, DATA, RESOURCE.

Dev MUST embed `// Scenario: {scenario_id}` Go comments at the top of each test function — `*review 3.2` greps these comments for AC traceability per Story 2.2 / 2.3 / 2.4 / 2.5 / 2.6 / 3.1 precedent.
