## Detailed Risk Analysis

### TECH-001 (R1): Upstream-failure-mode coverage incomplete — **HIGH** (Score: 16)

**Description:** The BR-1.4 mapping table (Story Dev Notes line 294) enumerates 8 upstream failure modes (5xx, connection timeout, TLS handshake, DNS, 4xx, Connect-RPC Code.{DeadlineExceeded, Unavailable, Internal}, adapter panic). A drift between the BR-1.4 specification and the implementation — e.g., upstream returning a NEW failure mode like HTTP/2 RST_STREAM, or a Connect-RPC code Story 4.1 doesn't anticipate — would leak as `500_internal_error` to the user (defensive remap per Story 3.6 `openaierr.Write` BR-1.4 fallback) OR worse, as a malformed envelope.

**Probability: 4 (High)** — DeepSeek is a new upstream; we have not exercised every failure mode against the real `api.deepseek.com` (E2E-007 is opt-in). Real-world upstreams emit failure modes we cannot predict.

**Impact: 4 (High)** — A regression here is silent: the user sees a generic 500, but ops cannot triage because the slog attributes don't carry the upstream root cause. R1 is precedent-setting for Epic 4 (Stories 4.2-4.6 inherit the BR-1.4 mapping logic).

**Mitigations:**

1. **CHAOS suite (CHAOS-001..006)** — Toxiproxy fault matrix injected between adapter and upstream-fake covers the 6 named failure modes; nightly CI runs catch regressions.
2. **Unit-tier mapping table (UNIT-014/015/016)** — handler adapter-branch tests every Connect-RPC code → HTTP status mapping in isolation.
3. **Integration-tier negative paths (INT-003/004/014/015/016)** — upstream 5xx, upstream 401, missing usage, unknown model, adapter pod down.
4. **Contract-tier SDK error surface (CONTRACT-004/005)** — SDK-observed error shape across the gateway↔adapter hop.
5. **M2 disambiguation (Architect Round 2)** — slog attribute `upstream_error_kind ∈ {"auth_revoked","quota_exhausted","upstream_5xx","upstream_timeout","tls","dns"}` enables ops alerting routes.

**Residual Risk:** Low — provided CHAOS suite passes nightly AND M2 disambiguation is wired into the slog attributes.

**Required Test Gates Before Dev → Review:**

- ✅ CHAOS-001..006 (six Toxiproxy fault modes — must be green on `// +build chaos` nightly run)
- ✅ UNIT-014/015/016 (handler adapter-branch fanout)
- ✅ INT-003/004/014/015/016 (negative paths at integration tier)

### TECH-002 (R2): Token-usage drift undetected — **HIGH** (Score: 12)

**Description:** Story 4.1's BR-3.1 establishes upstream-as-oracle for token usage; the adapter MUST NOT re-tokenise to "verify". If DeepSeek emits drifting `usage` values (vendor-side bug — e.g., `completion_tokens=0` for a non-empty content response), our adapter trusts the count. Without surface detection, billing-svc (Epic 7) will silently undercharge / overcharge based on the drift.

**Probability: 3 (Medium)** — vendor-side bugs DO happen (OpenAI, Anthropic, and Google have all had token-accounting regressions in 2024-2026); DeepSeek is no different.

**Impact: 4 (High)** — silent revenue impact compounded across the billing chain (Epic 7 + quota-svc Epic 5). Detection lag could be hours-to-days.

**Mitigations:**

1. **UNIT-034..039** — Normaliser constraint violations (negative tokens, total ≠ sum) caught at unit tier.
2. **UNIT-040 BR-3.6 log** — `event=adapter_chat_request_end` carries `prompt_tokens/completion_tokens/total_tokens` — this IS the audit trail Ops monitoring uses to detect drift.
3. **INT-013 fixture replay** — ~20-fixture set validates oracle invariant against canonical DeepSeek shapes.
4. **INT-014 missing-usage hostile path** — adapter HARD-fails (Connect-RPC `Code.Unavailable`) rather than silently emitting `usage=null`.
5. **E2E-007 live fixture replay** — gated by `HE_API_DEEPSEEK_LIVE=1`, runs against real `api.deepseek.com` for the ~20 fixtures.
6. **BLIND-DATA-002** — three-way equality (adapter slog == gateway body == SDK chunk) catches any mid-chain corruption.

**Residual Risk:** Medium — the oracle policy itself (BR-3.1) is the open vulnerability; we trust upstream by design. Mitigation is OPERATIONAL (BR-3.6 log + Grafana alert on `total_tokens=0` for non-empty content) rather than CODE.

**Required Test Gates Before Dev → Review:**

- ✅ UNIT-034..039 (Normaliser constraint enforcement)
- ✅ UNIT-040 (BR-3.6 log shape — the audit trail)
- ✅ INT-013/014 (fixture replay + hostile path)
- ✅ BLIND-DATA-002 (three-way equality invariant)
- ⚠️ Ops handoff: Grafana alert rule for `adapter_chat_request_end{total_tokens=0,content_length>0}` to be wired in Epic 9 (recorded as Story 4.1 → Epic 9 follow-up in Dev Open Issues)

### TECH-003 (R3): Request-id chain breaks at gateway↔adapter hop — **MEDIUM** (Score: 9)

**Description:** Story 3.6 established `X-He-Request-Id` stamping at the gateway; Story 4.1 adds a NEW Connect-RPC hop (gateway→adapter) that MUST propagate the request id. If the propagation regresses, end-to-end tracing breaks (slog records in adapter pods cannot be joined with gateway pods) and customer-support workflows that rely on the request-id-as-search-key fail.

**Probability: 3 (Medium)** — Connect-RPC header propagation is manual (no automatic-passthrough middleware); easy to forget.

**Impact: 3 (Medium)** — observability degradation, not user-facing outage; affects ops triage latency.

**Mitigations:**

1. **UNIT-040** — adapter slog `event=adapter_chat_request_end` carries `he_request_id` (extracted via `packages/go-observability/requestid.FromContext` per Architect Round 2 OQ8 lifted package).
2. **INT-005/011** — request-id propagated across gateway → adapter Connect-RPC + adapter → upstream HTTPS (non-streaming + streaming variants).
3. **CONTRACT-006** — SDK-observed request-id continuity end-to-end (four-point equality: gateway entry middleware == gateway→adapter outbound == adapter→upstream outbound == adapter slog record).
4. **BLIND-DATA-001** — three-way equality invariant (header == body field == slog attribute).

**Residual Risk:** Low — quadruple-layered detection.

### TECH-004 (R4): SSE decoder strictness — **MEDIUM** (Score: 8)

**Description:** Architect Round 2 OQ6 binding: strict-RFC SSE decoder (`data: <json>\n\n` only, error on deviation). Silent coercion would mask vendor protocol drift. False positives (decoder rejecting valid-but-unusual upstream framing) surface as 502; false negatives (decoder silently accepting malformed frames) mask vendor bugs.

**Probability: 2 (Low)** — DeepSeek's framing matches OpenAI's spec exactly per draft-time `curl` exploration.

**Impact: 4 (High)** — a decoder regression that silently coerces non-canonical framing into "successful" decode hides a vendor-side protocol drift that Stories 4.2-4.6 will inherit (the decoder is the seam for all SSE-shaped upstreams).

**Mitigations:**

1. **UNIT-021..025** — strict-RFC decoder positive + negative test matrix; malformed → error; `[DONE]` → io.EOF.
2. **INT-008** — streaming happy path through real decoder (regression guard).
3. **CHAOS-006** — malformed-frame injection via Toxiproxy `noop_toxic` rewriting upstream framing (planned but optional — chaos suite priority P1).
4. **BR-2.8 documented escape hatch** — vendor quirks open follow-up bugs in `docs/dev/issues/`, NOT silent decoder coercion.

**Residual Risk:** Low — provided the strict-RFC policy is preserved in T2.4 implementation (no `bytes.TrimRight` shortcuts that swallow trailing whitespace).

### TECH-006 (R6): Mid-stream resource leak — **MEDIUM** (Score: 9)

**Description:** Client disconnects mid-stream, or upstream RSTs mid-stream — these are the most common failure modes for the streaming path. If the adapter doesn't cleanly cancel the outbound HTTPS connection (via `req.Context()` propagation per BR-1.8) AND release its own goroutine, sustained traffic produces a goroutine leak → adapter pod OOM-kills → cascading 502s.

**Probability: 3 (Medium)** — Client disconnects are routine (mobile network drops, user navigates away mid-stream); upstream RSTs are rarer but happen during DeepSeek incident windows.

**Impact: 3 (Medium)** — resource exhaustion is observable (Grafana goroutine count + memory) and recoverable (K8s pod restart). Cumulative impact compounds over hours of sustained leak.

**Mitigations:**

1. **INT-012** — client-disconnect-mid-stream: adapter cancels outbound within 200ms; slog `event=adapter_chat_stream_client_disconnect`.
2. **CHAOS-003** — mid-stream RST after first chunk: BR-2.6 SSE error frame + clean goroutine exit.
3. **BLIND-RESOURCE-001** — connection released on every exit path (table-driven across success / 5xx / cancel / DeadlineExceeded).
4. **BLIND-RESOURCE-002** — 1000-request sustained-load no connection pool leak.

**Residual Risk:** Low — quadruple-layered (BLIND-RESOURCE-002 is the long-tail catch).

---

### TECH-007 (R7): Concurrency state corruption under load — **MEDIUM** (Score: 8)

**Description:** Adapter `Chat` is called from many concurrent goroutines (one per gateway client request). Shared state — the HTTP client, the registry map, the slog logger, the upstream connection pool — must be goroutine-safe. A regression that introduces a non-thread-safe pattern (e.g., `var sharedBuf bytes.Buffer` at package level) corrupts response bodies across requests.

**Probability: 2 (Low)** — Go's stdlib HTTP client is goroutine-safe by default; the regression would have to be NEW shared state introduced in T2 implementation.

**Impact: 4 (High)** — silent response-body corruption is catastrophic — user A receives part of user B's response. Hard to detect without explicit concurrency tests.

**Mitigations:**

1. **UNIT-008** — 50 concurrent goroutines call `adapter.Chat` against same upstream fake; each receives independent ChatChunk.
2. **UNIT-011** — Registry.Resolve goroutine-safe under 100 concurrent reads.
3. **BLIND-CONCURRENCY-001** — 100 concurrent mixed stream/non-stream calls; no state corruption; no panic.

**Residual Risk:** Low — Go race detector (`go test -race`) catches most regressions; concurrency tests catch the rest.

### OPS-005 (R5): Cold-start regression — **LOW** (Score: 4)

**Description:** Architect Round 2 M5 ratified ≤ 2s adapter cold-start budget. K8s readiness probe + ArgoCD progressive rollout absorb the budget (cold pods do NOT receive traffic until ready). Regression beyond 2s is operationally annoying (slower rolling deploys) but NOT user-facing.

**Probability: 2 (Low)** — adapter is a small Go binary with no DB connections to warm up.

**Impact: 2 (Low)** — operational, not user-facing.

**Mitigations:**

1. **T6.5 cold-start bench** — re-runs Story 3.1 TC-10 harness with 2s budget for adapter.
2. **K8s readiness probe** — gates traffic until adapter is ready; absorbs cold-start.

**Residual Risk:** Acceptable — no test gate required (operational measurement).

## Risk Score Methodology

- **Probability scale 1-5**: 1=Rare (< 1% per year), 2=Unlikely (1-10%), 3=Possible (10-30%), 4=Likely (30-70%), 5=Almost certain (> 70%)
- **Impact scale 1-5**: 1=Negligible (no observable user impact), 2=Minor (operational annoyance), 3=Moderate (degraded UX or ops triage delay), 4=Major (revenue impact or trust degradation), 5=Severe (data loss / outage / security breach)
- **Score = P × I**: Critical (20-25) · High (13-19) · Medium (6-12) · Low (1-5)
