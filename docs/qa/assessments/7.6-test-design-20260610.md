# Test Design: 7.6 — 微信支付 WeChat Pay HK / Cross-border

2026-06-10 | Turing (QA) | Level: **Comprehensive** | security_focus: **true**

> **Scope discipline (the defining lens of this design).** Story 7.6 adds the FIFTH and FINAL payment channel by plugging ONE `wechat.PaymentProvider` impl into the seam Story 7.3 stood up, the Architect ratified (provider.go:2-6 names 7.6 by name; 0010_*.sql:42 reserves `"wechat"`), and Stories 7.4 (USDC, Done) + 7.5 (Alipay+, Done) already proved end-to-end. The exactly-once credit machinery, the `recharge_orders` pending→paid state-machine, the amount-integrity guard **(including the 7.5 paid-currency fix at credit.go:194-204)**, the `payment.completed` producer, the provider-agnostic `credit.go` applier **(including its `toUSD()` non-USD branch)**, the Redis mirror, and the envelope codes are **REUSED VERBATIM** and already adversarially proven by 7.3's 62-scenario + 7.4's 54-scenario + 7.5's 66-scenario suites. ⚠️ Unlike 7.5 (which justifiably *fixed* the guard), **7.6 needs ZERO credit.go change** — HKD/CNY credit out-of-the-box; this is the clean-reuse story. This design therefore **focuses the genuinely-new surface**, which is concentrated in `wechat.VerifyWebhook` and is distinct from every prior channel:
>
> 1. **⭐ The platform's FIRST ENCRYPTED webhook body** — WeChat APIv3 callbacks deliver the payment result as an **AES-256-GCM `resource`** `{algorithm, ciphertext, nonce, associated_data}` that MUST be decrypted with the symmetric `APIV3Key` **AFTER** the asymmetric signature verifies. Stripe/Coinbase HMAC + Alipay+ RSA all signed **plaintext** bodies; none was encrypted. The GCM 16-byte auth tag is a **SECOND integrity guard** under the signature — a tag mismatch (tampered ciphertext/nonce/AAD **or** a wrong key) MUST fail-closed, never parse a partial plaintext, never credit.
> 2. **WeChat APIv3 asymmetric verify (platform-cert-serial selection)** — the SAME RSA-SHA256 family 7.5 de-risked, but a **SIMPLER** signed string `<Wechatpay-Timestamp>\n<Wechatpay-Nonce>\n<rawBody>\n` (NO method/URI → **NO `r.URL.Path` canonicalisation trap** that bit Alipay+), verified with the WeChat **PLATFORM** public key **SELECTED BY** the `Wechatpay-Serial` header (an unknown serial → reject).
> 3. **HKD as a NEW fx-at-credit pair** — 7.6 is the FIRST channel to settle HKD; it drives the inherited `credit.go toUSD()` branch for HKD→USD (CNY reuses the 7.5-driven branch; USD is the pass-through).
>
> Inherited invariants are **re-asserted once for the wechat path** (not re-proven from scratch). 7.6 also closes the **5-channel seam proof** (Epic-7 DoD: "5 通道支付 … 至少各完成一笔结算").

**Level mix rationale (shift-left).** The new surface is provider-impl logic — request-shaping, outbound RSA signing, asymmetric signature verification over a simple 3-component string, `Wechatpay-Serial` platform-key selection, `Wechatpay-Timestamp` freshness, **AES-256-GCM `resource` decrypt**, `trade_state`→`Kind` mapping, and minor-unit money parsing — all unit-testable with `httptest`-mocked WeChat + an **ephemeral in-test RSA keypair** (sign callback fixtures with the test platform private key; verify with its public key) **and a random in-test 32-byte APIV3Key** (GCM-encrypt the `resource` fixture; decrypt under test) — no real WeChat key needed (`[[project_toolchain_env_limits]]`). Hence the heavy unit tilt (40 unit, of which 16 are the AC3 verify+decrypt core). The credit, idempotency, atomicity, raw-body+header integrity, fx-at-credit, and route-auth invariants are component-boundary concerns proven at integration with `pgxmock`/`miniredis` (31 int). E2E is reserved for the three highest-value full-stack lanes — the USD recharge→confirm→credit happy path, the **HKD→USD fx-credit** path (the headline new currency lane), and the forged-webhook security proof (3 e2e). Heavy E2E is deliberately avoided: the spine it would exercise is already covered by 7.3/7.4/7.5.

**Why 74 > 7.5's 66 despite being "scoped/lighter than 7.3."** The "scoped" framing (Decision 8B) means QA does NOT re-run the full generic-spine suite — it re-asserts each inherited invariant **once** for the wechat path. The count rises above 7.5 because the **encryption layer is genuinely new** and adds vectors with **no 7.5 analogue**: a happy AES-GCM decrypt + three adversarial decrypt lanes (tampered-ciphertext, tampered-nonce/AAD, **wrong-APIV3Key** → tag mismatch), the **verify-before-decrypt order-of-operations** proof (no decrypt oracle), and an encryption-layer no-side-effect integration. On the signature side 7.6 is *slightly* simpler than 7.5 (the 3-component string has no constructed-URI / `r.URL.Path` trap), but it adds the **`Wechatpay-Serial` platform-key-selection** vector, and the currency side adds a **second** new fx pair (HKD) on top of the inherited CNY. Every added scenario maps to a genuinely-new code path, not redundant spine coverage.

## Test Skeleton Note (Output 2 — deliberate deferral, documented)

The standard skeleton output is TypeScript-shaped (one throwing `test()` per scenario). For this Go workspace it is **deliberately NOT materialised as an executable `_test.go` file at test-design time**, for two compile-safety reasons (identical to the 7.4/7.5 precedent):

1. The `apps/payment-svc/internal/provider/wechat/` package **does not yet exist** (it is Dev deliverable T1.1). Instead, the **scenario IDs in this document ARE the skeleton checklist**, and the per-AC **Test Specs are already embedded in the story Tasks** (T1/T2/T3) as the Dev-facing TDD contract — the SM-seeded placeholder IDs in those tables match the authoritative IDs designed here (no Task rewrite required).
