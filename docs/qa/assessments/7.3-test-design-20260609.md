**Test levels** (Decision 8B): `unit, integration, contract, e2e`. No browser/UI lane — 7.3 is **BACKEND-ONLY MVP** (the `<PaymentMethodGrid>`/redirect/SSE wiring is a deferred Console story). "E2E" here = service-level flows over testcontainers/compose with a **mock provider** (Stripe/PayPal SDKs are never hit with real money in CI).

**Mocking posture** ([[project_toolchain_env_limits]] / [[project_otel_version_pin_gotcha]]):
- `pgxmock` (plain pgxpool, no otelpgx) for the credit-tx unit lane; a scratch PG (testcontainers) in CI for the atomicity/UNIQUE/concurrency lanes.
- `miniredis` for the realtime-mirror fan-out; a fake Kafka **or** testcontainers for the `payment.completed` producer/consumer loop.
- **Provider seam is mocked at the `PaymentProvider` interface** — `VerifyWebhook` is exercised with **canned signed payloads + the test webhook-signing-secret** (`*_TEST` per Q-SECRETS), so signature math is real but no network egress. Stripe verification uses `webhook.ConstructEvent` against a locally-HMAC'd fixture; PayPal verification is unit-tested against the thin-REST verify response (mocked HTTP).
- `buf`/`atlas`/`docker` abort locally → `he.payment.v1` + the additive `he.billing.v1 CreateRechargeOrder` RPC verified via hand-edited `*.pb.go` round-trip; `0010` migration round-trip + `atlas.sum` run on a scratch PG in CI.

### Architect Round-1 rulings folded into assertions

- **Q-WEBHOOK-INGRESS (transparent reverse proxy → payment-svc HTTP ingress):** `7.3-INT-012` is the **byte-faithful-proxy** test — it proves a re-serialized/normalized body **fails** HMAC, i.e. the gateway MUST forward raw bytes verbatim (no `json.Unmarshal`/re-marshal). `7.3-INT-011` proves the webhook routes mount OUTSIDE the bearer chain (4.7 `/public/*` precedent). No webhook gRPC exists in `he.payment.v1` (m1 resolved).
- **m2 (amount-mismatch disposition):** `7.3-INT-017` asserts the exact ruling — tampered settled≠intent ⇒ **NO credit AND order stays `status='pending'` (NOT `paid`, NO new enum value) AND `payment_amount_mismatch` metric + non-PII slog emitted AND provider gets 200-ACK** (verified event, don't trigger redelivery).
- **m3 (currency scope):** `7.3-INT-007`/`UNIT-001` assert `currency ∈ {USD}` for 7.3 → non-USD rejected `400_unsupported_currency`; `7.3-UNIT-003` separately proves the CNY→USD conversion path is **built + unit-tested** (T1.5) even though the endpoint rejects CNY until 7.5/7.6.
- **Q-AMOUNT / §5.1.2 codes:** provider `CreateCheckout`/`CreateSubscription` API error → `402_payment_failed` (NOT 502). 5xx is reserved strictly for our-own-infra failures (PG down on apply). Asserted in `7.3-INT-006` (402) and `7.3-INT-019` (5xx redelivery).
- **Q-SUBSCOPE (RAIL only):** `7.3-INT-010` asserts a paid subscription marks `subscriptions.status=active` ONLY — it does **NOT** credit `balances` and does **NOT** grant entitlements/rate-limits/Beta (that mapping is 7.8).
- **Q-REFUND (defer):** `7.3-INT-021` asserts a verified `charge.refunded`/`charge.dispute.*` webhook is **200-ACK'd but no-op** (no money reversal in 7.3).

### AC3: webhook 安全 + 精确一次入账 — signature verification + exactly-once backbone

> The financial-fraud-resistance core. Forged / replay / amount-tamper / double-credit are **first-class P0 adversarial scenarios**, not afterthoughts.

**Signature verification (T3.2 / T3.3) — the credential**

| ID | Lvl | Pri | Test | Why |
|----|-----|-----|------|-----|
| 7.3-UNIT-005 | U | P0 | Stripe: valid `Stripe-Signature` (HMAC-SHA256 over `timestamp.payload`, fresh) → verified event returned (`webhook.ConstructEvent`) | Lane (a) genuine |
| 7.3-UNIT-006 | U | P0 | Stripe: **invalid / absent / tampered** signature → reject; the body is **NEVER parsed into a money action** | `RISK-FORGE` (BR-W-1) |
| 7.3-UNIT-007 | U | P0 | Stripe: valid-but-**stale** timestamp (outside tolerance) → reject | `RISK-REPLAY` freshness (BR-W-4) |
| 7.3-UNIT-008 | U | P0 | PayPal: valid `verify-webhook-signature` → ok; invalid → reject — **adversarial parity** with the Stripe lane | Lane (j); thin-REST client (Q-SDK) |
| 7.3-UNIT-009 | U | P0 | **PCI no-PAN**: no payment endpoint accepts/stores a card PAN/CVV; only provider token + order id are persisted | `RISK-PCI` (BR-R-3/W-7, §8.4 SAQ-A) |
| 7.3-UNIT-010 | U | P1 | Constant-time compare used for the signature check (no early-exit byte compare); secrets never appear in slog output | `RISK-SECRET` (BR-W-6 redaction) |

**Ingress topology & raw-body integrity (T3.1) — Q-WEBHOOK-INGRESS ruling**

| ID | Lvl | Pri | Test | Why |
|----|-----|-----|------|-----|
| 7.3-INT-011 | I | P0 | `POST /v1/billing/webhooks/{stripe,paypal}` are mounted **OUTSIDE** the bearer/JWT chain — a request with no JWT but a valid signature is processed; the routes are not in the authed group | 4.7 `/public/*` precedent (signature IS the credential) |
| 7.3-INT-012 | I | P0 | **Byte-faithful proxy**: the gateway forwards the raw body verbatim; a re-serialized/normalized body (`json.Unmarshal`+re-marshal) **FAILS** HMAC — proving the no-deserialize contract | BR-W-2 / Q-WEBHOOK-INGRESS ruling (Architect recommendation) |
| 7.3-INT-018 | I | P0 | Forged webhook → `400_webhook_signature_invalid` envelope (NEW §5.1.2 code, registered in `openaierr.CodeMetadata` single-writer) + `payment_webhook_rejected{reason:'signature'}` metric; zero DB mutation | T3.4 (`RISK-FORGE`) |

**Exactly-once credit + amount integrity (T1.3 / T4.2 / T4.3)**

| ID | Lvl | Pri | Test | Why |
|----|-----|-----|------|-----|
| 7.3-INT-013 | I | P0 | Same `payment.completed` delivered **twice** → balance credited **ONCE** (2nd find `status='paid'` → zero-row UPDATE → skip) | `RISK-DOUBLE` exactly-once (BR-W-3) |
| 7.3-INT-014 | I | P0 | **Concurrent** duplicate delivery (two consumers, same event) → exactly ONE credit (PG `WHERE status='pending'` row-guard race) | `RISK-DOUBLE` race (CONCURRENCY) |
| 7.3-INT-015 | I | P0 | **Atomicity**: inject a failure between the status-flip and the balance-credit → **neither** persists (no half-credited order) | DATA-001 (BR-W-3 one-tx) |
| 7.3-INT-016 | I | P0 | `UNIQUE(payment_provider, external_order_id)` — two orders attempting to bind one provider charge → 2nd rejected at the constraint | Q-CREDIT-IDEMPOTENCY UNIQUE fence |
| 7.3-INT-017 | I | P0 | **Amount tampering**: settled ≠ order intent → **NO credit** AND order **stays `status='pending'`** (NOT `paid`, no new enum) AND `payment_amount_mismatch` alert emitted AND provider **200-ACK'd** | `RISK-TAMPER` (m2 ruling, BR-R-1/Q-AMOUNT) |

**Provider 2xx discipline + Kafka (T3.5 / T4.1 / T4.2)**

| ID | Lvl | Pri | Test | Why |
|----|-----|-----|------|-----|
| 7.3-INT-019 | I | P0 | Provider 2xx discipline: verified+already-processed → **200** (stop retries); bad signature → **400**; transient apply error (PG down) → **5xx** (provider redelivers) | BR-W-5 |
| 7.3-CONTRACT-002 | C | P0 | `he.payment.v1` `PaymentEvent` round-trip over hand-edited `*.pb.go` — `{order_id,user_id,payment_provider,external_order_id,settled_amount,currency,status,ts}`; `settled_amount` is string-decimal | Proto contract ([[project_toolchain_env_limits]]) |
| 7.3-CONTRACT-003 | C | P0 | NEW `he.payment.v1` package crosses no `buf breaking: FILE`; additive `he.billing.v1 CreateRechargeOrder` passes `buf breaking` (CI) | Additive-proto guarantee |
| 7.3-INT-020 | I | P0 | `payment.completed` producer emits on a **verified** event; the consumer commits its offset **only post-PG-commit** (PG-down → offset not committed → redelivery) | T4.1/T4.2 at-least-once + idempotent (DATA cross-service) |
| 7.3-INT-021 | I | P1 | `charge.refunded` / `charge.dispute.*` webhook → signature-verified + **200-ACK'd but no-op** (no money reversal; `recharge_orders` unmutated) | Q-REFUND defer ruling |

**Webhook security E2E**

| ID | Lvl | Pri | Test | Why |
|----|-----|-----|------|-----|
| 7.3-E2E-003 | E | P0 | **Forged-webhook E2E**: forged signature → 400, **zero** balance change, **zero** `recharge_orders` mutation | T5.2 (`RISK-FORGE` end-to-end) |
| 7.3-E2E-004 | E | P0 | **Replay E2E**: a captured valid webhook re-POSTed (stale timestamp) → rejected; a still-fresh duplicate → idempotent no-op credit (defence in depth) | `RISK-REPLAY` end-to-end (BR-W-4) |
| 7.3-E2E-005 | E | P1 | **Amount-tamper E2E**: provider session manipulated so settled<intent → order stays pending, no credit, alert raised | `RISK-TAMPER` end-to-end (m2) |
| 7.3-E2E-006 | E | P1 | **Cross-user E2E**: webhook resolves the user via OUR order id metadata, never a client-asserted user_id → credits the correct user only | `RISK-XUSER` (BR-R-4) |

## Coverage Validation

- ✅ Every AC has ≥1 P0 test (AC1: UNIT-001/E2E-001; AC2: INT-008/INT-010; AC3: the whole adversarial block).
- ✅ Critical paths multi-level (credit: UNIT-002/003 → INT-004/013/015 → E2E-001; signature: UNIT-005/006 → INT-012/018 → E2E-003).
- ✅ Each input field has a BOUNDARY scenario (amount, currency, provider, plan).
- ✅ Each external dependency has an ERROR scenario (provider API, PG, Redis, Kafka).
- ✅ Each multi-step process has a FLOW scenario (recharge double-submit, failed-payment).
- ✅ Security-sensitive operations have CONCURRENCY + adversarial scenarios (double-credit race, forged/replay/tamper).
- ✅ DB operations have DATA scenarios (atomicity, UNIQUE, cross-service offset).
- ⚠️ No duplicate coverage — BLIND-CONCURRENCY-001 / DATA-001 / DATA-002 are cross-refs to the core P0s, not re-implementations.
