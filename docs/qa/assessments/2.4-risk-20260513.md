## Detailed Risk Analysis

### SEC-009: Real-time phishing relay (TOTP MITM) — **ACCEPTED GAP**

**Category:** Security · **Probability:** 4 (Likely) · **Impact:** 4 (High) · **Score: 16 — High**

**Description:**
TOTP is vulnerable to real-time phishing where an attacker proxies the user's signin flow: the attacker captures the user's password + live TOTP code on a lookalike domain, then relays both to He-API within the ±1 30s validity window. Industry tooling exists (Evilginx, Modlishka, EvilProxy) that automates this. The user's 5-min mfa_token + IP/UA binding offer only weak resistance — the attacker can pre-position to use the same IP (CGNAT) and copy the UA.

**Mitigation Strategy:**
- **Prevention:**
  - **Documented as accepted gap.** TOTP cannot fully resist real-time MITM by design; only phishing-resistant factors (WebAuthn / FIDO2 / passkeys / origin-bound cryptography) eliminate this class of attack.
  - WebAuthn is explicitly OUT-OF-SCOPE per Story §Boundary lock line 45 ("WebAuthn / FIDO2 / passkeys — separate Story, post-MVP").
  - Partial defense-in-depth: IP/UA binding (BR-2.3) reduces non-targeted attack surface; out-of-band email on 2fa.enabled / disabled / recovery_used (BR-5.9) gives user post-hoc visibility.
- **Detection:**
  - User reports via support ticket (typical detection latency: hours-to-days).
  - Audit `2fa.challenge.binding_failed` HIGH for IP/UA mismatch — does not detect a true MITM that matches IP+UA but flags lower-effort attacks.
  - Production: SIEM correlation of geographic-impossibility (user in country A, 2FA challenge from country B 30s later) — Story 2.5 / observability epic.
- **Response:**
  - User-reported: invalidate sessions; force password reset + recovery code regeneration; audit-trail review.
  - WebAuthn migration tracked in `docs/prd/epic-9/vault-pki-and-transit-migration.md` follow-up (Architect §Recommendations.3) or a new Epic-9 WebAuthn Story.
- **Owner:** Architect (documents accepted gap); QA (validates documentation in ASVS L2 checklist §V2).

**Test Requirements:**
- N/A automated (gap is by design). QA verifies via `docs/qa/checkpoints/2.4/asvs-l2-checklist.md` §V2 attestation that the gap is documented + WebAuthn future-migration tracker linked.
- T9.2 threat-model walkthrough (attack #2 "Phishing kit captures TOTP + password") explicitly notes "accepted gap, documented as 'phishing-resistant 2FA = WebAuthn, future Story'".

**References:**
- [Evilginx Phishing Framework](https://github.com/kgretzky/evilginx2) — public open-source TOTP-relay tooling
- OWASP ASVS L2 V2.7.1 — Out-of-Band Verifier Requirements (TOTP exemption)
- NIST SP 800-63B §5.1.5 — AAL2 acknowledges OTP MITM susceptibility

### SEC-003: `mfa_token` replay attack post-success

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score: 15 — High**

**Description:**
If an attacker captures a valid `he_mfa` cookie (XSS, network sniff, machine compromise) AFTER the user successfully completed a TOTP challenge, replaying that mfa_token would mint additional access/refresh sessions for the attacker. Without single-use JTI enforcement, the 5-min TTL window is a meaningful attack surface.

**Mitigation Strategy:**
- **Prevention:**
  - **(LOAD-BEARING)** BR-2.2 single-use JTI: Redis DELETE happens AFTER successful code validation + token issuance. Replay of same `mfa_token` → 401_mfa_token_invalid (JTI absent from Redis).
  - BR-2.1 5-min hard cap on TTL — bounds attack window even before single-use enforcement.
  - BR-2.3 IP/UA binding adds a second defense layer (different client → 401_mfa_token_binding_mismatch).
- **Detection:**
  - Audit count: `2fa.challenge.success` per user per minute > 1 = anomaly (legitimate users challenge once per signin).
  - Test gates: P0 `2.4-SEC-003` (replay attack); P0 `2.4-UNIT-046` happy path JTI DELETE; P0 `2.4-UNIT-047` wrong code does NOT consume JTI.
- **Response:**
  - Detected: invalidate all user's `he_access` + `he_refresh` cookies; force re-signin; audit-trail review for `2fa.challenge.success` events in past 24h.
- **Owner:** Dev Team (implementation) + QA (verification).

**Test Requirements:**
- P0 `2.4-SEC-003`: replay attack — second submit with same cookie returns 401 + audit count = 1
- P0 `2.4-UNIT-046`: happy path: JTI deleted on success
- P0 `2.4-UNIT-047`: failure path: JTI NOT deleted (allows retry within ratelimit ceiling)
- P0 `2.4-UNIT-049`: 5th failure deletes JTI + locks user

**References:**
- BR-2.2 + BR-5.11 (story file lines 197-198 + 473)
- OWASP ASVS L2 V3.5 — Token-based Session Management

- **Owner:** Dev Team (implementation) + Ops (alerting).

### SEC-005: Brute-force TOTP 6-digit code

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score: 12 — Medium**

**Description:**
6-digit TOTP code has 10^6 entropy. Without rate limiting, an attacker with a valid mfa_token (e.g., compromised through phishing of the password layer) could brute-force the 6-digit code within the 5-min mfa_token TTL.

**Mitigation Strategy:**
- **Prevention:** BR-2.6 — `ratelimit:2fa:challenge:{user_id}` 5 failures/15min → soft-lock 1h. With ±1 window = ~3 valid codes out of 10^6 → expected ~166K attempts before guess; 5-attempt lockout prevents anything close.
- **Detection:** Audit `2fa.challenge.locked` HIGH spike.
- **Response:** Self-heal at locked_until; user signs in again; if pattern recurs (multiple users locked from same IP) → ops investigation.
- **Owner:** Dev.

**Test Requirements:**
- P0 `2.4-UNIT-048`: counter increments on wrong code
- P0 `2.4-UNIT-049`: 5th failure locks + audit HIGH
- P0 `2.4-SEC-005`: brute-force 10× attempts blocked at 5th
- P0 `2.4-E2E-009`: full lockout → self-heal → success E2E

**References:** BR-2.6 (story file line 201)

### SEC-006: Recovery code guessing (50-bit entropy)

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score: 12 — Medium**

**Description:**
Recovery codes are 10-char RFC 4648 base32 → ~50 bits of entropy per code, 10 codes × ~500 bits aggregate. An attacker with mfa_token could attempt to guess a recovery code; expected attempts before hit ≈ 2^49 per code (impossible by brute force). Risk is much lower than TOTP but rate-limit tightened (3/15min vs 5/15min) because each guess is more valuable.

**Mitigation Strategy:**
- **Prevention:** BR-3.6 stricter limit (3/15min lockout 1h); constant-time bcrypt-compare iterates ALL 10 rows even after match (BR-5.5 invariant).
- **Detection:** Audit `2fa.challenge.locked` for recovery-counter path.
- **Owner:** Dev.

**Test Requirements:**
- P0 `2.4-UNIT-067`: 3rd recovery failure locks
- P0 `2.4-UNIT-064`: constant-time iteration of all 10 rows (no early-cancel from errgroup)
- P1 `2.4-UNIT-105`: constant-time statistical timing test

**References:** BR-3.6 + BR-5.5 (story file lines 300, 467-468)

### SEC-010: Anti-enumeration — signin response leaks 2FA-enabled state

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 3 (Medium) · **Score: 9 — Medium**

**Description:**
If signin response distinguishes between `status='ok'` (totp_enabled=FALSE, direct dashboard) vs `status='requires_2fa'` (totp_enabled=TRUE, redirect to challenge), an unauthenticated attacker who guesses credentials of many emails can enumerate which users have 2FA enabled — useful for credential-stuffing targeting (attacker focuses on weaker-defended accounts) or pre-positioning phishing kits.

**Mitigation Strategy:**
- **Prevention:**
  - BR-5.10 (Architect): status='locked' precedence BEFORE 2FA branch — both 2FA and non-2FA locked users see identical 423 response (no 2FA-status leak).

### TECH-002: KMS decrypt cold-path latency stacks on every TOTP challenge

**Category:** Technical · **Probability:** 3 (Possible) · **Impact:** 3 (Medium) · **Score: 9 — Medium**

**Description:**
Each ChallengeTOTP call performs KMS decrypt on `users.totp_secret_encrypted`. With K8s Secret bootstrap, decrypt is local AES-256-GCM (~1ms). With future Aliyun KMS or Vault Transit, decrypt is a network round-trip (~10-50ms). Per BR Technical Constraints, KMS decrypt should be cached per-request (single decrypt per challenge) but NEVER cached cross-request (defeats envelope encryption).

**Mitigation Strategy:**
- **Prevention:** Local AES-256-GCM design (Architect Q1) keeps decrypt latency local. Per-request caching: pass decrypted secret through call-stack within a single ChallengeTOTP invocation — no global cache.
- **Detection:** p95 latency monitoring; UNIT-106 BenchmarkRecoveryCompare-equivalent for ChallengeTOTP.
- **Owner:** Dev Team.

**Test Requirements:**
- P1 integration latency: p95 < 200ms for ChallengeTOTP end-to-end (including KMS decrypt)
- Production Prometheus counter `auth_2fa_challenge_duration_seconds` (T5.4)

**References:** Story Technical Constraints §performance budget (story file line 845)
