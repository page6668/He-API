## Detailed Risk Analysis

### SEC-001: Account takeover via unverified email (Branch B link bypass)

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score: 15 — High**

**Description:**
An attacker registers a Google/GitHub account with a victim's email address (e.g., `victim@gmail.com`) — Google/GitHub allow registration without proving control of the email if the provider's verification is bypassed or the attacker controls the SMTP path. The attacker then triggers OAuth login on He-API; without proper verification-first guarding, the attacker's `(oauth_provider, oauth_subject)` would be linked to the victim's existing He-API account, granting full session access. **Industry precedent: GitLab CVE-2022-1162, Auth0 multiple OAuth linking bugs, LLM-platform takeover incidents (2024-2025).**

**Mitigation Strategy:**
- **Prevention:**
  - **(LOAD-BEARING)** Branch B.1 hard-gate: `email_verified_at IS NOT NULL` required before auto-link (Architect Round 1 Q2 ruling `(a)`).
  - **(LOAD-BEARING)** Branch B.2 → 403 `403_oauth_link_unverified` with no DB write.
  - Trust provider's own `email_verified=true` for Branch C new-user creation (Google ID token + GitHub `/user/emails` `verified=true`).
- **Detection:**
  - Audit event `auth.oauth.link.rejected_unverified` rate spike → Alertmanager warning.
  - P0 unit test `2.3-UNIT-036` verifies Branch B.2 reject path returns 403 with zero DB writes.
  - P0 E2E test `2.3-E2E-004` exercises full reject flow including i18n toast.
- **Response:**
  - If incident detected: invalidate suspect sessions; force password reset for affected `users.email`; audit-trail review for `auth.oauth.link.success` events in 24h preceding incident.
  - Architect emergency patch: tighten `email_verified_at` check (e.g., require recency).
- **Owner:** Dev Team (implementation) + QA (verification gate)

**Test Requirements:**
- P0 `2.3-UNIT-036`: Branch B.2 unverified → 403, no DB write, audit reject event
- P0 `2.3-E2E-004`: E2E unverified user toast + signin redirect
- P0 `2.3-UNIT-013`: Google `email_verified=false` rejected at provider layer
- P0 `2.3-UNIT-023`: GitHub `/user/emails` no verified primary → reject
- P0 `2.3-SEC-013`: Anti-enumeration: pending_deletion same response as unknown email

**References:**
- [GitLab CVE-2022-1162](https://about.gitlab.com/releases/2022/03/31/critical-security-release-gitlab-14-9-2-released/)
- OWASP ASVS L2 V2.7 — Out of Band Verifier Requirements
- Architect Round 1 Q2 ruling block in story `decision_8b_test_design_level.reasoning`

### SEC-002: state CSRF / forgery / replay attack

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score: 15 — High**

**Description:**
Standard OAuth 2.0 CSRF attack (RFC 6749 §10.12): attacker tricks victim's browser into hitting the `/callback` endpoint with attacker-controlled `state` and `code` parameters, causing the victim's account to be linked to the attacker's OAuth identity. Variants: state replay (reusing valid state within TTL), state forgery (constructing fake state), cookie stripping (callback without `he_oauth_state` cookie).

**Mitigation Strategy:**
- **Prevention (4-layer defense per BR-1.1..BR-1.6 + Architect Round 1 Q1=(a)):**
  - Layer 1: state_id ≥ 256-bit entropy via `crypto/rand.Read(32)`.
  - Layer 2: Redis `auth:oauth:state:{sha256(state_id)}` TTL=600s, one-shot via GETDEL.
  - Layer 3: `he_oauth_state` cookie (Secure, HttpOnly, SameSite=Lax, Path=/v1/auth/oauth) — callback requires cookie.state == query.state.
  - Layer 4: IP + UA hash binding stored in state payload; callback strict match.
- **Detection:**
  - Audit event `auth.oauth.callback.error_state` with reason field (cookie_missing, redis_miss, replay, binding_mismatch).
  - Alertmanager warning when `auth.oauth.callback.error_state` rate > 5/min (likely active attack).
  - P0 security tests `2.3-SEC-001..006` exercise all 6 attack vectors.
- **Response:**
  - Investigate audit trail; block source IP if pattern matches automated attack.
  - No DB rollback needed (rejected requests never write).
- **Owner:** Dev (implementation) + Ops (Alertmanager rule)

**Test Requirements:**
- P0 `2.3-SEC-001`: state replay → 2nd callback rejected
- P0 `2.3-SEC-002`: cookie missing → reject
- P0 `2.3-SEC-003`: cookie ≠ query state → reject
- P0 `2.3-SEC-004`: IP binding mismatch → reject
- P0 `2.3-SEC-005`: UA binding mismatch → reject
- P0 `2.3-SEC-006`: forged state (not in Redis) → reject BEFORE Google token endpoint call (anti-SSRF — see SEC-005)
- P0 `2.3-UNIT-001..007` + `2.3-INT-001..002`: foundational state lifecycle

**References:**
- RFC 6749 §10.12 Cross-Site Request Forgery
- OWASP ASVS L2 V3.5.3 — Authentication and Session Management
- Architect Round 1 Q1 ruling

### SEC-006: Provider client-credential leak in logs / audit / error paths

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score: 15 — High**

**Description:**
`GOOGLE_CLIENT_SECRET` / `GITHUB_CLIENT_SECRET` are powerful long-lived credentials that, if leaked into structured logs / audit events / error response bodies / panic stack traces, enable attackers to issue OAuth tokens on behalf of the He-API application — full OAuth flow impersonation. Even more dangerous: leaked GitHub `access_token` from `/user/emails` flow could compromise user GitHub account scope (read:user + user:email). Logging hygiene mistakes are extremely common in OAuth client implementations.

**Mitigation Strategy:**
- **Prevention:**
  - K8s Secret `he-api-oauth-credentials` KMS-wrapped at rest, mounted as env var (Architect Round 1 Q5=(a)).
  - `BR-1.8`: structured logger MUST redact any `client_secret` / `access_token` / `code` field — implement field-name allowlist in `pkg/logging` with explicit reject for these keys.
  - `BR-2.6`: GitHub access_token never persisted (no Redis SET, no DB column).
  - `BR-3.9`: audit events use `sha256()` of PII; never raw values.
  - `panic` recovery middleware MUST strip sensitive env-var values from stack frames.
- **Detection:**
  - Pre-commit/CI scan: `gitleaks` / `trufflehog` over `apps/auth-svc` + `apps/api-gateway` (catches accidental hardcoded secrets).
  - Post-deploy log-grep CI job: scan production log streams for patterns matching `client_secret=`, `access_token=`, `Bearer gho_`, `Bearer ya29.` — alert on any match.
  - P0 security test `2.3-SEC-011`: full-flow log scan asserts ZERO occurrences of raw credential values.
  - P0 unit `2.3-UNIT-018`: structured logger redacts `client_secret` field.
- **Response:**
  - Immediate: rotate K8s Secret (Terraform apply + pod rolling restart).
  - Audit-trail review: all OAuth flows in window of leak → invalidate sessions if user impact possible.
  - Post-mortem: tighten log-redaction allowlist.
- **Owner:** Dev (logger + audit hygiene) + Ops (secret rotation + CI scanning)

**Test Requirements:**
- P0 `2.3-UNIT-018`: structured logger redacts `client_secret`
- P0 `2.3-SEC-011`: full-flow log scan zero credential occurrences
- P0 `2.3-UNIT-061`: audit Event type-safe constructors never emit raw PII
- P1 `2.3-UNIT-028`: GitHub `access_token` not persisted
- P0 CI scan job: `gitleaks` + `trufflehog` on every PR touching `apps/auth-svc/internal/oauth/**`

**References:**
- BR-1.8, BR-2.6, BR-3.9 in Story 2.3
- OWASP ASVS L2 V8.3.4 — Sensitive Data in Logs

### SEC-003: Open-redirect phishing via `return_to`

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score: 12 — Medium**

**Description:**
Without strict allow-list, attacker constructs phishing link `/v1/auth/oauth/google/initiate?return_to=https://attacker.com/looks-like-he-api` — after successful OAuth, victim is redirected to attacker site that mimics He-API UI to harvest further credentials or distribute malware. The phishing context is highly trusted because the user just authenticated on the legitimate domain.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-1.5` strict allow-list: prod (`https://console.he-api.com/`), staging (`https://staging.console.he-api.com/`), dev (`localhost`), relative (`/{locale}/`).
  - Validation at `BeginOAuth` entry BEFORE Redis write (avoid polluted state).
  - Defense in depth: `redirect.IsAllowed` rejects `javascript:`, `//attacker.com`, subdomain-confusion (`console.he-api.com.attacker.com`).
- **Detection:**
  - Audit event `auth.oauth.invalid_return_to` with `return_to_host` field — Prometheus counter + Alertmanager rule on rate spike (signals scanning).
  - P0 unit tests `2.3-UNIT-050..059` cover all bypass patterns including scheme-relative URLs and subdomain confusion.
  - P0 E2E `2.3-E2E-007` exercises full reject flow.
- **Response:**
  - Block source IP if scanning detected.
  - Tighten allow-list if novel bypass found.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-UNIT-050..059`: 10 redirect bypass patterns
- P0 `2.3-E2E-007`: attacker.com return_to rejected with toast
- P0 `2.3-INT-020`: return_to validation BEFORE Redis write

**References:** OWASP ASVS L2 V5.1.5 — URL Redirect Validation · BR-4.5

### SEC-007: Account enumeration via response/timing divergence

**Category:** Security · **Probability:** 4 (Likely) · **Impact:** 3 (Medium) · **Score: 12 — Medium**

**Description:**
Attackers probe whether an email exists in He-API by triggering OAuth and observing response differences: status code variation, response body wording, response timing, or DB-query-path divergence (e.g., `pending_deletion` vs unknown email may take different code paths). Enables targeted phishing / credential stuffing on known accounts.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-3.1` + Story 2.2 m-5 model: `pending_deletion` AND unknown-email both return identical generic `401_authentication_failed` body + headers.
  - Constant-time-ish path: avoid early returns that skip downstream code (e.g., don't skip JWT issuance simulation in reject paths if it diverges timing).
- **Detection:**
  - P0 security test `2.3-SEC-009`/`SEC-013`: response time delta < 50ms p95 between pending_deletion and unknown-email paths.
  - P0 unit `2.3-UNIT-033`/`UNIT-040`: response body equality assertion.
- **Response:**
  - If divergence detected: add artificial delay to faster path, OR refactor reject paths to share dummy work.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-UNIT-033`/`UNIT-040`: identical response body for pending_deletion vs unknown
- P0 `2.3-SEC-009`/`SEC-013`: timing delta < 50ms p95
- P1 monitoring: 2026-Q3 add prometheus histogram per response-code to catch drift over time

**References:** Story 2.2 m-5 ruling · OWASP ASVS L2 V2.2.1

### TECH-001: Redis state-flooding DoS (state-exhaustion)

**Category:** Technical · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score: 12 — Medium**

**Description:**
Attacker spams `BeginOAuth` from many IPs to fill Redis with state keys (each 256-bit + payload, TTL=600s). At scale, exhausts Redis memory → service degradation across all Redis-backed features (sessions, ratelimit, OAuth state). Affects Story 2.2 (signin/signup) too.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-4.2` ratelimit `ratelimit:oauth:initiate:ip:{ip}` 30/min/IP — caps single-IP impact.
  - TTL=600s ensures natural cleanup; state keys auto-expire even if never consumed.
  - K8s Redis (Tair) memory limits + eviction policy = `allkeys-lru` (Story 1.6) bounds blast radius.
- **Detection:**
  - Prometheus `redis_memory_used_bytes` gauge; Alertmanager warning at 80% memory.
  - `he_auth_oauth_initiate_total{provider}` rate spike alert.
  - P0 security test `2.3-SEC-008`: 50 concurrent BeginOAuth → ratelimit kicks in by request 31.
- **Response:**
  - Scale Redis cluster (Tair auto-scaling) or tighten ratelimit to 10/min/IP.
  - Block source IP range via NetworkPolicy / CDN WAF.
- **Owner:** Dev (ratelimit) + Ops (Redis sizing + Alertmanager)

**Test Requirements:**
- P0 `2.3-INT-019..020`: ratelimit enforcement
- P0 `2.3-SEC-008`: state-exhaustion test
- P1 chaos test: Redis at 90% memory → OAuth flow degrades gracefully (fail-closed per BR-4.2)

**References:** BR-4.2 · OWASP ASVS L2 V11.1.4 (Resource Exhaustion)

### TECH-003: Provider 5xx storm cascading to 502 user errors

**Category:** Technical · **Probability:** 4 (Likely) · **Impact:** 3 (Medium) · **Score: 12 — Medium**

**Description:**
Google or GitHub outage (historically 1-2x per year for several hours each) causes ALL in-flight OAuth flows to return 502. User experience: "We couldn't reach {provider}. Please try again." Repeated retries amplify load; users may abandon registration.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-2.9`: backoff retry (1 retry on 5xx after 250ms) absorbs transient failures.
  - 5s HTTP client timeout caps wait time → user sees error faster than browser timeout.
  - Two providers (Google + GitHub) → user can fall back to alternative (most users have at least one).
  - Password login (Story 2.2) as ultimate fallback.
- **Detection:**
  - Prometheus `he_auth_oauth_callback_total{outcome='error_provider'}` rate > 5/min → Feishu warning (BR-4.8 a).
  - Provider latency histogram `he_auth_oauth_provider_latency_seconds` p99 alert.
- **Response:**
  - Status page entry: "OAuth login via {provider} temporarily degraded. Use password login or alternative provider."
  - No service-level rollback needed; transient.
- **Owner:** Dev (retry) + Ops (status page automation)

**Test Requirements:**
- P0 `2.3-UNIT-014`/`UNIT-020`: token endpoint 5xx → 502 mapping
- P1 `2.3-INT-013`: retry on 5xx succeeds on 2nd attempt
- P1 `2.3-BLIND-ERROR-001`/`ERROR-002`: timeout handling
- P2 chaos test: kill mock provider stub mid-flow → graceful 502

- **Owner:** UX (copy) + Dev (CTA wiring) + Support (ticket tagging)

**Test Requirements:**

### SEC-005: SSRF via attacker-controlled state (callback hits attacker URL)

**Category:** Security · **Probability:** 2 (Unlikely) · **Impact:** 5 (Critical) · **Score: 10 — Medium**

**Description:**
If state validation is loose, attacker crafts callback with valid-looking but never-registered state_id; if auth-svc proceeds to call Google's token endpoint (or worse, a provider URL derived from state payload) before validating state, attacker could potentially redirect the server to call attacker-controlled URLs (SSRF). Less likely in current design because state is read-only metadata, but a regression could open this.

**Mitigation Strategy:**
- **Prevention:**
  - `2.3-SEC-006` test: validate Redis state lookup happens BEFORE any HTTP call to Google/GitHub.
  - Provider URLs hardcoded as constants in `apps/auth-svc/internal/oauth/google.go` + `github.go` — never derived from request input.
  - State payload contains only opaque IDs + hashes; never URLs.
- **Detection:**
  - P0 security test `2.3-SEC-006` (anti-SSRF assertion: mock Google receives ZERO calls on forged-state path).
  - Code review checklist: any new field in StatePayload must not be a URL.
- **Response:**
  - Patch immediately; audit-trail review of all outbound HTTP from auth-svc pods in window.
- **Owner:** Dev (implementation) + QA (test gate)

**Test Requirements:**
- P0 `2.3-SEC-006`: anti-SSRF assertion

### SEC-010: Google JWKS rotation race (cached key vs new signature)

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 3 (Medium) · **Score: 9 — Medium**

**Description:**
Google rotates JWKS keys periodically (every few weeks). `coreos/go-oidc/v3` caches JWKS (default 5min TTL); during rotation window, id_tokens signed with new key may fail verification against cached old key. Behavior: 1) user OAuth fails until cache refreshes (5min worst case), or 2) signature-verify failure path doesn't trigger refresh → indefinite failure.

**Mitigation Strategy:**
- **Prevention:**
  - `2.3-UNIT-017`: client refreshes JWKS on signature-verify failure, retries once before reject.
  - `coreos/go-oidc/v3` `oidc.NewProvider` with explicit refresh-on-failure config.
- **Detection:**
  - Prometheus `he_auth_oauth_callback_total{outcome='error_provider', reason='id_token_invalid'}` rate alert.
  - Synthetic: pre-prod env hits Google's JWKS endpoint hourly, asserts cache consistency.
- **Response:**
  - Manual JWKS cache flush (pod restart) if widespread.
  - Long-term: shorten JWKS cache TTL to 1min.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-SEC-007`: mock JWKS rotation, refresh-on-failure path
- P1 `2.3-UNIT-017`: client retries with fresh JWKS

### TECH-002: Concurrent Branch C INSERT race (lost-update)

**Category:** Technical · **Probability:** 3 (Possible) · **Impact:** 3 (Medium) · **Score: 9 — Medium**

**Description:**
User opens 2 browser tabs and completes OAuth flow concurrently for the same new email (Branch C path). Without race protection, both INSERT statements could succeed → duplicate users rows (violates UNIQUE on email) OR one succeeds + one returns 500 with leaked details.

- **Detection:**
  - Prometheus `he_auth_oauth_link_total{branch='C_race_fallback'}` counter for observability.
  - PG `pg_stat_database.tup_inserted` vs `users.count` reconciliation.
- **Response:**
  - If duplicate rows observed: manual dedup + investigation of race-detection logic.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-INT-016`: concurrent Branch C race
- P0 `2.3-UNIT-043`: 0-rows fallback path
- P0 `2.3-BLIND-CONCURRENCY-001`: high-concurrency stress

### SEC-004: Provider account hijack via subject reassignment

**Category:** Security · **Probability:** 2 (Unlikely) · **Impact:** 4 (High) · **Score: 8 — Medium**

**Description:**
Rare scenario: user changes their Google account (e.g., employee leaves company, gets new corporate Google account with same email recycled by IT). New Google subject (`sub` claim) is different even though email matches. If He-API auto-relinks to the new subject without challenge, the new owner of the Google account would gain access to the previous user's He-API session.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-1` Branch B.4: detect `oauth_provider=$p AND oauth_subject != $sub` → 409 `409_oauth_subject_mismatch`, no DB write, user must contact support.
  - Email link rotation policy reminder in onboarding (Story 2.5).
- **Detection:**
  - Prometheus `he_auth_oauth_link_total{branch='B4_rejected'}` rate > 1/min → PagerDuty critical (BR-4.8 b) — signals potential mass hijack attempt or provider migration event.
- **Response:**
  - Manual review of affected accounts; support workflow to verify rightful owner and re-link.
- **Owner:** Dev (B.4 logic) + Support (rightful-owner workflow)

**Test Requirements:**
- P0 `2.3-UNIT-038`: B.4 subject mismatch → 409
- P1 alert manager rule for B.4 spike

### SEC-008: Cross-provider conflict (B.5) abused for account discovery

**Category:** Security · **Probability:** 2 (Unlikely) · **Impact:** 4 (High) · **Score: 8 — Medium**

**Description:**
User existing with Google-linked account; attacker probes with GitHub OAuth for victim@gmail.com → receives 409 `409_oauth_conflict_other_provider` with message "This account is already linked to Google" → leaks that victim has a Google-linked He-API account.

**Mitigation Strategy:**
- **Prevention:**
  - Trade-off: B.5 specificity HELPS legitimate user discovery ("oh right, I linked Google") but HARMS anti-enumeration posture.
  - Architect Round 1 accepted this trade-off (Q2 ruling); B.5 message kept specific.
  - Mitigated by ratelimit: probing many emails would hit `ratelimit:oauth:callback:ip` 30/min cap.
- **Detection:**
  - Prometheus rate alert on B.5 if > 5/min from single IP (signal of enumeration scan).
- **Response:**
  - If scanning detected: block IP, consider tightening B.5 to generic 401 (security > UX).
- **Owner:** Dev + Ops

**Test Requirements:**
- P1 monitor: B.5 rate alert
- P2 future story: consider B.5 generic 401 mode (toggle via feature flag)

### SEC-009: PKCE downgrade attack (`plain` method accepted)

**Category:** Security · **Probability:** 2 (Unlikely) · **Impact:** 4 (High) · **Score: 8 — Medium**

**Description:**
RFC 7636 PKCE supports both `plain` (verifier = challenge, weak) and `S256` (challenge = SHA-256(verifier), strong). If client accepts `plain` from provider response or attacker MITM injects `code_challenge_method=plain` into authorize URL, PKCE defense is nullified.

**Mitigation Strategy:**
- **Prevention:**
  - `BR-1.2`: code hardcodes `code_challenge_method=S256` — never accepts other value.
  - `2.3-UNIT-008`: BuildAuthorizeURL asserts `code_challenge_method=S256` literal.
- **Detection:**
  - Code review: grep for `code_challenge_method` — should only appear as constant.
- **Response:**
  - Patch immediately if regression detected.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-UNIT-008` (Google) + `2.3-UNIT-019` (GitHub): assert S256 in URL

### TECH-005: Index regression — `idx_users_oauth` not used (seq scan)

**Category:** Technical · **Probability:** 2 (Unlikely) · **Impact:** 4 (High) · **Score: 8 — Medium**

**Description:**
Story 2.2 created `idx_users_oauth` (partial WHERE oauth_provider IS NOT NULL); Story 2.3 is first to actually query it. If query plan doesn't pick the partial index (e.g., wrong WHERE clause shape, missing statistics, PG version edge case), Branch A degrades to seq scan → O(N) on users table → latency cliff at scale.

**Mitigation Strategy:**
- **Prevention:**
  - `2.3-INT-007`/`2.3-INT-014`: integration test runs EXPLAIN ANALYZE, asserts plan uses `Index Scan using idx_users_oauth`.
  - PG `ANALYZE users` post-migration to ensure statistics fresh.
- **Detection:**
  - Prometheus `he_auth_oauth_provider_latency_seconds` p99 alert.
  - PG `pg_stat_user_indexes.idx_scan` for idx_users_oauth — should be > 0 in production.
- **Response:**
  - Manual `ANALYZE`; add query hint if needed; in extreme case, refactor query to force index.
- **Owner:** Dev

**Test Requirements:**
- P0 `2.3-INT-007`/`INT-014`: EXPLAIN assertion

### OPS-002: K8s Secret rotation race (rotate without pod restart)

**Category:** Operational · **Probability:** 2 (Unlikely) · **Impact:** 4 (High) · **Score: 8 — Medium**

**Description:**
`he-api-oauth-credentials` Secret rotated (e.g., quarterly per security policy or after suspected leak). K8s does NOT auto-restart pods on env-var-from-Secret change → running pods continue using old credentials until manual restart or natural reschedule. New OAuth flows fail.

**Mitigation Strategy:**
- **Prevention:**
  - Reloader (https://github.com/stakater/Reloader) Helm dependency: auto-restart deployments on Secret change.
  - Or: deployment annotation `secret-hash: {checksum}` triggers rolling restart via Argo CD.
- **Detection:**
  - Prometheus `he_auth_oauth_callback_total{outcome='error_provider'}` spike post-rotation.
- **Response:**
  - Manual `kubectl rollout restart deployment/auth-svc`.
- **Owner:** Ops

**Test Requirements:**
- P1 staging drill: rotate Secret + verify pods restart automatically within 1min

### TECH-004: OIDC discovery cache TTL stampede on cold start

**Category:** Technical · **Probability:** 2 · **Impact:** 3 · **Score: 6 — Medium**

**Description:**
On auth-svc pod fleet rolling restart (e.g., deploy), ALL new pods simultaneously call Google's `/.well-known/openid-configuration` → thundering herd. Google might rate-limit (unlikely at He-API scale but possible).

**Mitigation Strategy:**
- **Prevention:** Staggered pod rollout (maxSurge=1, maxUnavailable=0). m-2 medium-issue fix (BR-1.9 retry with backoff) absorbs transient throttle.
- **Detection:** Pod readiness probe failure alerts on rolling deploy.
- **Owner:** Dev (retry) + Ops (rollout strategy)

**Test Requirements:** P2 chaos test: kill all auth-svc pods, observe rolling restart succeeds

### TECH-006: Kafka audit producer backpressure
