# Test Design: 7.5 — 支付宝 Alipay+ 国际版集成

2026-06-10 | Turing (QA) | Level: **Comprehensive** | security_focus: **true**

> **Scope discipline (the defining lens of this design).** Story 7.5 adds the FOURTH payment channel by plugging ONE `alipay.PaymentProvider` impl into the seam Story 7.3 stood up, the Architect ratified, and Story 7.4 (USDC, Done) already proved. The exactly-once credit machinery, the `recharge_orders` pending→paid state-machine, the amount-integrity guard, the `payment.completed` producer, the provider-agnostic `credit.go` applier (**including its `toUSD()` CNY→USD branch**), the Redis mirror, and the envelope codes are **REUSED VERBATIM** and already adversarially proven by 7.3's 62-scenario + 7.4's 54-scenario suites. This design therefore **focuses the genuinely-new + risk-bearing surface**, which is strictly larger than 7.4's because the new primitive is asymmetric: `alipay.CreateCheckout` (Antom Cashier Payment create + outbound RSA sign), `alipay.VerifyWebhook` (the platform's **FIRST ASYMMETRIC RSA2 scheme** — public-key verify over a **CONSTRUCTED signing string** `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>`, with a **Request-Time freshness window**), the minor-unit integer-amount parse, the `resultStatus` S/U/F → `VerifiedEvent` mapping, and the **FIRST real CNY→USD fx-at-credit exercise** of the inherited `toUSD()` branch. Inherited invariants are **re-asserted once for the alipay path** (not re-proven from scratch) so 7.5 is also the proof-of-reuse for 7.6 (WeChat Pay HK — same asymmetric-scheme family + HKD/CNY fx).

**Level mix rationale (shift-left).** The new surface is provider-impl logic — request-shaping, outbound RSA signing, asymmetric signature verification over a constructed string, Request-Time freshness, `resultStatus`→Kind mapping, and minor-unit money parsing — all unit-testable with `httptest`-mocked Antom + an **ephemeral in-test RSA keypair** (sign fixtures with the test private key, verify with its public key; no real Alipay+ key needed — `[[project_toolchain_env_limits]]`). Hence the heavy unit tilt (35 unit). The credit, idempotency, atomicity, raw-body+header integrity, fx-at-credit, and route-auth invariants are component-boundary concerns proven at integration with `pgxmock`/`miniredis` (28 int). E2E is reserved for the three highest-value full-stack lanes — the USD recharge→confirm→credit happy path, the **CNY recharge→fx-credit** path (the headline new lane), and the forged-webhook security proof (3 e2e). Heavy E2E is deliberately avoided: the spine it would exercise is already covered by 7.3/7.4.

**Why 66 > 7.4's 54 despite being "scoped/lighter than 7.3."** The "scoped" framing (Decision 8B) means QA does NOT re-run 7.3's full generic-spine suite — it re-asserts each inherited invariant **once** for the alipay path. The count rises above 7.4 purely because the asymmetric constructed-string scheme has strictly **more distinct failure vectors** than a single symmetric HMAC: wrong-public-key, four independently-tamperable signing-string components (URI/Client-Id/Request-Time/body), the configured-public-notify-path reconstruction, the Request-Time freshness window, and keyVersion rotation — **plus** a brand-new CNY→USD fx-at-credit correctness lane (with the Q-FX-INTENT paid-currency comparison) that 7.4's USDC pass-through never exercised. Every added scenario maps to a genuinely-new code path, not redundant spine coverage.

### AC3: Alipay+ webhook 安全 — RSA2 asymmetric signature verification + inherited exactly-once backbone

| ID | Lvl | Pri | Test | Why (level justification) |
| --- | --- | --- | --- | --- |
| 7.5-UNIT-020 | U | P0 | **Valid signature**: `VerifyWebhook` reconstructs `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>`, base64-decodes the `Signature` value, and verifies via `rsa.VerifyPKCS1v15(alipayPublicKey, crypto.SHA256, sha256(string), sig)` → match + fresh Request-Time → parses + maps → `VerifiedEvent` | Pure crypto + parse; deterministic with an ephemeral test keypair / known body / Request-Time |
| 7.5-UNIT-021 | U | P0 | **[FORGED]** Invalid signature (bad bytes) → `provider.ErrSignatureInvalid`; the body is **NEVER** parsed into any money action | Adversarial pure unit; the load-bearing forgery fence (BR-W-1) |
| 7.5-UNIT-022 | U | P0 | **[FORGED]** Absent `Signature` header (or absent `Client-Id`/`Request-Time`) → `ErrSignatureInvalid` | Adversarial pure unit; missing-credential path |
| 7.5-UNIT-023 | U | P0 | **[FORGED — asymmetric-specific]** Notification signed by an **attacker's private key** (verified against the configured Alipay+ public key) → `ErrSignatureInvalid` | Adversarial pure unit; the asymmetric guarantee — the channel cannot be forged without Alipay+'s private key (BR-W-2). **No 7.4 analogue** |
| 7.5-UNIT-024 | U | P0 | **[TAMPER — constructed-string, table-driven]** Altering **ANY** signing-string component — the URI, `Client-Id`, `Request-Time`, or `rawBody` — invalidates the signature → `ErrSignatureInvalid` (fail-closed); body never parsed | Adversarial pure unit (4-row table); the NEW constructed-string integrity surface (BR-W-2/W-3) |
| 7.5-UNIT-025 | U | P0 | **[CANONICALISATION]** The impl reconstructs the URI from its **configured public notify path** (`WithNotifyPath`), **NOT** `r.URL.Path` (the internal proxied path); a genuine notification verifies, and an impl wrongly using `r.URL.Path` would fail every genuine notification (Q-NOTIFY-PATH) | Pure assertion of the signing-string source; getting it wrong breaks 100% of genuine traffic — a P0 correctness trap |
| 7.5-UNIT-026 | U | P0 | **[REPLAY — layer 1]** A captured VALID notification with a **stale Request-Time** (outside the bounded freshness skew) → `ErrSignatureInvalid`/reject | Adversarial pure unit (uses `WithClock`); the signature-timestamp freshness layer Coinbase lacked, RESTORED (BR-W-4) |
| 7.5-UNIT-027 | U | P1 | Request-Time freshness **boundary**: just-inside the skew window → accept; just-outside → reject (clock injected via `WithClock`) | Pure boundary on the freshness comparator; off-by-one guard |
| 7.5-UNIT-028 | U | P1 | Malformed `Signature` header (unknown `algorithm`, missing `signature=`, non-base64 value) → `ErrSignatureInvalid` (never a permissive parse) | Pure format-guard branch; defensive |
| 7.5-UNIT-029 | U | P1 | `keyVersion` selects the correct public key for verification (rotation support); an unknown `keyVersion` → reject | Pure rotation branch; supports key-rotation without an outage |
| 7.5-UNIT-030 | U | P1 | **Secret discipline**: on any sign/verify/Antom error, neither `ALIPAY_PLUS_MERCHANT_PRIVATE_KEY` (⚠️ broad blast radius) nor the public key appears in the error/log (generic wrapping); payload carries NO card PAN (wallet channel, trivially true) | Pure assertion over error strings; secret-leak + PCI boundary (BR-W-6/W-8) |
| 7.5-INT-020 | I | P0 | The `POST /v1/billing/webhooks/alipay` route is mounted **OUTSIDE** the bearer/CSRF chain (reachable with no auth token — the signature is the sole credential, 4.7 `/public/*` precedent) | Route-auth wiring is an integration concern (middleware chain) |
| 7.5-INT-021 | I | P0 | Raw-body + header integrity: the gateway `billing_webhook.go` proxy forwards the EXACT bytes Antom signed **AND** `Client-Id`/`Request-Time`/`Signature` verbatim (billing_webhook.go:70-76) so the downstream RSA verify succeeds | Cross-process byte+header fidelity (gateway→payment-svc); only provable at the boundary (BR-W-3) — broader than 7.4 (headers matter now, not just body) |
| 7.5-INT-022 | I | P0 | **[FORGED]** Forged-signature POST → `400_webhook_signature_invalid`, **zero** `recharge_orders` mutation, **zero** balance change | End-to-end forgery rejection across handler→applier→PG (no-side-effect proof) |
| 7.5-INT-023 | I | P0 | **[REPLAY — layer 2]** A captured VALID `S` notification re-POSTed **within** the freshness window → the `recharge_orders` pending→paid state-machine makes it a no-op → **exactly one** credit total | The within-window replay leans on the inherited state-machine (defence-in-depth); proven at the persistence boundary (BR-W-4) |
| 7.5-INT-024 | I | P0 | **[REPLAY — layer 1, full path]** A captured VALID `S` notification re-POSTed **after** the window → `400_webhook_signature_invalid` (stale Request-Time), zero side effects | The freshness layer end-to-end; the layer Coinbase (7.4) could not have (BR-W-4) |
| 7.5-INT-025 | I | P0 | Provider 2xx discipline: verified+already-processed → **200** (Antom stops retrying); verification failure → **400**; transient processing error (PG down) → **5xx** (Antom redelivers) | HTTP-status contract across the handler; drives at-least-once redelivery correctness (BR-W-5) |

## Test Skeleton Note (Output 2 — deliberate deferral, documented)

The standard skeleton output is TypeScript-shaped (one throwing `test()` per scenario). For this Go workspace it is **deliberately NOT materialised as an executable `_test.go` file at test-design time**, for two compile-safety reasons:

1. The `apps/payment-svc/internal/provider/alipay/` package **does not yet exist** (it is Dev deliverable T1.1). A `package alipay` test file referencing a non-existent `Provider`/`New`/`VerifyWebhook` would not build, and a directory containing only a `_test.go` with no buildable non-test package would break `go test ./...` workspace-wide (`no non-test Go files`).
2. The local toolchain cannot build/run Go (`[[project_toolchain_env_limits]]`), so a "throwing skeleton" could not be validated here and would land as a red build.

Instead, the **scenario IDs in this document ARE the skeleton checklist**, and the per-AC **Test Specs are backfilled into the story Tasks** (Output 4.5 below) as the Dev-facing TDD contract. Dev writes `apps/payment-svc/internal/provider/alipay/alipay_test.go` as the first TDD step of T1.1 (white-box `package alipay`, ephemeral in-test RSA keypair to sign fixtures, `httptest`-mocked Antom — mirroring `coinbase/coinbase_test.go`), implementing exactly the IDs above. QA verifies at review that every P0 ID has a corresponding test and no `t.Skip` lacks a written reason. This mirrors how 7.4's `coinbase_test.go` actually materialised (Dev-authored from the QA design).
