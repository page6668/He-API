**Story Title:** 支付宝 Alipay+ 国际版集成 (Alipay+ / Antom international payment channel)
**Assessment Date:** 2026-06-10
**Assessed By:** Turing (Test Architect / QA)
**Story Complexity:** 5/7 (api_changes, new_patterns, cross_service, core_docs, data_sync; db_schema + performance = false)
**Scope:** **Scoped** (Decision 8B). The exactly-once credit spine, the `recharge_orders` state-machine, the amount-integrity guard, the `payment.completed` producer, the provider-agnostic `credit.go` applier (incl. its `toUSD()` branch), the Redis mirror, and the PCI no-PAN boundary are **REUSED VERBATIM** and already adversarially proven by 7.3 (62 scenarios) + 7.4 (54 scenarios). Inherited-and-proven risks therefore score a **low residual probability** (mitigation is in place, reused unchanged); this profile concentrates on the **genuinely-new alipay surface**: the FIRST asymmetric RSA2 constructed-string verify, the minor-unit integer-amount parse, and the FIRST real CNY→USD fx-at-credit exercise.

## Detailed Risk Analysis

### SEC-002: Constructed-String Canonicalisation Error (the availability trap)

**Category:** Security/Technical · **Probability:** 4 (Likely) · **Impact:** 4 (High) · **Score:** 16 (High)

**Description:**
The platform's FIRST constructed-string signature: the signed content is `POST <publicNotifyPath>\n<Client-Id>.<Request-Time>.<rawBody>` — **not** the raw body alone. Antom signs over the **public** URL it POSTed to, but the gateway proxies the request to a **different internal** payment-svc path, so at the handler `r.URL.Path` is the *internal* path. An impl that reconstructs the URI from `r.URL.Path` (the natural mistake) — or that mis-orders/mis-delimits the components — produces a signing string that never matches Antom's, so **100% of genuine notifications fail verification and no credit ever lands**. This is fail-closed (no fraud), but it silently breaks the entire channel. Explicitly flagged as Q-NOTIFY-PATH.

**Mitigation Strategy:**
- **Prevention:** Reconstruct the URI from the impl's **configured** public notify path (`WithNotifyPath`, default `/v1/billing/webhooks/alipay`), NEVER `r.URL.Path`; fix method `POST`; build the string from the forwarded `Client-Id`/`Request-Time` headers + the exact raw body bytes; consider the official `global-open-sdk-go` verifier if it eases canonicalisation (Q-SDK).
- **Detection:** P0 unit assertion that the impl uses the configured path (7.5-UNIT-025); a valid-signature golden-vector test (7.5-UNIT-020); the E2E happy path proving a genuine notification credits (7.5-E2E-001/002).
- **Response:** If genuine notifications are rejected in prod, Antom redelivers (at-least-once) — fixing the path + redeploy recovers the backlog; no data loss (orders stay `pending`).
- **Owner:** Dev

**Test Requirements:** 7.5-UNIT-020, **7.5-UNIT-025** (canonicalisation source), 7.5-INT-021 (raw-body+header integrity), 7.5-E2E-001/002

**References:** Story Q-NOTIFY-PATH; AC3 BR-W-2/W-3; `billing_webhook.go:70-76` (header pass-through)

### SEC-001: Forged-Notification Acceptance (the fraud fence)

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score:** 15 (High)

**Description:**
The webhook route is mounted outside the bearer/CSRF chain — the Alipay+ signature is the **sole credential**. A bug in the NEW asymmetric verify (parsing the body before verifying, a permissive fallback when the `Signature` header is malformed/absent, accepting a non-`RSA256` algorithm, or verifying against the wrong key) would let a forged `resultStatus=S` mint free balance — direct financial fraud. Probability is *Possible* (not *Likely*) because the handler path (verify→emit) is inherited and proven and the asymmetric design means an attacker cannot forge without Alipay+'s private key; the residual is purely an impl defect in `alipay.VerifyWebhook`.

**Mitigation Strategy:**
- **Prevention:** `VerifyWebhook` MUST verify `rsa.VerifyPKCS1v15(alipayPublicKey, crypto.SHA256, sha256(signedString), sig)` and return `provider.ErrSignatureInvalid` (parsing **nothing**) BEFORE any body→money mapping (BR-W-1); reject absent/malformed `Signature`/`Client-Id`/`Request-Time`; only the configured Alipay+ public key verifies (an attacker key → reject).
- **Detection:** Adversarial P0 unit lane — forged/absent/**wrong-key** (7.5-UNIT-021/022/023), 4-component tamper (7.5-UNIT-024); integration + E2E no-side-effect proofs (7.5-INT-022, 7.5-E2E-020); `payment_webhook_rejected{provider:"alipay",reason:"signature"}` metric + slog for runtime alerting.
- **Response:** Forged attempts are rejected at 400 with zero side effects; an anomaly in the reject metric triggers a security review.
- **Owner:** Dev

**Test Requirements:** 7.5-UNIT-021/022/023/024, 7.5-INT-022, 7.5-E2E-020

**References:** AC3 BR-W-1/W-2; PCI SAQ-A boundary; 4.7 `/public/*` precedent

### DATA-001: Minor-Unit Mis-Scale (the 100× defect)

**Category:** Data/Financial · **Probability:** 3 (Possible) · **Impact:** 5 (Critical) · **Score:** 15 (High)

**Description:**
Antom `paymentAmount.value` is an **integer in the currency's minor units** (`"5000"` = 50.00). The FIRST minor-unit parse on the platform. A hardcoded `/100`, a wrong per-currency scale, or silent truncation of a sub-minor-unit input produces a credit that is 100× too large or too small — a direct financial-integrity defect on both the outbound create (over-charge) and the inbound credit (over-credit).

**Mitigation Strategy:**
- **Prevention:** A **per-currency minor-unit table** (NOT a hardcoded `/100`), string-decimal end-to-end (`shopspring/decimal`), and **fail-closed** on any scale loss/non-representable value → park + alert, never a mis-scaled credit (BR-W-7, Q-AMOUNT-UNITS).
- **Detection:** P0 unit round-trip (7.5-UNIT-006: `"50.00"↔"5000"`, `"350.00"↔"35000"`), fail-closed boundary (7.5-UNIT-007, 7.5-BLIND-BOUNDARY-005), notification-side parse-fail (7.5-UNIT-016), and the integration mis-scale park (7.5-BLIND-DATA-005).
- **Response:** A parked order surfaces via alert for manual reconciliation; no wrong credit is ever applied.
- **Owner:** Dev

**Test Requirements:** 7.5-UNIT-006/007/015/016, 7.5-BLIND-BOUNDARY-005, 7.5-BLIND-DATA-005

**References:** Q-AMOUNT-UNITS; AC2 BR-C-3; AC3 BR-W-7

### SEC-003: Replay — Request-Time Freshness

**Category:** Security · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score:** 12 (Medium)

**Description:**
A captured valid `resultStatus=S` re-POSTed to double-credit. Posture is **better than 7.4** (Coinbase had no signature timestamp): the Alipay+ signed string includes `Request-Time`, enabling a freshness window. Risk is that the window is not enforced or set too wide, leaving the state-machine as the sole fence. Defence-in-depth requires both layers.

**Mitigation Strategy:**
- **Prevention:** Reject a notification whose `Request-Time` is outside a bounded skew (layer 1); the inherited `recharge_orders` pending→paid state-machine neutralises any within-window replay (layer 2).
- **Detection:** 7.5-UNIT-026 (stale → reject), 7.5-UNIT-027 (window boundary), 7.5-INT-023 (within-window → one credit), 7.5-INT-024 (after-window → 400).
- **Response:** Replays are rejected (stale) or no-op (state-machine); exactly-once holds.
- **Owner:** Dev

**Test Requirements:** 7.5-UNIT-026/027, 7.5-INT-023/024

**References:** AC3 BR-W-4 (replay layer RESTORED vs 7.4)

### DATA-002: CNY→USD FX-at-Credit Correctness (the new lane)

**Category:** Data/Financial · **Probability:** 3 (Possible) · **Impact:** 4 (High) · **Score:** 12 (Medium)

**Description:**
7.5 is the FIRST channel to settle a native non-USD currency (RMB) and thus the FIRST real exercise of the inherited `credit.go toUSD()` branch (credit.go:290-311). The math is inherited code, but the *first-run* risks are: reading the wrong/stale 7.2 fx_rate, rounding ≠ DivRound HALF-UP moneyScale=4, crediting `current_rmb` instead of `current_usd` (violating the 7.2 single-USD-SoT), or — the subtle one — the amount-integrity guard comparing settled-vs-intent **post-fx** (USD-vs-USD), letting fx drift between order-create and settlement falsely trip the park (Q-FX-INTENT).

**Mitigation Strategy:**
- **Prevention:** Drive the inherited `toUSD()` unchanged (USD = settled / CNY-per-USD rate, HALF-UP, moneyScale=4); compare settled-vs-intent in the **PAID currency** BEFORE conversion (Q-FX-INTENT); keep `current_rmb` reserved/0; require a CNY fx_rate row (fail-closed if absent).
- **Detection:** 7.5-INT-012 (fx credit + exact rounding + SoT), 7.5-INT-013/014 (Q-FX-INTENT within-tol credit / short park), 7.5-E2E-002 (full-stack fx), 7.5-BLIND-ERROR-006 (missing rate → fail-closed).
- **Response:** A missing-rate or short-settle parks for reconciliation; no wrong credit lands.
- **Owner:** Dev

**Test Requirements:** 7.5-INT-012/013/014, 7.5-E2E-002, 7.5-BLIND-ERROR-006

**References:** Q-CURRENCY, Q-FX-INTENT; AC2 BR-C-4; credit.go:290-311 + fxRateSQL:103-104

### SEC-004: Merchant Private-Key Leak (broad blast radius)

**Category:** Security · **Probability:** 2 (Unlikely) · **Impact:** 5 (Critical) · **Score:** 10 (Medium)

**Description:**
`ALIPAY_PLUS_MERCHANT_PRIVATE_KEY` signs ALL our outbound Antom calls — leaking it lets an attacker impersonate **us** to Antom (create/refund payments), a broader blast radius than a single webhook HMAC secret. Distinct from the Alipay+ public verify key (a public key, not a secret) and the client id.

**Mitigation Strategy:**
- **Prevention:** Env-injected only, NEVER logged (generic error wrapping — the 7.3/7.4 secret discipline cascade); registered in `docs/dev/secrets`; the private signing key, the public verify key, and the client id are distinct config items; `keyVersion` supports rotation.
- **Detection:** 7.5-UNIT-030 (no key in any error/log string); secret-scanning in CI.
- **Response:** Rotate the key (keyVersion-aware) on any suspected leak.
- **Owner:** Dev

**Test Requirements:** 7.5-UNIT-030

**References:** Q-SIG; AC3 BR-W-6; `[[project_toolchain_env_limits]]`

## Compliance and Regulatory Considerations

- **Secret handling:** The merchant private key (broad blast radius) is env-injected, never logged, rotation-capable (keyVersion).
