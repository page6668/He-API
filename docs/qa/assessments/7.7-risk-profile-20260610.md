This profile drives the P0/P1/P2 test priorities already reflected in the companion test-design.

## Detailed Risk Analysis

### FIN-001: Auto-recharge storm (concurrent debits → N top-ups)

**Category:** Technical / Financial-integrity · **Probability:** 3 · **Impact:** 5 · **Score:** 15 (High)

**Description.** The 7.1 `usage.recorded` consumer is parallel; a burst of chat requests each commits a debit, and each post-deduction evaluation can independently observe `balance < threshold`. Without a fence this fans out into N simultaneous off-session charges, over-charging the user N×`amount_usd`. This is the **dominant risk** of the story — the money-IN analogue of the 7.1 exactly-once debit fence, and the first such fence ever built on the trigger side.

**Mitigation:**
- **Prevention:** `SETNX autorecharge:lock:user:{id}` (TTL ≈ provider-charge + webhook-settle window) as the fast gate **AND** a DB-level pending-auto-order guard (no new auto-recharge if a pending auto `recharge_order` exists). Net invariant: **AT MOST ONE** in-flight auto-recharge per user. Trigger runs AFTER the PG deduction commits, off the chat hot path, never holding a `balances` row lock (BR-R-1/BR-R-2).
- **Detection:** P0 integration storm test (N concurrent debits → exactly one `recharge_order`); counter on fence-contention no-ops; alert on >1 in-flight per user.
- **Response:** the 7.3 exactly-once webhook fence still guards the CREDIT (a stray second pending order that never settles is harmless); refund path is a future credit-note story.
- **Owner:** Dev

**Test Requirements (P0):** 7.7-INT (storm — N concurrent debits → exactly one `recharge_order`); fence release on terminal order state (paid/failed) and on TTL expiry; the "other observers find the fence held → no-op" branch.
**References:** [Story 7.7 SM data_sync_analysis; BR-R-1/BR-R-2; Architect Q-TRIGGER ruling]

### FIN-002: Storm-fence not durable across Redis loss

**Category:** Technical / Financial-integrity · **Probability:** 3 · **Impact:** 5 · **Score:** 15 (High)

**Description.** Architect Round-1 hardening note (Q-TRIGGER): the Redis SETNX lock alone does NOT suffice — a Redis-less window (eviction, failover, cold key) could double-start before the first pending `recharge_order` row commits. The **DB-level pending-order guard is the durable fence** and must survive Redis loss; the Redis lock is only the TTL-bounded fast gate.

**Mitigation:**
- **Prevention:** enforce the pending-auto-order guard at the DB level (a partial-unique constraint or an explicit "no pending auto `recharge_order` for user" check inside the order-creation tx), independent of Redis. Keep BOTH layers (defense in depth).
- **Detection:** P0 integration test simulating Redis unavailable / lock-not-held → the DB guard still yields exactly one order.
- **Response:** same as FIN-001 (7.3 credit fence caps the blast radius at the settle step).
- **Owner:** Dev

**Test Requirements (P0):** 7.7-INT (Redis-loss path: lock absent/failed → DB pending-order guard → exactly one order); concurrent insert race on the guard.
**References:** [Architect Round-1 Rulings → Q-TRIGGER "RATIFY with a hardening note"]

### TECH-001: Lock-TTL mis-tuning

**Category:** Technical · **Probability:** 3 · **Impact:** 4 · **Score:** 12 (Medium)

**Description.** The lock TTL must bound a stuck charge yet outlive the provider-charge + webhook-settle round-trip. **Too short** → the lock releases mid-settle and a later debit double-starts (re-opens FIN-001). **Too long** → a failed charge that didn't cleanly release leaves the fence stuck, blocking a legitimate later recharge → the user hits the hard zero-balance stop the feature exists to prevent.

**Mitigation:**
- **Prevention:** the PRIMARY release is on terminal order state (paid/failed); the TTL is only the fail-safe. Size the TTL conservatively above the p99 settle window. Make the failed-charge path release the fence explicitly.
- **Detection:** unit test on the release-on-terminal-state path; integration test on TTL-expiry fail-safe → next debit re-evaluates cleanly.
- **Owner:** Dev

**Test Requirements (P1):** TTL-expiry fail-safe release; explicit release on `recharge_order=failed`.
**References:** [BR-R-2; Error Handling "Lock TTL expiry with no terminal state"]

### SEC-001: Cross-user payment_method binding

**Category:** Security · **Probability:** 2 · **Impact:** 5 · **Score:** 10 (Medium)

**Description.** The off-session token is a standing authorization to pull funds. If `PUT /v1/billing/auto-recharge` accepts a `payment_method_id` belonging to another user, an attacker charges that user's card into their own balance — financial fraud (threat_model #2), parity with 7.3 forged-webhook severity.

**Mitigation:**
- **Prevention:** server-side ownership validation (`payment_methods.user_id = session user`) on every bind — never client-asserted. FK + application-level check (defense in depth). Token usable ONLY for its owner's auto-recharge into their own balance.
- **Detection:** **P0** test — foreign `payment_method_id` → `422_invalid_payment_method`/`403`, not enabled, `balances` unchanged.
- **Owner:** Dev

**Test Requirements (P0):** 7.7-INT-002 (cross-user binding rejected); non-existent method id → 422.
**References:** [BR-R-7; threat_model #2; security_analysis]

### FIN-005: Invoice accuracy / reconciliation drift

**Category:** Technical / Financial-integrity · **Probability:** 3 · **Impact:** 3 · **Score:** 9 (Medium)

**Description.** Invoice `total_debit_usd` / `total_credit_usd` aggregate `usage_ledger` debits + `recharge_orders` paid credits for the period. A boundary error (inclusive/exclusive period edges, timezone, double-count, missed paid-at) produces an invoice that does not reconcile against the 7.1 `GET /v1/usage` figure for the same window — an auditable billing record that is wrong.

**Mitigation:**
- **Prevention:** aggregate on the SAME UTC month boundary as 7.1's current-month aggregate + the 5.4 reset; string-decimal arithmetic; freeze figures at generation.
- **Detection:** P0 accuracy test — `total_debit == GET /v1/usage total_cost` for P; `total_credit == SUM(paid recharge_orders in P)`; no double-count, no missing charge.
- **Owner:** Dev

**Test Requirements (P0):** 7.7-INT accuracy reconciliation vs `GET /v1/usage`; period-boundary edge rows.
**References:** [AC3 accuracy invariant; BR-I-3]

### SEC-002: Stored token / SetupIntent secret leaked in logs

**Category:** Security · **Probability:** 2 · **Impact:** 4 · **Score:** 8 (Medium)

**Description.** The Stripe PaymentMethod token / SetupIntent client-secret is secret-grade. A naive `slog` of a request/response struct leaks a standing charge authorization.

**Mitigation:** slog-redaction; never log the token in full; env-injected Stripe secret (7.3 discipline cascade); register the stored token in the dev/secrets discipline. **Detection (P0):** token-never-logged assertion over the off-session + save-token paths. **Owner:** Dev.

**References:** [threat_model #4; Technical Constraints — PCI §8.4]

### SEC-004: Invoice PDF IDOR

**Category:** Security · **Probability:** 2 · **Impact:** 4 · **Score:** 8 (Medium)

**Description.** `GET /v1/billing/invoices/{id}/pdf` exposing another user's invoice leaks billing PII (usage, amounts).

**Mitigation:** owner-only authorization (`invoices.user_id = session user`); non-enumerable object key; **404 not 403** to avoid existence disclosure; no public/un-authed PDF route; private bucket (proxy-stream for the API, time-boxed signed URL acceptable for the email link). **Detection (P0):** foreign invoice id → 404. **Owner:** Dev.

**References:** [BR-I-6; threat_model #5/#6; Architect Q-PDF ruling]

### FIN-003: Off-session charge double-credit on webhook redelivery

**Category:** Technical / Financial-integrity · **Probability:** 2 · **Impact:** 4 · **Score:** 8 (Medium)

**Description.** If the off-session settle does NOT reuse the 7.3 exactly-once webhook fence verbatim, a redelivered `payment.completed` could credit twice.

**Mitigation:** NO new credit path — the off-session charge settles through the existing 7.3 `recharge_orders` pending→paid state-machine + `UNIQUE(provider, external_order_id)` (already adversarially proven by 7.3/7.4/7.5/7.6). **Detection (P0, re-assert once):** redelivered settle webhook → idempotent credit. **Owner:** Dev.

**References:** [BR-R-5; Technical Constraints "No new money SoT, no new credit path"]

---

### TECH-003: Money precision loss

**Category:** Technical · **Probability:** 2 · **Impact:** 4 · **Score:** 8 (Medium)

**Description.** A money field serialized as a JSON number, or float64 arithmetic, loses precision (Q-Spec-4 violation) across auto-recharge amounts, invoice totals, alert balances.

**Mitigation:** string-decimal everywhere on the wire; `shopspring/decimal` (the 7.1 lib) for arithmetic, never float64. **Detection (P0):** every money field is a string-decimal; round-trip precision preserved. **Owner:** Dev.

**References:** [BR-R-3/BR-A-5/BR-I-5; Q-Spec-4 cascade]

---

### FIN-004: Invoice duplicate on CronJob retry

**Category:** Technical / Financial-integrity · **Probability:** 2 · **Impact:** 3 · **Score:** 6 (Medium)

**Description.** The monthly `cmd/monthly-invoice` CronJob may be retried (backoffLimit) after a partial failure. Without a fence a re-run double-inserts / double-emails.

**Mitigation:** `invoices` UNIQUE(user_id, period) + INSERT ON CONFLICT DO NOTHING; the generated→emailed transition advanced once (guarded). NOTE (Architect): a CronJob Job runs as a single pod, so the fence guards **retry/backoff re-runs**, not concurrent pods. **Detection (P0):** cron re-run → one invoice + one email per (user, period). **Owner:** Dev.

**References:** [BR-I-1; Architect Q-SCHEDULER overrule]

---

### TECH-002: Retry-loop against a dead card (no auto-disable)

**Category:** Technical · **Probability:** 2 · **Impact:** 3 · **Score:** 6 (Medium)

**Description.** An expired/declined saved card with no auto-disable generates endless failed off-session charges + low-balance alerts, spamming the provider and the user.

**Mitigation (Q-FAILMODE):** after N=3 consecutive failed charges within a window → `auto_recharge_enabled=false` + "update your payment method" notify; success resets the counter. **Detection (P1):** 3-fail → disabled; success resets. **Owner:** Dev.

**References:** [BR-R-6; Architect Q-FAILMODE ruling N=3]

---

### TECH-004: Cron period / timezone boundary error

**Category:** Technical · **Probability:** 2 · **Impact:** 3 · **Score:** 6 (Medium)

**Description.** A wrong period derivation (DST-free UTC assumed; off-by-one on the just-ended month) aggregates the wrong window.

**Mitigation:** period = just-ended UTC calendar month, aligned with 5.4 00:00-UTC-1st reset + 7.1 current-month boundary; CronJob `0 0 1 * *` UTC. **Detection (P1):** fires at 00:00 UTC 1st for the prior month; boundary rows land in the correct period. **Owner:** Dev.

**References:** [BR-I-3; Architect Q-SCHEDULER]

---

### BUS-001: Auto-recharge fails silently → hard zero-stop / churn

**Category:** Business · **Probability:** 2 · **Impact:** 3 · **Score:** 6 (Medium)

**Description.** If a failed/blocked auto-recharge does not surface (alert + auto-disable notify), the user hits the 7.1 `402_balance_insufficient` stop the feature exists to prevent → involuntary churn.

**Mitigation:** the AC2 "auto-recharge failed" alert variant fires on decline; auto-disable notify on repeated failure; the low-balance alert is the fallback for OFF/failed auto-recharge. **Detection (P1):** failed charge → alert; OFF → alert. **Owner:** PM/Dev.

**References:** [AC1 decline branch; AC2 BR-A-2; Epic-7 DoD context]

### OPS-001: New CronJob mis-deployed / mis-scheduled

**Category:** Operational · **Probability:** 2 · **Impact:** 3 · **Score:** 6 (Medium)

**Description.** `cmd/monthly-invoice` is a NEW dedicated K8s CronJob binary (Architect overrule of the in-process default). If not deployed / mis-scheduled, invoices are never generated — silent until month-end.

**Mitigation:** mirror the `cmd/fx-refresh` deployment pattern (PG pool only, exit-code discipline, backoffLimit); deploy-time verification; a "no invoices generated this period" ops alert. **Detection (P2 / ops):** deployment smoke + a synthetic period run. **Owner:** Dev/Ops.

**References:** [Architect High #1 → Q-SCHEDULER overrule; cmd/fx-refresh H-1 precedent]

### OPS-002: BillingService RPC surface unenumerated

**Category:** Operational · **Probability:** 3 · **Impact:** 2 · **Score:** 6 (Medium)

**Description.** Architect High #2: T0.2 only extends `he.payment.v1.PaymentService`, but the gateway's new public routes proxy to **billing-svc**, whose RPCs (`SetAutoRecharge`, `SavePaymentMethod`/`List`/`Delete`, `ListInvoices`, `GetInvoicePdf`) are never enumerated → the gateway↔billing-svc contract is undefined → mid-implementation rework.

**Mitigation:** enumerate the additive `he.billing.v1.BillingService` RPCs (or rule internal-HTTP explicitly) in T0.2 + §5.2 before Dev starts; billing-svc single-writes `payment_methods`/`invoices`/`balances.auto_recharge_*`. **Detection:** contract test on the gateway→billing-svc boundary. **Owner:** Dev/Architect.

**References:** [Architect High #2]

### SEC-003: Card PAN accidentally stored (PCI §8.4 breach)

**Category:** Security · **Probability:** 1 · **Impact:** 5 · **Score:** 5 (Low)

**Description.** Storing any card PAN would break the SAQ-A boundary (full PCI scope, regulatory). Probability is low because the design is token-only by construction (Stripe SetupIntent → opaque PaymentMethod token), but the impact is critical → kept on the P0 test lane despite a Low score.

**Mitigation:** store ONLY the opaque provider token in `payment_methods.provider_pm_token`; never accept/persist a PAN; display surface is brand/last4 only. **Detection (P0):** no card-PAN ever accepted/stored. **Owner:** Dev.

**References:** [Technical Constraints — PCI §8.4; threat_model #1; security.md §8.4]

### OPS-003: Migration ordinal collision

**Category:** Operational · **Probability:** 2 · **Impact:** 2 · **Score:** 4 (Low)

**Description.** The story defaults `0014`; Architect Medium #1 corrects the true next free ordinal to **0011** (7.4–7.6 were additive, no migration). Blind use of 0014 leaves a gap / collides.

## Compliance and Regulatory Considerations

- **PCI-DSS §8.4 / SAQ-A** — He-API stores ONLY the opaque Stripe PaymentMethod token, NEVER card data. The stored off-session token is a **standing charge authorization** and is treated as a secret-grade value (SEC-002/SEC-003). The boundary is *extended* but the SAQ-A posture is *held*.
- **Billing PII** — monthly invoices contain usage + amounts; owner-only access (SEC-004), private bucket, no public-read.
- **Financial-integrity** — the storm invariant (FIN-001/002) and exactly-once credit (FIN-003) are tested with security-grade rigour, consistent with the 7.1 money-OUT / 7.3 money-IN posture.
