### Test-Level Interpretation for DB-Foundation Stories

Story 1.6 delivers an **infrastructure baseline** (3 Terraform DB modules + 2 migration toolchains + 4 SQL/Bash probe files + 1 Helm CronJob chart + 1 CI workflow + 6-section operator doc + source-tree/README updates). Unlike 1.5 (template-source files rendered into a dogfood service), 1.6's primary artefacts are **configuration-as-code with no runtime in this repo** — the runtime is the staging ACK cluster + Alibaba RDS/Tair/CH managed DBs. The pyramid therefore tilts even harder toward Unit (static text/regex on Terraform HCL + migration SQL + bash scripts + Helm templates + docs), with Integration on the CI gates (`db-migrate-check.yml`, `infra-lint.yml`'s helm-lint job, tflint per module) and E2E on the staging cluster (real `terraform apply`, real `db-doctor.sh` 5-minute SLO, real CronJob → Prometheus metric → alertmanager).

> **Risk profile**: Comprehensive tier triggers `[test-design, risk-profile]` per `core-config.yaml.qa.testDesignThresholds.comprehensive.tasks`. A separate `*risk-profile 1.6` invocation can produce `docs/qa/assessments/1.6-risk-{YYYYMMDD}.md` if Dev or Architect requests it; for this Story security_sensitive=true and Architect Round 2 score is 9.5/10 (1 cosmetic m-6 finding, **now cleaned up in-pass by QA per Architect Round 2 Recommendation #2** — see Change Log + the m-6 cleanup mapping in the Risk Coverage section below). This test-design document therefore doubles as the de-facto risk register: each Architect Round 1 Q-ruling (Q1–Q5), each High-severity Round-1 issue resolution (M-1, M-2), each Round-1 minor (m-1…m-5) and the Round-2 m-6 cleanup is mapped to regression-guard scenarios.

> **Architectural note (infrastructure-as-deliverables)**: Story 1.6's primary artefacts are **configuration files that drive cloud resource creation** (Terraform HCL, Helm templates, Kubernetes manifests, SQL migration files). The deliverable is the **declarative intent**, not a running service in this repo. Most scenarios therefore assert source-text properties; the few "did it actually create the resource" scenarios (E2E section) require manual staging-cluster execution and capture Dev-log evidence with timestamps. This dual treatment is the cheapest possible drift guard for the 14 Epic 2-10 services that will inherit from 1.6's DB foundation.
