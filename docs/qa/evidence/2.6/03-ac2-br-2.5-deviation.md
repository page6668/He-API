# Evidence 03 — AC2 BR-2.5 implementation deviation

**Severity:** MEDIUM
**ACs affected:** AC2 BR-2.5

## What BR-2.5 requires

> "Idempotency check (existing-row lookup) + Redis rate-limit INCR + PG insert MUST be inside one `BEGIN ... COMMIT` transaction with `SELECT ... FOR UPDATE` on a sentinel row to prevent two concurrent requests in the same 100ms window both winning. The Redis INCR-and-EXPIRE step happens INSIDE the transaction (using Redis MULTI/EXEC or Lua script for atomicity); if INCR returns > 1, the PG transaction is rolled back and the handler returns 429."

## What's implemented

`apps/notification-svc/internal/handlers/data_export.go:131-201`

```
1. tx, err := s.DB.Begin(ctx)
2. existing, err := repo.FindCurrentInWindow(...)   // regular SELECT (no FOR UPDATE)
3. if existing: COMMIT + return 200 (idempotent)
4. exportID, _, _ := repo.Insert(ctx, userID)        // new row
5. s.Limiter.CheckAndIncr(...)                       // Redis Lua INCR
6. tx.Commit(ctx)                                    // PG commit BEFORE Kafka publish
7. s.Producer.Publish(...)                           // gdpr.export.requested topic
8. audit.PublishBestEffort(...)                      // audit.event topic
```

`apps/notification-svc/internal/repository/data_export_requests.go:64-77` (FindCurrentInWindow):

```sql
SELECT id, user_id, status, requested_at, ...
FROM he_api.data_export_requests
WHERE user_id = $1
  AND status IN ('pending', 'processing', 'completed')
  AND requested_at > NOW() - $2::interval
ORDER BY requested_at DESC
LIMIT 1
```

— no `FOR UPDATE`, no sentinel row, no `pg_advisory_xact_lock(hashtext(user_id))`.

## Why this matters

The repository code comment (lines 61-63) explicitly claims:
> "Caller MUST hold a transaction with `SELECT ... FOR UPDATE` on a sentinel row (or otherwise serialize concurrent requests for the same user) — see handlers/data_export.go for the canonical wiring."

But the caller does NOT do this. **The repository doc-comment and the handler code disagree.** A future maintainer reading the repository code expects the caller to provide the lock; a future maintainer reading the handler thinks the lock is the repository's job. This is a documentation defect that will cause incident-time confusion.

## Effective behavior

In practice the implementation IS race-safe because:
1. Two concurrent requests both `BEGIN tx` + `SELECT no rows` + `INSERT row A` and `INSERT row B`.
2. Both call `Limiter.CheckAndIncr(userID)`. Redis Lua makes this atomic: count=1 wins, count=2 loses with `ErrRateLimited`.
3. Loser's deferred `tx.Rollback()` removes its inserted row → no orphan.
4. Winner commits, returns 200 with its own export_id.

So Redis Lua provides the race coverage that BR-2.5 wanted PG `FOR UPDATE` to provide. The guarantee is preserved but the mechanism is different.

## Recommended remediation

Choose one:

**Option A** — Implement what the spec says:
```go
// At the top of RequestDataExport, inside the tx:
_, err := tx.Exec(ctx, "SELECT pg_advisory_xact_lock(hashtext($1))", userID)
```
Cheap, lock auto-released at COMMIT/ROLLBACK, no sentinel table needed.

**Option B** — Update the spec + the repository code-comment to reflect the as-built design:
- BR-2.5: "atomicity is provided by the Redis Lua INCR (single-shot), not by PG row-locking; PG rollback is the cleanup for the loser."
- Repository: remove the "caller MUST hold a transaction with SELECT FOR UPDATE" comment.

Option B is honest about the design choice; Option A is defense-in-depth.
