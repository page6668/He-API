## 6. P2a Implementation Summary — password package (Story 2.2 T1.1)

P2a lands the password primitives. The package is dependency-free aside from
`golang.org/x/crypto/bcrypt` and is the single source of truth for bcrypt cost,
HIBP k-anonymity, and length / wipe contracts referenced from every later
handler.

### 6.1 Deliverables

| File | Surface |
|------|---------|
| `apps/auth-svc/internal/password/password.go` | `BcryptCost = 12` (compile-time const). `Hash(pw []byte) ([]byte, error)` — bcrypt cost=12 + `defer wipe(pw)` mutates caller's slice. `Compare(hash, pw []byte) error` — wraps `bcrypt.CompareHashAndPassword`. `ValidateLength(pw []byte) error` — ≥ 10 chars, no class enforcement. `wipe(b []byte)` — package-private zero-fill helper. `ErrPasswordTooShort` exported. |
| `apps/auth-svc/internal/password/hibp.go` | `HIBPClient{BaseURL, HTTPClient}` — injectable for tests. `NewHIBPClient()` — defaults to `https://api.pwnedpasswords.com` + 3 s timeout (TS-CONS-004). `CheckBreached(ctx, pw) error` — sends only `SHA-1(pw)[0:5]` (k-anonymity), fail-closed on transport / 5xx / parse. Returns `ErrPasswordBreached` / `ErrHIBPUnavailable` / nil. `Add-Padding: true` header sent for HIBP response-size defense. |
| `apps/auth-svc/internal/password/password_test.go` | UNIT-001..006 + UNIT-011 + UNIT-012 (8 tests). Memory-wipe asserted by mutating-slice diff. Timing variance test runs 100 match × 100 miss iterations and asserts `|p99_match - p99_miss| < 50ms`. Source-leak scan rejects `fmt.Errorf` / `slog.*` / `errors.New` patterns that interpolate `pw`/`password`/`plaintext`/`cleartext`. |
| `apps/auth-svc/internal/password/hibp_test.go` | UNIT-007..010 (6 tests). httptest stub returns realistic `SUFFIX:COUNT\r\n` body for the breached SHA-1 prefix only. Fail-closed coverage: 500, connection-refused, request timeout, default-timeout-3s. |

### 8.2 Atomicity design choice

QA's UNIT-170 allows either `MULTI/EXEC` or `EVAL`. Implementation picked
Lua-script `EVAL` for two reasons:

1. **Stronger atomicity story.** `MULTI/EXEC` is optimistic (WATCH-based);
   under network partition the EXEC can be aborted. A Lua script runs as a
   single Redis command — no partition between INCR and EXPIRE.
2. **Pod-restart safety.** If auth-svc crashes between `INCR` and `EXPIRE` in
   a pipelined-but-not-bundled command flow, the counter would live forever.
   The Lua script's atomicity removes that failure mode.

miniredis (`gopher-lua` runtime) executes the same script identically to real
Redis, so the unit test exercises the production code path.

### 10.2 Design choices worth noting

- **No SendGrid SDK.** The v3 API is one POST; the official sendgrid-go SDK
  brings in `helpers/mail` builders + transitive deps. A 100-line HTTP
  wrapper is cheaper to maintain, smaller in the distroless image, and
  trivial to mock via `httptest`.
- **Subject as first non-comment line of `.txt`.** Avoids adding a third
  per-locale file just for subjects (10 locales × 3 files would be 30, vs.
  the current 20). Comment-stripping in the parser keeps the `# TODO:
  localize` markers from showing up in the rendered email.
- **Snake_case template vars matching proto.** Templates were PascalCase
  at P1 (`{{.VerificationLink}}`) but the proto `SendEmailRequest.variables`
  uses snake_case keys (`verification_link`) — those have to match for
  `text/template` to resolve the values. Templates realigned to snake_case;
  this is the only path that satisfies the wire contract without a
  case-translation shim.
- **Connect-go error mapping defaults to transient.** An unknown upstream
  error code is treated as retryable rather than permanent — better to
  surface "we couldn't send the email, retry" than to silently drop a
  verification because we couldn't categorize the failure.

convention, so the physical directory `app/[locale]/(auth)/signup/` serves
at `/<locale>/signup/`, not `/<locale>/(auth)/signup/`.

Implementation follows Next.js. The Server Action redirects to
`/<locale>/signup/check-inbox?email=...`. The vitest UNIT-058 test asserts
the Next-idiomatic URL with a comment pointing back to this note. The
Playwright E2E spec (P6 / QA review) will need a one-line update to drop
the parens from its URL regex — flag for QA.

### 17.2 Algorithm-confusion defense (UNIT-115)

The classic CVE-2015-9235 attack: an attacker takes a token, swaps the
header's `alg` from `RS256` to `HS256`, and signs the payload using the
verifier's PUBLIC key as the HMAC secret. A naïve verifier that accepts
whatever `alg` the header declares would accept this — the signature
verifies under HS256 because the attacker used the same "secret" the
verifier holds.

The keyfunc inside `Verify` defends against this by rejecting any
`alg != "RS256"` BEFORE returning the public key. The defense is unit-
tested via a HS256-signed token whose "secret" is exactly the public-key
PEM bytes — the classic attack shape. The first attempt to use
`gojwt.WithValidMethods` short-circuited the keyfunc and returned a
library-level error that was awkward to chain via `errors.Is`; removed
that option so the keyfunc check IS the canonical defense and the
sentinel `ErrInvalidAlgorithm` propagates cleanly.

### 18.2 Timing-parity constraints (BR-3.2 + UNIT-132)

Three branches MUST be statistically indistinguishable from each other
by response time:

1. **Unknown email** — `DummyCompare` consumes the bcrypt budget (~100-200ms
   on cost=12) so the response time tracks the real-compare branches.
2. **Wrong password** — real `password.Compare` runs the same bcrypt work.
3. **5th-wrong-password soft-lock activation** — still returns 401, NOT
   423 (UNIT-139). The 423 response only fires on a subsequent signin
   inside the locked window. Without this, an attacker could binary-search
   the threshold by observing when the response code changes.

### 18.3 Soft-lock counter design (BR-3.3 + BR-4.4)

The signin-failure counter (`auth:signin:failures:{email_hash}`) is
deliberately separate from the per-window rate-limit counter
(`ratelimit:signin:email:{email_hash}`):

- **Rate-limit counter** (5/15min) — coarse-grained protection against
  rapid-fire signin attempts. Resets on the window roll-over.
- **Soft-lock counter** (5/1h) — fine-grained protection that activates
  status=locked + locked_until=NOW+1h on the 5th failure. DEL'd only on
  successful signin or when the soft-lock fires.

Both use the canonical Lua INCR+EXPIRE pattern (same atomicity guarantee
as P2c ratelimit). The soft-lock counter's longer TTL ensures the 5
failures span attacker windows.

### 18.4 Refresh-family tracker (BR-3.9, prep for P4c)

LoginUser writes `auth:refresh:{family_id}` = `refresh_jti` to Redis
with TTL=RefreshTokenTTL (30d). RefreshToken handler (P4c) uses this to
detect reuse — if the jti in a presented refresh token != the stored
value, the family is compromised and revoked.

`jtiFromToken` extracts the jti claim from the just-signed token without
re-verifying the signature (we just signed it). Pure base64-decode +
JSON unmarshal of the payload section.

### 19.2 RefreshToken flow

```
1. Sanity: refresh_token != "" else 401.
2. JWTVerifier.Verify(refresh_token):
     - signature, exp, alg=RS256, aud=he-api all checked.
     - On any error → 401 + audit signin_failure.
     - Defensive: claims.FamilyID == "" (access token) → 401.
3. Pre-sign the new refresh token (so its jti can go into the Lua
   SET argument). Sign new access token AFTER the rotation succeeds.
4. luaRotateRefreshFamily:
     KEYS[1] = auth:refresh:{family_id}
     ARGV[1] = presented_jti, ARGV[2] = new_jti, ARGV[3] = TTL
     Cases:
       "not_found"   → family was revoked / never tracked → 401 + audit
                       refresh.family_revoked
       "compromised" → stored != presented → DEL family + 401 +
                       audit refresh.reuse_detected
       "ok"          → DEL + SET new jti (1 round-trip) → proceed
5. Sign new access token, return RefreshTokenResponse{access, refresh,
   900s, 2592000s}. Audit signin_success with refresh.rotated.
```

### 19.3 Why Lua is the right tool here

Two reasons:

1. **No GET+SET race.** Between `GET stored_jti` and `DEL old + SET new`
   on the application side, another concurrent refresh could rotate the
   family. Without the Lua wrapper, two simultaneous refreshes from the
   same browser (e.g., fetch dedupe failure) could leave the tracker in
   a half-state. Lua serializes server-side.
2. **Reuse detection is a single atomic transition.** "Reuse detected →
   DEL family" can't be safely implemented as separate GET + DEL because
   the legitimate current jti might rotate between the two. Lua collapses
   the whole decision into one Redis command.

### 19.4 401 vs distinguished response

All three RefreshToken failure paths (expired / invalid-sig / wrong-alg /
family-revoked / reuse-detected) surface as `401_invalid_credentials`.
The audit log records the discriminator (`refresh.reuse_detected` vs
`refresh.family_revoked` vs the verifier's error chain) so ops can see
why; the client just knows to re-sign-in. This matches the AC3 error-
handling table — refresh failures collapse into "your session is dead,
log in again" for the user.
